Restablecimiento de contraseña

⚙️ Intermedio 11 min Autenticación y Autorización Módulo 2 · Registro y Login

La recuperación también se defiende

El flujo «olvidé mi contraseña» es una puerta trasera si se implementa mal. Dos errores clásicos: responder siempre «si el email existe te enviamos un enlace» pero con distintos tiempos, o usar el hash de la contraseña como token. La regla de oro: el token de reset es un secreto aleatorio de un solo uso, con expiración, independiente del hash.

Generar y guardar el token

En base de datos solo se guarda el hash del token (lo mismo que con contraseñas): una filtración de una tabla no convierte los tokens en reseteos útiles.

Consumir el token

Buenas prácticas extra

  • Limita intentos de reset por email e IP (rate limiting).
  • Pide confirmación de la nueva contraseña en el frontend, no en el backend.
  • Tras un reset exitoso, revoca las sesiones activas del usuario.
  • El enlace debe ser GET /reset?t=TOKEN en la UI; el cambio de contraseña, un POST con el token.

Ejercicio

  1. Implementa la tabla reset_tokens con las columnas: id, usuario_id, token_hash, expira_en, usado, creado_en.
  2. Prueba el flujo completo y consumiendo el token dos veces (la segunda debe fallar).
  3. Explica por qué guardamos token_hash y no el token en claro.

Resumen

  • Token aleatorio criptográfico, expiración y un solo uso.
  • En BD solo se guarda el hash del token.
  • Respuestas idénticas evitan enumerar usuarios.
  • Tras el cambio, revoca las sesiones anteriores.
