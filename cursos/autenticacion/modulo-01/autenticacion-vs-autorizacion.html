Autenticación vs Autorización

⚙️ Intermedio 10 min Autenticación y Autorización Módulo 1 · Fundamentos

Introducción

Cuando entras a un edificio de oficinas te piden una credencial en recepción: eso verifica quién eres. Aunque ya estés identificado, no puedes entrar a cualquier sala: la de servidores y la dirección tienen llaves que solo algunos tienen. Ese segundo paso decide qué puedes hacer. En el mundo del backend esos dos momentos son la autenticación y la autorización, y aunque suenan parecido, son responsabilidades distintas que se implementan en momentos distintos del ciclo de una petición.

Confundirlas es una de las causas más comunes de vulnerabilidades: un sistema que verifica el login pero no comprueba permisos en cada ruta permite que un usuario común lea datos de administrador. Este módulo entrena tu ojo para separar ambos problemas desde el diseño.

Las dos preguntas

  • Autenticación: responde a «¿quién eres?». Valida una credencial (contraseña, código TOTP, clave pública) contra una fuente de verdad: sistema de usuarios, directorio LDAP o proveedor externo.
  • Autorización: responde a «¿qué tienes permitido hacer?». Se decide tras la autenticación, usando identidad, roles y permisos.

La autorización nunca debe depender de datos que el cliente envíe (como un parámetro ?rol=admin): debe computarse en el servidor a partir del usuario autenticado.

Ejemplos en una API real

Imagina una app de una clínica: POST /api/login autentica (verifica credenciales), mientras que GET /api/pacientes autoriza (solo doctores). Un paciente tiene sesión activa, pero no el permiso para listar pacientes ajenos.

Los códigos 401 y 403

HTTP te ayuda a comunicar cada resultado de forma precisa:

  • 401 Unauthorized: faltan credenciales o son inválidas. El servidor no sabe quién eres. Se usa en el momento de autenticar.
  • 403 Forbidden: ya estás autenticado, pero la acción no está permitida para tu perfil. Se usa en el momento de autorizar.

Muchas APIs devuelven 401 para ambos casos para no filtrar información; pero en proyectos internos ser exacto ayuda a depurar. Lo importante es no devolver 200 con datos que el usuario no debía ver.

Errores típicos

  • Confiar en el frontend para ocultar botones en lugar de proteger rutas en el servidor.
  • Autorizar solo en el login y olvidar comprobar permisos en cada endpoint.
  • Leer el rol desde el request en lugar de desde la sesión o token firmado.
  • Devolver 200 con un {"datos": []} cuando el usuario no debería saber que el recurso existe.

Ejercicio

  1. Enumera 5 acciones de una app de tu elección y clasifícalas en «requiere autenticación» y «requiere además autorización».
  2. Escribe un endpoint GET /api/perfil/{id} en PHP que devuelva 401 sin sesión, 403 si el perfil no es propio ni de un admin autorizado, y 200 en el resto de casos.
  3. Explica en una línea por qué «ocultar el botón» no es una medida de autorización.

Resumen

  • Autenticación verifica identidad; autorización verifica permisos.
  • La autorización se decide en el servidor, nunca desde datos del cliente.
  • 401 para identidad fallida; 403 para permiso denegado.
  • Comprueba permisos en cada ruta, no solo en el login.
