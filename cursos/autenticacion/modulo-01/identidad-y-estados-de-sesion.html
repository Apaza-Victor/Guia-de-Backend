Identidad y estados de sesión

⚙️ Intermedio 9 min Autenticación y Autorización Módulo 1 · Fundamentos

El problema del estado

El protocolo HTTP no recuerda nada: cada petición llega sin contexto, como si el servidor conociera al visitante por primera vez. Si un usuario inicia sesión y en la siguiente petición el servidor ya no lo reconoce, el login no sirve de nada. Por eso la autenticación construye estado sobre un protocolo sin estado.

La identidad es el conjunto de atributos que distingue a un usuario (id, email, nombre, rol). La sesión es el período durante el cual el servidor recuerda «esta petición pertenece a este usuario» después de que ya se autenticó.

Dos familias de estado

  • Sesiones del lado servidor: el estado vive en el servidor (memoria, base de datos o Redis). El cliente solo guarda un identificador opaco de sesión en una cookie.
  • Tokens stateless: el estado viaja dentro de un token firmado (JWT) que el propio servidor puede verificar sin mirar una base de datos.

Ambas familias son válidas; se eligen según la arquitectura. Este módulo y los siguientes las estudian por separado para que puedas compararlas con criterio.

Ciclo de vida de una sesión

El ciclo completo es: inicio → login → uso → expiración/cierre. Controlar cada transición es el trabajo de un buen backend.

Los estados de una sesión

  • Anónima: existe una sesión técnica pero sin identidad asociada.
  • Autenticada: la sesión contiene la identidad del usuario verificada.
  • Expirada: pasó el tiempo de inactividad o la vigencia máxima; el servidor la invalida.
  • Revocada: el usuario cerró sesión o un administrador la invalidó, incluso antes de expirar.

Reglas mínimas

  • Nunca guardes la contraseña en la sesión; guarda el user_id y datos estables.
  • Establece tiempos de expiración y de inactividad separados.
  • Regenera el identificador de sesión tras el login para evitar session fixation.
  • Si cambia la contraseña, invalida las sesiones anteriores.

Ejercicio

  1. Dibuja el diagrama del ciclo de vida de una sesión con sus cuatro estados.
  2. Modifica el ejemplo para que, si last_seen supera 30 minutos, la sesión se destruya.
  3. Explica por qué guardar el rol en la sesión nadie más que el servidor debe poder cambiarlo.

Resumen

  • HTTP no tiene estado; la sesión lo añade.
  • Hay sesiones de servidor y tokens stateless.
  • La identidad se fija tras el login y se consulta en cada petición.
  • Anónima, autenticada, expirada y revocada son los estados posibles.
