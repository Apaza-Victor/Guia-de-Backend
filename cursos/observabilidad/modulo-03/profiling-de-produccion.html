Profiling y correlación

🚀 Avanzado 10 min Observabilidad Backend Módulo 3 · Alertas y dashboards

El profiling como cuarto pilar

Las trazas te dicen dónde se gasta el tiempo; el profiling te dice en qué código. Un perfil de CPU o de memoria es una fotografía del stack de llamadas del proceso: qué funciones se ejecutan y cuánto tiempo (o memoria, o locks) consumen.

Los flame graphs son su visualización clásica: cada barra es una función, su ancho la proporción de tiempo. El diagnóstico más típico en backend: el servicio no se cae, pero gasta 70 % de la CPU en serializar JSON de un campo que nadie lee.

Herramientas según el lenguaje

La idea es la misma: muestrear el stack en marcha (entre 10 y 1000 veces por segundo) durante una ventana de tiempo, sin detener el servicio. La sobrecarga es pequeña y acotada a la ventana.

Cuándo perfilas: cuando las trazas ya apuntaron a una función/operación concreta. El profiling responde el «¿por qué este span tarda tanto?». Perfilar a ciegas sin la traza que acote el problema es barrido de bala.

Profiling continuo

Versiones modernas (Parca, Pyroscope, Datadog, Elastic) recolectan perfiles de forma continua como si fueran métricas y los asocian por servicio y release. Ventajas: ves regresiones (un release que aumentó 20 % la CPU hasta notarlo) y correlacionas perfiles con el resto de señales por el mismo sentido temporal. Coste: algo de CPU por proceso muestreado — se configura con porcentaje objetivo.

Semconv: que todos hablen igual

La correlación entre señales exige que los nombres de los atributos sean consistentes. Las convenciones semánticas (SemConv) de OpenTelemetry definen cómo llamar a http, db, red, cloud, etc. Este es el motivo por el que puedes mirar un dashboard de Grafana que importaste y entender cada serie sin preguntar al que la creó:

Cuanto más uses los nombres estándar, mejor se integran Prometheus, Grafana, ELK y Jaeger entre sí — y migrar a otra herramienta no rompe tus dashboards: tus consultas y atributos sobreviven porque el vocabulario común.

El flujo completo de una incidencia

Pongamos todas las piezas juntas: tu métrica p99 de checkout salta de 200 ms a 3 s. La investigación de 360°:

  1. Métrica: el p99 subió exactamente a las 09:00 (dashboard RED).
  2. Traza: abres las trazas de esa ruta y ves que el span SELECT stock pasó de 50 ms a 2,5 s.
  3. Log: filtras por trace_id y el log dice «lock_time_ms=2400» en esa consulta.
  4. Perfil: el perfil del QPS de esa ruta muestra el driver de BD acumulando tiempo en wait_for_connection: el pool está saturado.
  5. Decisión: subir el pool + añadir índice = causa raíz atacada con datos, no con corazonadas.

Reglas para no perderse

  • Métricas prima la alerta: el objetivo del dashboard es detectar. Trazas el dónde; logs el qué; perfiles el por qué en el código.
  • Usa siempre el mismo trace_id en las tres señales: es la llave que une los sistemas.
  • SemConv por defecto; inventa nombres de atributos solo cuando no exista el estándar.
  • Perfila con ventana corta y dirigida por una traza, no como actividad del día a día.

Ejercicio

  1. Toma una ruta lenta de tu API y ejecuta un perfil de CPU de 30 s sobre el proceso (pprof, py-spy o async-profiler).
  2. Identifica la función más cara del perfil y compárala con el span que más tarda en una traza de esa ruta.
  3. Reescribe los atributos de tus logs y spans usando semconv para dejar de inventar nombres.

Resumen

  • El profiling muestra en qué funciones se gasta CPU, memoria o tiempo de bloqueo.
  • Herramientas: pprof (Go), py-spy (Python), async-profiler (JVM); o profiling continuo de plataforma.
  • SemConv estandariza nombres de atributos para que las señales se integren.
  • Métrica → traza → log → perfil es un recorrido completo: cada señal cierra una parte del problema.
