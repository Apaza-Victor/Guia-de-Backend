OpenTelemetry aplicado a tu API

🔥 Avanzado 15 min Observabilidad Módulo 5 · Trazas y distributed tracing

Introducción

OpenTelemetry (OTel) se convirtió en el estándar de la observabilidad: una API única para generar logs, métricas y trazas y exportarlas a Prometheus, Jaeger o tu proveedor favorito. Instrumentar una vez no significa atarte a una herramienta.

Esta lección monta el ciclo completo sobre una API: SDK configurado, recursos anotados, exportador en marcha y trazas visibles en un backend. Con eso, cada servicio nuevo hereda la observabilidad.

Definición

OpenTelemetry es un framework open source que estandariza la instrumentación: genera trazas, métricas y logs con una API y SDK común y los exporta a múltiples backends mediante exporters.

Por qué importa. Resuelve el vendor-lock: no reescribes la instrumentación al cambiar de Jaeger a Tempo o de Prometheus a Datadog; cambias el endpoint del exporter.

Cuándo usarlo. Adóptalo como estándar del equipo desde el primer servicio: la instrumentación automática cubre frameworks HTTP, BDs y clientes, y los spans manuales completan tu dominio.

Conceptos clave

  • API y SDK: la API define las operaciones y el SDK las conecta al exporter.
  • Instrumentación automática: paquetes que generan spans para HTTP, SQL, Redis.
  • Resources: atributos del proceso (service.name, version, host) que enriquecen todo.
  • Exporters: envían las señales a Jaeger, Tempo, OTEL collector, Prometheus.
  • OTLP: el protocolo estándar de transporte de OpenTelemetry.

Ejemplo real

Un equipo estandarizó OTel en sus 12 microservicios: la instrumentación automática evitó reescribir código y los spans manuales documentan el dominio. Hoy exportan a Grafana Tempo y cambiaron de exporter sin tocar una línea de los servicios.

  • Arranca con la instrumentación automática y suma spans de dominio después.
  • Define recursos comunes (service.name, version) para filtrar por versión.
  • Centraliza la configuración en un OTel Collector para no repetir exporters.

El colector central gestiona transformaciones y buffering: cada servicio solo conoce un endpoint.

Explicación

  • La API de OTel genera las señales; el SDK las procesa y el exporter las manda.
  • La instrumentación automática cubre el 80% de las señales sin tocar código.
  • Los resources etiquetan todos los spans/métricas con contexto del servicio.
  • El collector centraliza transporte, buffer y múltiples destinos.
  • El protocolo OTLP permite enviar trazas, métricas y logs con el mismo pipeline.

Errores comunes

  • Configurar un recurso distinto por entorno: filtras mal y pierdes contexto.
  • Enviar cada servicio a exporters directos: duplicas config y atras la centralización.
  • Olvidar el buffer del BatchSpanProcessor: estresas el backend con cada span.

Buenas prácticas

  • Emplea env vars para el endpoint del collector: cambias de destino sin recompilar.
  • Estandariza service.name: la variante de 'nombre-fácil' rompe los filtros.
  • Empieza por el módulo de Flask/Express y valida una traza antes de ampliar.

Ejercicio

  1. Configura el SDK de OTel en una API y expórtala a Jaeger.
  2. Añade un span manual de una operación de dominio con atributos.
  3. Levanta un OTel Collector y enruta un mismo flujo a dos backends.

Resumen

  • OpenTelemetry estandariza la instrumentación con un único SDK y exporters.
  • La instrumentación automática más spans de dominio cubre el servicio completo.
  • El OTel Collector centraliza el transporte y permite cambiar de backend sin tocar el código.
