Instrumentando tu aplicación con client libraries

🔥 Avanzado 14 min Observabilidad Módulo 4 · Métricas y servidores de métricas

Introducción

Las métricas del servidor dicen cuánto consume el nodo, pero no qué hace tu lógica. Para saber qué pasa dentro del proceso hay que instrumentar: añadir contadores, histogramas y gauges en los puntos que importan.

Esta lección muestra cómo instrumentar una API con una client library (prometheus_client, opentelemetry) siguiendo patrones limpios: middleware para HTTP, métricas por operación y carencia de etiquetas peligrosas.

Definición

La instrumentación con client libraries añade puntos de medición en el código de la aplicación: middleware, repositorios y servicios exponen métricas en /metrics que el servidor recoge.

Por qué importa. Solo el código sabe la latencia de cada operación, el encuentro de errores por tipo o el tamaño de lo que devuelve: es la capa de observabilidad que más valor da por construcción.

Cuándo usarlo. Instrumenta desde el primer endpoint y con middleware centralizado; quiere decir: no esparzas métricas sueltas sin vistas, haz que la librería lo cubra para toda la app.

Conceptos clave

  • Middleware de métricas: captura request, status y latencia de cada ruta automáticamente.
  • Histograma por operación: latencia de cada método de tu dominio (buscar, crear, pagar).
  • Contadores de negocio: pedidos creados, importes totales: las que hablan de producto.
  • Etiquetas seguras: path y status como labels, nunca ids de entidades.
  • Exposición en /metrics: el endpoint que Prometheus scrapea de forma estandarizada.

Ejemplo real

Un equipo instrumentó su API con middleware: al día siguiente encontraron que el endpoint de búsqueda tenía p95 de 2s solo cuando el query llegaba vacío. La métrica por operación (latencia de repo.buscar) apuntó a la consulta mal construida que solo saltaba en ese caso.

  • Usa middleware para HTTP y métricas por operación para la lógica de dominio.
  • Cuenta los resultados de cada flujo (ok, rechazo, timeout) para ver tasas.
  • Nunca pongas el id de una entidad como etiqueta: usa el tipo o el nombre.

La instrumentación de OpenTelemetry cubre lo mismo y más, con métricas y trazas de una sola API.

Explicación

  • El middleware concentra la instrumentación HTTP en un solo punto, evitando duplicados.
  • Las métricas por operación de dominio señalan qué capa concreta se degrada.
  • Los contadores por resultado permiten tasas (cuántos de cada 100 pagos fallan).
  • Las etiquetas correctas hacen las series útiles sin reventar la cardinalidad.
  • El endpoint /metrics estándar permite al servidor descubrir el servicio sin esfuerzo.

Errores comunes

  • Instrumentar cada ruta a mano: duplicados, olvidos y cardinidad dispar.
  • Etiquetas con ids de usuario o pedido: miles de series al mínimo volumen.
  • Poner la instrumentación después de los bugs: debería ser parte del contrato del endpoint.

Buenas prácticas

  • Crea un middleware o decorador de métricas y úsalo en toda la app.
  • Añade una métrica de negocio por flujo ejecutable (crear, pagar, enviar).
  • Prueba con un endpoint de desarrollo que el /metrics responda antes de promulgar.

Ejercicio

  1. Instrumenta una ruta con middleware y observa tus series en /metrics.
  2. Añade una métrica por operación de dominio con su contador de resultado.
  3. Comprueba la cardinalidad de series de tu servicio y corrige una etiqueta peligrosa.

Resumen

  • La instrumentación con client libraries mide la lógica desde dentro del proceso.
  • El middleware centraliza HTTP; las operaciones de dominio localizan el cuello.
  • Etiquetas seguras y métricas de negocio completan un servicio observable.
