Las métricas doradas y los enfoques RED y USE

🔥 Avanzado 12 min Observabilidad Módulo 4 · Métricas y servidores de métricas

Introducción

Google popularizó las 'four golden signals': latencia, tráfico, errores y saturación. Si tu sistema responde esas cuatro preguntas en un incidente, ya tienes el 80% de la observabilidad operativa.

RED y USE son dos implementaciones concretas: RED para la perspectiva de la petición (Rate, Errors, Duration) y USE para la de los recursos (Utilization, Saturation, Errors). Juntas cubren el sistema entero.

Definición

Las cuatro señales doradas describen la experiencia y la salud: latencia (tiempo de cada petición), tráfico (cantidad de trabajo), errores (fallos sobre el total) y saturación (cercanía al límite de un recurso). RED y USE son dos plantillas para aplicarlas.

Por qué importa. Son el mínimo que un dashboard de incidentes debe responder: ante una alerta, en segundos sabes si sufre la puerta de entrada, la salida o un recurso interno.

Cuándo usarlo. Aplícalas en todo servicio, en cada zona de la infraestructura (proxy, app, BD, cola) y combina RED (peticiones) con USE (recursos) para no quedarte con medir solo la mitad.

Conceptos clave

  • Four golden signals: latencia, tráfico, errores y saturación.
  • RED: Rate (tráfico), Errors (tasa), Duration (latencia) para servicios de petición-respuesta.
  • USE: Utilization (uso), Saturation (saturación), Errors (errores) para recursos.
  • Cada capa se evalúa con su propio par RED/USE: proxy, servicio, BD, cola.
  • Un incidente se explica cruzando dos señales: p99 alto + saturación alta = recurso ahogado.

Ejemplo básico

El cuadro RED de un servicio API: velocidad, errores y duración en tres queries.

Ejemplo intermedio

El cuadro USE de un recurso, por ejemplo la base de datos: uso, saturación y errores.

Ejemplo real

Durante un pico de campaña, el dashboard RED mostró p99 alto y el USE de la BD mostró conexiones al 95% y waits crecientes. Cruzando las dos señales, el equipo supo en minutos que era saturación de conexiones, no un bug de código, y subió el pool.

  • Pon RED y USE en el mismo dashboard para cruzar petición y recurso.
  • Cada capa (proxy, servicio, BD, cola) tiene su propio RED/USE.
  • Realiza la correlación: p99 alto con saturación alta es receta de límite de recurso.

El tráfico alto sin errores ni saturación alta es carga sana; el p99 alto sin saturación apunta a lógica de código u otra dependencia.

Explicación

  • La latencia contesta '¿cuánto cuesta?'; el tráfico, '¿cuánto trabajo?'; errores, '¿cuánto falla?'; saturación, '¿cuánto le queda?'. Con eso se explica casi cualquier incidente.
  • RED se aplica a servicios de petición-respuesta; para colas o trabajos en batch se adapta la duración a tiempo de procesamiento.
  • USE se aplica a recursos: cada uno tiene su medida de utilización y saturación.
  • Las señales se cruzan: una alerta sola cuenta media historia.
  • Es el vocabulario común que permite a dos personas del equipo hablar del mismo incidente en segundos.

Errores comunes

  • Medir solo latencia media: esconde la cola lenta que es el verdadero dolor.
  • Aplicar RED a recursos y USE a peticiones: los marcos no son intercambiables.
  • Vigilar el servicio sin su BD ni su proxy: el cuello se queda fuera del cuadro.

Buenas prácticas

  • Construye un dashboard RED/USE compartido por equipo para no duplicar paneles.
  • Añade las señales al runbook: cada incidente empieza mirando las mismas cuatro.
  • Revisa trimestralmente los umbrales para que sigan reflejando tu realidad.

Ejercicio

  1. Diseña el dashboard RED de tu servicio principal con sus tres queries.
  2. Construye el USE de la base de datos que más usas.
  3. Cruza dos señales para explicar el último incidente real que recuerdes.

Resumen

  • Las cuatro señales doradas describen la latencia, el tráfico, los errores y la saturación.
  • RED mira la petición; USE mira el recurso.
  • Cruzando las señales se explica un incidente en segundos.
