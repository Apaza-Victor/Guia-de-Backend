Logs estructurados

🚀 Avanzado 9 min Observabilidad Backend Módulo 1 · Fundamentos

El problema del log en texto plano

Un log clásico se escribía a mano, sin formato fijo:

2026-02-18 09:31:02 ERROR Fallo al procesar compra co_93812 por usuario 4421 proveedor mercadopago red timeout

Sirve de poco porque no puedes consultarlo de forma fiable: el campo «usuario» no está en una posición estable, el formato cambia con cada mensaje y hacer búsquedas ad hoc exige inventar expresiones para cada patrón. Un log estructurado es máquina-legible: un objeto JSON con campos estables que puedes filtrar con una consulta.

Prueba de calidad: si no puedes hacer jq select(.level == "error") sobre tu log, aún no son logs estructurados.

Qué campos debe tener

  • ts: timestamp en ISO 8601 con zona horaria.
  • level: nivel del mensaje (trace, debug, info, warn, error, fatal).
  • msg: mensaje legible; los datos variables van como campos, no interpolados.
  • service y version: qué servicio y qué release lo produjo.
  • trace_id / span_id: correlación con la petición completa.
  • Contexto de negocio: user_id, tenant, order_id, checkout.id, product.sku…

Los campos de contexto son los que permiten responder «¿qué tenían en común los fallos?» agrupando por cuesa cautidad que sí importa, sin modificar mensajes ni instrumentación.

Niveles y cuándo usarlos

trace / debug
detalle de diagnóstico que casi siempre está apagado en producción.
info
eventos de flujo normal: request atendida, trabajo procesado, compra creada.
warn
algo funciona pero degradado o con riesgo: reintento, timeout puntual, stock bajo.
error
un fallo que afecta a un usuario o a una operación: exception capturada, cobro rechazado.
fatal
el proceso no puede continuar: fallo de arranque, out-of-memory, configuración inválida.

Logs de acceso

El log de acceso (quién pidió qué, con qué código) es la base del debugging HTTP. No lo dejes en el formato del servidor web: transfórmalo a JSON para poder consultar por ruta, status y duración.

Ejercicio

  1. Convierte tu logger actual a JSON: si usas Python, implementa el JsonFormatter; si usas Node, integra pino.
  2. Mete el trace_id de cada request en el logger hijo (child) para que todas las líneas lo lleven.
  3. Escribe 3 consultas que ahora puedes hacer y antes no: por ejemplo, «errores 5xx por tenant en la última hora».

Resumen

  • Los logs estructurados son objetos JSON consultables, no frases sueltas.
  • Los campos obligatorios: ts, level, msg, service, trace_id y contexto de negocio.
  • Los valores variables van como campos, nunca interpolados en el mensaje.
  • El mismo trace_id en todos los logs de una petición permite reconstruir todo el recorrido.
