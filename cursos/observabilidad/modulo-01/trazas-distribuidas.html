Trazas distribuidas

🚀 Avanzado 9 min Observabilidad Backend Módulo 1 · Fundamentos

El problema que resuelven

Cuando una petición toca la API, un servicio de búsqueda, una base de datos y una cola, cada componente logra su propio tiempo. La suma de «tiempo medio» no te dice dónde se esperó de verdad. Las trazas distribuidas reconstruyen el camino completo de una petición: qué llamó a quién, en qué orden, en cuánto tiempo y dónde falló.

Los dos conceptos base:

Span
una unidad de trabajo con nombre, tiempo de inicio, duración, atributos y su padre. Un span puede ser una llamada HTTP, una consulta SQL, un publish a una cola.
Trace
el árbol de spans que comparte un traceId: la petición completa de extremo a extremo.

Anatomía de una traza

Observa el árbol: cada span tiene un parentSpanId. El span raíz (root) no tiene padre. Los hijos comparten el mismo traceId.

La petición tardó 850 ms en total. El span «SELECT stock» tardó 640 de esos 850. Esa es la diferencia entre ver el porcentaje total y ver dónde está el cuello de botella: la consulta a inventor toma tres cuartas partes del tiempo.

Propagación de contexto

Cuando la API llama a inventario por HTTP, el cliente inyecta ese header. Inventario lo lee, crea su span hijo, responde, y el contexto vuelve al padre. Si usas colas o Kafka, la propagación se hace en las cabeceras del mensaje. Esto ya lo resuelve la instrumentación automática de OpenTelemetry, pero es imprescindible entenderlo para las integraciones manuales.

Muestreo

Guardar la traza de cada petición es caro. Lo habitual es el muestreo: un porcentaje del tráfico se tracea (5 %–10 % es un punto de partida común). Eso alcanza para ver distribuciones y errores recurrentes; cuando una petición concreta falla, la correlación por traceId te sigue dando el detalle del caso.

En la práctica: muestrea menos (1–5 %) el tráfico normal, y muestrea el 100 % de las peticiones con error o de más de N ms. Esa estrategia doble te da el mapa y la evidencia del incidente.

Para qué usarlas

  • Encontrar latencia: ver el span que más tarda en el árbol.
  • Descubrir dependencias: qué servicio telefonea a quién (dependencies graph).
  • Investigar errores: traceId de un fallo → logs de todos los servicios.
  • Validar hipótesis: ¿la base de datos se satura? Ordena las trazas por duración del span de BD.

Ejercicio

  1. Dibuja el árbol de spans de una petición que cruce API → BD → cola de notificaciones.
  2. Escribe el header traceparent que enviaría tu servicio al llamar a otro.
  3. Busca en tu proyecto una operación que hoy tarda «mucho» y describe cómo la dividirías en 3 spans para localizar el costo.

Resumen

  • Una traza es un árbol de spans con un traceId común y relaciones parentSpanId.
  • El contexto se propaga entre servicios con headers (W3C traceparent) o cabeceras de mensajes.
  • OpenTelemetry instrumenta lo común automáticamente y permite spans manuales.
  • El muestreo equilibra el coste de almacenamiento con la utilidad diagnóstica.
