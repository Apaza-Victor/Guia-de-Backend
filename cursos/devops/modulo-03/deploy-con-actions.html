Despliegue con Actions

🔥 Avanzado 13 min DevOps para Backend Módulo 3 · GitHub Actions

Introducción

Una vez que tu CI da verde, el siguiente paso del ciclo es el despliegue: mover el artefacto ya probado a producción. Aquí verás cómo GitHub Actions puede conectar por SSH a un VPS, copiar el código con rsync y reiniciar el servicio con systemctl.

Preparativos en el servidor

Antes del pipeline necesitas credenciales SSH para el runner. Lo más fácil: crear un usuario sin shell para despliegues y una llave SSH dedicada (nunca tu llave personal, nunca tu contraseña).

Después, en GitHub (Settings → Secrets and variables → Actions) guarda la llave privada como SSH_PRIVATE_KEY, y el host/usuario como variables o secrets.

Seguridad en el deploy

  • La llave privada vive solo como secret, nunca en el repo.
  • Restringe acciones de despliegue a main y hazlas manuales con workflow_dispatch cuando quieras mayor control.
  • Usa un usuario dedicado y revoca su llave si el repositorio deja de usarse.

Ejercicio

  1. Prepara un usuario deployer y la llave SSH en tu servidor de pruebas.
  2. Escribe un workflow que sincronice el código y reinicie el servicio con systemctl.
  3. Añade un healthcheck que falle a propósito (renombra el endpoint) y verifica que el job se marque en rojo.

Resumen

  • El despliegue por SSH usa una llave dedicada almacenada como secret.
  • rsync copia los cambios y systemctl restart activa el servicio.
  • El pipeline termina con un healthcheck que valida el resultado.
  • Cualquier secret en el repo es una vulnerabilidad: todo a GitHub Secrets.
