Rollbacks y reversiones

🔥 Avanzado 15 min DevOps para Backend Módulo 5 · Despliegue Continuo

El plan de escape

Toda estrategia de despliegue debe responder una pregunta: ¿cómo vuelvo atrás si esto explota? Un rollback rápido reduce minutos de caída a segundos. Sin plan de escape, un fallo menor se convierte en incidente de horas.

Rollback de código vs rollback de despliegue

  • Git revert: crea un commit que deshace el cambio del código y lo despliega. Sirve cuando la versión vieja del código ya no es compatible con la base de datos actual.
  • Rollback de despliegue: vuelve a publicar la versión anterior tal cual (misma imagen o mismo tag). Es lo más rápido y no toca el historial de git.

Regla práctica: para un problema puntual y urgente usa rollback de despliegue (minutos); cuando el código nuevo es el problema estructural, haz git revert y despliega el revert.

Rollback de despliegue en la práctica

El punto clave: nunca borres la versión anterior. Mantén al menos dos versiones disponibles con un symlink current o con etiquetas de imagen inmutables.

El problema de la base de datos

Verdad incómoda: si la versión nueva ejecutó una migración destructiva (borrar columna, renombrar tabla), volver al código viejo no basta: el código anterior esperará una estructura que ya no existe.

  • Las migraciones deben ser aditivas: agregar columnas/índices, nunca quitar en el mismo deploy.
  • Separar deploy de código y migración de datos. Primero migra, después despliega, y haz que el código antiguo tolerante ignore lo nuevo.
  • Patrón "expand and contract": fase 1 agregar (expand), fase 2 limpiar (contract) una release después.

Automatizar el rollback

El rollback no debería depender de alguien recordando pasos. Ideas:

  • Workflow de GitHub Actions workflow_dispatch con el tag a restaurar como parámetro.
  • Script rollback.sh idempotente en el servidor.
  • Rollback automático basado en alertas: si el healthcheck falla a los 2 minutos, restaura la versión previa.

La automatización reduce el MTTR (tiempo medio de recuperación) y eso se nota en el SLA.

Qué hacer después del rollback

  • Congela nuevos deploys mientras se investiga.
  • Aísla la causa: ¿bug, configuración, datos, dependencia?
  • Agrega una prueba o test de regresión que hubiera detectado el problema.
  • Documenta el incidente en un postmortem breve: qué pasó, cómo se revirtió, qué cambia.

Ejercicio

  1. Simula un fallo: despliega una versión rota en tu servidor de pruebas y ejecuta un rollback con symlink o tag anterior.
  2. Escribe un script rollback.sh que lo repita con un solo comando.
  3. Revisa tus migraciones: ¿alguna es destructiva? Reescríbela con el patrón expand and contract.

Resumen

  • El rollback de despliegue es lo más rápido; el git revert corrige el código a largo plazo.
  • Mantén versiones anteriores disponibles con symlinks o tags inmutables.
  • Las migraciones destructivas rompen los rollbacks: usa expand and contract.
  • Automatizar el rollback y documentar el incidente completa el ciclo.
