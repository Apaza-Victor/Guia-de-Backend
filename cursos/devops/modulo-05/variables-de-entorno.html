Variables de entorno en producción

🔥 Avanzado 10 min DevOps para Backend Módulo 5 · Despliegue Continuo

Por qué configuración ≠ código

Una API debe correr igual en dev, staging y producción cambiando solo su configuración. Las variables de entorno logran esto: valores inyectados desde fuera del proceso, sin tocar el código ni the repo. Así la misma imagen o el mismo commit se despliega en cualquier entorno con seguridad.

Qué se considera variable de entorno

  • No secretas: puerto, nivel de log, URL pública, feature flags.
  • Secretas: claves de base de datos, tokens de APIs, llaves de firma JWT.

La regla: si el valor puede cambiar entre entornos → variable. Si es secreto → nunca en el repo, siempre por un gestor seguro.

El patrón .env

En desarrollo, un archivo .env con valores locales hace la vida fácil. En producción el archivo se genera en el servidor y nunca se sube al repositorio.

Gestión segura de secretos

  • Nunca subir .env, nunca loguear variables, nunca imprimir su valor en el healthcheck.
  • Rotar los secretos periódicamente y al sospechar filtración.
  • En equipos grandes usa un gestor: GitHub Secrets, AWS Secrets Manager, Vault, o al menos --env-file con permisos restrictivos.
  • Usa valores de respaldo por defecto solo para desarrollo; en producción exige la variable y falla rápido si falta.

Ejercicio

  1. Crea un .env.example para tu API con al menos 4 variables y comitéalo.
  2. Asegúrate de que tu .env real está en .gitignore y verifícalo con git status.
  3. Configura la API con EnvironmentFile o --env-file en tu servidor de pruebas y confirma que arranca.

Resumen

  • La configuración viaja por variables de entorno, no por el código.
  • .env.example documenta; .env no se commitea.
  • En producción las variables se inyectan con systemd, Docker u orquestadores.
  • Los secretos viven fuera del repo y se gestionan con herramientas dedicadas.
