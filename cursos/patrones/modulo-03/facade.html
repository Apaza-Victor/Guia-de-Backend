Facade

🔥 Avanzado 8 min Patrones de Diseño Módulo 3 · Estructurales

Introducción

El Facade ofrece una cara simple frente a un subsistema con muchas partes. No esconde el subsistema (sigue accesible si hay que ir fino), pero la operación común se vuelve una llamada.

El subsistema ruidoso

El controller conoce pasos, orden y detalles operativos que no le corresponden. Cualquier cambio de proceso rompe a todos los llamadores.

La fachada: un método con intención

El controller ahora dice «procesa este pedido» y no sabe — ni le importa — el cómo.

Distinción clave

  • Facade ≠ mediador: la fachada secuencia para simplificar un caso de uso; no se interpone en cada interacción entre los componentes internos.
  • No llevas el subsistema dentro: inyectas sus servicios; la fachada solo coreografía.
  • No mezcles con Service Layer: son hermanos cercanos; el Service Layer organiza el negocio, la fachada simplifica la integración. A menudo conviven: un Servicio implementa el caso de uso y una fachada empaqueta varios servicios externos.

Cuándo aplicar

  • Una operación común necesita orquestar 3+ componentes en orden fijo.
  • Quieres una API mínima de integración para los controllers o clientes.
  • El subsistema es ajeno y no quieres depender de su API completa.

Cuidado con el «facade frente a una sola clase»: si hay un solo paso, la fachada es ruido.

Ejercicio

  1. Busca un método largo que llame a 3+ servicios en secuencia.
  2. Extrae una fachada con un método que exprese la intención.
  3. Reemplaza las llamadas del llamador por la fachada.

Resumen

  • Facade: simplifica el acceso a un subsistema.
  • El subsistema sigue disponible para los casos finos.
  • Inyecta los servicios; no encierres el subsistema.
  • Con una sola operación simple, la fachada es innecesaria.
