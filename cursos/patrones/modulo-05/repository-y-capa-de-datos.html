Repository y la capa de datos

🔥 Avanzado 10 min Patrones de Diseño Módulo 5 · Backend

Introducción

El Repository proyecta una colección de entidades sobre cualquier fuente: sabes «buscar», «guardar», «eliminar» por entidad, sin que el negocio sepa si detrás hay MySQL, PostgreSQL, una API o una caché. Es el puente entre dominio y datos.

Sin Repository: SQL por todos lados

Con Repository: datos= colección de objetos

El negocio llama al repositorio; el repositorio decide la tecnología.

El caso de uso ya no tiene detalles

El día que cambies a PostgreSQL, Elasticsearch o una API, solo escribes una nueva implementación y la inyectas.

Testear es trivial

Cuidados de diseño

  • Granularidad: un repositorio por agregado, no por tabla (en dominios ricos).
  • Idioma del dominio: métodos como buscarPendientes(), no query('WHERE estado=?').
  • No filtres genericidad: evita repositorios «todopoderosos» findWhere(campo, valor) que devuelven todo el universo.
  • ORM ≠ patrón: usar Eloquent/Doctrine no te exime de la API de dominio si quieres desacople real.

Ejercicio

  1. Elige una entidad que hoy se consulta con SQL directo.
  2. Define la interfaz del repositorio en el idioma del dominio.
  3. Implementa y reemplaza dos llamadas sin tocar la lógica de negocio.

Resumen

  • Repository: colección de entidades detrás de una interfaz.
  • El negocio no sabe de SQL ni de tecnología.
  • Cambiar de fuente = escribir una implementación nueva.
  • Testear el negocio sin base de datos, gracias al fake.
