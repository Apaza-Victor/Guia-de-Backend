Service Layer en acción

🔥 Avanzado 10 min Patrones de Diseño Módulo 5 · Backend

Introducción

El Service Layer da nombre propio a los casos de uso del negocio (ConfirmarPedido, TransferirFondos) y los separa de la capa HTTP. El controller delega; el servicio orquesta repositorios, otras services y reglas.

El controller gordo

HTML/JSON, validación HTTP, reglas de negocio y efectos secundarios revueltos. Imposible reutilizar o testear el flujo.

El servicio con nombre de caso de uso

El controller vuelve a ser delgado

Ahora el mismo ConfirmarPedido funciona desde un controller, un comando CLI o una job.

Reglas sanas para services

  • Un caso de uso por servicio: método único y con nombre de intención (ejecutar, __invoke).
  • No cuelgues el estado: un servicio de negocio no guarda estado por request; comparte solo dependencias.
  • Recibe dependencias por inyección: repositorios, otros servicios, nada estático.
  • Resuelve un nivel por vez: un servicio puede usar otros servicios; evita espagueti de llamadas cruzadas sin control.
  • Devuelve valores/resultados: rara vez manipula el response; el transporte de datos va con DTO.

Service Layer vs. Facade vs. Command

  • Service Layer: organiza los casos de uso del negocio.
  • Facade: simplifica un subsistema de integración externo.
  • Command: convierte la acción en objeto para colas/registro; el Service puede ser el handler del Command.

No son rivales: conviven. Un Command Bus puede enrutar comandos hacia tus services.

Ejercicio

  1. Escoge el controller más gordo de tu proyecto.
  2. Extrae su flujo a un servicio con nombre de caso de uso.
  3. Haz que el controller solo traduzca HTTP ↔ servicio.

Resumen

  • Service Layer nombra y orquesta los casos de uso.
  • El controller traduce HTTP; el servicio decide.
  • Reutilizable desde API, CLI o colas.
  • Un caso de uso por servicio, dependencias inyectadas.
