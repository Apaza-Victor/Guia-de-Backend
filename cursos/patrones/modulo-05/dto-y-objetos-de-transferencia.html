DTO y objetos de transferencia

🔥 Avanzado 8 min Patrones de Diseño Módulo 5 · Backend

Introducción

Un DTO (Data Transfer Object) es un objeto plano: solo campos y, a lo sumo, métodos de acceso de solo lectura. Su trabajo es transportar datos entre capas — respuesta de API, entrada de un caso de uso, payload de una cola — sin lógica de negocio.

Por qué no pasar el modelo crudo

  • Fugas de interior: exponer la entidad a JSON o a otra capa regala campos internos (id de tabla, campos sensibles).
  • Lógica accidental: el serializador empieza a activar getters con cálculos del dominio.
  • Contrato frágil: cualquier cambio en la entidad se refleja al cliente o al servidor remoto.
  • Cambios de forma: la API quiere totalRedondeado, el dominio guarda total; un DTO lo separa limpiamente.

Un DTO de respuesta

El controller pide toArray() y el serializador no conoce el dominio.

DTO de entrada (el caso de uso no ve HTTP)

El service ni se entera de Request. En CQRS, este «command DTO» es el objeto que viaja por el bus.

Reglas del buen DTO

  • Inmutable: campos readonly; se crea una vez y se lee.
  • Sin lógica de negocio: solo forma, nunca reglas.
  • Solo transporte: no tiene identidad ni ciclo de vida de dominio.
  • Serializable: fácil de convertir a JSON, YAML o lo que pida el canal.
  • No lo sobrescribas: si la forma cambia, crea un nuevo DTO; es el contrato de tu API.

Ejercicio

  1. Busca dónde tu entidad se convierte directo a JSON.
  2. Crea un DTO con solo los campos públicos que la API debe ver.
  3. Mapea la entidad al DTO y cambia la serialización.

Resumen

  • DTO: datos planos, solo forma, sin comportamiento.
  • Protege a la entidad del mundo exterior.
  • Hace estable el contrato de API y de colas.
  • En CQRS, los comandos de aplicación son DTOs de entrada.
