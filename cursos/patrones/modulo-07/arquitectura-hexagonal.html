Arquitectura hexagonal

🔥 Avanzado 12 min Patrones de Diseño Módulo 7 · Patrones emergentes y arquitectura moderna

Introducción

Los backends que sobreviven años no son los que tienen mejor tecnología, sino los que pueden cambiar de base de datos, de cola de mensajes o de pasarela de pago sin reescribir la lógica de negocio. La arquitectura hexagonal, también llamada puertos y adaptadores, existe para eso.

La idea es sencilla: el dominio, el corazón de tu aplicación, no sabe nada del mundo exterior. Todo lo que entra y sale (HTTP, base de datos, mensajería) viaja a través de interfaces llamadas puertos, y las implementaciones concretas son los adaptadores.

Definición

La arquitectura hexagonal organiza la aplicación en un núcleo (dominio y casos de uso) aislado del exterior mediante puertos (interfaces) que cada adaptador externo implementa, de modo que la infraestructura es intercambiable.

Por qué importa. En backend, la base de datos, la cola y el framework cambian más rápido de lo que te gustaría. Si el dominio solo depende de interfaces, esos cambios se convierten en reemplazar un adaptador, no en una reescritura.

Cuándo usarlo. Úsala cuando el proyecto va a vivir varios años, hay varias fuentes de datos o quieres probar el núcleo sin levantar infraestructura. No la forces en scripts simples o prototipos desechables.

Conceptos clave

  • Dominio: entidades y reglas de negocio sin importar HTTP ni SQL.
  • Puerto (port): interfaz que el dominio declara y necesita.
  • Adaptador (adapter): implementación concreta de ese puerto.
  • Infraestructura: controladores HTTP, repositorios SQL, clientes de colas.
  • Testeabilidad: se prueba el núcleo con dobles en lugar de servicios reales.

Ejemplo intermedio

Añadir un adaptador PostgreSQL solo requiere implementar el mismo puerto. El dominio no cambia una línea.

Ejemplo real

Una plataforma de e-commerce cambió su API de pagos y su base de datos en el mismo año. Como el dominio dependía de puertos, el cambio fue añadir dos adaptadores nuevos y arrancar la app con otras configuraciones.

  • Coloca las interfaces (puertos) en el mismo paquete que el dominio.
  • Inyecta los adaptadores desde el punto de arranque, no desde el dominio.
  • Mantén el dominio libre de imports de frameworks y drivers.
  • Aprovecha la hexagonal para testear sin levantar Postgres ni Redis.

El framework web es otro adaptador: el caso de uso se invoca igual desde FastAPI que desde una CLI.

Explicación

  • Los puertos se dibujan como hexágonos porque la estructura no impone una dirección de entrada única: entra y sale por cualquier lado.
  • La regla de dependencia apunta siempre hacia dentro: el dominio nunca importa infraestructura.
  • Separar puertos de su implementación hace los tests unitarios triviales.
  • No confundas hexagonal con microservicios: es una organización interna que funciona también en monolitos.
  • El coste es más indirección; recompénsalo solo cuando el proyecto se beneficie de la flexibilidad.

Errores comunes

  • Convertir el dominio en un CRUD sin reglas: la persistencia manda y el patrón pierde sentido.
  • Importar el driver de base de datos dentro de un caso de uso.
  • Crear interfaces para absolutamente todo, incluso llamadas internas que nunca cambian.

Buenas prácticas

  • Empieza por los puertos de salida (base de datos, colas) que son los que más varían.
  • Prueba el núcleo con implementaciones falsas en memoria.
  • Si el proyecto es pequeño, aplica la idea de forma pragmática sin 30 carpetas vacías.

Ejercicio

  1. Extrae una interfaz para tu cliente de pagos y crea un adaptador Sandbox.
  2. Convierte tu repositorio Framework en un puerto con dos implementaciones del mismo.
  3. Escribe un test del caso de uso CrearPedido sin tocar infraestructura real.

Resumen

  • El dominio depende de puertos, y los adaptadores implementan esas interfaces.
  • La infraestructura se vuelve intercambiable y el núcleo testable sin servicios reales.
  • Es una inversión que vale la pena cuando el backend va a evolucionar durante años.
