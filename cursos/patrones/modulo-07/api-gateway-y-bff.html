API Gateway y Backend for Frontend

🔥 Avanzado 11 min Patrones de Diseño Módulo 7 · Patrones emergentes y arquitectura moderna

Introducción

Cuando un solo cliente tiene que hablar con usuarios, pedidos, pagos y búsqueda, las llamadas se multiplican, la seguridad se dispersa y cada refactor acopla a todos. El API Gateway concentra ese frente en un único punto de entrada.

El Backend for Frontend (BFF) afina la idea: un backend adaptado a las necesidades de cada cliente concreto, de modo que la app móvil y la web reciben justo lo que necesitan, ni más ni menos.

Definición

Un API Gateway es un único punto de entrada que enruta, autentica, agrega y gestiona el tráfico hacia el resto de servicios internos. El BFF es una variante que crea una API específica para cada tipo de cliente.

Por qué importa. Reduce la complejidad del cliente, centraliza la seguridad y el rate limiting, y permite agregar varias llamadas internas en una sola respuesta de red.

Cuándo usarlo. Úsalo al pasar de unos pocos microservicios a varios, o cuando distintos clientes necesitan contratos distintos. En monolitos pequeños añade latencia sin beneficio.

Conceptos clave

  • Enrutado: reenvía cada petición al servicio responsable.
  • Agregación: responde combinando llamadas a varios servicios.
  • Autenticación central: valida tokens una sola vez en el borde.
  • Rate limiting: protege los servicios de abuso desde fuera.
  • BFF: una API adaptada por cliente (web, móvil, terceros).

Ejemplo básico

Una agregación sencilla: el gateway recibe /pedido/12 y encadena las llamadas a pedidos y cliente para devolver una sola respuesta.

Dos llamadas internas se convierten en una respuesta para el cliente.

Ejemplo intermedio

Configuración de un gateway con Express: enrutado con validación de token y límite de peticiones para clientes anónimos.

Ejemplo real

Una app de comercio necesita un perfil con pedidos e historial de pagos en la primera pantalla. El gateway agrega tres servicios y también oculta los detalles internos (URLs, formatos) al móvil.

  • Centraliza ahí la autenticación, el rate limiting y el logging de entrada.
  • Agrega solo lo necesario para ahorrar round-trips; evita ir sobrevuelos con timeout largo.
  • Mantén contratos estables por versión para no romper clientes publicados.
  • Diferencia un BFF por cliente cuando los contratos divergen de verdad.

Un gateway que solo enruta sin agregar sigue siendo útil, pero el valor real aparece con la agregación y la seguridad centralizada.

Explicación

  • El gateway se convierte en el contrato público que los equipos internos pueden mover libremente.
  • La agregación con Promise.all reduce latencia: las llamadas internas van en paralelo.
  • Centralizar el rate limiting evita que un cliente ruidoso sature un servicio crítico.
  • El BFF permite que el equipo móvil cambie su API sin tocar la web.
  • Su riesgo es convertirse en un monolito de integración: vigila su tamaño y split en dominios.

Errores comunes

  • Crear un gateway sin rate limiting y exponer directamente los servicios internos.
  • Agregar llamadas en serie que multiplican la latencia total.
  • Mantener el contrato del gateway rígido cuando los clientes evolucionan.

Buenas prácticas

  • Diseña el gateway en torno a casos de uso del cliente, no a tablas del servidor.
  • Mide la latencia de cada ruta agregada para detectar cuellos de botella.
  • Combínalo con circuit breakers hacia los servicios internos.

Ejercicio

  1. Crea una ruta /perfil/... que agregue usuario, pedidos y pagos en paralelo.
  2. Añade rate limiting por IP y un mensaje claro al superar el límite.
  3. Separa un BFF móvil con un contrato reducido y mide la diferencia de payload.

Resumen

  • Un API Gateway unifica entrada, seguridad y agregación de servicios.
  • El BFF adapta la API a cada cliente concreto.
  • Bien diseñado, reduce latencia y acoplamiento; mal diseñado, es otro monolito.
