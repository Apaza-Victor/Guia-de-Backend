Qué hace grande a un portafolio backend

🔥 Avanzado 10 min Proyectos Backend Módulo 4 · Del portafolio al proyecto real

Introducción

Un portafolio backend no se mide en número de repositorios sino en proyectos que cuentan una historia técnica completa: una base de datos, una API, una autenticación, un despliegue y un README que explica las decisiones.

El reclutador pasa veinte segundos por proyecto. Tu trabajo es que en esos veinte segundos sepa qué construiste, cómo lo hiciste y qué dice de ti como ingeniero.

Definición

Un portafolio backend es un conjunto de proyectos en producción que demuestra una progresión técnica: de lo fundamental a lo complejo, cada uno con su código, su documentación y un resultado visible.

Por qué importa. En un mundo con miles de candidatos, el portafolio es la prueba de que sabes hacer, no solo afirmar que sabes.

Cuándo usarlo. Elige de tres a cinco proyectos en los que el código, el despliegue y la explicación estén al mismo nivel de calidad.

Conceptos clave

  • Cada proyecto debe demostrar una habilidad concreta y nombrable.
  • El proyecto en producción vale más que el repo sin desplegar.
  • El README es la primera pantalla de tu proyecto y debe venderse sola.
  • La progresión técnica muestra crecimiento: no repitas el mismo CRUD tres veces.
  • La calidad de una sola decisión bien explicada pesa más que veinte features.

Ejemplo real

Dos candidatos llegan a la entrevista: el primero tiene doce repos de ejercicios desordenados; el segundo tiene tres proyectos desplegados, cada uno con su README, su arquitectura y su despliegue. El segundo explica su decisión de usar una cola en el proyecto de notificaciones y la entrevista da un salto de calidad: ya no se prueba memoria, se conversa de criterio.

  • Despliega cada proyecto: nadie se lleva impresión de un repo que no corre.
  • Escribe un README con secciones fijas: qué, cómo, decisiones, cómo probar.
  • Nombra una decisión técnica por proyecto y prepárate para defenderla.

La progresión importa: empieza por un CRUD sólido y sube a microservicios, no al revés.

Explicación

  • El portafolio demuestra competencia con evidencia, no con afirmaciones.
  • Cada proyecto debe tener un verbo claro: 'implementé', 'desplegué', 'optimicé'.
  • El despliegue separa a quien emula de quien termina.
  • El README bien escrito demuestra comunicación, la habilidad más infravalorada.
  • La progresión de proyectos muestra capacidad de aprender y asumir retos crecientes.

Errores comunes

  • Tener un solo CRUD y repetirlo en todos los proyectos.
  • Repos sin README ni despliegue que parecen tareas de clase.
  • Proyectos gigantes que nunca terminan en producción.

Buenas prácticas

  • Elige tres a cinco proyectos que cuenten una historia ascendente.
  • Despliega el primero desde la primera semana, no al final.
  • Actualiza cada README como si fuera tu carta de presentación.
  • Añade capturas, un diagrama de arquitectura y métricas del proyecto.

Ejercicio

  1. Evalúa tus proyectos: cuántos están desplegados y cuántos se explican solos.
  2. Escribe el README de un proyecto tuyo con las cinco secciones clave.
  3. Elige la decisión técnica que defenderías en una entrevista.

Resumen

  • El portafolio gana con tres a cinco proyectos desplegados y bien explicados.
  • Cada proyecto demuestra una habilidad y una decisión técnica defensible.
  • El README y el despliegue son parte del proyecto, no extras.
