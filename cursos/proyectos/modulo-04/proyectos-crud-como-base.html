El CRUD bien hecho como base

🔥 Avanzado 11 min Proyectos Backend Módulo 4 · Del portafolio al proyecto real

Introducción

Todo portafolio tiene un CRUD. La diferencia entre el que se nota y el que no está en lo que rodea a las cuatro letras: validación de entrada, paginación, errores consistentes, casos de prueba y una organización que no se repite para cada recurso.

El CRUD bien hecho es la base de cualquier proyecto porque casi todo el negocio se reduce a gestionar recursos. Si el tuyo está bien construido, cada feature nueva es una variante, no una aventura.

Definición

Un CRUD (Create, Read, Update, Delete) es la gestión de un recurso sobre un almacén, expuesta de forma consistente; bien hecho incluye validación, paginación, errores uniformes y prueba.

Por qué importa. El CRUD es el esqueleto de las aplicaciones; su calidad define el techo de todo lo que construyas encima.

Cuándo usarlo. Diseña el CRUD con el molde del recurso desde el primer endpoint; dos recursos iguales sin abstracción son el primer paso hacia la duplicación.

Conceptos clave

  • La validación de entrada rechaza lo inválido antes de tocar tu lógica.
  • La paginación evita respuestas infinitas y sobrecarga.
  • El contrato de error uniforme enseña a los clientes a parsear fallos.
  • La organización por recurso (ruta, servicio, repositorio) se repite sin copiar.
  • Las pruebas del CRUD protegen la base de todo el proyecto.

Ejemplo real

Una API de inventario usa el mismo repositorio para productos, categorías y proveedores. La prometida es simple: cualquier bug de validación o error de contrato se arregla una vez. Cuando llega el cuarto recurso, el equipo lo tiene listo en una tarde porque el molde ya está probado.

  • Valida con el esquema del recurso en la frontera de entrada.
  • Pagina todos los listados con el mismo cursor.
  • Prueba el molde una vez por recurso y mantén los tests verdes.

La abstracción se paga con flexibilidad: no te esfuerces por generalizar hasta el segundo recurso.

Explicación

  • La validación en la entrada marca la frontera de confianza.
  • La paginación protege latencias y cargas de la base de datos.
  • El contrato de error uniforme facilita la vida a los clientes.
  • El molde repetible evita duplicar reglas dispersas.
  • Las pruebas del CRUD dan red de seguridad a cada feature nueva.

Errores comunes

  • Validar a medias y descubrir los fallos en producción.
  • Listados sin paginar que mueren cuando el recurso crece.
  • Errores con formas distintas en cada ruta.

Buenas prácticas

  • Valida en la frontera con el esquema del recurso.
  • Página todos los listados desde el día uno.
  • Centraliza la construcción del error en una función única.
  • Escribe los tests del CRUD antes de añadir features.

Ejercicio

  1. Crea un recurso completo con validación, paginación y error uniforme.
  2. Escribe los cuatro tests del CRUD (ok, inválido, no existe, duplicado).
  3. Refactoriza dos recursos duplicados hacia un molde común.

Resumen

  • El CRUD bien hecho es validación, paginación, errores y molde repetible.
  • El contrato de error uniforme enseña a los clientes a trabajar con fallos.
  • Las pruebas del CRUD protegen todas las features que construyas encima.
