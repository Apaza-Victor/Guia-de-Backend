Testing integral del proyecto

🧠 Experto 11 min Proyectos Backend Módulo 7 · Hacia el perfil senior

Introducción

Un proyecto de portafolio con una buena estrategia de testing es un argumento de seniority: demuestra que entiendes la pirámide, los dobles y que tus pruebas protegen reglas reales de negocio, no solo el código.

La clave está en la proporción: muchas pruebas unitarias de lógica pura, algunas de integración con la base de datos y un par de E2E que recorran el flujo completo. La red se diseña, no se llena de humo.

Definición

La estrategia de testing integral cubre tres niveles: unitarias (lógica pura y casos de uso), integración (base de datos y HTTP reales) y E2E (flujos completos por la API pública).

Por qué importa. Las reglas de negocio (propiedad de datos, stock, tokens) son las que más cuestan cuando fallan: merecen una red de seguridad.

Cuándo usarlo. Empieza por las reglas de negocio; sube a integración para la base y deja el E2E para los flujos críticos.

Conceptos clave

  • La pirámide: muchas unitarias, menos integración, pocas E2E.
  • El doble (mock o stub) aísla la lógica de sus vecinos.
  • La integración real valida las consultas y las transacciones.
  • El E2E recorre el flujo completo por la API pública.
  • La cobertura vale menos que las pruebas de las reglas críticas.

  • Prueba las reglas de negocio antes que los detalles.
  • Usa una base de test con migraciones y seeds mínimos.
  • Del E2E de los flujos críticos, no uno por cada ruta.

Documenta en el README cómo correr la suite y qué cubre cada nivel.

Explicación

  • La pirámide equilibra velocidad y confianza.
  • El doble aísla la lógica y sube la velocidad de la suite.
  • La integración con base real valida SQL, transacciones y mapeos.
  • El E2E protege los flujos que tocan varias capas.
  • El bug capturado por un test vale más que el 100 % de cobertura en código trillado.

Errores comunes

  • Cobertura altísima en código trivial y reglas de negocio sin probar.
  • E2E frágiles que dependen de la red y rompen por estar flakies.
  • Suite que tarda veinte minutos y nadie corre local.

Buenas prácticas

  • Empieza por las reglas de propiedad y stock.
  • Mantén tests de integración rápidos con una base de test.
  • Deja 3-5 E2E de flujos críticos, no uno por endpoint.
  • Corre la suite en cada pull request.

Ejercicio

  1. Escribe la prueba de la regla más crítica de tu proyecto.
  2. Añade una integración con base real y un caso de transacción.
  3. Diseña el E2E del flujo de registro y pedido.

Resumen

  • La red de testing cubre unitarias, integración y E2E en proporción.
  • Las reglas de negocio críticas merecen prueba explícita.
  • La suite rápida corre en cada PR y protege el producto.
