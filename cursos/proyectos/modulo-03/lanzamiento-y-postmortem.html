Lanzamientos y postmortem

⚙️ Intermedio 8 min Gestión de Proyectos Backend Módulo 3 · Comunicación y entrega

El lanzamiento como el momento más sereno

La paradoja del release backend es que el momento de más riesgo debería verse como el más tranquilo del ciclo: si el despliegue depende de los nervios de una persona a medianoche, algo está mal gestionado. Un lanzamiento maduro es una checklist repetida que ya se ensayó, no un acto de fe.

Todo lo que vimos en los módulos anteriores confluye aquí: el contrato probado en la CI, el staging verificado, la estrategia de deploy y el plan de rollback listo. Si alguno falta, el release se pospone — no se «lanza y a ver».

Feature flags: separar el despliegue del lanzamiento

El superpoder de management que mejor resuelve el miedo al release es el feature flag: poder desplegar código «dormido» y activarlo cuando se quiera, sin volver a desplegar. Así, desplegar y lanzar dejan de ser lo mismo:

# config de flags (ejemplo en JSON de configuración)
curl -X POST https://flags.miservidor.com/api/flags \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -d '{"nombre":"reembolso_automatico","estado":"desactivada"}'

# En el código el destino decide (leído en el arranque o en caliente)
# if (flags["reembolso_automatico"]) { /* ruta nueva */ } else { /* ruta antigua */ }

# Lanzamiento progresivo: activar para 5% de clientes
curl -X PATCH https://flags.miservidor.com/api/flags/reembolso_automatico \
  -d '{"estado":"activada","rollout":0.05}'

Beneficios directos: release independiente de la sincronización (el código puede esperar días), kill-switch instantáneo (desactivar sin deploy de emergencia) y canary a porcentajes. El costo: tiene un flag por cada característica; los flags se retiran cuando la feature está estable, o se vuelven deuda.

La checklist de release que evita sorpresas

{
  "release": "v2.4.0 · reembolsos automáticos",
  "checklist": [
    { "paso": "CI verde en main con los tests de integración", "ok": true },
    { "paso": "Despliegue en staging y prueba manual del flujo crítico", "ok": true },
    { "paso": "Migraciones aplicadas y reversibles, backup creado", "ok": true },
    { "paso": "Contrato validado (OpenAPI) y documentación lista", "ok": true },
    { "paso": "Feature flag desactivado por defecto", "ok": true },
    { "paso": "Alertas de error rate, latencia y 5xx configuradas", "ok": true },
    { "paso": "Plan de rollback aprobado y ensayado en staging", "ok": true }
  ],
  "responsable": "ana@equipo",
  "ventana": "lunes 09:00-11:00 (hora de menor tráfico de pagos)"
}

Fíjate en la ventana: elegir el momento de menor riesgo y con gente despierta es parte del plan. El release no «se hace a las 3am para no molestar»: se hace a la hora con la mejor relación riesgo/cobertura de alertas.

La retrospectiva: cerrar el ciclo

Después del lanzamiento, el ciclo Scrum se cierra con la retrospectiva — la única ceremonia cuyo propósito es mejorar el proceso, no el producto. Su formato clásico es el trío:

  • Lo que salió bien: para repetirlo (y escriturarlo, para que no se olvide).
  • Lo que salió mal: sin culpas, con su causa raíz.
  • Lo que mejoraremos: máximo 2-3 acciones concretas con dueño y fecha, que entren al backlog del siguiente sprint.

El test de una retrospectiva útil es a los 15 días: ¿las acciones acordadas se ejecutaron? ¿o fueron puras palabras lindas? Si no entran al tablero, la retrospectiva fue una tertulia.

El postmortem sin culpables

Los incidentes de producción son inevitables; lo evitable es repetirlos. El postmortem (o revisión de incidente) es el documento que transforma una caída en aprendizaje concreto. Sus reglas de oro:

  1. Sin culpables: se analizan condiciones y decisiones, no personas. La frase prohibida: «¿por qué no pensó X?».
  2. Cronología factual: qué pasó, en qué orden, con horas y evidencia (logs, métricas, commits).
  3. Causa raíz real: no la próxima (el input mal formateado) sino la profunda (no había validación; el flag se lanzó sin canario).
  4. Acciones accionables UNA por causa: cada acción con dueño y fecha, y se convierte en ticket.

Una estructura mínima de postmortem que sirve en cualquier equipo:

{
  "incidente": "INC-2026-09-22 · double cargo en te mla",
  "fecha": "2026-09-22T14:05Z",
  "impacto": "437 cargos duplicados (se compensó manualmente)",
  "cronologia": [
    "13:40  deploy a prod de v2.4 (flag reembolso desactivado)",
    "13:55  error rate de cobros sube a 4.3%",
    "14:00  rollback a v2.3",
    "14:05  normalizado",
    "14:20  postmortem convocado"
  ],
  "causa_raiz": "retry del consumidor reenviaba el cargo sin clave de idempotencia perdida en el release actual",
  "acciones": [
    { "accion": "idempotencia por Idempotency-Key en los cargos", "dueño": "bruno", "fecha": "2026-10-01" },
    { "accion": "alertas de error rate por endpoint", "dueño": "ana", "fecha": "2026-09-29" }
  ]
}

El postmortem no castiga: protege. Alguien que sabe que el incidente se analiza sin resolver culpables reportará temprano y sin miedo, y eso vale más que cualquier sistema de responsabilidad.

Cultura de entrega: el ciclo se respira

Para cerrar el curso: la gestión de proyectos backend no es un conjunto de fórmulas; es una cultura de entregas pequeñas, medidas y revisadas. Si este ciclo —planificar según capacidad, seguir con datos, comunicar por escrito, revisar en equipo, desplegar con rollback y aprender con postmortems— se repite con disciplina, lo que era riesgo se convierte en rutina.

Y cada ciclo, la velocidad, la estabilidad y la confianza del equipo suben un poco. Eso es lo que finalmente distingue un proyecto bien gestionado de uno que solo tiene suerte.

Ejercicio

  1. Elige una feature próxima en tu proyecto y escribe cómo la desplegarías con feature flag, incluida la activación progresiva por porcentaje.
  2. Redacta tu checklist de release en 7 pasos y asigna a cada uno su responsable y su señal de verificación.
  3. Reconstruye un incidente (o inventa uno plausible) en un postmortem de 4 secciones con 2 acciones accionables y dueño.

Resumen

  • Un lanzamiento maduro es una checklist repetida y ensayada, no un acto de fe a medianoche.
  • Los feature flags separan desplegar de lanzar: kill-switch y canary sin nuevo deploy.
  • La retrospectiva cierra el ciclo con acciones reales que entran al backlog.
  • El postmortem sin culpables convierte incidentes en mejoras con causa raíz y acciones con dueño.
