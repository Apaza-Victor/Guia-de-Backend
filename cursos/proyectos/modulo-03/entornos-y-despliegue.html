Entornos y despliegue

⚙️ Intermedio 8 min Gestión de Proyectos Backend Módulo 3 · Comunicación y entrega

El mapa de entornos

Cada línea de código viaja por entornos de menor a mayor confianza. El backend exige que este mapa esté claro porque aquí cada salto tiene acceso a datos reales:

  • Local: tu máquina, datos de prueba, sin estrés. Razo de iteración máxima.
  • Desarrollo (dev): integración del equipo, datos sintéticos, se rompe sin drama.
  • Staging: gemelo de producción —misma base, mismas dosis, mismas secrets de prueba—. Sirve para verificar lo que la CI no puede: la integración verdadera.
  • Producción: usuarios reales. Lo que falla aquí paga factura.

La ley no escrita: lo que no se probó en staging no se despliega en producción. Si saltas el escalón, el error se vuelve «descubierto por el usuario», que es la peor forma de hacer QA.

Configuración por entorno: los secretos no van en git

La misma aplicación cambia de comportamiento según el entorno mediante la configuración, no mediante el código. Todo lo que distingue dev de producción —conexiones, claves, flags— es variable de entorno:

# .env.staging (ejemplo de configuración de staging)
DATABASE_URL=postgres://app:app@db-staging:5432/tienda
REDIS_URL=redis://redis-staging:6379/0
IDEMPOTENCIA_TTL_SECS=86400

# .env de producción vive en el secret manager, NO en el repo
# gcloud secrets versions access latest --secret=DATABASE_URL

# Verificación: ¿hay secretos en el repo?
git ls-files | xargs grep -l "password\s*=" 2>/dev/null || echo "limpio: sin secretos"

Dos motivos por los que esto lo decide la cultura del equipo: la higiene de secretos (un `.env` commiteado es una backdoor pública) y la paridad de entornos (si staging usa otra base, el desplegué a producción lleva sorpresas).

Estrategias de despliegue

El despliegue no es «subir a producción»: es un conjunto de estrategias con distinto tiempo de exposición al fallo:

    "riesgo": "Ventana de caída total si el despliegue falla",
    "cuando": "MVP, servicios internos, infra con slot de mantenimiento"
  },
  {
    "estrategia": "rolling",
    "descripcion": "Se actualiza de a un nodo; mientras tanto quedan los viejos sirviendo.",
    "riesgo": "Dos versiones conviven unos minutos (compatibilidad de contrato obligatoria)",
    "cuando": "API con pods/replicas detrás del balanceador"
  },
  {
    "estrategia": "blue-green (canary)",
    "descripcion": "Se monta el entorno nuevo completo (verde) y el tráfico se mueve por porcentaje.",
    "riesgo": "Costo de tener dos entornos vivos",
    "cuando": "Releases grandes con necesidad de observabilidad previa"
  }
]

La regla común a todas: decide antes del despliegue cuál es el criterio para volver atrás (síntoma: error rate > X%, latencia > Y). Si el rollback se decide durante la crisis, será tarde.

El plan de rollback que da tranquilidad

Rollback es tan importante como deploy. Un buen plan de reversa tiene tres piezas:

  1. App: el binario/versión anterior lista para volver (imagen viejita en el registry, tag anterior en git).
  2. Base: las migraciones reversibles — si una columna se eliminó, el down debe poder recrearla. Nunca migrar sin script de reversa.
  3. Paridad: datos probablemente ya tocados por la versión nueva (tipos, campos, enriquecimiento). Si la versión nueva modificó datos, el rollback de app no es suficiente: se necesita un plan de data.
# Plan de rollback de un release (cheatlist)
git tag list — release-2026-09-22   # version desplegada
git checkout v2026-09-01            # última versión estable
docker compose build —tag api:rollback
docker compose up -d --no-deps api:rollback

# Base de datos: ejecutar el down de la migración 48
npx prisma migrate resolve --applied 47
npx prisma migrate deploy            # baja a la estructura anterior

La señal de madurez es el juego de guerra: probar el rollback en staging antes del release. Si nunca lo ensayaste, el día que lo necesites será tu primer ensayo.

Deploy automatizado y repetible

El despliegue manual —comandos tecleados por una persona con memoria— es el peor riesgo que gestiona un backend. Todo desplegué debe ser la misma receta ejecutada por la máquina:

  • Despliegue = hacer build, correr migraciones (con chocheo), mover el tráfico, verificar health.
  • El paso a staging se dispara automáticamente con cada merge.
  • El paso a producción se dispara con un botón/approved del release, siempre el mismo playbook.
  • Healthcheck real (endpoint /healthz que compruebe DB y dependencias), no solo «el proceso está vivo».

Con esto, desplegar deja de ser «hazaña del mes» y se vuelve rutina semanal — la frecuencia es la prueba de madurez del pipeline.

Ejercicio

  1. Dibuja el mapa de entornos de tu proyecto y verifica si staging usa la misma base, tus mismas versiones y configuraciones que producción.
  2. Elige una estrategia de despliegue para tu API principal y escribe el criterio numérico de rollback (error rate, latencia).
  3. Redacta tu plan de reversa en 3 pasos: app, migración (down) y plan de datos.

Resumen

  • El mapa dev → staging → producción da un lugar para cada tipo de error, y staging es el gemelo que debe parecerse a producción.
  • La configuración diferencia entornos; los secretos viven en el secret manager, nunca en git.
  • Redeploy, rolling y blue-green son estrategias con distinta exposición al fallo.
  • El rollback se decide antes del despliegue y se practica en staging — app, migración y plan de datos.
