Code review y colaboración

⚙️ Intermedio 9 min Gestión de Proyectos Backend Módulo 3 · Comunicación y entrega

El code review no es una inspección

El code review —la revisión de modificaciones de código por otro miembro del equipo antes de integrarlas— es la práctica de colaboración con mejor relación costo/beneficio del backend. Su función real no es cazar errores (aunque atrape algunos): es aumentar el conocimiento compartido, impedir que las decisiones muertas en el head y que el código reciba cuarto aviso.

Cuando se hace bien, cada PR que sale de tu equipo se vuelve un acuerdo revisado por ojos frescos: «esto encaja con el sistema, tiene tests honestos y no añade deuda». Cuando se hace mal, es un trámite que nadie quiere firmar y todos quieren saltar.

El PR bien armado

Un pull request es la unidad de revisión. Si el PR es un monstruo de 3000 líneas que toca 20 archivos, la revisión es imposible de hacer bien. La preparación del PR es el 50% de la revisión:

# Extracto de plantilla de PR backend
# Titulo: [ORQ-230] Idempotencia en el endpoint de cargos
#
# Qué cambia
# - Endpoint POST /v1/cargos acepta header Idempotency-Key
# - Clave validada contra Redis (TTL 24h) antes de crear el cargo
# - Test de integración para el caso de reintento con misma clave
#
# Cómo se probó
# - npx jest tests/integracion/cargos-idempotencia.test.js
# - Cargo con clave repetida devuelve el MISMO cargo, sin duplicar
#
# Riesgos
# - Si Redis cae se rechaza con 503 (fail-closed) — ver ADR-9

git checkout -b feat/ORQ-230-idempotencia
# ...commits pequeños y con mensajes que cuentan historia...
git push -u origin feat/ORQ-230-idempotencia

La regla práctica: si el PR tarda más de 30-45 minutos en revisarse, está demasiado grande. Se parte en PRs más pequeños y desplegables, o se escalona.

Qué revisar (y qué no)

Un buen checklist de revisión de backend, en orden de prioridad:

  1. Comportamiento y contrato: ¿la API respeta el contrato? ¿qué pasa con el request inválido, el retry, el caso vacío?
  2. Datos: ¿la migración es reversible? ¿hay índices para las consultas nuevas? ¿qué pasa si el worker muere a mitad?
  3. Seguridad: ¿entrada validada? ¿escapado? ¿no hay secretos hardcodeados
  4. Tests: ¿cubren el flujo crítico y los casos de fallo, no solo el feliz?
  5. Estilo y deuda: ¿sigue los estándares? ¿añade duplicación innecesaria?

En cambio, no se discute en el PR lo que el linter ya decide (esa conversación la gana el lint), ni se usa el comentario para imponer gustos personales sin justificación.

Los comentarios se categorizan para que el autor sepa qué le están pidiendo:

# Convención de comentarios de review
# [bloqueante]  -> no se mergea hasta resolver (defecto, datos, seguridad)
# [sugerencia]  -> opcional, el autor decide
# [pregunta]    -> no entiendo, explícame (no es una exigencia)
# [nit]         -> detalle menor, se puede arreglar en el futuro

git commit -m "fix(ORQ-230): rechazo 409 si la clave ya fue usada [bloqueante]"

Pair programming y mobbing

El pair programming (dos personas, un problema) es quizá la práctica de colaboración más desprestigiada por los mitos y la más útil en backend:

  • Disminuye el conocimiento concentrado: dos cabezas saben el flujo de pagos, no una.
  • Reduce el feedback ossificado de la review: las decisiones y correcciones se toman en el momento, no 3 días después.
  • Mejora la calidad del momento: con alguien mirando, es difícil pasar por alto el caso borde.

No es obligatorio programar todo en parejas; funciona como herramienta puntual: complejidad alta, componente nuevo, onboarding, o deuda que da miedo tocar.

Estándares de equipo, no señores del código

La pieza final es tener estándares escritos — guías que el equipo aceptó, no impuestas por una sola voz. Sin estándares, cada review es una pelea de religión; con ellos, el PR se revisa contra un checklist, no contra el humor del revisor.

El estándar mínimo de un backend moderno:

{
  "git": {
    "branch": "feat/-",
    "commits": "conventional: fix, feat, docs, refactor...",
    "pr": "máximo ~400 líneas, mensaje con template"
  },
  "calidad": ["lint automático en CI", "tests unitarios + integración", "al menos 1 aprobación"],
  "datos": ["migraciones reversibles", "índices revisados por el equipo", "sin SELECT * en código"],
  "revision": ["redactado a la solución, no a la persona", "comentarios con etiqueta", "merge cuando CI verde"]
}

Los estándares se revisan en las retrospectivas: si el equipo ya no cree en uno, se cambia, pero mientras está vigente se cumple — ese respeto al acuerdo es lo que evita que el review se vuelva ruido.

Ejercicio

  1. Toma un PR reciente de tu equipo y asígnale las etiquetas [bloqueante]/[sugerencia]/[pregunta]/[nit] a sus comentarios.
  2. Escribe una plantilla de PR con qué cambia, cómo se probó y riesgos, enfocada en datos y contrato.
  3. Propón una sesión de pair programming para el componente de mayor riesgo de tu proyecto y explica en 3 líneas por qué.

Resumen

  • El code review multiplica conocimiento compartido y protege contra el conocimiento concentrado.
  • Un PR revisable es pequeño, con commits que cuentan historia y una plantilla que explica qué, cómo y riesgos.
  • Se revisa contrato, datos, seguridad y tests; el estilo lo decide el lint y la discusión técnica vive en el PR.
  • El pair programming es una herramienta puntual poderosísima, y los estándares escritos evitan reviews de religión.
