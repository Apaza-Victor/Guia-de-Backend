Calidad y verificación

⚙️ Intermedio 9 min Gestión de Proyectos Backend Módulo 3 · Comunicación y entrega

La calidad de un backend no es accidental

En el frontend, una interfaz rota se nota a los tres segundos. En el backend, un defecto puede dormir en producción durante semanas: en una consulta que degrada, en un raza de integer que corrompe estados, en una validación que dejó escapar un cargo duplicado. Por eso la verificación automatizada no es un lujo: es el único sistema de indicadores que funciona 24/7 sin recordar a nadie.

Toda la calidad de un equipo backend se resume en una pregunta: ¿el código que está a punto de integrarse está verificado por una máquina, no solo por el que lo escribió? Si no, cada merge es una apuesta.

La pirámide de pruebas

Ningún tipo de prueba basta solo. La convención del backend es la pirámide de pruebas, de base ancha a cúspide:

  • Base — unitarias: rápidas y aisladas (función, clase, caso de negocio). Miles, corren en segundos.
  • Medio — integración: componentes reales juntos: servicio + base de datos, endpoint + contrato. Decenas, corren en minutos.
  • Cúspide — end-to-end: el flujo completo como lo usa el usuario. Pocas y caras, se usan para los caminos críticos.

La pirámide existe porque cada nivel sube la fidelidad y sube la fragilidad: el e2e es el más parecido a la realidad y el que más se rompe por motivos ajenos al código. El diseño correcto es: muchas unitarias, suficientes de integración, pocas e2e.

La CI como portero del merge

La integración continua (CI) ejecuta la verificación automáticamente en cada pull request. No es «deploy automático» ni «tests que alguien corre»: es la máquina que decide si el PR tiene derecho a discutirse en review con algo que ya verificó:

{
  "pipeline": "merge a main",
  "etapas": [
    { "nombre": "lint", "comando": "npm run lint", "falla": "no revisar estilo a mano" },
    { "nombre": "unitarias", "comando": "npx jest tests/unitarios", "falla": "detener PR" },
    { "nombre": "integración", "comando": "npx jest tests/integracion", "falla": "detener PR" },
    { "nombre": "migraciones", "comando": "prisma migrate dev --preview-feature", "falla": "revisar schema vs datos" },
    { "nombre": "cobertura", "comando": "npx jest --coverage --coverageThreshold 80", "falla": "pedir tests del codigo nuevo" },
    { "nombre": "contrato", "comando": "npx openapi-generator validate contrato.yml", "falla": "contrato inconsistente" }
  ]
}

La regla de oro operativa: un PR no se mergea con CI roja. Si lo permiten «solo un momentito», la cadena entera pierde significado — y la siguiente persona que vea una roja pensará que también puede pasarla.

Pruebas de integración que valen la pena

Son las que rompen de verdad en backend: el endpoint correcto con la base equivocada, el worker que asume campos que el productor no envía, el contrato que cambió sin aviso. Los equipos sanos las escriben como primer reflejo de cada historia, no como relleno.

const request = require('supertest');
const { app } = require('../src/app');
const db = require('../src/db');

describe('Flujo crítico: cobro con saldo insuficiente', () => {
  beforeEach(async () => {
    await db('cuentas').insert([{ id: 1, saldo: 100 }, { id: 2, saldo: 5000 }]);
  });

  it('rechaza el cargo cuando el saldo cubre el movimiento', async () => {
    const resp = await request(app)
      .post('/v1/cargos')
      .send({ cuentaId: 1, monto: 150, referencia: 'R-900' });

    expect(resp.status).toBe(422);
    const movimientos = await db('movimientos').where({ cuentaId: 1 });
    expect(movimientos).toHaveLength(0); // nada a medias en la base
  });
});

Fíjate que el test verifica el efecto colateral (la tabla movimientos), no solo el código HTTP: ahí es donde el backend muestra la verdad.

Cobertura: número necesario, no suficiente

La cobertura (qué porcentaje de líneas tocan los tests) es un termómetro barato: si es baja, algo mal; si es alta, puede que cubras 90% de líneas y 10% de la lógica real. El 100% de cobertura no garantiza calidad — garantiza que alguien ejecutó código.

Usos correctos de la cobertura:

  • Umbral mínimo como guardarraíl de la CI (p. ej. 70-80% global).
  • Detección de zonas muertas: el módulo de conciliación con 5% de cobertura es sospechoso.
  • Foco en lo crítico: el flujo de pagos, auth y datos merecen más cobertura que la capa de presentación.

El criterio del equipo no debe ser «subamos la cobertura» sino «¿los caminos que producen dinero o mueven datos están probados?». La cobertura es la evidencia, no el objetivo.

CI en lenguaje comunidad

La descripción de la CI vive en el repo (GitHub Actions, GitLab CI, etc.) y es de tres líneas en cada lenguaje. El patrón mínimo es universal:

# .github/workflows/ci.yml (esquema)
# name: CI
# on: [push]
# jobs:
#   test:
#     runs-on: ubuntu-latest
#     services:
#       postgres:
#         image: postgres:16
#     steps:
#       - uses: actions/checkout@v4
#       - run: docker compose build
#       - run: docker compose run --rm app npm run lint
#       - run: docker compose run --rm app npx jest --coverage

gh workflow run ci.yml --ref main   # lanzar a mano si hace falta

La regla de calidad esencial: la CI local debe reproducirse localmente. Si solo pasa «en el servidor de CI», nadie la ejecutar en su máquina y la iteración se vuelve espera.

Ejercicio

  1. Dibuja la pirámide de pruebas de tu proyecto y anota cuántas pruebas tienes en cada nivel (aprox).
  2. Escribe el pipeline de CI de tu equipo en 5 etapas, incluyendo lint, unitarias, integración, migraciones y cobertura.
  3. Selecciona la prueba de integración del flujo que más dinero mueve en tu sistema y redacta su caso: precondición, acción, esperado.

Resumen

  • La calidad del backend no es accidental: se apoya en verificación automática que corre 24/7.
  • La pirámide de pruebas equilibra unitarias, integración y e2e según fidelidad y fragilidad.
  • La CI es el portero del merge: si no pasa, el PR no se integra, jamás «por un momento».
  • La cobertura es una señal barata de salud, no el objetivo; lo crítico es probar los caminos que movilizan dinero o datos.
