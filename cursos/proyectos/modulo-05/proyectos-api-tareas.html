API de tareas con autenticación

🔥 Avanzado 12 min Proyectos Backend Módulo 5 · Casos de uso reales

Introducción

La API de tareas es el 'hola mundo profesional' del backend porque reúne en un solo proyecto todo lo que se pregunta en una entrevista junior: modelado de datos, autenticación real, autorización por usuario, caché y pruebas.

La diferencia está en no quedarse en el tutorial: usa refresh tokens, propiedad de los datos por usuario y una suite de tests que proteja el conjunto.

Definición

La API de tareas es un CRUD de tareas privadas por usuario, con registro y login JWT, refresh tokens, listados filtrados y pruebas de los flujos completos.

Por qué importa. En un solo proyecto demuestra base de datos, seguridad, caché, contrato y testing: la hoja completa de un backend.

Cuándo usarlo. Úsala como primer proyecto del portafolio por su tamaño acotado y capacidad de enseñanza.

Conceptos clave

  • El usuario es dueño de sus tareas: toda consulta filtra por su id.
  • El access token corto y el refresh con rotación dan sesión segura.
  • Las tareas tienen estado, prioridad, fechas y búsqueda de texto.
  • El contrato de la API separa datos de errores.
  • Las pruebas cubren registro, login, CRUD y propiedad de datos.

Ejemplo real

El proyecto se despliega con Redis como sesión de bloqueo y Nginx por delante. En la entrevista, el candidato explica cómo el refresh token con rotación impide el robo de sesión y cómo el filtro por usuario hace que un bug de búsqueda jamás exponga tareas ajenas. Ese nivel de detalle es el que separa a quien siguió un curso de quien construyó un producto.

  • Guarda el hash de la contraseña, nunca la contraseña.
  • Filtra por usuario en cada consulta, incluso las que parecen globales.
  • Prueba la propiedad de datos: usuario B no ve tareas del usuario A.

Añade una ruta de métricas (número de tareas por estado) para darle un toque analítico.

Explicación

  • La propiedad de datos convierte el CRUD genérico en una API personal.
  • El refresh token con rotación endurece la autenticación.
  • La caché de listados reduce latencia en los recursos calientes.
  • Las pruebas del flujo completo protegen las reglas de negocio.
  • Cada decisión documentada en el ADR vale oro en la entrevista.

Errores comunes

  • Olvidar filtrar por usuario en un endpoint y exponer datos ajenos.
  • Guardar tokens en localStorage de la web y abrir la puerta al XSS.
  • No probar la propiedad de los datos y descubrirlo en una revisión.

Buenas prácticas

  • Estructura por capas: ruta, middleware, servicio y repositorio.
  • Escribe los tests de propiedad de datos primero.
  • Documenta la decisión del refresh token en un ADR.
  • Deja el proyecto desplegado y con datos de ejemplo.

Ejercicio

  1. Implementa el CRUD de tareas con filtro por usuario.
  2. Añade el flujo de refresh con rotación y prueba el logout.
  3. Escribe los tests de propiedad de datos entre dos usuarios.

Resumen

  • La API de tareas junta CRUD, auth, caché y tests en un proyecto acotado.
  • La propiedad de los datos por usuario es la regla que todo endpoint respeta.
  • El refresh token con rotación endurece la autenticación real.
