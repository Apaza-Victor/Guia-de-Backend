Metodologías ágiles

⚙️ Intermedio 9 min Gestión de Proyectos Backend Módulo 1 · Fundamentos de gestión

El manifiesto ágil

En 2001 un grupo de desarrolladores publicó el Manifiesto Ágil, una declaración de principios que reordenó la industria. Sus cuatro valores dan la clave de todo lo que verás en este curso:

  • Individuos e interacciones sobre procesos y herramientas.
  • Software funcionando sobre documentación extensiva.
  • Colaboración con el cliente sobre negociación de contratos.
  • Respuesta ante el cambio sobre seguir un plan rígido.

No significa que los procesos, la documentación o los planes desaparezcan: significa que cuando hay conflicto, gana el lado izquierdo. Para un backend suena raro (¿documentación?), pero detrás está una lógica durísima: lo único que entrega valor es código que corre en producción.

Scrum, Kanban y XP de un vistazo

Hay muchos marcos ágiles, pero tres concentran la mayoría del mercado:

  • Scrum: ciclos fijos llamados sprints (normalmente 1-4 semanas), roles definidos y ceremonias periódicas. Bueno cuando el equipo entrega una porción coherente de producto en cada ciclo.
  • Kanban: flujo continuo visualizado en un tablero con límites de trabajo en curso (WIP). Ideal para equipos de soporte, operaciones o mantenciones donde las prioridades cambian a diario.
  • XP (Extreme Programming): se enfoca en prácticas de ingeniería: TDD, pair programming, integración continua y releases frecuentes. Es la base técnica de muchos equipos backend sin llamarse a sí mismos XP.

No son excluyentes: muchos equipos backend corren iteraciones basadas en Scrum con las prácticas de ingeniería de XP y visualizan tickets al estilo Kanban.

Kanban: el tablero como contrato visual

El corazón de Kanban es limitar el trabajo en curso. Cada columna refleja un estado del ciclo y un límite WIP: si lo superas, no entran más tareas hasta que salgan las que ya están. Que el tablero represente el ciclo real del backend:

{
  "proyecto": "api-pagos",
  "columnas": [
    { "nombre": "Por hacer", "wip": null, "tarjetas": ["WEB-132: webhook de reembolso"] },
    { "nombre": "En desarrollo", "wip": 2, "tarjetas": ["WEB-128: idempotencia", "WEB-130: rate limit"] },
    { "nombre": "En revisión", "wip": 1, "tarjetas": ["WEB-125: secreto en env"] },
    { "nombre": "Listo", "wip": null, "tarjetas": ["WEB-121: migrar a PG 16"] }
  ],
  "regla": "Nadie inicia una tarjeta si su columna 'En desarrollo' ya alcanzó el wip"
}

El límite de WIP no es un capricho: obliga a terminar lo empezado antes de acumular trabajo a medio hacer — el peor enemigo de un backend donde medio-desplegado muere entre dos commits.

Por qué lo ágil le encaja al backend

El backend tiene tres características que hacen del enfoque iterativo una necesidad, no una moda:

  1. La incertidumbre vive en la integración: nadie sabe cuánto costará el enlace con el proveedor de pagos hasta probarlo. Los ciclos cortos miden eso de verdad.
  2. El riesgo es invisible para el usuario: si el frontend se rompe lo ves; si el SQL degrada la base, aparece en silencio en la madrugada. Las iteraciones fuerzan a desplegar seguido y a medir.
  3. Los requisitos técnicos cambian con el contexto: SDKs, versiones, dependencias y APIs externas mutan sin aviso; responder al cambio es parte del oficio.

Aplicarlo no significa «sin plan». Significa planear el siguiente tramo con la mejor información, no el mapa completo de tres años que estará obsoleto a los dos meses.

El flujo de una iteración backend típica

Un ciclo ágil de servidor, de principio a fin, se parece a esto:

# 1) Definición de "terminado" acordada
git checkout -b feat/envio-idempotente

# 2) Test que describe el comportamiento esperado
npx jest tests/unitarios/envio.test.js --watch

# 3) Implementación mínima
# ...código del endpoint con clave de idempotencia en Redis...

# 4) Verificación automatizada + revisión de pares
npm run lint && npm test
git push -u origin feat/envio-idempotente

# 5) Integración continua despliega en staging automáticamente
gh pr create --title "Envío idempotente" --base main

Fíjate en el orden: primero el objetivo verificable (el test), luego el código, después la revisión, y finalmente la entrega progresiva. Cada paso se completa en horas, no en semanas, y produce feedback real (¿el test falla? ¿el PR tiene dudas?).

Las ceremonias que tocan al backend

Según el marco elegido, el equipo se reúne con distintas frecuencias. En un equipo de servidores, las más valiosas suelen ser:

  • Refinamiento: el product owner trae historias; el backend las convierte en tareas técnicas y descubre supuestos ocultos («¿esto se replica a la base de analytics?»).
  • Planificación: se compromete el siguiente bloque de trabajo con capacidad realista.
  • Revisión / demo: se muestra lo desplegado. Si la demo es «docker logs», algo anda mal en tu pipeline.
  • Retrospectiva: de aquí salen las mejoras de proceso (ver módulo 3).

Ejercicio

  1. Dibuja el tablero Kanban de tu proyecto actual (o de uno ficticio) con sus columnas y asigna un límite WIP de 2 a la columna «En desarrollo».
  2. Elige una de las tres metodologías (Scrum, Kanban, XP) y justifica en 3 líneas por qué le conviene a un equipo backend de 4 personas.
  3. Anota las tres prácticas de ingeniería ágil (TDD, CI, pair) que aplicaría tu equipo esta semana y cuál harías primero.

Resumen

  • El Manifiesto Ágil prioriza individuos, software funcionando, colaboración y respuesta al cambio.
  • Scrum usa sprints fijos; Kanban usa flujo continuo con límites de WIP; XP aporta las prácticas de ingeniería.
  • El backend se beneficia del enfoque iterativo por su incertidumbre en integraciones y su riesgo invisible.
  • Lo ágil no elimina el plan: planifica el siguiente tramo con datos reales.
