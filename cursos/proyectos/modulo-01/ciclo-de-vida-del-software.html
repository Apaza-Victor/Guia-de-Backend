Ciclo de vida del software

⚙️ Intermedio 9 min Gestión de Proyectos Backend Módulo 1 · Fundamentos de gestión

Introducción

Se te ocurre una idea (o llega un pedido del negocio), se dibuja un contrato de API, se escribe código, se prueba, se despliega y se opera durante meses. Ese recorrido tiene una estructura repetible que llamamos ciclo de vida del software: el conjunto de fases por las que pasa un producto desde que es una intención hasta que vive —y muere— en producción.

Entenderlo es la primera habilidad de gestión de un backend: te permite saber en qué fase estás, qué información te falta y quién debe aportarla. El código es solo una parte del camino.

Las fases clásicas

El modelo en cascada (waterfall) propone avanzar en línea recta de una fase a la siguiente. Meramente entenderlo basta para ubicarte, aunque hoy casi nadie lo ejecuta al pie de la letra:

  1. Requerimientos: qué debe hacer el sistema, con qué reglas y para quién.
  2. Diseño: arquitectura, modelo de datos y contratos entre componentes.
  3. Desarrollo: implementación — en backend, la API, los workers, las integraciones.
  4. Pruebas: verificación funcional y no funcional del sistema completo.
  5. Despliegue: publicación en el entorno de producción.
  6. Operación y mantenimiento: monitoreo, bugs, evoluciones y retirada.

En la práctica el software moderno itera sobre estas fases en ciclos cortos. El backend participa en todas: aclara requerimientos técnicos en la fase 1, decide la base de datos en la 2, programa en la 3, escribe pruebas de servicio en la 4, automatiza el despliegue en la 5 y atiende alertas en la 6.

Cada fase tiene entradas y salidas

Una manera práctica de pensar el ciclo es como una cadena de artefactos: cada fase consume algo material (un documento, un esquema, un commit) y produce otro artefacto que alimenta la siguiente. Si un artefacto no existe, la fase siguiente se enamora de supuestos.

Por ejemplo, en un proyecto backend típico, el contrato de la API es el artefacto puente entre diseño y desarrollo. Establecerlo temprano evita que el frontend y el backend construyan cada uno sus propias reglas:

{
  "openapi": "3.0.3",
  "info": { "title": "API de pagos", "version": "1.0.0" },
  "paths": {
    "/v1/cargos": {
      "post": {
        "summary": "Crear un cargo",
        "requestBody": {
          "required": true,
          "content": {
            "application/json": {
              "schema": {
                "type": "object",
                "required": ["monto", "moneda", "referencia"],
                "properties": {
                  "monto": { "type": "integer" },
                  "moneda": { "type": "string", "enum": ["PEN", "USD"] },
                  "referencia": { "type": "string" }
                }
              }
            }
          }
        },
        "responses": {
          "201": { "description": "Cargo creado" },
          "422": { "description": "Datos inválidos" }
        }
      }
    }
  }
}

Ese mismo contrato se convierte después en la base de las pruebas de integración y de la documentación para el equipo que consume la API.

¿Qué hace el backend en cada fase?

Aterricemos las fases con responsabilidades concretas de un equipo de servidores:

  • Requerimientos: convertir reglas de negocio en historias técnicas. Ejemplo: «el usuario no puede rebasar su línea de crédito» debe traducirse en una validación transaccional en servidor, no en el formulario.
  • Diseño: elegir stack, modelar entidades, planear índices y decidir qué lógica vive en la base y cuál en la aplicación.
  • Desarrollo: escribir endpoints, consumidores de colas, migraciones y todo lo que corre fuera del navegador.
  • Pruebas: testear con datos reales, medir rendimiento y validar los casos borde que el frontend no puede cubrir.
  • Operación: leer logs, revisar métricas, escalar y corregir defectos descubiertos por los usuarios.

Regla práctica: si en tu equipo nadie puede responder «¿en qué fase estamos?», el proyecto ya está en modo cascada accidental: mucho trabajo al inicio, cero retroalimentación y una entrega gigante al final.

La evolución del modelo: iterar en vez de caminar en fila

El problema del ciclo lineal es que descubre los errores demasiado tarde. La respuesta ágil fue recorrer el ciclo completo en pequeñas porciones: requerimientos parciales, un diseño ligero, una implementación pequeña que se prueba y se entrega, y de nuevo. Así el costo de una suposición equivocada en la fase 1 se paga en días, no en meses.

Un backend iterativo organiza el trabajo en incrementos que puedan ponerse en producción de forma independiente. Un ejemplo de plan básico de un incremento:

# Incremento 1 — infraestructura base
git init
docker compose up -d postgres redis
npx prisma migrate dev --name inicio

# Incremento 2 — primer flujo de negocio (autenticación)
npx prisma migrate dev --name identificacion
npx jest auth --coverage

# Incremento 3 — facturación con validación de saldo
npx prisma migrate dev --name facturacion
npx k6 run tests/carga/cobros.js

Cada comando representa un mini-ciclo completo: diseño (migración), desarrollo (feature), verificación (tests y prueba de carga). Al final tienes algo desplegable, no un repositorio a medio construir.

Gestionar el ciclo en un equipo real

Gestionar el ciclo de vida no es burocrático: es sincronizar artefactos. Concretamente:

  1. Mantén un único documento vivo de requerimientos (backlog), no un PDF congelado.
  2. Acuerda el contrato de la API antes de empezar el código; evolucionarlo después cuesta caro.
  3. Automatiza cada fase que se repita: migraciones, tests, despliegues.
  4. Define la definición de «terminado» y aplícala igual a cada incremento.

Ejercicio

  1. Toma un proyecto backend que conozcas y enumera las 6 fases del ciclo, señalando en qué fase está ahora mismo.
  2. Identifica el artefacto «puente» que conecta el diseño con el desarrollo (contrato OpenAPI, migración, esquema) y verifica si está documentado en el repositorio.
  3. Escribe los comandos de un mini-ciclo completo (migración + test + deploy) para una feature nueva que te gustaría agregar.

Resumen

  • El ciclo de vida del software recorre requerimientos, diseño, desarrollo, pruebas, despliegue y operación.
  • Cada fase consume y produce artefactos; el contrato de API es el puente típico entre diseño y desarrollo del backend.
  • El modelo en cascada descubre errores tarde; el enfoque iterativo repite el ciclo en incrementos pequeños.
  • El backend participa en todas las fases, desde aclarar reglas hasta operar y escalar lo construido.
