Requerimientos y aclaraciones

⚙️ Intermedio 9 min Gestión de Proyectos Backend Módulo 1 · Fundamentos de gestión

El costo oculto de las suposiciones

El backend traduce intenciones de negocio a reglas rigurosas: validaciones, transacciones, estados, concurrencia. Si una intención llega vaga («que el usuario pueda cancelar su compra»), el equipo llena los huecos por su cuenta y cada suposición es una potencial catástrofe:

  • ¿Qué pasa si el pago ya fue cobrado por el banco?
  • ¿La cancelación debe funcionar para compras en proceso de envío?
  • ¿Reembolso automático o manual con aprobación?
  • ¿Qué hace el endpoint si la tienda ya cerró el pedido del día?

Cuanto más tarde descubras que respondiste mal una de estas, más caro es arreglarlo. Por eso, el refinamiento de requerimientos es una conversación: el PO trae lo que quiere, el equipo devuelve preguntas, y la respuesta se vuelve regla escrita.

User stories: el formato mínimo

Una user story es una descripción corta de una funcionalidad contada desde el valor que produce, no desde su implementación. La plantilla clásica es «Como persona, quiero algo, para beneficio»:

{
  "id": "PYM-220",
  "como": "responsable de tienda",
  "quiero": "cancelar una compra pagada por tarjeta",
  "para": "devolver el dinero sin intervención manual",
  "estado": "listo para desarrollo",
  "criterios_de_aceptacion": [
    "Si la compra está pagada, cancelarla dispara un reembolso automático",
    "Si el reembolso falla, la compra queda en estado 'reembolso_pendiente'",
    "Un comprobante de cancelación se emite y se envía por email",
    "Cancelar una compra ya cancelada devuelve el mismo comprobante sin reembolsar dos veces"
  ]
}

Tres trampas frecuentes con las stories: escribirlas como soluciones («montar una tabla de cancelaciones» — el equipo debe decidir eso), hacerlas gigantes (deben caber en un sprint) y saltarse los criterios de aceptación (las reglas que convierten la intención en algo verificable).

Criterios de aceptación: lo exclusivamente comprobable

Un criterio de aceptación es una declaración verificable: se cumple o no se cumple. El formato más usado es Dado/Cuando/Entonces (Given/When/Then), que describe precondición, acción y resultado. Su belleza es que se traduce directamente a tests:

const request = require('supertest');
const app = require('../src/app');

describe('Cancelar compra', () => {
  it('reembolsa automáticamente cuando la compra está pagada', async () => {
    const api = request(app);

    // Dado: existe una compra pagada por tarjeta
    const compra = await api.post('/api/compras').send({ id: 'C-401', medio: 'tarjeta' });
    expect(compra.body.estado).toBe('pagada');

    // Cuando: el responsable la cancela
    const resp = await api.post('/api/compras/C-401/cancelar').send({ motivo: 'devolución' });

    // Entonces: se emite reembolso y la compra cambia de estado
    expect(resp.status).toBe(200);
    expect(resp.body.estado).toBe('reembolso_solicitado');
    expect(resp.body.comprobante).toMatch(/^RMB-/);
  });

  it('no reembolsa dos veces una compra ya cancelada', async () => {
    await request(app).post('/api/compras/C-402/cancelar');
    const segunda = await request(app).post('/api/compras/C-402/cancelar');
    expect(segunda.status).toBe(409);
  });
});

Cuando el criterio está escrito así, el test deja de ser una tarea post-desarrollo y se vuelve el contrato que define cuándo la historia está terminada.

Las preguntas de aclaración que salvan semanas

Hay preguntas que todo backend debe hacer antes de aceptar una historia. Un buen listado de partida:

  1. Volumen y latencia: ¿cuántas operaciones por segundo esperamos? ¿Qué latencia es aceptable?
  2. Consistencia: ¿este dato puede leerse eventualmente consistente o debe ser estricto?
  3. Puntos de integración: ¿qué servicios externos participan y quién los prueba?
  4. Casos de fallo: ¿qué hacemos si el proveedor de pagos cae a mitad de proceso?
  5. Observabilidad: ¿qué queremos medir al desplegar esta feature?
  6. Seguridad y acceso: ¿quién puede ejecutar esto y qué datos expone?

No todas aplican a todas las historias, pero responderlas juntas es el refinamiento que el backend aporta al negocio. Es la diferencia entre «implementar» y entender lo que se implementa.

Definition of Ready y el ticket que siempre rebota

Para que el desarrollo no arranque con vicio, muchos equipos usan una Definition of Ready (DoR): el checklist que una historia debe cumplir antes de entrar a un sprint. Si falla la DoR, la historia vuelve al refinamiento:

# Definition of Ready: la historia solo entra al sprint si
git check-ignore .  # trivial, solo para que puedas bater el flujo

# [ ] Tiene valor claro y un dueño que responde preguntas
# [ ] Tiene criterios de aceptación verificables (no "se ve bien")
# [ ] Los casos de fallo del proveedor/integración están definidos
# [ ] Las reglas de consistencia y volumen están acordadas
# [ ] Su estimación es viable en un sprint (≤ 13 puntos)
# [ ] El contrato o payload esperado está esbozado

echo "Si no se cumple todo lo anterior, no se planifica: se refina."

Cuidado: la DoR no es burocracia para frenar trabajo. Es un filtro para que el previsible endurecimiento no pase a través del costo que produce: flujo detenido, contexto perdido y PQRS.

Ejercicio

  1. Convierte «el usuario quiere recuperar su contraseña» en una user story con 4 criterios de aceptación verificables.
  2. Aplica el formato Dado/Cuando/Entonces a uno de esos criterios y transfórmalo en un test de ejemplo (puedes sketchearlo en JS).
  3. Escribe 5 de las 6 preguntas de aclaración que le harías a tu PO sobre esa historia, enfocadas en seguridad y fallos.

Resumen

  • Un requerimiento vago se convierte en suposiciones peligrosas; refinarlos es una conversación, no un trámite.
  • Las user stories describen valor con criterios de aceptación verificables.
  • Dado/Cuando/Entonces permite traducir cada criterio a un test automatizado.
  • La DoR filtra las historias no listas: volumen, consistencia, fallos y seguridad se acuerdan antes del sprint.
