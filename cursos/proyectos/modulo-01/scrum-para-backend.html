Scrum aplicado a backend

⚙️ Intermedio 9 min Gestión de Proyectos Backend Módulo 1 · Fundamentos de gestión

Qué es Scrum

Scrum es un marco de trabajo para desarrollar, entregar y sostener productos complejos sobre ciclos cortos llamados sprints. No prescribe cómo programar: prescribiría la caja de ritmo que obliga al equipo a planear, ejecutar, inspeccionar y adaptarse cada pocas semanas.

Para un equipo de backend, el sprint es el «pulso» del proyecto: define qué se promete, cuánto se entrega y qué tan rápido se adquiere feedback real del producto.

Los tres roles

  • Product Owner (PO): dueño del backlog y del valor de negocio. Decide prioridades y aclara el «para qué». No necesariamente sabe SQL ni Docker, y no hace falta.
  • Scrum Master: cuidador del proceso. Quita bloqueos, facilita ceremonias y protege al equipo de compromisos imposibles. A veces rota entre miembros.
  • Equipo de desarrollo: backend, DevOps, QA técnico. Son auto-organizados: el equipo decide cómo se cumple el compromiso del sprint.

La frontera entre roles es donde más se aprende en un backend: el PO sabe que «notificaciones push» tardan, pero no porque sí; el equipo sabe explicarle el porqué (proveedor, certificados, colas) sin tecnicismos inútiles.

Las ceremonias: qué pasa en cada una

  1. Sprint Planning: el equipo elige un compromiso alcanzable del backlog y lo descompone en tareas. Planear es la única forma de saber si el sprint cabe.
  2. Daily: reunión corta (15 min) de sincronización: qué hice, qué haré, qué me bloquea. No es un reporte al jefe; es un radar de riesgos.
  3. Sprint Review: demostración y ajuste del producto con el PO. En backend, el criterio es «lo que se pudo desplegar», no «lo que se programó».
  4. Retrospectiva: mejora del proceso. Aquí salen decisas como «probemos trunk-based» o «reduzcamos el WIP».

El detalle poco obvio: las ceremonias son inspección y adaptación. Si una se repite sin producir cambios, deja de ser útil y el equipo debe ajustarla o eliminarla.

Historias técnicas: cuando el usuario es el sistema

No todo es una user story dirigida a un cliente. El backend tiene trabajo que beneficia al producto pero no al usuario final directamente: migraciones, índices, integraciones, refactors, seguridad. En Scrum estas se agregan al backlog igual que cualquier otra y se negocian con el PO.

    { "id": "PYM-216", "tipo": "tecnica", "titulo": "Spike: latencia del CDN en uploads", "puntos": 2 },
    { "id": "PYM-217", "tipo": "deuda", "titulo": "Migrar cliente HTTP a retries con backoff", "puntos": 5 },
    { "id": "PYM-218", "tipo": "bug", "titulo": "Corregir doble cargo por retry sin idempotencia", "puntos": 8 }
  ]
}

Spike: una historia de investigación acotada en el tiempo. Sirve para responder una pregunta técnica (¿funciona el SDK? ¿cuánto cuesta esa API? ¿qué orden de magnitud tiene?) y es honesta: su entregable es información, no código.

Definición de Terminado para backend

La Definición de Terminado (DoD) es el contrato invisible del sprint: los criterios que una historia debe cumplir para contarse como entregada. Un DoD típico a nivel de servidor incluye:

# Definición de Terminado (DoD) del equipo backend
# [ ] Código revisado en PR por al menos un par
# [ ] CI verde (lint + tests unitarios + tests de integración)
# [ ] Migración de base de datos versionada y aplicada en staging
# [ ] Cobertura del flujo crítico con test de integración
# [ ] Documentación del endpoint/contrato actualizada
# [ ] Desplegado en staging y verificado con datos reales
# [ ] Sin secretos en el repositorio (revisión de .env*)

# Verificación rápida en la terminal
git diff --name-only --diff-filter=AM '*.env*' . | xargs -I{} echo "revisar: {}"
npm run lint && npm test && npm run test:integration

La potencia de una DoD escrita es que evita las discusiones de fin de sprint: «¿"listo" es que probaste el endpoint o que lo desplegaste?». Respondido de antemano.

Medir el ritmo con la velocidad

Al terminar el sprint se suman los puntos efectivamente completados. Esa cifra —la velocidad— es la materia prima del planning siguiente: si tu equipo promedia 34 puntos con 5 personas, comprometerse a 60 es futuro doom.

velocidades = [34, 38, 31, 36, 33]

def proyeccion(velocidades, sprints_restantes):
    promedio = sum(velocidades) / len(velocidades)
    return promedio * sprints_restantes

# La velocidad es histórica, no una promesa moral
print(proyeccion(velocidades, sprints_restantes=4))  # ~137 puntos

La velocidad es un dato estadístico, no un KPI para castigar al equipo. Si usas el gráfico como vara, el equipo subestimará y perderá tu dato más valioso.

Ejercicio

  1. Escribe el backlog de un sprint propio con al menos 6 items y sepáralos por tipo: historia, técnica, deuda y bug.
  2. Redacta la Definición de Terminado de tu equipo en 7 puntos, incluyendo verificación real (CI, staging, revisión de secretos).
  3. Calcula la velocidad promedio de 4 sprints pasados y decide cuántos puntos puedes comprometer para el próximo.

Resumen

  • Scrum estructura el trabajo en sprints con roles definidos y ceremonias de inspección y adaptación.
  • El equipo backend también pone historias técnicas, spikes y deuda en el backlog y las negocia con el PO.
  • La Definición de Terminado evita discusiones: establece qué significa «listo» para código de servidor.
  • La velocidad histórica guía el planning del siguiente sprint; se usa como dato, no como castigo.
