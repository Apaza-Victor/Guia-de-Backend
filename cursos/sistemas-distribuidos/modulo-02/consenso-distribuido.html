Consenso distribuido

🚀 Avanzado 10 min Sistemas Distribuidos Módulo 2 · Replicación y consistencia

Introducción

El consenso es el problema de lograr que varios nodos se pongan de acuerdo sobre un valor, incluso cuando algunos fallan. Suena simple, pero el teorema de FLP demostró que, en un sistema asíncrono, es imposible garantizar consenso con fallos no detectables. Por eso los algoritmos reales usan hipótesis pragmáticas: timeouts y mayorías.

El problema del consenso

  • Acuerdo: todos los nodos correctos deciden el mismo valor.
  • Validez: el valor decidido fue propuesto por algún nodo.
  • Terminación: los nodos correctos eventualmente deciden.

Si un nodo cae y se reinicia, o si la red divide el cluster, queremos que todos sigan decidiendo lo mismo. La herramienta práctica es el quórum de mayoría: una decisión no se cierra hasta que la confirman más de la mitad de los nodos.

Raft: el consenso didáctico

Raft divide el problema en tres subproblemas: elección de líder, replicación de log y seguridad.

  1. Cada nodo está en estado líder, seguidor o candidato.
  2. El tiempo se parte en términos; cada término puede tener un líder.
  3. Los seguidores esperan latidos (heartbeats) del líder. Si expira un election timeout aleatorio, el seguidor pasa a candidato, pide votos y gana si obtiene mayoría.
  4. El líder recibe las escrituras, las escribe en su log y las replica; una entrada del log se commite cuando la mayoría la confirma.

El truco del timeout aleatorio evita que dos candidatos gocen todos los votos y se peleen eternamente (aunque pueden empate y hay que repetir).

Raft en código simplificado

Este esqueleto (Node.js) captura el «heartbeat que renueva el mandato»:

const ESTADOS = { SEGUIDOR: 0, CANDIDATO: 1, LIDER: 2 };

class NodoRaft {
  constructor(id, peers) {
    this.id = id;
    this.peers = peers;
    this.estado = ESTADOS.SEGUIDOR;
    this.term = 0;
    this.ultimoLatido = Date.now();
    this.electionTimeout = 150 + Math.random() * 150; // ms aleatorio
  }

  // Seguidor: si no llega latido del líder, lanza elección
  tick() {
    if (this.estado === ESTADOS.SEGUIDOR &&
        Date.now() - this.ultimoLatido > this.electionTimeout) {
      this.estado = ESTADOS.CANDIDATO;
      this.term += 1;
      this.votarPorMiMismo();
    }
  }

  recibirLatido(termLider) {
    if (termLider < this.term) return; // ignorar líder de término viejo
    this.term = termLider;
    this.estado = ESTADOS.SEGUIDOR;
    this.ultimoLatido = Date.now();
  }
}

La decisión «cuál es el líder» y las escrituras aprobadas quedan en un log replicado: cada entrada con su término, confirmada por la mayoría:

Paxos: el abuelo

Paxos (Lamport, 1990) resuelve el mismo problema con dos fases (prepare y accept) y propositores que compiten. Es elegante pero notoriamente difícil de implementar; la mayoría de sistemas modernos (etcd, Consul, TiKV, CockroachDB) usa Raft o variantes.

# etcd implementa Raft y expone un API mínima de consenso:
etcdctl put "clave-distribuida" "v1"        # escribe a través del líder
etcdctl get "clave-distribuida"             # lee con tupla de consenso
etcdctl endpoint status --write-out=table   # término y líder actuales

Elección de líder en la práctica

En un sistema con un único líder, la elección es consenso. Los equivalentes comerciales:

  • PostgreSQL: failover con repmgr/Patroni (que a su vez usa etcd o ZooKeeper).
  • Kafka: cada partición elige un líder entre sus réplicas con su propio protocolo (KRaft).
  • Redis Cluster: la promoción de réplicas usa votos con majority.

El objetivo siempre es el mismo: que ante la muerte del líder actual, exactamente uno nuevo tome el control, sin split-brain.

Split-brain: dos líderes vivos en el mismo clúster escribiendo a la vez. La mayoría de quórum (más de N/2 nodos) es lo que impide elegir dos líderes.

Limitaciones y costes

El consenso garantiza seguridad (acuerdo y validez) a costa de la liveness bajo fallos: si pierdes mayoría, el sistema se detiene hasta recuperarla. Además, cada decisión exige una ida y vuelta de mensajes; por eso el consenso por operación es caro y se usa solo en operaciones críticas.

Ejercicio

  1. Con 5 nodos que implementan Raft, ¿cuántos deben aprobar una escritura para commit? ¿Cuántos pueden caer sin frenar el sistema?
  2. Explica con tus palabras por qué un «election timeout aleatorio» reduce la probabilidad de que dos candidatos se peleen por el liderazgo.
  3. Investiga y describe qué pasa en etcd cuando el número de nodos caídos supera la mayoría (quorate lost).

Resumen

  • El consenso logra acuerdo, validez y terminación entre nodos con fallos.
  • La mayoría de quórum es el mecanismo que impide dos líderes (split-brain).
  • Raft divide el problema en elección de líder, replicación de log y seguridad; usa términos y timeouts aleatorios.
  • Paxos fue el primer algoritmo famoso, pero Raft es el que implementan etcd, Consul y otros.
