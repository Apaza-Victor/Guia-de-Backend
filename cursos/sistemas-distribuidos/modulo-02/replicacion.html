Replicación de datos

🚀 Avanzado 10 min Sistemas Distribuidos Módulo 2 · Replicación y consistencia

Introducción

La replicación consiste en mantener varias copias de los mismos datos en distintas máquinas. Por qué: disponibilidad (si un nodo cae, queda otro), tolerancia a fallos (no hay punto único de fallo) y rendimiento (las lecturas se reparten entre réplicas).

La pregunta central es cómo se propagan los cambios entre copias. Hay tres grandes familias de modelos y cada una responde distinto a esa pregunta.

Leader-follower (un solo líder)

El modelo más extendido (PostgreSQL, MySQL, MongoDB, Kafka). Reglas:

  • Solo el líder acepta escrituras.
  • Los seguidores replican el log del líder y sirven lecturas.
  • Si el líder muere, un seguidor se promueve (failover) mediante elección o configuración.

Ventajas: es simple y evita conflictos de escritura. Desventaja: si el líder cae y el failover es manual, hay tiempo de inactividad; y si la promoción es automática pero torpe, se corre el riesgo de «líder y ex-líder» escribiendo a la vez.

# docker-compose: PostgreSQL con réplica de lectura (leader-follower)
services:
  pg-leader:
    image: postgres:16
    environment:
      POSTGRES_DB: app
      POSTGRES_REPLICATION: "true"
    ports: ["5432:5432"]

  pg-replica:
    image: postgres:16
    command: |
      bash -c "pg_basebackup -h pg-leader -D /var/lib/postgresql/data -R
               && docker-entrypoint.sh postgres"
    depends_on: [pg-leader]
    ports: ["5433:5432"]

Las aplicaciones suelen escribir al líder y leer de las réplicas para no saturarlo:

// En la práctica cada pool apunta a un host distinto
const poolEscritura = new Pool({ host: "pg-leader" });   // solo escrituras
const poolLectura  = new Pool({ host: "pg-replica" });   // solo lecturas

async function crearUsuario(usuario) {
  // Escritura al líder
  const { rows } = await poolEscritura.query(
    "INSERT INTO usuarios (nombre) VALUES ($1) RETURNING id",
    [usuario.nombre]
  );
  return rows[0].id;
}

async function listarUsuarios() {
  // Lectura a la réplica: puede verse un usuario que aún no ha llegado
  const { rows } = await poolLectura.query("SELECT nombre FROM usuarios");
  return rows;
}

Multi-leader

Varios nodos aceptan escrituras (por ejemplo, uno por zona geográfica) y se replican entre sí. Útil cuando hay usuarios por región (escritura local, baja latencia) o estructuras tipo CRDT con edición offline.

  • Ventaja: alta disponibilidad de escritura y baja latencia local.
  • Desventaja: conflictos de escritura entre líderes (ej.: dos líderes modifican el mismo registro a la vez). Hay que decidir cómo resolverlos: last-writer-wins, fusión de valores, o guardar versiones.

Suele aparecer en Git (cada repo es un «líder»), en editores colaborativos y en despliegues multiregionales de ciertas bases.

Leaderless

Aquí no hay líder ni seguidores: cualquier nodo acepta lecturas y escrituras, y el cliente habla con varios a la vez (quórum). Modelo popularizado por DynamoDB y adoptado por Cassandra, Riak y Voldemort.

Elimina el punto único de fallo de escritura, pero sin un líder pasa a ser responsabilidad del cliente leer de varios nodos y del sistema reconciliar versiones divergentes — el tema de la próxima lección y de relojes vectoriales.

Síncrona vs asíncrona

  • Replicación síncrona: el líder espera confirmación del seguidor antes de responder al cliente. Consistencia fuerte, pero si el seguidor cae, la escritura se bloquea.
  • Replicación asíncrona: el líder responde y replica después. Rápida, pero hay un retraso y riesgo de perder escrituras si el líder cae antes de propagar.

Los sistemas suelen combinar ambas: un seguidor síncrono (para no perder datos) y el resto asíncronos (para no frenar). El retraso de las réplicas asíncronas se llama replication lag y produce lecturas desactualizadas.

El costo del replication lag

Cuando una réplica va lenta, un usuario puede hacer una escritura y «no verla» en la siguiente lectura. Es el famoso patrón read-your-own-writes: si distribuyes lecturas entre réplicas sin más control, tu propio guardado puede «desaparecer».

Mitigaciones habituales: enrutar las lecturas del usuario recién escrito al líder, usar sesiones pegajosas, o aceptar el lag para datos no críticos. La lección siguiente (quórums) ofrece el control fino de consistencia.

# Mitigación read-your-own-writes: el creador lee del líder siempre
def leer_perfil(usuario_id, es_autor):
    if es_autor:
        # las lecturas del propio usuario van al líder
        return bd_lectura_leader.obtener(usuario_id)
    # el resto reparte entre réplicas
    return bd_lectura_replica.obtener(usuario_id)

Ejercicio

  1. Para tu base de datos actual identifica el modelo de replicación (leader-follower, multi-leader o leaderless) y si usa replicación síncrona o asíncrona.
  2. Diseña un flujo «escríbo mi perfil y lo leo al instante» utilizando la estrategia read-your-own-writes y explícalo con un diagrama de flechas.
  3. Responde: ¿por qué la replicación asíncrona puede perder escrituras si el líder cae a la vez?

Resumen

  • La replicación da disponibilidad y reparte lecturas, pero introduce el problema de propagar los cambios.
  • Leader-follower: un líder escribe y los seguidores replican; es el modelo más común.
  • Multi-leader escala escrituras por región a costa de conflictos que hay que resolver.
  • Leaderless: cualquier nodo escribe; el cliente gestiona el quórum de lecturas/escrituras.
  • La replicación asíncrona produce lag y lecturas desactualizadas que hay que saber mitigar.
