Transacciones distribuidas

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 2 · Replicación y consistencia

Introducción

Cuando una operación de negocio toca varios servicios o varias bases, un COMMIT local ya no es suficiente: no puedes «hacer commit» en dos bases a la vez con la garantía ACID clásica. Aparecen las transacciones distribuidas. Hay dos grandes familias: el protocolo 2PC (fuerte, bloqueante) y las sagas (débiles, sin bloqueos).

Two-phase commit (2PC)

Un coordinador dirige a varios participantes:

  1. Fase de preparación (votar): el coordinador pregunta a cada participante «¿puedes preparar?». Cada uno responde sí o abort, sin hacer commit todavía.
  2. Fase de commit (decidir): si todos dijeron que sí, el coordinador ordena commit a todos; si alguien aborta, ordena rollback a todos.
{
  "coordinador": "servicio-pagos",
  "participantes": ["bd-pagos", "bd-inventario", "bd-envios"],
  "fase_1": {
    "estado": "prepare",
    "votos": { "bd-pagos": "si", "bd-inventario": "si", "bd-envios": "si" }
  },
  "fase_2": { "decision": "commit", "estado": "todos_confirman" }
}

Su talón de Aquiles: si el coordinador muere después de la fase 1, los participantes quedan bloqueados en preparado sin saber si deben commitear o abortar, hasta que llegue un reemplazo. Por eso 2PC escalar mal en arquitecturas de microservicios modernas.

Sagas: transacciones sin bloqueo

Una saga divide la operación en pasos locales, cada uno con su propia transacción ACID, y prevé un paso compensatorio para deshacer cada uno:

  • Orquestación: un coordinador «coreógrafo» guía el flujo llamando a cada servicio y sus compensaciones. Es fácil de seguir, pero el coordinador se vuelve un punto central.
  • Coreografía: cada servicio publica eventos y reacciona a eventos de otros. Sin coordinador; el flujo se ve en los eventos, pero se dispersa y es más difícil de trazar.

El truco está en el patrón de compensación: cada paso debe saber cómo deshacerse (la reserva con su cancelación, la transferencia con su reversa, etc.).

Saga orquestada en código

class OrquestadorPedido:
    PASOS = [
        (crear_pedido, cancelar_pedido),
        (cobrar_pago,  reembolsar_pago),
        (reservar_inventario, liberar_inventario),
        (programar_envio, cancelar_envio),
    ]

    def ejecutar(self, datos):
        hechos = []
        for paso, compensacion in self.PASOS:
            try:
                paso(datos)
                hechos.append(compensacion)
            except Exception as exc:
                # rollback en orden inverso: compensamos lo ya hecho
                for comp in reversed(hechos):
                    comp(datos)
                raise SagaRota(exc)

        return {"estado": "pedido_completado"}

Observa el detalle clave: los pasos compensatorios se ejecutan en orden inverso al de producción.

Saga coreografiada con eventos

En la variante coreografiada, cada servicio reacciona a eventos. Aquí, un servicio escucha el evento de pago y actúa en consecuencia:

// Consumidor del servicio de inventario (coreografía)
colas.consume("eventos.pedido", (evento) => {
  switch (evento.tipo) {
    case "pedido.creado":
      reservar(evento.producto, evento.cantidad);   // paso
      emitir("inventario.reservado", evento);        // sigue el flujo
      break;
    case "pago.fallido":
      liberar(evento.producto, evento.cantidad);     // compensación
      emitir("inventario.liberado", evento);
      break;
  }
});

La cadena de eventos es el «ADN» del flujo: si un paso falla, el evento de fallo dispara compensaciones escalonadas en cada servicio.

¿2PC o saga?

Criterio2PCSaga
ConsistenciaFuerte (todas o ninguna)Eventual (compensable)
BloqueosSí, al quedarse en preparadoNo; cada paso es local
LatenciaAlta con pocos nodosBaja, pasos paralelos posibles
Casos idealesPocos sistemas homogéneosMicroservicios heterogéneos y colas

La industria moderna tiende a las sagas: no se bloquea, se compensa. Pagos incluidos — «el dinero se reversa». Antes de elegir, pregunta: ¿el negocio tolera ver el pedido «en proceso» un rato?

Ejercicio

  1. Toma «comprar en una tienda online» y lista sus pasos con su compensación (pedido, pago, inventario, envío).
  2. Describe el mismo flujo primero como orquestación y luego como coreografía; ¿en qué cambia la trazabilidad?
  3. Explica por qué 2PC puede «bloquear» recursos indefinidamente y por qué una saga solo los libera con compensación.

Resumen

  • 2PC ofrece atomicidad total con dos fases, pero bloquea nodos y escala mal.
  • Las sagas dividen la operación en pasos locales con compensaciones.
  • La compensación se ejecuta en orden inverso a los pasos realizados.
  • La orquestación centraliza el flujo; la coreografía lo dispersa en eventos.
