Teorema CAP

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 1 · Fundamentos

Introducción

El teorema CAP, formulado por Eric Brewer en el 2000 y demostrado por Seth Gilbert y Nancy Lynch en 2002, afirma que un sistema distribuido con datos replicados no puede garantizar simultáneamente Consistencia (C), Disponibilidad (A) y Tolerancia a particiones (P). Durante una partición de red, tienes que elegir entre C y A.

Interpretarlo bien es la diferencia entre tomar decisiones de arquitectura con criterio o memorizar «elige 2 de 3».

Las tres propiedades

  • Consistencia (C): todas las lecturas devuelven la última escritura confirmada. Todo cliente ve el mismo valor al mismo tiempo, como una única copia.
  • Disponibilidad (A): cada petición (lectura o escritura) recibe una respuesta no errónea, aunque sea con datos viejos. El sistema nunca «ignora» una petición durante la partición.
  • Tolerancia a particiones (P): el sistema sigue funcionando aunque la red se divida en dos (o más) grupos que no pueden comunicarse entre sí. En Internet, la partición es inevitable.

Clave: la partición de red no es un fallo raro; es una condición permanente del mundo real (latencia, caídas de enrutadores, zona de disponibilidad caída). Por eso, en la práctica, siempre debemos tolerar P, y la decisión real es «durante una partición, ¿prefieres CP o AP?».

Qué decidimos realmente

Cuando la red funciona, puedes dar C + A. El dilema aparece en la partición:

  • Sistema CP (consistencia ante disponibilidad): ante una partición, el lado minoritario deja de responder (sacrifica A) para no servir datos viejos. Ejemplos: etcd, ZooKeeper, HBase, PostgreSQL con conmutación, Redis Cluster en modo estricto.
  • Sistema AP (disponibilidad ante consistencia): ambos lados siguen sirviendo (sacrifica C), y el conflicto se resuelve después con reconciliación. Ejemplos: Cassandra, CouchDB, DynamoDB (en modo eventual), S3 en modo eventual.

Simulación de una partición

Observa la diferencia entre ambas políticas en código. Dos nodos se quedan incomunicados; uno decide rechazar la escritura (CP) y el otro aceptarla con riesgo (AP):

def escribir(nodo, clave, valor, politica):
    if politica == "CP":
        # Si no alcanzo quórum de la otra mitad, niego la escritura
        if not nodo.quorum_disponible():
            return {"status": 503, "body": "No hay quórum: se rechaza la escritura"}
    elif politica == "AP":
        # Acepto y prometo reconciliar después (stale read posible)
        nodo.guardar_local(clave, valor)
        return {"status": 200, "body": "Escrito en local; pendiente de sincronizar"}

# durante la partición, cada lado llamaría a escribir() con su política

Configuración real de cada política

Bases como Cassandra permiten elegir el nivel de consistencia por operación. Fíjate en cómo QUORUM fuerza C (más lento) y ONE optimiza A (con datos posiblemente viejos):

# Cassandra: política fuerte (CP) - espera confirmación de quórum
cqlsh -e "CONSISTENCY QUORUM;
INSERT INTO usuarios (id, nombre) VALUES (100, 'Ana García');"

# Cassandra: política débil (AP) - una sola réplica confirma
cqlsh -e "CONSISTENCY ONE;
SELECT * FROM usuarios WHERE id = 100;"

Estos niveles se declaran también desde la aplicación. Así quedaría registrado en la configuración de un servicio:

{
  "cluster": "catalogo",
  "duracion_lectura": "QUORUM",
  "duracion_escritura": "LOCAL_QUORUM",
  "comentario_politica": "CP durante lecturas críticas; AP permitido en analytics",
  "consistencia_diagnostica": { "en_dudoso": "rechazar" }
}

Elegir entre CP y AP

No existe la «mejor» opción; existe la correcta para el negocio:

  • Un saldo bancario o un inventario estricto suele querer CP: un error de consistencia es peor que una caída momentánea.
  • Un carrito de compras, un feed o un contador de «me gusta» suelen tolerar AP: mejor responder con datos un poco viejos que fallar.

Y recuerda: el CAP habla de la partición, no del rendimiento. Latencia y «consistencia eventual» son temas aparte (ver siguiente lección).

Ejercicio

  1. Elige tres sistemas que uses habitualmente (bases, cachés, colas) y clasifica cada uno como CP o AP durante una partición.
  2. Propón un caso de negocio donde prefieras AP y otro donde prefieras CP, y justifica por qué en una frase.
  3. Diseña una simulación por escrito: dos nodos replican el stock de un producto. Describe qué ve un cliente si el sistema es CP y qué ve si es AP cuando la red se parte.

Resumen

  • CAP: consistencia, disponibilidad y tolerancia a particiones; no se pueden lograr las tres a la vez durante una partición.
  • La partición es inevitable en Internet: siempre se elige entre CP y AP en esos momentos.
  • CP sacrifica disponibilidad para no servir datos viejos; AP sacrifica consistencia para seguir respondiendo.
  • Los niveles de consistencia por operación (QUORUM, ONE) materializan esa elección en sistemas reales como Cassandra.
