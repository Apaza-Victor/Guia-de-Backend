Consistencia eventual

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 1 · Fundamentos

Introducción

La consistencia eventual es el modelo que eligen la mayoría de las bases de datos «NoSQL» modernas: las réplicas pueden divergir temporalmente, pero eventualmente (sin límite de tiempo fijo) convergen al mismo valor. Es la letra «E» de BASE vs ACID.

En lugar de bloquear el sistema para que todos vean lo mismo (como ACID), aceptamos ventanas de divergencia y diseñamos para que el estado final sea correcto.

Qué significa «eventual»

Formalmente: si dejas de escribir al sistema, todas las réplicas convergerán al mismo valor en algún momento futuro. No se promete un tiempo; solo que la divergencia no es permanente.

  • Una lectura desactualizada (stale read) es aceptable: puedes leer un valor viejo que se corregirá.
  • La propagación es asíncrona: las escrituras se aplican primero en una réplica y se difunden al resto con retraso.
  • Hay monotonicidad borrosa: no se garantiza que veas siempre el valor más nuevo al instante, pero sí que no «viajas» atrás en el tiempo de forma arbitraria.

Ejemplo cotidiano: cuando marcas «me gusta», la app te responde al instante aunque el contador global tarde unos segundos en actualizarse. Persiste, converge.

Réplicas y quórum

La convergencia se apoya en la replicación: cada dato vive en varias máquinas. Al leer y escribir con quórums (un número mínimo de réplicas que deben confirmar), controlas la probabilidad de lecturas desactualizadas.

Con 3 réplicas y la regla W + R > N —donde N es el número total de réplicas, W los acuses de escritura y R los de lectura— siempre leerás al menos de una réplica que tenga la última escritura. Es la base de la lección sobre quórums del módulo 2.

Ejemplo: un contador que converge

Este pequeño simulador muestra cómo dos réplicas sincronizan su estado tras divergir durante una caída de red:

class Replica:
    def __init__(self, nombre):
        self.nombre = nombre
        self.valor = 0
        self.pendiente = []

    def aplicar(self, delta):
        self.valor += delta
        self.pendiente.append(("write", delta))

    def sincronizar(self, otras):
        # Propaga las escrituras que la otra réplica aún no conoce
        for evento in self.pendiente:
            for otra in otras:
                if evento not in otra.pendiente:
                    otra.valor += evento[1]
                    otra.pendiente.append(evento)
        self.pendiente = []

a = Replica("A")
b = Replica("B")

a.aplicar(5)   # A=5, B=0  -> divergen
b.aplicar(3)   # A=5, B=3
a.sincronizar([b])  # B recibe +5 -> B=8
b.sincronizar([a])  # A recibe +3 -> A=8
assert a.valor == b.valor == 8  # convergieron

En la vida real, la propagación no reenvía «eventos» lineales como este; usa versiones de objetos completos y resuelve conflictos (ver la lección de relojes vectoriales).

La lectura desactualizada en acción

Observa cómo un consumidor puede leer un valor viejo mientras la escritura viaja. Esta es la firma de un sistema eventual:

# Escritura llega a la réplica 1 (líder de zona A)
curl -X PUT localhost:9101/usuarios/42 \
     -H 'Content-Type: application/json' \
     -d '{"estado": "premium"}'

# Lectura a la réplica 2 (zona B): aún no se propagó, devuelve el viejo
curl localhost:9102/usuarios/42
# { "estado": "gratis" }   <- stale read aceptado

# Segundos después, la misma lectura devuelve el valor convergido
curl localhost:9102/usuarios/42
# { "estado": "premium" }

BASE: el modelo que lo sustenta

BASE es el acrónimo que describe a estos sistemas, en contraste con ACID:

  • Básicamente disponible (Basically Available): todo nodo responde casi siempre, aunque sea con datos viejos.
  • Estado suave (Soft state): el estado cambia con el tiempo incluso sin entradas nuevas (durante la propagación).
  • Eventualmente consistente (Eventually consistent): convergen cuando termina la divergencia.

Bases como Cassandra, DynamoDB, CouchDB y MongoDB (en ciertas configuraciones) siguen este espíritu, y el desarrollador elige por operación el punto entre C y A del CAP. Esa elección se declara por operación en la configuración de tu cliente:

{
  "cliente": "catalogo-reader",
  "operaciones": {
    "consultar_precio":      { "consistencia": "LOCAL_QUORUM", "acepta_stale": false },
    "recomendados":          { "consistencia": "ONE",          "acepta_stale": true },
    "auditoria_contador":    { "consistencia": "ANY",          "acepta_stale": true }
  },
  "regla": "los datos críticos leen con quórum; el resto tolera replicación eventual"
}

Cuándo NO usar consistencia eventual

  • Pagos y saldos donde una lectura vieja produce pérdida real.
  • Inventario con reglas invariantes estrictas («no vender más existencias de las que hay»).
  • Cualquier caso donde la reconciliación de conflictos no tenga una regla clara.

Para esos casos, el siguiente módulo explorará consistencia fuerte con quórums, relojes y consenso.

Ejercicio

  1. Describe un caso de tu aplicación donde una lectura desactualizada de 5 segundos sea irrelevante y otro donde sea inaceptable.
  2. Con 3 réplicas, ¿qué valores de W y R elegirías para forzar consistencia fuerte en lecturas de inventario? Justifícalo.
  3. Implementa el simulador de réplicas de esta lección y añade un tercer nodo que se caiga a mitad de la sincronización. ¿Qué pasa con los pendientes?

Resumen

  • La consistencia eventual permite divergencia temporal entre réplicas que converge sin tiempo garantizado.
  • La regla W + R > N controla la probabilidad de lecturas desactualizadas.
  • BASE (básicamente disponible, estado suave, eventual) es la contracara de ACID.
  • Conviene cuando la disponibilidad vale más que la lectura al instante; es inadecuada con invariantes estrictas.
