Modelos de fallo

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 1 · Fundamentos

Introducción

Antes de responder «¿cómo hago tolerante a fallos mi sistema?» hay que responder «¿qué tipo de fallos asumo?». Los modelos de fallo describen, de forma jerárquica, cómo se puede comportar mal un nodo. Cada modelo hace que el problema sea más difícil de resolver y, por tanto, más caro.

La clasificación clásica, propuesta por Chandy y Lamport en 1985, ordena los fallos de menor a mayor severidad: crash → omisión → temporización → bizantino.

Fallo por crash

El nodo ejecuta su lógica correctamente hasta que, en un instante, deja de funcionar para siempre y no vuelve a responder. No corrompe datos, no envía mensajes raros: simplemente muere. Es el modelo más benigno y el que asumen la mayoría de bases de datos y servicios.

Estrategias aplicables: reiniciar, failover con un nodo de respaldo y replicación. Por eso el 99,9 % de los sistemas operan aquí y no necesitan lógica bizantina.

Ojo: en el modelo crash se asume que el nodo caído no se levanta con datos corruptos. Si puede reiniciarse y continuar mal, ya no es un fallo crash puro.

Fallo por omisión

El nodo está vivo pero no envía mensajes que debía enviar (omisión de envío) o recibe y no procesa lo que le llega (omisión de recepción). Un paquete perdido en la red cae aquí: nadie «se rompió», pero el mensaje no llegó.

  • Omisión de envío: un nodo decide (o no) despachar un mensaje pendiente; lo viste cuando una respuesta nunca llega.
  • Omisión de recepción: el mensaje llega al buffer pero se descarta o el proceso no lo lee a tiempo.

La red en IP (UDP, TCP sin ACK) provoca este tipo de fallos constantemente. La respuesta típica es el retry con timeout, que verás en detalle en el módulo 3.

Fallo de temporización

El nodo responde, pero fuera del tiempo esperado: respuestas demasiado lentas, relojes locales desviados o un proceso recién despertado por un GC largo. El problema no es que falte la respuesta, sino que llegó tarde.

Este modelo importa porque los timeouts del resto del sistema pueden interpretar un «lento» como un «caído», y tomar decisiones apresuradas como promover a un segundo líder. Por eso el consenso (módulo 2) usa tiempos de espera que evitan líderes espurios.

import time

# Simulación: un nodo que responde pero con latencia variable
def llamada_con_timeout(cliente, servicio, timeout_ms):
    inicio = time.monotonic()
    resp = cliente.llamar(servicio)
    if time.monotonic() - inicio > timeout_ms / 1000:
        # Respondió tarde: en la práctica es indistinguible de un crash
        return "TIMEOUT: tratar como fallo temporal"
    return resp

Fallo bizantino

El peor caso: el nodo se comporta de forma arbitraria — miente, envía mensajes contradictorios, simula ser otro nodo o corrompe su estado. Puede deberse a un bug, a hardware defectuoso o a un atacante comprometiendo la máquina.

Tolerar fallos bizantinos (el famoso problema de los generales bizantinos) exige algoritmos como PBFT o cadenas de bloques: con f nodos bizantinos necesitas al menos 3f + 1 nodos en total. Por eso, en un backend «normal» se asume el modelo crash y se evita este coste.

En la práctica

En producción casi siempre se asume una combinación pragmática: crash + omisión + temporización (el riesgo de nodos «lentos»). Por eso los clientes de bases de datos usan timeouts, reintentos y tolerancia a fallos con quórums.

Un ejemplo real: lanzar un proceso en un clúster y dejar que el orquestador lo reinicie si muere. En Kubernetes, esto se expresa como un restartPolicy, asumiendo fallos crash:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: worker-cola
spec:
  replicas: 3
  template:
    spec:
      restartPolicy: Always
      containers:
        - name: worker
          image: mi-worker:1.0
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 10

El livenessProbe detecta un nodo que dejó de responder (crash colgado) y lo reinicia; el replicas: 3 cubre la omisión cuando uno de los tres se pierde temporalmente.

Ejercicio

  1. Clasifica las siguientes incidencias en un modelo de fallo concreto: a) un contenedor que el kernel mata por OOM, b) un paquete TCP que se reenvía pero llega tardísimo, c) una réplica de BD que devuelve filas duplicadas.
  2. Para cada caso, propón una mitigación (reiniciar, retry con timeout, replicación…).
  3. Responde por escrito: ¿por qué asumir fallo crash reducido hace viable un sistema como Redis, que no implementa tolerancia bizantina?

Resumen

  • Los modelos de fallo se ordenan por severidad: crash < omisión < temporización < bizantino.
  • El modelo crash asume muerte limpia y es el más barato de tolerar.
  • La omisión y la temporización aparecen por la red y por la lentitud; se manejan con retries, timeouts y quórums.
  • El bizantino es el más caro (3f+1 nodos) y solo aparece en sistemas con adversarios o hardware no confiable.
