¿Qué es un sistema distribuido?

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 1 · Fundamentos

Introducción

Casi cualquier Backend que sirva tráfico real es, hoy, un sistema distribuido: varios servidores detrás de un balanceador, una base con réplicas, un clúster de caché y una cola de mensajes. El problema es que, cuando tienes más de una máquina, las reglas del juego cambian. Lo que en un solo proceso era obvio —una variable, un reloj, un fallo— deja de serlo.

Un sistema distribuido es un conjunto de computadoras (nodos) que colaboran entre sí por red y que se presentan al usuario como un único sistema coherente. La palabra clave es coherente: la coordinación es lo difícil, porque cada nodo ve el mundo por su propia ventana.

Definición y características

La definición clásica de Leslie Lamport —«un sistema en el que el fallo de una computadora de la que no sabes siquiera que existe puede impedir que tu sistema funcione»— sigue vigente. Las características que definen a estos sistemas:

  • Concurrencia: varios nodos ejecutan al mismo tiempo y compiten por recursos.
  • Ausencia de reloj global: cada máquina tiene su propio reloj y no puedes sincronizarlos perfectamente.
  • Fallas independientes: un nodo puede caerse, ralentizarse o corromperse sin avisar y sin afectar a los demás.
  • Comunicación solo por red: los nodos no comparten memoria; todo intercambio es un mensaje que puede perderse.

Idea clave: en un sistema distribuido asumimos que podemos agregar más máquinas para ganar rendimiento y disponibilidad, pero cada máquina nueva añade incertidumbre: más red, más relojes, más fallos posibles.

Fallas parciales

En un programa normal, cuando algo falla, falla todo el proceso y lo sabes: la excepción está en la misma máquina. En un sistema distribuido, el escenario típico es la falla parcial: un nodo deja de responder, pero el resto del sistema sigue vivo. El problema es que no sabes por qué no responde:

  • El nodo se cayó (process crash).
  • El nodo está vivo pero la red perdió el paquete.
  • El nodo está tan lento que parece muerto (falso positivo).
  • El nodo procesó tu mensaje, respondió, y la respuesta se perdió.

Operar bajo incertidumbre es el arte del backend distribuido: no puedes distinguir un nodo caído de un nodo inalcanzable.

No hay un reloj global

Si dos nodos guardan una marca de tiempo cada uno, ¿cuál ocurrió antes? Depende de en qué reloj confíes. Los relojes físicos se desvían (el problema de NTP) y, aunque se sincronicen a la mañana, pueden recalibrarse a mitad del día. Por eso en sistemas distribuidos hablamos de relojes lógicos (contadores, relojes vectoriales) para ordenar eventos, tema que verás en el módulo 2.

Dónde aparecen en el backend

Cuando escalas cualquiera de estas piezas, ya estás en territorio distribuido:

  • Load balancer + N servidores: varios procesos sirven la misma API.
  • Base de datos con réplicas: escrituras al líder, lecturas a réplicas.
  • Redis Cluster o Kafka: datos particionados entre varias máquinas.
  • Workers: N procesos consumen la misma cola.

Ejemplo: una API replicada

Imagina que despliegas dos instancias del mismo servicio detrás de un balanceador. En un solo nodo, contar los «me gusta» es trivial; con dos, cada nodo puede tener una copia distinta:

// Nodo A: recibe una petición y suma 1
contadorA += 1; // contadorA = 100
guardar(contadorA);

// Nodo B: recibe otra petición y suma 1 también
contadorB += 1; // contadorB = 100 (obsoleto: le faltan las escrituras de A)

// Resultado: el cliente ve 100 en A y 100 en B,
// pero el valor "correcto" pudo haber sido 101.

La solución pasa por replicar (módulo 2): elegir un nodo como líder, propagar las escrituras y decidir qué leen los clientes.

Un despliegue típico con Docker Compose ya es un mini-sistema distribuido. Observa cómo declaramos replicas:

services:
  api:
    image: mi-api:1.0
    deploy:
      replicas: 3
      restart_policy:
        condition: on-failure
    depends_on:
      - postgres
      - redis

  postgres:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data

  redis:
    image: redis:7-alpine

volumes:
  pgdata:

Con tres réplicas de la API tienes más capacidad, pero también tres puntos donde las cosas pueden fallar de forma distinta. Y si el balanceador reenvía la misma petición dos veces, ¿qué pasa con el pago del usuario? La clave está en la idempotencia, que verás en la lección de comunicación entre nodos.

Detectar un nodo caído

La detección de fallos se hace habitualmente con heartbeats: cada nodo envía una señal periódica y, si no llega dentro del timeout, se le declara inalcanzable. La incertidumbre es inevitable: un timeout demasiado corto y marcas nodos sanos como caídos; demasiado largo y tardas en reaccionar.

import asyncio

TIEMPO_ESPERA = 30  # segundos sin latido -> nodo sospechoso

async def vigilar(nodo, id_ultimo_latido):
    # Cada latido recibe un número de secuencia para diferenciar "vivo"
    # de "la red reenvió un paquete viejo".
    while True:
        await asyncio.sleep(1)
        antiguo = await nodo.ultimo_latido()
        if id_ultimo_latido.get(nodo.id, -1) < antiguo:
            id_ultimo_latido[nodo.id] = antiguo
            print(f"{nodo.id}: vivo")
        elif (ultima_marca >= TIEMPO_ESPERA):
            marcar_como_sospechoso(nodo.id)

Recuerda: un nodo «caído» a menudo no lo está; solo es un nodo cuyo mensaje no conseguimos recibir a tiempo. Diseña siempre para la incertidumbre.

Ejercicio

  1. Lista tres servicios de tu proyecto actual (o de uno conocido) que formen parte de un sistema distribuido y explica qué nodos participan.
  2. Elige una petición concreta (crear un pedido, registrar un pago) y enumera todos los puntos donde puede producirse una falla parcial.
  3. Responde: ¿qué le pasa a tu base de datos si dos instancias de la API escriben al mismo tiempo sin coordinación? Escribe el escenario con tus palabras.

Resumen

  • Un sistema distribuido es un conjunto de nodos que colaboran por red y se presentan como un todo.
  • La falla parcial es la regla: puedes distinguir nodo caído, inalcanzable o lento.
  • No existe un reloj global: el orden debe derivarse con relojes lógicos.
  • Detectar nodos caídos requiere heartbeats con timeout, siempre con incertidumbre.
