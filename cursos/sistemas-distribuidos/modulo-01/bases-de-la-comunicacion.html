Comunicación entre nodos

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 1 · Fundamentos

Introducción

Los nodos de un sistema distribuido se comunican por red mediante mensajes. El problema fundamental: una llamada remota (RPC) puede fallar de tres maneras, pero para el llamador siempre parecen una: «no sé qué pasó».

  1. El mensaje nunca llegó.
  2. El mensaje llegó, se procesó, pero la respuesta se perdió.
  3. El mensaje llegó, el servicio se cayó a mitad del procesamiento.

Como viste en la lección de fallas parciales, tu código debe vivir con esa incertidumbre. Esta lección cubre las herramientas para hacerlo: RPC con timeouts, idempotencia y las garantías de entrega.

RPC y llamadas remotas

Una llamada a procedimiento remoto (RPC) disfraza una comunicación de red con el aspecto de una llamada local. Frameworks como gRPC, Thrift o los clientes HTTP de toda la vida hacen esto. La tentación es tratarla como síncrona y local; la realidad es que puede fallar, tardar o repetirse.

Patrón básico: llamar con un timeout y decidir qué se hace si no llega la respuesta a tiempo.

const TOLERANCIA_MS = 2000;

async function llamarConTimeout(receta) {
    const controlador = new AbortController();
    const temporizador = setTimeout(() => controlador.abort(), TOLERANCIA_MS);
    try {
        const resp = await fetch(receta.url, { signal: controlador.signal });
        return await resp.json();
    } catch (error) {
        if (error.name === 'AbortError') {
            // No sabemos si el nodo procesó la petición.
            throw new Error('TIMEOUT: estado desconocido');
        }
        throw error;
    } finally {
        clearTimeout(temporizador);
    }
}

Idempotencia

Una operación es idempotente si aplicarla varias veces produce el mismo resultado que aplicarla una vez. Es la defensa natural contra los reintentos: si reintentamos una petición que ya se ejecutó, no queremos cobrar dos veces ni duplicar el pedido.

  • GET y PUT de HTTP son idempotentes por definición; DELETE también lo es en práctica.
  • POST no lo es: crea un recurso nuevo cada vez. Por eso se usa la clave de idempotencia.

Ejemplo real en la cabecera de una pasarela de pagos:

POST /v1/cargos
Content-Type: application/json
Idempotency-Key: pago-orden-48231-c7f1

{
  "monto": 4990,
  "moneda": "MXN",
  "ordenId": "48231"
}

El servidor guarda la clave junto con la respuesta. Si llega de nuevo la misma clave, devuelve la respuesta guardada en lugar de cobrar otra vez:

def cobrar(cliente, clave_idempotencia, monto):
    respuesta_previa = almacen.get(clave_idempotencia)
    if respuesta_previa:
        return respuesta_previa, "duplicada"

    respuesta = pasarela.crear_cargo(monto)
    almacen.set(clave_idempotencia, respuesta)
    return respuesta, "nueva"

Garantías de entrega

La red y los protocolos definen cuántas veces puede llegar un mensaje:

  • At-most-once (a lo sumo una vez): el mensaje se envía una vez, sin reintento. Puede perderse, pero nunca se duplica. Ideal para lecturas o telemetría.
  • At-least-once (al menos una vez): se reintenta hasta confirmar. Puede duplicarse, por lo que el consumidor/operación debe ser idempotente. Es la garantía por defecto de colas como Kafka y SQS.
  • Exactly-once (exactamente una vez): ni se pierde ni se duplica. Es la más cara y, en la práctica, se emula combinando at-least-once + idempotencia en el procesamiento (por ejemplo, en transacciones de Kafka Streams o INSERT ... ON CONFLICT).

Regla práctica: apunta a «at-least-once + idempotencia». Garantizar realmente exactly-once en la red es imposible; se logra que el efecto sea único.

Un reintento con backoff exponencial implementa at-least-once evitando sobrecargar al servicio:

import time

def enviar_con_reintento(cliente, mensaje, max_intentos=5):
    intentos = 0
    while intentos < max_intentos:
        try:
            return cliente.enviar(mensaje)
        except TransientFailure:
            espera = 0.2 * (2 ** intentos)   # 0.2, 0.4, 0.8, 1.6, 3.2 s
            time.sleep(espera)
            intentos += 1
    raise PermanentFailure("mensaje no entregado tras reintentos")

Modelos de comunicación

  • Request/Reply síncrono: el cliente espera la respuesta (REST, gRPC). Fácil de razonar; sensible a timeouts y encadenamiento de fallos.
  • Mensajería asíncrona: el cliente publica en una cola y sigue su vida (RabbitMQ, Kafka, SQS). Descopla a los participantes; la entrega pasa a ser responsabilidad del broker.

La regla de oro del backend distribuido: la comunicación débilmente acoplada y asíncrona aguanta mejor los fallos, porque no hay una cadena de esperas que se rompa.

Ejercicio

  1. Busca en tu código una llamada HTTP que haga POST y evalúa: ¿qué pasaría si el cliente reintentara automáticamente la petición?
  2. Añade una clave de idempotencia (un UUID por operación) a ese flujo y escribe el pseudocódigo del controlador que la valida.
  3. Clasifica estas operaciones como at-most-once, at-least-once o exactly-once: un evento de auditoría, un débito de tarjeta, una lectura de inventario por caché.

Resumen

  • Toda RPC puede fallar de tres formas indistinguibles: no llegó, se procesó y se perdió la respuesta, o murió a medias.
  • La idempotencia (claves, PUT/DELETE) permite reintentar sin efectos duplicados.
  • Las garantías de entrega van de at-most-once a exactly-once; lo pragmático es at-least-once + idempotencia.
  • La comunicación asíncrona desacopla nodos y mejora la tolerancia a fallos.
