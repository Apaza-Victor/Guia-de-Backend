Clústeres y coordinación

🚀 Avanzado 9 min Sistemas Distribuidos Módulo 3 · Escalabilidad y casos reales

Introducción

Un clúster necesita «saber» quién es el líder, qué nodos están vivos, dónde está el estado global. Eso se puede improvisar en cada servicio, o delegarse a un servicio de coordinación: un sistema pequeño, consistente y altamente disponible que ofrece consenso, locks y registro de nodos.

Los dos grandes son ZooKeeper (de Apache, usado por Kafka y HBase) y etcd (de CNCF, usado por Kubernetes). Ambos implementan consenso (Zab y Raft respectivamente) sobre un clúster impar de nodos.

ZooKeeper: nodos y znode

ZooKeeper guarda un árbol de znodes (como un filesystem). Características clave:

  • Persistentes: sobreviven a la desconexión de su creador.
  • Efímeros (ephemeral): desaparecen automáticamente cuando el cliente se desconecta o muere. Perfectos para registrar nodos vivos.
  • Secuenciales: el nombre se autoincrementa, permitiendo construir colas y locks justos.
  • Watch: los clientes reciben notificaciones al cambiar un znode.
# Crear un znode efímero que representa a un worker vivo
zkCli.sh -server zk1:2181 create -e /workers/worker-7 "" 

# Crear znode secuencial para construcción de un lock
zkCli.sh -server zk1:2181 create -e -s /locks/recurso lock- 

# Listar workers activos (los muertos ya no aparecen)
zkCli.sh -server zk1:2181 ls /workers

El hecho de que el znode efímero desaparezca solo al morir el proceso hace de ZooKeeper un detector de fallos natural para registro de nodos y elección de líder.

Lock distribuido con ZooKeeper

El patrón clásico para una sección crítica distribuida: cada contendiente crea un znode secuencial bajo el mismo padre; gana el de número más bajo y espera ser el siguiente cuando el anterior desaparezca.

# Pseudocódigo realista (klinkeeper / kazoo)
def adquirir_lock(zk, ruta_lock):
    mi_nodo = zk.create(route.ruta + "/lock-", value="",
                        sequence=True, ephemeral=True)
    while True:
        hijos = sorted(zk.get_children(ruta_lock))
        if mi_nodo.endswith(hijos[0]):
            return mi_nodo              # soy el primer nodo: tengo el lock
        anterior = hijos[hijos.index(mi_nodo.split("/")[-1]) - 1]
        # espero a que desaparezca el anterior (watch ephemeral)
        zk.wait_for(anterior, exist=True)

def liberar_lock(zk, mi_nodo):
    zk.delete(mi_nodo)

etcd: claves y leases

etcd guarda pares clave-valor y añade dos piezas útiles:

  • Leases: una clave puede asociarse a una concesión con TTL; si el concesionario no la renueva, la clave expira.
  • CAS (compare-and-set): operaciones «solo si la versión actual coincide», base de los locks atómicos.
# Registrar un nodo viva con lease de 10s (Kubernetes usa este modelo)
etcdctl lease grant 10            # -> lease 6941e... con TTL 10s
etcdctl put /nodos/worker-9 "" --lease=6941e...

# Lock atómico con versión (compare-and-swap)
etcdctl txn --interactive "
put /locks/cron 'recurso-bloqueado'
"

Elección de líder con coordinación

Con la elección de líder delegada, el servicio solo pregunta «¿soy el líder?». Si la respuesta es sí, trabaja; si muere, su znode efímero o lease expira y otro toma el relevo sin que los clientes lo noten.

{
  "servicio": "job-distribuido",
  "coordinacion": { "tipo": "etcd", "endpoints": ["etcd-1:2379"] },
  "lider": {
    "clave": "/servicios/job-distribuido/lider",
    "valor": "nod-7",
    "lease_ttl_seg": 10,
    "renovacion_cada_ms": 3000
  },
  "regla": "solo el propietario del lider ejecuta el cron; los demás esperan"
}

Los peligros de los locks distribuidos

Los locks distribuidos parecen sencillos y esconden dos trampas famosas:

  1. El lock vence pero el trabajo sigue: el proceso «dueño» retiene el recurso más que el TTL. Solución: usar fencing tokens (un número que invalida operaciones viejas).
  2. Consenso 2 de 3: el servicio de coordinación debe ser él mismo un clúster; si pierde mayoría, no da locks y el mundo espera — la costa que mencionamos en consenso.

Por eso, aunque ZooKeeper/etcd resuelven la coordinación, el diseño de un lock correcto sigue exigiendo cuidado (ver manejo de fallos graceful en la próxima lección).

Ejercicio

  1. ¿Qué znode usarías (persistente, efímero, secuencial) para: a) descubrir workers vivos, b) elegir líder, c) guardar la versión de configuración?
  2. Explica por qué el znode efímero es «auto-limpio» y qué riesgo escondería un znode persistente mezclado con nodos muertos.
  3. Diseña el patrón de fencing token para tu lock: ¿qué valor se incrementa y cómo lo valida el recurso protegido?

Resumen

  • ZooKeeper y etcd ofrecen consenso, registro de nodos y locks a un clúster completo.
  • Znodes efímeros y leases hacen que los nodos muertos «se limpien solos».
  • La elección de líder delegada evita reinventar elecciones en cada servicio.
  • Los locks distribuidos exigen fencing tokens para no operar con un lock vencido.
