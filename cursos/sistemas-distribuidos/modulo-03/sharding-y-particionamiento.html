Sharding y particionamiento

🚀 Avanzado 10 min Sistemas Distribuidos Módulo 3 · Escalabilidad y casos reales

Introducción

La replicación copia los mismos datos en varias máquinas; el particionado (sharding) reparte datos distintos entre máquinas. Cada partición o shard guarda un subconjunto de las claves. Así, el tamaño y la carga se dividen horizontalmente: agrega máquinas y ganas capacidad.

Objetivos del particionado

  • Escanear pocos datos: una consulta va solo al shard que la contiene.
  • Escribir en paralelo: escrituras repartidas entre distintas máquinas.
  • Evitar puntos calientes: ninguna máquina debe recibir la mayor parte del tráfico.

El sufijo sharding aparece siempre que una única base de datos se queda corta (miles de millones de filas o QPS muy alto). El reto: elegir la función de particionado y reequilibrar cuando crezca el número de shards.

Particionado por rango

Asigna rango continuos de claves a cada shard:

  • shard-1: claves de 0000 a 1FFF
  • shard-2: claves de 2000 a 3FFF
  • shard-3: claves de 4000 a FFFF

Ventaja: las consultas por rangos contiguos caen en un mismo shard. Desventaja: ciertas claves (por ejemplo, los usuarios más recientes) crean puntos calientes.

-- PostgreSQL declarativo: partición por rango de fecha
CREATE TABLE eventos (
    id uuid,
    ocurrido_en timestamptz NOT NULL
) PARTITION BY RANGE (ocurrido_en);

CREATE TABLE eventos_2024 PARTITION OF eventos
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE eventos_2025 PARTITION OF eventos
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

Particionado por hash

Aplicas una función de hash a la clave y asignas el resultado a un shard:

import hashlib

NUMERO_DE_SHARDS = 16

def shard_de_clave(clave):
    digesto = hashlib.sha256(clave.encode()).hexdigest()
    return int(digesto, 16) % NUMERO_DE_SHARDS

# Distribución aproximadamente uniforme de claves entre shards
for clave in ["usuario-1", "usuario-2", "producto-7", "pedido-99"]:
    print(clave, "->", shard_de_clave(clave))

El hash reparte bien y elimina puntos calientes por clave, pero las consultas por rango mueren: cada clave se reparte pseudoaleatoriamente. Y reequilibrar es costoso, porque casi todas las claves cambian de shard cuando NUMERO_DE_SHARDS cambia.

Hash consistente

Para minimizar los movimientos al añadir o quitar máquinas, se usa el hash consistente: las claves y los nodos se mapean a un anillo; cada clave cae en el primer nodo que encuentra en el sentido de las agujas del reloj. Si añades un nodo, solo las claves cercanas a él se mueven (1/n en promedio).

# Redis Cluster reparte las 16384 slots con hash consistente.
# Un slot se mueve mínimo cuando cambia el mapa de nodos:
redis-cli cluster addslots 0 1 2 3           # añadir slots al nodo actual
redis-cli cluster setslot 3000 migrating 1   # migrar un slot a otro nodo
redis-cli cluster rebalance --threshold 10%  # reequilibrar automático

Este anillo es la razón por la que Cassandra y Redis Cluster resisten bien el escalado: añadir una máquina redistribuye una fracción mínima de los datos.

Tabla de ruteo

Al final del día, el sistema necesita saber dónde vive cada clave. Un diseño clásico guarda un mapa clave→shard:

{
  "tipo": "tabla_de_ruteo",
  "meta": { "generacion": 12, "total_shards": 16 },
  "shards": {
    "shard-01": { "host": "sdb1.prod", "rango": "SHA-0000 a SHA-03FF" },
    "shard-02": { "host": "sdb2.prod", "rango": "SHA-0400 a SHA-07FF" }
  },
  "regla": "sha256(clave) mod 16 -> ver tabla de shards"
}

Reequilibrio y trampas

  • Cross-shard queries: consultas que necesitan juntar datos de varios shards (joins, agregados) se vuelven costosas.
  • Hot keys: una clave popular (una celebridad, un producto virando) crea un shard caliente. Solución parcial: key splitting (dividir la clave en varias nuevas).
  • Migración: mover datos entre shards mientras se sirve tráfico es delicado; se hace en lotes y con verificación.

Por eso la elección de la clave de shard es una de las decisiones más importantes y permanentes de un sistema: cambiarla después cuesta una migración masiva.

Ejercicio

  1. Para «mensajes de una app de chat», ¿qué clave usarías (usuario, sala, fecha)? Justifica qué consultas se benefician.
  2. Implementa el hash por shard del ejemplo y añade el manejo de «distribución desigual» simulando 1000 claves: ¿cuántas caen en cada shard?
  3. Compara por escrito particionar por rango (por fecha de pedido) vs por hash (por usuario): ¿cuándo prefieres uno u otro?

Resumen

  • El sharding reparte datos distintos entre máquinas y escala horizontalmente.
  • El particionado por rango favorece consultas de rango; el por hash reparte bien pero mata los rangos.
  • El hash consistente minimiza la migración al añadir/quitar nodos.
  • Las claves calientes y las consultas cross-shard son los dos grandes costos.
