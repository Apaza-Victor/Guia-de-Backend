Diseñar un sistema distribuido

🚀 Avanzado 8 min Sistemas Distribuidos Módulo 3 · Escalabilidad y casos reales

Introducción

Esta es la lección que junta todo el curso: un checklist reproducible para diseñar un sistema distribuido, seguido de las decisiones clave y una plantilla para evaluar el resultado. La idea no es memorizar recetas, sino tener un orden para razonar.

Paso 1: requisitos y restricciones

Antes de dibujar nodos, define qué debe cumplir el sistema. Sin esto, toda decisión posterior es arbitraria:

  • Carga esperada: QPS pico, escrituras vs lecturas, tamaño de los datos.
  • Latencia pretendida: ¿200 ms ya es tarde? ¿puede tolerar timeout en momentos de fallo?
  • Disponibilidad objetivo: 99 % / 99,9 % / 99,99 % (define cuántos 9 necesitas).
  • Consistencia necesaria: fuerte, causal o eventual, y en qué operaciones.
{
  "proyecto": "catalogo-distribuido",
  "requisitos": {
    "qps_pico": 8000,
    "ratio_lectura_escritura": "90/10",
    "latencia_p99": "250ms",
    "disponibilidad": "99.95%",
    "consistencia": "eventual para lectura de precios; fuerte para stock"
  }
}

Paso 2: particionar y replicar

Con los requisitos claros, llegan las dos grandes decisiones estructurales:

  1. Clave de partición (shard): por usuario, cliente, sala o región. Debe repartir la carga y no romper las consultas frecuentes.
  2. Modelo de replicación: leader-follower (simple), leaderless (quórums) o multi-leader (multiregión). Decide de paso el N, W y R.

Regla práctica: empieza mínimo viable —un solo shard con réplicas de lectura— y escala cuando las mediciones lo pidan. Diseñar sharding prematuro complica sin necesidad.

Paso 3: coordinación y fallos

Añade después la «capa de cerebro» y la «capa de resiliencia»:

  • Elección de líder / locks: etcd, ZooKeeper, o el consenso de tu base si ya la provee.
  • Timeouts y reintentos: backoff exponencial + jitter, siempre con idempotencia.
  • Fusibles: para aislar dependencias enfermas.
  • Degradación: qué sirve caché, qué se apaga, qué se mantiene crítica.
  • Failover probado: que un nodo muerto no requiera un humano a las 3am.
servicios:
  api-catalogo:
    replicas: 4
    dependencias:
      - redis-cluster      # caché: degradable a cache-backed
      - kafka              # eventos de cambio de stock
      - postgres-cluster   # líder + 2 réplicas de lectura
    politicas:
      timeout_ms: 800
      reintentos: 3
      backoff: exponencial
      fusible: on
    degradacion:
      con_cache: true
      sin_origen: servir cache de 5 min

Paso 4: documentar decisiones (ADR)

Cada decisión de arquitectura merece un Architecture Decision Record breve: contexto, decisión, alternativas y consecuencias. Es el seguro contra los «¿por qué hicimos esto?» dentro de un año:

# ADR-007: Consistencia del stock

## Contexto
El "stock" se lee desde réplicas con lag y eso provoca
ventas duplicadas cuando el cliente reintenta.

## Decisión
Las escrituras de stock usan nivel CONSISTENCY=QUORUM
(2 de 3 réplicas) y el endpoint de venta es idempotente
con Idempotency-Key.

## Alternativas
- Transacciones 2PC rechazadas por el bloqueo de recursos.
- Consistencia fuerte global rechazada por latencia.

## Consecuencias
(+) Lecturas de stock siempre frescas tras el quórum.
(-) Las escrituras de stock son ~30 % más lentas.

Evaluar el diseño

Antes de decir «terminado», responde estas seis preguntas con hechos (no intuiciones):

  1. ¿Qué pasa si se cae el nodo X? ¿Alguien nota la caída?
  2. ¿Qué pasa si se corta la red entre dos zonas? (¿CP o AP elegido intencionalmente?)
  3. Si duplico el tráfico mañana, ¿qué satura primero?
  4. ¿Los reintentos son idempotentes? ¿Pueden causar doble efecto?
  5. ¿Puedo medir latencia, errores y réplicas atrasadas en un dashboard?
  6. ¿Puedo probar el failover sin miedo cada semana?

Si alguna respuesta te incomoda, esa es la siguiente iteración del diseño. Un sistema distribuido se termina cuando deja de ser un misterio qué pasa cuando algo falla.

Ejercicio

  1. Diseña un «sistema de notificaciones distribuido» (envios por email/push) siguiendo los 4 pasos. Rellena el JSON de requisitos y el YAML de servicios.
  2. Escribe un ADR de una decisión que tomaste (o tomarías) en tu proyecto real, con contexto, decisión, alternativas y consecuencias.
  3. Responde las 6 preguntas de evaluación para el sistema que diseño en el punto 1.

Resumen

  • Empieza por requisitos y restricciones medibles, no por elegir tecnologías.
  • Parten y replicas después: clave de sharding y modelo de replicación son las decisiones más difíciles de revertir.
  • Añade coordinación, timeouts, fusibles y degradación como una capa explícita.
  • Documenta con ADRs y evalúa con 6 preguntas que se responden con datos.
