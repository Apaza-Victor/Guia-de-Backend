Manejo de fallos graceful

🚀 Avanzado 10 min Sistemas Distribuidos Módulo 3 · Escalabilidad y casos reales

Introducción

Un sistema tolerante a fallos no es el que nunca falla: es el que decaen de forma controlada y se recupera. La traducción de «manejo de fallos graceful» es precisamente eso: ante un nodo muerto o una red rota, el usuario apenas nota nada porque hay respaldo, reintento o una funcionalidad degradada.

El fundamento: timeouts

Todo empieza por decidir cuánto esperamos antes de dar la llamada por fallida. Un timeout ausente convierte una lentitud en un montón de peticiones colgadas (y en threads agotados). Las buenas prácticas:

  • Ajustar el timeout por capa: conectarse, responder, leer.
  • Aplicar timeouts decrecientes en cascada: si el servicio lento es lejano, no reinventes; corta pronto.
  • Separar «no responde» (lento) de «refusó» (423, 503): el reintento no es la misma política.
// Timeouts por fase en Node.js (fetch)
function llamarFinanzas(datos) {
  const c = new AbortController();
  const t = setTimeout(() => c.abort(), 1200); // todo el viaje: 1.2s
  return fetch("https://finanzas.internal/v1/debito", {
    method: "POST",
    body: JSON.stringify(datos),
    signal: c.signal,
  }).finally(() => clearTimeout(t));
}

Reintentos con backoff y jitter

Tras un fallo transitorio, reintentar ayuda; reintentar a ciegas y al instante derrumba al servicio ya estresado (el thundering herd). Se usa backoff exponencial —cada espera dobla— y jitter —un poco de azar— para que los reintentos no colisionen entre sí:

import random

def espera_backoff(intento, base_s=0.2, max_s=8.0):
    exp = min(base_s * (2 ** intento), max_s)
    return random.uniform(0, exp)   # jitter full: evita sincronización

for intento in range(5):
    try:
        return servicio.llamar()
    except FalloTransitorio:
        time.sleep(espera_backoff(intento))
raise FalloPermanente("agotados los reintentos")

Eso sí: reintenta solo operaciones idempotentes (recuerda la lección de comunicación). Un cargo de tarjeta re-reintentado sin clave de idempotencia cobra dos veces.

Failover y degradación

Cuando el nodo primario muere, el tráfico se conmuta (failover) a un nodo sano: réplica promovida, zona de disponibilidad vecina, o el cluster de respaldo. En paralelo, se usa la degradación como cortafuegos:

  • Sirve una versión cacheada si el origen cae.
  • Desactiva funciones no esenciales (recomendaciones, analytics) para proteger el núcleo.
  • Devuelve 503 temprano antes que iniciar una avalancha de retries.
{
  "estado": "degradado-parcial",
  "causa": "origen de catálogo caido",
  "modulos": {
    "detalle-producto": { "fuente": "cache-vieja-30m", "aviso": "datos pueden estar desactualizados" },
    "recomendados": { "fuente": "off", "aviso": "funcionalidad desactivada" },
    "checkout": { "fuente": "activo", "aviso": null }
  }
}

Circuit breaker o fusible

Cuando un nodo falla repetidamente, dejamos de llamarlo durante un tiempo (open), probamos poco a poco (half-open) y, si se recupera, volvemos a la normalidad (closed). Es el «fusible del software» que protege a los nodos sanos de los dañados.

# Configuración típica de un fusible (p.ej. resilience4j)
cb:
  registro:
    nombre: "mongodb-principal"
    failure_rate_threshold: 60        # 60% de fallos -> abre
    sliding_window_size: 20           # evalúa las últimas 20 llamadas
    wait_duration_in_open_state: 15s  # reabrir después de 15s
    permitted_number_of_calls_in_half_open: 3

Chaos engineering

La única forma de saber si tu sistema se recupera solo es romperlo a propósito. El chaos engineering introduce fallos controlados en producción (mata nodos, inyecta latencia, particiona la red) para verificar que el failover y el retry se comportan.

# Chaos Monkey (o su equivalente local): mata una réplica al azar
aws ec2 stop-instances --instance-ids $(elegir_worker_al_azar)

# Simular latencia o pérdida de paquetes en una región
tc qdisc add dev eth0 root netem delay 400ms loss 10%
# (el cluster debería seguir sirviendo con quórum)

La regla: solo se hacen experimentos de caos cuando ya existe una red de seguridad (monitoreo, runbooks, rollback) para no convertir un ejercicio en un incidente real.

Ejercicio

  1. Revisa una llamada a un servicio externo de tu código: ¿qué timeout tiene, cuántos reintentos, y es idempotente? Señala tres mejoras.
  2. Diseña el estado de un fusible de 3 estados (cerrado/abierto/semiabierto) para el endpoint de pagos y describe cuándo se pasa de uno a otro.
  3. Propón un experimento de chaos seguro para probar el failover de tu base: qué matas, qué mides y cuándo decides abortar.

Resumen

  • El manejo graceful combina timeouts, reintentos con backoff+jitter, y degradación.
  • El failover conmuta a un nodo sano y protege el núcleo con funcionalidad degradada.
  • El circuit breaker aísla nodos que fallan de forma sostenida.
  • El chaos engineering prueba el sistema rompiéndolo controladamente.
