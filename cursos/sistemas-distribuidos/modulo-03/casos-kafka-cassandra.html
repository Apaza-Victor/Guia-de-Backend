Casos: Kafka, Cassandra, Redis cluster

🚀 Avanzado 10 min Sistemas Distribuidos Módulo 3 · Escalabilidad y casos reales

Introducción

Tres sistemas reales que ya resolvieron —a su manera— replicación, particionado y consistencia. Estudiarlos es la mejor forma de traducir la teoría: Kafka (log replicado con líder por partición), Cassandra (quórums sin líder) y Redis Cluster (slots de hash con failover propio).

Kafka: particiones con líder

Kafka organiza los mensajes en topics ➝ particiones. Cada partición tiene un líder y varias réplicas en brokers distintos. Los productores escriben al líder; los consumidores leen ordenadamente de cada partición.

  • El factor de replicación indica cuántas copias de cada partición se mantienen.
  • El min.insync.replicas controla cuántas deben confirmar antes de aceptar la escritura (la arista C/P del CAP).
  • La partición se elige por clave: la misma clave siempre al mismo broker, garantizando orden por clave.
# Crear topic con 6 particiones y 3 réplicas por partición
kafka-topics.sh --create \
  --topic pedidos \
  --partitions 6 \
  --replication-factor 3 \
  --config min.insync.replicas=2 \
  --bootstrap-server kafka-1:9092

# Ver el estado de los líderes y la distribución de réplicas
kafka-topics.sh --describe \
  --topic pedidos \
  --bootstrap-server kafka-1:9092

Toda la «alta disponibilidad» de Kafka viene de elegir un nuevo líder de partición cuando el actual muere (KRaft en versiones modernas). El consumidor en el otro extremo con enable.auto.commit=false decide cuándo dar un mensaje por procesado, para no perderlo ni duplicar:

from kafka import KafkaConsumer

consumer = KafkaConsumer(
    "pedidos",
    bootstrap_servers=["kafka-1:9092"],
    group_id="procesador-pedidos",
    enable_auto_commit=False,        # nosotros decidimos el offset
    auto_offset_reset="earliest",
)

for mensaje in consumer:
    procesar(mensaje.value)
    # confirmamos solo tras procesar: si el worker muere,
    # el mensaje se re-entrega (at-least-once)
    consumer.commit()

Cassandra: quórum sin líder

Cassandra es puro modelo leaderless: cualquier nodo acepta lecturas y escrituras, y el nodo «coordinador» espera las confirmaciones de un quórum. Los datos se replican por keyspace con un factor de replicación, usando hash consistente sobre un anillo.

# Createspace con factor de replicación N=3 (una clave vive en 3 nodos)
cqlsh -e "
CREATE KEYSPACE app
  WITH replication = {'class': 'SimpleStrategy', 'replication_factor': 3};
USE app;

# Lecturas/escrituras con nivel de consistencia por sentencia
CONSISTENCY QUORUM;   # W=quórum (2 de 3 con N=3)
SELECT * FROM usuarios WHERE id = 42;
"

Cuando un nodo se cae, el coordinador guarda un hint y entrega las escrituras atrasadas cuando el nodo regresa (hinted handoff). Y con las lecturas quórum ejecuta read repair sobre réplicas desactualizadas, que vimos en la lección de quórums.

Redis Cluster: 16384 slots

Redis Cluster divide el espacio de claves en 16 384 slots, repartidos entre los nodos maestro. Cada slot pertenece a un maestro, y cada maestro tiene una o más réplicas.

  • La clave va al slot CRC16(clave) mod 16384.
  • Si una escritura llega al nodo equivocado, devuelve MOVED con el slot correcto y el cliente reenruta.
  • Los master-slots se reasignan durante el rebalanceo migrando slots (hash consistente en la práctica).
# Crear un clúster de 3 maestros x 1 réplica (6 nodos)
redis-cli --cluster create \
  redis-1:6379 redis-2:6379 redis-3:6379 \
  redis-1r:6379 redis-2r:6379 redis-3r:6379 \
  --cluster-replicas 1

# Forzar la elección de una réplica cuando su maestro muere
redis-cli -p 6379 CLUSTER FAILOVER

La respuesta MOVED es el mecanismo de coordinación «a la antigua»: no hay una tabla central en la red; el cliente inteligente cachea el mapa de slots.

La lección común

Los tres combinan particionado + replicación + un mecanismo de coordinación, y cada uno elige un punto distinto del CAP:

  • Kafka garantiza orden y tolera perder tráfico de escrituras solo si aceptas acks=1; para no perder datos usas min.insync.replicas y aceptas la espera.
  • Cassandra maximiza disponibilidad y te deja subir la consistencia por operación al precio que quieras pagar.
  • Redis Cluster da consistencia fuerte dentro de un nodo maestro con failover, pero la coordinación de slots añade complejidad al cliente.

Si entiendes por qué cada uno eligió distinto, entiendes el tema completo del curso: no hay solución ganadora, hay trade-offs.

Ejercicio

  1. Explica qué elegirías para un log de eventos de auditoría (Kafka, Cassandra o Redis) y por qué, citando el modelo de consistencia.
  2. Con Kafka y replication.factor=3, ¿cuántos brokers pueden caer sin perder la disponibilidad de escritura con min.insync.replicas=2?
  3. En Redis Cluster, ¿qué devuelve un nodo cuando recibe una clave que pertenece a otro slot? Investiga el comando que el cliente usa para aprender el mapa.

Resumen

  • Kafka: log replicado con líder por partición y confirmaciones configurable.
  • Cassandra: modelo leaderless con quórums, hinted handoff y read repair.
  • Redis Cluster: 16384 slots, hash de la clave y redirección MOVED al cliente.
  • Los tres demuestran que particionado + replicación + coordinación = trade-off del CAP.
