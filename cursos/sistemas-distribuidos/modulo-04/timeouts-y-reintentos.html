Timeouts y reintentos

🧠 Experto 12 min Sistemas Distribuidos Módulo 4 · Tolerancia a fallos

Introducción

Sin timeout, una llamada cuelga a un proceso para siempre. Con timeout y reintentos, tu sistema se recupera solo. Pero reintentar sin control es amplificar el fallo: cada cliente reintentando multiplica la carga de un servicio ya caído.

La solución clásica combina timeout, reintentos con backoff exponencial y jitter (variación aleatoria) para que los reintentos no caigan juntos como una manada.

Definición

Un timeout limita cuánto esperas una respuesta; los reintentos repiten la operación fallida con backoff (espera creciente) y jitter (aleatoriedad) para repartir la carga.

Por qué importa. La red pierde mensajes y los servicios se caen: sin timeouts y reintentos razonables, el sistema se degrada hasta la caída.

Cuándo usarlo. Reintenta errores transitorios (502, 503, timeouts) pero nunca errores 4xx: son permanentes.

Conceptos clave

  • Timeout: el límite de espera que protege a tu proceso.
  • Backoff exponencial: espera 100ms, 200ms, 400ms... entre reintentos.
  • Jitter: variación aleatoria que evita el efecto manada.
  • Reintento idempotente: solo si la operación no produce efectos duplicados.
  • Límites: máximo de reintentos antes de ceder al error final.

Ejemplo básico

Cliente HTTP con timeout, backoff exponencial y jitter.

Ejemplo intermedio

Integrar reintentos en una base de datos de red o un broker.

Ejemplo real

Un proceso de facturación reintenta tres veces un cobro con backoff. La pasarela está saturada: el jitter evita que todas las colas de reintento exploten a la vez y la cola se recupera sola.

  • Reintenta solo lo transitorio, jamás un 4xx permanente.
  • Siempre idempotencia si reintentas escrituras.
  • Registra cada reintento con su número para no perder el rastro.

El jitter rompe el sincronismo que el backoff exponencial puro crea entre clientes.

Explicación

  • El timeout convierte una caída silenciosa en un fallo manejable.
  • El backoff exponencial da tiempo al servicio a recuperarse.
  • El jitter evita el efecto manada de reintentos simultáneos.
  • Reintentar sin idempotencia puede duplicar cobros o pedidos.
  • Registrar el intento y el error previo acelera el diagnóstico.

Errores comunes

  • Timeout de 30 s en una API interna: toda la cadena espera colgada.
  • Reintentos sin jitter: miles de clientes golpean a la vez.
  • Reintentar un 401/400: el error no se arregla repitiendo.

Buenas prácticas

  • Ajusta el timeout según el SLO del servicio llamado.
  • Cap de reintentos: mejor fallar rápido que esperar una eternidad.
  • Mete retry policy en el cliente de tu DB y de tu broker.
  • Monitorea el ratio de reintentos: si crece, es síntoma, no solución.

Ejercicio

  1. Añade timeout de 2 s y 3 reintentos con backoff a tu cliente HTTP.
  2. Reintenta un 503 y comprueba que no tocas los 4xx.
  3. Añade jitter y mide cómo se descorrelacionan los reintentos.

Resumen

  • Los timeouts limitan la espera; los reintentos dan segundas oportunidades.
  • Backoff exponencial y jitter evitan el efecto manada.
  • Solo reintentos para errores transitorios y con idempotencia.
