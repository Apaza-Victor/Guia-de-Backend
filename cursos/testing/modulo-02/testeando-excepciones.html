Testeando excepciones

🔧 Intermedio 12 min Testing Backend Módulo 2 · Unit Testing

El error también es comportamiento

Si tu código espera que algo falle en una condición dada, ese fallo es parte del contrato y se testea igual que el camino feliz. Un test de excepción protege: «aquí, en estas condiciones, la API responde así».

expectException y sus primas

  • expectException(Clase::class): tipo exacto o subclase.
  • expectExceptionMessage('...'): trozo del mensaje.
  • expectExceptionCode(422): para excepciones con código.
  • Se declaran antes de la línea que debe fallar.

La trampa de los errores silenciosos

  • If a dominio «no debe fallar» captura y devuelve false, es imposible saber si el fallo fue del negocio.
  • Regla: capturalo donde puedas hacer algo (retry, log, cola) o dejalo subir.
  • Un test sobre el camino return false junto a un stub que lanza, documenta la decisión.

Ejercicio

  1. Crea una clase CuentaBancaria con retirar() que lance SaldoInsuficiente.
  2. Test tipo: expectException + expectExceptionMessage.
  3. Test con assertThrows validando el monto que faltó.

Resumen

  • El error es contrato: si está previsto, se testea.
  • expectException* declara antes; try/catch da control fino.
  • assertThrows devuelve la excepción para inspeccionarla.
  • No tragues excepciones: capturá donde puedas actuar.
