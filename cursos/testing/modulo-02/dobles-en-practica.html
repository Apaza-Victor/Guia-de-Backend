Dobles en práctica

🔧 Intermedio 13 min Testing Backend Módulo 2 · Unit Testing

La tecnología que hace todo posible: interfaces

Los dobles funcionan mejor cuando tu código depende de abstracciones, no de clases concretas. Si RegistrarUsuario espera una Notificador (interfaz), el doble se crea en una línea. Si espera Swift_Notificador (implementación con SMTP), tu test se carga toda la infraestructura.

Inyección por constructor, no estática

Un test completo con 3 dobles

Fíjate: ningún test tocó la red ni la base de datos, y aun así probamos el comportamiento completo. El fake le da vida a los datos y el stub aísla lo que no interesa.

Errores comunes al usar dobles

Receta para diseñar para dobles

  1. Identifica las dependencias que tocan el mundo (BD, SMTP, HTTP, reloj).
  2. Extrae una interfaz por cada una, con métodos pequeños.
  3. Inyéctalas por constructor, nunca instancies adentro.
  4. En el test: fake para datos, stub para respuestas, mock solo si la llamada es contrato.
  5. Huye de estáticos y finales en los bordes del sistema.

Ejercicio

  1. Busca en tu código una clase que instancie internamente su BD o su reloj.
  2. Extrae la interfaz y muévela al constructor.
  3. Escribe un test usando el fake de datos y un stub para el resto.

Resumen

  • Los dobles se vuelven triviales si dependes de interfaces.
  • Inyección por constructor: nunca «nuevo algo()» adentro.
  • Fake para datos, stub para respuestas, mock solo para contratos.
  • Un doble mal diseñado repite el bug o acopla el test.
