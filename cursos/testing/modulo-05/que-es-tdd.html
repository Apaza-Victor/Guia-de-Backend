¿Qué es TDD?

🔧 Intermedio 13 min Testing Backend Módulo 5 · TDD

El orden que lo cambia todo

TDD (Test-Driven Development) invierte el orden natural: primero escribes una prueba de un comportamiento que aún no existe, la ves fallar, luego escribes el mínimo código para que pase. Repites y refactorizas.

Por qué funciona

  • Piensas antes de escribir: diseñar el test obliga a decidir la API pública (nombres, parámetros, retorno).
  • El test nunca miente: lo viste fallar por la razón correcta; cuando pasa, pasó por la tuya.
  • Diseño guiado por el consumo: escribes el uso antes que la implementación; la API resulta ergonómica.
  • Siempre tienes verde: cada paso es un commit seguro.

Lo que NO es TDD

Cuándo usarlo (y cuándo no)

  • Sí: reglas de negocio, servicios, controladores, transformaciones, serialización compleja.
  • No tanto: glue code trivial, prototipos descartables, integración de herramienta desconocida.
  • Regla sana: si el programa no te cuenta el «cómo», TDD te obliga a decidir el «qué»; eso siempre vale.

Ejercicio

  1. Elige la próxima función que vayas a implementar.
  2. Escribe TU test primero (rojo).
  3. Implementa el mínimo para el verde.
  4. Refactoriza. Anota cómo cambió el diseño.

Resumen

  • TDD: test → rojo → mínimo → verde → refactor.
  • El test fuerza decisiones de API antes del código.
  • Verlo fallar por la causa correcta es la garantía.
  • No es cobertura; es disciplina de diseño.
