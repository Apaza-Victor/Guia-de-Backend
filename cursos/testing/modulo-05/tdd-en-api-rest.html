TDD aplicado a una API REST

🔧 Intermedio 16 min Testing Backend Módulo 5 · TDD

TDD de fuera hacia dentro

Para una API, el TDD más efectivo es de fuera hacia dentro: un test HTTP (Supertest o PHPUnit+cliente) define el contrato público, y luego viajas al interior solo lo imprescindible. El E2E es el diseño; los unit, la malla fina.

ROJO: la ruta no existe

Falla porque la ruta no existe (404 o Cannot POST). Es el rojo correcto.

VERDE: la ruta mínima

REFACTOR: sacar la lógica de la ruta

La lógica pura ahora vive en crearCupon(), testable con unit tests (red → verde dentro del mismo refactor).

El siguiente rojo: validación

El equilibrio hacia fuera/hacia dentro

Ejercicio

  1. Inventa un endpoint de tu dominio (ej: POST /api/reservas).
  2. Escribe el test HTTP primero (201).
  3. Implementa la ruta mínima.
  4. Extrae la lógica a una función unitaria.
  5. Añade validación 422 con su rojo correspondiente.

Resumen

  • TDD de fuera hacia dentro: el HTTP guía el diseño.
  • ROJO = ruta/validación que falta; VERDE = mínimo; REFACTOR = extraer.
  • Cada contrato con test HTTP; cada regla con unit.
  • La API crece testeada por capas, no a saltos.
