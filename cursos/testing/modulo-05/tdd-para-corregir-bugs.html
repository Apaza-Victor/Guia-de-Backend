TDD para corregir bugs

🔧 Intermedio 14 min Testing Backend Módulo 5 · TDD

El bug como primer paso del TDD

Un bug reportado es la mejor historia de usuario que hay: ya tienes el ejemplo, el resultado esperado y el resultado real. El TDD para bugs usa exactamente esa triada.

ROJO: reproducir con un test

Falla con 109.99. Ese es el rojo del bug: ya lo tenemos prisionero.

VERDE: la corrección mínima

El test que verificaba el comportamiento viejo (redondear primero) debería ahora actualizarse si era incorrecto, o fallará legítimamente.

Confirma: la suite completa

Si el fix rompió otro test, es una señal real: el cambio afectó un comportamiento que cuidabas. No lo borres: re-lees la intención y decides con datos.

Bugs que deben tener un caso extra

Cultura: un bug = un test para siempre

  • Todo fix sin su test de regresión es una promesa rota de que «no volverá».
  • Escribir el test primero evita que el fix «arregle el síntoma y no la causa» (el test lo demuestra).
  • El commit del bug se vuelve documentación viva: «este caso ya no se rompe, y aquí está el porqué».

Ejercicio

  1. Copia el reporte mínimo: «el total del carrito sale 1 centavo distinto».
  2. Escribe tu test que falla (rojo).
  3. Aplica el fix y verifica el verde.
  4. Corre la suite entera y responde la pregunta: ¿rompí algo?

Resumen

  • El bug se convierte en un test que reproduce y falla.
  • Fix mínimo que respeta la intención del código.
  • Suite completa después: cero regresiones.
  • Un bug = un test de regresión para siempre.
