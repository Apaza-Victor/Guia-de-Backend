Pruebas contractuales

🔧 Intermedio 13 min Testing Backend Módulo 3 · Integración

Qué es un contrato de API

El contrato es el acuerdo tácito entre quien produce una API y quien la consume: qué estructura, qué campos, qué códigos, qué errores. Las pruebas contractuales hacen ejecutable ese acuerdo, para que un cambio de un lado no rompa en silencio al otro.

El contrato: OpenAPI primero

Si tu especificación está versionada, es el «test más importante» que tienes: define qué es válido para siempre.

Matchers: no valores, SÍ estructura

La idea: los tests contractuales verifican forma (tipos, requeridos, rangos), no datos concretos que cambian con cada inventario.

El lado consumidor

El consumidor es quien más sufre el cambio no avisado. Su prueba contractual ideal:

Si el proveedor añade campos, el consumidor no se rompe (usa lo que usa). Si cambia tipos u omite requeridos, el stub del contrato falla y se negocia antes de romper producción.

Herramientas: Pact y más

Cuándo vale la pena

  • Cuando dos equipos (o microservicios) se comunican sin llamarse.
  • Cuando un tercero (SAAS, partner) define la API que tú consumes.
  • Cuando produces una API pública: el contrato ES tu doc.
  • Regla: más vale un contrato escrito hace 3 meses que una conversación de pasillo.

Ejercicio

  1. Define un openapi.yml mínimo para un endpoint tuyo.
  2. Escribe un test de contrato con matchers de estructura.
  3. Cambia un tipo en el endpoint y observa el fallo del test.

Resumen

  • El contrato es el acuerdo; los tests lo hacen ejecutable.
  • OpenAPI versionado = spec como fuente de verdad.
  • Matchers de forma, no valores concretos.
  • El consumidor protege su mundo con stubs del contrato.
