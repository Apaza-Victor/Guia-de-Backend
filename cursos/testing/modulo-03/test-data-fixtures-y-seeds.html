Test data, fixtures y seeds

🔧 Intermedio 14 min Testing Backend Módulo 3 · Integración

Fixture, test data y seed: no son lo mismo

Fixture dentro del test

El mejor lugar para un fixture es el propio test: visible, editable y local.

Los números con intención (100 y 50, no 37.19 y 8.44) hacen que el cálculo sea verificable a ojo.

Factories para no repetir

Cuando un objeto tarda 15 líneas, un factoría en el test reduce ruido y deja que cada test sobreescriba solo lo que importa:

Seeds para dev y demo: sí, pero aislados

  • Los seeds nunca deben tocar la BD de produccion: ejecútalos solo en entornos test/demo.
  • Marca de agua clara: emails con prefijo demo- que el código respete y nunca considere reales.

Cómo se contamina un dataset

La solución: cada test construye sus propios fixtures en su Arrange, explícitos y con intención. Si algo se repite mucho, una factory, nunca un dataset global genérico.

Fixture en archivo vs en código

Para JSON de entrada/salida de APIs, a veces conviene un archivo tests/Fixtures/:

Úsalo solo cuando el dato es grande y formato externo. Para lógica propia, en el test.

Ejercicio

  1. Extrae una ProductoFactory de un test repetido.
  2. Reemplaza el dataset global de tu suite por fixtures locales por test.
  3. Comprueba que cada test pasa en solitario (--filter).

Resumen

  • Fixture local, factory de refactor, seed para arranque.
  • Datos con números intencionales y fecha inyectada.
  • Nunca dependas del orden ni de IDs hardcodeados.
  • Archivo Fixtures solo para payloads externos grandes.
