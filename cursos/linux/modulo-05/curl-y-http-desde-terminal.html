curl: HTTP desde la terminal

💻 Básico 9 min Linux y Terminal para Backend Módulo 5 · Redes y servicios

Introducción

Antes de mirar el código, prueba el endpoint. curl es el cliente HTTP universal de la terminal: ver peticiones, probar respuestas y descargar archivos sin salir del shell.

Con curl haces GET y POST, ves cabeceras, sigues redirecciones y simulas peticiones de una API desde el propio servidor.

Definición

curl es una herramienta de línea de comandos para transferir datos con URL (HTTP, HTTPS, FTP y más), ideal para probar APIs, descargar recursos y depurar servidores.

Por qué importa. Es el primer paso de cualquier diagnóstico del backend: probar el endpoint real, con sus cabeceras y códigos, aísla al instante si el problema es tuyo o del servidor.

Cuándo usarlo. Úsalo para probar endpoints, ver códigos de estado, simular POST con JSON y descargar archivos. Es tu cliente HTTP sin abstracciones.

Conceptos clave

  • curl URL hace un GET y muestra el cuerpo.
  • -i muestra también las cabeceras; -v el diálogo completo.
  • -X POST y -d '...' envían datos.
  • -H 'Content-Type: application/json' fija cabeceras.
  • -o archivo guarda la descarga; -L sigue redirecciones.

Ejemplo básico

Probar la API local con curl y ver cabeceras y código.

Ejemplo intermedio

Simular un POST con JSON contra tu API.

Ejemplo real

Diagnóstico completo de un endpoint en producción: estado, tiempo y contenido.

  • -w saca métricas (código, tiempos) del diálogo.
  • -i distingue cabeceras del cuerpo.
  • Prueba con -d en el localhost antes de echárselas a la red.

curl es tu herramienta de smoke test: si responde bien aquí, el problema está más arriba (proxy, CDN, DNS).

Explicación

  • -i mezcla cabecera y cuerpo; -v revela el handshake completo.
  • -d envía datos; con -X POST cambias el método.
  • -H fija cualquier cabecera: auth, content-type, cookies.
  • -w responde métricas como http_code y time_total.
  • -L sigue redirecciones 301/302.

Errores comunes

  • Olvidar -X POST y que el servidor reciba un GET de tu -d.
  • No fijar Content-Type en POSTs JSON.
  • Simular frente a localhost y olvidar el proxy de producción.

Buenas prácticas

  • Usa -s (silencioso) y -w para automatizar checks.
  • Localiza el endpoint con curl -i antes de abrir el navegador.
  • Guarda los smoke tests curl como scripts.

Ejercicio

  1. Haz un GET de tu API y muestra cabeceras.
  2. Realiza un POST JSON y comprueba el 201.
  3. Mide con -w el código y el tiempo de un endpoint.

Resumen

  • curl es tu cliente HTTP universal en la terminal.
  • -i, -v, -d, -H y -w cubren la mayoría de los casos.
  • Un smoke test con curl aísla el problema en segundos.
