DNS y resolución de nombres

💻 Básico 9 min Linux y Terminal para Backend Módulo 5 · Redes y servicios

Introducción

Escribes api.ejemplo.com y el sistema la convierte en una IP. Ese puente invisible es el DNS, la libreta telefónica que hace utilizable Internet.

Cuando 'no resuelve', la causa está en la cadena DNS: tu resolv.conf, el servidor que consulta o el registro del dominio.

Definición

El DNS traduce nombres de dominio a direcciones IP mediante una jerarquía de servidores. Para verificar, dig (o nslookup) consulta registros A, CNAME, MX y demás.

Por qué importa. Tu backend se alcanza por nombre: si DNS falla, ni curl ni los clientes llegarán a la API, y el problema parece 'el servidor caído'.

Cuándo usarlo. Diagnostica con dig ante fallos de resolución, cambios de DNS recientes o al apuntar un dominio a un nuevo VPS.

Conceptos clave

  • resolv.conf define qué servidores DNS usa el sistema.
  • dig nombre resuelve por registros.
  • Los tipos A/AAAA ips, CNAME alias, MX correo.
  • El registro A de api.ejemplo.com apunta a la IP del VPS.
  • Los cambios de DNS tardan (TTL) en propagar por todo el mundo.

Ejemplo real

Apuntar tu dominio a un VPS nuevo: creas los registros A y CNAME, y compruebas la propagación desde varios puntos.

  • Registros A para el dominio raiz y subdominios.
  • Usa 1.1.1.1/8.8.8.8 para contrastar.
  • El TTL corto facilita los cambios, largo reduce consultas.

El check de DNS con dig @otroResolvedor te dice si el problema es tu red o el registro del dominio.

Explicación

  • resolv.conf configura la librería de resolución del sistema.
  • dig hace consultas crudas a los servidores DNS.
  • El TTL indica cuánto cachean los resolvedores.
  • A para IPv4, AAAA para IPv6, CNAME alias, MX correo.
  • getent comprueba la resolución que usaría el sistema.

Errores comunes

  • Confundir un fallo de DNS con un servidor caído.
  • Olvidar el TTL y esperar cambios inmediatos.
  • Añadir CNAME a un dominio raiz (toque RFC).

Buenas prácticas

  • Dig era arma de diagnóstico: aprendelo bien.
  • Contrasta siempre con @1.1.1.1 o @8.8.8.8.
  • Mide los tiempos: un DNS lento degrada tu backend.

Ejercicio

  1. Resuelve tu dominio con dig tanto A como CNAME.
  2. Comprueba la propagación con dos resolvedores diferentes.
  3. Consulta los MX de tu dominio.

Resumen

  • El DNS traduce nombres a IPs mediante registros.
  • dig y getent diagnostican la cadena de resolución.
  • El TTL rige la propagación de los cambios.
