Despliegue con Nginx y PHP-FPM

⚙️ Intermedio 12 min PHP desde cero hasta avanzado Módulo 7 · Seguridad y despliegue

Introducción

Llevar el código a un servidor real implica decidir quién sirve los archivos y quién ejecuta el PHP. Nginx se destaca por su velocidad sirviendo estáticos y su configuración clara para PHP.

Nginx y PHP-FPM trabajan en equipo: Nginx recibe la petición, entrega los estáticos él mismo y pasa lo dinámico a PHP-FPM por un socket Unix, que ejecuta tu código y devuelve la respuesta.

Definición

PHP-FPM (FastCGI Process Manager) ejecuta los scripts PHP como un servicio independiente. Nginx actúa de servidor web: sirve estáticos, aplica reescrituras y delega el .php a FPM por fastcgi.

Por qué importa. Separar el servidor web del ejecutor permite escalar FPM por separado, servir estáticos muy rápido y aislar fallos de una app del resto del servidor.

Cuándo usarlo. En producción usa esta arquitectura (o Apache+mod_php si ya lo tienes). Para desarrollo, el servidor integrado php -S sirve, pero no es para producción.

Conceptos clave

  • El block server {} define un virtual host de Nginx.
  • root apunta a la carpeta public/ de la aplicación.
  • try_files redirige toda petición al front controller.
  • location ~ \.php$ declara cómo ejecutar el PHP con fastcgi.
  • OPcache en php.ini acelera reutilizando el opcode compilado.

Ejemplo real

El despliegue de verdad cuida permisos y entornos: el usuario del proceso no escribe en el código, los secretos vienen de variables y los logs quedan claros.

  • El docroot es solo public/: el resto del repo queda fuera del alcance web.
  • Permisos mínimos: el proceso de FPM escribe solo donde hace falta.
  • Configuración y secretos fuera del código, vía variables de entorno.

con opcache.validate_timestamps=0 debes recargar FPM al desplegar (systemctl reload php8.2-fpm). Asegúrate de incluir ese reload en el script de deploy.

Explicación

  • Nginx sirve estáticos a toda velocidad y delega el PHP por FastCGI.
  • try_files reenvía todo lo no estático al front controller de la app.
  • La ubicación \.php$ decide qué ejecuta FPM; se incluye fastcgi-php.conf.
  • OPcache reutiliza el código compilado y reduce drásticamente el CPU.
  • Los permisos mínimos y secretos externos blindan el servidor.

Errores comunes

  • Poner root en /var/www/tienda en vez de public/ y quedar expuesto a src/.
  • Olvidar reload de FPM con opcache.validate_timestamps=0 y desplegar "nada".
  • Confundir sockets Unix y TCP: ambos deben coincidir en Nginx y FPM.

Buenas prácticas

  • Haz que el docroot sea public/: nunca expongas el código completo.
  • Prueba Nginx con nginx -t antes de recargar.
  • Revisa los logs de error de Nginx y FPM en cada despliegue.
  • Automatiza el deploy con un script que corra tests y recargas.

Ejercicio

  1. Escribe un virtual host de Nginx para tu aplicación y verifícalo con nginx -t.
  2. Configura OPcache y mide la mejora con un benchmark sencillo.
  3. Crea un script deploy.sh que haga pull, install y recargos sin downtime.

Resumen

  • Nginx sirve estáticos y delega el PHP a PHP-FPM por FastCGI.
  • OPcache reutiliza el opcode y acelera el runtime en producción.
  • Docroot en public/, secretos por entorno y permisos mínimos blindan el deploy.
