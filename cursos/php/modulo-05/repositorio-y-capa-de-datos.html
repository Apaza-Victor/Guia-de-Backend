Repositorio y capa de datos

⚙️ Intermedio 12 min PHP desde cero hasta avanzado Módulo 5 · Base de datos con PDO

Introducción

Cuando el SQL se esparce por controladores y servicios, cambiar una tabla significa rebuscar en todo el proyecto. La solución madura es aislar la persistencia en una capa de repositorios.

Un repositorio centraliza las consultas de un agregado (pedidos, usuarios, productos) y expone métodos intencionales en lugar de strings SQL.

Definición

El patrón Repository encapsula el acceso a datos de una entidad: cada repositorio recibe la conexión (PDO) por inyección y ofrece métodos del dominio como porId($id) o guardar($data), ocultando el SQL a quien lo consume.

Por qué importa. Aísla las sentencias SQL, simplifica los tests (puedes usar dobles) y facilita cambiar el motor o la tabla sin tocar la lógica de negocio.

Cuándo usarlo. Aplícalo cuando la consultas de una entidad se repiten en varios sitios. En scripts pequeños, sirve igual como arquitectura que crecerá contigo.

Conceptos clave

  • El repositorio recibe el PDO en el constructor (inyección de dependencias).
  • Los métodos de dominio devuelven datos ya listos: ?array, objeto o lista.
  • La capa de servicio decide qué dato pedir, nunca cómo pedirlo.
  • Las transacciones se coordinan en servicios que usan el mismo PDO.
  • Un repositorio por agregado mantiene la capa fina y comprensible.

Ejemplo real

En una API, el controlador pide al servicio los datos y el servicio orquesta varios repositorios dentro de una transacción compartida.

  • El repositorio nunca recibe un objeto Request ni escribe respuestas HTTP.
  • Devuelve estructuras simples (arrays o DTOs) a la capa de servicio.
  • Las transacciones se abren en el servicio con el PDO compartido.

Esperado: repositorios inyectados en el servicio y el mismo PDO para coordinar transacciones. Este es el esqueleto de un backend PHP mantenible.

Explicación

  • La inyección del PDO por constructor hace que cada repositorio sea testeable.
  • Los métodos del dominio ocultan el SQL y dan intención al consumidor.
  • El repositorio devuelve estructuras listas: arrays o DTOs, nunca records.
  • Las transacciones se gestionan en servicios orquestadores.
  • Un agregado = un repositorio mantiene el tamaño y la claridad de la capa.

Errores comunes

  • Pegar SQL en los controladores en lugar de delegar en el repositorio.
  • Devolver el PDOStatement desde el repositorio (fuga de la capa de datos).
  • Instanciar un nuevo PDO dentro de cada método del repositorio.

Buenas prácticas

  • Inyecta el PDO una vez y compártelo entre repositorios.
  • Devuelve datos ya formateados: ?array o DTO, nunca el statement.
  • → Empieza con un único repositorio y extrae cuando veas repetirte.

Ejercicio

  1. Crea un UsuarioRepositorio con porEmail y crear.
  2. Encapsula una consulta que esté duplicada en dos controladores.
  3. Orquesta dos repositorios en un servicio dentro de una transacción.

Resumen

  • El repositorio encapsula el SQL y expone métodos intencionales.
  • La inyección de PDO por constructor lo hace testeable y claro.
  • Las transacciones las coordina el servicio con el mismo PDO compartido.
