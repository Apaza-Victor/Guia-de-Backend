Front controller y enrutado

⚙️ Intermedio 12 min PHP desde cero hasta avanzado Módulo 6 · APIs y servicios

Introducción

Cuando cada página tenía su propio archivo PHP, el mantenimiento se convertía en una jungla. El patrón front controller concentra todas las peticiones en un único archivo que decide qué parte del código atiende.

Así controlas en un solo sitio el log, la autenticación, las cabeceras y el enrutado antes de que la petición toque tu lógica.

Definición

Un front controller es un único script (normalmente public/index.php) que recibe todas las peticiones, las enruta según la URI y el método y delega en el controlador correspondiente.

Por qué importa. Unifica el ciclo de vida de la petición (middlewares, cabeceras, errores) y evita que cada endpoint repita la misma lógica de arranque.

Cuándo usarlo. Úsalo en toda API; para sitios muy pequeños seguirás necesitando al menos un index.php que ordene la entrada.

Conceptos clave

  • El front controller es el único archivo PHP accesible desde la web.
  • La URI se normaliza con parse_url() y se compara contra las rutas.
  • Router: tabla de rutas que mapea (método, patrón) a un controlador.
  • El método HTTP (GET, POST) forma parte del contrato de la ruta.
  • Las rutas desconocidas devuelven 404 de forma centralizada.

Ejemplo básico

Un front controller mínimo que enruta dos URIs y responde 404 el resto.

GET /salud -> {"status":"ok"}; GET /otra -> 404 con JSON de error.

Ejemplo intermedio

Una ruta configura el controlador y el método a invocar en un solo mapa.

Ejemplo real

El servidor web redirige todas las peticiones al front controller con reglas de reescritura, de modo que URLs limpias como /pedidos/42 acaben en index.php.

  • Redirige con Nginx: try_files $uri /index.php?$query_string;.
  • Nunca expongas archivos internos: el docroot es la carpeta public/.
  • Deja que el router construya las URLs limpias, sin extensión .php.

El front controller se convierte en tu capa de arranque: ahí conectas la base de datos, cargas autoload e inicias la aplicación antes de enrutar.

Explicación

  • Todas las peticiones pasan por index.php, que concentra arranque y router.
  • La URI se normaliza y se combina con el método para buscar la ruta.
  • El 404 es centralizado: respuesta uniforme para rutas inexistentes.
  • las reglas de reescritura hacen que las URLs limpias no pierdan query strings.
  • El arranque vive en el front controller: autoload, errores y configuración.

Errores comunes

  • Perder los query params al reescribir la URL (falta $query_string).
  • Exponer el directorio raíz como docroot y servir archivos internos sueltos.
  • No contemplar el método HTTP y enrutar solo por URI.

Buenas prácticas

  • Mantén cero lógica de negocio en index.php: solo arranque y dispatch.
  • Empieza con rutas exactas y pasa a patrones con parámetros cuando las necesites.
  • Usa una sola respuesta JSON de error para 404 y 405 uniforme.

Ejercicio

  1. Añade una ruta POST /pedidos a tu router y compruébala con curl.
  2. Implementa el 405 para rutas existentes con método incorrecto.
  3. Aísla el arranque (DB, autoload) en un bootstrap.php llamado por index.php.

Resumen

  • El front controller convierte un único archivo en el centro de la aplicación.
  • El router mapea método + URI hacia un controlador en un mapa claro.
  • Las reglas de reescritura dan URLs limpias dirigidas a index.php.
