La regla de dependencia

🔥 Avanzado 10 min Arquitectura de Software Módulo 5 · Clean Architecture

Introducción

Toda la Clean Architecture se resume en una sola línea: las dependencias del código fuente apuntan siempre hacia dentro, hacia el núcleo del negocio. Esta «regla de dependencia» es lo que hace que los frameworks, las bases de datos y los transports sean reemplazables sin tocar el dominio.

¿Qué significa «hacia dentro»?

Imagina círculos concéntricos. Lo más externo es lo más «técnico» (framework, DB, HTTP, mail) y lo más interno es lo más «de negocio» (entidades, casos de uso). La regla dice que el código de un círculo nunca puede depender de los detalles de un círculo más exterior.

  • Domain → nada externo. Cero imports de framework.
  • Application/casos de uso → puede usar entidades y definir interfaces del mundo exterior.
  • Infrastructure → implementa las interfaces que el dominio/application definió.

Cuando se invierte la flecha (el dominio conoce la infraestructura), el detalle externo contagia al corazón y la lógica dejo de sercribe en términos de negocio.

El truco: dependencia invertida

¿Cómo logra la infraestructura «depender» del dominio a la vez que el dominio la llama tranquilamente? Con interfaces invertidas:

El dominio declara «necesito un repositorio» (puerto) y la infraestructura decide con qué (implementación). El flujo del control emite hacia afuera; la flecha de dependencia apunta hacia dentro. Exactamente la misma idea que DI.

Qué se gana

  • Reemplazabilidad: cambiar de BD toca un adaptador, no el negocio.
  • Testabilidad: la lógica de dominio se testea con implementaciones falsas en memoria.
  • Migración de framework: si mañana cambias Laravel por Symfony, el core se declara intacto.
  • Legibilidad: el código cuenta la historia del negocio, no la de la pila técnica.

Ejercicio

  1. Encuentra dónde tu dominio (entidad/servicio de negocio) importa una clase del framework.
  2. Define en el dominio la interfaz (puerto) que desacople esa necesidad.
  3. Mueve la implementación concreta a infraestructura.

Resumen

  • La regla de dependencia: las flechas apuntan hacia dentro (hacia el dominio).
  • El dominio define puertos (interfaces); la infraestructura los implementa.
  • Débalo o no: DI + interfaces invertidas = la regla cumplida.
  • El beneficio: framework y BD reemplazables, dominio testeable.
