Cliente-servidor y aplicaciones web

🔥 Avanzado 9 min Arquitectura de Software Módulo 2 · Estilos

Introducción

El estilo cliente-servidor es el fundamento de casi toda aplicación web y móvil: un cliente (navegador, app, otro servicio) hace peticiones a un servidor que procesa y responde. El servidor es centralizado: concentra la lógica, los datos y el control de acceso.

Su variante actual más popular es la arquitectura de dos capas con API: frontend (SPA) + API backend + base de datos.

Roles y responsabilidades

Cliente
Captura la interacción del usuario, hace peticiones y renderiza. Puede ser «gordo» (SPA con mucha lógica) o «delgado» (solo HTML).
Servidor
Recibe peticiones, valida, aplica reglas, consulta datos y responde. Posee la fuente de verdad.
Apache/Nginx/Framework
El servidor web que despierta el código, sirve estáticos y enruta.

La separación física permite: múltiples clientes (web, iOS, Android) compartiendo el mismo backend, y escalar el servidor de forma independiente.

El principio de statelessness

Un servidor stateless no guarda información del cliente entre peticiones: cada request trae todo lo necesario (tokens, headers) para ser comprendida por sí sola. Las consecuencias son arquitectónicas:

  • Puedes ejecutar muchas instancias del servidor sin sincronizar memoria entre ellas.
  • Un load balancer reparte peticiones a cualquier instancia sin problemas de sesión atada a una máquina.
  • Es más fácil escalar de forma horizontal (más servidores) en lugar de vertical (una máquina gigante).

El estado se externaliza a la base de datos, la caché (Redis) o tokens firmados como JWT.

Variedades de la arquitectura web

Multi-page (MPA)
El servidor genera HTML en cada petición (PHP + Blade, Django templates). Simple y potente para SEO.
Single-page (SPA)
El frontend es una app que solo habla JSON con la API. Experiencia fluida, pero más lógica en el cliente.
Server-rendered con hidratación
Vué/React renderizado en servidor por velocidad, luego hidratado en el navegador.
API-only
Backend que solo expone una API consumida por cualquier cliente externo: la base de los microservicios.

Ejemplo de flujo

El token viaja en cada request; el servidor no guarda nada entre llamadas. Si mañana hay 3 instancias de la API detrás de un balanceador, el flujo no cambia en absoluto.

Ejercicio

  1. Identifica si tu app favorita es MPA, SPA o híbrida, y qué API consume.
  2. Explica qué pasa con las sesiones de PHP si hoy «viven» en memoria del servidor y duplicas las instancias.
  3. Dibuja el flujo cliente-API-datos de un login real (token, validación, respuesta).

Resumen

  • Cliente-servidor separa presentación y lógica en procesos distintos.
  • Un servidor stateless permite escalar horizontalmente sin problemas.
  • Las arquitecturas web van de MPA a SPA y API-only.
  • El estado vive fuera del proceso: en la BD, la caché o los tokens.
