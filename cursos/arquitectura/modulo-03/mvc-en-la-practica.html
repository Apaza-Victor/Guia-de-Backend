MVC en la práctica

🔥 Avanzado 11 min Arquitectura de Software Módulo 3 · Patrones

Introducción

MVC (Model-View-Controller) es el patrón más difundido del backend: separa el acceso a los datos (Model), la representación de la salida (View) y la orquestación de la petición (Controller). Todos los frameworks populares —Laravel, Express, Spring— lo usan en alguna forma.

Su valor real no es técnico: es disciplina. Establece dónde vive cada preocupación para que el código no se mezcle.

Los tres roles

Controller
Recibe la petición, valida la entrada, llama al modelo (o servicio) y decide la respuesta. Debe ser delgado: solo orquesta.
Model
Representa los datos y la lógica de negocio asociada (entidades, repositorios, servicios). En backend suele ser la capa de dominio + datos.
View
Renderiza la salida: un template HTML o un JSON para la API. No contiene lógica de negocio.

El flujo clásico: HTTP → Controller → Model → Controller → View → HTTP.

El anti-patrón del controller gordo

El error número uno de MVC es el fat controller: miles de líneas que validan, consultan, calculan y serializan. Síntomas: métodos que no se pueden testear, SQL dentro del controlador y lógica duplicada entre endpoints.

La solución es extraer: validación → FormRequest; lógica de negocio → Service Layer; consultas → Repository. El controlador se queda con 5 líneas de orquestación.

Ejemplo: controlador delgado

El controlador ahora es un «traductor»: valida, llama y responde. La regla de cálculo de total e impuestos vive en el servicio, donde puede testearse sola.

MVC y las arquitecturas modernas

MVC sigue siendo la puerta de entrada: el Controller = presentación, el Model crece hasta convertirse en dominio y aparecen las capas de servicio y repositorio. Clean Architecture y Hexagonal son refinamientos de esta misma separación, no su sustitución.

Ejercicio

  1. Identifica en tu código un controlador con más de 30 líneas y marca qué partes son validación, negocio y datos.
  2. Extrae la lógica de cálculo a una clase de servicio (Service Layer).
  3. Responde por escrito: ¿qué le pasa a un controller gordo cuando llega la segunda vista/API?

Resumen

  • MVC separa datos (modelo), salida (vista) y orquestación (controlador).
  • El controlador debe ser delgado: validar, llamar y responder.
  • El fat controller es el síntoma más peligroso; se cura con servicios y repositorios.
  • MVC es la base de las arquitecturas modernas de capas.
