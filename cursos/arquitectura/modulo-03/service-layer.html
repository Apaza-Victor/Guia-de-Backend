Service Layer

🔥 Avanzado 10 min Arquitectura de Software Módulo 3 · Patrones

Introducción

El Service Layer (capa de servicios) es la capa de aplicación que define los casos de uso del sistema: «crear pedido», «devolver producto», «cambiar contraseña». Cada servicio expone un método por operación de negocio y es el único lugar donde se orquesta la lógica que antes se colaba en los controladores.

Su existencia viene de una observación simple: cuando hay que hacer lo mismo desde un endpoint HTTP y desde un comando de consola, esa lógica no puede vivir en el controlador.

Responsabilidades de un servicio

  • Ejecutar un caso de uso de principio a fin.
  • Orquestar repositorios y colaboradores (mailer, pagos, eventos).
  • Gestionar transacciones en operaciones compuestas.
  • Devolver un resultado claro al controlador (éxito, error de dominio, error de infraestructura).
  • Defender las invariantes de negocio antes de persistir.

Un servicio suele tener 1-4 métodos públicos, todos referidos a operaciones de negocio concretas. Si el tuyo tiene 20, probablemente es un «utility» disfrazado de servicio.

Cómo se ve en el código

Nótese: el servicio no sabe nada de HTTP. El mismo método lo puede llamar un controlador, un comando CLI o un event listener. Eso lo hace reutilizable y testeable.

Transacciones en la capa de servicios

Cuando un caso de uso escribe en varios lugares, debe ser atómico. La transacción se abre en el servicio (que conoce todo el alcance de la operación), no en el repositorio:

Si el segundo guardar falla, todo se revierte; el dinero nunca «se pierde a mitad del camino».

Errores comunes

  • Servicio-transported: copiar el servicio a cada framework en vez de compartirlo.
  • Servicios anémicos: solo llaman a repositorios sin aplicar reglas de negocio (se vuelven DLL de datos).
  • Transacciones en el controlador: se pierde la atomicidad cuando hay varias entradas.
  • Métodos genéricos: `procesar()` sin nombre de caso de uso.

Ejercicio

  1. Elige un flujo de tu proyecto (por ejemplo, «crear usuario + enviar correo») y extrae su lógica a un servicio.
  2. Mueve la transacción al servicio si la estabas manejando en el controlador.
  3. Escribe los casos de uso de tu sistema como una lista de métodos de servicios.

Resumen

  • El Service Layer centraliza los casos de uso del sistema.
  • No conoce HTTP: sirve a cualquier entrada (controlador, CLI, eventos).
  • Es el lugar correcto para transacciones multi-escritura.
  • Los servicios son útiles si aplican reglas de negocio, no si solo serializan datos.
