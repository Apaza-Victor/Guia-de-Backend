¿Qué es arquitectura de software?

🔥 Avanzado 8 min Arquitectura de Software Módulo 1 · Fundamentos

Introducción

Imagina que te encargan construir un edificio. Podrías empezar a poner ladrillos de inmediato y, a mitad de camino, darte cuenta de que no hay dónde instalar los ascensores o que el techo pesa más de lo que las columnas pueden soportar. Eso mismo le ocurre al software sin arquitectura: funciona un rato, y después cada cambio cuesta carísimo porque «el techo no aguanta».

La arquitectura de software es el conjunto de decisiones estructurales que dan forma a un sistema antes de que el código crezca: qué partes lo componen, cómo se comunican, por dónde fluyen los datos y qué reglas rigen los cambios. Es la columna vertebral del proyecto.

Los componentes de la arquitectura

Cuando hablamos de arquitectura hablamos de piezas grandes y de las relaciones entre ellas. Algunos ejemplos:

  • Componentes: el frontend, la API, la base de datos, un worker de colas, un servicio de correo.
  • Conectores: REST, GraphQL, colas de mensajes, eventos, sockets.
  • Datastores: bases SQL, bases NoSQL, cachés, almacenes de archivos.
  • Reglas de dependencia: qué capa puede llamar a cuál y quién no puede importar a quién.

Definir papeles como director de orquesta que reparte responsabilidades entre módulos, la arquitectura determina el esqueleto del sistema antes de que escribamos los músculos.

Arquitectura vs diseño

Hay una diferencia de escala muy útil:

  • Diseño (bajo nivel): decisiones locales que se pueden cambiar en horas o días. Cómo se llama una clase, cómo se ordena una lista, qué algoritmo usar.
  • Arquitectura (>alto nivel): decisiones estructurales difíciles o muy costosas de revertir. Qué base de datos usar, si el sistema es un monolito o microservicios, cómo se cachea y dónde vive la lógica de negocio.

Regla práctica: la arquitectura es la parte del sistema cuya decisión tardaría semanas o meses en corregirse si estuviera equivocada.

Por qué importa

Los sistemas crecen. Lo que hoy es una API con tres endpoints, mañana es un ecosistema con miles de usuarios concurrentes. Sin una estructura pensada, cada feature nuevo cuesta más que el anterior y el equipo frena. Con una buena arquitectura, el coste crece de forma lineal o incluso se aplana: porque el sistema está preparado para absorber el cambio.

Ejercicio

  1. Elige una aplicación que conozcas (una API, una tienda, tu proyecto propio) y dibuja sus componentes principales en un papel: frontend, API, BD, caché, colas.
  2. Clasifica cada decisión que se te ocurra en arquitectónica o de diseño. Ejemplo: «usar MySQL» es arquitectónica.
  3. Responde por escrito: si mañana cambias de MySQL a PostgreSQL, ¿cuánto tendrías que tocar y por qué? Ese esfuerzo es el coste de una decisión arquitectónica.

Resumen

  • La arquitectura es el conjunto de decisiones estructurales difíciles de cambiar.
  • Se compone de componentes, conectores, datastores y reglas de dependencia.
  • Se diferencia del diseño de bajo nivel por la escala y el coste de revertirla.
  • Sin arquitectura, cada cambio nuevo se vuelve más caro y el equipo más lento.
