Migrar de REST a GraphQL

🔥 Avanzado 11 min GraphQL Módulo 7 · GraphQL en producción

Introducción

Pasar un sistema entero de REST a GraphQL de golpe es la receta del desastre. La estrategia real es de coexistencia: GraphQL llama internamente a los mismos servicios que REST y ambos se sirven a la vez.

Se envuelve, se extiende, se observa y, cuando un endpoint queda sin clientes, se retira. Así la migración no corta operación ni obliga a un apagón.

Definición

La migración incremental envuelve los sistemas REST existentes con resolvers, coexisten ambos APIS y retira los endpoints obsoletos por el uso real.

Por qué importa. GraphQL no obliga a tirar REST: la envoltura da valor inmediato y permite migrar con cero downtime.

Cuándo usarlo. Migra cuando tengas problemas de overfetch, N+1 en el cliente o muchas peticiones encadenadas; envuelve primero lo que más duela.

Conceptos clave

  • Un resolver puede llamar al servicio REST interno existente.
  • El overfetch y el N+1 se resuelven al recombine datos en el resolver.
  • REST y GraphQL conviven en el mismo dominio.
  • Se retira un endpoint cuando la telemetría confirma uso cero.
  • La migración es por dominio, no por recurso individual.

Ejemplo básico

Un resolver que llama al REST interno para traer una publicación.

Tenemos GraphQL encima de REST sin reescribir el servicio.

Ejemplo intermedio

Resolver el N+1 que el cliente sufria en REST con un solo batch interno.

Ejemplo real

La telemetría decide el retiro: si un endpoint REST lleva semanas sin uso, se archiva.

  • Empieza por el cliente que más sufre: overfetch o muchas llamadas.
  • Mide el uso de cada endpoint antes de retirarlo.
  • Añade paginacion y filtros también en GraphQL para no perder funcionalidad.

La coexistencia da plan B: si GraphQL falla, el cliente puede volver a REST.

Explicación

  • El resolver que llama a REST hereda su comportamiento: es una traducción de contrato.
  • El overfetch se corrige porque el resolver solo pide el campo pedido.
  • El N+1 del cliente (muchas peticiones REST) se convierte en un resolver con batched.
  • La telemetría de endpoints dirige el plan de retirada.
  • La migración por dominio mantiene bloques clínicos de adopción.

Errores comunes

  • Reescribir todo el backend de REST a GraphQL de una vez.
  • Olvidar la paginación o el filtrado en GraphQL.
  • Retirar REST sin confirmar uso cero con telemetría.

Buenas prácticas

  • Envuelve primero lo que duele: endpoints con overfetch o cadenas de llamadas.
  • Coexisten ambas APIs durante la transición.
  • Registra tiempo de respuesta de REST y de GraphQL para comparar.
  • Migra dominio por dominio, no recurso a recurso.

Ejercicio

  1. Envuelve un endpoint REST en un resolver GraphQL.
  2. Agrupa el N+1 de autores con Promise.all.
  3. Mide el uso de un endpoint y decide su retirada.

Resumen

  • GraphQL envuelve REST sin apagón: coexisten y migran por dominio.
  • Resolver desde REST hereda su contrato y resuelve overfetch.
  • La telemetría guía la retirada de los viejos endpoints.
