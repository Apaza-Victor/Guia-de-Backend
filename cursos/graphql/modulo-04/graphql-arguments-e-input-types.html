Argumentos e input types

🔥 Avanzado 11 min GraphQL Módulo 4 · Queries y resolvers avanzados

Introducción

A medida que tu API crece, los argumentos dejan de ser un simple id o un filtro de una sola línea. El mismo set de entradas se repite en queries, mutations y filtros: ahí nacen los input types.

GraphQL permite definir tipos de entrada reutilizables, anidables y obligatorios, lo que convierte tus argumentos en un contrato tan explícito como el schema de salida.

Definición

Un input type es un tipo de GraphQL pensado para la entrada: define la forma de los argumentos, sus campos y obligatoriedad, y puede contener otros inputs o listas.

Por qué importa. Los inputs evitan repetir argumentos sueltos en cada operación, validan la forma de los datos en tiempo de ejecución y documentan la API por sí solos.

Cuándo usarlo. Usa inputs para mutaciones complejas, filtros avanzados o cuando el mismo grupo de argumentos se repite en más de una operación.

Conceptos clave

  • input define un tipo de entrada, distinto de los type de salida.
  • Un campo obligatorio se marca con ! y un default con =.
  • Los inputs pueden anidar otros inputs y listas.
  • Los argumentos se declaran en resolver como args y ya validados.
  • Con Apollo Server los inputs se reflejan en la introspección.

Ejemplo real

En un backend real los inputs se combinan con validación en el resolver y con tipos enumerados para campos controlados.

  • Marca ! lo que nunca puede faltar y da defaults con sensatez.
  • Usa enums en lugar de strings libres para estados o categorías.
  • Valida en el resolver además de confiar en la forma del input.

La validación estructural del input es automática; la semántica (que el id exista) sigue siendo tuya.

Explicación

  • Los input types no pueden contener resolvers: son datos puros de entrada.
  • Un argumento sin ! admite null y por tanto ausencia; con ! el cliente debe enviarlo.
  • Los enums reducen los errores por tipeo y mejoran la documentación.
  • Apollo Server valida los inputs contra el schema antes de invocar al resolver.
  • Anidar inputs permite operaciones complejas sin explosión de argumentos planos.

Errores comunes

  • Usar type en lugar de input para datos de entrada.
  • Repetir un montón de argumentos sueltos en vez de agruparlos.
  • Olvidar el ! en un campo que la lógica de negocio exige.

Buenas prácticas

  • Agrupa todos los filtros de un recurso en un solo input.
  • Nombra los inputs con sufijos como Input o Filtro.
  • Aprovecha los defaults para que el cliente envíe lo mínimo.
  • Documenta cada campo con descripciones en el propio schema.

Ejercicio

  1. Define un FiltroPublicaciones y úsalo en dos queries.
  2. Crea un input CrearPostInput con autor anidado.
  3. Cambia un campo suelto de mutation por un input con default.

Resumen

  • Los input types estructuran la entrada y la validan por forma.
  • Se anidan, se listan y admiten defaults y enums.
  • La semántica la validas tú: la forma la valida GraphQL.
