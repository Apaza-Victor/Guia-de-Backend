Resolvers y contexto

🔥 Avanzado 11 min GraphQL Módulo 4 · Queries y resolvers avanzados

Introducción

Un resolver es una función con signatura fija que GraphQL invoca cuando un cliente pide un campo. Gracias al cuarto argumento —context— cada resolver puede compartir datos de la petición: usuario autenticado, carga de base de datos o la instancia de un DataLoader.

Entender cómo se encadenan los resolvers te permite estructurar consultas profundas sin repetir trabajo ni perder seguridad.

Definición

Los resolvers son funciones (raiz, args, context, info) que determinan el valor de cada campo; el contexto es un objeto compartido a lo largo de una misma petición.

Por qué importa. El contexto centraliza dependencias —usuario, conexiones, DataLoaders— y evita que cada resolver se autentique o abra su propia conexión.

Cuándo usarlo. Usa contexto para identidad, idioma, tenant o servicios compartidos; no metas datos voluminosos que caducan entre peticiones.

Conceptos clave

  • Todos los fields tienen resolver, aunque GraphQL te dé uno por defecto.
  • El contexto se crea una vez por petición y viaja a todos los resolvers.
  • Puedes sobrescribir el contexto con headers como Authorization.
  • Un resolver encadena al del padre: recibe el objeto resuelto.
  • El mismo resolver de una lista se reutiliza por cada elemento.

Ejemplo real

En una API real el contexto suele reunir identidad, idioma y servicios, y un middleware valida el token antes de ejecutar la query.

  • Valida la identidad en el contexto y lanza errores tempranos.
  • Crea los DataLoaders por petición y colócalos en context.
  • No compartas datos mutables entre peticiones en un servidor multi-tenant.

El contexto también existe en suscripciones: aprovéchalo para autorizar el socket.

Explicación

  • GraphQL resuelve cada campo de forma independiente y luego compone el objeto de respuesta.
  • El resolver por defecto devuelve la propiedad del mismo nombre del objeto padre.
  • El contexto se crea al inicio y se destruye al final: nunca lo guardes globalmente.
  • Encadenar resolvers permite dividir el trabajo: cada nivel solo conoce lo que le toca.
  • El orden de resolución es por capas: primero los campos de nivel superior, después los anidados.

Errores comunes

  • Olvidar pasar el contexto y recrear conexiones en cada resolver.
  • Guardar datos del usuario en una variable global compartida entre peticiones.
  • Resolver campos anidados con N consultas en lugar de usar un loader.

Buenas prácticas

  • Valida el token una vez en el contexto, no en cada resolver.
  • Nombra los resolvers con el patrón campo + raiz para trazar errores.
  • Registra el tiempo de cada resolver para detectar los lentos.
  • Usa info.fieldNodes cuando quieras optimizar según los campos pedidos.

Ejercicio

  1. Añade un campo autor a Post y resuélvelo desde el contexto.
  2. Expón el usuario actual como campo de la Query raiz.
  3. Pasa un DataLoader en el contexto y úsalo en dos resolvers.

Resumen

  • Cada campo tiene un resolver y el contexto se comparte por petición.
  • El contexto concentra identidad y dependencias: valida una sola vez.
  • Encadenar combinado con loaders produce consultas de bajo coste.
