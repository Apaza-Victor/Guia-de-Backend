Subscriptions

🔥 Avanzado 10 min GraphQL Módulo 3 · Avanzado y producción

Introducción

Una query lee, una mutation escribe y una subscription escucha: el servidor empuja datos al cliente cuando ocurre un evento, sin que el cliente tenga que preguntar. Es la forma que tiene GraphQL de ofrecer tiempo real sobre WebSocket.

Los casos típicos son los mismos que estudiaste en el curso de WebSockets: notificaciones, chats, feeds en vivo, paneles de monitoreo, colaboración y estados de pedidos que cambian en marcha.

El tercer tipo raíz

La subscription se declara en el schema como un tipo raíz más. Cada campo de Subscription describe un evento al que el cliente puede conectarse:

type Subscription {
  nuevoMensaje(canalId: ID!): Mensaje!
}

type Mensaje {
  id: ID!
  canalId: ID!
  texto: String!
  autor: Usuario!
  enviadoEn: String!
}

El cliente no hace la "petición" de datos: establece una conexión persistente y espera que el servidor le envíe cada evento que cumpla el filtro (aquí, por canalId).

PubSub: el bus en memoria

El servidor necesita un mecanismo para conectar los eventos a los suscriptores. En Apollo se usa un PubSub, a menudo en memoria para empezar:

import { PubSub } from "graphql-subscriptions";

const pubsub = new PubSub();
const CANAL_NUEVO_MENSAJE = "nuevo_mensaje";
let contador = 0;

La constante es el nombre del "canal" interno: las mutations publican en él y las subscriptions escuchan. En producción, PubSub en memoria no sirve con múltiples instancias; se sustituye por Redis, como verás al escalar.

Resolver de suscripción

Un resolver de subscription no devuelve un valor directo; expone un subscribe que escucha el canal. La mutation, al guardar el mensaje, publica el evento:

const resolvers = {
  Mutation: {
    enviarMensaje: (parent, { canalId, texto }, context) => {
      const mensaje = {
        id: String(++contador),
        canalId,
        texto,
        autor: context.usuario,
        enviadoEn: new Date().toISOString(),
      };
      pubsub.publish(CANAL_NUEVO_MENSAJE, { nuevoMensaje: mensaje });
      return mensaje;
    },
  },
  Subscription: {
    nuevoMensaje: {
      subscribe: (parent, { canalId }) => pubsub.asyncIterator(CANAL_NUEVO_MENSAJE),
    },
  },
};

El contrato es publish(tema, payload) aquí y subscribe allá. La clave del payload coincide con el nombre del campo de la subscription (nuevoMensaje).

El cliente por WebSocket

Desde el cliente se establece la conexión con graphql-ws (el estándar de la industria) y se suscribe a la operación. El servidor le envía cada evento en next:

import { createClient } from "graphql-ws";

const client = createClient({ url: "ws://localhost:4000/graphql" });

const unsubscribe = client.subscribe(
  {
    query: `
      subscription {
        nuevoMensaje(canalId: "c1") {
          texto
          autor { nombre }
        }
      }`,
  },
  {
    next: (result) => {
      console.log("Nuevo mensaje:", result.data.nuevoMensaje);
    },
    error: (err) => console.error("Error de subscription:", err),
    complete: () => console.log("Suscripción terminada"),
  },
);

La función devuelta permite cancelar la suscripción cuando el componente se desmonta. La conexión WebSocket se reutiliza para varias subscriptions al mismo tiempo y gestiona el keep-alive por sí misma.

Consideraciones de infraestructura

Las subscriptions mantienen conexiones abiertas de forma persistente, lo que cambia las reglas frente a HTTP:

  • Escalado: cada nodo debe conocer los eventos de todos; se usa un PubSub compartido (Redis) en vez del de memoria.
  • Carga: cada suscripción consume memoria y sockets; hay que vigilarlas y expulsar a los clientes inactivos.
  • Autenticación: el handshake del WebSocket debe validar el token igual que una petición HTTP.
  • TLS: en producción el cliente usa wss://, no ws://.

Si tu caso solo requiere que la UI se entere de cambios (no bidireccional), a veces un simple poll o SSE con cache HTTP es más barato que una conexión persistente por usuario.

Ejercicio

  1. Declara un campo de subscription notificacionesNuevas que emita un objeto Notificacion.
  2. Haz que una mutation crearNotificacion publique el evento por PubSub.
  3. Conecta un cliente graphql-ws que loguee cada evento recibido.
  4. Escribe en una frase qué haría falta cambiar en el PubSub para desplegar dos instancias del servidor.

Resumen

  • Las subscriptions son el tercer tipo raíz: escuchan eventos en lugar de leer o escribir.
  • El servidor usa PubSub: las mutations publican, las subscriptions escuchan.
  • El resolver de suscripción expone subscribe y devuelve un asyncIterator.
  • El cliente se conecta por WebSocket con graphql-ws.
  • En producción se necesita un PubSub compartido (Redis), TLS y autenticación en el handshake.
