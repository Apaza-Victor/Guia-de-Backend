DataLoader y N+1

🔥 Avanzado 9 min GraphQL Módulo 3 · Avanzado y producción

Introducción

Viste en la lección de resolvers que cada campo se resuelve de forma independiente. Esa libertad tiene un precio: si pides una lista de posts y el resolver de cada autor consulta la base por separado, una sola query dispara 1 + N consultas. Ese es el famoso problema N+1, el enemigo de la latencia de GraphQL.

El problema en código

Este schema tan inocente esconde la trampa: pedir 100 posts con sus autores son 1 consulta (posts) + 100 consultas (un autor cada una):

const resolvers = {
  Query: {
    posts: async (parent, args, context) => {
      const { rows } = await context.db.query("SELECT * FROM posts");
      return rows;
    },
  },
  Post: {
    autor: async (post, args, context) => {
      const { rows } = await context.db.query(
        "SELECT * FROM usuarios WHERE id = $1",
        [post.autorId],
      );
      return rows[0];
    },
  },
};
query {
  posts {
    titulo
    autor { nombre }
  }
}

Con 100 posts el servidor hace 101 viajes a la base. Cuantos más niveles anidados pidas, peor: posts → autor → posts del autor → … crece de forma exponencial en el peor caso.

DataLoader: batching automático

DataLoader resuelve el N+1 agrupando todas las llamadas que llegan en el mismo "tick" del event loop y ejecutándolas en una sola consulta. Es un concepto sencillo con dos superpoderes:

  • Batching — junta los load(id) de una tanda y los resuelve juntos.
  • Caching — recuerda resultados dentro de una sola request para no duplicar trabajo.
import DataLoader from "dataloader";

async function batchUsuarios(ids) {
  const { rows } = await pool.query(
    "SELECT * FROM usuarios WHERE id = ANY($1::int[])",
    [ids],
  );
  const porId = new Map(rows.map((usuario) => [usuario.id, usuario]));
  return ids.map((id) => porId.get(id) ?? null);
}

const cargadorUsuarios = new DataLoader(batchUsuarios);

La regla del loader: debe devolver un resultado por cada id recibido, en el mismo orden. Por eso se reconstruye el arreglo con ids.map(...) y se rellena con null lo que falte.

Usar el loader en el resolver

El resolver cambia de "consulta por id" a "carga por clave". Los N resolvers de autor se ejecutan en el mismo tick, el loader los agrupa y solo cruza la red una vez:

const resolvers = {
  Post: {
    autor: (post, args, context) => context.cargadores.usuarios.load(post.autorId),
  },
  Comentario: {
    autor: (comentario, args, context) => context.cargadores.usuarios.load(comentario.autorId),
  },
};

En una query que pidiera posts, autores y comentarios con sus autores: 1 consulta de posts + 1 lote de usuarios + 1 lote de comentarios + 1 lote de usuarios = 4 llamadas en total, en vez de decenas.

Caché por request, no global

El punto clave de diseño: los loaders se crean por request y se desechan al terminar. Así el caché evita duplicados dentro de una operación (por ejemplo, el mismo autor aparece en 20 posts) sin provocar datos obsoletos entre peticiones distintas:

import { ApolloServer } from "@apollo/server";

function crearCargadores() {
  return {
    usuarios: new DataLoader(batchUsuarios),
    comentarios: new DataLoader(batchComentarios),
  };
}

const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: () => ({ cargadores: crearCargadores() }),
});

Si compartieras el loader entre usuarios distintos, un usuario podría ver datos del caché de otro — y los datos quedarían rancios. El ciclo de vida del loader = ciclo de vida de la operación.

Alternativas y cuándo prescindir

No todo requiere DataLoader:

  • Si la consulta raíz ya hace un JOIN en SQL y devuelve los autores embebidos, ningún loader hace falta.
  • Los ORMs (Prisma, Sequelize, TypeORM) ofrecen eager loading con include; DataLoader brilla cuando el acceso a datos es por repositorios o APIs remotas.
  • Para relaciones anidadas profundas conviene combinarlo con paginación para acotar el tamaño del lote.
SELECT p.id, p.titulo, u.nombre AS autor
FROM posts p
JOIN usuarios u ON u.id = p.autor_id
WHERE p.publicado = true;

Regla práctica: mide primero. Si una query muestra N+1 en el log de consultas, data loader es la cura correcta.

Ejercicio

  1. Recrea el schema posts → autor y observa cuántas consultas dispara con 20 posts en el log.
  2. Implementa batchUsuarios con un DataLoader que agote con ANY($1::int[]).
  3. Reemplaza el resolver Post.autor por cargadores.usuarios.load(...) y compara el número de consultas.
  4. Razona por escrito por qué el loader debe vivirse por request y no ser global.

Resumen

  • El N+1 ocurre cuando cada campo relacionado consulta la base por separado.
  • DataLoader agrupa los load del mismo tick en un solo lote.
  • Devuelve resultados en el mismo orden que los ids recibidos y con null para los ausentes.
  • El caché es por request; nunca un loader compartido entre usuarios.
  • Antes de optimizar, comprueba si un JOIN o el eager loading del ORM lo resuelven.
