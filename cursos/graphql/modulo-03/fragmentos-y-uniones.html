Fragmentos, uniones e interfaces

🔥 Avanzado 9 min GraphQL Módulo 3 · Avanzado y producción

Introducción

Dos herramientas que la especificación ofrece para no repetirte cuando los datos se parecen o cuando un campo puede ser de varios tipos: los fragmentos (reutilizar selecciones) y las interfaces y uniones (polimorfismo). Ambas son muy usadas en clientes de verdad y en schemas de dominios ricos.

Fragmentos: reutiliza selecciones

Un fragmento es un paquete de campos reutilizable que se incluye con .... Definido una vez, se extiende (spread) en varias partes de la consulta:

fragment DatosBasicosUsuario on Usuario {
  nombre
  avatar
  email
}

query {
  autor: usuario(id: "u1") {
    ...DatosBasicosUsuario
    posts { titulo }
  }
  editor: usuario(id: "u2") {
    ...DatosBasicosUsuario
  }
}

Ventajas que van más allá de la estética:

  • Coherencia: el avatar se pide igual en todas las pantallas — un solo lugar que editar.
  • Cache: los clientes Apollo/Relay normalizan por __typename + id; los campos coincidentes se reutilizan.
  • Legibilidad: el selection set describe intención, no verbosidad.

Interfaces

Una interfaz define campos comunes que varios tipos deben cumplir (implements). Sirve para agrupar cosas que comparten comportamiento, como medios de pago:

interface MedioPago {
  id: ID!
  marca: String!
}

type Tarjeta implements MedioPago {
  id: ID!
  marca: String!
  ultimosCuatro: String!
}

type PayPal implements MedioPago {
  id: ID!
  marca: String!
  email: String!
}

type Query {
  metodosDePago: [MedioPago!]!
}

El cliente puede pedir los campos comunes sin conocer el tipo concreto, y para los específicos usa los fragmentos inline con ... on:

query {
  metodosDePago {
    id
    marca
    ... on Tarjeta { ultimosCuatro }
    ... on PayPal { email }
  }
}

Uniones

La unión es más libre: agrupa tipos sin campos comunes. El ejemplo clásico es un buscador que devuelve resultados heterogéneos:

union ResultadoBusqueda = Post | Usuario | Comentario

type Query {
  buscar(termino: String!): [ResultadoBusqueda!]!
}

Al no haber denominador común, la consulta debe discriminar por tipo. El campo meta __typename siempre está disponible y los fragmentos inline seleccionan campos por tipo:

query {
  buscar(termino: "graphql") {
    __typename
    ... on Post { titulo autor { nombre } }
    ... on Usuario { nombre email }
    ... on Comentario { texto }
  }
}

Resolver el tipo concreto: __resolveType

Cuando GraphQL devuelve un valor de una interfaz o unión, necesita saber qué tipo concreto es. Lo deduce con el campo __typename que ya trae el objeto, y si no, con __resolveType:

const resolvers = {
  ResultadoBusqueda: {
    __resolveType: (objeto) => {
      if (objeto.titulo !== undefined) return "Post";
      if (objeto.nombre !== undefined) return "Usuario";
      return "Comentario";
    },
  },
  MedioPago: {
    __resolveType: (objeto) => (objeto.ultimosCuatro ? "Tarjeta" : "PayPal"),
  },
};

Cuanto más limpia sea la discriminación (__typename presente, o un campo discriminador), menos costoso. Si varios tipos comparten todas las claves, es recomendable añadir un campo tipo explícito al modelo para no adivinar.

¿Cuál elegir?

  • Interfaz si los tipos comparten una identidad y campos (medios de pago, eventos, nodos).
  • Unión si son resultados inconexos que coinciden en un endpoint (búsqueda, notificaciones, feed mixto).
  • Fragments siempre que repitas un selection set: son la herramienta de composición del cliente.

En el schema también existen las interfaces clave: la interfaz Node con un campo id es un patrón clásico para campos "buscables por id global". Elegir entre ellas es una decisión de diseño de dominio, no puramente técnica.

Ejercicio

  1. Define un fragmento CamposAutor y úsalo en tres puntos de una query.
  2. Crea una interfaz Evento con id y ocurridoen, e implements en Compra y Login.
  3. Cambia la query raíz para que historial(usuarioId) devuelva [Evento!]!.
  4. Escribe __resolveType para esa interfaz discriminando por un campo.

Resumen

  • Los fragmentos reutilizan selection sets y mejoran cache y coherencia.
  • Las interfaces declaran campos comunes que varios tipos implementan.
  • Las uniones agrupan tipos sin denominador común.
  • __typename y los fragmentos inline ... on Tipo discriminan en la consulta.
  • __resolveType le dice al servidor qué tipo concreto devolver.
