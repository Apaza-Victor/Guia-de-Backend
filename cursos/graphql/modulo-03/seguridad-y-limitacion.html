Seguridad y limitación

🔥 Avanzado 9 min GraphQL Módulo 3 · Avanzado y producción

Introducción

La flexibilidad de GraphQL es también su superficie de ataque: un cliente abusivo puede pedir consultas profundísimas, con miles de aliases o de complejidad enorme, y tumbar el servidor. A diferencia de REST, donde los endpoints son fijos, aquí el coste de una operación lo elige quien pregunta. La seguridad se convierte en un problema de control de coste + identidad + permisos.

El modelo de coste

Tres trucos clásicos contra una API GraphQL:

  • Profundidad: anidar posts → autor → posts → autor… hasta agotar el stack o el tiempo.
  • Aliases: repetir un mismo campo caro miles de veces en una operación.
  • Complejidad: pedir listas muy largas o campos que requieren computación costosa en cada salto.

El ejemplo abusivo con aliases muestra lo fácil que es inflar una query contra un servidor sin límites:

query Abuso {
  a1: posts { titulo autor { nombre } }
  a2: posts { titulo autor { nombre } }
  a3: posts { titulo autor { nombre } }
  # ... el atacante repite el campo cientos de veces
}

Limitar la profundidad

La regla de validación graphql-depth-limit rechaza operaciones que pasen un número de niveles. Siete niveles es un techo típico incluso para UIs ricas:

import depthLimit from "graphql-depth-limit";

const server = new ApolloServer({
  typeDefs,
  resolvers,
  validationRules: [depthLimit(7)],
});

Al ser una validation rule, la query se rechaza antes de ejecutar ningún resolver, sin tocar la base de datos. Es la primera línea de defensa y cuesta una línea.

Limitar la complejidad

La complejidad computa un "precio" por nodo y tipo que la query puede visitar, y corta las operaciones que lo superan. La técnica @complexity permite declarar el coste por campo:

import { getComplexity, simpleEstimator } from "graphql-query-complexity";
import { separateOperations } from "graphql";

const server = new ApolloServer({
  typeDefs,
  resolvers,
  plugins: [
    {
      async requestDidStart({ request, document }) {
        const complexity = getComplexity({
          schema: server.schema,
          operationName: request.operationName,
          query: document,
          variables: request.variables,
          estimators: [simpleEstimator({ defaultComplexity: 1 })],
        });
        if (complexity > 1000) {
          throw new GraphQLError(
            `La operación es demasiado compleja (${complexity})`,
            { extensions: { code: "TOO_COMPLEX" } },
          );
        }
      },
    },
  ],
});

La complejidad se calcula sobre la operación concretamente enviada, así que captura tantos los aliases como los listados largos de una sola pasada.

Rate limiting

Además de la complejidad por operación, hay que limitar el ritmo. En GraphQL se suele medir la "unidad de cóstese" por usuario, no solo el número de peticiones:

import { RedisRateLimiter } from "@gr2m/graphql-rate-limit";

const rateLimiter = new RedisRateLimiter({
  RedisClient: redis,
  name: "coste_por_usuario",
  points: 1000,
  duration: 60 * 15,
});

const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: ({ req }) => ({
    usuarioActual: autenticar(req),
    rate: rateLimiter,
  }),
});

La clave de rate limit es el usuario autenticado; para IPs, un middleware en el proxy o Express cubre bien el caso anónimo.

Autenticación y autorización

La autenticación (¿quién eres?) se resuelve en el contexto, leyendo el token de cada petición. La autorización (¿puedes ver esto?) se decide en el resolver:

import jwt from "jsonwebtoken";

const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: ({ req }) => {
    const token = req.headers.authorization?.replace("Bearer ", "");
    return {
      usuarioActual: token
        ? jwt.verify(token, process.env.JWT_SECRET)
        : null,
    };
  },
});
const resolvers = {
  Query: {
    panelAdmin: (parent, args, context) => {
      if (context.usuarioActual?.rol !== "ADMIN") {
        throw new GraphQLError("Acceso denegado", {
          extensions: { code: "FORBIDDEN", http: { status: 403 } },
        });
      }
      return context.db.obtenerDatosAdmin();
    },
  },
};

Para no repetir el if en cada campo se usan directivas (@auth(rol: [...])) o una capa de autorización centralizada que envuelve los resolvers."

Desactivar la introspección

En una API pública, dejar la introspección activa regala un mapa completo del schema al atacante. Se desactiva por llave de entorno:

import { ApolloServer } from "@apollo/server";

const server = new ApolloServer({
  typeDefs,
  resolvers,
  introspection: process.env.NODE_ENV !== "production",
});

En desarrollo sigues disfrutando de GraphiQL y, en producción, el camino de ataque con __schema desaparece. Si necesitas documentación pública, genera un schema estático en el pipeline.

Ejercicio

  1. Añade depthLimit(7) a tu servidor y comprueba que una query de 8 niveles se rechaza.
  2. Calcula la complejidad de una operación con 50 aliases y establece un tope que la bloquee.
  3. Implementa la autorización de panelAdmin con context.usuarioActual y un code: "FORBIDDEN".
  4. Activa la introspección solo en desarrollo y verifica que en producción __schema da error.

Resumen

  • En GraphQL el coste de la operación lo elige el cliente: hay que limitarlo.
  • La profundidad se acota con reglas de validación antes de ejecutar resolvers.
  • La complejidad pondera nodos, aliases y listas y corta operaciones costosas.
  • El rate limiting se aplica por usuario real y coste consumido.
  • Autenticar en el contexto + autorizar por resolver o directiva.
  • Desactiva la introspección en producción pública.
