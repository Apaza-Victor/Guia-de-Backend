Federation y gateway

🔥 Avanzado 10 min GraphQL Módulo 3 · Avanzado y producción

Introducción

Cuando un solo equipo crece demasiado o varios equipos despliegan servicios que comparten dominio, un único servidor GraphQL se vuelve un cuello de botella organizativo: un equipo no puede avanzar sin coordinarse con los demás.

Apollo Federation resuelve esto dividiendo el schema en subgraphs (uno por servicio/equipo) que se componen en un supergraph, servido por un gateway que enruta cada campo al servicio dueño.

Supergraph y subgraphs

El supergraph es el schema unificado que el gateway expone al cliente. Cada subgraph solo declara su parte: productos define el catálogo, reviews las reseñas. Para que un subgraph pueda "enriquecer" un tipo que pertenece a otro, Federation introduce las entidades:

# Subgraph de reviews
type Review @key(fields: "id") {
  id: ID!
  cuerpo: String!
  producto: Producto!
}

type Producto @key(fields: "id") {
  id: ID! @external
}

extend type Query {
  reviewsDeProducto(productoId: ID!): [Review!]!
}

La directiva @key declara la clave que identifica al objeto (id), @external marca que un campo viene de otro subgraph, y extend type Query añade operaciones al tipo raíz común.

Resolver una entidad

Cuando el gateway necesita los datos de Producto desde el subgraph de reviews, le envía una "referencia" con su clave. El subgraph resuelve esa entidad con __resolveReference:

const resolvers = {
  Producto: {
    __resolveReference(reference) {
      return { id: reference.id, nombre: `Producto ${reference.id}` };
    },
  },
};

El resultado puede incluir campos nuevos del subgraph que se mezclan con los del subgraph original en la respuesta final del supergraph.

Levantar un subgraph

Un subgraph se publica como un Apollo Server normal, pero usando buildSubgraphSchema en lugar del schema plano. Se conecta a la red interna y el gateway lo descubre:

import { ApolloServer } from "@apollo/server";
import { startStandaloneServer } from "@apollo/server/standalone";
import { buildSubgraphSchema } from "@apollo/subgraph";

const server = new ApolloServer({
  schema: buildSubgraphSchema({ typeDefs, resolvers }),
});

const { url } = await startStandaloneServer(server, {
  listen: { port: 4002 },
});
console.log(`Subgraph reviews en ${url}`);

Configurar el gateway

El gateway conoce los subgraphs (por URL en la red interna o por un manifiesto) y compone el supergraph al arrancar. Los campos de cada subgraph se delegan de forma transparente:

import { ApolloGateway, IntrospectAndCompose } from "@apollo/gateway";
import { ApolloServer } from "@apollo/server";

const gateway = new ApolloGateway({
  supergraphSdl: new IntrospectAndCompose({
    subgraphs: [
      { name: "productos", url: "http://productos:4001/graphql" },
      { name: "reviews", url: "http://reviews:4002/graphql" },
    ],
  }),
});

const server = new ApolloServer({ gateway });

const { url } = await startStandaloneServer(server, { listen: { port: 4000 } });
console.log(`Gateway en ${url}`);

Desde el punto de vista del cliente, solo existe el gateway en /graphql: una query que toque productos y reviews se divide en llamadas a los subgraphs y se reensambla en una sola respuesta.

Federation vs la agregación manual

Federation no es la única vía para GraphQL en microservicios. Las alternativas y sus trade-offs:

  • Schema stitching: el antecesor; une schemas de forma más manual y frágil. Farming comprehensivo hoy es menos recomendado.
  • BFF (Backend for Frontend): un servicio que agrega otros por código. Flexible, pero hay que mantener la agregación a mano y duplica lógica de composición.
  • Monolito GraphQL: para equipos pequeños sigues mejor con un único servidor bien modularizado que con la infraestructura de gateway.

Federation aporta composición declarativa (el report graphos: schema diff avisa de cambios rotos), pero introduce un componente más en la red y una capa de enrutado que medir y escalar.

¿Cuándo federar?

La señal más clara es organizativa, no técnica:

  • Varios equipos despliegan servicios de forma independiente.
  • Comparten entidades (Producto, Pedido) y quieren un solo contrato para el cliente.
  • Necesitan evolucionar el schema sin coordinar deploys en un solo repositorio.

Si tu equipo es pequeño o despliegas un solo servicio, la complejidad de Federation no te compensa todavía. Empieza monomódulo; Federation escala contigo cuando la organización lo pide.

Ejercicio

  1. Levanta dos subgraphs: productos con Producto @key(id) y reviews con Review.
  2. Declara la relación entre Review y Producto con @external y __resolveReference.
  3. Monta el gateway con IntrospectAndCompose y comprueba que una query cruza ambos subgraphs.
  4. Responde en una frase cuál es la señal organizativa clave para empezar a federar.

Resumen

  • Federation divide el schema en subgraphs que se componen en un supergraph.
  • Las entidades se identifican con @key y se enriquecen con @external y __resolveReference.
  • El gateway compone el supergraph y enruta cada campo a su subgraph dueño.
  • Federation compite con stitching, BFF o el monolito; la señal de uso es organizativa.
