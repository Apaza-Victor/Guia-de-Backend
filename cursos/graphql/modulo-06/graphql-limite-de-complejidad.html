Límite de complejidad y profundidad

🔥 Avanzado 11 min GraphQL Módulo 6 · Seguridad y rendimiento GraphQL

Introducción

GraphQL delega la forma de la query al cliente, y un cliente malicioso —o un bug— puede pedir árboles de miles de campos. La complejidad de una query no es gratis: cada campo es trabajo en los resolvers.

Los límites de complejidad y profundidad son la cortina de humo: se calculan antes de ejecutar y rechazan las queries que exceden el presupuesto.

Definición

La complejidad es una puntuación heurística de una query (por campos, conexiones y coste); la profundidad es el nivel máximo de anidamiento permitido.

Por qué importa. Una query cara consume CPU y base de datos de una sola llamada; limitarla es el rate limiting de GraphQL.

Cuándo usarlo. Configura complejidad y profundidad si tu API escón campos con resolvers caros o conexiones profundas.

Conceptos clave

  • Cada campo contribuye con puntos de complejidad.
  • Un campo de lista o uno caro multiplica su coste.
  • La profundidad limita el anidamiento de la query.
  • Apollo plugin graphql-query-complexity calcula antes de ejecutar.
  • El presupuesto rechaza la query con un error tipado.

Ejemplo básico

Activar el límite de complejidad con graphql-query-complexity en Apollo.

Ejemplo intermedio

Complejidad ponderada: los campos de lista que cuestan caro multiplican.

Ejemplo real

Las APIs públicas combinan complejidad con rate limiting por IP y autenticación.

  • Fija un presupuesto que admita las queries reales del producto.
  • Pesa más los campos con resolvers caros (importaciones, cálculos).
  • Registra las queries rechazadas para ajustar umbrales.

Empieza con un umbral generoso y baja según las métricas de rejections.

Explicación

  • La complejidad heurística no es el coste exacto, pero correlaciona bien.
  • Los campos de lista son los que más multiplican: listFactor castiga anidarlos.
  • La profundidad limita el árbol aunque cada hoja sea barata.
  • La validación previa evita ejecutar queries que nunca pasarían.
  • Combinar límite y rate limiting protege al servicio de picos y de abuso.

Errores comunes

  • No limitar ni complejidad ni profundidad en APIs públicas.
  • Pesos uniformes que dejan pasar campos gigantes.
  • Un umbral demasiado bajo que rompe queries legítimas del front.

Buenas prácticas

  • Mide las queries reales de tu producto antes de fijar el umbral.
  • Pesa más lo que sabes que es caro en la base de datos.
  • Rechaza con un código COMPLEXITY estable para el cliente.
  • Ajusta los umbrales con los datos de monitorización.

Ejercicio

  1. Activa depthLimit(7) y comprueba que una query profunda falla.
  2. Pondera las listas con listFactor y observa el coste.
  3. Registra las queries rechazadas y ajusta el umbral.

Resumen

  • La complejidad puntúa cada query y rechaza la cara.
  • La profundidad limita el anidamiento del árbol.
  • Umbrales basados en métricas reales evitan romper el front.
