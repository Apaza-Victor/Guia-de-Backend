Tracing y métricas por resolver

🔥 Avanzado 10 min GraphQL Módulo 6 · Seguridad y rendimiento GraphQL

Introducción

Una query que responde en 700 ms puede esconder un resolver que tarda 600 y otros diez casi gratis. Para optimizar GraphQL hay que verlo por campo: el tracing descompone el tiempo de cada resolver.

Con métricas por resolver sabes qué campo trae la ralentización, si la base de datos es la culpable o si un campo anidado multiplica el coste.

Definición

El tracing registra la duración de cada resolver dentro de una operación; las métricas agregan esos tiempos por tipo, campo y operación.

Por qué importa. Sin trazado, optimizar GraphQL es adivinar: el coste está repartido en decenas de campos y niveles.

Cuándo usarlo. Activa tracing desde el día uno y agrega paneles cuando el API cobre importancia.

Conceptos clave

  • El trace de una operación lista cada resolver con su duración.
  • PersistedUptime se agregatea por campo y operación.
  • Apollo Server integra tracing con plugins.
  • Los gráficos visibilitan el p95 por resolver.
  • Un campo caro repetido en N+1 se descubre al trazar.

Ejemplo básico

Activar un plugin de tracing que registra la duración de cada resolver.

Los informes de uso llegan con el tiempo de cada resolver.

Ejemplo intermedio

Un plugin local que imprime los resolvers más lentos de cada operación.

Ejemplo real

Con los traces agregados detectas qué campo crackea el p95 de una operación de contax.

  • Activa el plugin de usage reporting en producción.
  • Construye gráficos de tiempo medio por campo.
  • Alerta cuando el p95 de un resolver supere el umbral.

Los plugins de Apollo Server no reemplazan a OpenTelemetry cuando quieras correlación completa.

Explicación

  • El trace de una operación es un árbol: el tiempo del padre incluye a los hijos.
  • Agregar por campo revela los resolvers que valen la pena optimizar.
  • El N+1 se ve en el trace como muchas llamadas cortas duplicadas.
  • Comparar traces entre consultas del mismo tipo muestra outliers.
  • Traza solo lo que necesitas: trace completo de todo puede ser caro y ruidoso.

Errores comunes

  • Optimizar a ciegas sin medir primero.
  • Traces en producción que revelan datos sensibles en los spans.
  • Configurar tracing solo en development y adivinar en producción.

Buenas prácticas

  • Activa el trazado en producción pero reduciendo el muestreo.
  • Correla traces con métricas de base de datos.
  • Asigna el p95 como métrica de alerta, no la media.
  • Guarda ejemplos de traces de queries lentas para depurar.

Ejercicio

  1. Activa el plugin de usage reporting y observa los resolvers.
  2. Crea un plugin local que liste los campos de más de 100 ms.
  3. Detecta un N+1 en el trace de una query anidada.

Resumen

  • El tracing descompone la duración de cada resolver.
  • Las métricas por campo señalan dónde optimizar.
  • El p95 por resolver es la señal de alerta correcta.
