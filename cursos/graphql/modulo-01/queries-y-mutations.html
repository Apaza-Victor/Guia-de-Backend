Queries y Mutations

🔥 Avanzado 9 min GraphQL Módulo 1 · Fundamentos de GraphQL

Introducción

En GraphQL hay tres tipos de operación. La query es una lectura: pide datos sin efectos secundarios. La mutation es una escritura: crea, actualiza o borra, como un POST/PUT/DELETE de REST. Ambas comparten sintaxis; la diferencia es de intención y de garantías de ejecución.

Vamos a desmontar la sintaxis de query paso a paso: operación, selección, argumentos y aliases, y después veremos cómo se escribe una mutation.

La operación query

Una query nombrada empieza con la palabra clave query, un nombre opcional (buena práctica para logs y depuración) y su campo raíz:

query ObtenerUsuario {
  usuario(id: "u1") {
    nombre
    email
    avatar
  }
}

El selection set es el bloque entre llaves: la lista de campos que se devuelven. El servidor ignora lo que no se pide. Si el cliente más adelante necesita telefono, basta con añadirlo a la consulta — no hace falta una nueva versión de la API ni un endpoint nuevo.

GraphQL también permite la forma abreviada sin la palabra query (útil en consolas), pero en producción es recomendable nombrar las operaciones para identificarlas en logs y métricas.

Argumentos

Los campos llevan argumentos: parámetros con tipo que el resolver recibe. Un campo puede combinarse con argumentos de filtrado, paginación u orden, y los argumentos pueden anidarse campo a campo:

query BuscarPost {
  post(id: "p42") {
    titulo
    autor {
      nombre
      email
    }
  }
}

Aquí post recibe id, y autor se resuelve como una relación anidada. El resultado viaja en una sola respuesta, aunque en el servidor haya habido dos consultas a la base de datos (o tres, si el autor mira sus propios posts). Los argumentos también pueden ser obligatorios o no — el schema decide.

Aliases

¿Qué pasa si quieres pedir el mismo campo con argumentos distintos dos veces en la misma consulta? Sin más, fallaría porque los campos con el mismo nombre colisionan. La solución son los aliases: un nombre propio para cada instancia:

query {
  perfil: usuario(id: "u1") {
    nombre
  }
  contacto: usuario(id: "u2") {
    nombre
  }
}

La respuesta llega con los nombres de los alias como claves, lo que permite comparar dos usuarios o pedir el mismo dataset con parámetros distintos en una sola petición:

{
  "data": {
    "perfil": { "nombre": "Ana Torres" },
    "contacto": { "nombre": "Luis Mora" }
  }
}

Mutaciones

Las mutations modifican el estado y, como en REST, pueden devolver los datos creados. Es buena práctica que devuelvan el objeto completo o una proyección útil, para que el cliente actualice su UI sin hacer una query extra:

mutation CrearPost {
  crearPost(titulo: "Hola GraphQL", contenido: "Primer post del curso") {
    id
    titulo
    creadoEn
  }
}

Una diferencia clave con REST: las mutations se ejecutan en serie. Si una mutation tiene varios campos raíz, GraphQL los ejecuta uno tras otro en orden, mientras que las queries se ejecutan en paralelo. Esto permite que una mutation dependa del resultado de la anterior dentro del mismo documento.

La forma de la respuesta

Toda operación responde con la misma estructura: una clave data con la forma exacta de la consulta, y opcionalmente errors:

{
  "data": {
    "crearPost": {
      "id": "p47",
      "titulo": "Hola GraphQL",
      "creadoEn": "2026-09-22T09:15:00Z"
    }
  }
}

Si un campo falla, aparece errors con la descripción y la ruta del campo fallido — el resto de la respuesta se entrega igualmente. Ese modelo de errores estructurados lo estudiarás a fondo en la lección de errores y validación.

Ejercicio

  1. Escribe una query nombrada que traiga un usuario y sus últimos 3 posts (anida el selection set de posts).
  2. Usa un alias para pedir el mismo usuario dos veces con IDs distintos en una sola request.
  3. Escribe una mutation actualizarPerfil que reciba un nuevo nombre y devuelva el usuario actualizado.
  4. Responde por escrito: ¿por qué las mutations se ejecutan en serie mientras las queries pueden hacerlo en paralelo?

Resumen

  • Una query lee datos; una mutation los escribe. La sintaxis es idéntica.
  • El selection set define exactamente qué campos se devuelven.
  • Los campos reciben argumentos tipados y pueden anidarse.
  • Los aliases permiten pedir el mismo campo varias veces sin colisión.
  • Las mutations se ejecutan en serie y suelen devolver el objeto modificado.
