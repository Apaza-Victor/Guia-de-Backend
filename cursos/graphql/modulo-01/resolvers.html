Resolvers

🔥 Avanzado 8 min GraphQL Módulo 1 · Fundamentos de GraphQL

Introducción

El schema dice qué existe; los resolvers dicen cómo se obtiene. Cada campo del schema tiene asociada una función, el resolver, que devuelve su valor: un dato de la base de datos, el resultado de una llamada a otra API o el resultado de computar algo en memoria.

Cuando llega una consulta, el motor de GraphQL recorre el árbol de campos y ejecuta un resolver por cada uno, componiendo la respuesta. Esto quiere decir que no hay "un resolver por query", sino un resolver por campo.

El campo como función

En la práctica, los resolvers son un objeto con la misma forma que el schema. El resolver de un campo raíz de Query recibe los argumentos de la consulta y busca los datos:

const resolvers = {
  Query: {
    usuario: (parent, args, context) => {
      return context.db.usuarios.find((u) => u.id === args.id);
    },
    posts: (parent, args, context) => context.db.obtenerPosts(),
  },
};

Es un patrón muy directo: el nombre del campo en el objeto resolvers coincide con el nombre en el schema, y el valor devuelto pasa a formar parte de la respuesta.

La firma del resolver

Cada resolver recibe cuatro argumentos estándar. En orden:

  • parent — el valor devuelto por el resolver del campo padre. Si es Query, suele ser null o el valor raíz.
  • args — el objeto con los argumentos que recibió el campo en la consulta.
  • context — un objeto compartido por toda la operación: base de datos, usuario autenticado, logger…
  • info — metadatos del estado de ejecución (ruta, selección de campos, nombre de la operación).
const resolvers = {
  Query: {
    articulo: (parent, args, context, info) => {
      console.log('Operación:', info.operation.name?.value);
      return context.db.articulos.findById(args.id);
    },
  },
};

En la práctica casi siempre usas args y context; parent lo necesitas para relaciones y info para casos avanzados como log costoso o directivas personalizadas.

La cadena de resolvers

Cuando el schema anida tipos, GraphQL resuelve las relaciones encadenando resolvers. El resolver de Post.autor recibe en parent el objeto post que devolvió el resolver del padre, y con eso busca al usuario:

const resolvers = {
  Query: {
    post: (parent, args, context) => context.db.posts.findById(args.id),
  },
  Post: {
    autor: (post, args, context) => context.db.usuarios.findById(post.autorId),
  },
};

Fíjate en la ventaja enorme: Post.autor solo se ejecuta si la consulta lo pide. Si el cliente no selecciona autor, no se hace esa llamada. Ese aplazamiento es lo que permite que una API GraphQL no haga más trabajo del necesario. (También es el origen del famoso problema N+1, que resolverás en el módulo 3 con DataLoader.)

El contexto

El context se construye una vez por request y viaja a todos los resolvers. Es el lugar natural para el pool de base de datos, el usuario autenticado o un logger, evitando pasarlos de resolver en resolver:

const server = new ApolloServer({
  typeDefs,
  resolvers,
  context: ({ req }) => ({
    db: pool,
    usuarioActual: req.auth?.usuario ?? null,
  }),
});

Con eso, cualquier resolver puede decidir si quien consulta tiene permiso para ver un dato:

const resolvers = {
  Query: {
    datosPrivados: (parent, args, context) => {
      if (!context.usuarioActual) {
        throw new Error('Autenticación requerida');
      }
      return context.db.cargarDatosPrivados(context.usuarioActual.id);
    },
  },
};

Resolvers asíncronos

Los resolvers pueden ser async porque GraphQL espera Promesas. Casi todo trabajo real de backend —una consulta SQL, un fetch a otra API— es asíncrono:

const resolvers = {
  Query: {
    pedidos: async (parent, args, context) => {
      const { rows } = await context.db.query(
        'SELECT * FROM pedidos WHERE usuario_id = $1',
        [args.usuarioId],
      );
      return rows;
    },
  },
};

El motor ejecuta los resolvers de un nivel en paralelo y espera todas sus Promesas antes de bajar al siguiente nivel. Por eso una query con tres campos raíz puede lanzar tres búsquedas simultáneas, y una relación anidada espera primero al padre.

Ejercicio

  1. Escribe los resolvers para el schema usuario(id) y posts usando un arreglo en memoria.
  2. Añade un resolver de campo Post.autor que use parent para buscar al autor.
  3. Haz un resolver async que consulte una tabla con context.db.query.
  4. Responde por escrito: ¿por qué el resolver de Post.autor puede no ejecutarse nunca en una misma consulta?

Resumen

  • Cada campo del schema tiene un resolver; no hay uno solo por query.
  • La firma es (parent, args, context, info).
  • Las relaciones se resuelven encadenando resolvers a través de parent.
  • El context comparte BD, autenticación y utilidades entre todos los resolvers.
  • Los resolvers pueden ser asíncronos; GraphQL espera sus Promesas.
