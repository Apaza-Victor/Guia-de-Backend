¿Qué es GraphQL?

🔥 Avanzado 8 min GraphQL Módulo 1 · Fundamentos de GraphQL

Introducción

GraphQL es un lenguaje de consulta para APIs desarrollado por Facebook en 2012 y liberado en 2015. En lugar de exponer un conjunto de URLs por recurso, la API expone un solo endpoint al que el cliente envía una consulta estructurada que describe exactamente qué datos quiere y en qué forma.

Esas consultas son texto plano con una sintaxis llamada SDL (Schema Definition Language), el mismo lenguaje que usan los desarrolladores, las aplicaciones móviles y los navegadores. Esto convierte a la API en un contrato tipado: el servidor sabe qué campos existen, qué argumentos aceptan y qué tipo devuelven.

Al ser un lenguaje de consulta, GraphQL no es una librería ni un framework específico: es una especificación abierta (graphql.org) con implementaciones en casi todos los lenguajes, desde JavaScript y Python hasta Go, Ruby y .NET.

El problema con REST

REST es el estándar que dominó la década pasada: cada recurso tiene una URL y unos verbos HTTP, y el servidor devuelve una representación fija. Funciona muy bien, pero a medida que las apps son más complejas aparecen dos problemas constantes:

  • Over-fetching: el servidor envía campos que el cliente no va a usar. Cargar la pantalla de perfil trae también los posts, los seguidores y los datos sensibles "por si acaso".
  • Under-fetching: la respuesta se queda corta y el cliente debe hacer varias peticiones encadenadas. Una vista que mezcla perfil + últimas compras + reviews requiere 3 (o 5) llamadas a 3 (o 5) endpoints distintos.

El peor escenario combina ambos: la app móvil pide el doble de datos que necesita y aun así tiene que encadenar llamadas para terminar de pintar una sola pantalla.

Cómo funciona GraphQL

En GraphQL no hay docenas de endpoints: hay una sola URL (normalmente /graphql) a la que llegan todas las operaciones. El cliente envía un documento de operación y el servidor, guiado por el schema, lo ejecuta campo por campo con sus propios resolvers.

El flujo es siempre el mismo:

  • El cliente envía una consulta describiendo la forma de la respuesta.
  • El servidor valida la consulta contra el schema (campos correctos, tipos correctos).
  • Cada campo tiene un resolver que devuelve su valor, enlazando la base de datos, otras APIs o el código de negocio.
  • GraphQL ensambla la respuesta respetando la forma pedida y la entrega en JSON.

El cliente no decide "qué devolver el servidor", pero sí qué parte quiere ver y cómo quiere anidarla. Esa libertad, controlada por el schema, es la clave de todo lo demás.

Tu primera consulta

Observa cómo el cliente pide un usuario y, bajo cada campo, puede anidar sus posts eligiendo los campos que le interesan:

{
  usuario(id: "u1") {
    nombre
    email
    posts {
      titulo
    }
  }
}

El servidor responde con exactamente esa forma, sin campos extras:

{
  "data": {
    "usuario": {
      "nombre": "Ana Torres",
      "email": "ana@example.com",
      "posts": [
        { "titulo": "Hola GraphQL" },
        { "titulo": "Resolvers en acción" }
      ]
    }
  }
}

La misma consulta que en REST exigiría dos o tres peticiones (GET /usuarios/1, GET /usuarios/1/posts) aquí se resuelve en una sola operación. Se puede probar fácilmente con un cliente HTTP:

curl -X POST http://localhost:4000/graphql \
  -H "Content-Type: application/json" \
  -d '{"query": "{ usuario(id: \"u1\") { nombre email } }"}'

GraphQL vs REST

No es "uno reemplaza al otro", sino modelos con prioridades distintas. La comparación rápida:

  • Endpoints: REST expone muchos recursos (uno por entidad); GraphQL expone un único endpoint con todas las operaciones.
  • Forma de la respuesta: en REST el servidor decide; en GraphQL la decide el cliente dentro de los límites del schema.
  • Tipado: REST suele documentarse aparte (OpenAPI); GraphQL es tipado y auto-documentado por introspección.
  • Versionado: REST versiona la URL (/v1/, /v2/); GraphQL agrega campos de forma evolutiva sin romper a los clientes.
  • Errores: REST usa códigos HTTP; GraphQL siempre responde 200 con un cuerpo errors estructurado.

REST sigue siendo excelente para APIs públicas, simples y orientadas a recursos. GraphQL brilla cuando hay clientes diversos (web, móvil, TV), relaciones de datos complejas y equipos que quieren evolucionar la API sin coordinar versionado manual.

¿Cuándo usar GraphQL?

GraphQL aporta más valor cuando existen varias de estas condiciones:

  • Clientes heterogéneos: web de escritorio, móvil y aplicaciones internas con necesidades de datos distintas.
  • Relaciones profundas: datos entrecruzados (usuario → posts → comentarios → autor) que en REST obligarían a encadenar llamadas.
  • Productos con UI densa: feeds, dashboards y paneles donde una pantalla consume muchísimos datos.
  • Equipos que evolucionan la API seguido: añadir campos sin versionar la URL.

En cambio, para una API pública sencilla, un contrato REST estable o cuando el cliente solo necesita datos planos, GraphQL añade complejidad sin beneficio claro. Decidir con criterio —como harás en el módulo 3— es parte del trabajo del backend.

Ejercicio

  1. Toma una API REST que conozcas y elige una pantalla de tu app que la consuma.
  2. Anota cuántas peticiones hace esa pantalla y qué campos recibe que no usa. Clasifícalos en over-fetching o under-fetching.
  3. Escribe esa misma pantalla como una consulta GraphQL: un campo raíz, campos anidados y solo las propiedades que realmente pintas.
  4. Responde por escrito: en tu caso, ¿merece la pena cambiar a GraphQL? ¿Por qué?

Resumen

  • GraphQL es un lenguaje de consulta tipado para APIs con un único endpoint.
  • Resuelve el over-fetching y el under-fetching típicos de REST.
  • El cliente describe la forma de la respuesta y el servidor la valida contra el schema.
  • GraphQL y REST coexisten: cada uno tiene escenarios donde brilla.
