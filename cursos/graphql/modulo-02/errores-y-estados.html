Errores y validación

🔥 Avanzado 8 min GraphQL Módulo 2 · Implementación con Node.js

Introducción

GraphQL no usa decenas de códigos HTTP para los errores de negocio: concentra toda la señal en el cuerpo. Una respuesta puede contener data, errors o ambos, siempre con la misma estructura JSON. Entenderla es imprescindible para escribir clientes robustos y servidores que no filtren información.

El formato del error

Cada error incluye un mensaje, su ubicación en el texto de la consulta y la ruta hasta el campo que falló:

{
  "errors": [
    {
      "message": "El post p99 no existe",
      "locations": [{ "line": 3, "column": 5 }],
      "path": ["post"]
    }
  ],
  "data": { "post": null }
}

locations señala dónde en el documento se pidió el campo; path indica qué campo del árbol falló (["post"], o anidado como ["usuario", "posts"]). El cliente puede pintar las partes que sí funcionaron y marcar las que no.

Errores parciales

Un dato importante: los errores de campo no tiran toda la respuesta. Si una query pide tres campos y uno falla, los otros dos se entregan con normalidad:

{
  "errors": [{ "message": "Sin acceso", "path": ["usuario", "email"] }],
  "data": { "usuario": { "nombre": "Ana Torres", "email": null } }
}

Es distinto del modelo REST (todo o error). Esto obliga al cliente a comprobar errors y tratar cada campo como posible Nulo en la UI.

Extensiones y códigos

La especificación permite añadir metadatos en extensions. La convención práctica es un code estable para que el cliente decida sin parsear mensajes (traducir un mensaje es responsabilidad de la UI, no del backend):

import { GraphQLError } from "graphql";

function permitirSolo(rol) {
  if (context.usuario?.rol !== rol) {
    throw new GraphQLError("No tienes permisos para esta operación", {
      extensions: {
        code: "FORBIDDEN",
        http: { status: 403 },
      },
    });
  }
}

Apollo Server interpreta la subclave http.status para elegir el código HTTP de la respuesta completa. Códigos frecuentes propios: UNAUTHENTICATED, FORBIDDEN, NOT_FOUND, VALIDATION_ERROR, EMAIL_EXISTS, INTERNAL_SERVER_ERROR.

Estados HTTP

En GraphQL el HTTP suele quedarse en unos pocos estados:

  • 200 OK — operación ejecutada; puede llevar errors de negocio dentro.
  • 400 Bad Request — JSON malformado o sintaxis inválida de la consulta.
  • 401/403 — suelen forzarse con extensiones http.status en Apollo, o con middlewares de Express previos.
  • 500 — fallo interno del servidor.

Por eso no se puede decidir el comportamiento del cliente mirando solo el HTTP: hay que leer errors[].extensions.code para discriminar lógica de negocio.

Formateo seguro de errores

En producción jamás expongas un stacktrace ni detalles internos. Apollo permite reescribir lo que sale antes de responder con formatError:

const server = new ApolloServer({
  typeDefs,
  resolvers,
  formatError: (formattedError) => {
    if (formattedError.extensions?.code === "INTERNAL_SERVER_ERROR") {
      console.error("Error interno:", formattedError.message);
      return { message: "Error interno del servidor" };
    }
    return formattedError;
  },
});

Con este patrón, los errores intencionales (con su code) pasan tal cual, mientras que los inesperados se sustituyen por un mensaje genérico y el detalle queda en el log para el equipo.

Ejercicio

  1. Lanza un GraphQLError desde un resolver con code: "NOT_FOUND" y revisa el JSON completo que devuelve el servidor.
  2. Haz que un campo de una query falle y comprueba que los demás campos de data se entregan igualmente.
  3. Configura formatError para enmascarar los errores internos en producción.
  4. Escribe un pequeño cliente que decida qué mostrar según extensions.code y no según el texto del mensaje.

Resumen

  • La respuesta lleva data y/o errors; un fallo de campo no tumba a los demás.
  • Cada error tiene locations y path para localizarlo.
  • Las extensions aportan un code estable que el cliente debe usar.
  • HTTP se queda en pocos estados (normalmente 200) y la realidad viaja en el cuerpo.
  • formatError evita filtrar stacktraces en producción.
