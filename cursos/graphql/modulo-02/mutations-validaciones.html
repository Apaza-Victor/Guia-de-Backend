Mutations y validación

🔥 Avanzado 9 min GraphQL Módulo 2 · Implementación con Node.js

Introducción

Una mutation escribe y por tanto exige más cuidado que una query: validar la entrada, proteger el dato, garantizar consistencia y responder con el resultado útil. GraphQL te facilita el tipo de entrada mediante input types, pero la validación de negocio y las transacciones son puro backend.

La regla general: el schema valida la forma; el resolver valida el significado.

Input types

En vez de recibir una decena de argumentos sueltos, una mutation recibe un input object: un tipo de solo entrada (se declara con input) agrupando todos los campos:

enum Rol {
  ADMIN
  EDITOR
  LECTOR
}

input NuevoUsuarioInput {
  nombre: String!
  email: String!
  password: String!
  rol: Rol = LECTOR
}

type Mutation {
  crearUsuario(input: NuevoUsuarioInput!): Usuario!
}

A diferencia de type, un input no tiene resolvers ni relaciones: es un plano de datos puro. Los inputs pueden anidarse, listarse y asignar valores por defecto, como rol aquí.

La operación desde el cliente

El cliente pasa las variables tipadas como un solo objeto y selecciona qué ve del resultado:

mutation CrearUsuario($input: NuevoUsuarioInput!) {
  crearUsuario(input: $input) {
    id
    nombre
    email
  }
}
{
  "input": {
    "nombre": "Valeria Ruiz",
    "email": "valeria@example.com",
    "password": "S3gura*123"
  }
}

Devolver el objeto recién creado (con el id generado) evita una segunda petición para refrescar la UI.

Validar en el resolver

Aquí están las reglas que el tipo de datos no conoce: el email no puede repetirse, la contraseña debe cumplir una política. Fallar se expresa lanzando un GraphQLError con su code:

import { GraphQLError } from "graphql";
import bcrypt from "bcrypt";

const resolvers = {
  Mutation: {
    crearUsuario: async (parent, { input }, context) => {
      const existe = await context.db.usuarios.porEmail(input.email);
      if (existe) {
        throw new GraphQLError("El email ya está registrado", {
          extensions: { code: "EMAIL_EXISTS" },
        });
      }
      if (input.password.length < 8) {
        throw new GraphQLError("La contraseña debe tener 8 caracteres o más", {
          extensions: { code: "VALIDATION_ERROR", campo: "password" },
        });
      }
      const hash = await bcrypt.hash(input.password, 10);
      return context.db.usuarios.crear({ ...input, password: hash });
    },
  },
};

Nunca guardes la contraseña en claro: el hash (bcrypt/argon2) es responsabilidad del resolver, no del schema.

Transacciones

Cuando una mutation toca varias tablas, una operación a medias corrompe los datos. La solución es una transacción: todo se confirma (COMMIT) o todo se revierte (ROLLBACK):

const resolvers = {
  Mutation: {
    crearPedido: async (parent, { items, usuarioId }, context) => {
      const cliente = await context.db.pool.connect();
      try {
        await cliente.query("BEGIN");
        const { rows } = await cliente.query(
          "INSERT INTO pedidos (usuario_id, estado) VALUES ($1, $2) RETURNING id",
          [usuarioId, "PENDIENTE"],
        );
        const pedidoId = rows[0].id;
        for (const item of items) {
          await cliente.query(
            "INSERT INTO pedido_items (pedido_id, producto_id, cantidad) VALUES ($1, $2, $3)",
            [pedidoId, item.productoId, item.cantidad],
          );
        }
        await cliente.query("COMMIT");
        return { id: pedidoId, estado: "PENDIENTE" };
      } catch (error) {
        await cliente.query("ROLLBACK");
        throw new GraphQLError("No se pudo crear el pedido", {
          extensions: { code: "TRANSACTION_FAILED" },
        });
      } finally {
        cliente.release();
      }
    },
  },
};

El patrón es siempre el mismo: BEGIN al inicio, COMMIT al éxito, ROLLBACK en el catch y liberar el cliente en el finally.

Idempotencia y buenas prácticas

Al igual que en REST, una mutation mal reintentada puede duplicar efectos. Algunas protecciones habituales:

  • Claves únicas en BD para emails, slugs o códigos de pago.
  • Tokens de idempotencia: un campo opcional en el input que se reutiliza en el callback de pago para no cargar dos veces la tarjeta.
  • Versionado de concurrencia: comparar un versión o updatedAt del recurso antes de actualizar.

Decidir qué campo validar con el schema, cuál con una librería (zod, joi) y cuál en la BD es parte del diseño. La regla de oro: cerca de la fuente. El constraint único de la BD debe estar siempre, aunque el resolver lo compruebe antes por DX.

Ejercicio

  1. Define un input ActualizarPerfilInput con nombre, biografia y avatar (todos opcionales).
  2. Escribe una mutation actualizarPerfil(id, input) que valide que el id pertenece al usuario autenticado.
  3. Comprueba el email duplicado y lanza GraphQLError con code propio.
  4. Envuelve la creación de un pedido + sus líneas en una transacción con COMMIT/ROLLBACK.

Resumen

  • Los input types agrupan los argumentos de una mutation.
  • El schema valida la forma; el resolver valida el significado de negocio.
  • Los errores intencionales se lanzan como GraphQLError con extensions.code.
  • Las escrituras multi-tabla van dentro de transacciones con COMMIT/ROLLBACK.
  • La idempotencia se protege con constraints únicos y tokens de idempotencia.
