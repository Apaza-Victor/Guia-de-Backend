Argumentos y variables

🔥 Avanzado 9 min GraphQL Módulo 2 · Implementación con Node.js

Introducción

Escribir valores fijos dentro de la query funciona para probar, pero en una aplicación real los argumentos cambian en cada llamada: el id del perfil que abre el usuario, la página que pide, el término de búsqueda. Por eso GraphQL define las variables: parámetros declarados con $ que se pasan aparte, en el payload JSON de la petición.

Además de hacer la query reutilizable, las variables tienen un beneficio de seguridad adicional: jamás deben concatenarse en el texto de la query, lo que elimina una familia de inyecciones.

Declarar variables en la operación

La operación declara sus variables entre paréntesis, indicando tipo y, si aplica, el carácter no-null. Después se usan donde antes había un literal:

query ObtenerPost($id: ID!) {
  post(id: $id) {
    titulo
    contenido
  }
}

La variable $id es de tipo ID!: obligatoria. Si el cliente la omite, la validación la rechaza antes de ejecutar nada. El resolver recibe el valor final dentro de args, como si hubiera llegado como literal.

El payload de variables

Las variables viajan como un objeto JSON aparte dentro de la petición. En GraphiQL se escriben en el panel "Variables" y por HTTP van en el cuerpo:

{
  "id": "p42"
}
curl -X POST http://localhost:4000/graphql \
  -H "Content-Type: application/json" \
  -d '{
    "query": "query ObtenerPost($id: ID!) { post(id: $id) { titulo } }",
    "variables": { "id": "p42" }
  }'

Valores por defecto

Las variables pueden declararse con un valor por defecto (=), que se usa cuando el cliente no envía ese dato. Es práctico para paginación, idioma o límites:

query ObtenerFeed($limite: Int = 10, $filtro: String) {
  posts(limite: $limite, filtro: $filtro) {
    id
    titulo
  }
}

Aquí $limite tiene 10 por defecto y $filtro es opcional (puede ser null). El cliente puede enviar solo {} y la query se ejecuta con limite = 10.

Usar los argumentos en el resolver

En el resolver, args contiene las variables ya resueltas. El valor del límite puede (con cuidado) componer la consulta SQL siempre que el parámetro se pase como placeholder:

const resolvers = {
  Query: {
    posts: async (parent, { limite, filtro }, context) => {
      const where = filtro ? "WHERE titulo ILIKE $1" : "";
      const parametros = filtro ? [`%${filtro}%`, limite] : [limite];
      const texto = `SELECT * FROM posts ${where} LIMIT $${where ? 2 : 1}`;
      const { rows } = await context.db.query(texto, parametros);
      return rows;
    },
  },
};

Nunca interpoles variables dentro del SQL: pasa por placeholders y deja que el driver escape. Componer la cláusula WHERE condicionalmente es normal; interpolar el valor es un riesgo de inyección.

Validación automática del servidor

Una de las ventajas del tipado fuerte: enviar una variable con el tipo equivocado o faltante produce un error de validación estándar antes de tocar los resolvers:

{
  "errors": [
    {
      "message": "Variable \"$id\" of required type \"ID!\" was not provided.",
      "locations": [{ "line": 1, "column": 20 }]
    }
  ]
}

Así, una variable mal tipada no llega a la base de datos: el schema actúa como primera capa de defensa. La lógica de negocio (¿el id existe?, ¿tiene permiso?) la validas tú en el resolver.

Ejercicio

  1. Escribe una query posts($pagina: Int = 1, $tamano: Int = 20) que pagine resultados.
  2. Envíala desde GraphiQL con variables JSON y sin variables (usa los defaults).
  3. Intenta enviar $pagina como "uno" y observa el error de validación.
  4. Adapta el resolver para que pase las variables como placeholders SQL y nunca como literales interpolados.

Resumen

  • Las variables se declaran con $ en la operación y se tipan.
  • Los valores viajan aparte, en el payload JSON variables.
  • Pueden tener valores por defecto y ser opcionales o no-null.
  • El servidor valida tipos y obligatoriedad antes de ejecutar resolvers.
  • Las variables se pasan a la BD como placeholders, nunca interpolar en SQL.
