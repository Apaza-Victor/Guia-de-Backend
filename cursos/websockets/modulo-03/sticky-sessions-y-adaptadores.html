Sticky sessions y adaptadores

🔥 Avanzado 10 min WebSockets y Tiempo Real Módulo 3 · Escalar y asegurar WebSockets

Session affinity: el cliente vuelve a casa

Un WebSocket es una conexión larga: el handshake envía el token y la conexión permanece, pero el estado de esa sesión (usuario autenticado, salas registradas en memoria) vive en el nodo que la aceptó. Si el balanceador reenvía la siguiente conexión a otro nodo, el cliente se «des-autentica» o pierde sus salas.

Las sticky sessions (o session affinity) hacen que el balanceador dirija cada conexión de un mismo cliente SIEMPRE al mismo nodo, durante toda la vida de la sesión. En el reparto inicial (por ejemplo, con una cookie) se decide el nodo, y de ahí en adelante se respeta.

# nginx: ip_hash da afinidad por IP, simple pero imperfecta con IPv6/CGNAT.
upstream chat_backend {
    # sticky session por cookie, respetando la conexión larga del socket
    sticky cookie srv_id;
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    server 10.0.0.13:8080;
}

server {
    listen 443 ssl;
    location /ws {
        proxy_pass http://chat_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

Con ip_hash o una cookie de afinidad consigues que un mismo cliente termine siempre en la misma instancia, preservando su estado en memoria sin tocar una línea de tu código.

Qué se rompe sin sticky sessions

  • Autenticación de handshake en memoria: el token se validó en el nodo X; el nodo Y no conoce esa sesión para la nueva conexión.
  • Salas registradas en Map: los clientes del «nodo A» no aparecen en la lista de la misma sala en el «nodo B».
  • Presencia: un usuario conectado en dos pestañas puede acabar en dos nodos distintos y aparecer duplicado.
  • Reconexión: si el cliente cae y reconecta yendo a otro nodo, su estado debe reconstruirse (o se pierde).

El adaptador de Redis

Las sticky sessions mantienen a cada cliente en su nodo, pero ¿qué pasa si una sala tiene miembros en tres nodos? Ahí entran los adaptadores: componentes que sustituyen la memoria local por una capa compartida. El @socket.io/redis-adapter (sucesor práctico de socket.io-redis) usa dos canales y un pub/sub para que emit, join, leave y los broadcasts tengan alcance de clúster sin que tu código cambie.

// Instalar: npm i socket.io @socket.io/redis-adapter ioredis
const { Server } = require('socket.io');
const { createAdapter } = require('@socket.io/redis-adapter');
const { createClient } = require('redis');

const io = new Server(3000);

// Dos clientes de Redis: un publicador y un suscriptor.
const publicador = createClient({ url: 'redis://redis-cache:6379' });
const suscriptor = publicador.duplicate();

Promise.all([publicador.connect(), suscriptor.connect()]).then(() => {
  io.adapter(createAdapter(publicador, suscriptor));
});

// A partir de aquí, join/leave y emit funcionan en todo el clúster:
io.on('connection', (socket) => {
  socket.on('entrar', (sala) => socket.join('partida:' + sala));
  socket.on('ficha', (dato) => io.to('partida:' + dato.sala).emit('tablero', dato));
});

Con el adaptador, el broadcast a una sala cruza nodos de forma transparente: Redis entrega el evento al suscriptor de cada instancia y esa instancia lo reparte a sus clientes locales. Es el mismo principio del módulo anterior, automatizado.

¿Sticky, adaptador o ambos?

  • Solo sticky + bus propio: válido con ws, cuando controlas tú el transporte (mapas de salas + Redis pub/sub manual).
  • Solo adaptador: suficiente cuando el handshake no depende de estado del nodo (actúa de forma stateless) y las salas son lo único compartido.
  • Ambos (recomendado): sticky para mantener el estado de sesión del nodo, adaptador para sincronizar salas y broadcasts. Así cada pieza cubre una brecha.

Regla de memoria: el sticky resuelve «¿a qué nodo va este cliente?». El bus/adaptador resuelve «¿cómo se entera el resto del mundo?». Son capas complementarias, no alternativas.

Ejercicio

  1. Levanta dos instancias de Socket.IO con el adaptador de Redis y conecta dos clientes; verifica que el broadcast de sala cruza de nodo a nodo.
  2. Desactiva el adaptador en una de las instancias y con los mismos clientes comprueba qué mensajes se pierden; anota el síntoma.
  3. Describe en tres líneas qué pasaría con tu chat si tuvieras sticky sessions pero ningún adaptador.

Resumen

  • Las sticky sessions dirigen a cada cliente siempre al mismo nodo, preservando su estado en memoria.
  • Sin afinidad, la autenticación de handshake, las salas y la presencia se rompen entre nodos.
  • Los adaptadores de Redis reemplazan la memoria local por un pub/sub compartido.
  • @socket.io/redis-adapter da alcance de clúster a join/leave/emit sin cambiar tu lógica.
  • Sticky y adaptador son complementarios: uno fija el nodo, el otro propaga los eventos.
