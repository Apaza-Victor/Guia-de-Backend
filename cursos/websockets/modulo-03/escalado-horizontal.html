Escalado horizontal

🔥 Avanzado 10 min WebSockets y Tiempo Real Módulo 3 · Escalar y asegurar WebSockets

El problema de un solo nodo

Un servidor WebSocket mantiene estado en memoria: el objetivo y sus salas, la presencia, los usuarios conectados. En un proceso único eso funciona, pero agota sus límites cuando crecen las conexiones concurrentes: cada socket vivo ocupa memoria, descriptores de archivo y un hilo del event loop.

El escalado vertical (una máquina más gorda) aporta tarde o temprano un techo físico. La respuesta natural es el escalado horizontal: repartir los clientes entre varias instancias del servidor. Pero entonces nace un enemigo nuevo: una sala puede tener a sus miembros en tres nodos distintos, y el mensaje que llega al nodo A debe llegar también a los clientes del nodo B.

Múltiples instancias, un mismo servicio

Ante un balanceador, los clientes caen a cualquiera de las instancias disponibles. Cada instancia conoce solo A SUS conexiones. Para que el sistema siga pareciendo uno solo necesitamos resolver dos cosas:

  • Mantener la sesión: que el cliente vuelva siempre a la misma instancia (sticky sessions, la siguiente lección).
  • Propagar el mensaje: que un evento emitido en un nodo se replique en los demás (Redis pub/sub, esta lección).
# Topología típica de un servicio real-time horizontal:
#
#              ┌──────────────────┐
#              │  Load balancer   │  (nginx / HAProxy / ALB)
#              └────────┬─────────┘
#        ┌──────────┬───┴────┬──────────┐
#        ▼          ▼        ▼          ▼
#   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
#   │ ws :1  │ │ ws :2  │ │ ws :3  │ │ ws :4  │
#   └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘
#       └──────────┴────┬─────┴──────────┘
#                       ▼
#               ┌──────────────┐
#               │  Redis       │
#               │  (pub/sub)   │
#               └──────────────┘

Redis pub/sub como bus de mensajes

La solución clásica es un bus de mensajes donde todos los nodos se suscriben a un canal (por ejemplo socket-events) y publican cada evento que debe propagarse. La idea:

  1. El nodo A recibe un mensaje «chat en sala general».
  2. El nodo A publica ese evento en el canal de Redis.
  3. Todos los nodos (incluido A) reciben el evento por el suscriptor de Redis.
  4. Cada nodo reenvía el mensaje a los clientes de su sala local.
const { WebSocketServer } = require('ws');
const { createClient } = require('redis');

const wss = new WebSocketServer({ port: 8080 });

// Canales de Redis
const BUS = 'socket-events';

// Suscriptor: escucha eventos de otros nodos y los reenvía localmente.
const suscriptor = createClient();
await suscriptor.connect();
await suscriptor.subscribe(BUS, (mensaje) => {
  const evento = JSON.parse(mensaje);
  reenviarLocal(evento); // a los clientes de ESTE nodo
});

// Publicador: difunde un evento a todos los nodos.
const publicador = createClient();
await publicador.connect();

function propagar(tipo, datos, sala) {
  const evento = JSON.stringify({ tipo, datos, sala, emitidoEn: Date.now() });
  publicador.publish(BUS, evento);
}

// Cuando llega de un cliente local, propagamos y también reenviamos.
wss.on('connection', (ws) => {
  ws.on('message', (datos) => {
    const m = JSON.parse(String(datos));
    propagar(m.tipo, m.datos, m.sala);   // a otros nodos vía Redis
    reenviarLocal(m);                     // a este nodo
  });
});

function reenviarLocal(evento) {
  for (const cliente of wss.clients) {
    if (cliente.readyState === cliente.OPEN) {
      cliente.send(JSON.stringify({ tipo: evento.tipo, datos: evento.datos }));
    }
  }
}

Salas con alcance global

Cuando hay salas, el bus se vuelve aún más útil: publicas con el nombre de la sala en el payload, y cada nodo entrega solo a los clientes locales que pertenecen a esa sala. Optamos por canal único con campo sala (no un canal por sala) para no multiplicar las suscripciones.

function propagarASala(sala, tipo, datos) {
  publicador.publish(BUS, JSON.stringify({ tipo, datos, sala }));
}

function reenviarALaSalaLocal(sala, tipo, datos) {
  const miembros = salasLocales.get(sala);
  if (!miembros) return;
  const marco = JSON.stringify({ tipo, datos });
  for (const ws of miembros) {
    if (ws.readyState === ws.OPEN) ws.send(marco);
  }
}

// Suscriptor de Redis: reconstruir el evento en este nodo.
suscriptor.subscribe(BUS, (msj) => {
  const ev = JSON.parse(msj);
  reenviarALaSalaLocal(ev.sala, ev.tipo, ev.datos);
});

Think before you echo: si publicas en Redis y a la vez reenvías en local, no publiques de vuelta lo que llega del suscriptor (marcar el evento con emitidoEn y un nodoId suele bastar). El patrón es «una sola fuente de verdad en el bus».

Alternativas al pub/sub manual

  • Socket.IO + adapter: la librería trae adaptadores oficiales que hacen exactamente esto: @socket.io/redis-adapter propaga cambios de salas y broadcasts sin tocar el transporte.
  • Colas (Kafka, NATS, RabbitMQ): cuando necesitas persistencia o rejugabilidad de eventos además de difusión.
  • Nube gestionada (AWS API Gateway, Ably, Pusher): el bus y la red de sockets son un servicio; pagas tú por conexión y mensajes.

Ejercicio

  1. Levanta dos instancias de tu servidor de la lección 2 del módulo anterior (con Redis instalado o Docker) en puertos 8081 y 8082.
  2. Conéctate con dos clientes, uno a cada puerto, y comprueba que un mensaje de la sala «general» llega a ambos nodos.
  3. Apaga Redis y anota qué pasa con los mensajes inter-nodo; documenta por qué el sistema sigue funcionando mal por dentro pero los nodos no fallan.

Resumen

  • Un nodo WebSocket mantiene estado en memoria: por eso el escalado horizontal complica las salas y la presencia.
  • El escalado horizontal necesita sticky sessions (misma sesión) + un bus de mensajes entre nodos.
  • Redis pub/sub es el bus clásico: publicar en un canal y estar suscrito a él desde cada instancia.
  • Cada nodo reenvía solo a sus clientes locales de la sala; el bus hace el resto.
  • Socket.IO/adaptadores y servicios gestionados ahorran el transporte manual.
