Heartbeat y timeouts

🔥 Avanzado 9 min WebSockets y Tiempo Real Módulo 3 · Escalar y asegurar WebSockets

El problema de los sockets zombies

Cuando un cliente se va sin despedirse (apagón, wifi cortado, aplicación cerrada de golpe), el servidor no recibe un frame de cierre. La conexión TCP puede quedar «viva» durante minutos: el socket sigue en tu memoria y consumiendo recursos, aunque nadie está al otro lado. Es un socket zombie que ensucia la presencia, las salas y la factura de memoria.

La solución estándar es el heartbeat: una lanza de pings periódicos + comprobación de que el cliente responde con pong. Si no responde en un plazo, el servidor cierra y limpia.

Ping/pong del protocolo

El protocolo ya trae los mecanismos: el servidor envía un frame ping y el peer responde automáticamente un frame pong. En el navegador, el pong surge solo; tu código solo tiene que confiar en que, si el cliente está vivo, tarde o temprano llega algún frame (mensaje, pong…).

// Heartbeat con el paquete ws: sonsacar al cliente cada 30 segundos.
const { WebSocketServer } = require('ws');
const wss = new WebSocketServer({ port: 8080 });

const INTERVALO_PING_MS = 30_000;
const TIMEOUT_PONG_MS = 10_000;

wss.on('connection', (ws) => {
  ws.estaVivo = true;

  // Cualquier tráfico del cliente demuestra vida.
  ws.on('pong', () => (ws.estaVivo = true));
  ws.on('message', () => (ws.estaVivo = true));

  ws.on('close', () => clearInterval(ws.heartbeatTimer));
});

const sondeo = setInterval(() => {
  for (const ws of wss.clients) {
    if (!ws.estaVivo) {
      // Dos rondas sin responder: adiós, zombie.
      ws.terminate();
      continue;
    }
    ws.estaVivo = false;            // si no llega pong/mensaje, muere
    ws.ping();
  }
}, INTERVALO_PING_MS);

wss.on('close', () => clearInterval(sondeo));

La idea «reversible» (cambiar a false ANTES de preguntar y volver a true al recibir respuesta) evita falsos positivos con un solo temporizador.

Heartbeat en Socket.IO

Socket.IO incorpora su propio heartbeat con ping/pong y valores configurables. Los parámetros clave son pingInterval (cada cuánto pregunta) y pingTimeout (cuánto espera la respuesta antes de cortar). El servidor desconecta el cliente y este provoca su reconexión automática.

const { Server } = require('socket.io');
const io = new Server(3000, {
  pingInterval: 25_000,   // pregunta cada 25 s
  pingTimeout: 20_000,    // corta si no responde en 20 s
  transports: ['websocket'] // forzar WebSocket puro (opcional)
});

io.on('connection', (socket) => {
  socket.on('disconnect', (razon) => {
    // razon suele ser 'ping timeout' cuando se detecta un zombie.
    console.log('Desconectado:', socket.id, 'por', razon);
  });
});

El otro lado: reconexión del cliente

El heartbeat detecta muertos, pero quien sufre la caída es el cliente: debe reconectar solo y reconstruir su estado. El esquema ideal tiene tres piezas: reintentos con backoff, carga del estado pendiente (mensajes no entregados, salas) y una UI que avise al usuario.

let intentos = 0;

function conectar() {
  const socket = new WebSocket('wss://api.miservidor.com/chat');

  socket.onopen = () => {
    intentos = 0;
    // Al volver, reintenta unirse a la sala que tenía.
    socket.send(JSON.stringify({ tipo: 'unirse', sala: 'general' }));
  };

  socket.onclose = (e) => {
    if (e.code === 1000) return; // cierre intencional: no reconectar

    const espera = Math.min(500 * Math.pow(2, intentos), 10000);
    intentos += 1;
    console.log(`Reconectando en ${espera} ms…`);
    setTimeout(conectar, espera + Math.random() * 500);
  };

  return socket;
}

const socket = conectar();

Tolerancia a fallos y límites

Un sistema robusto combina heartbeat con límites sensatos:

  • Límite de discontinuidad: corta la reconexión tras N intentos (p. ej. 10) y muestra un mensaje «revisa tu conexión».
  • Capacity del servidor: establece un máximo de conexiones por nodo; al llegar, rechaza nuevas (1008/1024) y avisa a operaciones.
  • Autoescala: encaja con el módulo de escalado: si la memoria o la CPU suben, el orquestador añade nodos y el balanceador reparte.

Regla práctica: configura el timeout de conexión y el heartbeat para que cualquier abandono sea detectado en menos de un minuto, y que la reconexión automática no supere de largo ese ciclo de vida con picos de tráfico.»

Ejercicio

  1. Añade el heartbeat de ws de la lección a tu servidor y conéctale un cliente con DevTools abiertas.
  2. Activa la regulación de red (throttle) o apaga el wifi 45 segundos y observa en el log cómo el servidor termina el socket zombie.
  3. Implementa la reconexión del cliente y comprueba que, al volver la red, la sala se re-establece automáticamente.

Resumen

  • Los sockets zombies son conexiones muertas que consumen recursos y ensucian la presencia.
  • El heartbeat (ping/pong) detecta a los que no responden y los termina.
  • Socket.IO trae heartbeat configurable con pingInterval y pingTimeout.
  • El cliente debe reconectar con backoff y reconstruir su estado (salas, mensajes).
  • Pon límites a los reintentos y a las conexiones por nodo para no degradar el servicio.
