Despliegue tras proxy

🔥 Avanzado 10 min WebSockets y Tiempo Real Módulo 3 · Escalar y asegurar WebSockets

Por qué detrás de un proxy

En producción casi nunca se expone directamente el puerto del servidor Node. Delante colocas un proxy inverso que concentra TLS, balanceo, cabeceras de seguridad, compresión y el WAF (Web Application Firewall). El reto: HTTP por defecto trata cada petición como conversaciones sueltas y cierra la conexión, así que un WebSocket a través de un proxy necesita que este no cortocircuite el flujo.

Para que el socket sobreviva al proxy hacen falta dos cabeceras mágicas en la petición entrante: Upgrade: websocket y Connection: Upgrade. El proxy debe reenviarlas tal cual a la instancia de Node, porque son las que disparan el handshake 101.

nginx: el secreto está en las cabeceras

Esta es la configuración canónica para exponer sockets con nginx:

map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;   # sin cabecera Upgrade => conexión HTTP normal
}

upstream chat_backend {
    least_conn;                       # reparto por conexiones activas
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
}

server {
    listen 443 ssl;
    server_name chat.miservidor.com;

    ssl_certificate     /etc/letsencrypt/live/chat.miservidor.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/chat.miservidor.com/privkey.pem;

    location /ws {
        proxy_pass http://chat_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

El bloque map convierte la conexión en upgrade cuando el cliente lo pide y en close (comportamiento HTTP normal) cuando no, lo que permite servir REST y WebSocket por el mismo servidor.

Timeouts de proxy para conexiones largas

El error más común al desplegar sockets tras un proxy son las desconexiones «por tiempo»: nginx y HAProxy tienen timeouts de lectura/escritura pensados para HTTP corto (habitualmente 60 s). Un socket que lleva 2 minutos abierto parece «una petición abandonada» y el proxy lo corta.

# nginx: subir los timeouts para conexiones WebSocket largas.
proxy_read_timeout 3600s;
proxy_send_timeout 3600s;
proxy_connect_timeout 5s;   # el handshake 101 debe ser rápido

# Y el par de rigor:
proxy_buffering off;        # no almacenes en buffer antes de enviar
proxy_cache off;            # nada de cachear frames

# HAProxy: lo mismo pero en su propio dialecto.
frontend https_in
    bind *:443 ssl crt /etc/haproxy/chat.pem
    mode http
    timeout client 3600s
    default_backend chat_ws

backend chat_ws
    mode http
    timeout server 3600s
    timeout connect 5s
    option http-server-close
    server ws1 127.0.0.1:8080 check
    server ws2 127.0.0.1:8081 check

Sticky sessions en el proxy

Recuerda el módulo de escalado: si tus nodos guardan el estado de sesión en memoria, el balanceador debe ser sticky. En nginx se logra con una cookie de afinidad (antes viste sticky cookie srv_id) o con ip_hash; en HAProxy con balance hdr(X-Forwarded-For) o con cookie SERVERID insert.

# HAProxy con afinidad por cookie:
backend chat_ws
    mode http
    cookie SERVERID insert indirect nocache
    server ws1 127.0.0.1:8080 check cookie ws1
    server ws2 127.0.0.1:8081 check cookie ws2

Esta cookie no tiene nada que ver con la autenticación: solo recuerda al balanceador a qué nodo asignó a ese cliente.

WAF, rate limits y observación

El proxy es también tu punto de control:

  • WAF: un Web Application Firewall delante (o un proxy que filtre payloads) puede bloquear payloads sospechosos antes de llegar a tu Node.
  • Rate limiting global: limita conexiones nuevas por IP (limit_req_zone en nginx) además del rate limiting por socket del servidor.
  • Logging HTTP/X-Real-IP: confía en X-Forwarded-For con cuidado; valida si tu servidor la lee. Fíjate el maxPayload en ws para no aceptar frames gigantes.
# nginx: limitar conexiones nuevas por IP antes de llegar a Node.
limit_req_zone $binary_remote_addr zone=ws_conn:10m rate=10r/s;

location /ws {
    limit_req zone=ws_conn burst=20 nodelay;
    proxy_pass http://chat_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}

Ejercicio

  1. Despliega tu servidor Node en localhost:8080 y añade delante una config de nginx (o HAProxy) con handshake Upgrade correcto.
  2. Baja proxy_read_timeout a 5 s a propósito y comprueba la desconexión del socket a los 5 s; explica por qué pasa.
  3. Incluye sticky sessions y verifica con dos clientes que la segunda conexión de un mismo usuario cae al mismo nodo (log del servidor).

Resumen

  • El proxy inverso aporta TLS, balanceo, seguridad y observación; debe reenviar Upgrade/Connection para los sockets.
  • Los timeouts de proxy por defecto matan las conexiones largas: súbelos a 3600s o más.
  • Destierra buffering y caché en la ruta de los frames.
  • Sticky sessions en el proxy si los nodos guardan estado en memoria.
  • WAF, rate limits por IP y maxPayload completan la defensa en producción.
