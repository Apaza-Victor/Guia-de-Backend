Seguridad

🔥 Avanzado 11 min WebSockets y Tiempo Real Módulo 3 · Escalar y asegurar WebSockets

Transporte cifrado: wss:// siempre

En producción, la regla número uno es exigir wss:// (TLS por detrás). Un socket sin cifrar deja que cualquiera entre la red lea y reenvíe los mensajes: se puede robar tokens, suplantar mensajes o inyectar frames. El coste de TLS moderno es mínimo y lo absorbe un proxy o el balanceador.

  • Nunca termines el TLS dentro del código de tu aplicación si puedes evitarlo: nginx/caddy o el balanceador lo gestionan.
  • El navegador ya fuerza el bloqueo: una página HTTPS no puede abrir un socket ws:// (contenido mixto).
  • Redirige cualquier intento ws:// hacia wss:// o recházalo con un error claro.
# nginx: forzar wss y no aceptar ws plano
server {
    listen 80;
    return 301 https://$host$request_uri;   # hasta el upgrade se va por 443
}

server {
    listen 443 ssl;
    ssl_certificate     /etc/letsencrypt/live/.../fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/.../privkey.pem;

    location /ws {
        proxy_pass http://chat_backend;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

Validar el origen del cliente

La cabecera Origin del handshake dice de qué página viene el navegador. Sin validarla, cualquier web maliciosa puede abrir sockets contra tu servidor y usar tu API desde el lado del usuario (un CSWSH: Cross-Site WebSocket Hijacking). La defensa es comprobar el origen contra una lista blanca de dominios propios.

const { WebSocketServer } = require('ws');
const wss = new WebSocketServer({ port: 8080, verifyClient });

const ORIGENES_PERMITIDOS = new Set([
  'https://app.miservidor.com',
  'https://admin.miservidor.com',
]);

function verifyClient({ origin }, callback) {
  if (!origin || ORIGENES_PERMITIDOS.has(origin)) {
    callback(true);
    return;
  }
  console.warn('Origen rechazado:', origin);
  callback(false, 403, 'Origen no permitido');
}

Añade una segunda capa con la autenticación por token de la lección anterior: el origin valida al «navegador» y el token valida al «usuario».

Rate limiting por conexión

Los sockets pueden convertirse en un canal de abuso: un nodo que emite miles de mensajes por segundo satura la CPU, el bus de Redis y la base de datos. El rate limiting por conexión cuenta los mensajes en una ventana de tiempo y corta al que exceda el límite.

// Rate limiting simple por socket: ventana de 10 s, máximo 30 mensajes.
const VENTANA_MS = 10_000;
const MAX_MENSAJES = 30;

wss.on('connection', (ws) => {
  ws.contador = 0;
  ws.ventanaInicio = Date.now();

  ws.on('message', (datos) => {
    const ahora = Date.now();
    if (ahora - ws.ventanaInicio > VENTANA_MS) {
      ws.contador = 0;
      ws.ventanaInicio = ahora;
    }

    ws.contador += 1;
    if (ws.contador > MAX_MENSAJES) {
      ws.close(1008, 'Demasiados mensajes en la ventana');
      return;
    }

    procesarMensaje(ws, datos);
  });
});

Para sistemas en clúster, mueve el contador a Redis (INCR con EXPIRE) para que el límite sea global y no por nodo: con ws es todo tuyo; con Socket.IO añade un middleware use() que cuente eventos.

Sanitizar y validar los mensajes

Todo lo que entra por un socket es no confiable. Valida el JSON con un esquema, comprueba tamaños y tipos, y nunca interpoles datos de usuario en HTML o en comandos. Un chat que devuelve el texto sin limpiar permite XSS: el navegador de la víctima ejecuta el fragmento HTML que otro usuario envió.

function sanitizarEntrada(mensaje) {
  // 1) Límites de tamaño antes de procesar.
  if (mensaje.length > 4096) throw new Error('mensaje demasiado largo');

  // 2) Validar estructura mínima.
  const datos = JSON.parse(mensaje);
  if (typeof datos.tipo !== 'string') throw new Error('tipo inválido');
  if (datos.datos && typeof datos.datos.texto === 'string') {
    // 3) Escapar antes de guardar/emitir para neutralizar HTML.
    datos.datos.texto = datos.datos.texto
      .replace(/&/g, '&amp;')
      .replace(/</g, '&lt;')
      .replace(/>/g, '&gt;')
      .replace(/\//g, '&#x2F;');
  }
  return datos;
}

ws.on('message', (datos) => {
  try {
    const limpio = sanitizarEntrada(String(datos));
    broadcast('chat', limpio.datos);
  } catch (err) {
    ws.send(JSON.stringify({ tipo: 'error', razon: err.message }));
  }
});

En el cliente, además de confiar en el escape, pinta mensajes con textContent en vez de innerHTML para que el navegador nunca los trate como HTML.

Autorización por evento

Autenticar no es lo mismo que autorizar. Aunque el usuario esté identificado, debe comprobarse si tiene derecho a ejecutar cada acción: ¿está en esa sala? ¿puede ver el canal privado de otro usuario? Pide siempre el rol o la pertenencia antes de responder.

function puedeEscucharCanal(ws, canal) {
  // Ejemplo real: un canal privado exigirá autoría o rol de admin.
  if (canal.startsWith('privado:')) {
    return ws.usuario?.rol === 'admin' || canal === 'privado:' + ws.usuario?.id;
  }
  return true; // canales públicos
}

ws.on('message', (datos) => {
  const m = JSON.parse(String(datos));
  if (!puedeEscucharCanal(ws, m.sala)) {
    ws.close(1008, 'No tienes acceso a ese canal');
    return;
  }
  unirseASala(ws, m.sala);
});

Ejercicio

  1. Añade a tu servidor la validación de origen con una lista blanca de un dominio de prueba.
  2. Implementa el rate limiting de la lección: conéctale dos clientes, inunda con 50 mensajes y observa cómo se corta el abusador con 1008.
  3. Envía el payload <script>alert(1)</script> y comprueba que llega escapado a los clientes y, pintándolo con textContent, no se ejecuta.

Resumen

  • Obliga a wss:// (TLS) y deja la terminación SSL al proxy.
  • Valida el Origin del handshake contra una lista blanca de dominios.
  • Aplica rate limiting por conexión (y global con Redis si escalas).
  • Valida y escapa todo mensaje; usa textContent en el cliente.
  • Autoriza por evento además de autenticar en el handshake.
