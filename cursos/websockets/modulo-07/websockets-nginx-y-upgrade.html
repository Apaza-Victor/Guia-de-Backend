Nginx y el header Upgrade

🔥 Avanzado 11 min WebSockets y Tiempo Real Módulo 7 · WebSockets en producción

Introducción

En producción casi nunca expones el servidor de socket al mundo: delante hay un Nginx, un CDN o el ingress de Kubernetes. Si el proxy no entiende tu upgrade, la conexión muere al poco de nacer.

La clave son dos cabeceras: Connection: upgrade y Upgrade: websocket. Por defecto Nginx no las reenvía; hay que decírselo de forma explícita.

Definición

Para que el handshake WebSocket atraviese Nginx, la configuración debe reenviar HTTP/1.1, las cabeceras Upgrade y Connection, y fijar timeouts largos para las conexiones persistentes.

Por qué importa. Un proxy bien configurado da TLS, balanceo, caché y protección de abuso a tus sockets; mal configurado, rompe conexiones cada 60 segundos.

Cuándo usarlo. Configura el upgrade siempre que quieras servir REST y WebSockets desde el mismo dominio, cifrar en el proxy o distribuir entre varias instancias.

Conceptos clave

  • proxy_http_version 1.1 permite conexiones persistentes.
  • proxy_set_header Upgrade $http_upgrade conserva la petición de cambio.
  • Connection: upgrade obliga a pasar la conexión tal cual.
  • Timeouts de lectura y escritura largos evitan que Nginx mate el socket.
  • proxy_read_timeout afecta también a sockets inactivos.

Ejemplo real

Con varias instancias, un upstream con hash por IP mantiene a cada socket en su nodo.

  • Fija proxy_read_timeout por encima del heartbeat de tu aplicación.
  • Reenvía la IP real con X-Real-IP para logs y seguridad.
  • Para varias instancias, usa upstream con hash por IP o una cookie.

El hash por IP es una fijación pobre tras NAT; la alternativa robusta es cookie o adaptador con estado compartido.

Explicación

  • Nginx usa HTTP/1.0 por defecto en proxy_pass, que no soporta bien conexiones persistentes.
  • La cabecera Connection pasa a indicar upgrade en el proxy.
  • El timeout por defecto de 60 segundos corta sockets inactivos: de ahí los cortes típicos.
  • Los logs de Nginx guardan el estado de conexión para diagnosticar cortes.
  • La misma directiva proxy_http_version sirve para REST con keep-alive.

Errores comunes

  • Olvidar proxy_http_version 1.1 y romper el keep-alive.
  • Dejar proxy_read_timeout en 60 segundos y cortar sockets inactivos.
  • Añadir dos veces la cabecera Connection en cadenas de proxies.

Buenas prácticas

  • Empieza con la configuración mínima y añade solo lo que necesites.
  • Fija timeouts largos; que el heartbeat de tu app los alimente.
  • Prueba con una pausa de cinco minutos para validar el timeout.
  • Reenvía el protocolo real para que el backend sepa si vino por wss.

Ejercicio

  1. Configura Nginx para /ws y conéctate desde el navegador.
  2. Reproduce el corte a los 60 segundos y sube proxy_read_timeout.
  3. Añade el upstream con hash y comprueba la fijación del socket.

Resumen

  • Nginx exige HTTP/1.1 y reenviar Upgrade y Connection.
  • Los timeouts del proxy matan sockets inactivos: alárgalos.
  • Con TLS y hash, un solo bloque sirve web y sockets.
