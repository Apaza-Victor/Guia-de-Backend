Despliegue en contenedores

🔥 Avanzado 11 min WebSockets y Tiempo Real Módulo 7 · WebSockets en producción

Introducción

Un socket detrás de un contenedor cambia la dinámica: si el contenedor se reinicia, todas las conexiones mueren con él. En un mundo con replicas y pods, el diseño debe contemplar reconexión, drenaje y salud.

Empaquetar el servidor WebSocket en una imagen pequeña y definir healthchecks correctos es la base de despliegues repetibles y seguros.

Definición

Desplegar en contenedores significa empaquetar el servidor en una imagen inmutable, definir healthchecks de readiness y planificar el drenaje y la reconexión de los clientes cuando una réplica muere.

Por qué importa. La orquestación reinicia contenedores sin aviso; el sistema gana si las conexiones se cierran con elegancia y los clientes reconectan a otra réplica sin perder el chat.

Cuándo usarlo. Conteneriza siempre tu backend de socket para despliegues uniformes, y añade el patrón de drenaje (graceful shutdown) antes de escalar a varias réplicas.

Conceptos clave

  • Una imagen base con Node mantiene el contenedor pequeño y reproducible.
  • El readinessProbe matricula el socket solo cuando el servidor acepta conexiones.
  • El graceful shutdown cierra los sockets con el código 1001 y espera un drenaje.
  • Las réplicas comparten estado por Redis para que el broadcast sobreviva.
  • El ingress reenvía el upgrade igual que Nginx vimos antes.

Ejemplo real

En Kubernetes el Ingress encadena TLS y upgrade, y las sondas deciden cuándo el pod acepta tráfico.

  • Define readinessProbe sobre /healthz y livenessProbe aparte.
  • Drena para que los clientes reconecten a otra réplica sin perder mensaje.
  • Comparte el estado con Redis para que el broadcast sobreviva al pod.

Con máquinas de muchos clientes, sube el número de réplicas en lugar de meter miles de sockets en una.

Explicación

  • El empaquetado en contenedores hace el despliegue reproducible en todos los entornos.
  • El kernel limita los file descriptors: ajusta el límite del contenedor al número de sockets estimado.
  • El graceful shutdown respeta el protocolo y da margen para pasar a otra instancia.
  • Una imagen pequeña acelera los despliegues y reduce la superficie de ataque.
  • Las actualizaciones graduales (rolling update) alternan réplicas para no matar todo a la vez.

Errores comunes

  • Dejar fuera el graceful shutdown: cada despliegue corta todas las conexiones de golpe.
  • No configurar el límite de file descriptors y quedarse sin sockets.
  • Contenerizar sin healthcheck: el orquestador nunca sabe si el pod está listo.

Buenas prácticas

  • Baja el timeout de cierre a pocos segundos y fuerza la salida si no drena.
  • Registra los eventos de shutdown para auditarlos.
  • Comparte el estado en Redis: es lo que permite escalar réplicas.
  • Prueba el rollout matando un pod con el chat abierto.

Ejercicio

  1. Empaqueta tu servidor y levántalo en un contenedor con healthcheck.
  2. Añade graceful shutdown y comprueba que los clientes reconectan.
  3. Sube el límite de file descriptors y mide el máximo de conexiones soportadas.

Resumen

  • Los contenedores aportan imágenes inmutables y despliegues uniformes.
  • Readiness, liveness y graceful shutdown hacen los reinicios inocuos.
  • Con estado compartido, la granja de réplicas sobrevive a cada pod.
