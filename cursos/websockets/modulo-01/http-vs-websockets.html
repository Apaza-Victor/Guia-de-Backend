HTTP vs WebSockets

🔥 Avanzado 9 min WebSockets y Tiempo Real Módulo 1 · Fundamentos de WebSocket

El modelo petición-respuesta

HTTP funciona como un buzón de correo: el cliente escribe una carta (la petición), espera a que llegue al servidor y recibe una carta de vuelta (la respuesta). Cada intercambio es una unidad completa: el cliente pregunta, el servidor contesta y la historia termina hasta la siguiente petición.

Este modelo es estupendo para leer recursos (una página, un JSON, una imagen) y para registrar acciones (crear un pedido, iniciar sesión). Pero el servidor nunca puede hablar por iniciativa propia: si ha pasado algo mientras el cliente está en silencio, la información queda esperando a que alguien pregunte.

// Un cliente HTTP clásico: pregunta y espera respuesta.
async function obtenerEstadoPedido(pedidoId) {
  const respuesta = await fetch('/api/pedidos/' + pedidoId);
  const pedido = await respuesta.json();
  console.log('Estado actual:', pedido.estado);
  return pedido;
}

// Si el pedido cambia a los 3 segundos, nosotros no nos enteramos
// hasta que volvamos a preguntar. Ese es el problema que resuelve
// la comunicación en tiempo real.
obtenerEstadoPedido('PED-2041');

Polling y long-polling

Para simular «tiempo real» con HTTP puro, el truco clásico es el polling: el cliente pregunta a intervalos fijos, por ejemplo cada 5 segundos. Es simple, pero desperdicia recursos: la mayoría de las respuestas repiten información «nada ha cambiado», y la latencia media percibida es de hasta 5 segundos.

El long-polling mejora la latencia: el servidor retiene la petición abierta hasta que tenga algo que decir, y responde en el momento en que ocurre el evento; el cliente entonces abre otra petición inmediatamente. Fue la técnica dominante antes de WebSockets, pero consume una conexión por cliente de forma casi permanente y complica el servidor.

// Polling: preguntar cada 4 segundos si hay novedades.
const intervalo = setInterval(async () => {
  const res = await fetch('/api/timbres/nuevos');
  const timbres = await res.json();
  if (timbres.length > 0) {
    console.log('¡Nueva notificación recibida!', timbres);
  }
}, 4000);

// Detener el polling cuando el usuario cierra la sesión.
function cerrarSesion() {
  clearInterval(intervalo);
}
// Long-polling: la petición se queda "colgada" hasta que haya datos.
async function escuchar() {
  const res = await fetch('/api/eventos/largo');
  const evento = await res.json();
  procesarEvento(evento);
  escuchar(); // y vuelta a preguntar, inmediatamente.
}

Push real con WebSockets

Con WebSocket la situación cambia de raíz: la conexión se abre una vez y queda tendida un puente permanente. El servidor puede empujar (push) mensajes cuando ocurre un evento, sin que nadie pregunte, y el cliente también puede enviar datos sin esperar:

  • Latencia: de segundos (polling) a milisegundos (socket).
  • Coste: una sola conexión TCP con unos pocos bytes de cabecera por cada mensaje, no un HTTP completo por consulta.
  • Bidireccionalidad: el mismo canal sirve para enviar y recibir; en HTTP el envío de datos siempre requiere una petición aparte.
const socket = new WebSocket('wss://tienda.miweb.com/pedidos');

socket.onmessage = (evento) => {
  const pedido = JSON.parse(evento.data);
  if (pedido.estado === 'en-camino') {
    mostrarMapaEnVivo(pedido.id);
  }
};

// El servidor decide cuándo avisar: push real, sin polling.
socket.send(JSON.stringify({ tipo: 'suscribirse', pedidoId: 'PED-2041' }));

Comparativa y cuándo elegir

Ninguna tecnología es «mejor» en abstracto; cada una resuelve un problema distinto. Esta tabla resume las diferencias esenciales:

  • HTTP: petición-respuesta, sin estado por conexión, fácil de cachear y escalar con balanceadores sin más. Ideal para consultas y mutaciones puntuales.
  • HTTP + polling: aceptable para novedades poco frecuentes y cuando no se puede usar un socket. Desperdicia peticiones.
  • WebSocket: conexión persistente, bidireccional, de baja latencia. Ideal para chat, notificaciones y streaming, pero mantiene recursos vivos por cliente.

Regla práctica: si el usuario necesita enterarse en menos de un segundo de lo que otros hacen, usa un socket. Si la página puede refrescarse cuando el propio usuario lo pide, HTTP es más simple y barato.

Ejercicio

  1. Elige una aplicación real (tu red social, un messenger o un dashboard) y anota tres momentos donde use polling o push.
  2. Calcula cuántas peticiones HTTP al día genera un polling de 5 segundos en una sola pestaña abierta 8 horas (8 h × 720 peticiones/hora).
  3. Propón para cada caso anterior una alternativa: WebSocket, long-polling o mantener HTTP. Justifica brevemente cada elección.

Resumen

  • HTTP es petición-respuesta: el servidor solo habla cuando el cliente pregunta.
  • El polling pregunta por intervalos y el long-polling mantiene la petición abierta para reducir la latencia.
  • WebSocket es una conexión persistente y bidireccional: el push es inmediato.
  • Elige HTTP para consultas puntuales y WebSocket para lo que deba llegar en milisegundos.
