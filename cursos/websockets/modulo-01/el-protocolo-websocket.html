El protocolo WebSocket

🔥 Avanzado 9 min WebSockets y Tiempo Real Módulo 1 · Fundamentos de WebSocket

El estándar RFC 6455

WebSocket no es un invento de una empresa ni una librería mágica: es un protocolo formal definido en el documento RFC 6455 del IETF. Bajo la superficie, todo se reduce a unas reglas precisas sobre cómo empezar la conversación, cómo se trocea la información y cómo se cierra la conexión.

Conocer esas reglas te sirve por dos razones: entiendes por qué el «handshake» se parece sospechosamente a HTTP, y puedes leer capturas de red o mensajes de error sin que parezcan jeroglíficos.

El handshake: HTTP Upgrade

Todo WebSocket nace como una petición HTTP normal de la que el cliente pide «promover» el protocolo con la cabecera Upgrade. El servidor, si acepta, responde con el código 101 Switching Protocols y a partir de ese segundo ya no habla HTTP sino frames WebSocket sobre la misma conexión TCP.

# Petición del cliente (lo que el navegador envía por ti):
GET /chat HTTP/1.1
Host: api.miservidor.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.miservidor.com

# Respuesta del servidor si acepta:
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

La clave Sec-WebSocket-Key se combina con un GUID fijo del estándar (258EAFA5-E914-47DA-95CA-C5AB0DC85B11), se aplica SHA-1 y base64, y el resultado viaja en Sec-WebSocket-Accept. Así el servidor demuestra que de verdad habla el protocolo, sin necesidad de credenciales.

Por diseño, casi cualquier cliente puede hacer un handshake: WebSocket funciona sobre el puerto 80 (ws) o 443 (wss), así que el tráfico atraviesa firewalls y proxies que ya permiten salida web.

Los marcos (frames)

Después del 101, la comunicación deja de usar líneas de texto HTTP y pasa a enviar marcos (frames): trocitos de datos con una cabecera pequeña que indica qué son. La cabecera de un frame WebSocket empieza con:

  • FIN: 1 bit que marca si es el último fragmento de un mensaje (si un mensaje se parte, los frames en cadena lo recomponen).
  • Opcode: 4 bits que indican el tipo del frame (texto, binario, ping, pong, cierre).
  • MASK: 1 bit. Los clientes deben enmascarar sus frames (bit a 1); el servidor no, para detectar bugs de intermediarios.
  • Longitud: 7 bits estándar, ampliables a 16 o 64 bits para mensajes grandes.

Esa cabecera tan compacta es lo que hace a WebSocket tan ligero frente a HTTP: cada mensaje puede costar solo 2-6 bytes de overhead, en lugar de cientos de bytes de cabeceras.

Opcodes que debes conocer

Los opcodes más relevantes del RFC 6455 en la práctica:

  • 0x1 text — mensaje de texto (UTF-8), el que usas con JSON.
  • 0x2 binary — datos binarios (imágenes, buffers).
  • 0x8 close — cierre de conexión; puede llevar un código de cierre.
  • 0x9 ping — comprobación de vida enviada por el servidor.
  • 0xA pong — respuesta automática a un ping.

Curiosidad útil: los clientes no pueden enviar pings. Los pings son cosa del servidor (o del proxy), y el otro extremo responde el pong solo. Eso lo aprovecharemos al montar el heartbeat de los sockets.

// En el navegador no ves el frame, pero detrás ocurre esto:
// Envío de un frame de texto con FIN=1, opcode=0x1 y payload JSON.
const datos = { tipo: 'mensaje', texto: '¡Hola, mundo!' };
const json = JSON.stringify(datos);
socket.send(json); // un frame WebSocket de texto enmascarado por el cliente

// Protocolo de salto: un frame 0x8 (close) sin más es decir adiós.
socket.close(1000, 'me voy de casa');

Fragmentación y control

Un mensaje grande puede enviarse en varios frames: los intermedios llevan el mismo opcode, el último desactiva FIN. Los frames de control (ping, pong, close) nunca se fragmentan y pueden aparecer entre fragmentos de un mensaje largo, lo que permite mantener viva la conexión mientras un archivo grande va por partes.

El protocolo también define el enmascarado de los datos del cliente con un array aleatorio de 4 bytes: evita que un proxy mal configurado (o un atacante intermedio) pueda inyectar contenido camuflado en la conexión.

Ejercicio

  1. Abre las herramientas de desarrollador (pestaña Red/Network) y filtra por WS: conecta a wss://echo.websocket.events y envía un mensaje.
  2. Inspecciona el frame enviado: anota el opcode y la longitud visible en los detalles del mensaje.
  3. Explica en una frase por qué el handshake se hace con HTTP en vez de inventar un protocolo nuevo desde cero.

Resumen

  • WebSocket está estandarizado en el RFC 6455 sobre TCP.
  • La conexión empieza con un handshake HTTP Upgrade y la respuesta 101 Switching Protocols.
  • Los mensajes viajan en frames con cabecera mínima: FIN, opcode, mask y longitud.
  • Los opcodes principales son texto, binario, ping, pong y cierre.
  • El enmascarado del cliente protege de proxies y de inyección de contenido.
