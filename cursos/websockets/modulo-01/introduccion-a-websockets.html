Introducción a WebSockets

🔥 Avanzado 8 min WebSockets y Tiempo Real Módulo 1 · Fundamentos de WebSocket

Introducción

Imagina un chat en el que el servidor te avisa al instante cuando llega un mensaje, sin que tengas que recargar la página ni preguntar «¿hay algo nuevo?». El mecanismo que lo hace posible es el WebSocket: un protocolo de comunicación que abre una conexión persistente entre el navegador (o cliente) y el servidor, y que permite enviar mensajes en ambas direcciones de forma continua.

A diferencia de HTTP, donde cada conversación empieza con una petición y termina con una respuesta, un WebSocket se abre una sola vez y permanece conectado durante toda la sesión, intercambiando miles de mensajes por esa misma conexión abierta.

Usamos WebSockets cuando la información debe llegar casi en tiempo real: chats, notificaciones, tableros colaborativos, juegos multijugador, cotización de acciones o el estado de un pedido en un sistema de delivery.

Comunicación full-duplex

El adjetivo full-duplex describe que las dos partes pueden hablar a la vez por el mismo canal: el cliente envía, el servidor envía, y ambos reaccionan en tiempo real sin esperar turnos. Es como una llamada telefónica: mientras tú hablas, la otra persona puede interrumpirte, y viceversa.

  • Simplex: una sola dirección. Como una radio comercial: solo se transmite.
  • Half-duplex: ambas direcciones, pero no a la vez. Como un walkie-talkie: presionas y hablas, sueltas y escuchas.
  • Full-duplex: ambas direcciones simultáneamente. WebSocket es full-duplex.

Esta propiedad es la que diferencia a WebSocket de un simple push del servidor: el cliente también puede enviar datos en cuanto la conexión existe, sin esperar a que el servidor «pregunte».

Las URLs ws:// y wss://

Las conexiones WebSocket usan sus propios esquemas de URL, muy parecidos a los de HTTP. La única diferencia visible entre una y otra es la seguridad de la capa de transporte:

  • ws:// — WebSocket sin cifrar, el equivalente de http://. Útil para desarrollo local y pruebas.
  • wss:// — WebSocket sobre TLS (el mismo cifrado que usa HTTPS), el equivalente de https://. Obligatorio en producción sobre el puerto 443.

En el navegador, una misma conexión puede comenzar como HTTPS y usar los datos de la página para actualizarse por wss. Conviene recordar la regla de oro: si tu página se sirve por HTTPS, los sockets deben ser wss://, o el navegador los bloqueará por contenido mixto.

const socket = new WebSocket('wss://api.miservidor.com/notificaciones');

socket.onopen = () => {
  console.log('Conexión establecida sobre wss://');
  socket.send(JSON.stringify({ tipo: 'suscripcion', canal: 'resumen-de-precios' }));
};

socket.onmessage = (evento) => {
  const mensaje = JSON.parse(evento.data);
  console.log('Evento recibido:', mensaje.tipo);
};

¿Cuándo usar WebSockets?

WebSocket no es la respuesta a todo: aporta valor cuando la latencia importa y cuando hay comunicación bidireccional frecuente. Algunos casos ideales:

  • Chats y mensajería: los mensajes de otros usuarios deben aparecer al instante.
  • Notificaciones en vivo: avisos de eventos, alertas del sistema, campañas que llegan mientras el usuario navega.
  • Colaboración en tiempo real: editores compartidos, tableros kanban, pizarras de dibujo.
  • Streaming de estado o métricas: paneles de monitoreo, colas de trabajo, progreso de tareas largas.
  • Juegos y apps interactivas: sincronización de posiciones y acciones entre varios jugadores.

En cambio, para consultas puntuales (por ejemplo, cargar el perfil de un usuario) sigue siendo preferible una API REST o GraphQL normal sobre HTTP: crean y cierran conexiones cortas y escalan sin mantener tantos recursos vivos.

El mensaje: texto o binario

Por un socket viajan mensajes, no peticiones ni respuestas. Un mensaje puede ser texto (lo más común, casi siempre JSON) o datos binarios (imágenes, audio, buffers). El navegador los entrega a través del evento onmessage y decide codificación.

La práctica habitual es usar un pequeño sobre JSON que indica el tipo de evento y sus datos; así el servidor puede enrutar cada mensaje sin acoplarse a un formato rígido:

{
  "tipo": "mensaje_nuevo",
  "datos": {
    "canal": "soporte",
    "autor": "ana",
    "texto": "¿Puedes revisar mi pedido?",
    "enviadoEn": "2026-09-21T10:32:00Z"
  }
}

Más adelante verás que este patrón de tipo + datos es la base de librerías como Socket.IO, que lo convierten en un concepto central llamado eventos.

Ejercicio

  1. Abre la consola de desarrollador de tu navegador y ejecuta new WebSocket('wss://echo.websocket.events') para crear una conexión de prueba.
  2. Escucha onopen y onmessage con la consola y responde al servidor con un mensaje JSON: socket.send(JSON.stringify({tipo:'hola'})).
  3. Cierra la conexión con socket.close() y escribe en una frase cuándo usarías wss:// en vez de ws:// en un producto real.

Resumen

  • WebSocket es un protocolo de comunicación sobre TCP que mantiene una conexión persistente entre cliente y servidor.
  • Es full-duplex: ambas partes envían y reciben mensajes simultáneamente.
  • Se conecta con las URLs ws:// (sin cifrar) y wss:// (cifrada con TLS).
  • Es ideal para chats, notificaciones y datos en vivo; HTTP sigue siendo mejor para consultas puntuales.
  • Los mensajes viajan como texto (normalmente JSON) o datos binarios.
