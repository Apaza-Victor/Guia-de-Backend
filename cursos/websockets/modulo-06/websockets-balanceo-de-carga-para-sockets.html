Balanceo de carga para sockets

🔥 Avanzado 11 min WebSockets y Tiempo Real Módulo 6 · Escalado y balanceo

Introducción

Tus instancias reparten peticiones HTTP con un simple round-robin, pero un socket no es una petición: una vez establecido, es una conexión larga que debe quedarse en la misma máquina durante horas.

El balanceador debe pegar cada socket a una instancia (sticky sessions) o el protocolo de la capa de aplicación debe repartir con estado compartido, como hace un balanceador de capa 7 con el upgrade.

Definición

El balanceo para tiempo real es la distribución de conexiones largas entre instancias garantizando que cada conexión siga atendida por la misma máquina, o bien que el estado compartido permita entregarla desde cualquiera.

Por qué importa. Un socket es estado: el broadcast local, las salas y la presencia dependen de saber dónde vive cada conexión; dividirlas sin lógica rompe el sistema.

Cuándo usarlo. Usa sticky sessions con ws puro y estado en memoria; con el estado compartido en Redis puedes repartir con menos restricciones y usar balanceo de capa 7.

Conceptos clave

  • Sticky session fija cada cliente a una instancia.
  • Los balanceadores de capa 7 entienden el upgrade WebSocket.
  • El hash por IP o una cookie permiten la fijación.
  • Con estado en Redis el reparto puede ser más flexible.
  • Nginx y HAProxy soportan upgrades a nivel de capa 7.

Ejemplo real

En producción conviene verificar que el balanceador reenvía las cabeceras correctas y que cada nodo reporta salud.

  • Elige sticky solo si hay estado en memoria; si no, prefiere balanceo L7 con estado compartido.
  • Válida que el balanceador reenvíe Upgrade y Connection.
  • Mide el reparto para detectar nodos calientes.

Los ingress de Kubernetes también necesitan la anotación o configuración de upgrade para sockets.

Explicación

  • Una vez establecido, el socket no se puede trasladar: esa es la esencia de la fijación.
  • El hash consistente minimiza los repartos cuando se añaden instancias.
  • Con estado en Redis, un cliente puede caer en cualquier nodo sin perder salas ni presencia.
  • El reinicio de una instancia sigue siendo molesto: los clientes reconectan y el estado compartido da continuidad.
  • Mide el reparto: un nodo caliente degrada la latencia de su grupo.

Errores comunes

  • Repartir sockets con round-robin sin sticky y perder broadcasts.
  • Olvidar las cabeceras de upgrade en el proxy.
  • Guardar presencia solo en memoria de una instancia con varias réplicas.

Buenas prácticas

  • Empieza con una sola instancia y añade nodos gradualmente.
  • Configura Nginx con hash por IP o con una cookie del cliente.
  • Prueba matar una instancia y comprobar que los clientes reconectan.
  • Combina estado compartido con un healthcheck del balanceador.

Ejercicio

  1. Levanta dos instancias con estado en memoria y un Nginx: reproduce el bug de broadcast.
  2. Añade Redis Pub/Sub y confirma que el broadcast funciona con hash por IP.
  3. Configura el healthcheck del balanceador para retirar instancias caídas.

Resumen

  • Los sockets son conexiones largas: necesitan quedar fijas o escalar con estado compartido.
  • Los balanceadores de capa 7 reenvían el upgrade si se lo dices.
  • El estado en Redis relaja la necesidad de sticky sessions.
