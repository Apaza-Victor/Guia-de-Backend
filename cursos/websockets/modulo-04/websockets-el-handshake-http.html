El handshake HTTP al detalle

🔥 Avanzado 11 min WebSockets y Tiempo Real Módulo 4 · Protocolo WebSocket en profundidad

Introducción

Toda conexión WebSocket empieza siendo una petición HTTP normal. El cliente envía un GET con cabeceras especiales y, si el servidor acepta, la respuesta 101 cambia el protocolo en mitad de la conexión.

Este handshake es la razón por la que WebSocket atraviesa firewalls y frameworks web sin dramas: no es un puerto mágico, es una petición HTTP que se transforma.

Definición

El handshake es el intercambio de una petición HTTP GET con Sec-WebSocket-Key y Sec-WebSocket-Version; si el servidor responde 101 Switching Protocols, la conexión pasa a ser un socket WebSocket.

Por qué importa. Te permite servir REST y WebSocket en el mismo servidor y ruta, y entender por qué algunos proxies bloquean el upgrade.

Cuándo usarlo. Analiza el handshake al configurar un reverse proxy, al recordar la petición original (query, cookies, token) o al depurar rechazos de conexión.

Conceptos clave

  • La petición inicial es un GET HTTP/1.1 con cabeceras de upgrade.
  • Sec-WebSocket-Key es un nonce que el servidor devuelve firmado en Sec-WebSocket-Accept.
  • La respuesta 101 Switching Protocols materializa la conexión.
  • El cliente puede incluir query params, cookies o Authorization en el handshake.
  • La mayoría de implementaciones usan HTTP/1.1 para el handshake.

Ejemplo real

En producción el handshake es la puerta de entrada: sirve para autenticar y sembrar el estado de cada socket.

  • Autentica en el handshake para no abrir sockets anónimos.
  • Valida la URL del handshake para rechazar rutas no permitidas.
  • Guarda el estado inicial (usuario, salas) en el objeto del socket.

Los proxies deben reenvníar Upgrade y Connection; con Nginx hay que añadir esas cabeceras explícitamente.

Explicación

  • El servidor calcula Sec-WebSocket-Accept con SHA-1 sobre la key y un GUID fijo del protocolo.
  • Un código 400 en el handshake suele indicar cabeceras incorrectas o una versión no soportada.
  • La petición original sirve de seed de estado: evitas un segundo round-trip de autenticación.
  • Express no gestiona sockets; hace falta el servidor HTTP con handleUpgrade o un montaje noServer.
  • Comprender el handshake es la llave para integrar WebSocket en servicios ya desplegados.

Errores comunes

  • Rechazar todas las conexiones porque el proxy no reenvía Connection: upgrade.
  • Depender del evento connection sin pasar el objeto req al callback.
  • Olvidar cerrar el socket cuando la validación de la URL lo rechaza.

Buenas prácticas

  • Pasa req a la conexión: te da query, cookies y cabeceras del handshake.
  • Valida el origen en producción para bloquear conexiones cross-site.
  • Inspecciona el handshake con wscat o con una pestaña de red del navegador.
  • Mantén el servidor HTTP para seguir sirviendo REST junto al socket.

Ejercicio

  1. Muestra por consola todos los headers del handshake al conectar un cliente.
  2. Rechaza conexiones cuya URL no empiece por /ws.
  3. Autentica en el handshake y guarda el usuario en el objeto del socket.

Resumen

  • WebSocket nace como una petición HTTP GET y se materializa con el 101.
  • El handshake transporta key, versión, subprotocolos y extensiones.
  • Usa la petición original para autenticar y sembrar el estado del socket.
