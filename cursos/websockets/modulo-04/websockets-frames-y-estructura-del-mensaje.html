Frames y estructura del mensaje

🔥 Avanzado 12 min WebSockets y Tiempo Real Módulo 4 · Protocolo WebSocket en profundidad

Introducción

Cuando un cliente gana el socket, ya no hay cabeceras ni métodos: lo que viaja por el cable son frames. Cada frame tiene un encabezado mínimo de bits que indica si es el último fragmento, la operación (texto, binario, ping, pong, close) y la longitud del payload.

Comprender el frame te ayuda a leer los mensajes como hace la librería ws, depurar tráfico con wscat y elegir entre texto y binario para cada tipo de dato del backend.

Definición

Un frame WebSocket es la unidad de datos del protocolo: combina bits de control (FIN, opcode, MASK) con una longitud y un payload, entregado como texto UTF-8 o como datos binarios.

Por qué importa. El frame define eficiencia y límites: modelar mensajes cortos y estructurados reduce la latencia, y conocer el masking previene abusos del protocolo a través de proxies maliciosos.

Cuándo usarlo. Usa texto para JSON legible y binario para imágenes o buffers; estudia los frames cuando depures el tráfico o quieras optimizar el tamaño de cada mensaje.

Conceptos clave

  • FIN indica si el frame es el último de un mensaje continuado.
  • El opcode clasifica el frame: 0x1 texto, 0x2 binario, 0x8 cierre, 0x9 ping y 0xA pong.
  • Todo payload de cliente a servidor viaja enmascarado (MASK activo) para evitar abusos de proxies.
  • La longitud puede ocupar 7 bits, 16 bits o 64 bits según el tamaño del mensaje.
  • Un mensaje puede dividirse en varios frames de datos con FIN en el último.

Ejemplo real

En un backend real conviene un contrato de mensajes: la envoltura determina qué hacer con cada frame y cuánto medir.

  • Define una envoltura JSON con type y payload para todos los mensajes.
  • Mide el tamaño real de cada frame: pocos KB son normales, pocos MB son un problema.
  • Usa binario solo cuando el texto no sea legible o necesites buffers nativos.

ws ya gestiona el enmascarado y el ensamblado de frames; tú decides el contenido y su formato.

Explicación

  • El encabezado mínimo de un frame son dos bytes, lo que hace el protocolo muy ligero frente a repetir cabeceras HTTP en cada mensaje.
  • El opcode 0x0 (continuación) une fragmentos cuando un mensaje grande se trocea en varios frames.
  • El servidor rechaza frames del cliente que no lleven máscara, por diseño del protocolo.
  • El servidor no enmascara sus propios frames, solo lo hace el cliente.
  • Conocer los límites de tamaño te permite bloquear mensajes gigantes antes de que lleguen a tu lógica.

Errores comunes

  • Enviar un frame binario cuando el cliente espera texto rompe la compatibilidad del contrato.
  • Olvidar cerrar sockets tras errores satura el pool de conexiones.
  • No limitar el tamaño del mensaje agota la memoria del servidor.

Buenas prácticas

  • Crea una capa de serialización (encode y decode) al inicio; no repitas JSON.stringify a mano.
  • Añade un tamaño máximo de mensaje en ws con la opción maxPayload.
  • Registra el tamaño y el tipo de cada frame para auditar el tráfico.
  • Mantén los mensajes pequeños y frecuentes para no bloquear otras conexiones.

Ejercicio

  1. Envía un mensaje binario de tipo JSON e imprime su tamaño en bytes.
  2. Divide un mensaje largo en dos partes y comprueba cómo lo recibe el cliente.
  3. Rechaza mensajes de más de 1 KB en tu servidor.

Resumen

  • Un frame es la unidad mínima de datos del protocolo WebSocket.
  • El opcode distingue texto, binario, ping, pong y cierre.
  • Texto para JSON, binario para buffers: elige según tu contrato.
