Documentación con OpenAPI y Swagger

⚙️ Intermedio 11 min Node.js desde cero hasta avanzado Módulo 6 · APIs REST en Node

Introducción

Una API sin documentación es una caja negra: cada cliente adivina contratos y el soporte paga el precio. OpenAPI es el estándar para describir la API en un documento legible por máquinas y humanos.

Con OpenAPI defines endpoints, parámetros y respuestas en un JSON/YAML, y Swagger UI lo convierte en una página interactiva para probar cada llamada.

Definición

OpenAPI (antes Swagger) es un estándar JSON/YAML que describe una API: rutas, métodos, parámetros, cuerpos y respuestas. Swagger UI renderiza esa spec y permite ejecutar peticiones desde el navegador.

Por qué importa. La documentación viva se mantiene con el código, sirve para generar clientes y pruebas, y convierte el "cómo llamo a esto" en algo resuelto.

Cuándo usarlo. Documenta desde el primer endpoint. Herramientas como swagger-ui-express exponen la spec en tu propio servidor.

Conceptos clave

  • Un documento OpenAPI con paths, parameters y responses.
  • Swagger UI muestra la spec interactiva en /api-docs.
  • Los esquemas de cuerpo se reutilizan entre petición y respuesta.
  • Los códigos de respuesta se documentan por endpoint.
  • La spec se puede generar con herramientas (swagger-autogen, tsoa).

Ejemplo intermedio

Ejemplo real

La spec se coloca en un archivo versionado y se sirve en un middleware, de modo que la documentación viaja con el despliegue.

  • Mantén la spec en el repo y ciñela a la implementación.
  • Genera clientes tipados desde la spec (openapi-generator).
  • Protege /api-docs en producción si no quieres exponer el contrato.

Existen generadores automáticos (swagger-autogen, @tsoa/cli, tsoa) que derivan la spec de tu código, reduciendo la duplicación.

Explicación

  • OpenAPI describe rutas, parámetros, cuerpos y respuestas en un doc.
  • Swagger UI sirve la spec como página interactiva.
  • Los $ref reutilizan esquemas sin repetirlos.
  • La spec alimenta la generación de clientes y mocks.
  • Mantener spec y código sincronizados es un contrato de equipo.

Errores comunes

  • Documentar y no mantener: la spec miente y confunde.
  • Olvidar los códigos de error en un endpoint.
  • Servir la spec solo desde memoria sin versionarla.

Buenas prácticas

  • Empieza documentando el CRUD con sus 4 verbos.
  • Usa generación automática si el proyecto es grande.
  • Revisa /api-docs en cada deploy de desarrollo.

Ejercicio

  1. Añade Swagger UI con una spec mínima a tu Express.
  2. Documenta el endpoint POST /pedidos con cuerpo y 422.
  3. Mueve la spec a un archivo openapi.yaml y cárgala.

Resumen

  • OpenAPI describe tu API en un estándar legible por máquinas.
  • Swagger UI la convierte en una página interactiva.
  • La spec versionada alimenta clientes, mocks y pruebas.
