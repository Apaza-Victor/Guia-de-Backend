Worker Threads

⚙️ Intermedio 12 min Node.js desde cero hasta avanzado Módulo 3 · Asincronía avanzada

¿Por qué hace falta un hilo extra?

El event loop de Node es excelente esperando operaciones de entrada/salida, pero mediocre ejecutando pura matemática. Un bucle de un millón de iteraciones ocupa la CPU sin darle respiro al hilo único: mientras "cansas" el procesador, ninguna petición HTTP avanza.

Para cómputo teórico sí podemos paralelizar porque Node tiene algo mejor que callbacks: el módulo node:worker_threads. Crea hilos reales del sistema operativo que corren JavaScript propio, cada uno con su event loop, su V8 y su memoria. Hasta ahora nuestra asincronía era por concurrencia; con workers conseguimos paralelismo.

Tu primer worker

Un worker se construye pasándole la ruta del archivo que debe ejecutar y, opcionalmente, datos de entrada a través de workerData. Dentro del trabajador, parentPort es el canal de vuelta hacia el hilo principal.

La magia: el hilo principal no se congela. Puedes seguir atendiendo peticiones mientras los workers parten los datos en paralelo.

Divide y vencerás: un pool sencillo

Un solo worker no basta para aprovechar una máquina con 8 núcleos. La técnica estándar es repartir el trabajo en os.cpus().length workers, cada uno con su tramo.

Transferencia eficiente: SharedArrayBuffer

Por defecto, postMessage copia los datos (estructura clonable). Para volúmenes grandes, la copia se paga en tiempo y memoria. La alternativa es SharedArrayBuffer: una zona de memoria que el hilo principal y los workers comparten de verdad, sin copia ni serialización.

Atención: la memoria compartida trae una nueva categoría de bugs, las carreras (dos hilos escribiendo a la vez). En JavaScript se evitan con Atomics: operaciones atómicas de lectura-escritura-suma que el hardware garantiza sin interleaving.

No te asustes: la mayoría de proyectos backend nunca tocan Atomics. Pero saber que existen te prepara si algún día procesas logs, imágenes o cálculos financieros masivos.

¿Cuándo usar worker threads?

  • Sí: análisis de datos, redimensionado de imágenes, compresión, hashing/lighthouse, procesos de ETL.
  • No: operaciones de red y archivos ligeros (el event loop ya las maneja bien), o tareas de milisegundos (el coste del worker las vuelve más lentas).

Ejercicio

  1. Crea el ejemplo de primos con un solo worker y cronometra con console.time.
  2. Repítelo con un pool de os.cpus().length workers y compara los tiempos.
  3. Responde: ¿por qué llegar a 50 millones se vuelve inmanejable con un solo hilo?
  4. Modifica el código de SharedArrayBuffer para que el worker sume cada resultado con Atomics.
  5. Enumera dos proyectos backend donde usarías worker threads y dos donde no.

Resumen

  • worker_threads crea hilos reales del SO con su propio V8 y event loop.
  • workerData lleva datos al worker y parentPort los trae de vuelta.
  • Un pool con os.cpus().length workers reparte la CPU en paralelo.
  • postMessage copia por defecto; SharedArrayBuffer comparte sin copiar.
  • Cuando hay memoria compartida, usa Atomics para operaciones seguras.
  • Workers son para CPU intensiva, no para I/O ligera.
