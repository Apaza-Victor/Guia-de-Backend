Manejo centralizado de errores

⚙️ Intermedio 11 min Node.js desde cero hasta avanzado Módulo 4 · Express avanzado

Introducción

Cuando cada ruta maneja sus errores a su manera, la API contesta formatos dispares y los fallos internos se filtran al cliente. El manejo centralizado pone a todos los errores en una sola puerta de salida.

Express distingue los middlewares de error por su firma de cuatro parámetros: reciben el fallo de cualquier ruta anterior y deciden la respuesta.

Definición

Un middleware de error tiene la firma (err, req, res, next), se registra al final del pipeline y recibe cualquier error que next(err) o una excepción lanzada provoquen en las rutas anteriores.

Por qué importa. Respuestas de error uniformes, logs sin secretos y la lógica de errores en un único lugar hacen el backend debugeable y seguro.

Cuándo usarlo. Úsalo en toda API de tamaño medio. Combínalo con una clase propia de errores para enviar códigos HTTP precisos.

Conceptos clave

  • La firma (err, req, res, next) identifica al manejador de error.
  • next(err) salta a la primera capa de error desde cualquier punto.
  • Una clase ErrorHttp con statusCode transporta el código HTTP.
  • Los errores desconocidos se mapean a 500 y se registran sin filtrar.
  • El manejador va el ÚLTIMO, tras las rutas y middlewares.

Ejemplo intermedio

Ejemplo real

El manejo centralizado convierte fallos de rutas, validaciones, base de datos y JSON mal formado en respuestas coherentes de un solo formato.

  • Usa codes HTTP precisos: 400, 401, 403, 404, 409, 422, 500.
  • Loggea el stack en el servidor pero nunca lo envíes al cliente.
  • Lanza ErrorHttp en servicios, no solo en las rutas.

Con async/await en las rutas, envuelve el try/catch para reenviar a next(err). Un helper wrapAsync te ahorra repetirlo (lo verás en la siguiente lección).

Explicación

  • Express solo ejecuta un middleware de error cuando detecta los 4 parámetros.
  • next(err) detiene el pipeline normal y salta a los manejadores de error.
  • Una excepción no capturada en un async handler se pierde: captúrala.
  • Mapear desconocidos a 500 mantiene la API consistente.
  • Los logs internos quedan para operaciones, no para el cliente.

Errores comunes

  • Registrar el manejador de error antes de las rutas (no se ejecutará).
  • Filtrar el stack de errores al JSON de respuesta.
  • Olvidar capturar async: el error se pierde y la petición se cuelga.

Buenas prácticas

  • Crea ErrorHttp como única vía de errores con código.
  • Mantén los mensajes en español, sin detalles internos.
  • Registra siempre: el log es tu faro al debugear producción.

Ejercicio

  1. Crea ErrorHttp y haz que una ruta devuelva 404 al faltar el recurso.
  2. Registra el manejador de error al final y verifica un 500 genérico.
  3. Envía un error 422 cuando la validación falle.

Resumen

  • El manejador central de errores vive al final del pipeline.
  • ErrorHttp transporta el código HTTP hasta la respuesta.
  • Los fallos internos se loguean y nunca se exponen al cliente.
