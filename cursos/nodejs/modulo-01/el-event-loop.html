El Event Loop de Node.js

⚙️ Intermedio 12 min Node.js desde cero hasta avanzado Módulo 1 · Introducción a Node.js

Un solo hilo que nunca se bloquea

Node.js procesa tu JavaScript en un único hilo. Eso significa que el código que escribes se ejecuta de forma secuencial, pero las operaciones lentas (archivos, red, bases de datos) se delegan a libuv. Cuando terminan, sus resultados vuelven en forma de eventos y el event loop decide cuándo ejecutarlos.

Imagina un camarero (el hilo único) que toma pedidos. En lugar de quedarse parado junto al fogón mientras la comida se cocina, toma otro pedido. Cuando la cocina (libuv) avisa, el camarero lleva el plato a la mesa. Eso es el event loop.

Las fases del event loop

El event loop es un bucle que recorre varias fases en cada iteración:

  1. Timers: ejecuta los callbacks de setTimeout y setInterval con el tiempo vencido.
  2. Pending: algunos callbacks del sistema (como errores de TCP).
  3. Idle / Prepare: trabajos internos de Node.
  4. Poll: la fase principal: recoge nuevos eventos de I/O y ejecuta sus callbacks; aquí espera cuando no hay nada que hacer.
  5. Check: ejecuta los callbacks de setImmediate.
  6. Close: callbacks de cierre (por ejemplo socket.on("close")).

Además, entre o después de cada fase se procesan las microtareas: las promesas (y queueMicrotask) tienen prioridad sobre el resto.

El orden real en la práctica

Para no memorizar fases, queda con la regla práctica de prioridades:

  1. Código síncrono actual.
  2. Microtareas (promesas, queueMicrotask).
  3. Timers y I/O (fases del loop).

Ejecútalo varias veces: el orden de setTimeout y setImmediate puede variar según la carga, pero el 1, 2, 3, 3.1 y 4 siempre saldrán antes que el 5 y el 6.

Un bloqueo puede detenerlo todo

Si dentro de un callback ejecutas una operación síncrona pesada, el hilo único se queda ocupado y ninguna otra petición avanza. El event loop sigue vivo, pero se atasca.

La CPU no puede ejecutar, por ejemplo, un while infinito. Una operación de cálculo puro muy pesada (como cifrar miles de datos) también bloquea. Para esos casos existen worker_threads (lo veremos en el módulo 3) o caminos alternativos.

Ejercicio

  1. Copia el script de prioridades y ejecútalo. Anota el orden exacto de la consola.
  2. Modifica el ejemplo añadiendo un Promise.resolve() dentro de un then y observa dónde aparece.
  3. Explica con tus palabras qué pasaría si un servidor usara readFileSync en cada petición.
  4. Sustituye la variable suma del capítulo de V8 por operaciones dentro del hilo y piensa cómo la repartirías entre Microtasks.

Resumen

  • Node usa un hilo único para tu JavaScript; libuv gestiona las operaciones lentas.
  • El event loop recorre fases: timers, poll, check y close.
  • Las microtareas (promesas) corren antes que los timers y la I/O.
  • Una operación síncrona pesada bloquea el loop y a todos los clientes.
  • Siempre prefieres las versiones asíncronas de fs y de red en servidores.
