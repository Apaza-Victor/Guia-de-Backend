Consultas parametrizadas y seguras

⚙️ Intermedio 12 min Node.js desde cero hasta avanzado Módulo 5 · Bases de datos con Node

Introducción

El atajo de pegar el valor del usuario dentro del SQL es la puerta que han usado décadas de ataques por inyección. Node no escapa de ese peligro: la defensa está en usar parámetros.

pg soporta parámetros posicionales ($1, $2, ...) que el servidor de PostgreSQL une de forma segura, transportando los datos y no el código.

Definición

Una consulta parametrizada separa el texto SQL de sus valores: los marcadores $1, $2 se sustituyen en el servidor (PostgreSQL los trata como datos), eliminando la inyección por construcción.

Por qué importa. Con parámetros, un valor malicioso como '; DROP TABLE usuarios; -- no puede alterar la estructura del comando: es solo un dato.

Cuándo usarlo. Usa parámetros en TOTA consulta que contenga datos del exterior: body, query params, path params o cualquier valor dinámico.

Conceptos clave

  • query(text, valores) separa SQL de parámetros.
  • $1, $2 son marcadores posicionales de PostgreSQL.
  • pasar un array como parámetro sirve así para IN (…) en muchas versiones.
  • Las tablas y columnas NO van como parámetro: se validan con lista blanca.
  • Los parámetros preservan el tipo (number, string, boolean, null).

Ejemplo básico

Buscamos un usuario por id y email usando parámetros posicionales.

1 [ { id: 3, email: 'ana@mail.com' } ]

Ejemplo intermedio

Los inserts parametrizados y el RETURNING nos devuelven la fila creada.

Ejemplo real

Casos reales: búsquedas con filtros dinámicos y la lista blanca para columnas.

  • Construye el WHERE por partes añadiendo condiciones con parámetros.
  • Valida y mapea las columnas ordenables a una lista fija.
  • Usa ORDER BY con identificadores ya conocidos, nunca con entrada cruda.

Los límites y el orden se interpolan SOLO tras sanitizarlos (parseo a número y lista blanca). Los valores viajan por parámetros.

Explicación

  • PostgreSQL prepara el plan con marcadores y sustituye valores después.
  • Un parámetro nunca se interpreta como código SQL.
  • El motor conserva los tipos: comparaciones felices y sin '1' == 1.
  • La lista blanca para columnas cierra el único hueco restante.
  • Los counts y límites se parsean a número antes de interpolar.

Errores comunes

  • Pegar el valor con template literals directamente en SQL.
  • Poner nombre de tabla o columna como parámetro ($1 no vale ahí).
  • Olvidar comprobar resultado.rowCount para saber si encontró algo.

Buenas prácticas

  • Sanea filtros con una lista blanca por cada columna permitida.
  • Revisa los logs: una excepción de tipos delata un parámetro mal tipado.
  • Haz counts con RETURNING o rowCount en vez de suponer.

Ejercicio

  1. Reescribe una consulta interpolada en una parametrizada.
  2. Construye un filtro dinámico por email y activo con params.
  3. Añade una lista blanca de columnas ordenables en tu endpoint.

Resumen

  • $1, $2 transportan datos seguros al servidor y eliminan la inyección.
  • Las columnas se mapean con listas blancas, no con parámetros.
  • Los límites y conteos se parsean antes de interpolar.
