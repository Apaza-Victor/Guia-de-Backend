Modelando datos con Prisma

⚙️ Intermedio 12 min Node.js desde cero hasta avanzado Módulo 5 · Bases de datos con Node

Introducción

Escribir SQL a mano para cada consulta funciona, pero cuando el dominio crece surge el ORM: una capa que modela las tablas como objetos y las consultas como métodos con IntelliSense.

Prisma destaca por su esquema declarativo (model), migraciones generadas y un cliente con tipos que convierten errores de columna en fallos de compilación.

Definición

Prisma define el esquema en schema.prisma (conectores, datasource y models), genera migraciones SQL y un Cliente (PrismaClient) con métodos tipados como prisma.usuario.findUnique().

Por qué importa. El esquema vive como código revisable, las relaciones se declaran (no se unen a mano) y el cliente generado evita errores de campo y tipa las respuestas.

Cuándo usarlo. Usa Prisma en proyectos relacionales con PostgreSQL/MySQL/SQLite cuando la velocidad de desarrollo y el tipado importen más que el control manual del SQL.

Conceptos clave

  • prisma/schema.prisma declara datasource, generador y models.
  • Cada model mapea a una tabla y cada campo a una columna.
  • @id, @unique y @default definen claves y valores por defecto.
  • Las relaciones (usuario.pedidos) se declaran y se consultan con include.
  • npx prisma migrate dev genera y aplica migraciones tipadas.

Ejemplo real

En una API, el repositorio se vuelve casi decorativo: el cliente de Prisma ya desespacia SQL y datos, y las transacciones se manejan con $transaction.

  • Usa select para devolver solo lo que el cliente necesita.
  • Las transacciones con $transaction mantienen la atomicidad.
  • Cierra el cliente al apagar la app (prisma.$disconnect).

Prisma genera el cliente cada vez que cambias el esquema (prisma generate). Los tipos de tus consultas reflejan el modelo exacto.

Explicación

  • El esquema declarativo es una sola fuente de verdad para tablas y relaciones.
  • Las migraciones de Prisma se revisan y aplican como cualquier cambio.
  • El cliente tipado convierte errores de campo en fallos en desarrollo.
  • Las relaciones evitan los JOIN escritos a mano y tipan las filas.
  • $transaction conserva la atomicidad multi-tabla.

Errores comunes

  • Editar la base a mano y no tocar el schema: desincronización total.
  • Olvidar prisma generate tras el schema (client desactualizado).
  • Seleccionar todo un model y exponer el hash de contraseña.

Buenas prácticas

  • Mantén el hash fuera de las respuestas: usa select explícito.
  • Aplica prisma migrate dev al cambiar el esquema.
  • Define relaciones con onDelete para controlar los borrados.

Ejercicio

  1. Modela usuario y pedido con una relación one-to-many y migra.
  2. Consulta con include las relaciones y con select los campos mínimos.
  3. Escribe una transacción $transaction que cree pedido y líneas.

Resumen

  • Prisma declara el esquema y genera un cliente tipado.
  • Las relaciones se declaran y se consultan sin JOIN a mano.
  • $transaction mantiene la atomicidad en operaciones múltiples.
