Errores y reintentos

⚙️ Intermedio 12 min Integraciones y Servicios Externos Módulo 3 · Robustez

Introducción

Las APIs externas fallan. No es un accidente: es la definición de un servicio de terceros. La diferencia entre una integración amateur y una profesional es cómo tratas ese fallo. Un reintento sin pensarlo es casi tan malo como no reintentar nunca: si 100 clientes reintentan a la vez tras una caída del proveedor, la propia recuperación se vuelve imposible. Reintentar bien significa clasificar el error, esperar el tiempo justo, dispersar la avalancha (jitter) y saber cuándo rendirse.

Clasificar el error primero

No todas las respuestas merecen reintento. La regla más importante del manejo de errores:

  • Reintenta: 408 (timeout), 429 (rate limit, espera respetando Retry-After), 5xx (fallo del proveedor) y errores de red/timeout.
  • No reintentes: 400, 401, 403, 404, 422: el error no desaparecerá por insistir, y en caso de 429 permanente solo empeorarás tu posición.

Reaparecer ante el mismo 422 10 veces es quemar cuota (y dinero) en un error que tu código debe corregir, no tu bucle de reintentos.

Backoff exponencial

El patrón estándar: espera que crece exponencialmente entre intentos, con un tope máximo. Después del primer fallo esperas 1 s, luego 2, 4, 8, ... hasta un máximo (30–60 s). Eso da al proveedor tiempo de recuperarse sin bombardearlo:

export async function peticionConReintentos(fn, { intentos = 5, base = 1000, max = 30000 } = {}) {
  let ultimoError;
  for (let i = 1; i <= intentos; i++) {
    try {
      return await fn();
    } catch (err) {
      ultimoError = err;
      if (!esReintentable(err)) throw err;     // 4xx definitivo: no insistas
      const espera = Math.min(base * 2 ** (i - 1), max);
      await sleep(espera + jitter(espera));
    }
  }
  throw ultimoError;
}

Jitter: dispersa la avalancha

Si todos los clientes reintentan con la misma secuencia 1s, 2s, 4s..., vuelven a sincronizarse al mismo segundo y generan picos simultáneos. El jitter añade aleatoriedad a cada espera. La variante más robusta es full jitter: en lugar de sumar tiempo al azar, eliges un valor aleatorio entre 0 y la espera calculada:

import random, time

def espera_backoff(intento: int, base: float = 1.0, tope: float = 30.0) -> float:
    exponencial = base * (2 ** intento)
    # full jitter: entre 0 y el valor exponencial, nunca pasando el tope
    return random.uniform(0, min(exponencial, tope))

for intento in range(5):
    try:
        cliente.peticion()
        break
    except ErrorReintentable:
        time.sleep(espera_backoff(intento))

Presupuesto de reintentos y circuito

Reintentar indefinidamente no solo daña tu cuota: si tu servicio síncrono espera 30 reintentos encadenados, el usuario aguanta minutos por una API caída. Define un presupuesto total (por ejemplo, 3 intentos o 20 s) y, si el flujo es crítico, encola el trabajo para reintentar en background. Cuando el proveedor falla demasiado seguido, un circuit breaker corta en seco los intentos y va probando de a poco (medio abierto) hasta recuperarse:

{
  "circuito": {
    "estado": "cerrado",
    "umbral_fallos_consecutivos": 5,
    "ventana_apertura_s": 30,
    "prueba_medio_abierta": { "max_peticiones": 2 }
  },
  "reintentos": {
    "max_intentos": 3,
    "base_ms": 500,
    "jitter": "full",
    "presupuesto_total_ms": 20000
  }
}

Idempotencia en el cliente y el servidor

Un reintento puede provocar la ejecución doble de la operación: imagina que el pago se procesó, pero la respuesta se perdió en la red y tu cliente reintenta. La solución es la clave de idempotencia: el mismo identificador en todos los intentos de la misma operación, para que el servicio externo devuelva el resultado original en lugar de ejecutar otra vez:

# Todas las repeticiones de la misma operación usan la misma clave
curl -X POST https://api.proveedor.com/v1/cobros \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: pedido-12345-intento-1" \
  -d '{"amount":4900,"currency":"mxn"}'

Del lado del proveedor, registrarlo por clave; del tuyo como consumidor, usar una clave nueva por cada operación de negocio distinta y reutilizarla en sus reintentos. Así el mundo sigue siendo consistente aunque se pierda una respuesta.

Ejercicio

  1. Escribe una función peticionConReintentos con full jitter y que no reintente los 4xx.
  2. Simula un proveedor que falla con 503 los primeros 3 intentos y verifica el presupuesto total.
  3. Añade una clave de idempotencia a una operación de cobro de prueba y comprueba que el doble envío no duplica el cobro.

Resumen

  • Reintenta 408/429/5xx; nunca 4xx definitivos.
  • Backoff exponencial con tope máximo y full jitter evita avalanchas sincronizadas.
  • Define un presupuesto de reintentos y usa circuit breaker para fallos continuos.
  • La clave de idempotencia evita el doble efecto de un reintento.
