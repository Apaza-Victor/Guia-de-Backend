Pruebas de integración

⚙️ Intermedio 11 min Integraciones y Servicios Externos Módulo 3 · Robustez

Introducción

Probar una integración tiene una dificultad que no tienen los tests normales: el proveedor no es tuyo. No puedes elegir cuándo responde, ni forzar un 500 a propósito, ni reproducir un timeout exacto en producción. La estrategia se arma en tres niveles: mocks para tu CI (rápidos y deterministas), contratos para detectar cambios del proveedor y sandbox para verificar el flujo completo de verdad antes de ir a producción.

Mocks: tu CI no depende del proveedor

En la suite de tests la API externa se sustituye por un mock controlado. Así pruebas tu lógica —parseo, errores, reintentos— sin red y sin cuota:

import pytest
from unittest.mock import patch

@patch("integraciones.geocode.httpx.get")
def test_geocodificacion_ok(mock_get):
    mock_get.return_value = RespuestaFalsa(
        status_code=200,
        json_data={"status": "OK", "results": [{
            "geometry": {"location": {"lat": 19.4, "lng": -99.1}}
        }]},
    )
    coordinadas = geocodificar("Av. Siempre Viva 742")
    assert coordinadas["lat"] == 19.4

Un test con mock es la única forma de probar el caso «el proveedor devuelve un 503» sin esperar a que eso ocurra en la vida real.

Pruebas de contrato

Una prueba de contrato verifica que la respuesta real del proveedor sigue teniendo la forma que tu código espera. Se ejecuta contra el sandbox de forma periódica (cron o CI programado) y no corresponde al release normal:

// test/contrato.proveedor.spec.js — contra el sandbox del proveedor
test('el estado del pedido sigue devolviendo status y trackingUrl', async () => {
  const resp = await clienteProveedor.obtener('pedido-123');
  expect(resp).toMatchObject({
    status: expect.any(String),
    trackingUrl: expect.any(String)
  });
});

Cuando el proveedor cambia el JSON sin avisar, esta prueba te avisa antes de que el cambio llegue a tus usuarios.

El sandbox del proveedor

Para el flujo completo y real (registrar un pago de prueba, verificar un webhook firmado) existe el sandbox: el entorno de pruebas del proveedor con tarjetas y datos falsos, misma API y casi mismo comportamiento. Antes de tocar producción, la integración debe pasar por sandbox con casos felices y casos de error. La clave de sandbox y la de producción son distintas — tenerlo claro desde el día uno evita cobrar a un cliente real con una prueba mal hecha.

Testcontainers: infraestructura en el test

Las integraciones viven rodeadas de infraestructura propia: Redis para la cola, PostgreSQL para deduplicación, el servidor de correo de prueba. Testcontainers levanta esos servicios en contenedores efímeros dentro de la suite y los apaga al terminar:

with PostgresContainer("postgres:16") as db:
    conexion = db.get_connection_url()
    # apuntar la app de pruebas a este postgres y correr las assertions

El resultado: pruebas de integración de verdad (con Redis real, con Postgres real) que no dependen de lo que haya instalado en tu máquina. Un solo comando de test reproduce el entorno completo en cualquier developer.

{
  "entorno_test": {
    "contenedores": {
      "postgres": "postgres:16",
      "redis": "redis:7-alpine",
      "maildev": "maildev/maildev:latest"
    },
    "mocks": ["proveedor-pagos", "proveedor-geocoder"],
    "sandbox": { "proveedor-cobros": true }
  }
}

Qué probar de cada integración

  • Respuesta feliz y cada código de error que tu código maneja (400, 401, 429, 503).
  • El comportamiento de timeout: que se corte y no cuelgue el request.
  • Que los reintentos respeten backoff y no disparen el efecto dos veces.
  • Que una firma inválida en el webhook sea rechazada.
  • Que el mapper traduzca campos renombrados o ausentes.

Regla práctica: si una integración no se puede testear sin red, no está lista; si no se puede testear con errores provocados, no está probada.

Ejercicio

  1. Escribe un test con mock para el caso «el proveedor devuelve 503 y el retry respeta el backoff».
  2. Crea una prueba de contrato contra el sandbox de una API pública de tu interés.
  3. Levanta un servicio con Testcontainers en tu proyecto y escribe un test de integración real contra él.

Resumen

  • Mocks: tu CI funciona sin red ni cuota del proveedor.
  • Contratos: detectan cambios silenciosos del JSON del proveedor.
  • Sandbox: verifica el flujo completo real antes de producción.
  • Testcontainers reproducen la infraestructura de la integración en cada test.
  • Cada código de error que manejas debe tener su test.
