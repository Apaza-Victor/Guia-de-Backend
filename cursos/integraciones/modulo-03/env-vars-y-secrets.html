Configuración y secretos

⚙️ Intermedio 10 min Integraciones y Servicios Externos Módulo 3 · Robustez

Introducción

Tu código de integración no funciona sin configuración: URLs de proveedores, claves de API, secretos de firma, credenciales y endpoints de sandbox vs producción. La regla número uno del factor 12 es que la configuración vive en el entorno, no en el código. El mismo artefacto debe desplegarse en dev, staging y producción simplemente cambiando las variables de entorno.

Variables de entorno: lo no secreto

Todo lo que no es confidencial pero cambia entre entornos se declara como variable: API_URL, LOG_LEVEL, ENTORNO. En desarrollo se cargan desde un .env local; en producción las inyecta la plataforma o el secret manager:

# .env — solo para desarrollo; jamás se sube al repositorio
ENTORNO=development
API_PROVEEDOR_URL=https://api.sandbox.proveedor.com
API_PROVEEDOR_KEY=clave-sandbox-de-prueba
CACHE_TTL_SEGUNDOS=300
export function configuracion() {
  return {
    env: process.env.ENTORNO ?? 'development',
    apiProveedor: {
      url: process.env.API_PROVEEDOR_URL,
      clave: process.env.API_PROVEEDOR_KEY
    },
    cacheTtl: Number(process.env.CACHE_TTL_SEGUNDOS ?? 300)
  };
}

Ese .env se declara en .gitignore y en su lugar se sube un .env.example con las mismas llaves y valores vacíos o de ejemplo.

Secretos: lo que nunca va al código

Las claves reales de los proveedores —secret de Stripe, private key de firma, credenciales de bucket— son secretos. No son configuración normal: van cifrados en un secret manager (AWS Secrets Manager, Vault, GCP Secret Manager) y el runtime los recupera al arrancar:

import boto3
from botocore.exceptions import ClientError

sm = boto3.client("secretsmanager", region_name="us-east-1")

def obtener_secreto(nombre: str) -> str:
    resp = sm.get_secret_value(SecretId=nombre)
    return resp["SecretString"]

El valor nunca se imprime en logs, nunca viaja en un console.log y nunca se escribe en un archivo de configuración versionado. Solo la plataforma sabe dónde está.

Rotación y separación de roles

Un secreto filtrado es un incidente; un secreto sin rotación es tiempo bomba. Buenas prácticas:

  • Claves separadas por entorno: la clave de sandbox vale para probar, la de producción para cobrar. Compartir la de producción para tests es un desastre.
  • Scopes mínimos: un token de solo lectura nunca debe poder enviar correos ni borrar.
  • Rotación programada: los secret managers permiten rotar automáticamente; si es manual, agenda un recordatorio y ensaya el procedimiento.
  • Revocación inmediata: ante cualquier sospecha, regenera la clave ya y busca su presencia en git y logs.
{
  "secreto": "proveedor/firma_webhook",
  "entorno": "produccion",
  "ultima_rotacion": "2026-08-15",
  "proxima_rotacion": "2026-11-15",
  "rotacion_automatica": true,
  "generacion": 4
}

Cómo se fuga un secreto

  • Commit accidental: el .env se sube al repo. Se previene con .gitignore + escaneo en CI.
  • Logs con datos de request: imprimir la respuesta completa de un proveedor suele incluir tokens.
  • Frontend: claves inyectadas en HTML o JS que cualquiera puede leer.
  • Backup y dashboards: variables exportadas a herramientas de terceros sin cifrar.

Regla práctica: «no lo quiero ver» no basta. Activa un scanner de secretos en CI (como Gitleaks o detect-secrets) y considera cualquier aparición en git como un hallazgo a rotar.

Checklist al integrar un proveedor nuevo

Cuando añades una integración, la configuración debería listar: la URL del sandbox y de producción, la clave/firma (secreta), el .env.example actualizado, el nombre del secreto en el manager y las alertas que no debería disparar. Sin eso, el próximo «precaución, esto no va» se convierte en un secreto fugado.

Ejercicio

  1. Crea un .env.example y un .gitignore correctos para una integración de pago y otra de correo.
  2. Implementa la lectura de variables y la obtención de un secreto desde el manager en tu lenguaje.
  3. Escribe el procedimiento de rotación para una clave: qué se regenera, qué se actualiza y cómo se prueba sin cortar servicio.

Resumen

  • La configuración no secreta vive en variables de entorno, no en el código.
  • Los secretos van en un secret manager cifrado y rotable.
  • Claves separadas por entorno, scopes mínimos y rotación programada.
  • Los `.env` se ignoran del repo; los secretos jamás se loguean ni se sirven al frontend.
