Monitoreo de integraciones

⚙️ Intermedio 10 min Integraciones y Servicios Externos Módulo 3 · Robustez

Introducción

Tu integración puede funcionar en desarrollo y romperse en producción sin que tu código cambie: el proveedor degradó su API, tu clave alcanzó la cuota, un webhook dejó de llegar. Sin observabilidad no puedes saber si el problema está en tu código, en el proveedor o en la red. Monitorear integraciones es registrar cómo se comporta cada proveedor desde tu punto de vista: logs con contexto, métricas de latencia y error, y presupuestos de disponibilidad por servicio.

Logs estructurados por integración

Cada llamada a un proveedor debe poder reconstruirse a posteriori. Un log estructurado (JSON) con el proveedor, el endpoint, el status y la duración responde en segundos «¿qué pasó con Stripe a las 14:03?»:

{
  "timestamp": "2026-09-22T14:03:12.100Z",
  "nivel": "error",
  "evento": "integracion.llamada_fallida",
  "proveedor": "stripe",
  "servicio": "pagos",
  "endpoint": "POST /v1/checkout/sessions",
  "http_status": 503,
  "duration_ms": 842,
  "reintento": 2,
  "trace_id": "abc123f"
}

En producción jamás loguees el cuerpo completo de una respuesta si puede contener tokens o datos sensibles: registra status, duración e id, no secretos.

Métricas: lo que se mide, se arregla

Las métricas dicen « qué tan bien está el conjunto». Para una integración las imprescindibles son: latencia (p50/p95/p99), tasa de error y consumo de cuota. Se etiquetan con proveedor, servicio y endpoint para poder agrupar:

import time
from prometheus_client import Histogram, Counter, Gauge

LATENCIA = Histogram("integracion_latencia_ms", "Latencia de llamadas a proveedores",
                     labelnames=["proveedor", "endpoint"], buckets=[50, 200, 1000, 5000])
ERRORES = Counter("integracion_errores", "Errores de integración",
                  labelnames=["proveedor", "endpoint", "codigo"])
CUOTA = Gauge("integracion_cuota_restante", "Cuota restante del proveedor",
              labelnames=["proveedor"])

def llamada_tiempo(proveedor, endpoint):
    def deco(fn):
        def wrapper(*args, **kwargs):
            inicio = time.time()
            try:
                return fn(*args, **kwargs)
            except Exception as err:
                ERRORES.labels(proveedor, endpoint, getattr(err, "status", "net")).inc()
                raise
            finally:
                LATENCIA.labels(proveedor, endpoint).observe((time.time() - inicio) * 1000)
        return wrapper
    return deco

Con latencia y errores segmentados por proveedor, un dashboard te dice de un vistazo «el lento/averiado hoy es el geocoder, no SMS».

SLA y presupuesto de error

Los proveedores publican disponibilidad de 99.9%; tu integración vive por debajo. Define un presupuesto realista por servicio (por ejemplo, reprograma webhooks con >1% de errores 5xx) y así las alertas solo suenan cuando importa:

{
  "sla_integraciones": {
    "stripe_pagos":     { "disponibilidad_objetivo": "99.95%", "error_budget_ms": 2628000 },
    "correo_transaccional": { "disponibilidad_objetivo": "99.90%" },
    "geocoder":         { "disponibilidad_objetivo": "99.00%" }
  },
  "ventana": "30 días"
}

Alertas accionables

Si tu alerta no dice qué hacer, el turno solo se estresa. Una buena alerta de integración incluye proveedor, servicio, síntoma, y el primer paso del runbook. Además de la tasa de error, alerta sobre:

  • P95 de latencia por encima del umbral sostenido (el proveedor está lento para todos).
  • Webhooks que dejan de llegar: sin eventos firmados durante X minutos, probablemente el proveedor no está entregando. Un healthcheck o un contador de eventos por hora lo captura.
  • Cuota agotándose: al 80% de consumo, avisa antes de fallar en seco.
  • Dead letter creciente: tareas que agotan reintentos; si crece, algo se rompió de verdad.

Regla práctica: la mínima observabilidad de una integración son 3 métricas por proveedor (latencia, error, cuota) + 1 contador de eventos que diga «sigue llegando tráfico».

Ejercicio

  1. Instrumenta una integración propia con las 3 mediciones (latencia, errores, cuota) y etiqueta el proveedor.
  2. Diseña las alertas para un webhook que deja de llegar y para una cuota al 80%.
  3. Escribe el runbook de 5 pasos para «la cola muerta crece»: qué revisar primero y quién es el responsable.

Resumen

  • Logs estructurados con proveedor, endpoint, status y traceId reconstruyen cualquier llamada.
  • Latencia, error y cuota por proveedor son las métricas base de toda integración.
  • Un presupuesto de error realista evita alertas por cualquier bache del proveedor.
  • Las buenas alertas incluyen proveedor, síntoma y el primer paso del runbook.
