Colas para tareas lentas

⚙️ Intermedio 11 min Integraciones y Servicios Externos Módulo 3 · Robustez

Introducción

Hay integraciones que duran milisegundos y otras que duran minutos: generar un PDF pesado, sincronizar miles de clientes con un CRM, enviar o reenviar correos, procesar una factura. Si las ejecutas dentro del request HTTP, tu API queda bloqueada, el usuario espera sin límite y un timeout del proveedor puede tirar abajo todo el endpoint. La solución es el trabajo asíncrono: el request encola la tarea y responde inmediatamente; un worker aparte la procesa en su propio ritmo.

Productor: encolar y responder ya

La API no llama al proveedor lento directamente: publica un trabajo en una cola. El cliente recibe un 202 Accepted al instante y puede consultar el estado después:

import { Queue } from 'bullmq';
import redis from 'ioredis';

const colaSincronizacion = new Queue('sync-crm', { connection: redis });

export async function encolarSincronizacion(clienteId) {
  const job = await colaSincronizacion.add('sync', { clienteId }, {
    attempts: 4,
    backoff: { type: 'exponential', delay: 2000 },
    removeOnComplete: { age: 86400 }
  });
  return { jobId: job.id };  // el cliente puede consultar {jobId}
}

El worker se ejecuta en un proceso separado y puede escalar horizontalmente: más workers, más tareas en paralelo, sin tocar la API.

Worker: el procesador de fondo

El worker escucha la cola, ejecuta la integración y marca el resultado. Si la tarea falla, el sistema reintenta automáticamente según la configuración, y al agotarse los intentos la manda a una cola de dead letters para revisión humana:

# worker.py — procesa la sincronización con el CRM
def sincronizar(job):
    cliente_id = job.payload["clienteId"]
    try:
        crm_client.upsert(cliente_id)          # llamada lenta al tercero
    except ErrorReintentable as err:
        raise JobRetryableError(err) from None  # se reintenta
    return {"sincronizado": cliente_id}

Separa errores que merecen reintento (5xx del proveedor, timeout) de los irreparables (cliente inexistente, 422): los segundos no deben agotar los intentos de nadie.

Estados de un trabajo

Todo el ciclo queda visible si asignas estados a cada tarea. Así puedes responder al cliente y monitorizar el progreso:

{
  "job_id": "b2d1a9f3",
  "tipo": "sync.crm",
  "estado": "procesando",
  "intentos": 2,
  "colas_posibles": [
    "encolado", "procesando", "completado",
    "fallido", "en_cola_muerta"
  ],
  "created_at": "2026-09-22T10:15:00Z"
}

Un endpoint GET /trabajos/:id devuelve ese estado y el frontend puede mostrar «Generando tu factura…» sin bloquear nada.

Idempotencia entre reintentos del worker

El worker puede morir a mitad de tarea y reintentarse desde cero. Si la tarea ya había cobrado o enviado algo, el reintento duplica la acción. Por eso la lógica del worker debe ser idempotente: registra el efecto (guardar el messageId, el pagoId) en la base antes de terminar, y al inicio del trabajo comprueba si el efecto ya existe:

# Escala workers sin tocar la API: cuantos más, más paralelo
worker sync-crm --concurrency 4
worker sync-crm --concurrency 4   # segundo proceso, misma cola

Regla práctica: si la tarea puede provocar un efecto externo (un pago, un correo, un borrado), tu worker es idempotente o tus reintentos tienen fugas.

La cola muerta

Cuando una tarea agota sus reintentos no puede desaparecer silenciosamente: va a la dead letter queue con su historial completo de errores. Esa cola es la lista de espera de operación: alguien la revisa, corrige la causa (una dirección mal escrita) y reencola la tarea con un origen manual que no vuelva a fallar.

Ejercicio

  1. Diseña el modelo de estados de tu tarea asíncrona más lenta y escribe el JSON de ejemplo.
  2. Configura una cola con 4 intentos y backoff exponencial para una sincronización con un CRM ficticio.
  3. Escribe el worker que distingue errores reintentables de irreparables y responde el estado al API.

Resumen

  • Las tareas lentas se encolan y se procesan en workers, no dentro del request.
  • Los workers escalan horizontalmente y reintentan con backoff automático.
  • El estado del trabajo da visibilidad a API y frontend.
  • La idempotencia del worker protege contra el doble efecto de un reintento.
  • La dead letter queue captura lo que no pudo completarse para revisión manual.
