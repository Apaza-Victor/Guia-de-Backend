¿Qué son las integraciones?

⚙️ Intermedio 10 min Integraciones y Servicios Externos Módulo 1 · Fundamentos

Introducción

Ningún producto real es una isla. Aunque tu aplicación pudiera cobrar, autenticar, enviar correos y almacenar archivos por sí sola, reconstruir funcionalidades maduras como pasarelas de pago o redes sociales solo conduce a meses de trabajo y a sistemas con errores que otros ya resolvieron. Una integración es el proceso de conectar dos o más sistemas para que intercambien datos y actúen como una sola unidad de negocio.

El backend moderno pasa gran parte de su existencia integrando: consumir una API de pagos, recibir eventos de un proveedor de correo, sincronizar datos con un ERP o delegar la autenticación a Google. Cuando ese trabajo se hace bien, el producto gana utilidades por día; cuando se hace mal, cada fallo del proveedor se convierte en un fallo tuyo.

Tipos de integración

Las integraciones se pueden clasificar por la dirección del flujo de datos y por el modelo de comunicación:

  • Consumo de APIs: tu backend llama a un servicio de terceros para leer o crear datos (geocodificar una dirección, registrar un pago).
  • Exposición de APIs: un tercero consume tu API (tu plataforma como proveedor de datos para clientes o socios).
  • Eventos entrantes (webhooks): el proveedor te avisa cuando algo ocurre en su sistema (un pago confirmado, un repositorio actualizado).
  • Eventos salientes: tu sistema notifica a otros cuando cambia tu estado interno (publicar eventos de dominio).
  • Sincronización batch: intercambio masivo programado (sincronizar inventario cada noche con el ERP).

Cada tipo exige herramientas distintas: timeouts y reintentos para las llamadas síncronas, colas y verificación de firmas para los eventos, y validación de archivos para los lotes. Un buen inventario de integraciones documenta exactamente eso:

{
  "integraciones": [
    { "nombre": "pagos", "tipo": "api",       "modelo": "sincrono", "critica": true },
    { "nombre": "stripe_eventos", "tipo": "webhook", "modelo": "evento", "critica": true },
    { "nombre": "crm_sync", "tipo": "batch",  "modelo": "lote",     "critica": false }
  ]
}

El valor de negocio

Integrar no es un capricho técnico: es la forma de comprar capacidad probada en lugar de reconstruirla. Los motivos más frecuentes:

  • Velocidad de salida al mercado: pagar con Stripe sale antes que certificar tu propio procesador de tarjetas.
  • Economía de escala: mantener una pasarela de pago, un datacenter o una red de correo cuesta muchísimo más que consumirla.
  • Ecosistema: «inicia sesión con Google» reduce la fricción de registro y con ella el abandono del embudo.
  • Cumplimiento: proveedores certificados (PCI-DSS, SOC 2) te dan garantías regulatorias que tú no podrías afrontar solos.

Para las sincronizaciones batch el patrón es siempre el mismo: leer el origen, transformar y escribir en el destino, registrando el estado de cada lote:

def sincronizar_inventario(lote: list[dict]) -> dict:
    sincronizados = 0
    for item in lote:
        crm.actualizar_stock(sku=item["sku"], stock=item["stock"])
        sincronizados += 1
    return {"lote": len(lote), "sincronizados": sincronizados}

Ejemplo: integrar un servicio de correo

Imagina que tu aplicación necesita enviar un correo cada vez que un usuario completa un pedido. La versión ingenua abre un socket SMTP con tu propio servidor. La versión integrada delega en un servicio transaccional de terceros con plantillas, trackeo y métricas de entrega:

import { send } from '@acme/email-service';

export async function notificarPedido(pedido, cliente) {
  const resultado = await send({
    to: cliente.email,
    template: 'pedido-confirmado',
    context: { nroPedido: pedido.id, total: pedido.total }
  });
  return resultado.messageId;
}

Después de la llamada, tu código no conoce la infraestructura del proveedor: solo conoce un messageId. Ese nivel de abstracción es precisamente lo que convierte un cable eléctrico entre sistemas en una integración mantenible.

Los riesgos de una integración

Integrar también significa ceder control. Los riesgos más comunes:

  • Dependencia de la disponibilidad ajena: si el proveedor cae, tu función de pago cae. Por eso se diseñan timeouts, reintentos y degradaciones.
  • Contratos que cambian: una API puede deprecated campos y quitar endpoints sin avisar; por eso se versiona y se monitoriza.
  • Límites de uso: rate limits y cuotas pueden interrumpir tu servicio si no gestionas el consumo.
  • Privacidad: mandar datos a terceros implica contratos, cifrado en tránsito y, según la normativa, consentimiento del usuario.

Regla práctica: toda integración se comporta como un proveedor poco fiable. Diseña para el fracaso antes que para el éxito: el éxito también llega, pero el fracaso siempre llega antes.

Ejercicio

  1. Elige un producto real (una tienda en línea, un SaaS, una app de delivery) y lista sus 5 integraciones más evidentes.
  2. Clasifica cada una según el tipo: consumo de API, exposición, webhook entrante, evento saliente o sincronización batch.
  3. Para la integración más crítica, responde por escrito: ¿cómo falla, qué pasa sí el proveedor cae 5 minutos y qué datos intercambia con él?

Resumen

  • Integración es conectar sistemas para intercambiar datos y actuar como una sola unidad de negocio.
  • Se clasifican por dirección (consumo/exposición) y modelo (síncrono, eventos, batch).
  • Aportan velocidad y escala, pero ceden disponibilidad y control a terceros.
  • La clave está en abstraer al proveedor detrás de una capa propia y diseñar para el fracaso.
