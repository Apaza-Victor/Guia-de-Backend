Patrones de integración

⚙️ Intermedio 11 min Integraciones y Servicios Externos Módulo 1 · Fundamentos

Introducción

Integrar sistemas de forma improvisada produce el famoso «espagueti de integración»: llamadas directas a terceros por todo el código, contratos quemados en cada controlador y cambios de proveedor que cuestan semanas. Los patrones de integración (Enterprise Integration Patterns, EIP) son soluciones probadas a los problemas recurrentes: cómo aislar al proveedor, cómo traducir los datos y cómo coordinar flujos que atraviesan varios sistemas.

Los tres patrones que más rinden en el día a día son el adaptador, el mapper y la orquestación.

El patrón adaptador

El adaptador es una clase que envuelve a un proveedor externo y lo presenta al resto del sistema con una interfaz tuya. Si mañana cambias de proveedor de correo a otro, solo cambia el adaptador; el resto del código ni se entera:

class ProveedorCorreo {
  _sdk = null;

  constructor(sdk) {
    this._sdk = sdk; // SDK oficial del proveedor
  }

  async enviar({ to, template, context }) {
    const resp = await this._sdk.sendTemplate({ to, template, context });
    return { messageId: resp.id, status: resp.status };
  }

  async obtenerEstado(messageId) {
    return this._sdk.retrieve(messageId).status;
  }
}

La interfaz interna (enviar, obtenerEstado) pertenece a tu dominio. El adaptador es el único lugar del proyecto que conoce la API real del tercero: es la frontera entre «tu mundo» y «el mundo del proveedor».

El patrón mapper

El tercero no habla tu idioma de contratos: a veces llama a la fecha de creación created_at y a veces fechaCreacion; a veces te manda céntimos y a veces euros. El mapper traduce entre ambos mundos, evitando que el formato del proveedor contamine tu código de negocio:

from dataclasses import dataclass

@dataclass
class ClienteFacturacion:
    id_externo: str
    email: str
    nombre: str

def mapear_cliente_desde_proveedor(payload: dict) -> ClienteFacturacion:
    return ClienteFacturacion(
        id_externo=payload["customer_id"],
        email=payload["billing"]["email"],
        nombre=payload["name"]["given"] + " " + payload["name"]["family"],
    )

El mapper también sirve de defensa cuando el contrato cambia: si el proveedor renombra un campo, el único ajuste lo haces dentro del mapper y un test te avisa de qué esperaba antes.

Orquestación vs coreografía

Cuando un flujo cruza varios servicios (cobrar, actualizar inventario, enviar correo, guardar el pedido) necesitas decidir quién dirige el flujo:

  • Orquestación: un componente central (el orquestador) llama a cada servicio en orden y decide el resultado global. Es fácil de entender y de depurar, pero ese punto central puede convertirse en un cuello de botella.
  • Coreografía: no hay director. Cada servicio reacciona a eventos publicados por los demás y todos se coordinan de forma descentralizada. Es más escalable, pero más difícil de razonar.

Para integraciones con terceros, la orquestación suele ser la elección correcta al principio. Un flujo típico queda así:

{
  "flujo": "confirmar_pedido",
  "pasos": [
    { "servicio": "pagos",     "accion": "cobrar",     "retry": true },
    { "servicio": "inventario","accion": "reservar",   "retry": true },
    { "servicio": "correo",    "accion": "confirmacion","retry": false },
    { "servicio": "logistica", "accion": "programar",  "retry": true }
  ],
  "estrategia_fallo": "compensar_pasos_exitosos"
}

Cuando un paso falla, el orquestador decide si reintenta, si compensa lo ya hecho o si pasa el flujo a una cola para reintentarlo después.

Otros patrones útiles

  • Gateway: una versión del adaptador orientada a servicios completos, habitual cuando se integra un ERP o un legacy.
  • Router: decide a qué sistema va cada mensaje según su contenido (factura a SAP, pedido a Shopify).
  • Translator: transforma el mensaje completo entre formatos (JSON a XML) antes de entregarlo.
  • Aggregator: combina respuestas de varias fuentes en una única respuesta a tu sistema (un dashboard que consulta 3 APIs a la vez).

Regla práctica: ningún proveedor externo debe aparecer como tipo importado fuera de su adaptador. Si tu controlador hace new StripeAPI(), ya estás fuera del patrón.

Ejercicio

  1. Escribe la interfaz de un adaptador PasarelaDePagos con métodos para cobrar, reembolsar y consultar un pago.
  2. Implementa un mapper en Python o JavaScript que traduzca un payload de ejemplo del proveedor a tu modelo interno.
  3. Dibuja el flujo «registro de usuario» (validar correo, crear cuenta, dar bienvenida, crear workspace) y decide qué pasos requieren retry y cuáles no.

Resumen

  • Los patrones de integración resuelven problemas recurrentes de forma probada.
  • El adaptador aísla al proveedor detrás de una interfaz propia.
  • El mapper traduce contratos externos a tu modelo de dominio.
  • La orquestación centraliza el flujo; la coreografía lo descentraliza.
  • Ningún proveedor debe aparecer fuera de su adaptador.
