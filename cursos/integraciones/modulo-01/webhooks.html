Webhooks

⚙️ Intermedio 10 min Integraciones y Servicios Externos Módulo 1 · Fundamentos

Introducción

Casi toda la vida con terceros se reduce a dos modelos: preguntar o ser avisado. Consultar cada 30 segundos si el pago se confirmó (polling) es ineficiente y lento. El webhook invierte el flujo: el proveedor te llama a ti cuando algo ocurre, enviando un HTTP POST con los detalles del evento. Tu servidor se convierte temporalmente en el cliente.

Recibir avisos suena sencillo, pero implica cuatro responsabilidades que no puedes saltarte: verificar la firma, responder rápido, deduplicar eventos y tolerar reintentos.

Webhook vs polling

  • Polling: tu sistema consulta «¿pasó algo?» en intervalos fijos. Simple, pero late incluso cuando no hay cambios, desperdicia peticiones y añade latencia de hasta un intervalo completo.
  • Webhook: el proveedor te avisa en el momento exacto. Casi en tiempo real y sin peticiones perdidas, pero requiere que tu endpoint esté público, disponible y seguro.

En la práctica se complementan: los webhooks entregan el evento de forma inmediata y un polling de respaldo recupera eventos perdidos cuando un webhook falla o llega tarde.

Verificar la firma

Cualquiera puede fingir ser Stripe o GitHub y mandarte un POST falso. Por eso los proveedores firman cada payload con un esquema HMAC: calculan el hash del mensaje con un secreto que solo tú y ellos conocen y lo envían en un header. Tu trabajo es recalcular ese hash y compararlo:

import crypto from 'node:crypto';

const SECRETO = process.env.WEBHOOK_SECRETO;

function firmaValida(payloadBruto, firmaRecibida, timestamp) {
  const payload = `${timestamp}.${payloadBruto}`;
  const esperado = crypto
    .createHmac('sha256', SECRETO)
    .update(payload)
    .digest('hex');
  return crypto.timingSafeEqual(Buffer.from(esperado), Buffer.from(firmaRecibida));
}

Usa timingSafeEqual (comparación en tiempo constante) en lugar de === para no filtrar información por el tiempo de comparación, y regístrala incluso con idempotency-key en recibido.

Responder rápido y de forma correcta

El proveedor espera el 200 en pocos segundos. Si respondes 4xx o 5xx, o si se agota el tiempo, el webhook se considera fallido y se reintenta. Por eso el patrón ganador es: valida, encuela y responde 200; el trabajo pesado se hace después:

@app.post("/webhooks/pagos")
def webhook_pago():
    cuerpo = envio.get_json()
    if not firma_valida(envio):          # rechaza falsificaciones
        return "", 401
    encolar_workflow_pago(cuerpo)        # respondemos antes de procesar
    return "", 200                       # 200 = evento aceptado

Si el procesamiento fuera síncrono dentro del handler, un trabajador lento provocaría que el webhook se reintente (por timeout) y recibas el mismo evento dos veces.

Reintentos e idempotencia

Los proveedores reintentan con backoff: envían de nuevo el mismo evento pasados segundos o minutos. Como no puedes controlar cuántas veces llega, tu handler debe ser idempotente: procesar dos veces el mismo evento.id produce el mismo resultado. La técnica estándar es registrar los IDs ya procesados:

{
  "id": "evt_1MpF2rLsdH...",
  "type": "payment_intent.succeeded",
  "created": 1699992000,
  "data": { "object": { "id": "pi_3MpF...", "amount": 4900, "currency": "mxn" } }
}
curl -X POST https://tu-api.com/webhooks/pagos \
  -H "Stripe-Signature: t=1699992000,v1=abc123...." \
  -H "Content-Type: application/json" \
  -d '{"id":"evt_1MpF2rLsdH","type":"payment_intent.succeeded","data":{}}'

Antes de ejecutar la lógica de negocio, inserta el id con una clave única en tu base. Si la inserción falla por duplicado, el evento ya se procesó y simplemente respondes 200.

Ejercicio

  1. Crea una tabla webhook_events con una restricción única sobre el evento_id y escribe el SQL.
  2. Implementa la verificación HMAC en JavaScript o Python con tu propio secreto de prueba.
  3. Escribe el handler que responde 200, encola el trabajo y rechaza con 401 una firma inválida.

Resumen

  • Un webhook es un aviso HTTP del proveedor a tu servidor cuando ocurre un evento.
  • El polling complementa a los webhooks para recuperar eventos perdidos.
  • Siempre verifica la firma HMAC antes de confiar en el payload.
  • Responde 200 rápido y procesa después en una cola.
  • Los webshooks pueden llegar varias veces: deduplica por ID y sé idempotente.
