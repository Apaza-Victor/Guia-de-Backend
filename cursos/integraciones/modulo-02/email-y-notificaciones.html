Email y notificaciones

⚙️ Intermedio 11 min Integraciones y Servicios Externos Módulo 2 · Integraciones prácticas

Introducción

El correo puede ser la única comunicación que tu producto tiene con el usuario: confirmaciones, recuperación de contraseña, facturas, avisos de pago. Enviarlo mal tiene dos consecuencias: el mensaje no llega (y el usuario piensa que tu app no funciona) o tu dominio termina en listas de spam. Por eso el envío transaccional no se hace con tu propio SMTP sino con un proveedor de correo transaccional (SendGrid, Resend, SES) que se encarga de infraestructura, entregabilidad y métricas.

SMTP vs API transaccional

  • SMTP propio: simple para desarrollo local, inviable en producción seria: sin reputación, sin tracking y con riesgo alto de caer en spam.
  • API del proveedor: envía por HTTP, gestiona plantillas, reenvíos, aperturas/clics y eventos de entrega. Es la opción profesional.

En producción casi siempre usa la API del proveedor. El SMTP de un servidor de desarrollo/interino (Mailtrap) solo sirve para probar en local sin mandar nada real.

Envío con API transaccional

El patrón limpio es un adaptador que envía plantillas y no expone el SDK del proveedor al resto del sistema:

import { MailService } from '@sendgrid/mail';

const mail = new MailService();

export async function enviarTransaccional({ to, templateId, context }) {
  return mail.send({
    to,
    from: { email: process.env.EMAIL_FROM },
    templateId,
    dynamicTemplateData: context
  });
}

La plantilla vive en el proveedor (no en tu código): así marketing puede ajustar textos sin tocar tu repositorio. En tu backend solo envías el templateId y los datos dinámicos.

Entregabilidad: firma y reputación

Que el proveedor «acepte» el envío no significa que llegue a la bandeja de entrada. La entregabilidad se construye:

  • SPF, DKIM y DMARC: registros DNS que demuestran que el dominio tiene derecho a enviar en tu nombre. Sin ellos, Gmail y Outlook descartan.
  • Dominio remitente propio: no-reply@tuempresa.com en vez de no-reply@sendgrid.net.
  • Tracking de bounces y quejas: una reputación dañada tarda mucho en recuperarse.
# Verifica los registros DNS de tu dominio para correo
nslookup -type=TXT v=DKIM1; k=rsa el dominio.com
dig el dominio.com TXT    # debe incluir SPF, DKIM y DMARC

Eventos de entrega por webhook

Los proveedores transaccionales te avisan por webhook cuando un correo rebota, se marca como spam o se entrega. Reaccionar a esos eventos marca la diferencia entre una base sana y una llena de direcciones muertas:

{
  "event": "bounce",
  "email": "usuario@extinto.com",
  "category": "transaccional",
  "reason": "550 5.1.1 User unknown",
  "timestamp": 1699992000,
  "envio_id": "sg-5f1a2b3c"
}

La reacción típica ante un bounce: marcar el contacto como inválido y dejar de enviarle (a veces con uno o dos reintentos antes de darle de baja). Ante un spamreport: respetarlo inmediatamente.

Más allá del correo

El correo es solo un canal. Un backend de notificaciones decente separa el canal del mensaje: un evento de dominio (pedido creado) dispara varias entregas (email, push, SMS) según preferencias del usuario. El patrón es siempre el mismo: capa de adaptador + plantillas + gestión de fallos de entrega con cola.

Regla práctica: envía correos de forma asíncrona siempre. Una cola absorbe los picos y te permite reintentar sin bloquear la respuesta HTTP al usuario.

Ejercicio

  1. Crea un adaptador Notifier con un método enviar(plantilla, contexto) y prueba local con Mailtrap.
  2. Configura SPF, DKIM y DMARC en un dominio de prueba y verifica con dig.
  3. Escribe el handler de webhook que marca como inválido a un usuario tras un bounce confirmado.

Resumen

  • El correo transaccional se envía por API de un proveedor, no con tu SMTP propio.
  • Las plantillas viven en el proveedor; tu backend solo manda el id y los datos.
  • SPF, DKIM y DMARC determinan si el correo llega o va a spam.
  • Los webhooks de entrega te permiten limpiar bounces y proteger tu reputación.
