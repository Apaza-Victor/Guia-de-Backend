Pasarelas de pago

⚙️ Intermedio 12 min Integraciones y Servicios Externos Módulo 2 · Integraciones prácticas

Introducción

Integrar una pasarela de pago como Stripe o PayPal es una de las integraciones con más aristas de todo el backend: toca dinero, es irreversible de un día para otro y el flujo no termina cuando el usuario abandona su tarjeta. La regla de oro es que el servidor nunca debe tocar datos de tarjeta; toda la sensibilidad vive dentro del dominio de la pasarela. Por eso se usan sesiones de pago: el backend crea la sesión y el cliente solo la redirige y completa.

PCI-DSS y la regla de oro

  • Nunca almacenes números de tarjeta, CVV ni datos de banda magnética en tu infraestructura.
  • Usa Checkout / Payment Links o tarjetas tokenizadas por la pasarela (Payment Intents).
  • Nunca lleves datos de pago por tus logs: ni siquiera mascarados de más.
  • El sandbox de la pasarela es tu laboratorio: prueba todos los flujos con tarjetas de test.

Delegar el manejo del plástico en la pasarela no es una excusa: es la diferencia entre quedar fuera del alcance completo de PCI-DSS o convertirse en tu mayor riesgo.

Crear una sesión de pago

El flujo típico con Stripe Checkout: el backend valida el pedido y crea una sesión; el navegador redirige al usuario a la URL de la sesión; cuando el pago se completa, la pasarela avisa con un webhook y además redirige al usuario de vuelta a tu sitio:

import Stripe from 'stripe';
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);

export async function iniciarCheckout(pedido, cliente) {
  const sesion = await stripe.checkout.sessions.create({
    customer_email: cliente.email,
    line_items: [{
      price_data: {
        currency: 'mxn',
        product_data: { name: pedido.resumen },
        unit_amount: pedido.totalCentavos
      },
      quantity: 1
    }],
    mode: 'payment',
    success_url: `${process.env.SITIO}/pago-exitoso`,
    cancel_url: `${process.env.SITIO}/carrito`,
    metadata: { pedidoId: pedido.id }
  });
  return { url: sesion.url, id: sesion.id };
}

Guarda el id de la sesión en tu pedido. Fíjate en metadata: sirve para cruzar el webhook con tu pedido cuando la pasarela te conteste.

Confirmar con webhook

Jamás des por pagado un pedido porque el navegador volvió a success_url: esa URL se puede visitar sin pagar nada. La confirmación fiable llega por webhook desde la pasarela. El handler valida la firma, ignora eventos duplicados y marca el pedido como pagado:

import stripe

def webhook_stripe(envio):
    payload = envio.get_data(as_text=True)
    try:
        evento = stripe.Webhook.construct_event(payload, envio.headers["Stripe-Signature"], WEBHOOK_SECRETO)
    except stripe.error.SignatureVerificationError:
        return "Firma inválida", 400

    if evento["type"] == "checkout.session.completed":
        pedido_id = evento["data"]["object"]["metadata"]["pedidoId"]
        if not pedido_ya_procesado(pedido_id):   # deduplicación
            marcar_pedido_como_pagado(pedido_id)
    return "ok", 200

Idempotencia y doble cobro

La pasarela puede reintentar webhooks y tu usuario puede pulsar «pagar» dos veces. Sin protección, eso significa doble cobro. Tres defensas:

  • Una clave de idempotencia en la creación del Payment Intent: la misma clave + mismo payload recibe la misma respuesta, sin segundo cargo.
  • Confirmar pagos solo cuando el pedido está en estado pendiente (una transición de estado estricta).
  • Deduplicar webhooks por evento.id en la base antes de tocar el pedido.
# Usa una clave de idempotencia para crear intents de pago
curl https://api.stripe.com/v1/payment_intents \
  -u $STRIPE_SECRET_KEY: \
  -d amount=4900 \
  -d currency=mxn \
  -d "idempotency_key=pedido-12345"

Reembolsos y disputas

El dinero también vuelve. Los reembolsos suelen ser totales o parciales y se ejecutan contra el payment_intent. Planifica el flujo en tu backend: un endpoint admin, audit log y notificación al usuario. Y recuerda que los clientes pueden abrir disputas (chargebacks) con su banco: tu pasarela recibirá el evento correspondiente, que conviene monitorizar para reaccionar con evidencia.

Regla práctica: en pagos, el evento de la pasarela (webhook) manda sobre cualquier respuesta síncrona. El frontend solo muestra la redirección; la verdad la trae el evento firmado.

Ejercicio

  1. Crea un endpoint que genere una sesión de pago en sandbox con una clave de prueba.
  2. Implementa el handler de webhook que valida la firma y deduplica por evento.id.
  3. Escribe la transición de estados del pedido: pendiente → pagado → (fallido/reembolsado), y decide quién puede cambiar cada estado.

Resumen

  • El servidor nunca debe tocar datos de tarjeta: usa sesiones de pago de la pasarela.
  • La confirmación real llega por webhook firmado, no por la redirección del navegador.
  • La idempotencia (claves y deduplicación) evita el doble cobro.
  • Los reembolsos y los chargebacks son parte del flujo: diseña para ellos.
