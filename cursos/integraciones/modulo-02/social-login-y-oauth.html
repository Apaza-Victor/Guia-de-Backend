Social login y OAuth

⚙️ Intermedio 11 min Integraciones y Servicios Externos Módulo 2 · Integraciones prácticas

Introducción

«Inicia sesión con Google» no es magia: tu backend le da la bienvenida al usuario sin ver jamás su contraseña. Eso funciona porque el usuario autoriza a tu aplicación a saber quién es a través de OAuth 2.0 (delegación de acceso) y, si el proveedor soporta OIDC (OpenID Connect), tu app recibe además su identidad verificada. Tu papel es implementar el flujo correctamente y no guardar el token en un lugar frágil.

El flujo de authorization code

  1. Tu backend redirige al usuario al proveedor con su client_id y los scopes pedidos.
  2. El usuario se autentica en el proveedor y aprueba los permisos.
  3. El proveedor redirige de vuelta a tu redirect_uri con un code de un solo uso.
  4. Tu backend presenta el code al token endpoint junto con su client_secret y recibe los tokens.
const params = new URLSearchParams({
  client_id: process.env.GOOGLE_CLIENT_ID,
  redirect_uri: 'https://mi-app.com/auth/callback',
  response_type: 'code',
  scope: 'openid email profile',
  state: nonceAleatorio()
});
res.redirect(`https://accounts.google.com/o/oauth2/v2/auth?${params}`);

El parametro state es una protección anti-CSRF: comprueba que sea el mismo que generaste antes de aceptar el code. Nunca lo omitas.

Canjear el code por tokens

El code es corto y de un solo uso. El canje ocurre servidor a servidor, nunca en el navegador, porque requiere el client_secret:

import httpx

def canjear_code(code: str) -> dict:
    resp = httpx.post(
        "https://oauth2.googleapis.com/token",
        data={
            "code": code,
            "client_id": GOOGLE_CLIENT_ID,
            "client_secret": GOOGLE_CLIENT_SECRET,
            "redirect_uri": CALLBACK_URL,
            "grant_type": "authorization_code",
        },
    )
    resp.raise_for_status()
    return resp.json()
    # -> {"access_token": ..., "refresh_token": ..., "id_token": ..., "expires_in": 3600}

Con el id_token (un JWT firmado que verifica la identidad) creas o encuentras al usuario en tu base; con el access_token accedes a sus datos autorizados (su foto, su correo verificado).

OIDC: identidad verificada

OIDC añade el id_token: un JWT con los claims del usuario (sub, email, email_verified, name). Debes validarlo antes de confiar:

{
  "iss": "https://accounts.google.com",
  "sub": "1182347835209876",
  "email": "ana@correo.com",
  "email_verified": true,
  "aud": "mi-client-id.apps.googleusercontent.com",
  "exp": 1699992000
}
  • Verifica la firma con las claves públicas del proveedor (JWKS) al descargar de su discovery endpoint.
  • Comprueba iss, aud y exp. Un JWT firmado para otro aud o caducado no vale.
  • Usa el sub como identificador estable del usuario, no su correo (que puede cambiar).

Refresh y sesión propia

Los access_token expiran (una hora típicamente). El refresh_token de larga duración los renueva silenciosamente cuando el acceso sigue siendo necesario:

curl -X POST https://oauth2.googleapis.com/token \
  -d grant_type=refresh_token \
  -d client_id=$GOOGLE_CLIENT_ID \
  -d client_secret=$GOOGLE_CLIENT_SECRET \
  -d refresh_token=$REFRESH_TOKEN

El refresh_token se guarda cifrado y ligado a tu usuario. No lo envíes al navegador: tu backend mantiene su propia sesión (cookie HttpOnly), y los tokens del proveedor quedan a salvo en tus datos.

Regla práctica: el navegador solo ve la sesión de tu app. Los tokens de OAuth viven en tu backend, cifrados, nunca en localStorage del cliente.

Errores que verás seguido

  • invalid_grant — el code ya se usó o caducó; vuelve a empezar el flujo.
  • redirect_uri_mismatch — la URI configurada en el proveedor no coincide con la llamada.
  • invalid_client — secret mal configurado o expuesto.
  • unauthorized_client — el client_id no tiene permitido el scope pedido.

Ejercicio

  1. Registra una app en un proveedor (puedes usar uno de test) y configura redirect_uri y state.
  2. Implementa el endpoint callback que valida el state, canjea el code y verifica el id_token.
  3. Dibuja en un diagrama quién ve qué: proveedor, navegador, tu backend, y cuál guarda cada token.

Resumen

  • OAuth 2.0 delega acceso; OIDC añade identidad verificada con id_token.
  • El code se canjea servidor a servidor con el client_secret.
  • Siempre valida state, firma, iss, aud y exp.
  • El refresh_token se guarda en el backend; el navegador solo conoce tu sesión.
