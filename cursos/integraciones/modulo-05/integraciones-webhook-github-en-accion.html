Caso real: webhooks de GitHub

⚙️ Intermedio 10 min Integración y Servicios Externos Módulo 5 · Webhooks y eventos

Introducción

GitHub es probablemente el proveedor de webhooks más usado: manda eventos de push, pull request, comentarios o releases a cualquier URL que configuremos. Es un caso perfecto porque su documentación es clara, sus firmas se verifican con HMAC y sus eventos llegan con estructura conocida.

Integrar sus webhooks en tu backend te permite encadenar trabajo: validar el código ante cada push, publicar notas en un chat o disparar tus despliegues.

Definición

Un webhook de GitHub es una notificación HTTP firmada con HMAC con un secreto que genera el proveedor; cada tipo de evento (push, pull_request, release) llega a un payload con esquema propio.

Por qué importa. Permite que tu infraestructura reaccione al ciclo de desarrollo sin pollings ni scripts programados: el propio repositorio te avisa.

Cuándo usarlo. Úsalo para CI, para avisar a un canal de chat, para documentar cambios o para orquestar despliegues a partir de eventos.

Conceptos clave

  • Cada evento tiene un tipo y un payload con esquema específico (push, pull_request).
  • La firma X-Hub-Signature-256 usa HMAC-SHA256 con tu secreto.
  • El id de entrega está en la cabecera X-GitHub-Delivery.
  • GitHub reintenta los fallos de entrega con su propia política.
  • El evento push trae rama, commits, autor y antecesor del commit.

Ejemplo real

Un equipo de backend despliega en staging solo cuando un push toca la rama develop y pasa el CI. El webhook de push activa el pipeline, el pipeline notifica a un canal y el equipo ve verde o rojo sin mirar el panel. Cuando alguien hace push a una rama de feature, el webhook solo dispara lint rápido.

  • Mira la rama real del evento antes de decidir qué dispara.
  • anexa el aviso a un canal para que el equipo vea el resultado sin mirar paneles.
  • Usa el id de entrega como clave de deduplicación.

GitHub enviará también eventos de pull_request con la misma URL; filtra por tipo para no disparar el despliegue dos veces.

Explicación

  • La cabecera X-Hub-Signature-256 de GitHub exige el prefijo sha256= en la comparación.
  • El evento push contiene la rama entera en ref, que conviene limpiar antes de usar.
  • Filtrar por tipo de evento evita que cada pull request relance pipelines.
  • El id de entrega permite deduplicar si GitHub vuelve a entregar por un fallo.
  • Combinar webhook con pipeline convierte un push en un despliegue verificado.

Errores comunes

  • Olvidar el prefijo sha256= y fallar siempre la verificación.
  • Disparar el despliegue sin mirar la rama y publicar una feature a medias.
  • Loggear el payload entero del push con datos del autor innecesarios.

Buenas prácticas

  • Configura el secreto dentro de la consola de GitHub y mantenlo fuera del repo.
  • Prueba con el botón de reenviar de la consola de webhooks para reproducir un evento.
  • Rechaza eventos de tipos que no esperas con una respuesta limpia.
  • Documenta los eventos que consumes y los que reenvías a tus colas.

Ejercicio

  1. Verifica la firma de un webhook de GitHub con tu secreto y un payload de prueba.
  2. Configura un webhook para la rama develop que solo dispare lint.
  3. Dedupica dos entregas del mismo id de entrega en tu cola.

Resumen

  • GitHub firma cada entrega con HMAC y un secreto compartido.
  • Filtrar por tipo de evento y por rama decide qué reacciona y qué no.
  • El id de entrega y el pipeline convierten el push en despliegue verificado.
