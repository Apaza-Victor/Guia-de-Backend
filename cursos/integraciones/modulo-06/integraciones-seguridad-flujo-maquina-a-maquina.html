OAuth de máquina a máquina

⚙️ Intermedio 12 min Integración y Servicios Externos Módulo 6 · Seguridad en integraciones

Introducción

Cuando tu backend llama al de otro sistema sin que haya un usuario humano de por medio, el flujo OAuth adecuado es client credentials: no hay contraseña del usuario ni pantalla de consentimiento, solo tu aplicación pidiendo un token en nombre propio.

Ese token caduca, se renueva y lleva scopes. El flujo encaja perfecto con integraciones de facturación, sincronización o procesamiento por lotes.

Definición

El flujo client credentials es un modo de OAuth 2.0 donde la aplicación usa su propio par client_id y client_secret para obtener un access_token que representa al servicio, no a un usuario.

Por qué importa. Permite autorizar servicios completos entre sí y expira tokens para no dejar credenciales eternas en el aire.

Cuándo usarlo. Úsalo para integraciones servidor-a-servidor; si hay un usuario humano de por medio, necesitas authorization code con scopes del usuario.

Conceptos clave

  • client_id y client_secret identifican y autentican a tu aplicación.
  • El token se solicita una vez y se renueva antes de expirar.
  • Los scopes del token limitan qué puede hacer con el servicio ajeno.
  • El token nunca debe viajar en la URL; va en la cabecera de autorización.
  • La renovación se automatiza cuando el proveedor lo permite.

Ejemplo real

Una plataforma de nóminas sincroniza con la contabilidad cada noche. No hay usuario: el proceso nocturno obtiene su token con client credentials y scope de escritura de asientos. El token expira y se renueva solo; si el proceso falla, el siguiente turno vuelve a obtener token sin intervención.

  • Guarda el client_secret en el gestor de secretos, nunca en el repo.
  • Cachea el token y renóvalo antes de que expire.
  • Ampárate el scope en el proveedor y en tu propia política de red.

Algunos proveedores exigen mTLS o IP de origen autorizada; añádelo en la política de red y la configuración del token.

Explicación

  • client credentials representa a tu servicio, no a un usuario.
  • Los scopes del token acotan el alcance de la integración.
  • El tiempo de vida del token limita la validez de una fuga.
  • Cachear y renovar evita el despilfarro de peticiones de token.
  • La cabecera de autorización es el único sitio correcto para el token en movimiento.

Errores comunes

  • Guardar el client_secret en variables de entorno del código o en el repo.
  • Solicitar un scope amplio porque no se sabe cuál se necesita.
  • Pedir un token nuevo por cada llamada y agotar el rate limit.

Buenas prácticas

  • Renueva el token por debajo del tiempo real para dejar margen.
  • Audita en el proveedor cuántos tokens se emitieron y cuándo expiraron.
  • Define el scope mínimo y el tiempo de vida en el panel del proveedor.

Ejercicio

  1. Obtén un token con client credentials y úsalo en una llamada real.
  2. Escribe el caché de token con renovación y márgenes de seguridad.
  3. Solicita dos scopes distintos y compara qué permite cada uno.

Resumen

  • client credentials autoriza servicios entre sí sin usuarios.
  • El token con scopes y tiempo de vida limitado reduce el daño de una fuga.
  • Caché, renovación y cabecera de autorización mantienen la disciplina del flujo.
