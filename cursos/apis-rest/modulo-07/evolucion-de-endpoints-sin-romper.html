Evolucionar sin romper a los clientes

🔥 Avanzado 12 min APIs REST Módulo 7 · APIs en producción

Introducción

El peor sonido para un equipo de API es el de una aplicación móvil que deja de funcionar después de un deploy. Esas rupturas casi nunca son accidentales: son el precio de cambiar contratos sin estrategia.

La evolución compatible es la regla de oro: antes de eliminar o renombrar, pregúntate cómo añadir sin romper. Casi siempre hay un camino aditivo.

Definición

Evolucionar sin romper significa cambiar la API por dentro (también su lógica) manteniendo el contrato que los clientes ya usan: no borrar campos, no cambiar tipos, no exigir nuevos datos obligatorios.

Por qué importa. Cada cliente (apps, frontends, integraciones) asume tu contrato. Una ruptura no categórica se paga con incidentes, tickets y pérdida de confianza.

Cuándo usarlo. Aplícalo a cualquier API con consumidores desconocidos. En APIs internas con un único consumidor sincronizado, el cambio directo puede negociarse.

Conceptos clave

  • Compatibilidad hacia atrás: las respuestas viejas siguen siendo válidas.
  • Campos opcionales con valor por defecto: añadir sin exigir.
  • Convenciones de fecha y enumerados: solo ampliar, nunca reordenar.
  • Filtros y query params como puerta de acceso a nueva funcionalidad.
  • Códigos y mensajes de error: añadir nuevos casos, no reutilizar otros.

Ejemplo básico

Añadir un campo nuevo a la respuesta es retrocompatible: los clientes que no lo conocen simplemente lo ignoran.

Ejemplo intermedio

Cuando el cambio altera el formato de un campo existente, la negociación de contenido te deja servir el nuevo contrato sin migrar a nadie a la fuerza.

Ejemplo real

En APIs grandes, un nuevo campo suele proteger el despliegue de la implementación: lanzarlo como opcional, medir su uso y solo entonces hacerlo estándar.

  • Añade los nuevos campos al final de la respuesta, nunca en medio.
  • Da valores por defecto sensatos a todo campo nuevo.
  • Deprecia antes de romper: aviso, plazo y superposición.

El atributo deprecated del campo avisa en la documentación sin romper a quien sigue usándolo.

Explicación

  • Añadir es el movimiento preferido: obliga a los clientes a nada.
  • Los campos nuevos deben tener valores por defecto sensatos.
  • La negociación de contenido permite convivir dos contratos.
  • Cambios de formato de campos existentes casi siempre son ruptura.
  • Cada ruptura se evita con una estrategia aditiva o con sobreversión pactada.

Errores comunes

  • Añadir un campo nuevo obligatorio: los clientes viejos fallan al validar.
  • Renombrar un campo y dejar el viejo abajo sin alias.
  • Cambiar el tipo de total a string y declararlo MINOR.

Buenas prácticas

  • Revisa tu spec OpenAPI antes de cada deploy: ¿hay cambios no compatibles?
  • Dibuja el dif del contrato en la revisión de código.
  • Mide usos: telemetría que asocie endpoint a versión de contrato.
  • Mantén un catálogo de consumidores de tu API como mapa de influencia.

Ejercicio

  1. Añade el campo currency a tu esquema Order como opcional con por defecto.
  2. Compara el diff OpenAPI entre dos versiones y clasifica cada cambio.
  3. Sirve dos contratos con el mismo endpoint usando negociación de contenido.

Resumen

  • La evolución compatible se basa en añadir sin romper el contrato.
  • Campos opcionales, valores por defecto y nuevos querys son la vía aditiva.
  • La negociación de contenido permite superponer contratos sin migración forzada.
