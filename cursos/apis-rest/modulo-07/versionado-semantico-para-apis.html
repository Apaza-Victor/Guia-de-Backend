Versionado semántico para APIs

🔥 Avanzado 12 min APIs REST Módulo 7 · APIs en producción

Introducción

Tu API vivirá años y cambiará decenas de veces. Sin una forma de comunicar cuánto cambia cada release, los consumidores nunca sabrán si pueden actualizar con confianza o si se les romperá el contrato.

El versionado semántico (SemVer) resuelve esto con tres números que declaran la intención: MAJOR rompe, MINOR suma sin romper y PATCH corrige sin cambiar el contrato.

Definición

El versionado semántico usa MAJOR.MINOR.PATCH para comunicar el impacto de cada release de una API: MAJOR introduce cambios incompatibles, MINOR añade funcionalidad compatible y PATCH corrige errores sin alterar el contrato.

Por qué importa. El consumidor necesita saber, con solo leer la versión, si puede actualizar en caliente o si debe planificar una migración.

Cuándo usarlo. Aplícalo a partir de la primera versión estable de la API. Durante el desarrollo inicial, la convención 0.x ya avisa de inestabilidad.

Conceptos clave

  • MAJOR: cambios incompatibles (romper contrato, borrar campos).
  • MINOR: funciones nuevas retrocompatibles (añadir campos).
  • PATCH: correcciones que no cambian el comportamiento público.
  • Changelog: el registro legible de qué cambió en cada versión.
  • Versión del contrato vs versión de la implementación.

Ejemplo real

En producción, la decisión de saltar a una MAJOR se planifica: se anuncia, se da un plazo y se ofrecen versiones superpuestas mientras migran los consumidores.

  • Anuncia la ruptura con antelación en el changelog y en las notas de release.
  • Superpón temporalmente la versión nueva y la anterior.
  • Mide qué consumidores aún llaman a la versión vieja antes de retirarla.

Exponer la versión en una cabecera de respuesta ayuda a operaciones a auditar qué contrato está usando cada cliente.

Explicación

  • MAJOR rompe el contrato: cualquier cambio que haga fallar a un cliente existente.
  • MINOR añade sin romper: nuevos campos, nuevos endpoints opcionales.
  • PATCH corrige sin cambiar el comportamiento público de la API.
  • El changelog es parte del contrato: documenta el impacto de cada release.
  • No confundas la versión del paquete que implementa con la del contrato de la API.

Errores comunes

  • Etiquetar como MINOR un cambio que elimina campos y rompe clientes.
  • No publicar changelog que acompañe las versiones: el impacto se adivina.
  • Bumpear versiones sin relación real con los cambios del contrato.

Buenas prácticas

  • Añade version a info de tu spec OpenAPI y mantenla al día.
  • Escribe el changelog en cada PR: si no cambia, revisa si de verdad es un release.
  • Empieza en 0.1.0 y pasa a 1.0.0 cuando el contrato se estabilice.
  • Documenta las fechas de fin de soporte de cada MAJOR.

Ejercicio

  1. Escribe el changelog de una release 2.4.0 con dos añadidos y una corrección.
  2. Clasifica cinco cambios reales de tu API en MAJOR, MINOR o PATCH.
  3. Añade la versión SemVer a la cabecera info de tu spec OpenAPI.

Resumen

  • SemVer comunica el impacto de cada release con MAJOR.MINOR.PATCH.
  • El changelog documenta qué cambió y por qué en cada versión.
  • Las rupturas se planifican, se anuncian y se superponen con la versión anterior.
