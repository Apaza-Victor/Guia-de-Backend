Caché con ETag y Cache-Control

⚙️ Intermedio 10 min APIs REST Módulo 3 · Diseño

Frescura vs validación

La caché HTTP tiene dos mecanismos gemelos:

  • Expirada (frescura): decide por cuánto sirvo sin preguntar (Cache-Control).
  • Validación: decide saber si sigue igual con una petición ligera (If-None-Match + ETag).

Cache-Control: la política

  • public: cualquier caché intermedia (CDN, proxy) puede servirla.
  • private: solo la caché del cliente final (navegador).
  • max-age=N: N segundos de frescura.
  • no-store: prohibido guardar (datos sensibles).
  • no-cache: se puede guardar, pero pregunta siempre (valida).

ETag y la validación

El ETag es una huella del contenido (hash). Si cambia el recurso, cambia el ETag.

El cliente manda If-None-Match con su ETag; si coincide, 304 sin cuerpo y la caché local sigue valiendo.

Los primos Last-Modified / If-Modified-Since

  • Alternativa basada en fechas: Last-Modified + If-Modified-Since.
  • Más imprescindible que el ETag, pero más fácilmente engañosa (misma fecha, contenido distinto).
  • Si puedes, sirve ETag: es exacto. Los proxies antiguos prefieren fechas; los modernos, hashes.

Estrategia en tus endpoints

  • Catálogos de lectura (~productos): public, max-age=300 con ETag para validar.
  • Datos de usuario: private o no-store si hay datos sensibles.
  • Errores: no-store para que los fallos nunca queden atragantados.
  • Si tu CDN lo soporta, stale-while-revalidate da frescor tras expirar.

Ejercicio

  1. Consulta tu API de práctica dos veces y observa el ETag.
  2. Repite con If-None-Match y verifica el 304.
  3. Diseña la política de caché para cada recurso que ya tienes.

Resumen

  • Cache-Control decide cuánto vive; ETag decide si sigue viva.
  • Validación: 304 sin cuerpo ahorra ancho de banda.
  • No cachees datos personales ni errores sin permiso.
