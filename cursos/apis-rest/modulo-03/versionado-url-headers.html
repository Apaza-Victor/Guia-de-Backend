Versionado: URL vs headers

⚙️ Intermedio 10 min APIs REST Módulo 3 · Diseño

¿Para qué versionar?

Cambiar el contrato (campos, endpoints, semántica) sin romper a los clientes actuales. Versionar = dar tiempo de migración y coraje para evolucionar.

Versionado por URL (el campeón del amor)

  • Ventajas: visible, cachea bien, probar en un terminal es trivial, cada versión coexiste en su propio espacio.
  • Contras: URLs con versión “fea”, difícil de enlazar con nitidez, riesgo de duplicar motores de enrutado.
  • Es la elección más frecuente (GitHub, Stripe, Twilio).

Versionado por cabecera

  • Ventajas: URL limpia, cohesión con la negociación de contenido, versionao del formato de forma elegante.
  • Contras: invisible al ojear en un navegador, rompe caché compartida (hay que usar Vary), más complejo para clientes simples.

Otras variantes

  • Query param: fácil de cachear mal; colisiona con filtros y la caché se complica. Evítalo como versión principal.
  • Cabecera propietaria: X-API-Version: 2 — simple pero no estándar.

Decisión práctica

  • API pública genérica → URL (/api/v1). Corta, legible, nadie la confunde.
  • API interna con contrato negociado por media type → Accept con vendor type.
  • Cualquier opción definida y documentada es mejor que «sin versión pero con sorpresas».

Regla de saneamiento: versiona solo cuando haya cambios rotundos; los cambios aditivos (nuevos campos opcionales) no merecen versión.

Ejercicio

  1. Elige la estrategia de tu tienda y estampa v1 en todas sus URLs.
  2. Escribe el flujo de migración de un cliente de v1 a v2.
  3. Explica cuándo NO cambiarías de versión.

Resumen

  • Versionar da tiempo de migración y coraje.
  • URL: visible y cacheable (la más usada).
  • Header: limpio pero invisible y enredoso para el caché sin Vary.
  • Cambios aditivos no merecen nueva versión.
