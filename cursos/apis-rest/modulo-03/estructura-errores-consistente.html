Estructura de errores consistente

⚙️ Intermedio 10 min APIs REST Módulo 3 · Diseño

El error también es contrato

Un buen error JSON permite a tus clientes programar contra él: mostrar el mensaje, rellenar campos, lanzar reintentos. Errores «cada uno por su lado» condenan tu API a míticos if/else.

Un esquema mínimo y a prueba de balas

  • code: código interno legible (constante para la lógica del cliente).
  • message: frase humana en el idioma negociado.
  • status: el HTTP status code, duplicado en el cuerpo (facilita depurar).
  • trace_id: correlación con tus logs. Sin él, "¿me ayudas?" se vuelve una búsqueda con lupa.

Errores por campo: tu aliado en validaciones

El mismo contorno para todos los 422 del mundo: campos ↔ lista de mensajes.

Estándares útiles del ecosistema

  • RFC 7807 (Problem Details): type, title, detail, instance. Background de Spring y otras. Considéralo como esquema de adopción internacional.
  • OpenAPI error definitions: definidas tus respuestas de error una vez en tus schemas.
  • Si tu equipo ya habla con un formato (Stripe, GitHub lo hacen parecido), hérelo.

Reglas de oro

  1. El status code correcto es obligación, no alquimia.
  2. code estable y documentado; message humano.
  3. Nunca filtres stack traces ni SQL brutos al exterior.
  4. Siempre el mismo contorno: éxito en data(+meta); fracaso en error.
  5. Acompaña el error con un trace_id y regístralo.

Ejercicio

  1. Diseña un esquema de error único para tu tienda.
  2. Crea respuestas de ejemplo para 400, 401, 404, 422 y 503.
  3. Explica qué haría un cliente con tu errors por campo.

Resumen

  • El error es contrato: code + message + status + trace_id.
  • 422 con errors { campo: [mensajes] } para validaciones.
  • Nunca vayas por campo libre: consistencia o ruido.
