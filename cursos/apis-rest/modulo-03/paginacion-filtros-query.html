Paginación y filtros por query

⚙️ Intermedio 10 min APIs REST Módulo 3 · Diseño

El problema de devolverlo todo

Un GET a una colección no debe volcar 2 millones de filas. Paginar significa entregar un trozo firme (una página), con instrucciones claras de cómo pedir la siguiente.

Paginación por página y offset

  • limit (o per_page): cuántos devuelves (con tope duro: 100).
  • page: qué bloque de esos tantos.
  • Alternativa matemática: offset=40 — igual de simple, igual de frágil cuando hay inserciones en mitad de la tabla.
  • Verdad práctica: LIMIT/OFFSET se degrada en tablas enormes.

Paginación por cursor (el arma de las grandes colecciones)

  • El cursor es un marcador opaco (no llamable) que guarda tu posición: «sigue a partir de aquí».
  • Rápido con índices, a prueba de inserciones, sin resaltar por dónde saltar.
  • Lo sirven Stripe, GitHub y X.

Filtros y orden por query

  • Filtros simples: campo=valor.
  • Rangos: _gte, _lte, o helpers desde/hasta explícitos.
  • Orden: sort con el campo, guion para descendente (-precio); múltiples por comas.
  • La lista real de filtros soportados va en tu OpenAPI; el cliente no inventa.

Cotas para no volverte loco

  1. Maximum limit (100 por defecto; revísalo).
  2. Solo campos indexados ordenables/filtrables (o el servidor se ahoga).
  3. Nunca filtras por campos sin índice en grandes tablas.
  4. Documenta el esquema de paginación con un ejemplo visible.

Ejercicio

  1. Diseña la paginación de una lista de 100.000 tickets.
  2. Elige página o cursor y justifica por qué.
  3. Escribe la URL que busca los 10 pedidos recién enviados, ordenados por fecha.

Resumen

  • Nunca vuelques la colección entera.
  • page/limit simple; cursor opaco para escalas grandes.
  • Link header para navegación estándar; filtros y sort por query con límites duros.
