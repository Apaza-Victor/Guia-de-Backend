Testing de endpoints

⚙️ Intermedio 11 min APIs REST Módulo 6 · Calidad y seguridad

¿Por qué testear la API completa?

El test unitario protege piezas; el test de endpoint protege el contrato: enrutado + validación + serialización + la base de datos. Es el test con más retorno de una API.

Qué casos cubrir por cada operación

Ejemplo con supertest (Node)

Validar contra tu propio spec

  • Contrato de contrato: síntomas que el spec está desfasado se detectan en CI.
  • Algunas herramientas (Dredd, Schemathesis, Prism validate) recorren el spec lanzando todos los endpoints contra la API real.

Pitfalls clásicos

  • Testear con la misma DB de producción: usa una de prueba o SQLite aislada.
  • Testear solo el código, no la ruta: invoca el app real con supertest, no la función.
  • Saltarse el orden/determinismo: resetea estado en beforeEach.
  • Nunca testear contra localhost de otro servicio en CI sin docker-compose estable.

Ejercicio

  1. Escribe los 7 casos mínimos del CRUD de productos.
  2. Ejecútalos en tu segundo del proyecto y comprueba el 422.
  3. Añade una validación de contrato de CI (spectral) a tu repo.

Resumen

  • El test de endpoint protege el contrato completo.
  • Implementa los casos felices y los de error (200, 201, 204, 404, 422, 401).
  • Contrasta la API contra tu spec en CI para que no se desfase.
