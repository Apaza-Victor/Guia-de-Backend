Rate limiting y abuso de la API

⚙️ Intermedio 11 min APIs REST Módulo 6 · Calidad y seguridad

El abuso no es una teoría

Bucles con bug, scrapers, credenciales compartidas… Un host sin límite se ahoga con unas pocas peticiones descuidadas. Rate limiting = el semáforo que reparte el ancho de banda con justicia.

¿A qué le pones límite?

  • Por IP: la más simple (proxy, lugar común en oficinas: penaliza).
  • Por API key / usuario: la justa para SaaS: cada cliente su cupo.
  • Por endpoint: el login recibe menos que el catálogo.
  • Combina: IP + key + endpoint es lo típico.

Middleware sencillo (fixed window)

En producción usa backend compartido (Redis) si tienes varias réplicas.

Informa, no castigues en silencio

Clientes decentes leen estas cabeceras y ajustan su cadencia solos.

Cuotas vs rate limiting

  • Rate limit: peticiones por ventana de tiempo (por minuto).
  • Cuota: recursos por período largo (10.000 recl.: /mes, 150 GB transferidos).
  • Ambas se informan con cabeceras o endpoint /usage.

Defensa trás el reverse proxy

  • Nginx/Cloudflare hacen rate limiting sin tocar tu código.
  • Permite listos (IPs internas, monitors tu escalada) y bloquea drones en capa WAF.
  • Nunca limites tu propio health check.

Ejercicio

  1. Monta el rate limiter por IP en tu API local.
  2. Dispara 120 peticiones en un bucle y observa el primer 429.
  3. Añade las cabeceras X‑RateLimit y Retry-After.

Resumen

  • Límites por IP, key y endpoint; combínalos.
  • 429 + Retry-After: el cliente sabrá qué hacer.
  • Cabeceras X‑RateLimit para clientes proactivos.
