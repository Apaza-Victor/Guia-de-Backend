Manejo de errores centralizado

⚙️ Intermedio 10 min APIs REST Módulo 4 · Implementación

El infierno de los try/catch por esquina

Cada controlador repitiendo try/catch, cada uno con un JSON distinto… Eso es un smell de diseño. Lo correcto: un solo lugar captura, traduce y da formato a todas las excepciones.

Middleware de error en Express

Los controladores se voltean: lanzan throw new ApiError(...) y el middleware se encarga. Cero JSON manual repetido.

Flujo del error

  • Logging: guardas trace_id, ruta, método, código y mensaje (ya sin stack si es esperado).
  • Sin fuga: nunca mandes stack traces, SQL o mensajes de driver al cliente.

El dolor de las promesas rechazadas

Errores que preparan el terreno

  • Centraliza también la generación de trace_id (middleware de entrada + helper de logs).
  • Mapea los errores de BD a ApiError (duplicate key → 409, not found → 404) en el repo, no en el controlador.
  • En tu OpenAPI documenta las respuestas de error una sola vez y reutilízalas.

Ejercicio

  1. Implementa tu ApiError y tu middleware de error.
  2. Lanza tres errores distintos desde tus rutas y verifica el JSON.
  3. Añade el envoltorio asyncH y provoca un fallo real para ver el 500 limpio.

Resumen

  • Un solo middleware traduce errores → JSON uniforme.
  • ApiError con status + code (+ campos para 422) en el núcleo.
  • Promesas: envueltas para no perder excepciones.
  • Log con trace_id, sin stack al cliente.
