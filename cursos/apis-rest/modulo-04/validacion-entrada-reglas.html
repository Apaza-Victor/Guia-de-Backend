Validación de entrada y reglas

⚙️ Intermedio 11 min APIs REST Módulo 4 · Implementación

¿Por qué validar si el cliente es amable?

  • Tu usuario de UI no es tu único público: robots, scripts y personas con Postman mandan lo que sea.
  • La base de datos rechazará con errores feos si no lo haces tú con 422 bonitos.
  • Validar pronto = evitar datos corruptos y seguridad más floja.

Regla de seguridad: el nuestro backend no confía jamás. Trust nothing, validate everything.

Qué validar en cada rincón

  • Cuerpo: campos obligatorios, tipos, formatos, valores permitidos.
  • Parámetros de ruta: que el id sea el tipo correcto (entero, UUID…).
  • Query: paginación dentro de límites, filtros válidos.
  • Cabeceras: API keys bien formadas, Accepted content types.

Reglas comunes bien definidas

Normaliza después de validar

  • Recorta espacios: " hola " → "hola".
  • Convierte tipos: números y booleanos, no strings de verdad.
  • Decide valores por defecto (y regístralos).
  • Devuelve la entrada ya limpia al servicio, nunca la cruda.

Lo que NO debe pasar jamás

  • Usar la entrada cruda en consultas SQL: SELECT * FROM x WHERE id=" + req.body.id — inyección clásica.
  • Creer que el frontend «ya filtra»: la validación de UI es UX, no seguridad.
  • Guardar lo que llega sin tipar y sin recortar.

Ejercicio

  1. Define un schema de validación para tu recurso favorito.
  2. Prueba con inputs inválidos: campo vacío, precio en string, clave extra.
  3. Añade una regla de negocio tuya (p. ej. «descuento > 0 y < 100»).

Resumen

  • No confíes: valida cuerpo, ruta, query y cabeceras.
  • Schemas declarativos (+ Zod, Joi, OpenAPI) dan reglas claras.
  • Después de validar: normaliza, tipa y pasa entrada limpia.
