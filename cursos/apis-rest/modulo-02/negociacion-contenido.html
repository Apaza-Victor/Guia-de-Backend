Negociación de contenido

⚙️ Intermedio 10 min APIs REST Módulo 2 · HTTP

El único recurso, mil representaciones

Un solo recurso puede viajar como JSON, XML, CSV, PDF… Negociación de contenido = cliente anuncia su preferencia (Accept) y el servidor sirve la mejor representación posible.

Accept y cabeceras hermanas

  • Accept: tipos MIME; */* pacta cualquier cosa.
  • q (quality): prioridades relativas, 0 a 1.
  • Accept-Language / Accept-Charset / Accept-Encoding: idioma, juego de caracteres y compresión (gzip, brotli).

El servidor decide y anuncia

El servidor elige la mejor representación y confiesa en la respuesta qué y cómo sirvió:

Vary importa mucho: le dice a los proxies y cachés que urls idénticas dan respuestas distintas según Accept. Olvidarlo corrompe la caché.

Cuando no hay acuerdo: 406 y 415

  • 406 Not Acceptable: no puedo servir nada de lo que toleras.
  • 415 Unsupported Media Type: te mandas un cuerpo de formato que rechazo.

¿Negociar o no negociar?

  • API moderna, clientes propios: olvida un JSON fijo y no negocies; es menos cómico documentar.
  • API pública con públicos distintos: sí negocia (JSON + CSV + PDF, lenguaje por cabecera).
  • Alternativa práctica al 406: una página de error 406 sin HTML o responder JSON igualmente explicando.

Ejercicio

  1. Pide un endpoint común con Accept: application/xml y anota el resultado.
  2. Replica la negociación en tu API de práctica con dos formatos.
  3. Añade Vary y explica por qué es imprescindible.

Resumen

  • Negociación: cliente anuncia (Accept), servidor elige y confiesa (Content-Type).
  • 406 = no hay representación compatible; 415 = formato rechazado.
  • Vary protege la caché ante respuestas distintas.
