Métodos HTTP: GET, POST, PUT, PATCH y DELETE

⚙️ Intermedio 10 min APIs REST Módulo 2 · HTTP

Los cinco verbos del día a día

  • GET: leer. Nunca debe tener efectos secundarios.
  • POST: crear (o acción no idempotente). No manda la URL final.
  • PUT: reemplazar la representación completa del recurso.
  • PATCH: cambios parciales: solo los campos que llegan.
  • DELETE: eliminar el recurso.

Idempotencia, la pieza que salva retries

Una petición es idempotente si repetirla N veces produce el mismo efecto que una vez. HTTP garantiza:

  • GET, PUT, DELETE, HEAD, OPTIONS: idempotentes por contrato.
  • POST: no idempotente (dos POST crean dos recursos).
  • PATCH: sin garantía formal; en la práctica muchas APIs lo hacen idempotente.

Consecuencia práctica: si el cliente pierde la conexión y reintenta, un PUT repetido es seguro; un POST repetido duplicará el recurso.

En acción con cURL

Proxies y preflight: el peso de cada verbo

Get y DELETE llegan sin nada más en el cuerpo (o vacío). POST/PUT/PATCH suelen cargar el JSON. Los proxies y firewalls interpretan el método: un POST debe ser explícito si ocurre en contextos restrictivos. En el navegador, métodos no‑simples disparan un preflight OPTIONS; si en tu API ese verbo no está permitido, la petición nunca viaja.

Errores clásicos

  • Usar GET para operaciones que borran o actualizan.
  • Poner toda acción en POST y olvidar PUT/PATCH.
  • Usar POST vs PUT de forma arbitraria: consensua el criterio del equipo y quédate en él.

Ejercicio

  1. Desde cURL ejecuta un GET y un POST contra la API de práctica.
  2. Explica qué pasaría si eliminas con DELETE y reintentas el mismo DELETE.
  3. Diseña el flujo PATCH del carrito de compra de tu tienda imaginaria.

Resumen

  • GET lee, POST crea, PUT reemplaza, PATCH actualiza, DELETE borra.
  • Idempotencia: repetir N veces = mismo efecto. POST no lo es.
  • Los métodos no‑simples viajan con preflight en navegadores.
