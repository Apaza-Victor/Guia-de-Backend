El estilo REST y su historia

⚙️ Intermedio 8 min APIs REST Módulo 1 · Fundamentos

El origen: una tesis de 2000

REST (REpresentational State Transfer) vio la luz en la tesis doctoral de Roy Fielding (2000) sobre los problemas de escalabilidad de la web. No es un estándar oficial, sino un estilo arquitectónico: un conjunto de restricciones que, combinadas, producen sistemas web escalables, simples y con mundos separados entre clientes y servidores.

Las seis restricciones

  1. Cliente‑servidor: separa la interfaz del almacenamiento.
  2. Stateless (sin estado): cada petición carga con todo lo necesario; el servidor no guarda la sesión del cliente.
  3. Cacheable: las respuestas declaran si se pueden cachear (y por cuánto).
  4. Interfaz uniforme: recursos identificados, representaciones, mensajes autodescriptivos e hipermedia.
  5. Sistema por capas: proxies, balanceadores y cachés intermedios deben poder existir sin que el cliente lo note.
  6. Código bajo demanda (opcional): entregar lógica ejecutable al cliente.

REST hoy: el REST práctico

En el día a día, «API REST» se refiere a una web API que:

  • Identifica recursos por URL.
  • Usa los métodos HTTP como verbos.
  • Representa los recursos en JSON.
  • Comunica resultado con status codes.
  • Aplica hipermedia con moderación (links en las respuestas).

Competidores: SOAP y RPC

  • SOAP: XML pesado, contratos WSDL, verbos propios. Robustez empresarial, enorme overhead.
  • RPC: llamar funciones remotas (XML‑RPC, JSON‑RPC, gRPC): «/getUser?id=7». Simple pero ríspido mientras el esquema crece.
  • GraphQL: el cliente pide exactamente la forma (post-2015). Potente, pero con su curva de caché y seguridad.

REST se impuso por simplicidad, legibilidad y aprovechamiento nativo del HTTP que ya cargaba con la escabilidad de toda la web.

Mitos habituales

  • «Si responde JSON, es REST»: no; REST es una filosofía, JSON un formato. Puedes hacer «REST‑ish» en XML.
  • «REST exige verbos mágicos»: los estados y las URIs nomenjan acciones ni verbos en inglés.
  • «Stateless prohíbe cookies»: prohíbe depender de sesiones de servidor, no el envío de credenciales por petición.

Ejercicio

  1. Elige un recurso (películas, turnos, pedidos) y escribe las 6 URIs del patrón.
  2. Explica con tus palabras qué significa «sin estado».
  3. Compara SOAP vs REST y justifica por qué elegirías REST.

Resumen

  • REST nació en la tesis de Fielding (2000) como estilo arquitectónico.
  • Sus 6 restricciones buscan escala, simplicidad y desacoplamiento.
  • El REST práctico: recursos en URL, verbos HTTP, JSON y status codes.
  • Se impuso por su sencillez frente a SOAP y RPC.
