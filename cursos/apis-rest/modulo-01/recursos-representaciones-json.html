Recursos y representaciones con JSON

⚙️ Intermedio 9 min APIs REST Módulo 1 · Fundamentos

Recurso: el sustantivo de tu API

Un recurso es cualquier cosa que tu sistema expone: un producto, un usuario, un pedido. No es «datos» ni «tabla»; es el concepto con su identidad. El recurso vive en el servidor; lo que viaja es su representación.

Identificador único: cada recurso tiene su URL canónica.

Representación ≠ datos

La representación es una foto del recurso en un formato acordado. El mismo recurso se puede representar en JSON, XML o CSV; el cliente elige cuál quiere (negociación de contenido, módulo 2). En REST práctico, JSON es el rey:

Convenciones de formato

  • snake_case en JSON es común en REST (camelCase en otras casas: elige una y mantente firme).
  • Fechas ISO‑8601 con zona horaria: 2026-03-14T10:22:30Z. Nunca marcas locales ni manuscritas.
  • IDs explícitos cuando sean relevantes entre sistemas.
    Ojo: en APIs orientadas a uso externo se prefieren slugs o UUIDs a las claves de base de datos.
  • Envolturas opcionales: data y meta (paginación). Lo importante es ser predecible.
  • null para “sin valor”, no campos desaparecidos… salvo decisión documentada.

Relaciones entre recursos

Hay dos formas de representar “el producto pertenece a un fabricante”:

  • Anidar: cómodo para lecturas en una sola petición, pero duplica datos y complica actualizar.
  • Referenciar con link: magro, navegable, fácil de cachear por separado.
  • Regla práctica: anida cuando la relación es parte de el recurso (una línea de pedido dentro del pedido); referencia cuando es independiente.

Recursos vs acciones

REST modela sustantivos, no verbos. «Enviar email», «activar promoción», «publicar» suelen camuflarse. Cuando no queda otra, una acción se vuelve un sub‑recurso:

Es aceptable si está documentado y nombre sustantivo (no postSendOrder). Pero primero intenta modelarlo como recurso: enviar es, igualmente, “crear un evento de envío”.

Identificar recursos desde tu dominio

  1. Enumera los sustantivos del negocio (usuario, pedido, factura).
  2. Marca los que tienen ciclo de vida propio: esos son recursos.
  3. Marca las relaciones que deben viajar en la misma respuesta.
  4. Revisa los verbos: cada verbo es un no‑recurso que quizá se pueda desvanecer.

Ejercicio

  1. Elige 3 sustantivos de un dominio real y define sus URLs.
  2. Escribe la representación JSON de uno con al menos 5 campos.
  3. Representa una relación entre dos de esos recursos anidada y por link.

Resumen

  • Recurso = sustantivo con identidad; representación = su foto en un formato.
  • JSON convencional: snake_case, ISO‑8601, IDs claros.
  • Relaciones: anida si es parte; referencia con link si es independiente.
  • Modela sustantivos; respalda acciones como sub‑recursos solo si es justo.
