Bloques de construcción

🧠 Experto 10 min System Design Módulo 1 · Fundamentos

Las piezas que se repiten

Existe un puñado de componentes que aparecen en casi todos los sistemas de alto tráfico con el mismo propósito: distribuir carga, acelerar lecturas y desacoplar procesos. Aprenderlos por separado antes de combinarlos es la clave para no inventar arquitecturas de la nada.

Los cinco bloques esenciales son el load balancer, la caché, la cola de mensajes, la CDN y las bases de datos a escala.

Load balancer

Un load balancer reparte las peticiones entrantes entre varias instancias del mismo servicio. Cumple dos fines a la vez: escalabilidad (más nodos = más capacidad) y disponibilidad (si un nodo cae, el reparto ignora su health check y sigue con los demás).

Los algoritmos básicos son round-robin, least connections (al que está menos ocupado) e IP-hash o sticky sessions (mismo cliente, mismo nodo) cuando se necesita afinidad.

# nginx.conf — upstream con 3 réplicas y health check
upstream api {
    least_conn;                     # al nodo con menos conexiones activas
    server 10.0.0.11:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=30s;
    server 10.0.0.13:8080 max_fails=3 fail_timeout=30s;
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://api;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

El load balancer debe ser stateless: que no recuerde nada entre peticiones (excepto la afinidad elegida). Cuantos más LBs y réplicas añadas «detrás», más fácil es escalar sin reescribir código.

Caché

Una caché guarda en memoria datos que se leen mucho y cambian poco, aliviando a la base de datos. El patrón típico es cache-aside: se consulta primero la caché y solo si hay un fallo (miss) se va a la base y se rellena.

Redis, Memcached o las cachés en proceso son las herramientas habituales. El contrato mínimo que hay que dominar es: lectura con miss → relleno → TTL → invalidación al escribir.

import redis

cache = redis.Redis(host="cache", port=6379, decode_responses=True)
TTL_SEGUNDOS = 300

def get_producto(producto_id: int) -> dict:
    clave = f"producto:{producto_id}"
    valor = cache.get(clave)
    if valor is not None:
        return {"origen": "cache", "datos": valor}

    # cache miss → leer de la base de datos (simulado)
    datos = consultar_bd(producto_id)
    cache.setex(clave, TTL_SEGUNDOS, datos)
    return {"origen": "bd", "datos": datos}

def invalidar_producto(producto_id: int) -> None:
    cache.delete(f"producto:{producto_id}")

def consultar_bd(producto_id: int) -> str:
    return f"{{'id': {producto_id}, 'nombre': 'Producto {producto_id}'}}"

La caché mejora la latencia (milisegundos en vez de decenas) y multiplica el QPS efectivo de lecturas. Su precio: datos levemente desactualizados y una pieza más que puede fallar o desincronizarse.

Colas de mensajes

Una cola desacopla al productor del consumidor: el que recibe un trabajo no espera la respuesta de su procesamiento. Es el bloque preferido para tareas pesadas o lentas: enviar correos, generar imágenes, actualizar índices de búsqueda.

  • Desacoplamiento: la API responde al instante y el trabajo continúa en segundo plano.
  • Amortiguación (backpressure): si el consumidor va lento, los mensajes se acumulan ordenadamente.
  • Garantías: los mensajes se mantienen hasta ser reconocidos (ACK), tolerando caídas de nodos.

El cuerpo de un mensaje típico es un JSON con el tipo de trabajo y sus datos; la cola añade metadatos de enrutamiento, prioridad y reintentos:

{
  "tipo": "enviar_email",
  "payload": {
    "destinatario": "ana@correo.com",
    "plantilla": "bienvenida",
    "variables": { "nombre": "Ana" }
  },
  "correlacion": "7f3c2a11",
  "idempotencia": "evt_20260921_00142",
  "prioridad": 5,
  "reintentos": 0
}

Elegir cola cuando el procesamiento tarda más que la paciencia del usuario, o cuando quieres que un pico de tráfico no tumber al servicio que procesa.

CDN

Una CDN replica contenido estático (imágenes, CSS, JS, videos) en servidores ubicados cerca del usuario. El cliente que en Bogotá carga la página no viaja al centro de datos de Virginia: descarga desde un nodo de borde cercano.

# Ejemplo: mover estáticos a una CDN y liberar el origen
# Antes: el usuario descarga 300 KB desde el origen cada vez.
curl -s -o /dev/null -w "origen: %{time_total}s\n" \
  https://api.miservidor.com/static/app.css

# Después: la CDN sirve el archivo desde el borde con Cache-Control largo.
curl -s -o /dev/null -w "cdn: %{time_total}s\n" \
  https://cdn.miservidor.com/static/app.css

Como viste en las estimaciones, los estáticos suelen dominar el ancho de banda. La CDN es la forma más económica de absorber ese tráfico: mantiene una copia, define un TTL de cache y el origen solo se llama en el primer acceso o al invalidar.

Bases de datos a escala

La base de datos es el bloque más difícil de escalar porque guarda el estado. Las estrategias básicas, en orden de complejidad creciente:

  • Optimizar el motor: índices bien diseñados y consultas que los usan.
  • Caché por delante: las lecturas repetidas no llegan al disco.
  • Réplicas de lectura: una primaria recibe escrituras; varias réplicas atienden lecturas.
  • Particionamiento (sharding): cada shard guarda un subconjunto de los datos; la capacidad total se multiplica por el número de shards.

La elección relacional vs NoSQL se resume en una pregunta: ¿necesito transacciones ACID fuertes y consultas ad-hoc (relacional), o flexibilidad de esquema y escala horizontal barata (NoSQL)? No hay motor «mejor»: hay motor adecuado al acceso de datos.

Cómo se combinan

El flujo canónico de un sistema a escala se lee así: el usuario entra a una CDN para los estáticos, un load balancer reparte entre réplicas de la API, la API consulta la caché antes que la base, las tareas pesadas van por una cola y la base de datos se alivia con réplicas y particionamiento. Cada bloque se añadió porque un requisito medible lo pedía.

Ejercicio

  1. Para un sistema con 50.000 QPS de lectura y 500 QPS de escritura, propón dónde colocarías: caché, réplicas de lectura y cola. Justifica cada uno.
  2. Escribe el flujo de una petición de lectura con cache-aside (incluye qué pasa si la caché se cae) usando el código de la sección de caché.
  3. Identifica cuál de los cinco bloques NO añadirías en una aplicación pequeña (menos de 1.000 usuarios) y explica por qué.

Resumen

  • Load balancer: reparte tráfico y elimina puntos únicos de fallo; debe ser stateless.
  • Caché: acelera lecturas y alivia la base; el patrón base es cache-aside con TTL e invalidación.
  • Colas: desacoplan trabajo lento y dan backpressure y persistencia al trabajo pendiente.
  • CDN: mueve los estáticos al borde y reduce el ancho de banda del origen.
  • Bases de datos: escalan con índices, caché, réplicas de lectura y finalmente particionamiento.
  • Cada bloque se justifica con un requisito y un número: si no hay número, quizá no hace falta.
