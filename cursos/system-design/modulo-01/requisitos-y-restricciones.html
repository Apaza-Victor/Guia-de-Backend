Requisitos y restricciones

🧠 Experto 9 min System Design Módulo 1 · Fundamentos

Por qué empezar por los requisitos

El error más caro en el diseño de sistemas es resolver el problema equivocado. Antes de elegir una base de datos, un broker o un patrón de caching, hay que responder dos preguntas en voz alta: ¿qué debe hacer el sistema? y ¿con qué garantías?.

En una entrevista o en un proyecto real, el primer bloque de la sesión se dedica a esto. Es la fase donde el diseñador deja de escuchar y confirma: fragmenta el problema, define el alcance y elimina suposiciones silenciosas.

Un buen ejercicio mental: si dos equipos leen el mismo enunciado y construyen sistemas distintos, la diferencia casi siempre nació en los requisitos que interpretaron de forma distinta.

Requisitos funcionales

Los requisitos funcionales describen qué hace el sistema: las acciones que los usuarios pueden ejecutar y los resultados esperables. Son fáciles de escribir como casos de uso.

Tomemos como ejemplo un acortador de URLs:

  • El usuario pega una URL larga y el sistema devuelve una corta.
  • Alguien abre la URL corta y es redirigido a la original.
  • El usuario opcionalmente define una clave personalizada.
  • La URL corta tiene una fecha de expiración (opcional).
  • Se registran métricas básicas del enlace (clics por día).

Aquí es donde también se define qué no está en alcance: editar URLs, cuentas de usuario, análisis avanzado. Delimitar el universo evita que el diseño explote en complejidad.

from dataclasses import dataclass, field

@dataclass
class RequisitosFuncionales:
    """Casos de uso mínimos del sistema. Nada que no esté aquí se diseña."""
    crear_url_corta: bool = True
    redirigir_por_url_corta: bool = True
    clave_personalizada: bool = True
    expiracion_opcional: bool = True
    metricas_basicas_de_clics: bool = True
    editar_urls: bool = False          # fuera de alcance
    cuentas_de_usuario: bool = False   # fuera de alcance
    analytics_avanzado: bool = False   # fuera de alcance

    def en_alcance(self) -> list:
        return [campo for campo, activo in self.__dict__.items() if activo]

req = RequisitosFuncionales()
print("En alcance:", req.en_alcance())

Requisitos no funcionales (NFR)

Los requisitos no funcionales describen cómo debe comportarse el sistema. Son los que empujan el diseño hacia la escala, la redundancia y el caching.

  • Latencia: p50 de la reescritura de una URL por debajo de 100 ms y p95 por debajo de 300 ms.
  • Disponibilidad: objetivo del 99.9% (aproximadamente 8.7 horas de caída al año).
  • Consistencia: después de crear una URL, ¿es aceptable que tarde unos segundos en verse en todas las regiones? Normalmente sí.
  • Durabilidad: si un nodo se apaga, la URL no se pierde.
  • Capacidad: soportar N usuarios y M peticiones por segundo en el pico.
  • Seguridad y privacidad: cifrado en tránsito, protección de datos personales.

Muchos NFR se cuantifican con SLOs (objetivos de nivel de servicio): la métrica, el umbral y la ventana de tiempo en que debe cumplirse. Así los vuelves verificables en producción:

objetivos:
  - nombre: latencia_crear_url
    metrica: porcentaje_p95
    umbral_ms: 300
    ventana: 30d
    objetivo: 99.0
  - nombre: disponibilidad_api
    metrica: uptime
    umbral: 99.9
    ventana: 30d
    objetivo: 99.9
  - nombre: durabilidad_urls
    metrica: registros_persistidos
    umbral: 99.999
    ventana: 1d
    objetivo: 99.999

Cuando un requisito no tiene número, no es un requisito: es una opinión. «El sistema debe ser rápido» no se diseña; «p95 de 300 ms» sí.

Restricciones y supuestos

Las restricciones son límites duros que no podemos mover: presupuesto, capacitor de equipo, obligaciones legales, zonas geográficas, stack heredado. Los supuestos son estimaciones razonables que aceptamos como punto de partida y que luego verificamos con las estimaciones de capacidad.

Ejemplos de restricciones típicas:

  • Debe correr en servidores propios en una región concreta.
  • Presupuesto de 4 nodos para producción.
  • El equipo ya opera PostgreSQL y no puede agregar otro motor el primer año.
  • Los datos de usuarios en Europa requieren residir en la UE (GDPR).

Ejemplos de supuestos razonables:

  • 10 millones de usuarios registrados, 2 millones activos al día.
  • Cada usuario crea 1 URL por semana en promedio.
  • Cada URL recibe 10 visitas al día en promedio.

Los supuestos se declaran explícitamente porque sobre ellos se construyen las estimaciones, y las estimaciones sobre las decisiones de capacidad. Si el supuesto cambia, el tamaño de las máquinas cambia con él.

{
  "restricciones": {
    "regiones": ["us-east-1"],
    "max_nodos": 4,
    "motor_db": "postgresql",
    "cumplimiento": "gdpr"
  },
  "supuestos": {
    "usuarios_registrados": 10000000,
    "usuarios_activos_diarios": 2000000,
    "urls_por_usuario_semana": 1,
    "visitas_por_url_dia": 10,
    "ratio_lectura_escritura": "100:1"
  }
}

De requisitos a decisiones

Una vez clavados los requisitos, cada decisión de diseño debería poder justificarse apuntando a uno: «aumento réplicas de la base para cumplir con el p95», «agrego caché para que las lecturas no toquen la base», «uso una cola para que el envío de correos no bloquee la respuesta». Si una decisión no responde a un requisito, probablemente es complejidad innecesaria.

También es momento de detectar conflictos: alta latencia y consistencia global fuerte se pelean; disponibilidad del 99.99% y presupuesto de 2 máquinas también. El diseñador no los elimina: los pone sobre la mesa y propone el equilibrio para que el dueño del producto decida.

Ejercicio

  1. Elige un sistema conocido (una red social, un sistema de tickets, una pasarela de pagos) y escribe 5 requisitos funcionales y 5 no funcionales para él.
  2. Convierte cada NFR en un objetivo comprobable con métrica, umbral y ventana (formato de los YAML de arriba).
  3. Escribe 3 restricciones y 3 supuestos. Marca qué decisión de diseño podría cambiar si uno de tus supuestos se multiplicara por 10.

Resumen

  • Los requisitos funcionales describen qué hace el sistema; los no funcionales, con qué garantías.
  • Un NFR sin número no es un requisito: hay que cuantificarlo y convertirlo en un objetivo verificable (SLO).
  • Las restricciones son límites duros; los supuestos son estimaciones que se declaran y luego se verifican.
  • Cada decisión de diseño debe poder justificarse apuntando a un requisito concreto.
  • Los conflictos entre NFR se resuelven explicitando trade-offs, no ocultándolos.
