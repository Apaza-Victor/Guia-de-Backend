Modelado de datos

🧠 Experto 9 min System Design Módulo 1 · Fundamentos

El modelo es el diseño

En system design, el modelo de datos es donde las promesas del diseño se vuelven concretas. Las decisiones de base de datos y particionamiento dependen de cómo se leen y escriben los datos: qué consultas son hot, qué datos se agregan juntos y cuánto crece cada colección.

La pregunta guía es siempre la misma: ¿cuál es el acceso principal a estos datos y con qué patrón de lectura/escritura? La respuesta define si modelamos relacional, como documentos o como clave-valor.

Entidades y relaciones

Primero se listan las entidades y sus cardinalidades. Tomemos un acortador de URLs con usuarios:

  • Usuario → crea → muchas URL corta (1:N).
  • URL corta → genera → muchas Visita (1:N, eventos).
  • URL corta puede tener una analítica diaria agregada (1:1 derivado).

Estas relaciones se pueden modelar de forma relacional (tablas con llaves foráneas) o como documentos anidados si el acceso lee la entidad completa de una vez. En un modelo orientado a documentos, una URL con sus contadores recientes podría tratarse como un solo documento:

{
  "clave": "abC2xY",
  "url_original": "https://primerpaso.dev/blog/system-design-parte-3",
  "usuario_id": "usr_8821",
  "creado_en": "2026-09-20T14:03:00Z",
  "expira_en": null,
  "contador": {
    "clic_total": 1523,
    "clic_por_dia": {
      "2026-09-19": 311,
      "2026-09-20": 402,
      "2026-09-21": 375
    }
  }
}

Obseservar el mismo dato en una tabla relacional normalizada implicaría tres tablas y un JOIN por cada vista. El documento «desnormaliza» el contador dentro de la URL porque ese es exactamente el acceso que necesita el producto.

Redundancia y desnormalización

En bases relacionales, la normalización elimina la duplicación de datos; a escala, los JOINs multiplican la carga y desnormalizar (repetir datos calculados a propósito) se vuelve rentable. La regla es: repite el dato en el punto de lectura si eso elimina un JOIN por petición, siempre que puedas mantenerlo actualizado al escribir.

Ejemplos clásicos de desnormalización:

  • En el perfil se muestra el nombre del autor dentro de cada post (aunque el autor tenga su propia tabla).
  • El contador de likes se guarda en el post y no se calcula contando registros de la tabla de likes.
  • En el feed, el post ya trae la foto del autor para no resolverla en cada card.

El precio es la complejidad de mantener copias sincronizadas: se paga con eventos y procesos de reaprobando periódico. Si el dato nunca se consulta junto, no lo desnormalices.

Elegir las claves

La clave define cómo se busca un registro y, en bases distribuidas, en cuál partición vive. Tres estrategias habituales:

  • Clave natural: ya existe en el dominio (email, documento). Simple, pero cambia y puede ser larga.
  • UUID: globalmente única y generada sin coordinación; larga y dispersa en índices.
  • Clave secuencial / ID distribuible: corta y eficiente, pero requiere coordinar la generación (visto en el URL shortener).

Para sharding, la clave de partición debe elegirse según el acceso dominante. Si la actividad se lee por usuario, particionar por usuario_id mantiene todos sus datos juntos y cada reposo lee un solo shard.

import hashlib

NUM_SHARDS = 16

def shard_de(clave_entidad: str) -> int:
    """Asigna un shard por hash consistente de la clave de partición."""
    digest = hashlib.sha256(clave_entidad.encode("utf-8")).hexdigest()
    return int(digest[:8], 16) % NUM_SHARDS

def guardar_url(url: dict) -> str:
    shard = shard_de(url["usuario_id"])
    bd = conexiones[shard]          # pool por shard
    bd.insert("urls", url)
    return f"shard://{shard}"

conexiones = {i: None for i in range(NUM_SHARDS)}  # pools reales

url = {"usuario_id": "usr_8821", "clave": "abC2xY"}
print("Se escribe en:", guardar_url(url))

Tener todos los datos de un usuario en el mismo shard es lo que permite leer su historial completo con una sola consulta, en lugar de porcionarlo entre 16 servidores.

Particionamiento a escala

Hay dos niveles distintos de particionamiento:

  • Particionado lógico: separar tablas grandes (varias tablas por clave, ej. visitas_2026_09), útil para retención por tiempo.
  • Sharding físico: repartir la misma tabla entre múltiples servidores, eligiendo una clave de partición.

Cada estrategia tiene su coste de operación: los shards por rango permiten barridos eficientes por fecha, pero concentran las escrituras en un solo nodo «caliente»; por hash distribuyen uniforme pero rompen los rangos. Por eso la decisión depende de cómo crece tu dato caliente.

Y una advertencia recurrente: los índices no sirven si son grandes y la consulta es un scan. Antes de hacer sharding, verificar que el índice para el acceso principal ya se construyó. La mayoría de los desastres de rendimiento se arreglan con un índice, no con más máquinas.

Ejercicio

  1. Modela las entidades de un chat: Conversación, Mensaje y Participante. Escribe las cardinalidades y cuál usarías como clave de partición y por qué.
  2. Identifica un dato que desnormalizarías en una red social (por ejemplo, el nombre del autor en cada post) y explica cómo lo mantendrías actualizado si el usuario cambia su nombre.
  3. Con el script de sharding de arriba, calcula en qué shard caerían tres usuarios distintos y comprueba que se reparten de forma más o menos uniforme.

Resumen

  • El modelo de datos se define por los patrones de acceso, no por una teoría abstracta de normalización.
  • Entidades, cardinalidades y agregados se modelan antes de escoger motor relacional o NoSQL.
  • La desnormalización elimina JOINs calientes a costa de mantener copias sincronizadas.
  • La clave de partición se elige según el acceso dominante (casi siempre «por usuario»).
  • Se particiona primero por lógica y tiempo, y solo después físicamente, y siempre después de agotar los índices.
