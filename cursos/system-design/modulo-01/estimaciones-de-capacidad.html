Estimaciones de capacidad

🧠 Experto 10 min System Design Módulo 1 · Fundamentos

Estimar con orden de magnitud

No necesitas una hoja de cálculo milimétrica: necesitas números con un orden de magnitud correcto. Saber si el QPS es 100, 1.000 o 100.000 cambia por completo el diseño (una sola API basta, o hace falta un clúster). Saber si necesitamos gigabytes o petabytes cambia la elección del almacenamiento.

Este estilo de cálculo, llamado back-of-the-envelope (aritmética de servilleta), parte siempre de los supuestos declarados en los requisitos y realiza multiplicaciones simples con números redondos.

  • 1 día = 105 segundos (86.400 es un buen redondeo).
  • Una petición promedio dura entre 20 y 50 ms en una API típica.
  • Un servidor de aplicación medio maneja cientos de QPS; una API con caché, miles.
  • Las potencias de 1024: 1 KB = 210, 1 MB = 220, 1 GB = 230.

Calcular QPS

El QPS (queries per second) es la métrica reina para dimensionar el plano de aplicación. Se obtiene encadenando supuestos: usuarios activos por día × peticiones por usuario ÷ segundos por día, y luego se aplica un factor de pico.

Supongamos un servicio con 10 millones de usuarios registrados, 2 millones activos diarios, y cada uno genera 60 peticiones al día (una mezcla de lecturas y escrituras):

SEGUNDOS_POR_DIA = 86400

def qps_promedio(usuarios_activos_diarios, peticiones_por_usuario_dia):
    total_diario = usuarios_activos_diarios * peticiones_por_usuario_dia
    promedio = total_diario / SEGUNDOS_POR_DIA
    return total_diario, promedio

DAU = 2_000_000
REQS_POR_USUARIO = 60

total_diario, promedio = qps_promedio(DAU, REQS_POR_USUARIO)
print(f"Total diario: {total_diario:,} peticiones")
print(f"QPS promedio: {promedio:.0f}")

# El tráfico no es uniforme: el pico suele ser 2-3x el promedio.
FACTOR_PICO = 3
print(f"QPS pico (x{FACTOR_PICO}): {promedio * FACTOR_PICO:.0f}")

Resultado: 120 millones de peticiones al día, ≈1.389 QPS promedio y ≈4.167 QPS en pico. Con ese número ya podemos hablar de cuántos nodos de API y si la base de datos necesita caché o réplicas.

Regla práctica: una sola base de datos con réplica de lectura aguanta hasta unas pocas miles de QPS de lecturas si están cacheadas; por encima se necesita fragmentar o multiplicar réplicas.

Estimar almacenamiento

El almacenamiento se calcula como tasa de escritura × tamaño del registro × retención. Hay que incluir overhead: índices, metadatos y el factor de replicación si el dato se guarda varias veces.

Continuemos con el acortador de URLs: 2 millones de usuarios activos, cada uno crea 1 URL por semana. Cada registro pesa ~500 bytes (URL original, clave corta, timestamps, métricas).

DIAS_SEMANA = 7
BYTES_POR_KB = 1024
KB_POR_MB = 1024
MB_POR_GB = 1024
GB_POR_TB = 1024

def a_humanos(bytes_):
    for unidad in ["B", "KB", "MB", "GB", "TB", "PB"]:
        if bytes_ < 1024:
            return f"{bytes_:.1f} {unidad}"
        bytes_ /= 1024
    return f"{bytes_:.1f} EB"

DAU = 2_000_000
urls_por_semana = DAU / DIAS_SEMANA          # escrituras de URLs por día
tamano_registro = 500                        # bytes por registro
retencion_anios = 5
dias_en_un_anio = 365

escrituras_dia = urls_por_semana
bytes_dia = escrituras_dia * tamano_registro
total_bytes = bytes_dia * dias_en_un_anio * retencion_anios

print(f"Escrituras por día: {escrituras_dia:,.0f}")
print(f"Crecimiento diario: {a_humanos(bytes_dia)}")
print(f"Total 5 años (raw): {a_humanos(total_bytes)}")

# En producción se replica al menos 2 veces y hay índices (~20% overhead)
total_con_replicas = total_bytes * 2 * 1.2
print(f"Con réplicas x2 y overhead: {a_humanos(total_con_replicas)}")

Con esos números el equipo decide que una Postgres clásica alcanza de sobra, sin necesidad de sistemas distribuidos de almacenamiento. Si los bytes hubieran dado petabytes, la conversación sería otra.

Estimar ancho de banda

El ancho de banda de salida se estima multiplicando el QPS por el tamaño promedio de la respuesta. Importa para dimensionar el tráfico de red y para justificar una CDN cuando los estáticos dominan.

# Respuesta promedio de la API: 2 KB de JSON + 300 KB de assets cuando hay página
json_kb = 2
assets_kb = 300

# De los 60 req/usuario/día, supongamos 50 son de API y 10 cargan assets
qps_api = 2_000_000 * 50 / 86400
qps_assets = 2_000_000 * 10 / 86400

mbps_json = qps_api * json_kb * 8 / 1000         # bits, no bytes
mbps_assets = qps_assets * assets_kb * 8 / 1000

print(f"QPS API:   {qps_api:.0f} → ~{mbps_json:.0f} Mbps")
print(f"QPS assets:{qps_assets:.0f} → ~{mbps_assets:.1f} Gbps")
print("Conclusión: los assets dominan; una CDN lo mueve al borde.")

Este resultado es muy informativo: mover los estáticos a una CDN elimina ~1 Gbps de tráfico hacia el propio clúster y suele ser más barato en total.

Cómo presentar las estimaciones

Lo importante no es la precisión sino la cadena de razonamiento. En una entrevista o revisión de diseño conviene terminar con un mini panel donde se lean los resultados de un vistazo:

{
  "estimacion": {
    "usuarios_activos_diarios": 2000000,
    "peticiones_totales_dia": 120000000,
    "qps_promedio": 1389,
    "qps_pico_estimado": 4167,
    "escrituras_por_dia": 285714,
    "almacenamiento_5_anios": "6.1 TB",
    "ancho_de_banda": {
      "api": "100 Mbps",
      "assets": "1.1 Gbps",
      "accion": "mover assets a CDN"
    }
  }
}

Y siempre cierra con la frase clave: «si estos supuestos se multiplican por diez, ¿qué cambia?». Eso demuestra que entendiste qué decisiones dependen de cada número.

Ejercicio

  1. Toma los scripts de esta lección y cámbialos a un caso real: una red social con 50 millones de usuarios activos y 20 peticiones por usuario al día. ¿Qué QPS promedio y pico obtienes?
  2. Si cada post pesa 1 KB y cada usuario publica 0.5 posts al día, calcula el almacenamiento a 3 años con factor de réplica 2.
  3. Escribe un párrafo que explique qué decisión de diseño cambiarías si el pico resultara 10 veces el promedio (por ejemplo, un evento viral).

Resumen

  • Las estimaciones buscan orden de magnitud, no precisión fina; usan números redondos y potencias de 1024.
  • QPS = (usuarios activos × peticiones por usuario) ÷ segundos del día, con un factor de pico de 2–3x.
  • Almacenamiento = tasa de escritura × tamaño del registro × retención × factor de réplica e overhead.
  • Ancho de banda = QPS × tamaño promedio de respuesta; si los estáticos dominan, la CDN es la respuesta.
  • Siempre se presenta la cadena de razonamiento y qué cambiaría si los supuestos varían.
