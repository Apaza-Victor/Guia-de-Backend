¿Qué es system design?

🧠 Experto 8 min System Design Módulo 1 · Fundamentos

Introducción

Un sistema pequeño funciona de una manera casi intuitiva: una API, una base de datos y listo. El problema aparece cuando hay millones de usuarios: la API se satura, la base de datos se convierte en el cuello de botella, una falla en un componente tumba todo y cada nuevo cambio requiere tocar piezas que ya no se pueden tocar a la ligera.

System design es la disciplina de diseñar la arquitectura de un sistema a escala: decidir qué componentes lo forman, cómo se conectan, dónde vive cada dato, cómo se garantiza la disponibilidad y cómo se escala ante el crecimiento. No se trata de escribir el código de cada función, sino de elegir las piezas grandes y las reglas que las unen.

Los atributos de un buen diseño

Cuando diseñamos, lo hacemos para cumplir una lista de atributos de calidad. Todos compiten entre sí: mejorar uno suele empeorar otro.

  • Escalabilidad: capacidad de soportar más usuarios o más datos añadiendo recursos.
  • Disponibilidad: el porcentaje del tiempo en que el sistema responde correctamente (los famosos «nueves»: 99.9%, 99.99%).
  • Rendimiento: latencia y throughput. Cuánto tarda una petición y cuántas peticiones se atienden por segundo.
  • Fiabilidad: el sistema sigue funcionando aunque algunos componentes fallen. Sin puntos únicos de fallo.
  • Consistencia: los usuarios ven los mismos datos sin importar desde dónde o cuándo consulten.
  • Mantenibilidad: el costo de agregar features o corregir bugs sigue siendo razonable a lo largo del tiempo.

Los dos primeros, escalabilidad y disponibilidad, son los que más aparecen en el diseño de sistemas. Pero nunca se deciden solos: detrás siempre hay un balance de costos.

El proceso de diseño

Un diseño serio no empieza dibujando cajas. Sigue un proceso que se repite en cada problema y que será tu esqueleto en este curso:

  1. Requisitos: qué debe hacer el sistema (funcional) y con qué garantías (no funcional).
  2. Estimaciones: cuántos usuarios, cuántas peticiones por segundo, cuánta data se guarda.
  3. Componentes: elegir los bloques de construcción: load balancers, cachés, colas, bases de datos.
  4. Datos: modelar entidades, relaciones y particionamiento.
  5. Trade-offs: explicar qué ganamos y qué pagamos con cada decisión.

Lo común en system design es explicar el proceso y sus decisiones, más que llegar a un dibujo «perfecto». Un diagrama sin justificación vale poco.

Ejemplo: la anatomía de un sistema

Imagina una aplicación de productos mínima a escala. Los componentes clásicos se pueden describir con un archivo de infraestructura. Este es el tipo de «receta» que un diseñador razona antes de comprar máquinas:

version: "3.9"
services:
  lb:
    image: nginx:1.25
    ports: ["80:80"]
    volumes: ["./nginx.conf:/etc/nginx/nginx.conf:ro"]
  api:
    # 3 réplicas detrás del balanceador para escalar y quitar puntos únicos
    image: mi-api:1.4.0
    deploy:
      replicas: 3
      resources:
        limits: { cpus: "1", memory: 1G }
  cache:
    image: redis:7-alpine
    command: ["redis-server", "--save", "60", "1000"]
  db:
    image: postgres:16
    environment:
      POSTGRES_DB: productos
      POSTGRES_PASSWORD: ${PG_PASSWORD}
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata:

Fíjate en el patrón: un load balancer al frente, réplicas de la API, una caché para descomprimir la base de datos y una base de datos con su almacenamiento persistente. Esa misma estructura se redibuja casi igual en los millones de usuarios, solo que cada pieza se multiplica por muchos nodos.

System design vs arquitectura de software

Ambos términos se solapan, pero tienen énfasis distintos:

  • Arquitectura de software: se centra en la estructura interna y las decisiones de diseño de bajo/alto nivel: módulos, capas, principios SOLID, deuda técnica.
  • System design: se centra en el sistema completo a escala: componentes desplegados, red, distribución, replicación, fallas de máquinas y operación.

En la práctica, un arquitecto de sistemas decide qué piezas existen y dónde se ejecutan; el diseño a nivel de código llena el interior de cada pieza. En las entrevistas técnicas de empresas grandes, el «system design round» evalúa exactamente la visión de conjunto que verás en este curso.

Por qué importa el system design

Los sistemas bien diseñados escalan cambiando configuración o agregando nodos; los mal diseñados se rompen en formas costosas: podrían perder datos, quedarse sin memoria en el pico de tráfico o exigir reescribir la parte central para crecer. Un buen diseño anticipa el crecimiento y la falla como parte normal de la operación.

Además, es una habilidad de comunicación: el diseñador debe traducir números («10.000 peticiones por segundo») en decisiones concretas («tres nodos de API, caché Redis y réplica de lectura») y explicar los trade-offs con claridad.

Ejercicio

  1. Elige una aplicación que uses a diario (un delivery, una red social, una app de mensajería). Lista al menos cinco componentes que crees que la forman: frontend, API, base de datos, caché, cola, CDN.
  2. Para cada componente, escribe un atributo de calidad que deba garantizar. Por ejemplo: «el historial de mensajes debe ser duradero» (fiabilidad).
  3. Dibuja el flujo de una acción simple (un usuario publica algo) pasando por los componentes que listaste.

Resumen

  • System design es diseñar la arquitectura de un sistema a escala: componentes, conexiones y garantías.
  • Los atributos de calidad (escalabilidad, disponibilidad, rendimiento, fiabilidad, consistencia, mantenibilidad) compiten entre sí.
  • El proceso es: requisitos → estimaciones → componentes → datos → trade-offs.
  • Los bloques típicos son load balancer, réplicas de servicios, caché y base de datos con persistencia.
  • Se diferencia de la arquitectura de software en el énfasis sobre la escala, la red y la operación.
