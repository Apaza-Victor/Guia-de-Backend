Load balancing a escala

🧠 Experto 11 min System Design / Arquitectura de Sistemas Módulo 4 · Escalabilidad y distribución

Introducción

El load balancer (LB) es el portero de toda arquitectura que escala horizontal: recibe cada petición y decide a qué nodo sano va. Si está mal configurado, cualquier pico se convierte en una cascada de 5xx.

Aquí verás los algoritmos de reparto, las diferencias entre L4 y L7, y cómo la salud de los nodos (health checks) es la mitad del trabajo real.

Definición

Un load balancer distribuye las peticiones entrantes entre un pool de servidores según un algoritmo (round-robin, least-conn, hash de IP/URL) y retira del pool a los nodos que fallan los health checks.

Por qué importa. Sin balancer, un nodo recibe todo y el resto está ocioso; con un balancer mal configurado, los nodos sobrecargados reciben carga igual. El reparto correcto mejora latencia, disponibilidad y aprovechamiento.

Cuándo usarlo. Úsalo siempre que haya más de un nodo de un rol, y en más de una capa: edge (DNS/L4), servicio (L7) y hasta dentro del cluster (service mesh).

Conceptos clave

  • L4 balancea por TCP/UDP (IP y puerto) sin mirar el contenido; L7 mira HTTP: rutas, headers y cookies.
  • Round-robin reparte en ciclo; least-conn envía a quien menos conexiones abiertas tiene; hash de IP mantiene afinidad.
  • El health check decide quién está sano: TCP, HTTP /healthz o checks de dependencias reales.
  • Sticky sessions fijan el nodo del cliente por cookie: útil para sesiones, rompe el balanceo natural.
  • El LB es un punto único: hay que balancear el propio balancer (VIP + keepalived, DNS, o LB gestionado multi-AZ).

Ejemplo real

Un chat de 300k tareas al día balanceaba solo por round-robin y los nodos con sesiones largas (WebSocket) se morían de hambre, mientras el LB 'repartía' equitativamente conexiones de peso muy distinto. Se cambió a least_conn en la capa de sockets y las máquinas se nivelaron de 92 % a 55 % de CPU.

  • Poner timeout y max_fails en cada upstream para retirar nodos degradados.
  • Separar WebSocket y HTTP en pools porque su perfil de conexión es distinto.
  • Balancear por hash de cliente (IP o user_id) cuando la cache local por nodo lo justifique.
  • Monitorizar el reparto real: latencia y RPS por nodo, no solo del pool completo.

La afinidad por hash rompe el balanceo perfecto, pero para conexiones persistentes es el coste correcto.

Explicación

  • El algoritmo se elige por el perfil de la conexión: peticiones cortas a least_conn no les importa; sesiones largas lo necesitan.
  • El health check debe reflejar la salud real: un /healthz que no comprueba la BBDD deja entrar a nodos 'vivos' que fallan todo.
  • El propio LB se escala: en la nube usa el gestionado (multi-AZ), on-premise con VIP y keepalived.
  • Las conexiones rápidas de WebSocket hacen que round-robin mida mal la carga real del nodo.
  • La telemetría por nodo destapa los desequilibrios que el promedio del pool esconde.

Errores comunes

  • Health check de TCP puro que no detecta que la app está en fail loop.
  • Timeout cortísimo que escala cualquier lentitud del backend a porcentaje de error del front.
  • Sticky sessions activadas sin necesidad, impidiendo el rebalanceo natural del pool.

Buenas prácticas

  • Diseña /healthz para que compruebe las dependencias críticas con timeout corto propio.
  • Configura failover con proxy_next_upstream para errores 5xx y timeouts.
  • Balancea el balancer: gestionado multi-AZ, o VIP con keepalived en dos nodos.
  • Mide por nodo, no solo por pool: ahí viven los desequilibrios.

Ejercicio

  1. Diseña el balanceo de una API con 4 nodos y una regla de failover a 5xx.
  2. Elige algoritmo para chat (sesiones largas) y para una web estática.
  3. Escribe el health check de un servicio que depende de BBDD y caché.

Resumen

  • El LB reparte a nodos sanos según el perfil de conexión, no solo en ciclo.
  • Los health checks reales son tan importantes como el algoritmo de reparto.
  • Balancea el balancer y monitoriza el reparto por nodo.
