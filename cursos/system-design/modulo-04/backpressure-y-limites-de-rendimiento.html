Backpressure y límites de rendimiento

🧠 Experto 10 min System Design / Arquitectura de Sistemas Módulo 4 · Escalabilidad y distribución

Introducción

Todo sistema tiene un techo de rendimiento, y el tráfico no respeta techos. Cuando la demanda supera la capacidad, pasa una de dos: el sistema dice 'no' elegante (degradación, rechazo rápido) o se atasca acumulando trabajo hasta caerse.

La backpressure es la disciplina de no aceptar más de lo que puedes procesar: el truco es que el rechazo sea el comportamiento planeado, no el síntoma de un fallo.

Definición

La backpressure (contrapresión) hace que un consumidor lento limite al productor: autorregulación con control de flujo, límites de concurrencia o rechazo temprano cuando el buffer se llena.

Por qué importa. Si el productor lanza sin límite, las colas crecen sin tope, la memoria se llena y el sistema entero muere lejos del punto del problema. Rechazar temprano es años más barato que caerse más tarde.

Cuándo usarlo. Aplica límites en toda frontera: rate limiting por cliente, límite de workers y colas acotadas, timeout en cada llamada externa y rechazo 503 temprano cuando el sistema satura.

Conceptos clave

  • El buffer siempre se llena: la pregunta no es si, es qué pasa después (bloquea, descarta, rechaza con 429/503).
  • Timeout en cada espera: sin él, una dependencia lenta congela workers que deberían atender a otros.
  • Límite de concurrencia: cap de workers o semáforos para que las tareas no se multipliquen sin freno.
  • Rate limiting: por cliente/módulo, en su propia capa, decide quién entra antes de gastar recursos.
  • Rechazo temprano con señal explícita (429, 503, retry-after): el cliente sabe que debe esperar.

Ejemplo básico

Una cola acotada con descarte explícito: cuando está llena, la petición recibe un 503 claro en vez de acumularse.

Ejemplo intermedio

El patrón de confiabilidad en nubes: el cliente espera períodos de 'busy' y los respeta con backoff, mientras la cola acotada protege al servicio.

Ejemplo real

Una API de imágenes (3k req/s) recibió una campaña que la duplicó en diez minutos. La BBDD de cola se saturó, las peticiones se acumularon y el backend cayó con OOM. La corrección: límite de concurrencia en los workers, cola acotada con descarte, rate limit por API-key y 503 con Retry-After. Los usuarios vieron error controlado un rato en vez de una caída total de 40 minutos.

  • Cola acotada + descarte explícito antes de que la memoria decida por ti.
  • Rate limit por cliente en la capa de entrada con bustsize controlado.
  • Workers con semáforo y timeout por tarea para que una lenta no ocupe la flota.
  • 503 con Retry-After para que los clientes respeten la recuperación.

El 429/503 con Retry-After convierte el rechazo en un mecanismo legible por los clientes.

Explicación

  • La cola es un amortiguador, no un almacén: un tamaño grande esconde el colapso hasta que el tiempo de espera mata la experiencia.
  • Rechazo temprano localiza el problema: la petición que no puede atenderse se cae en la frontera, no en la dependencia profunda.
  • El rate limit protege a todo el sistema de un solo cliente transversal y del spam accidental.
  • Sin timeout, un worker bloqueado eternamente es capacidad muerta: cada tarea tiene su presupuesto.
  • El sistema degradado debe ser visible en métricas: tasa de 429/503 y longitud de la cola son tus sensores.

Errores comunes

  • Cola sin límite que llena la memoria y mata el proceso con OOM a las 3 de la mañana.
  • Retries infinitos del cliente que multiplican la carga justo cuando el servidor quiere recuperarse.
  • Sin rate limit, un cliente iterando acelerado come la flota de workers del resto.

Buenas prácticas

  • Dimensiona la cola por el peor caso de duración de pico, no por el promedio.
  • Usa 429 para límites de tasa y 503 para capacidad; ambos con Retry-After.
  • Los workers llevan timeout propio y límite de reintentos acotado.
  • Alerta sobre longitud de cola y request rate, no esperes al OOM.

Ejercicio

  1. Diseña una cola acotada de notificaciones con rechazo 503.
  2. Configura rate limit por API key para una API de 5 clientes grandes.
  3. Escribe el retry con backoff de un cliente que respeta Retry-After.

Resumen

  • El sistema debe decir 'no' con 429/503 y Retry-After cuando satura.
  • Cola acotada, workers con timeout y rate limit por cliente forman la red de seguridad.
  • La degradación planeada es mejor que la caída accidental.
