Sharding y particionado

🧠 Experto 12 min System Design / Arquitectura de Sistemas Módulo 4 · Escalabilidad y distribución

Introducción

Cuando una base de datos deja de caber en una máquina o su escritura no da abasto, la jugada estrella del system design es el sharding: cortar los datos en pedazos (shards) y repartirlos entre varias máquinas.

El truco suena simple y es brutal en la práctica: cada shard escribe sola, pero ahora el sistema entero necesita decidir dónde vive cada dato, y la redistribución de shards es donde se comete el 80 % de los errores.

Definición

Sharding es particionar una base de datos por una llave (shard key) de forma que cada registro caiga en un shard determinado por una función (hash, rango, directorio). Cada shard es una base independiente con sus propios recursos.

Por qué importa. Una sola instancia tiene un techo físico de IOPS y espacio; el sharding reparte escrituras, lecturas y almacenamiento entre N máquinas y escala casi de forma indefinida.

Cuándo usarlo. Úsalo cuando la BBDD supera el tamaño o la tasa de escritura que una máquina gestiona con latencia sana, y después de haber agotado caché, índices y réplicas de lectura.

Conceptos clave

  • Shard key: la columna que decide dónde vive un registro; debe repartir uniforme (evita llaves cardinales como status).
  • Hash vs rango: hash reparte uniforme y pierde rangos de consulta; rango ganan consultas por rango pero crean shards calientes.
  • Directorios (index table): un mapa llave→shard permite migrar datos sin que la app conozca el esquema.
  • El hot shard: una llave popular concentra tráfico y convierte un shard en cuello de botella.
  • La redistribución (re-sharding): mover llaves entre shards para re-equilibrar carga; los datos deben migrar con consistencia.

Ejemplo básico

Un sharding por hash de user_id mantiene las consultas de un usuario en una sola pieza y reparte el tráfico con uniformidad.

Ejemplo intermedio

Para evitarte re-hash cuando crezcan los shards, usa hash consistente: la reasignación solo mueve una fracción de las llaves.

Ejemplo real

Un sistema de mensajería almacena 400 GB mensuales; una sola réplica moría de IOPS en los picos. Se particionó la BBDD por org_id con 32 shards y un directorio: la app mira la tabla de particiones con caché TTL, la escritura se reparte 32x, y al añadir shard 33 solo se migran las llaves que el mapa asigna al nuevo.

  • La llave debe venir en cada petición: el cliente manda org_id o el gateway lo deriva del token.
  • Las consultas cruzadas (join entre shards) se evitan: se desnormalizan o se resuelven por aplicación.
  • Los hot shards reciben tráfico de rutina: monitoriza el uso por shard para detectarlos.
  • Las migraciones de re-sharding se ejecutan en segundo plano con doble escritura y validación.

El directorio evita re-hash globales y permite mover llaves calientes entre shards.

Explicación

  • La shard key es la decisión más importante: una mala llave convierte el sharding en un problema peor que el original.
  • Hash uniforme para escala, rango para consultas ordenadas: no se puede tener ambos sin capa extra.
  • Las transacciones que cruzan shards o mueren o cargan un coordinador: diseña las llaves para mantener juntos los datos que se consultan juntos.
  • El re-sharding vive en producción: por eso el directorio y el hash consistente son tus amigos.
  • La recuperación de un shard concreto debe ser automática: réplicas por shard y backups por shard, no del conjunto.

Errores comunes

  • Elegir una shard key de baja cardinalidad: 'status' reparte todo el tráfico a 2 de 16 shards.
  • Hacer joins entre shards y cargar la coordinación en la app en cada consulta.
  • Poner el re-sharding en vías muertas hasta que el hot shard derribe el servicio.

Buenas prácticas

  • Elige una llave de alta cardinalidad y de queries frecuentes (user_id, org_id).
  • Mantén un directorio y cachéalo con TTL corto para re-equilibrar sin corte.
  • Backup y réplicas por shard para que un fallo aísle una pieza.
  • Instrumenta el uso por shard: el calor se detecta antes con números.

Ejercicio

  1. Elige la shard key de un sistema de pedidos y justifica dónde viven los datos de un usuario.
  2. Simula pasar de 16 a 18 shards y cuenta cuántas llaves se mueven con hash consistente.
  3. Diseña el directorio de particiones con su caché TTL y su migración en caliente.

Resumen

  • El sharding reparte almacenamiento y escritura a cambio de elegir bien la llave.
  • Hash para uniformidad, rango para ordenar: decide por las consultas.
  • El re-sharding se hace con directorio y hash consistente, en segundo plano y por pieza.
