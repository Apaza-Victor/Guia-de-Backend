Patrones de durabilidad y caché

🧠 Experto 9 min System Design Módulo 2 · Patrones

Velocidad y resistencia no se pelean: se combinan

La caché acelera las lecturas; la durabilidad protege los datos contra fallas. El arte del diseño está en combinarlas sin que el sistema devuelva datos viejos cuando el producto exige lo actual, ni pierda escrituras que el cliente ya dio por hechas.

Cada patrón de caché responde a una pregunta distinta: ¿cuándo entra el dato en la caché? y ¿quién es responsable de mantenerlo fresco?

Cache-aside (lazy loading)

Es el patrón más usado. La aplicación consulta la caché; si no está (miss), va a la base, rellena la caché y devuelve. La caché se llena lazy, solo cuando se lee.

import redis

cache = redis.Redis(host="cache", decode_responses=True)
TTL = 300

def leer_catalogo(producto_id: int) -> dict:
    clave = f"producto:{producto_id}"
    if (valor := cache.get(clave)) is not None:
        return {"datos": valor, "fuente": "cache"}

    datos = catalogo_db.get(producto_id)      # cache miss
    if datos is None:
        return None
    cache.setex(clave, TTL, datos)             # rellena con TTL
    return {"datos": datos, "fuente": "bd"}

def actualizar_catalogo(producto_id: int, datos: dict) -> None:
    catalogo_db.upsert(producto_id, datos)
    cache.delete(f"producto:{producto_id}")    # invalida, no sobrescribe

Detalles sutiles que hacen que este patrón funcione o truene:

  • Invalidar en la escritura: borrar la clave (no sobreescribir con lo nuevo) evita carreras de escritura concurrente.
  • Proteger el miss: si la base cae, un miss masivo «golpea» la base de golpe (estampida). Un candado por clave (single flight) lo controla.
  • TTL: es la red de seguridad por si una invalidación se pierde; la entrada expira sola.

Write-through y write-back

Cuando el patrón necesita frescura casi inmediata, la escritura también pasa por la caché:

  • Write-through: la escritura va a la caché y a la base en la misma operación. Lecturas siempre frescas; la escritura paga el doble de latencia.
  • Write-back: la escritura solo va a la caché; la base se actualiza después en segundo plano. Escrituras rapidísimas, pero hay una ventana donde el dato vive solo en memoria: si el nodo muere sin volcar, se pierde.
# Write-back con vaciado diferido
def escribir_contador(usuario_id: int, delta: int) -> None:
    clave = f"contador:{usuario_id}"
    cache.incrby(clave, delta)                 # rápido: solo en memoria
    cola_sincronizacion.enqueue("flush", clave, delta)   # drenado en batch

def vaciador(nodo: int) -> None:
    lote = cola_sincronizacion.dequeue_many(500)
    for clave, delta in lote:
        contadores_db.incrby(clave.split(":")[1], delta)
    # Se vuelca un lote; las métricas del contador se mantienen al día

Write-back se usa cuando la escritura es el camino crítico (métricas, contadores, like en posts) y la consistencia puede ser eventual. Nunca para datos que deben aceptar sin discusión al instante (una transacción bancaria, un pedido).

Coherencia y estampidas

Dos problemas clásicos de cualquier caché distribuida:

  • Coherencia: cuánto puede tardar en verse un cambio. Elijes con el TTL y con el patrón: cache-aside con invalidation da ventanas de segundos; write-through, casi cero.
  • Estampida (thundering herd): cuando la clave expira y llegan mil peticiones a la vez, todas golpean la base. Soluciones: single flight (una sola petición rellena), TTL con jitter (expiración aleatoria) o categorías con probabilidad de cache.
import random, threading, time

lock_cache = threading.Lock()

def leer_con_estampida_controlada(clave: str, cargar):
    if (valor := cache.get(clave)) is not None:
        return valor
    with lock_cache:                       # single flight por nodo
        if (valor := cache.get(clave)) is not None:
            return valor
        valor = cargar()                   # solo esto golpea la base
        ttl = 300 + random.randint(0, 60)  # jitter evita expiración sincronizada
        cache.setex(clave, ttl, valor)
    return valor

CDN y durabilidad

La CDN es «la caché de cerca del usuario»: sirve estáticos o incluso respuestas de API desde un borde global. Sus cabeceras HTTP son el control de frescura; el Cache-Control y el ETag deciden si el navegador o la CDN reutilizan la copia:

{
  "cabeceras_publicadas_por_el_origen": {
    "Cache-Control": "public, max-age=86400, stale-while-revalidate=600",
    "ETag": "W/\"a1b2c3\""
  },
  "flujo": {
    "1er_acceso": "cd1: miss → origen → se almacena en el borde",
    "2do_acceso": "cd2: hit → borde → sin tocar el origen",
    "revalidacion": "If-None-Match: a1b2c3 → 304 si no cambió"
  }
}

Y la durabilidad convive con todo esto: la fuente de verdad siempre es el almacenamiento persistente (la base o el object storage). La caché, la CDN y el write-back son capas de velocidad; ninguna debe considerarse la única copia de un dato irremplazable. La regla que no falla: si se pierde la memoria de todos los nodos, el dato debe seguir existiendo.

Ejercicio

  1. Elige un recurso caliente de tu sistema: ¿usarías cache-aside, write-through o write-back? Justifica mirando la frescura requerida y el costo de lectura vs escritura.
  2. Implementa en pseudocódigo la invalidación de caché al actualizar el perfil de un usuario (cache-aside con borrado en escritura).
  3. Explica qué pasa, con el patrón write-back, si el nodo de caché muere antes de vaciar el lote. ¿Qué falta añadir para no perder ese dato?

Resumen

  • Cache-aside llena la caché solo al leer y elimina claves al escribir; es el patrón predeterminado.
  • Write-through da frescura a costa de latencia de escritura; write-back da escrituras rápidas con riesgo de pérdida temporal.
  • La coherencia se controla con TTL, invalidación y, si hace falta, revalidación al escribir.
  • Las estampidas se evitan con single flight y TTL con jitter.
  • CDN + cabeceras HTTP cachean en el borde; la durabilidad siempre vive en el almacenamiento persistente, no en la caché.
