Patrones de colas y eventos

🧠 Experto 9 min System Design Módulo 2 · Patrones

Dos mundos: colas y eventos

La mensajería asíncrona se divide en dos mentalidades complementarias:

  • Colas (punto a punto): un mensaje lo consume una de las instancias de un grupo de workers. Perfectas para distribuir trabajo: procesar imágenes, enviar correos.
  • Eventos / Pub-Sub (uno a muchos): el mismo mensaje se entrega a todos los suscriptores interesados. Perfectos para notificar: «usuario registrado» lo escuchan el servicio de correos, el de analítica y el de scoring.

Elegir el tipo equivocado produce uno de dos síntomas: mensajes duplicados donde debía haber uno (usar pub-sub) o trabajo perdido que debía llegar a varios (usar colas para eventos).

Producer y consumer con ACK

En una cola de trabajo, el productor publica y el consumidor reconoce (ACK) después de terminar, no al recibir. Si el worker muere antes del ACK, el broker reentrega el mensaje a otro nodo.

import pika, json

# Productor: encola una tarea sin bloquear la API.
def encolar_thumbnails(producto_id: int, ruta_imagen: str) -> None:
    conexion = pika.BlockingConnection(pika.ConnectionParameters("cola"))
    canal = conexion.channel()
    canal.queue_declare(queue="generar_thumbnails", durable=True)
    canal.basic_publish(
        exchange="",
        routing_key="generar_thumbnails",
        body=json.dumps({"producto_id": producto_id, "ruta": ruta_imagen}),
        properties=pika.BasicProperties(delivery_mode=2),  # persistente
    )
    conexion.close()

# Consumidor: procesa y solo entonces hace ACK.
def consumidor(ch, method, properties, body):
    datos = json.loads(body)
    try:
        generar_imagen_pequena(datos["producto_id"], datos["ruta"])
        ch.basic_ack(delivery_tag=method.delivery_tag)   # trabajo terminado
    except Exception:
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

canal.basic_qos(prefetch_count=1)  # un mensaje a la vez por worker
canal.basic_consume("generar_thumbnails", consumidor)

El ACK manual convierte la cola en un buffer seguro: si el proceso que trabaja se cae a mitad de la tarea, el mensaje vuelve a la cola y otro worker lo termina. Esta es la base del patrón at-least-once.

Dead letter y prioridad

Un mensaje que falla muchas veces puede envenenar la cola. La solución estándar es el dead letter exchange (DLX): mensajes que superan el máximo de reintentos o la vida útil del TTL se mueven a una cola especial de inspección, sin bloquear el flujo normal.

# Declaración de colas con dead letter y prioridad (configuración).
exchange:
  name: trabajos
  type: direct

queue trabajos_urgentes:
  durable: true
  arguments:
    x-max-priority: 10
    x-dead-letter-exchange: dlx
    x-dead-letter-routing-key: fallidos
    x-message-ttl: 3600000     # 1 hora viviendo en la cola

queue fallidos:
  durable: true

Reglas prácticas:

  • Prioridad: solo para mensajes que importan en minutos (un pago): la cola la configura con x-max-priority y puede que redistribuir orden.
  • TTL + DLX: el par estándar para que nada quede huérfano; el operador revisa fallidos con un dashboard.
  • Reintentos exponenciales: no repitas sobre la misma cola; usa una cola de espera con backoff antes de la principal.

Fanout: publicar a todos

En el patrón pub-sub, un exchange de tipo fanout copia cada evento a todas las colas suscritas. Es la forma de propagar un hecho de dominio a muchos suscriptores sin que el productor conozca a ninguno.

{
  "evento": "usuario_registrado",
  "version": "1.0",
  "id_ocurrencia": "evt_a1b2c3",
  "ocurrido_en": "2026-09-21T08:15:30Z",
  "entidad": { "id": "usr_8821", "email": "ana@correo.com" },
  "detalles": {
    "fuente": "api-registro",
    "region": "us-east-1"
  }
}

Un detalle que muchos equipos pasan por alto: un evento es un hecho del pasado, no una orden. Enviamos «usuario_registrado» y cada suscriptor decide su acción; si enviamos «envía el correo de bienvenida», el productor se está acoplando al comportamiento de otro sistema. Guardar primero el evento en una tabla/stream y procesarlo después (event sourcing, outbox) protege contra entregas perdidas.

Garantías de entrega e idempotencia

La garantía práctica de los brokers es at-least-once: puede que el mismo mensaje llegue dos veces (por un reintento o un ACK perdido). Por eso el consumidor debe ser idempotente: procesar el mismo evento dos veces debe producir el mismo resultado.

def procesar_registro(evento: dict) -> None:
    clave = f"procesado:{evento['id_ocurrencia']}"
    if redis.exists(clave):
        return                      # ya lo vimos; idempotencia
    enviar_correo_bienvenida(evento["entidad"])
    redis.setex(clave, 24 * 3600, "1")

La idempotencia se consigue con claves de deduplicación (el id_ocurrencia del evento), con tablas de processed-events o con operaciones matemáticamente idempotentes (guardar el máximo de un valor, por ejemplo). Sin ella, un reintento normal se convierte en correos duplicados o saldos duplicados.

Ejercicio

  1. Para «procesar cada pago exactamente una vez por el servicio de facturación», elige cola o pub-sub y justifica.
  2. Para «avisar a correos, notificaciones push y data warehouse de cada usuario nuevo», elige el patrón y escribe el evento JSON que publicarías.
  3. Implementa en pseudocódigo un consumidor idempotente para «aumentar el contador de pedidos de un usuario» que pueda recibir el mismo evento 3 veces.

Resumen

  • Colas = punto a punto (trabajo); eventos/pub-sub = uno a muchos (notificación).
  • El ACK debe llegar al finalizar el trabajo, no al recibir; así el broker reentrega tareas huérfanas.
  • DLX + TTL y prioridades evitan colas envenenadas y mensajes huérfanos.
  • Un evento describe un hecho pasado; los suscriptores deciden sus acciones.
  • La entrega real es at-least-once: los consumidores deben ser idempotentes.
