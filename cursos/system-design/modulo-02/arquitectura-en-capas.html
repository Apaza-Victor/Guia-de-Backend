Arquitectura en capas

🧠 Experto 9 min System Design Módulo 2 · Patrones

Separar responsabilidades

La arquitectura en capas (o layered architecture) organiza el código en niveles donde cada uno tiene una responsabilidad definida y solo puede hablar con el nivel inmediato inferior. Es el patrón más adoptado del backend porque es simple de razonar y de explicar: cada capa es reemplazable mientras mantenga su contrato.

En su forma clásica tiene tres capas:

  • Presentación (API/HTTP): recibe las peticiones, valida el input y devuelve respuestas. No conoce reglas de negocio.
  • Lógica de negocio (servicios/dominio): reglas, procesos y casos de uso. No conoce HTTP ni detalles de la base de datos.
  • Datos (repositorios/ORM): persiste y consulta. No decide qué reglas se aplican.

Flujo de una petición

La petición baja de capa en capa y las respuestas suben en orden inverso. Cada capa transforma: se valida, se procesa, se persiste y se devuelve. Es la misma estructura detrás de casi todos los backends reales, de un proyecto chico a un sistema de carritos:

# Capa de presentación: solo transporte HTTP y validación básica.
from fastapi import FastAPI, HTTPException
app = FastAPI()

@app.post("/carrito/{usuario_id}/items")
def agregar_item(usuario_id: int, item: dict):
    cantidad = int(item["cantidad"])
    if cantidad <= 0:
        raise HTTPException(400, "La cantidad debe ser positiva")
    # La lógica de negocio vive en la capa de servicios.
    return CarritoService.agregar_item(usuario_id, item["producto"], cantidad)


# Capa de negocio: las reglas del dominio, sin saber de HTTP.
class CarritoService:
    @staticmethod
    def agregar_item(usuario_id: int, producto_id: int, cantidad: int) -> dict:
        if not ProductoRepository.existe(producto_id):
            raise ValueError("Producto desconocido")
        if cantidad > MAX_POR_ITEM:
            raise ValueError(f"Máximo {MAX_POR_ITEM} unidades por item")
        return CarritoRepository.agregar(usuario_id, producto_id, cantidad)


# Capa de datos: cómo se guarda, sin decidir reglas.
class CarritoRepository:
    @staticmethod
    def agregar(usuario_id: int, producto_id: int, cantidad: int) -> dict:
        fila = ejecutar_sql(
            "INSERT INTO carrito (usuario_id, producto_id, cantidad) "
            "VALUES (%s, %s, %s) RETURNING id",
            (usuario_id, producto_id, cantidad),
        )
        return {"id": fila[0], "usuario": usuario_id, "producto": producto_id}

Si mañana cambiamos FastAPI por Express o la base por una NoSQL, la capa de negocio no se toca: solo cambian las capas de los extremos. Ese es el valor económico del patrón.

Reglas de dependencia

La regla de oro es la dirección de las dependencias: siempre hacia abajo. La presentación depende de la lógica de negocio; la lógica de negocio depende de la abstracción de datos; pero la capa de datos no debe depender de la presentación, y ninguna capa salta directamente a otra más profunda saltándose el medio.

  • ✔ La capa de API importa a los servicios.
  • ✔ Los servicios importan a los repositorios (a través de interfaces).
  • ✘ La capa de datos nunca importa a la capa de presentación.
  • ✘ Un controlador no debe escribir SQL directo.

Cuando las reglas de dependencia se respetan, los cambios en una capa no se filtran: un mal JSON no entra hasta la base, y un cambio de motor no sube hasta el endpoint.

Ventajas y riesgos

Ventajas:

  • Separación clara que hace más fácil probar cada nivel por separado.
  • Componentes intercambiables si se mantienen los contratos.
  • Es fácil de dibujar, explicar y arrancar para un equipo nuevo.

Riesgos:

  • Abstracciones con fugas (leaky abstractions): si la capa de datos «se escapa» (por ejemplo, el repositorio devuelve campos de la tabla a medias), la lógica de negocio termina sabiendo de la base.
  • Capa de datos mono-bloque: muchas veces todas las lógicas comparten una única base de datos, incluso cuando sus datos no tienen relación; luego es imposible dividir servicios sin acoplarse.
  • Transmisión de la API al dominio: si el modelo del endpoint es también el modelo de la tabla, cualquier cambio en la API obliga a tocar la base.

La estructura en el repo

Esta organización por carpetas es la que se ve en prácticamente todos los backends en capas; el árbol por sí solo ya cuenta la arquitectura:

mi-servicio/
├── app/
│   ├── api/            # capa de presentación: routers, DTOs, validadores
│   │   ├── routers/
│   │   └── schemas.py
│   ├── application/    # casos de uso y orquestación
│   │   └── services/
│   ├── domain/         # entidades, reglas y contratos de repositorio
│   │   └── models.py
│   └── infrastructure/ # capa de datos y conexión con el mundo externo
│       ├── database/
│       ├── repositories/
│       └── external/
├── tests/
└── pyproject.toml

La clave está en que la carpeta domain no importa a infrastructure: el dominio define la interfaz Repositorio y la infraestructura la implementa. Eso invierte la dependencia y mantiene el patrón en pie.

Ejercicio

  1. Toma un endpoint que conozcas (por ejemplo, «registrar usuario») y escribe en qué capa iría cada paso: validar el email, verificar que no exista, aplicar política de contraseñas, insertar en la tabla, responder el token.
  2. Identifica una violación típica de capas en tu codebase actual (por ejemplo, SQL en un controlador) y propón a qué capa se movería.
  3. Escribe el contrato de una clase RepositorioUsuario con dos métodos y su implementación ficticia para una base distinta en la infraestructura.

Resumen

  • La arquitectura en capas separa presentación, negocio y datos con responsabilidades exclusivas.
  • Las dependencias apuntan siempre hacia abajo; ninguna capa salta niveles.
  • Los repositorios se definen en el dominio e implementan en infraestructura (inversión de dependencias).
  • Ventajas: testabilidad y reemplazo de componentes. Riesgos: abstracciones con fugas y capa de datos acoplada.
  • La estructura de carpetas del repo debe reflejar la separación de capas.
