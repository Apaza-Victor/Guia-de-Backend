Caso: feed (newsfeed)

🧠 Experto 11 min System Design Módulo 3 · Diseño completo

1. Requisitos

Un feed es la lista de publicaciones de las personas que sigues, ordenada por relevancia, con scrolling infinito y carga rápida. Definimos el alcance:

  • Funcionales: ver el feed del usuario (post de seguidos, ordenados), publicar un post que aparece en feeds de seguidores, paginar con cursor. (Feed simple; los algoritmos de ML se mencionan como mejora.)
  • No funcionales: el feed de un usuario se sirve en menos de 150 ms; debe sentirse «instantáneo» al seguir a alguien nuevo; el post debe aparecer en los feeds de los seguidores en segundos (eventual).
  • Supuestos: 10 millones de usuarios, 1 millón activos diarios, 50 registros de seguimiento por usuario en promedio, 2 posts por usuario activo al día.

2. Fan-out: el corazón del diseño

Hay dos estrategias puras y una híbrida:

  • Pull (fan-out on read): al pedir el feed, se consultan los posts de los seguidos sobre la marcha. Barato de escribir, carísimo de leer: cada vista interroga a todos los seguidos.
  • Push (fan-out on write): al publicar, el post se copia al timeline cacheado de cada seguidor. Lectura instantánea (una lista ya lista), pero costosa de escribir con muchos seguidores.
  • Híbrido: fan-out on write para usuarios normales; fan-out on read para «celebrities» con millones de seguidores (copiar a un millón de timelines por post sería insostenible).
MAX_SEGUIDORES_PUSH = 10000

def publicar_post(autor_id: str, post: dict) -> None:
    posts_db.insert(post)                          # fuente de verdad

    seguidores = seguidores_db.ids_de(autor_id)
    if len(seguidores) <= MAX_SEGUIDORES_PUSH:
        fanout_push(seguidores, post)              # on write para la mayoría
    else:
        marca_celebridad(autor_id)                 # on read para los gigantes

def fanout_push(seguidores: list, post: dict) -> None:
    for seguidor in seguidores:
        timeline_cache.lpush(f"timeline:{seguidor}", post["id"], maxlen=500)
    cola_feed.pegar_evento("feed_actualizado", seguidores, post["id"])

def leer_timeline(usuario_id: str) -> list:
    ids = timeline_cache.lrange(f"timeline:{usuario_id}", 0, 20)
    if not ids:                                    # timeline vacío → pull
        return fanout_pull(usuario_id)
    return posts_db.buscar_muchos(ids)

La línea divisoria del híbrido se decide por costo: cuando los seguidores de un autor superan un umbral, el fan-out push cuesta más de lo que ahorra en lectura, y ese autor pasa al modo pull (su post se agrega al vuelo cuando alguien lo lee).

3. Caché de timelines

La timeline por usuario es una lista de IDs en una caché (idealmente Redis con listas TRIM). Se recorta a ~500 post IDs: nadie recorre un millón de posts de una sentada, y el recorte hace que cada operación sea barata y acotada.

MAX_TIMELINE = 500

def agregar_a_timeline(usuario_id: str, post_id: str) -> None:
    tl = f"timeline:{usuario_id}"
    timeline_cache.pipeline()          # operación atómica de pipeline
    timeline_cache.lpush(tl, post_id)
    timeline_cache.ltrim(tl, 0, MAX_TIMELINE - 1)
    timeline_cache.execute()

Cosas sutiles que se aprenden con esta caché:

  • Eliminar un post: borrarlo del feed no es quitar el de la base: hay que quitarlo de todos los timelines que lo contienen (evento de borrado → workers).
  • Frescor al seguir: al seguir a alguien nuevo, el timeline debe rellenarse con sus últimos IDs; aquí el push hibrido ya no aplica porque es evento único (backfill).
  • Miss: si la caché de un usuario se pierde (o nunca existió), se regenera con un pull inicial y se vuelve a cachear.

4. Ordenar: cronológico vs relevancia

El orden por tiempo es trivial y cache-friendly: los IDs en la lista ya están ordenados por inserción. La relevancia (algoritmos) pide más: cada post recibe un score en el momento de escribirse, y el orden de la timeline se basa en puntuaciones clasificadas.

from datetime import datetime, timezone

def score_post(interacciones: int, antiguedad_horas: float, peso_autor: float) -> float:
    """Versión simple de un ranking: interacción joven pesa más."""
    frescura = 1 / (antiguedad_horas + 2) ** 1.5
    return interacciones * 0.4 + frescura * 10 + peso_autor * 0.1

# Un post con pocas interacciones reciente y uno viral de hace un día
print(score_post(interacciones=3, antiguedad_horas=0.5, peso_autor=1.0))
print(score_post(interacciones=5000, antiguedad_horas=26, peso_autor=1.0))

Los scores se calculan al publicar (con un batch de interacciones) y se reordenan en segundo plano, no en la lectura: así el flujo de leer sigue siendo «lista ya ordenada». El «pain point» clásico es el recálculo en caliente: un post que escala viral agita la lista; el diseño permite boost puntual en vez de recálculos masivos.

5. Escalado y celebridades

El caso celebrity (un autor con 30 millones de seguidores) acota el diseño: su post no se copia a 30 millones de timelines. En su lugar:

  • El post queda marcado como «celebrity» en la base.
  • Al leer el feed, se hace un pull del top-N de posts de celebrities que sigo y se mezclan con la timeline cachead.
  • El merge ocurre en el borde o en primer nivel de la API (con caché corta), nunca en la base.
def leer_feed_hibrido(usuario_id: str) -> list:
    normales = timeline_cache.lrange(f"timeline:{usuario_id}", 0, 20)

    # Pull de los últimos posts de las celebrities seguidas (top 3 c/u).
    celebrities = seguimos_celebrities(usuario_id)
    extra = []
    for c in celebrities:
        extra.extend(celebrity_cache.lrange(f"celeb:{c}:recientes", 0, 2))

    mezcla = normales + extra
    mezcla.sort(key=score_post, reverse=True)      # orden por relevancia
    return mezcla[:20]

Este hybrid permite que el top del feed sea bueno aunque publiquen 100 celebrities a la vez, sin mover un byte hacia 100 millones de listas.

Ejercicio

  1. Calcula cuántas escrituras por día implica el fan-out push con los supuestos dados (1M activos × 2 posts). ¿A qué porcentaje del QPS total equivale?
  2. Explica qué harías si un usuario con 50.000 seguidores empieza a publicar 100 veces al día: ¿cuándo lo moverías a modo celebrity?
  3. Diseña el backfill al seguir a un usuario nuevo: ¿qué datos necesitas de su timeline y cómo evitas congestionar la caché?

Resumen

  • Pull (on read) es barato de escribir y carísimo de leer; push (on write) es lo inverso.
  • El híbrido envía con push a la mayoría y con pull a celebrities con límites.
  • La timeline es una lista cacheada y recortada de IDs, no el post completo.
  • La relevancia se calcula como score en segundo plano, no en la lectura.
  • El backfill al seguir, el borrado de posts y el caso celebrity se resuelven con eventos y workers.
