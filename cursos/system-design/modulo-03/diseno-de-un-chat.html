Caso: sistema de chat

🧠 Experto 11 min System Design Módulo 3 · Diseño completo

1. Requisitos

Definimos el sistema concreto: un chat grupal con 1:1 y canales. Declaramos alcance y supuestos:

  • Funcionales: enviar/recibir mensajes en tiempo real (1:1 y grupos), historial consultable, entrega con confirmación (✓✓), presencia (en línea/offline), notificaciones push cuando se está offline.
  • No funcionales: latencia de entrega en línea menor a 200 ms; el historial no se pierde; consistencia eventual aceptable en leídos (el mensaje se puede ver en segundos, no milisegundos); disponibilidad 99.9%.
  • Supuestos: 1 millón de usuarios activos diarios, ~1.000 mensajes por segundo promedio, cada conversación retiene los últimos 6 meses visibles.

2. Modelo de datos

El acceso dominante es «dame los mensajes de esta conversación, en orden, desde esta posición». Por eso la clave de partición es la conversación y la clave de orden es el cursor:

{
  "conversacion_id": "conv_8842",
  "mensaje_id": "msg_9f3a22",
  "autor_id": "usr_101",
  "tipo": "texto",
  "contenido": "¿Revisamos el despliegue de esta tarde?",
  "enviado_en": "2026-09-21T15:06:12Z",
  "cliente_id": "cli_1a2b"          // dedup: si el cliente reintenta, no se duplica
}

Las conversaciones se particionan por conversacion_id: leer todo el historial de una conversación toca un solo shard. El mensaje guarda cliente_id (idempotencia de la escritura) y un cursor que los clientes usan para paginar: el último mensaje conocido aparece en ?cursor=....

3. Tiempo real con WebSockets

La entrega en vivo usa WebSocket: el cliente abre una conexión persistente y el servidor empuja los mensajes. Cualquier diseño serio incluye reconexión automática y compensación de huecos: si el socket se cayó un segundo, el cliente debe volver a consultar el historial desde el último cursor.

// Cliente: conexión con reconexión exponencial y deduplicación de mensajes.
const MAX_RECONEXION = 30000;
let reintentos = 0;

function conectar(datosSesion) {
  const ws = new WebSocket(`wss://chat.primerpaso.dev/ws?token=${datosSesion.token}`);
  const ultimoCursor = localStorage.getItem("ultimoCursor") || "0";

  ws.onopen = () => reintentos = 0;

  ws.onmessage = (ev) => {
    const msg = JSON.parse(ev.data);
    if (msg.cursor <= ultimoCursor) return;       // dedup por cursor
    ultimoCursor = msg.cursor;
    localStorage.setItem("ultimoCursor", ultimoCursor);
    renderMensaje(msg);
  };

  ws.onclose = () => {
    reintentos += 1;
    const espera = Math.min(1000 * 2 ** reintentos, MAX_RECONEXION);
    setTimeout(() => conectar(datosSesion), espera);
  };
}

El cursor monotónico resuelve la «doble entrega» típica de las reconexiones: aunque el socket repita un mensaje, el cliente lo descarta.

4. Fanout entre nodos

Una conexión es atendida por un nodo concreto. Para que un mensaje publicado en el nodo A llegue a un suscriptor conectado al nodo B, hace falta un puente: el clásico es Redis Pub/Sub, donde cada nodo publica los mensajes de sus conversaciones y todos los nodos escuchan y reenvían a sus sockets locales.

import json, redis

pubsub = redis.Redis(host="redis-pubsub")

def entregar_a_online(mensaje: dict) -> None:
    """Guarda de forma duradera y difunde a los nodos conectados."""
    historial_db.insertar(mensaje)                    # durabilidad primero
    pubsub.publish("chat:mensajes", json.dumps(mensaje))

# En cada nodo, un suscriptor reenvía a sus sockets locales.
def difundir_nodo():
    canal = pubsub.pubsub()
    canal.subscribe("chat:mensajes")
    for evento in canal.listen():
        if evento["type"] != "message":
            continue
        msg = json.loads(evento["data"])
        for socket in sockets_locales_de(msg["conversacion_id"]):
            socket.enviar(msg)

Regla de oro del chat a escala: primero persiste, después difunde. Si un nodo cae en el instante de la difusión, el cliente que estuvo offline recupera el mensaje del historial al reconectar. La durabilidad nunca depende del fanout.

5. Entrega fiable y estados

Los estados ✓ y ✓✓ se modelan como hechos asíncronos: el cliente reclama «entregado» cuando lo recibe y «leído» cuando el usuario lo abre. Cada reclamación vuelve a la cola de presencia y se agrega al mensaje:

from dataclasses import dataclass

@dataclass
class EstadosEntrega:
    entregado: dict | None = None     # uid del último que confirmó
    leido: dict | None = None

def marcar_entregado(msg_id: str, usuario_id: str, usuario: int) -> None:
    cola_presencia.publish("entrega", {
        "msg_id": msg_id,
        "usuario_id": usuario_id,
        "evento": "entregado" if usuario else "recibido",
        "en": timestamp_utc(),
    })

El modelo por eventos permite replicar el estado de chat en varios lugares (presencia) sin transacciones distribuidas: cada reclamación es un evento que converge en la vista del mensaje.

6. Escalado del historial

El historial crece sin límite. Las decisiones clave:

  • TTL lógico: se retiene 6 meses en el camino caliente; los meses viejos van a almacenamiento frío (archivos) con búsqueda pesada.
  • Sharding por conversación: clúster de shards por conversacion_id; una conversación viva vive en un shard y su historial se lee con una sola consulta.
  • Cache del último mensaje: la barra de conversaciones «últimos mensajes» se sirve de una caché por sesión y no toca el historial completo.

Cerrar el círculo con las garantías: la consistencia es eventual por conversación (tú ves tu mensaje al instante; el resto lo ve en segundos), el historial es duradero (persistencia previa al fanout) y la latencia en línea depende de WebSockets, no de la base.

Ejercicio

  1. Escribe qué ocurre en tu diseño si el usuario envía un mensaje y su socket se cae antes de recibir el ACK del servidor. ¿Cómo evitas el duplicado usando cliente_id?
  2. ¿Por qué la persistencia va antes que el fanout? Explica con un escenario concreto de caída de un nodo.
  3. Diseña el contrato de reenvío de un mensaje: ¿qué campos necesita el histórico, y cuáles son solo del tiempo real (presencia, entrega)?

Resumen

  • El acceso dominante es el historial por conversación: se particiona y ordena por cursor.
  • La entrega en tiempo real usa WebSockets con reconexión exponencial y deduplicación por cursor.
  • Redis Pub/Sub conecta nodos: publicación local, difusión global, entrega en el nodo del suscriptor.
  • Primero persiste, después difunde: la durabilidad nunca depende del fanout.
  • Estados entregado/leído se modelan como eventos asíncronos que convergen.
