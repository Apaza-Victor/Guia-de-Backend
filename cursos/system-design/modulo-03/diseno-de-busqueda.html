Caso: búsqueda

🧠 Experto 11 min System Design Módulo 3 · Diseño completo

1. Requisitos

Diseñemos búsqueda de productos en una tienda a escala, con 100 millones de productos y millones de consultas diarias:

  • Funcionales: buscar por texto libre (título, descripción), con filtros (categoría, precio, marca), ordenar por relevancia y por precio, y paginar. Sin sinónimos complejos ni ML (se declaran fuera de alcance).
  • No funcionales: el primer resultado en menos de 200 ms (p95); frescura del índice en minutos; disponible 99.9%; un producto nuevo debe encontrarse poco después de publicarse.
  • Supuestos: 500.000 consultas/día (≈6 QPS promedio, pico ~20), 100 millones de documentos, tamaño medio de documento 2 KB.

Con esos QPS, la clave de diseño no es el tráfico: es el índice y su distribución. Un índice de 100 millones de documentos no cabe en una máquina cómoda; de ahí que casi todo en este caso gira alrededor de particionarlo.

2. Índice invertido

El corazón de la búsqueda por texto es el índice invertido: un mapa de término → lista de documentos que lo contienen (posting list). En vez de escanear 100 millones de documentos por consulta, el buscador consulta unos pocos términos y cruza listas.

from collections import defaultdict

def tokenizar(texto: str) -> list[str]:
    return texto.lower().split()

def construir_indice(docs: list[dict]) -> dict:
    indice = defaultdict(list)
    for doc in docs:
        for token in set(tokenizar(f'{doc["titulo"]} {doc["descripcion"]}')):
            indice[token].append(doc["id"])
    return dict(indice)

docs = [
    {"id": 1, "titulo": "Laptop Gamer RTX", "descripcion": "16 GB RAM SSD"},
    {"id": 2, "titulo": "Laptop Oficina", "descripcion": "8 GB RAM SSD"},
    {"id": 3, "titulo": "Monitor 27", "descripcion": "4K IPS"},
]
indice = construir_indice(docs)
print(indice["laptop"])      # [1, 2]
print(indice["ssd"])         # [1, 2]

El índice es un dato precomputado: se construye indexando doc a doc y después solo se consulta. La consulta «laptop ssd» intersecta las posting lists y devuelve los ids presentes en ambas. Términos stopwords (el, la, de) se filtran y raros y frecuentes se ponderan distinto, que es lo que alimenta el ranking.

3. Tokenización y normalización

El texto real exige normalizar antes de indexar: pasar a minúsculas, quitar tildes según idioma, manejar plurales y dividir correctamente. En español, «celular» y «celulars» no deben ser términos distintos; los buscadores reales aplican stemming o diccionarios de normalización.

import unicodedata, re

def normalizar(term: str) -> str:
    """Minúsculas, sin tildes y solo alfanuméricos."""
    sin_acentos = unicodedata.normalize("NFD", term)
    sin_acentos = "".join(ch for ch in sin_acentos
                          if unicodedata.category(ch) != "Mn")
    return re.sub(r"[^a-z0-9 ]", "", sin_acentos.lower())

print(normalizar("Café ☕"))     # cafe
print(normalizar("Laptops!"))    # laptops

Esta normalización se aplica a la consulta y a la indexación con las mismas reglas: si no coinciden, el término buscado nunca encuentra su posting list. Mantener reglas idénticas entre indexador y consumidor es una fuente clásica de búsquedas que «no encuentran nada».

4. Ranking de relevancia

Buscar más que devolver documentos: hay que ordenar por relevancia. El modelo clásico es TF-IDF y su refinamiento moderno BM25: penaliza términos que aparecen en todos lados y premia los que aparecen en el documento y la posición del término.

import math

def bm25(tf: int, dl: int, avgdl: float, N: int, df: int,
         k1: float = 1.2, b: float = 0.75) -> float:
    """Score BM25 de un término en un documento."""
    idf = math.log(1 + (N - df + 0.5) / (df + 0.5))
    den = tf + k1 * (1 - b + b * (dl / avgdl))
    return idf * (tf * (k1 + 1) / den)

texto_virgen = [("gamer", 5, 200), ("laptop", 3, 200)]   # término, tf, longitud doc
N, avgdl, df = 100_000_000, 150, 5_000_000
for termino, tf, dl in texto_virgen:
    print(termino, round(bm25(tf, dl, avgdl, N, df), 3))

El ranking admite boosts: un término en el título pesa más que en la descripción, y la marca o el precio de un producto premium se puede multiplicar. Los boosts son configuración del índice, no del código de consulta, lo que permite que producto ajuste relevancia sin deploy.

La salida de la query sería algo así — el buscador devuelve el id, el score y los campos cacheados para pintar la tarjeta:

{
  "query": "laptop gamer",
  "tiempo_ms": 45,
  "total": 1284,
  "resultados": [
    { "id": 88211, "score": 24.7, "titulo": "Laptop Gamer 15\" RTX 4070", "precio": 1899.99 },
    { "id": 88234, "score": 19.1, "titulo": "Laptop Gamer 14\" RTX 4060", "precio": 1499.99 }
  ],
  "filtros_aplicados": { "categoria": null, "precio_max": null }
}

5. Escalar el índice

El índice de 100 millones de documentos se escala de dos formas complementarias:

  • Sharding por documento (distribución por id): cada shard guarda su subconjunto del índice. Una consulta se envía a todos los shards en paralelo (fan-out), cada uno responde sus top-N, y el coordinador fusiona (merge). El costo de red crece con el número de shards.
  • Sharding por término (distribución por palabra): la posting list de cada término vive en un lugar; la consulta de 3 términos toca 3 máquinas. Elegante para consultas cortas, pero crea términos «calientes» y consultas que tocan muchas máquinas a la vez.

La decisión típica en producción es sharding por documento + réplicas, con el tiering en caliente y frío: los documentos «hot» (productos populares) se replican más veces y viven en memoria; el resto comparte disco y responde más lento.

6. Operación del índice

El índice no se actualiza en cada venta: se construye en lotes (índice primario o full index) y se fusiona con deltas que se producen mientras se indexa. La estrategia clásica de los motores: full + incremental.

# Pipeline de indexado diario (pseudocódigo de operación)
def job_indexado_diario():
    lotes = leer_productos_del_dia()              # deltas de la jornada
    for lote in reagrupar(lotes, tamano=50_000):
        indice_delta = construir_indice(lote)     # el mejor momento del día
        subir_a_nodos_calientes(indice_delta)     # compilar y desplegar
        marcar_delta_como_servido()

# La búsqueda sirve siempre el índice completo + los deltas activos

Los motores modernos (Elasticsearch/OpenSearch, Vespa, Solr) automatizan estas piezas: sharding, réplicas, fusiones de segmentos y rebalanceo. El diseñador de sistemas elige los parámetros (número de shards, réplicas, refresh interval) pensando en el compromiso «frescura vs costo de reindexación».

Ejercicio

  1. Construye el índice invertido de 3 frases tuyas y resuelve la consulta de dos palabras intersectando las listas.
  2. Explica por qué «un producto nuevo debe aparecer en minutos» obliga a un pipeline de deltas, y qué pasaría con solo un full-index diario.
  3. Si tu búsqueda tuviera 500.000 QPS en vez de 6, ¿cómo cambiaría la elección entre sharding por documento y por término?

Resumen

  • El índice invertido mapea término → documentos y permite consultas sin escanear todo.
  • Normalizar y tokenizar con las mismas reglas en indexación y consulta es crítico para el idioma.
  • BM25 + boosts sitúa la relevancia: frecuencias, raridades y campos importantes.
  • El índice se parte por documento o por término, con réplicas y tiering caliente/frío.
  • La frescura se logra con índice completo + deltas incrementales, no reindexando todo.
