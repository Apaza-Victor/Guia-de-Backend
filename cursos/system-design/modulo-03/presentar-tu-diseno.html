Presentar y comunicar

🧠 Experto 10 min System Design Módulo 3 · Diseño completo

El diseño se comunica

Un senior no solo diseña: presenta. En una entrevista de system design se evalúa el razonamiento tanto como el resultado: cómo ordenas la conversación, cómo justificas cada pieza y cómo reaccionas cuando te confrontan. En el trabajo, un diseño que no se explica se muere en un documento.

Este último capítulo condensa el método en un formato que puedes ejecutar una y otra vez: un framework, una manera de dibujar, un vocabulario de trade-offs y un checklist de cierre.

El framework en 5 pasos

El orden del 90% de las entrevistas de system design. El secreto está en no saltar pasos: la gente que dibuja cajas primero pierde puntos, la que pregunta y estima primero los gana.

  1. Requisitos (3-5 min): confirma alcance, funcionales y no funcionales clave, y fuera de alcance.
  2. Estimaciones (2-3 min): QPS, almacenamiento, ratios; cierra con «si esto se multiplica por 10…».
  3. API y datos (5 min): contratos y modelo de datos, con la clave de partición.
  4. Componentes (10 min): el diagrama, capa por capa, explicando cada bloque con su porqué.
  5. Profundidad y trade-offs (resto): búsqueda de cuellos de botella, fallos, y qué cambiar con más escala.
{
  "blueprint_de_la_sesion": {
    "1_requisitos": { "funcionales": ["crear", "leer"], "slo": "p95 < 300ms" },
    "2_estimaciones": { "qps": 4167, "almacenamiento_anio_gb": 260 },
    "3_api_datos": { "endpoints": 2, "clave_particion": "usuario_id" },
    "4_componentes": ["cdn", "lb", "api_x3", "cache", "bd_replicada", "cola"],
    "5_tradeoffs": ["consistencia_eventual_vs_disponibilidad",
                    "sharding_por_hash_vs_rango"]
  }
}

Nunca uses el tiempo de presentación para decidir: primero razona, luego dibuja. Y siempre vuelve al paso 5 preguntando: «¿hay alguna dirección en la que debería profundizar?». La entrevista trabaja contigo, no contra ti.

Cómo dibujar que te entiendan

Tu diagrama se va a interpretar en cadena. Buenas costumbres que separan a los buenos presentadores:

  • Una sola dirección de flujo: pinta siempre al cliente a la izquierda y los datos a la derecha; los flujos se leen de izquierda a derecha.
  • Etiqueta cada flecha: «HTTP», «descarga CDN», «colas de trabajo». Una flecha sin nombre es una pregunta sin respuesta.
  • Señala la redundancia: dibuja el punto de entrada y marca dónde hay réplicas y dónde hay un solo nodo (el riesgo).
  • Anota decisiones al borde: «shard por hash: 16 shards», «TTL cache 5 min». El número a mano vale más que diez cajas.

En la pizarra o en un documento, el típico diagrama de un buen diseño se lee así: clientes → CDN → LB → API → caché → BD, con una cola saliendo hacia workers y una región de réplicas de lectura debajo de la primaria. Si puedes dibujarlo en 2 minutos, dominas la forma.

Comunicar trade-offs

Decir «elijo cache-aside» vale menos que decir «elijo cache-aside porque las lecturas son 100x las escrituras y puedo tolerar 5 min de frescor en el catálogo». El vocabulario que vende cualquier decisión:

  • El beneficio: qué atributo cumple (latencia, disponibilidad, costo).
  • El precio: qué atributo se sacrifica (frescura, consistencia, complejidad).
  • El plan B: qué hago si el supuesto falla (¿y si el ratio fuera 1:1?).

La misma lógica queda registrada en un ADR cuando documentamos la decisión técnicamente:

# ADR-014: Caché del catálogo con cache-aside
estado: aceptado
fecha: 2026-09-21

contexto: >
  El catálogo se lee 100 veces más de lo que se escribe y soporta frescura
  de minutos. Una cache delante de la réplica de lectura reduce QPS a la BD.

decision: >
  Cache-aside con Redis, TTL de 5 minutos e invalidación al escribir.

consecuencia: >
  Latencia p95 de lecturas baja a menos de 50 ms. Coste: los cambios
  tardan hasta 5 min en verse y sumar mitad de pieza a operar.

alternativas: [write-through, write-back]
supuestos: { ratio_lectura_escritura: "100:1", frescura_tolerada_min: 5 }

Errores comunes a evitar

  • Saltar al papel: diseñar antes de preguntar los requisitos. Síntoma: sistema con features que nadie pidió.
  • Sin números: «escalable» sin QPS ni almacenamiento no decide nada.
  • Una sola pieza: el monolito total sin exponer cómo se partiría en el futuro, o el microservicio por microservicio.
  • Ignorar las fallas: nadie pregunta «¿y si este nodo muere?» y el diseño no tiene respuesta.
  • Argumentar contra el entrevistador: ante un reto se explica el trade-off y se ajusta, no se pelea.

Checklist de revisión final

Antes de dar por terminado cualquier diseño —pizarra o documento— pásalo por esta lista:

def revisar_diseno(d: dict) -> list:
    """Puntos de revisión: devuelve los que aún no están cerrados."""
    pendientes = []
    if not d.get("qps"):
        pendientes.append("estimar qps y pico")
    if not d.get("almacenamiento"):
        pendientes.append("estimar almacenamiento y retención")
    if not d.get("clave_particion"):
        pendientes.append("definir la clave de partición")
    if "replica" not in d and "shard" not in d:
        pendientes.append("explicar cómo escala la base por encima de 1 nodo")
    if not d.get("cola"):
        pendientes.append("decidir si alguna tarea pesada va por cola")
    if not d.get("cache"):
        pendientes.append("elegir dónde se cachea (y el TTL)")
    if not d.get("tradeoffs"):
        pendientes.append("nombrar qué se sacrifica en cada decisión")
    if not d.get("falla"):
        pendientes.append("responder qué pasa si el nodo central muere")
    return pendientes

diseno = {
    "qps": 4167, "almacenamiento": "260 GB/año",
    "clave_particion": "usuario_id",
    "replica": True, "cache": {"ttl_s": 300}, "cola": "metricas",
    "tradeoffs": ["frescura_vs_lecturas"],
}
print(revisar_diseno(diseno))   # lo que falta por cerrar

Con este checklist cerraste el curso completo: ya puedes enfrentar una entrevista de system design, revisar un diseño ajeno con criterio y defender el tuyo con números y trade-offs explícitos.

Ejercicio

  1. Toma uno de los cuatro casos del módulo (URL shortener, chat, feed o búsqueda) y pásalo por el checklist: ¿qué falta cerrar en tu diseño?
  2. Practica el framework completo con un cronómetro de 45 minutos: requisitos (5 min), estimaciones (3), API y datos (5), componentes (10) y trade-offs (resto).
  3. Escribe el ADR de una decisión real de tu diseño usando el YAML de la lección.

Resumen

  • El framework en 5 pasos ordena la sesión y evita saltarse lo que da puntos.
  • Los diagramas se leen de izquierda a derecha, con flechas etiquetadas y decisiones numeradas.
  • Un trade-off se comunica con beneficio, precio y plan B; los ADR lo dejan escrito.
  • Los errores típicos son diseñar sin requisitos, sin números y sin considerar fallas.
  • El checklist de revisión cierra el círculo y garantiza un diseño defendible.
