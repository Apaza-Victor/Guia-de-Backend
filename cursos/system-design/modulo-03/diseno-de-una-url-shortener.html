Caso: URL shortener

🧠 Experto 11 min System Design Módulo 3 · Diseño completo

1. Requisitos

Comencemos declarando alcance y supuestos, como dicta el método:

  • Funcionales: crear una URL corta a partir de una larga; redirigir la corta a la original; clave personalizada opcional; expiración opcional.
  • No funcionales: p99 de la redirección bajo 100 ms; disponibilidad 99.9%; la creación debe funcionar siempre (CP en escritura); consistencia eventual aceptable en redirecciones.
  • Supuestos: 2 millones de usuarios activos diarios, ~1 URL por usuario al día, 10 visitas por URL al día, ratio lectura/escritura 100:1.

Este alcance descarta por diseño cosas caras que nadie pidió: cuentas, análisis avanzado, edición de URLs.

2. Estimaciones

Convertimos los supuestos en números que dimensionan todo lo demás:

SEG_DIA = 86400
DAU = 2_000_000

escrituras_dia = DAU * 1                 # 1 URL por usuario al día
lecturas_dia = escrituras_dia * 10       # 10 visitas por URL
qps_escritura = escrituras_dia / SEG_DIA
qps_lectura = lecturas_dia / SEG_DIA

print(f"Escrituras/día: {escrituras_dia:,.0f} → QPS esc: {qps_escritura:.1f}")
print(f"Lecturas/día:  {lecturas_dia:,.0f} → QPS lec: {qps_lectura:.0f}")

TAMANO_REGISTRO = 500
bytes_anio = lecturas_dia * TAMANO_REGISTRO * 365
print(f"Almacenamiento 1 año: {bytes_anio/1024**3:.1f} GB")

# Cuántas claves hay disponibles con base62 según longitud
def combinaciones(longitud):
    return 62 ** longitud

for n in (5, 6, 7):
    if combinaciones(n) >= lecturas_dia * 2:
        print(f"Claves de {n} chars cubren {combinaciones(n):,}")

# Con 6 caracteres: 56.8 mil millones de combinaciones → de sobra.

Conclusiones: las escrituras son triviales (≈23 QPS); las lecturas (≈1.389 QPS promedio, pico ~4.000) se alivian con caché. El almacenamiento de un año se mide en centenares de GB: una base relacional con sharding por clave alcanza.

3. Generación de claves

El corazón del diseño: ¿de dónde salen claves cortas, únicas y no adivinables de más? El enfoque clásico usa base62 (a-z, A-Z, 0-9) con un contador global o la técnica del hash + colisión (MD5 truncado). La opción más limpia es un ID secuencial convertido a base62: cada número produce una clave reversible y sin colisiones.

ALFABETO = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
BASE = len(ALFABETO)  # 62

def id_a_clave(numero: int) -> str:
    """Convierte un ID numérico en una clave corta de 6-7 caracteres."""
    clave = []
    n = numero
    while n > 0:
        n, resto = divmod(n, BASE)
        clave.append(ALFABETO[resto])
    return "".join(reversed(clave)).rjust(6, "0")

def clave_a_id(clave: str) -> int:
    numero = 0
    for ch in clave:
        numero = numero * BASE + ALFABETO.index(ch)
    return numero

# Un contador global en la base (o un rango de tickets) alimenta el ID.
ids = [1, 62, 63, 1000, 9999999]
for i in ids:
    print(f"{i:>8} -> {id_a_clave(i)}")

print(clave_a_id(id_a_clave(1000)) == 1000)  # reversible

En producción el contador se reemplaza por un generador de IDs distribuido (por ejemplo, un rango de tickets por nodo), porque un contador único es un punto único de fallo. La técnica de los rangos: el nodo 1 usa [1..1000), el 2 [1000..2000)… así cada nodo genera claves sin red.

4. API y flujo de redirección

La API es diminuta: un endpoint de creación y la redirección. El contrato abierto queda claro para el cliente:

POST /api/v1/urls         2026-09-21 10:00:00 request
{
  "url": "https://primerpaso.dev/blog/sistema-de-pagos-escalable",
  "clave_personalizada": "pagos-2026",
  "expiracion": "2027-09-21"
}

201 Created
{
  "clave": "pagos-2026",
  "url_corta": "https://s.primerpaso.dev/pagos-2026",
  "expiracion": "2027-09-21"
}

GET /pagos-2026
  → DNS resuelve, el LB enruta, la caché falla → la BD lo busca
  → 301 Moved Permanently, Location: https://primerpaso.dev/.../

La redirección usa 301 (permanente): los navegadores y buscadores cachean el salto, aliviando al sistema; con 302 (temporal) cada visita pasa por el servidor y podemos medir clics. La elección depende de si necesitamos métricas por click: la mayoría de los acortadores usan 302 y miden.

5. Caché y escalado

El flujo final, con la caché delante:

import redis

REDIRECCIONES = redis.Redis(host="cache", decode_responses=True)

def resolver(clave: str) -> str | None:
    """Cache-aside: la caché absorbe el ~99% de las lecturas."""
    cacheado = REDIRECCIONES.get(f"url:{clave}")
    if cacheado is not None:
        return cacheado
    fila = urls_db.buscar_por_clave(clave)          # miss → BD
    if fila is None:
        return None
    REDIRECCIONES.setex(f"url:{clave}", 3600, fila["url_larga"])
    return fila["url_larga"]

Las estrategias de escalado se añaden en el orden natural:

  • Réplicas de lectura para absorber el QPS de redirección que no cubre la caché.
  • Sharding por hash de la clave cuando la tabla de URLs supere unos cientos de GB: cada shard guarda un rango de combinaciones y el resolutor elige el shard por hash(clave) % N.
  • Cola para métricas: cada click no espera al escritura de la métrica; va a una cola y un worker agrega contadores en batch.

Así quedan los números que cerramos en el diseño: escrituras leves son gratis, las lecturas viven en la caché con p99 de milisegundos, y el almacenamiento se mantiene en unidades manejables de una sola máquina por unos años.

Ejercicio

  1. Calcula con los scripts de la lección qué QPS de lectura y almacenamiento a 5 años tendrías si cada usuario creara 5 URLs al día.
  2. Modifica id_a_clave para impedir claves ofensivas (por ejemplo, saltando combinaciones que contengan palabras de una blacklist) y describe dónde pondrías esa validación.
  3. Responde: ¿usarías 301 o 302 para este producto y por qué? ¿Qué cambiaría si el producto vendiera «reportes de clics por campaña»?

Resumen

  • Requisitos y supuestos acotados primero: escrituras ligeras, lecturas dominantes (100:1).
  • La clave base62 de 6 caracteres cubre 56 mil millones de combinaciones y es reversible.
  • El ID se genera con rangos de tickets distribuidos para no crear un contador único.
  • Redirección 301 (cacheada por el cliente) o 302 (mide cada clic).
  • Cache-aside + réplicas + sharding por clave + cola de métricas son el camino de escalado.
