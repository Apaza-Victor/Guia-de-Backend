Backups y restauración

🌱 Principiante 10 min Bases de Datos Módulo 6 · MySQL y PostgreSQL

Introducción

El día que se borra algo importante, no importa lo bien que diseñaste tu esquema: importa si el respaldo y la restauración funcionan. Un backup que nunca se prueba no es un backup. En esta lección haces ambas cosas.

Backup con mysqldump

Backup con pg_dump

Diseñar la estrategia

  • Frecuencia: elige según el daño aceptable: diaria, horaria o continua.
  • Retención: guarda varios días/semanas para revertir errores «que aparecen tarde».
  • Offsite: copia el backup fuera del mismo disco/servidor (nube, otro host).
  • Automatización: usa cron o el planificador de tareas; los humanos olvidan.
  • Recuperación ante desastres: define un paso a paso documentado para volver en < X minutos.

PITR y el WAL

Los motores modernos guardan cada confirmación en un log de escritura anticipada (WAL). Combinando un backup base + los WAL posteriores puedes restaurar «al minuto del accidente» (PITR, point-in-time recovery). En producción esto reduce la pérdida de un día a segundos.

Verificar el backup

Operación obligatoria cada cierto tiempo: restaurar en una base de prueba y comparar conteos de filas o un checksum. Si la restauración falla, el backup no existía.

Ejercicio

  1. Con tu base de práctica, haz un mysqldump o pg_dump.
  2. Borra una tabla por error y «vuelve en el tiempo» restaurando el dump.
  3. Escribe la política de backup de tu proyecto: frecuencia, retención y lugar.

Resumen

  • mysqldump y pg_dump generan respaldos lógicos portables.
  • Restaurar es la prueba que valida el procedimiento.
  • Automatiza, retén varias generaciones y guarda en otro sitio.
  • El WAL habilita recuperación al minuto (PITR).
  • Un backup sin test de restauración es una ilusión.
