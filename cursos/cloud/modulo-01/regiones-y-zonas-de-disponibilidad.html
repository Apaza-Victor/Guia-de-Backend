Regiones y zonas de disponibilidad

🔥 Avanzado 10 min Cloud para Backend Módulo 1 · Fundamentos

El mapa de la nube

Cuando creas un recurso eliges dónde. Esa elección no es neutra: define la latencia para tus usuarios, el cumplimiento legal de tus datos y tu capacidad de sobrevivir a fallos. El modelo físico: región jurídica + zonas de disponibilidad dentro de ella.

Regiones

Una región es una zona geográfica con sus propios datacenters (ej. AWS: us-east-1, eu-west-1, sa-east-1; GCP: us-central1, europe-west1; Azure: eastus, westeurope). Al elegir región consideras:

  • Latencia: primera pregunta para una API pública; acércate a la audiencia.
  • Cumplimiento: leyes de datos (GDPR en Europa, RGPD en LATAM) exigen que la data viva en ciertos países.
  • Precio: no todas las regiones cobran igual.
  • Servicios: no todo lo nuevo está en todas las regiones.

Zonas de disponibilidad (AZs)

Dentro de una región hay 3 o más zonas de disponibilidad: datacenters aislados entre sí (energía, red y refrigeración independientes), conectados por fibra de baja latencia. Si una AZ se cae (tormenta, corte energético), las otras siguen vivas.

Diseñar para sobrevivir

Un Backend de producción se reparte entre al menos dos AZs: instancias espejo, base gestionada con réplica y un balanceador enfrente. En la práctica:

La lección: la alta disponibilidad se diseña, no se decreta. Una instancia "en la nube" sin réplica sigue siendo un punto único de fallo.

Decisión práctica

  • App local/LATAM: región cercana (sa-east-1 / southamerica-east1 / brazilsouth).
  • Público global: regiones múltiples + CDN y replicación de datos.
  • Startup MVP: una región, dos AZs, base con réplica; no más.

Ejercicio

  1. Elige la región para una app de usuarios latinos y justifica con latencia y cumplimiento.
  2. Dibuja cómo montarías 2 instancias en 2 AZs con un balanceador.
  3. ¿Qué pasaría con tu API si la pusieras en una sola AZ y se cae el datacenter?

Resumen

  • La región define latencia, ley y precio; las AZs definen tu resiliencia.
  • Las zonas de disponibilidad son datacenters aislados dentro de la región.
  • Repartir instancias en 2+ AZs elimina el punto único de fallo del hardware.
  • La alta disponibilidad se diseña desde el primer día, no después del incidente.
