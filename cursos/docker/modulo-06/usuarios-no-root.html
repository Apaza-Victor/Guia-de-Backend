Usuarios no root y capabilities

🔥 Avanzado 11 min Docker Módulo 6 · Seguridad en contenedores

Introducción

La mayoría de imágenes por defecto ejecutan como root. Si un atacante explota tu aplicación dentro del contenedor, ese root solo está limitado por un puñado de namespaces: demasiado poco para dormir tranquilo.

La solución es ejecutar como un usuario sin privilegios y recortar las capabilities, esos poderes especiales que el kernel concede a los procesos con permisos elevados.

Definición

Las capabilities son unidades de privilegio que el kernel otorga a procesos (CHOWN, NET_BIND_SERVICE, DAC_OVERRIDE...). Ejecutar sin root y descartar las que no necesitas limita lo que un proceso comprometido puede hacer.

Por qué importa. Un proceso no root no puede modificar ficheros sensibles del host ni escalar fácilmente. Reducir capabilities elimina vectores de ataque concretos sin perder funcionalidad.

Cuándo usarlo. Siempre en producción, y especialmente cuando ejecutas imágenes de terceros cuyos scripts 'de instalación' hacen trucos como root.

Conceptos clave

  • USER en el Dockerfile: el proceso arranca con ese usuario y grupo.
  • Capabilities: poderes granulares del kernel (CHOWN, NET_ADMIN, SETUID...).
  • cap-drop ALL: elimina todas las capabilities y añade solo las imprescindibles.
  • no-new-privileges: impide escalar privilegios incluso si hay un binario setuid.
  • host UID mapping: usar rangos de ids para evitar colisiones con el host.

Ejemplo básico

Ejecutar tu servicio con un usuario sin privilegios y sin capabilities peligrosas.

Ejemplo intermedio

Lo mejor es dejarlo escrito en el Dockerfile para que la imagen ya sea segura por defecto.

Ejemplo real

Una pasarela de pagos detectaba escapes de contenedores en fase beta. El análisis mostró que la mayoría usaban procesos root y capabilities de red demasiado amplias. Con usuario dedicado y cap-drop ALL, el escape quedó neutralizado en la mayoría de escenarios.

  • Define un usuario y grupo con ids explícitos y estables.
  • Revisa las capabilities de un contenedor con docker inspect y capsh.
  • Añade no-new-privileges para reforzar la barrera del setuid.
  • Prueba la imagen en un entorno con capacidad de escritura ajustada.

Combina el usuario no root con read-only y tmpfs para que ni /etc ni la raíz sean escribibles.

Explicación

  • La directiva USER cambia el uid/gid efectivo del proceso, pero no ocurre mágicamente: los ficheros deben pertenecer a ese usuario.
  • Docker Engine pone a disposición un conjunto de capabilities por defecto; --cap-drop ALL las quita todas y re-estableces las que necesites.
  • Un proceso con todas las capabilities puede montar unidades, cambiar owners o manipular la red del host.
  • no-new-privileges es una garantía adicional contra la escalada vía binarios setuid.
  • Las imágenes base como alpine tienen menos herramientas, lo que complica la vida del atacante a la vez que reduce tu superficie.

Errores comunes

  • Crear el usuario no root pero olvidar darle permisos sobre los ficheros de la app.
  • Aplicar cap-drop ALL y romper el arranque por necesitar un puerto privilegiado.
  • Usar USER root para 'simplificar' la instalación de dependencias en el runtime.

Buenas prácticas

  • Comprueba tu imagen con: docker run --user 10001:10001 --entrypoint whoami imagen.
  • Documenta las capabilities mínimas junto al Dockerfile para que el equipo sepa por qué están.
  • En Kubernetes, define securityContext con runAsNonRoot y allowPrivilegeEscalation: false.

Ejercicio

  1. Crea un Dockerfile con usuario no root para tu API y verifica quién ejecuta el proceso.
  2. Intenta escribir en /etc dentro de un contenedor read-only y observa el error.
  3. Lista las capabilities de un contenedor tuya con y sin --cap-drop ALL.

Resumen

  • Ejecutar sin root y con capabilities mínimas reduce drásticamente el poder de un atacante.
  • El Dockerfile debe declarar el usuario y la imagen debe ser segura por defecto.
  • Combina USER, cap-drop ALL, no-new-privileges y read-only para una defensa real.
