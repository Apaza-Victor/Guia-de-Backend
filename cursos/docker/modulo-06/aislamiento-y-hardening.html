Aislamiento y hardening del motor

🔥 Avanzado 11 min Docker Módulo 6 · Seguridad en contenedores

Introducción

Cuando endureces la imagen y el proceso, queda una última frontera: el propio motor y las syscalls que el kernel deja ejecutar. Un proceso que huye del namespace necesita syscalls específicas; tú puedes cerrar esa puerta.

El runtime de Docker soporta filtros seccomp, perfiles AppArmor y SELinux, además de opciones como no-new-privileges o el bloqueo de automount. Este módulo une todas las piezas en un perfil de aislamiento.

Definición

El hardening del host restringe qué syscalls puede hacer un contenedor (seccomp), qué paths y capabilities concede AppArmor, y qué operativas adicionales como el montaje se bloquean, reduciendo el potencial de escalada al host.

Por qué importa. Aunque el proceso esté 'dentro' de un contenedor, las syscalls viajan al kernel del host. Filtrarlas limita la superficie para escapes y ataques de kernel.

Cuándo usarlo. Siempre que el host corra código externo, y de forma obligatoria cuando proceses datos no confiables o ejecutes imágenes de terceros.

Conceptos clave

  • Syscall: la llamada al kernel; el contenedor la ejecuta en el named kernel del host.
  • seccomp: perfil que permite o niega syscalls concretas.
  • AppArmor: perfil de acceso que restringe paths, networks y capabilities.
  • no-new-privileges: impide ganar privilegios de binarios setuid.
  • Read-only rootfs: el sistema de ficheros raíz no se puede modificar.

Ejemplo básico

Reforzar el runtime de arranque combinando read-only, no-new-privileges y capabilities mínimas.

nginx corre sin capacidad de escritura, sin privileges y sin capabilities de red salvo las del arranque.

Ejemplo intermedio

Aplicar un perfil seccomp que solo permite las syscalls necesarias (modo estricto) en una imagen propia.

Ejemplo real

Un proveedor de SaaS ejecuta cientos de servicios multi-tenant del mismo pool. Cada uno corre con read-only, cap-drop ALL y un perfil AppArmor propio, más seccomp personalizado para las imágenes internas. Un escape probado en benchmarks no consiguió romper ninguno de los perfiles.

  • Empieza con no-new-privileges y read-only: el coste de aplicar es mínimo.
  • Perfiles AppArmor y seccomp por imagen, revisables y versionados.
  • No compartas imágenes con permisos privilegiados en tu registry.
  • Mide el impacto de los perfiles en las APIs SLO antes de estresar.

El runtime de contenedores modernos (containerd, cri-o) permite aplicar los mismos conceptos en Kubernetes vía securityContext.

Explicación

  • Las syscalls de un contenedor se ejecutan en el kernel del host: la frontera definitiva es ese kernel.
  • seccomp audita o bloquea las syscalls antes de que toquen los subsistemas sensibles.
  • AppArmor controla el acceso a rutas y operaciones más allá de las syscalls.
  • Read-only rootfs no impide escribir en /tmp o en volúmenes montados: define esos destinos explícitamente.
  • El conjunto mínimo de opciones robustas: USER, cap-drop ALL, no-new-privileges, read-only, tmpfs acotado.

Errores comunes

  • Depender de una única capa de aislamiento y del 'contenedor = seguro'.
  • Montar sockets, /proc o /sys del host en el contenedor.
  • Aplicar no-new-privileges a procesos que legítimamente necesitan setuid.

Buenas prácticas

  • Automatiza el perfil de hardening para que sea el default de tu plataforma.
  • Valida los perfiles con pentest y benchmarks (CIS Docker Benchmark).
  • Revisa versiones de kernels para parches de vulnerabilidades del kernel compartido.

Ejercicio

  1. Arranca tu API con read-only y resuelve los tmpfs que necesita.
  2. Escribe un perfil seccomp mínimo y ejecuta tu imagen con él.
  3. Comprueba un escape real: intenta montar el host desde un contenedor con todas las opciones por defecto.

Resumen

  • El aislamiento en runtime filtra syscalls, acceso y privilegios en el borde del kernel.
  • seccomp, AppArmor, read-only y no-new-privileges son tu cinturón de seguridad.
  • El hardening marca la diferencia entre una brecha contenida y un host comprometido.
