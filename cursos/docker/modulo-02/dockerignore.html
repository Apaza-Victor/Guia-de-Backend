El build context y .dockerignore

🔧 Intermedio 9 min Docker para Backend Módulo 2 · Imágenes y Dockerfile

Qué es el contexto

El . del docker build -t x . es el contexto: todo su contenido viaja al daemon antes de construir. `node_modules`, `.git`, logs o un .env tuyo suben al engine aunque no los copies. Por eso necesitas el .dockerignore.

El .dockerignore mínimo de un backend

Por qué importa (y cuánto)

  • Seguridad: secretos y claves de tu máquina no deben entrar.
  • Velocidad: un repo de 200MB se envía entero en cada build.
  • Paridad: evita que se copie node_modules de tu SO y rompa la imagen Linux.
  • Cache: los COPY que incluyen carpetas grandes invalidan capas en vano.

Sintaxis: cómo se limpia la lista

Verificar lo que entra

Ejercicio

  1. Crea un .dockerignore en tu proyecto de backend.
  2. Comenta node_modules → el contexto se dispara.
  3. Mide las diferencias del sending context en dos builds.

Resumen

  • Todo el contexto viaja al daemon, copies o no.
  • node_modules, .git, logs y .env no deben entrar.
  • El ! re-incluye; los comentarios documentan.
  • Un contexto gordo = build lento + riesgo de secretos.
