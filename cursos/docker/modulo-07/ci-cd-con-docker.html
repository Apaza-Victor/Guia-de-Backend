CI/CD con Docker

🔥 Avanzado 10 min Docker Módulo 7 · Docker en producción a escala

Introducción

La promesa de Docker, 'funciona en mi máquina', solo se cumple cuando la imagen que se despliega es exactamente la que se probó. El CI/CD convierte cada cambio de código en una imagen construida, escaneada y desplegada de forma automática.

El pipeline ideal construye una imagen con un tag reproducible, la somete a pruebas (unitarias, contrato y escaneo), la publica en un registry y la despliega solo si todo pasó. Ningún humano debería escribir docker build a mano en producción.

Definición

El CI/CD con Docker encadena la construcción de la imagen, el escaneo y las pruebas, la publicación en el registry y el despliegue en los entornos, todo en el mismo formato de imagen que se probó.

Por qué importa. Las imágenes inmutables y los pipelines automatizados eliminan la deriva entre entornos y permiten rollback instantáneo a un artefacto conocido.

Cuándo usarlo. Desde el primer proyecto serio: un pipeline mínimo (build + test + push) ya paga su coste y se amplía luego.

Conceptos clave

  • Artefacto único: una imagen es el mismo binario en dev, staging y producción.
  • Tag reproducible: versión + commit (mi-api:1.2.0-abc123) para trazabilidad.
  • Registry: repositorio central de imágenes (Docker Hub, ECR, GHCR).
  • Cache del build: aprovecha capas en CI para acelerar el pipeline.
  • Deploy con la misma imagen: lo que escaneaste y probaste es lo que corre.

Ejemplo básico

Construir, publicar y desplegar una imagen en GitHub Actions.

Ejemplo intermedio

Añadir escaneo y despliegue: la imagen pasa las pruebas y el escaneo antes de llegar al entorno.

Ejemplo real

Un equipo de deliveries despacha cada dos horas gracias a: imagen con tag del commit, pruebas y escaneo en el pipeline, y despliegue automático en staging con aprobación manual para producción. El rollback es cambiar el tag del servicio en el stack.

  • Versiona los tags: usa un semver del commit no solo latest.
  • Caché del build multicapa (buildx) para pipelines rápidos y baratos.
  • Protege el registry con autenticación y firmado de imágenes.
  • Separa el pipeline de staging de la aprobación de producción.

El artefacto desplazado es exactamente el mismo que el probado: cero deriva entre entornos.

Explicación

  • El hash del commit como tag hace cada imagen trazable a su código fuente.
  • El escaneo en el mismo pipeline evita que una imagen vulnerable llegue a registry.
  • La publicación en registry central garantiza que los nodos bajen la imagen del lugar correcto.
  • El despliegue declarativo por stack permite actualizar con la misma herramienta de orquestación.
  • Los pipelines de la nube (GH Actions, GitLab CI, Jenkins) ofrecen auth integrada con los registry.

Errores comunes

  • Desplegar con imágenes construidas a mano y no versionadas.
  • Usar el tag latest en producción: no sabes qué versión real corres.
  • No cachear el build y multiplicar el tiempo del pipeline.

Buenas prácticas

  • Empieza con un pipeline mínimo y añade escaneo al día siguiente.
  • Usa el contexto del CI para no sumar fricción: secrets desde el proveedor.
  • Regístrate un SBOM en el release repo para cumplimiento y auditoría.

Ejercicio

  1. Crea un flujo de GitHub Actions que construya y publique tu imagen.
  2. Añade el paso de escaneo con severidad y pruébalo con una versión intencionalmente vieja.
  3. Haz un deploy y un rollback modificando solo el tag del stack.

Resumen

  • El CI/CD garantiza que la imagen probada sea la desplegada.
  • Tags reproducibles, escaneo y registry central son el núcleo del pipeline.
  • La misma imagen viaja de dev a producción; el rollback es cambiar un tag.
