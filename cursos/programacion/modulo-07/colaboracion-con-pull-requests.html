Colaboración con pull requests

⚙️ Intermedio 11 min Programación para Backend Módulo 7 · Trabajo en equipo y herramientas

Introducción

El pull request (PR) es la puerta por la que cada cambio entra al código compartido. Más que una petición técnica, es una conversación: el autor explica qué hace y por qué, y los revisores señalan riesgos antes de que el código llegue a producción.

Dominar este ritual cambia tu forma de programar: sabes que alguien leerá tu código, así que lo escribes pensando en que otro lo entienda, no solo en que funcione.

Definición

Un pull request es una propuesta de cambio sobre una rama que otro desarrollador o un bot deben revisar antes de integrarla. Encierra diff, comentarios, discusión y estado de las comprobaciones.

Por qué importa. La revisión por pares atrapa bugs, aclara decisiones y distribuye conocimiento: deja de existir el único que entiende cada parte del backend.

Cuándo usarlo. Úsalo para todo cambio que toque lógica de negocio, modelos de datos o endpoints. Para cambios triviales de un archivo con tests verdes, un PR corto también vale.

Conceptos clave

  • Diff: la vista de exactamente qué líneas cambian (o se borran).
  • Revise/apprure: aprobar, pedir cambios o comentar sin bloquear.
  • Review en sitio: comentar sobre la propia línea de código.
  • Checks: tests, linters y compilaciones que corren sobre el PR.
  • Merge, squash y rebase: las tres formas de integrar la rama.

Ejemplo básico

Creamos un PR desde la rama de una funcionalidad con una descripción que orienta al revisor.

Ejemplo intermedio

La revisión suele pedir cambios. El autor los aplica en la misma rama y el PR se actualiza solo; la conversación queda documentada.

Ejemplo real

Un PR de backend profesional incluye tests, cambios de esquema y una descripción de impacto. El checklist de revisión fija el nivel de calidad.

  • ¿La lógica está testeada y los tests pasan en CI?
  • ¿Se respetan los contratos de la API y la versión del recurso?
  • ¿No cuelga algún dataset o credencial de ejemplo?

Los PR grandes y de una sola pieza se revisan peor. Fracciona el trabajo y revisa bloques pequeños.

Explicación

  • El cuerpo del PR explica el porqué porque el diff solo muestra el qué.
  • Los checks en CI corren los tests antes de que nadie revise a mano.
  • Un comentario en la línea correcta ahorra explicar contextos enteros.
  • Aprobación no es confianza ciega: es fecha límite para la corrección.
  • El squash al merge limpia el historial: varios commits de trabajo pasan a ser uno.

Errores comunes

  • Crear PRs gigantes de cientos de archivos imposibles de revisar.
  • Resolver comentarios en la cabeza sin subir los cambios.
  • Aprobar sin ejecutar: "parece bien" no es una revisión.

Buenas prácticas

  • Escribe el PR como una mini especificación de lo que hace y cómo probarlo.
  • Mantén la PR abierta poco tiempo; la revisión en caliente es mejor.
  • Usa plantillas de PR con checklist para que nadie olvide tests.
  • Revisa primero los archivos de pruebas: te cuentan la intención.

Ejercicio

  1. Abre un PR que combine una funcionalidad y sus tests en una sola rama.
  2. Revisa un PR de un compañero y pide un cambio justificado con un comentario.
  3. Configura una checklist de revisión en la plantilla de PR de tu proyecto.

Resumen

  • Un PR es una propuesta de cambio revisada por pares antes de integrarse.
  • La revisión en línea y los checks automáticos elevan el nivel del código.
  • El ritual completo: descripción clara, tests verdes y discusión resuelta.
