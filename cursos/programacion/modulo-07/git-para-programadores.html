Git para programadores

⚙️ Intermedio 12 min Programación para Backend Módulo 7 · Trabajo en equipo y herramientas

Introducción

Hasta ahora has escrito código solo en tu editor. En producción, sin embargo, el código vive en un repositorio que comparte todo el equipo: cada cambio tiene historia, autor y motivo. Git es el estándar para que eso sea posible.

Esta lección no trata de memorizar comandos: trata del flujo mental de guardar trabajo en pequeñas instantáneas comprensibles que después puedas revisar, comparar y restaurar.

Definición

Git es un sistema de control de versiones que registra los cambios de tu proyecto en instantáneas llamadas commits. Cada commit guarda un estado del código con autor, fecha y mensaje.

Por qué importa. En un backend real necesitas saber qué cambió, quién lo cambió y por qué para colaborar sin pisarte y para poder revertir un fallo en producción en segundos.

Cuándo usarlo. Úsalo siempre, incluso en proyectos de una sola persona: abre una rama por funcionalidad, haz commits pequeños y deja git add solo para los archivos que tocan el cambio.

Conceptos clave

  • Commit: una instantánea atómica del código con un mensaje claro.
  • Rama (branch): una línea de trabajo independiente que no rompe main.
  • Working tree, stage y repositorio: los tres espacios donde vive cada cambio.
  • git diff: la lectura obligada antes de cada commit para revisar qué vas a guardar.
  • git log: el historial legible de todo lo que ha pasado en el proyecto.

Ejemplo básico

El ciclo básico de un cambio con PHP: añadir los archivos que tocan esa tarea, revisar el diff y crear un commit con mensaje descriptivo.

* commit 8f3c9a2 (HEAD -> feature/login-intentos) feat(auth): valida intentos de login fallidos

Ejemplo intermedio

Cuando la funcionalidad viene de otra rama, la integramos y resolvemos los conflictos que Git no puede decidir por nosotros.

Ejemplo real

En un equipo de backend la regla es una rama por tarea, con el id del ticket en el nombre, y ningún push directo a main. Así cada cambio es auditable y reversible.

  • Mensajes convencionales: feat, fix, refactor, docs, chore.
  • Commits atómicos: un cambio lógico por commit, no diez.
  • Nunca versiones archivos generados, .env ni credenciales.

El servicio de reset y su test forman un solo commit: si algo falla, se revierte todo o nada.

Explicación

  • git add mueve cambios al stage; el commit los fija en el historial.
  • Las ramas son punteros baratos: crea tantas como necesites.
  • Un conflicto no es un error: es una decisión de negocio que debes tomar tú.
  • Revisar git diff antes de commit evita commits sucios y secretos colados.
  • Un historial limpio convierte git log en documentación del producto.

Errores comunes

  • Hacer git add . sin mirar el diff y versionar el .env con credenciales.
  • Mensajes como "cambios" o "fix" que no explican el porqué.
  • Commitear archivos generados (vendor, storage/cache) llenando el repo de ruido.

Buenas prácticas

  • Configura un .gitignore con vendor/, .env y los archivos de caché.
  • Usa git diff --cached para revisar qué tienes en el stage.
  • Haz git log --oneline --graph por la mañana para ver el estado del equipo.
  • Revertir es mejor que borrar: git revert crea un commit que anula el problema.

Ejercicio

  1. Crea una rama por cada funcionalidad de tu proyecto PHP y haz un commit por tarea.
  2. Fuerza un conflicto modificando la misma línea en dos ramas y resuélvelo.
  3. Escribe cinco mensajes de commit con prefijos feat y fix para cambios reales.

Resumen

  • Git guarda instantáneas atómicas con historia y motivo de cada cambio.
  • Las ramas aíslan el trabajo y los merges integran decisiones.
  • El flujo profesional: una rama por tarea, commits pequeños y main protegido.
