Principios SOLID

14 min Avanzado PHP Código profesional

Introducción

Los proyectos crecen. Sin un diseño nítido, cada funcionalidad nueva rompe otra y el mantenimiento se vuelve tortura. SOLID es un acrónimo de cinco principios que mantienen el código flexible ante el cambio.

Definición

Single Responsibility (responsabilidad única), Open/Closed (abierto a extensión, cerrado a modificación), Liskov (sustitución), Interface Segregation (segregación de interfaces) y Dependency Inversion (inversión de dependencias). No son reglas mágicas sino señales: si violar uno duele, es que el diseño pide cambios.

Conceptos clave

  • S — una clase tiene una razón para cambiar: procesar, persistir, renderizar: cada cosa en su sitio.
  • O — añade funciones nuevas con nuevas clases (interfaces), no tocando las que ya van bien.
  • L — las clases hijas deben ser intercambiables por la clase padre sin romper.
  • I — interfaces pequeñas y específicas; no obligues a implementar lo que no se usa.
  • D — depende de abstracciones (interfaces), no de implementaciones concretas.

Ejemplo básico

Violación de S: una clase que hace demasiado:

PHPviola-s.php
class ControladorPedidos {
    public function guardar(array $pedido): void {
        $this->validar($pedido);
        $this->insertarEnBD($pedido);
        $this->enviarEmail($pedido);
    }
}
// Tres razones para cambiar = tres clases: Pedido, Repositorio, Notificador

Ejemplo intermedio

Separando responsabilidades, cada pieza cambia por su propia razón:

PHPcumple-s.php
class ValidadorPedido {
    public function validar(array $pedido): void { /* reglas */ }
}

class RepositorioPedido {
    public function guardar(array $pedido): void { /* SQL */ }
}

class NotificadorPedido {
    public function enviar(array $pedido): void { /* SMTP */ }
}

class FlujoPedido {
    public function __construct(
        private ValidadorPedido $validar,
        private RepositorioPedido $bd,
        private NotificadorPedido $mail
    ) {}

    public function procesar(array $pedido): void {
        $this->validar->validar($pedido);
        $this->bd->guardar($pedido);
        $this->mail->enviar($pedido);
    }
}

Ejemplo real

O y D: nueva funcionalidad con nueva clase, sin tocar lo existente:

PHPopenclosed.php
interface Descuento {
    public function aplicar(float $total): float;
}

class SinDescuento implements Descuento {
    public function aplicar(float $total): float { return $total; }
}

class DescuentoFijo implements Descuento {
    public function __construct(private float $cantidad) {}
    public function aplicar(float $total): float { return $total - $this->cantidad; }
}

class DescuentoPorcentaje implements Descuento {
    public function __construct(private float $pct) {}
    public function aplicar(float $total): float { return $total * (1 - $this->pct); }
}

function precioFinal(Descuento $d, float $total): float {
    return max(0, $d->aplicar($total));
}

echo precioFinal(new DescuentoFijo(20), 100);      // 80
echo "\n" . precioFinal(new DescuentoPorcentaje(0.1), 100);   // 90

Código completo

Código completo: notificadores con inversión de dependencias para crecer sin tocar nada:

PHPsolid-real.php
<?php

declare(strict_types=1);

interface Canal {
    public function notificar(string $mensaje): string;
}

class CanalEmail implements Canal {
    public function notificar(string $mensaje): string {
        return "Email enviado: $mensaje";
    }
}

class CanalSMS implements Canal {
    public function notificar(string $mensaje): string {
        return "SMS enviado (" . strlen($mensaje) . " chars)";
    }
}

class Campana {
    public function __construct(private Canal $canal) {}

    public function lanzar(string $titulo): string {
        return $this->canal->notificar($titulo);
    }
}

// Añadir un canal nuevo NO modifica Campana (O + D)
$r = new Campana(new CanalEmail());
echo $r->lanzar("Nuevo curso") . "\n";

$r2 = new Campana(new CanalSMS());
echo $r2->lanzar("Recordatorio");

Explicación

El controlador violación de S tiene tres razones para cambiar: validación, persistencia y envío. Separarlas en tres clases hace que cada una evolucione sola, y FlujoPedido las orquesta inyectándolas — el patrón D aparece ya aquí de forma natural.

El sistema de descuentos aplica O literalmente: añadir "DescuentoNavidad" solo exige una clase nueva que implemente Descuento; nada existente se modifica. Y la campaña, al depender de la interfaz Canal, puede usar Email, SMS o cualquier canal futuro sin tocar Campana. Esa flexibilidad es SOLID enganchado: programas contra la interfaz.

Errores comunes

  • Aplicar SOLID sin necesidad: añadir capas de abstracción a proyectos triviales.
  • Confundir escritura con lectura: "clases similares" no siempre significa herencia; prefiere composición.
  • Interfaces gigantes con 8 métodos de los que se usan 2 (viola I).
  • Depender de new ClaseConcreta() a pelo dentro de otras clases (viola D).

Buenas prácticas

  • Detecta la violación por el dolor (cambios que se propagan), no por dogma.
  • Inyecta dependencias por constructor e interfaces.
  • Mantén interfaces pequeñas (1-2 métodos): las de Un identificador, una acción.

Ejercicio

Registro extensible

Dificultad: Difícil
  1. Define la interfaz Registro con escribir(string): void.
  2. Implementa RegistroArchivo y RegistroConsola.
  3. Compón Aplicacion.__construct(private Registro $log) para que usarla con cualquiera no requiera cambios (O + D).

Resumen

  • S — una razón para cambiar por clase.
  • O — extiende con clases nuevas, no modificando lo estable.
  • D — depende de interfaces, inyectadas por el constructor.
