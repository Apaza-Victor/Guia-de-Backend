Comunicación síncrona

🔥 Avanzado 12 min Microservicios Módulo 2 · Comunicación

Introducción

En la comunicación síncrona, el servicio cliente espera la respuesta del servicio proveedor: envía una petición HTTP o gRPC y bloquea hasta recibir el resultado. Es el modelo más simple de entender y el más natural para operaciones que necesitan confirmación inmediata (¿creó la orden?, ¿aceptó el pago?).

Esta lección cubre REST, gRPC, HTTP y la pieza que casi siempre se olvida: los timeouts.

REST por HTTP/JSON

REST sigue siendo el estándar dominante entre microservicios: recursos, métodos HTTP y un contrato JSON sencillo de inspeccionar. Buena elección para APIs públicas y cuando la facilidad de depuración pesa más que el rendimiento puro.

Fíjate en el AbortSignal.timeout(2000): sin timeout, una llamada colgada puede bloquearte para siempre. El timeout es obligatorio en cualquier comunicación entre servicios.

gRPC

gRPC es RPC moderno sobre HTTP/2: los contratos se definen en protobuf, los mensajes son binarios y compactos, soporta streaming y generación de clientes en muchos idiomas. Es ideal para comunicación service-to-service de alto volumen con contratos versionados.

Las ventajas frente a REST: menor latencia (binario + HTTP/2), contratos fuertes compilados y timeouts nativos por llamada.

¿REST o gRPC?

La decisión equilibra humanos y máquinas:

  • API hacia el exterior (navegadores, socios): REST/HTTP+JSON casi siempre, por interoperabilidad.
  • Backend interno de alto volumen: gRPC, cuando el rendimiento y los contratos importan más que la inspección manual.
  • Ecosistema heterogéneo (frontend, scripters, integradores): REST es más accesible.
  • Streaming y payloads binarios: gRPC destaca claramente.

Timeouts: la regla de oro

En un sistema distribuido, toda llamada síncrona debe tener timeout. Sin él:

  • Un servicio lento hace que todos sus dependientes acumulen hilos bloqueados.
  • El problema escala: la latencia se propaga en cadenas de espera.
  • La base de datos se llena de conexiones ociosas y el sistema se cae por sobrecarga, no por fallo real.

Configura timeouts decrecientes hacia afuera: 3000 ms en la puerta, 2000 ms internos, 1000 ms hacia bases de datos. Así un fallo profundo no agota el tiempo del cliente.

Idempotencia

Cuando un timeout se dispara, no sabes si el proveedor procesó o no la operación. Reintentar puede duplicar un cobro o una orden. La solución es la idempotencia: el proveedor debe devolver el mismo resultado si recibe la misma operación dos veces.

El cliente envía un Idempotency-Key (o cargo_id) que el proveedor recuerda. Así el retry es seguro.

Ejercicio

  1. Escribe un cliente REST con timeout de 1 segundo a un endpoint de prueba y observa qué sucede al agotarse.
  2. Diseña la clave de idempotencia para una operación de cobro y explica cómo evita duplicados.
  3. Define los timeouts decrecientes para una cadena de 3 servicios y justifica los valores.

Resumen

  • La comunicación síncrona espera respuesta: petición → proceso → respuesta.
  • REST/HTTP+JSON es ideal para APIs externas y de depuración fácil.
  • gRPC aporta contratos fuertes, binario y streaming para el backend interno.
  • Los timeouts son obligatorios y deben ser decrecientes hacia afuera.
  • La idempotencia convierte los reintentos en operaciones seguras.
