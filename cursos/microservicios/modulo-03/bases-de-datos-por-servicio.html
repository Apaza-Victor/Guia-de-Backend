Bases de datos por servicio

🔥 Avanzado 12 min Microservicios Módulo 3 · Datos y resiliencia

Introducción

En un monolito hay una base de datos compartida: cualquier parte del código puede tocar tablas de cualquier dominio. Si aplicamos lo mismo a los microservicios, un cambio de esquema en la tabla de pagos afecta a todos. El principio database per service (una base por servicio) es el que mantiene a los servicios realmente independientes: cada servicio es el único dueño de sus datos.

Ownership de datos

Con una base por servicio, ningún otro servicio puede leer ni escribir directamente las tablas del dueño; solo puede pedirlos a través de su API. Esto crea cadenas que se respetan (los bounded contexts del módulo 1 quedan aislados también en datos):

Por qué no una base compartida

Una única base para todos los microservicios es una bomba de tiempo:

  • Acoplamiento de esquemas: renombrar o borrar una columna rompe a otros servicios que la usan.
  • Migraciones en conflicto: los administradores de cada equipo no pueden evolucionar su parte con libertad.
  • Todos compiten por las mismas conexiones, caché y locks.
  • Un servicio dormilón pesado sobrecarga la base de todo el sistema.

En cuanto dos equipos quieren cambiar «su» esquema al mismo tiempo, el monolito de datos resucita.

Datos poliplásticos

Cada servicio puede elegir la tecnología de datos que mejor le venga: PostgreSQL para transacciones estrictas, Redis para caché/contadores, Elasticsearch para búsqueda, MongoDB para documentos DTojista. La «base multidialecto» es una ventaja de los microservicios: el almacenaje deja de ser único e igual para todos.

El patrón Repository

La base por servicio se materializa en código con el patrón Repository: el dominio del servicio no habla de tablas, solo de objetos del negocio, y una capa de repositorio traduce entre ambos. Si la base cambia, solo cambia el repositorio:

Las transacciones ya no son globales

Cuando cada servicio tiene su propia base, Una transacción ACID multi-tabla desaparece: no existe un mojón único que garantice atomicidad entre pagos e inventario. En su lugar usamos compensación con sagas. Es el precio del aislamiento, y se gestiona con diseño, no con más joins.

Ejercicio

  1. Diseña la división de datos de un e-commerce (clientes, pedidos, pagos, inventario) con una BD por servicio y justifica cada motor.
  2. Explica tres problemas concretos de una base compartida.
  3. Escribe el repositorio que protege la tabla inventario frente a accesos externos.

Resumen

  • Cada servicio es el único dueño de sus datos: database per service.
  • Los demás servicios acceden a los datos ajenos solo por API, nunca por JOIN.
  • La base compartida acopla esquemas, migraciones y carga entre equipos.
  • El poliglotismo de datos permite el motor adecuado para cada dominio.
  • Sin transacción global, la coordinación se apoya en sagas y compensación.
