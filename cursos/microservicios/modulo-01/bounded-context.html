Bounded contexts

🔥 Avanzado 10 min Microservicios Módulo 1 · Fundamentos de microservicios

Introducción

La palabra «cliente» significa cosas distintas según el área de una empresa. Para ventas es quien compra; para finanzas es quien adeuda; para logística es una dirección de envío. Si un solo sistema modela al «cliente» de las tres formas, el modelo se vuelve ambiguo, contradictorio y frágil.

El bounded context (contexto acotado) es la frontera dentro de la cual un modelo de dominio tiene un significado único y no ambiguo. Es el concepto central de Domain-Driven Design (DDD) y la herramienta más fiable para definir dónde cortar microservicios.

El lenguaje ubicuo

Cada contexto acotado posee su propio lenguaje ubicuo: el vocabulario compartido entre el negocio y los desarrolladores dentro de esa frontera. Ese lenguaje define los términos exactos que usarás para clases, tablas, endpoints y eventos.

  • Contexto Ventas: `Pedido`, `LíneaDePedido`, `Descuento`, `Total`.
  • Contexto Pagos: `Cargo`, `Reembolso`, `Transacción`, `ProcesadorDePago`.
  • Contexto Inventario: `Producto`, `Stock`, `Almacén`, `Reserva`.

Nótese que Producto aparece en Ventas e Inventario, pero con significados distintos: en uno es el ítem que se vende, en el otro la unidad que se almacena. Nunca fuerces a ambos a compartir la misma tabla o la misma clase.

Context map

El context map es el diagrama que muestra cómo se relacionan los contextos entre sí. Los patrones de relación más comunes:

  • Shared Kernel: dos contextos comparten una parte pequeña del modelo (por ejemplo, un DTO de evento), pero el resto es privado.
  • Customer/Supplier: un contexto provee datos y el otro los consume tal cual los recibe.
  • Conformist: el contexto consumidor acepta el modelo del proveedor sin intentar traducirlo.
  • Anticorruption Layer (ACL): una capa traductora protege al contexto consumidor de los cambios del proveedor.

El patrón más recomendado entre microservicios es Shared Kernel mínimo (contratos de eventos) combinado con ACL cuando un servicio consume el modelo de otro.

Cómo los bounded contexts definen servicios

Cuando un frontend quiere mostrar el resumen de un pedido, no necesita unificar los tres modelos. Necesita una agregación que consulte a cada servicio. El contrato entre ellos se define con eventos y DTOs isomórficos, jamás con la clase interna del otro servicio.

El evento es un contrato acotado: Ventas define su significado, Pagos lo consume y cada uno actualiza sus propios datos. No comparten tablas ni clases.

Reglas para trazarlo en la práctica

  • Pregunta al negocio qué significa cada término en cada área; si hay dos significados, hay dos contextos.
  • Un servicio debe mapearse a un bounded context (o una parte cohesiva de él).
  • Los datos compartidos solo viajan como contratos de interfaz (eventos, DTOs), nunca como acceso directo a la base de datos.
  • Dos equipos que necesitan un mismo modelo con reglas distintas no deben compartir repositorio ni esquema.

Ejercicio

  1. Escoge una empresa conocida (un banco, un e-commerce) y lista 3 bounded contexts posibles.
  2. Para cada uno, escribe 4 términos de su lenguaje ubicuo.
  3. Identifica una entidad que aparezca en dos contextos con significados distintos y describe ambos modelos.

Resumen

  • Un bounded context es la frontera donde un modelo de dominio tiene significado único.
  • Cada contexto tiene su lenguaje ubicuo propio.
  • Los contextos se comunican con contratos (events, DTOs, ACL), no compartiendo tablas.
  • Son la herramienta base para decidir dónde cortar los microservicios.
