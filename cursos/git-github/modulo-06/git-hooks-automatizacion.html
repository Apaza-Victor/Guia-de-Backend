Git hooks y automatización local

⚙️ Intermedio 11 min Git y GitHub Módulo 6 · Colaboración avanzada y code review

Introducción

¿Cuántas veces se te escapó un error de lint, un secreto accidental o un test roto hasta el CI? Los Git hooks ejecutan tu automatización en el momento justo, en tu máquina, antes de que el problema salga de tu rama.

pre-commit, pre-push y commit-msg son los hooks estrella: formatean, lintan, testean y validan tus mensajes en cada movimiento. Compartidos con el equipo, la calidad no depende de la disciplina de nadie.

Definición

Los Git hooks son scripts que Git ejecuta automáticamente en momentos concretos de su ciclo (pre-commit, post-commit, pre-push, pre-rebase). Herramientas como pre-commit o husky los comparten con el equipo.

Por qué importa. Mueven la corrección al momento más barato posible: localmente, antes de que un fallo viaje al repo compartido y moleste a todos.

Cuándo usarlo. En cualquier repositorio con reglas de estilo, secretos o tests; son el primer escalón de la calidad por default.

Conceptos clave

  • Hook: script que se dispara en un momento del ciclo de Git.
  • pre-commit: se ejecuta antes de crear el commit; ideal para lint y format.
  • pre-push: se ejecuta antes de enviar a remoto; ideal para tests y builds.
  • commit-msg: valida el formato del mensaje de commit.
  • pre-commit (la herramienta): framework que gestiona hooks declarativos por archivo.

Ejemplo básico

Configurar pre-commit con un hook de linter de Python y de Secret skip.

Cada commit limpia espacios, líneas y valida el diff antes de dejar pasar.

Ejemplo intermedio

Hooks más potentes con husky y una herramienta de lint de mensajes (commitlint) para el primer commit.

Ejemplo real

Un incidente de fuga de credenciales se evitó porque el hook detectaba el patrón de API key (gitleaks) en pre-commit. El desarrollador que lo cometió recibió el aviso antes de hacer push; el equipo añadió el hook a su config compartida.

  • Comparte hooks en el repositorio para que todo el mundo los tenga en un clone.
  • Usa linters y secretes (gitleaks) dentro de pre-commit.
  • Permite escape rápido (SKIP=id) para casos justificados.
  • Mantén hooks rápidos: un hook de 10 segundos se ejecuta; uno de 2 minutos se saltea.

Los hooks son locales por naturaleza; los puedes versionar pero no forzar en otros si no los instalan.

Explicación

  • cada hook tiene props distintos: pre-commit ve el staging, pre-push ve el estado ya commitado listo para enviar.
  • pre-commit (la herramienta) gestiona entornos por repositorio sin interferencia global.
  • commit-msg valida el mensaje antes de que quede registrado.
  • Los hooks pueden acceder al árbol de trabajo; por eso suelen terminar modificando archivos (format).
  • Con SKIP o --no-verify puedes saltar los hooks: es deliberadamente fácil, porque a veces es legítimo.

Errores comunes

  • Construir hooks gigantes que tarden minutos: nadie quiere revisar antes de tu script.
  • No versionar .pre-commit-config.yaml y perder la config al clonar.
  • Ignorar el hook y hacer --no-verify por costumbre, saltando la protección.

Buenas prácticas

  • Empieza con el pre-commit estándar y añade linters de tu lenguaje.
  • Añade la detección de secretos al primer día: es la más potente por el coste.
  • Prueba los hooks en una rama aislada para no fastidiar al equipo.

Ejercicio

  1. Configura pre-commit con lint de estilo en tu repositorio.
  2. Añade un hook que ejecute los tests de tu proyecto.
  3. Crea un commit-msg hook y valida un mensaje inválido.

Resumen

  • Los Git hooks ejecutan tu calidad local, en el momento más barato de corregir.
  • pre-commit (la herramienta) y husky los comparten y mantener.
  • Lint, formato, secretos y mensajes pasan a ser automáticos.
