Protected branches y reglas del repositorio

⚙️ Intermedio 10 min Git y GitHub Módulo 6 · Colaboración avanzada y code review

Introducción

Un solo push descontrolado a la rama principal puede enviar un bug a producción sin que nadie se entere. Las branch protection rules existen para convertirlo en imposible: nadie 'edita main directamente' en un equipo profesional.

GitHub permite exigir reviews, comprobaciones de estado (CI) y actualizaciones antes de fusionar, además de impedir que se borren ramas de protección por accidente.

Definición

Las protected branches son ramas configuradas con reglas que impiden el push directo, exigen reviews aprobadas y comprobaciones de estado preceptivas, y pueden limitar quién puede eliminar o modificar la historia.

Por qué importa. Garantizan que el código de producción pasa siempre por revisión y por los checks automáticos, y protegen a la rama principal de cambios accidentales o maliciosos.

Cuándo usarlo. Aplica protección al menos a main y a las ramas de release desde el primer día; amplíalo según crezca el equipo.

Conceptos clave

  • Require pull request reviews: ningún merge sin una revisión aprobada.
  • Require status checks: el CI debe pasar antes de fusionar.
  • Require up-to-date branches: la rama está al día con main para no romperlo.
  • Restricciones de push: quién puede escribir directamente en la rama.
  • Rulesets: agrupación moderna de reglas por patrón de rama.

Ejemplo real

Un incidente de producción se originó en un push directo de un cambio 'urgente'. Tras aplicar branch protection con CI obligatorio, la excusa de la urgencia se resuelve con una hotfix branch, no con un bypass de la protección.

  • Exigir también los checks de escaneo y los tests de conflictos en el merge.
  • Proteger no solo main, sino release y cualquier rama con nombre de patrón catch-all.
  • Aplicar a las ramas de protección el 'require signed commits' si tu compliance lo pide.
  • Revisar quién puede modificar las reglas de protección.

Los rulesets modernos permiten además restricciones de no-rebase y de merges de squash/only.

Explicación

  • La protección se materializa en el plan de control de GitHub: la operación se bloquea antes de escribir.
  • Require status checks enlaza el merge con tu pipeline: si el CI falla, el botón de merge se bloquea.
  • Require up-to-date evita la 'ventana': fusionar sobre una base desactualizada rompe el historial.
  • Los rulesets aplican reglas a todos los branches que cuadren con un patrón, no solo a main.
  • La protección no impide la revisión: la hace obligatoria y la nota en el historial.

Errores comunes

  • Proteger main pero permitir push directo a release.
  • Exigir checks pero no 'require branches to be up to date'.
  • Dar permisos de admin a más personas de las necesarias.

Buenas prácticas

  • Empieza con revisión obligatoria y CI; añade 'up-to-date' al mes siguiente.
  • Utiliza rulesets nuevos: son el estándar y más legibles.
  • Documenta el flujo de hotfix para que nadie intente saltarse la protección 'por urgencia'.

Ejercicio

  1. Protege main con una revisión obligatoria y comprúebalo con un push directo.
  2. Configura un status check con tu CI y valida que el merge se bloquea al fallar.
  3. Define un ruleset para las ramas v*.*.* de releases.

Resumen

  • Las protected branches impiden el push directo y exigen fuerza bruta en forma de reviews y CI.
  • Los rulesets aplican reglas por patrón y protegen todo el historial.
  • La protección bien configurada previene accidentes sin frenar al equipo.
