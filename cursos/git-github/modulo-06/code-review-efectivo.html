Code review efectivo y comentarios constructivos

⚙️ Intermedio 11 min Git y GitHub Módulo 6 · Colaboración avanzada y code review

Introducción

Un code review no es una inspección policial: es una conversación técnica sobre cómo mejorar el código antes de que llegue a producción. Bien hecho, es la herramienta que más errores detecta por cada euro invertido y, de paso, la que forma al equipo.

El objetivo no es aprobar o rechazar tu lista de cambios, sino que entre todos el código quede mejor: más claro, más seguro y más mantenible, con comentarios que explican el porqué y no solo el qué.

Definición

El code review es la revisión sistemática de un cambio de código por otra persona antes de fusionarlo, enfocada en encontrar defectos, mejorar el diseño y compartir conocimiento.

Por qué importa. Cada persona tiene puntos ciegos. Un par de ojos frescos detecta bugs, problemas de seguridad y malentendidos de negocio que el autor ya no ve.

Cuándo usarlo. Todo cambio a la rama principal debería pasar por review cuando hay algo en juego: calidad, seguridad o el contrato de una API.

Conceptos clave

  • Enfócate en el diff, no en el montón de archivos: cada línea que cambia tiene un motivo.
  • Comentarios constructivos: sugieren y explican, no castigan ni juzgan.
  • Alcance acotado: PRs pequeños se revisan mejor y más rápido.
  • Petición de cambios: aprueba, solicita cambios o comenta; úsalo con criterio.
  • Carácter asíncrono: el review es una herramienta de comunicación diferida.

Ejemplo básico

El patrón de oro de un comentario útil: señalar la línea, explicar por qué y proponer una alternativa concreta.

Comentario accionable y con contexto detrás del código.

Ejemplo intermedio

GitHub permite comentar en línea dentro del pull request; ancla el comentario al diff exacto y referencia issues o documentación.

Ejemplo real

Un equipo de pagos detectó en review un token de acceso que filtraba en los logs por una línea de debug. El comentario '¿seguro que queremos loggear el token?' evitó una fuga de información en producción.

  • Revisa primero los puntos críticos: auth, dinero, datos personales y errores.
  • No apruebes una PR solo 'para darle salida': la prisa se paga luego.
  • Usa plantillas de PR para que el autor cuente qué hace y por qué.
  • Divide reviews largos: una lista de 20 comentarios abruma a cualquiera.

El autor primero revisa su propio diff: la mitad de los comentarios del reviewers desaparecen solos.

Explicación

  • Un review de calidad se centra en comportamiento, seguridad y diseño, no en gustos de formato (eso lo automatizan los linters).
  • Los comentarios deben ofrecer una alternativa: criticar sin proponer solo crea fricción.
  • El tamaño de la PR importa: hasta ~300 líneas la revisión es eficaz; por encima, la atención se dispersa.
  • Las convenciones de equipo (título, ramas, tests) reducen la fricción de cada review.
  • El asincronismo permite pensar con calma, a diferencia de una decisión en caliente en una reunión.

Errores comunes

  • Dejar comentarios estilo 'esto está mal' sin explicación ni alternativa.
  • Aprobar 'hoy para no retrasar' y salvar el fallo en el siguiente deploy.
  • Revisar sin mirar los tests: el código de pruebas cuenta tanto como el resto.

Buenas prácticas

  • Empieza el review por los tests: si ninguno falta, el cambio está bien defendido.
  • Usa comandos cortos para reaccionar: LGTM invitando al autor para más contexto.
  • Framea tus comentarios como preguntas: '¿Nos ayudaría reutilizar este helper?'

Ejercicio

  1. Revisa una PR real y clasifica tus comentarios: bug, diseño, nit o pregunta.
  2. Escribe un plan de review de 5 minutos para una PR de autenticación.
  3. Practica el feedback: responde con una alternativa concreta a un cambio.

Resumen

  • El code review busca la mejor versión del código, no la rendición del autor.
  • Comentarios anclados, accionables y con contexto hacen avanzar al equipo.
  • PRs pequeñas con template y convenciones convierten el review en un hábito ganador.
