Semantic commits, convenciones y changelogs

⚙️ Intermedio 10 min Git y GitHub Módulo 6 · Colaboración avanzada y code review

Introducción

Un historial de commits bien escrito es la mejor documentación que tiene un proyecto: en cada commit puedes leer qué cambió, por qué y en qué parte del sistema. Un historial caótico convierte cada 'git blame' en una investigación policial.

Los conventional commits estandarizan ese mensaje: tipo (feat, fix, docs), alcance opcional y descripción. Y de paso, son el combustible de los changelogs y del versionado semántico automatizado.

Definición

Los conventional commits siguen el formato 'tipo(alcance): descripción' (feat, fix, BREAKING CHANGE...) y permiten deducir la versión semántica y generar changelogs de forma automática.

Por qué importa. Estandarizan la historia, alimentan la generación de releases y hacen que git log y git blame hablen el mismo idioma.

Cuándo usarlo. En equipos medianos y grandes, y en cualquier proyecto open source donde la comunicación por commits es la vía principal.

Conceptos clave

  • feat: añade una funcionalidad nueva visible para el usuario.
  • fix: corrige un bug sin cambiar comportamiento externo.
  • BREAKING CHANGE: rompe compatibilidad y dispara major version.
  • Alcance: la zona que toca el cambio (feat(api): ...).
  • Changelog: listado de cambios por versión, generable con conventional-commits.

Ejemplo real

Un servicio con estándar semántico releasea cada semana: al fusionar PRs con conventional commits, el pipeline calcula el siguiente número de versión y escribe el changelog, dejando a los ojos humanos solo la revisión final.

  • Aplica commitlint en el pre-commit o en el CI para que el formato nunca se rompa.
  • Asocia la convención con tu sistema de issues: 'fix(cliente): [42] corrige redirect'.
  • Usa BREAKING CHANGE para decisiones relevantes de contrato de API.
  • Mantén el changelog generado y, si quieres, añade notas manuales en la release.

La mayor parte de los repositorios de hoy mainstream usan esta convención; el paso de adoptarla es mínimo.

Explicación

  • El tipo define el impacto semántico; el alcance da contexto espacial a cada cambio.
  • fix y feat disparan patch y minor; BREAKING CHANGE dispara major.
  • commitlint valida el formato en el hook o en CI, no depender solo de la voluntad.
  • Los changelogs generados mantienen la historia del proyecto fresca sin trabajo manual.
  • El versionado semántico aplicado sobre el historial hace que la release sea reproducible.

Errores comunes

  • Mezclar varios tipos en un mismo commit: mejor uno por cambio.
  • Mensajes vagos como 'arreglos varios' que no permiten volver a contexto.
  • Romper el formato y que el changelog automático falle en silencio.

Buenas prácticas

  • Usa commitzen como asistente interactivo en vez de memorizar la sintaxis.
  • Incluye el número de issue para trazabilidad automática.
  • Roja línea: si un mensaje necesita 3 líneas de explicación, acompaña el porqué en el cuerpo del commit.

Ejercicio

  1. Reescribe el propio mensaje de este commit con conventional commits.
  2. Instala commitlint y haz que falle un commit con formato inválido.
  3. Genera tu primer changelog a partir de los últimos 10 commits.

Resumen

  • Los conventional commits estandarizan el formato y el impacto de cada cambio.
  • Alimentan versionado semántico y changelogs generados.
  • Automatízalo con hooks y CI para que sea un hábito, no un debate.
