GitHub Actions: CI/CD sobre tu historial

🔥 Avanzado 12 min Git y GitHub Módulo 7 · Git en equipos grandes

Introducción

Si tu CI corre fuera del repo, cada cambio necesita ser informado a un tercero. GitHub Actions integra los pipelines en el propio repositorio: los workflows viven versionados con el código y se disparan por eventos como push o pull_request.

Un buen flujo corre tests, lint, escaneo y build en cada push, y despliega automáticamente en staging (o en prod con aprobación) cuando el PR se fusiona.

Definición

GitHub Actions es la plataforma de CI/CD de GitHub: workflows YAML que definen jobs y steps ejecutados en runners por eventos del repositorio.

Por qué importa. Conecta la automatización al mismo sitio donde está el código y el histórico, con contextos (github, secrets) listos para usar.

Cuándo usarlo. Elige Actions cuando tu código vive en GitHub y quieres integración de la una al cero: queries, matrix de versiones y secrets integrados.

Conceptos clave

  • Workflow: definición YAML de un pipeline con jobs y triggers.
  • Job: conjunto de steps que se ejecutan en un runner aislado.
  • Runner: máquina que ejecuta los jobs (hosted o self-hosted).
  • Evento: lo que dispara el workflow (push, pull_request, schedule).
  • Secrets: variables cifradas disponibles solo en runtime.

Ejemplo real

Un monorepo con API, worker y CLI usa un workflow por área con paths: tocar solo la API no corre los tests del worker. La matriz de versiones y el escaneo de dependencias corren en cada PR, y los despliegues a staging se hacen al merge.

  • Usa paths para que cada área solo dispare su pipeline.
  • Cachea las dependencias entre runs para que el pipeline sea rápido.
  • Protege la rama con status checks apuntando a tus workflows.
  • Aprovecha los artefactos y reports para el code review.

Actions escala con matrices y reutiliza workflows vía actions/reusable-workflows.

Explicación

  • El contexto github.sha, github.ref te permite construir nombres y etiquetas dinámicas.
  • Los secrets nunca se exponen en logs; las variables de entorno las inyectas con env:.
  • Los artefactos permiten a los humanos revisar builds y los reports a los checks en PR.
  • Los runners self-hosted dan control total pero los mantienes tú.
  • Los concurrency grupos evitan que dos deploys del mismo flujo se pisen.

Errores comunes

  • Workflows sin cache: npm ci de 4 minutos en cada push ralentiza el feedback.
  • Disparar deploy en cada push en lugar de solo en el merge a main.
  • Guardar secretos en el workflow en lugar de en Settings > Secrets.

Buenas prácticas

  • Empieza con un workflow de test y añade despliegue cuando el repo esté maduro.
  • Usa matrix de node/python para cubrir las versiones soportadas.
  • Visualiza el estado en la pestaña Actions y protege la rama con status checks.

Ejercicio

  1. Crea un workflow CI que ejecute lint y tests de tu proyecto.
  2. Añade un job de build con cache de dependencias.
  3. Configura un status check que bloquee el merge si el pipeline falla.

Resumen

  • GitHub Actions integra CI/CD en el repo, versionado con el código.
  • Workflows, jobs, matrix y secrets cubren test, build y deploy.
  • Con actions y checks obligatorios, la calidad vive en la plataforma.
