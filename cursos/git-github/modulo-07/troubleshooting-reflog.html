Troubleshooting avanzado: reflog y cirugía segura

🔥 Avanzado 11 min Git y GitHub Módulo 7 · Git en equipos grandes

Introducción

A todos nos ha pasado: un reset --hard en la rama equivocada, un rebase que salió mal o un commit que 'desapareció'. La buena noticia es que Git guarda un diario de todo lo que hiciste: el reflog.

Con el reflog y unas cuantas operaciones de cirugía controlada (filter-repo, reset, rebase) se recupera o se repara cualquier historial. La clave es saber exactamente qué comando usar según el daño.

Definición

El reflog es un historial local de las referencias que apuntan a commits (HEAD, ramas) y registra cada movimiento que haces, lo que permite volver a un estado aunque lo hayas 'perdido' por un reset o rebase.

Por qué importa. Git no borra inmediatamente: los commits que dejas de referenciar permanecen apuntados por el reflog hasta que los recolecta garbage. Siempre hay camino de vuelta.

Cuándo usarlo. Después de un reset --hard, un rebase roto o un merge caprichoso: antes de tocar nada, consulta el reflog.

Conceptos clave

  • Reflog: registro de posiciones de HEAD y ramas con timestamps.
  • reset --hard: mueve la rama y el árbol; peligroso pero recuperable vía reflog.
  • restore/checkout: recupera ficheros individuales de un commit cualquiera.
  • filter-repo: filtra o reescribe historial (borra secretos, cambia autor).
  • GC (garbage collection): el momento en que Git borra definitivamente los huérfanos.

Ejemplo real

Un error de merge rompió la config de despliegue y el equipo confió en una rama ya resetada. Con el reflog identificaron el commit bueno en segundos, hicieron cherry-pick de los cambios y siguieron; el incidente duró 10 minutos.

  • Antes de cualquier reset destructivo, anota el SHA o consulta reflog.
  • Nunca fuerces push a ramas compartidas sin --force-with-lease.
  • Para borrar secretos del historial usa filter-repo y revoca la credencial ya filtrada.
  • Documenta los rescates del equipo para que nadie sufra lo mismo dos veces.

filter-repo reescribe los hash de todos los commits: todos los forks y clones deben sincronizarse después.

Explicación

  • El reflog es local: solo tu máquina lo ve; los demás no tienen su copia.
  • reset mueve la punta de la rama; el commit queda huérfano hasta que GC lo borra (30 días por defecto).
  • restore y checkout extraen ficheros de cualquier commit sin mover la rama.
  • filter-repo es la herramienta de cirugía ficil: filtra, mapea y reescribe histórico.
  • --force-with-lease protege a tus compañeros: solo fuerza si su versión está intacta.

Errores comunes

  • Hacer push --force a una rama compartida sin avisar: rompes historial ajeno.
  • Recurrir al GC por miedo: revisa primero el reflog; Git guarda lo suficiente.
  • Borrar un secreto solo del HEAD: sigue viviendo en el historial profundo.

Buenas prácticas

  • Configura los hook de reflog lifetime o simplemente no borres el .git.
  • Si un rescatista va por pronto, guarda un backup de la rama con git branch rescue.
  • Revoca la credencial que se te escapó SIEMPRE, incluso en repos privados.

Ejercicio

  1. Haz un reset --hard y recupérate con el reflog.
  2. Recupera un fichero concreto de un commit viejo sin tocar la rama.
  3. Crea un repos de prueba, filtra un archivo con filter-repo y force-mueve una rama propia.

Resumen

  • El reflog es tu seguro de vida: recupera estados que creíste perdidos.
  • reset, restore y cherry-pick permiten reparar daños con calma.
  • filter-repo hace cirugía grande, y la revocación siempre acompaña a la fuga.
