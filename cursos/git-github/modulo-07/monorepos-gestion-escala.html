Monorepos y gestión a escala

🔥 Avanzado 11 min Git y GitHub Módulo 7 · Git en equipos grandes

Introducción

Un monorepo almacena toda la organización en un único repositorio: código, config, librerías internas y servicios. Tiene ventajas claras de consistencia y refactor entre paquetes, y retos reales de tamaño y velocidad.

Git soporta repos grandes con sparse checkout, partial clone y submodules, y los monorepos se ayudan de hashes y nilos de CI que solo construyen lo que cambió.

Definición

Un monorepo es un repositorio único para varios proyectos y paquetes; técnicas como sparse checkout, partial clone y path filters lo mantienen ágil aunque crezca.

Por qué importa. Facilita el refactor transversal, garantiza una fuente de verdad común y simplifica el versionado de librerías internas.

Cuándo usarlo. Ideal para equipos que comparten código entre servicios, publican paquetes internos o quieren un solo trigger de CI para toda la organización.

Conceptos clave

  • Packages/workspaces: subdirectorios con su propio package.json y gestión de dependencias.
  • Sparse checkout: solo descargas las carpetas que necesitas.
  • Partial clone: evita bajar el historial completo al clonar.
  • Path filters: workflows CI solo para el área tocada.
  • Submodules: repositorios anidados con su propio control de versiones.

Ejemplo real

Una empresa con 60 microservicios decidió consolidar en un monorepo: los equipos comparten tipos de contrato comunes, los refactors de API se propagan de golpe y el CI con path filters solo prueba lo tocado. El ahorro de cabeceras fue del 40%.

  • Adopta una división de paquetes clara y una política de versionado de librerías internas.
  • Usa sparse checkout para developers que solo trabajan en su área.
  • Configura path filters en todos los pipelines para no construir lo innecesario.
  • Empaquetado como paquete: conserva la procedencia de quién modifica qué.

Los submodules por otra parte mantienen independencia de versiones, pero suman complejidad de sincronización.

Explicación

  • El formato de objeto Git por blob permite clonar con filtros para no bajar el histórico gigante.
  • Sparse checkout crea una vista parcial del árbol de trabajo.
  • Las workspaces (npm/pnpm) resuelven dependencias entre paquetes con symlinks.
  • Los path filters en CI con solo 2-3 directorios ahorran el 80% de los builds.
  • Elegir entre monorepo y multirepo depende de la cultura de tu equipo, no solo de la técnica.

Errores comunes

  • Construir todo el monorepo en cada pipeline: el tiempo de espera exaspera al equipo.
  • Un solo package.json para toda la base: rompe el aislamiento de versiones.
  • Submodules sin documentación: cada dev tropieza con su sincronización.

Buenas prácticas

  • Empieza pequeño: agrupa 2-3 paquetes y mide la fricción antes de abrazar el monorepo total.
  • Automatiza el mapa de dependencias para que el CI construya solo lo afectado.
  • Prueba el flujo de contribución: clonar con sparse debe ser trivial.

Ejercicio

  1. Clona un monorepo público grande con sparse checkout y mide el ahorro.
  2. Configura path filters en un workflow para solo correr los tests del área tocada.
  3. Divide un servicio en dos paquetes de workspace y versiona su dependencia.

Resumen

  • El monorepo centraliza código y configuración en un único repositorio.
  • Sparse checkout, partial clone y path filters lo mantienen ágil.
  • Workspaces y CI selectivo convierten la escala en un problema resuelto.
