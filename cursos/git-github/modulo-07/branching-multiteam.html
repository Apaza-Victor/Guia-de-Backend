Branching multiteam

🔥 Avanzado 10 min Git y GitHub Módulo 7 · Git en equipos grandes

Introducción

Cuando tres equipos viven en el mismo repositorio, las decisiones de ramas dejan de ser personales: qué se fusiona a main, cuándo se congela una release y cómo viaja una hotfix a producción son decisiones de plataforma.

Las estrategias maduras combinan ramas de soporte (main, develop, release) con el principio de compatibilidad continua, y definen quién escribe en cada rama y qué protecciones la cubren.

Definición

El branching multiteam organiza ramas de desarrollo, integración y releases (a menudo main + release branches), con reglas de fusión, protección y soporte para que equipos paralelos no se pisen ni rompan la release.

Por qué importa. La integración continua funciona solo si hay una rama compartida estable y controles de calidad que la protejen.

Cuándo usarlo. Cuando hay más de un equipo tocando el mismo código o releases coordinadas con clientes.

Conceptos clave

  • main: la rama de integración continua y única con fuente de verdad.
  • develop: (opcional) rama de integración de funcionalidades.
  • release branch: rama congelada para cada versión entregada.
  • hotfix branch: rama corta que sale de main o release y vuelve a las dos.
  • Trunk-based vs GitFlow: integración diaria en main frente a ramas largas.

Ejemplo real

Una plataforma con 4 equipos (api, web, mobile, data) definió main protegida, PRs obligatorios con CI, y release branches para las versiones de contrato con clientes. La hotfix a una release se aplica también a main: la disciplina evitó divergencias.

  • Que la PR incluya test, lint y veredicto del owner de la zona.
  • Usa squash merge para mantener main con commits limpios.
  • Define un dueño de la release: solo esa persona fusiona en la rama congelada.
  • Documenta qué rama sustenta cada entorno (dev/QA/prod).

La regla de oro: lo que no está en main no existe para los demás equipos.

Explicación

  • Trunk-based acorta ciclo de retroalimentación: todo integra a diario y los PRs son pequeños.
  • GitFlow añade ramas de soporte para releases coordinadas con mayor ceremonia.
  • Las branch protection impiden que equipos remotos rompan la rama compartida.
  • Las releases etiquetadas requieren del release branch congelado para el soporte.
  • Cualquier estrategia vale si hay protecciones, owners y disciplina de fusiòn.

Errores comunes

  • Ramas que viven semanas sin integrar: conflictos y sprint al final.
  • Nadie dueño de la release: todos escriben en rama congelada.
  • Merge a main sin PR ni CI: una reconstrucción cara para el resto.

Buenas prácticas

  • Elige una estrategia simple y hazla cumplir con protección y plantillas de PR.
  • Si empiezas, trunk-based + tags es la opción más baja en fricción.
  • Celebra los merge limpios: la disciplina se enseña con ejemplo.

Ejercicio

  1. Define para tu repo un flujo trunk-based con main protegida.
  2. Crea una release branch ficticia y simula aplicación de hotfix.
  3. Revisa la estrategia de ramas de un proyecto real y propón mejoras.

Resumen

  • El branching multiteam exige una estrategia clara, descrita y protegida.
  • Trunk-based integra a diario; GitFlow coordina releases con ramas de soporte.
  • Con dueños, protecciones y squash merges, la rama principal nunca se rompe.
