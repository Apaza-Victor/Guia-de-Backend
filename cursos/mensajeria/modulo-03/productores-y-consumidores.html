Productores y consumidores

🚀 Avanzado 10 min Mensajería Backend Módulo 3 · Kafka y event streaming

Introducción

Con la teoría de topics y particiones sobre la mesa, toca escribir de verdad. En esta lección verás el producer API y el consumer API de Kafka con sus decisiones más delicadas: en qué condición confirmar una escritura (acks) y cuándo y cómo commitar el offset del consumidor.

Trabajaremos con kafkajs (Node.js) y confluent-kafka (Python).

El productor: acks y orden

El productor serializa el evento, elige partición (por clave o round-robin) y lo envía. La garantía se decide con la opción acks:

  • acks=0: dispara y olvida. Rápido, pierde datos si algo falla.
  • acks=1: el líder lo escribió. Casi nada se pierde; el líder puede caerse tras confirmar.
  • acks=all (+ min.insync.replicas): todas las réplicas ISR confirmaron. Máxima seguridad.
const { Kafka } = require('kafkajs');

const kafka = new Kafka({
  clientId: 'api-pedidos',
  brokers: ['localhost:9092']
});

const productor = kafka.producer({
  allowAutoTopicCreation: true,
  transactionTimeout: 30000
});

async function publicarPedido(pedido) {
  await productor.connect();

  // acks=-1 en kafkajs equivale a acks=all (espera a réplicas ISR)
  await productor.send({
    topic: 'pedidos',
    acks: -1,
    messages: [
      {
        key: String(pedido.usuarioId),   // orden por usuario
        value: JSON.stringify(pedido),
        timestamp: new Date().toISOString()
      }
    ]
  });

  console.log('Pedido publicado:', pedido.id);
}

await publicarPedido({ id: 'P-2026-0001', usuarioId: 4242, total: 129.90 });

El productor no borra envíos fallidos: ante un error retry activo retries y retry.backoff.ms. Con idempotent: true (productor idempotente) Kafka evita duplicados debidos a reintentos, enlazado con la garantía exactly-once que vimos en el módulo 1.

El consumidor y el commit de offsets

El consumidor pertenece a un grupo (group.id) y lee asignaciones de particiones. Su únicorecordatorio es el offset: el broker lo guarda en un topic interno (__consumer_offsets) cuando el consumidor commitea.

from confluent_kafka import Consumer, KafkaError

conf = {
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'servicio-facturacion',
    'auto.offset.reset': 'earliest',
    'enable.auto.commit': False,   # commit manual: control total
    'session.timeout.ms': 10000,
}

consumidor = Consumer(conf)
consumidor.subscribe(['pedidos'])

try:
    while True:
        msg = consumidor.poll(1.0)
        if msg is None:
            continue
        if msg.error():
            if msg.error().code() == KafkaError._PARTITION_EOF:
                continue
            raise KafkaError(msg.error())

        facturar(msg.value())       # trabajo real

        # Commit MANUAL: solo después de persistir el efecto
        consumidor.commit(asynchronous=False)
        print(f'Offset commiteado: {msg.partition()}/{msg.offset()}')

finally:
    consumidor.close()

Auto-commit vs commit manual

La trampa que más dinero ha costado en producción:

  • Auto-commit (por defecto): el cliente commitea cada N segundos. Si el proceso muere antes del commit pero después de procesar, al reentrar se reprocesa (duplicado). Bien para eventos ligeros idempotentes.
  • Commit manual: tú decides el instante. Lo normal: procesar y persistir el efecto, después commit. Así, fallo antes del commit = reprocesar con seguridad (at-least-once).
  • Antes!No commitees antes de procesar: el efecto se pierde y el offset avanza: datos que desaparecen sin remedio.
const consumidor = kafka.consumer({ groupId: 'facturacion' });

await consumidor.connect();
await consumidor.subscribe({ topic: 'pedidos', fromBeginning: false });

await consumidor.run({
  eachMessage: async ({ topic, partition, message, heartbeat }) => {
    // 1) Procesar el evento (facturar, guardar, notificar)
    const factura = await generarFactura(JSON.parse(message.value));

    // 2) Persistir el resultado ANTES de commitear
    await db.crearFactura(factura);

    // 3) El offset se commitea tras el éxito (at-least-once)
    //    kafkajs auto-commitea al terminar eachMessage
    console.log('Factura creada:', factura.id);
  }
});

En este flujo, un fallo tras generarFactura pero antes de crearFactura... no existe: si cualquier paso lanza excepción, el offset no avanza y el mensaje se entrega en el próximo rebalanceo. Idempotencia en la base (clave pedidoId única) cierra la duplicidad.

Manejo de errores del consumidor

  • Eventos corruptos: captura el parseo y envía el payload crudo a un topic errores; commitea igual para no bloquear la partición.
  • Dependencias caídas: no commitees; deja que el rebalanceo reprocese cuando la dependencia vuelva.
  • Particiones muy grandes: procesa con eachBatch para batching eficiente en vez de eachMessage.
# Ejemplo mínimo del flujo de eventos corruptos
try:
    datos = json.loads(msg.value())
except json.JSONDecodeError:
    productor_correos.produce(
        topic='errores',
        value=msg.value(),           # guardamos el crudo para debug
        headers={'motivo': 'payload_invalido'}
    )
    consumidor.commit(asynchronous=False)  # y seguimos adelante
else:
    procesar(datos)
    consumidor.commit(asynchronous=False)

Ejercicio

  1. Escribe un productor con keys por usuarioId y publica 6 pedidos de 2 usuarios distintos; verifica con la CLI que cada usuario cae siempre en la misma partición.
  2. Implementa un consumidor con commit manual y desconéctalo a mitad de trabajo. ¿El evento se reprocesa? ¿Dónde quedó el offset?
  3. Responde: con auto-commit cada 5 s y un efecto que tarda 10 s, ¿cuántos duplicados esperarías ante un crash? ¿Y con commit manual?

Resumen

  • El productor define las garantías con acks (0, 1 o all) y la clave de partición.
  • El consumidor pertenece a un grupo y lee sus particiones asignadas con offsets propios.
  • Commit manual después de persistir el efecto es la combinación segura (at-least-once).
  • El auto-commit facilita duplicados; el commit antes de procesar pierde datos.
  • Eventos corruptos van a un topic de errores; el flujo no se bloquea.
