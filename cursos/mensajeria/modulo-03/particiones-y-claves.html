Particiones y claves

🚀 Avanzado 9 min Mensajería Backend Módulo 3 · Kafka y event streaming

Introducción

La partición es la moneda de orden y paralelismo de Kafka. Todo lo que pidamos a Kafka en términos de «procesa los eventos de una entidad en el orden exacto en que ocurrieron» depende de cómo elijamos la clave que decide la partición.

Si la clave es correcta, los eventos de una misma entidad caen siempre en la misma partición y se procesan en orden. Si la clave es un timestamp o un ID global, el orden por entidad se rompe en mil pedazos.

Cómo se elige la partición

Cuando el productor envía un mensaje con key, Kafka la hashea (murmur2) y calcula abs(hash(key)) % num_partitions. Con la misma clave, siempre la misma partición:

// En kafkajs, el particionador DefaultPartitioner usa murmur2 y % N.
// clave "usuario-4242" => siempre la misma partición (por ejemplo la 1)

const mensajes = [
  { key: 'usuario-4242', value: '{"tipo":"pedido.creado"}' },
  { key: 'usuario-4242', value: '{"tipo":"pago.aprobado"}' },
  { key: 'usuario-4242', value: '{"tipo":"pedido.enviado"}' }
];

// Los 3 eventos del USUARIO 4242 caen en la MISMA partición
// -> se procesan en el orden exacto en que fueron publicados.

// Dato práctico: NO confíes en cuál es esa partición;
// confía en que ES SIEMPRE la misma mientras el nº de particiones no cambie.

Sin clave (key: null), Kafka reparte en round-robin (o en ráfagas con sticky partitioning). Perfecto para logs y métricas donde el orden no importa.

El orden por entidad en acción

Imagina el recorrido de un pedido: creado → pagado → enviado → entregado. El servicio que mantiene el estado del pedido debe verlos en ese orden. Con la clave pedidoId, ningún pedido salta ni se procesa paralelamente contra un estado viejo:

from confluent_kafka import Producer

producer = Producer({'bootstrap.servers': 'localhost:9092'})

def publicar(topic, clave, evento):
    producer.produce(topic, key=clave.encode(), value=evento.encode())
    producer.flush()   # confirma el envío

# Todos los eventos del PEDIDO P-1 van a la misma partición y orden
publicar('pedidos', 'P-1', '{"estado":"creado","ts":1}')
publicar('pedidos', 'P-1', '{"estado":"pagado","ts":2}')
publicar('pedidos', 'P-1', '{"estado":"enviado","ts":3}')

# El consumidor que reconstruye el estado del pedido P-1
# leerá: creado -> pagado -> enviado, SIEMPRE en ese orden.

Éste es el contrato que permite hacer estado derivado con Kafka: el topic es la historia, y el consumidor aplica los hechos en orden.

Elegir el número de particiones

No elijas 100 particiones a lo loco. El número ideal depende de:

  • Cuánto throughput necesitas: más particiones = más paralelismo (un consumidor por partición como máximo, en el mismo grupo).
  • Cuánta cardinalidad de claves tienes: con claves por usuario y 4 particiones, miles de usuarios comparten cada partición; con 24 particiones, se distribuyen mejor.
  • El coste de la reordenación: cada partición es un archivo y metadatos en cada broker; miles de particiones degradan el rendimiento del broker.
  • El reequilibrio: las particiones se asignan entre los consumidores; cuantas más particiones, más equilibrado (pero más lento el rebalanceo).

Regla de dedo: empieza por 6-12 particiones por topic y multiplícalas solo cuando tu monitorización diga que el throughput lo exige. Los consumidores se escalan hasta el número de particiones; de ahí en adelante, añadir threads no ayuda.

Co-ubicar eventos correlacionados

Cuando dos tipos de eventos deben procesarse juntos en orden, comparte la misma clave lógica entre topics. Por ejemplo pedidos y envios se particionan ambos por pedidoId: un consumidor que los une hace join por la misma clave sin barajar datos.

# Ambos topics particionados por la MISMA clave lógica
# topic "pedidos"  key = pedido-77  -> partición X
# topic "envios"   key = pedido-77  -> partición X (mismo nº particiones)
#  => join sin movimiento de datos entre brokers en la misma partición

Esta propiedad (misma clave = misma partición = mismo orden) es la base de las tablas y joins de Kafka Streams, aunque allí se materializan con topics compactados.

Ejercicio

  1. Con un topic de 3 particiones, publica 9 eventos usando 2 claves diferentes. Verifica por tema: ¿por qué todos los de la clave A caen siempre en la misma partición?
  2. Responde: ¿qué pasa si incrementas las particiones de 3 a 4 mientras hay mensajes no consumidos? ¿Qué le ocurre al orden de las claves ya hasheadas con el nº antiguo?
  3. Diseña las claves para un sistema de seguimiento logístico: ¿qué agregarías para que un pedido con varios embarques se procese en orden y a la vez se reparta bien entre consumidores?

Resumen

  • La clave decide la partición: hash(clave) % nº_partitions.
  • Misma clave = misma partición = orden secuencial garantizado por entidad.
  • Sin clave, round-robin/sticky: buen paralelismo, orden por entidad inexistente.
  • El nº de particiones fija el paralelismo y el coste del rebalanceo.
  • Co-ubicar eventos relacionados con la misma clave permite joins sin barajar datos.
