Consumer groups y rebalanceo

🚀 Avanzado 10 min Mensajería Backend Módulo 3 · Kafka y event streaming

Introducción

Kafka no reparte los eventos a consumidores sueltos: los agrupa en consumer groups. Todos los miembros del grupo comparten la carga del topic —cada partición la procesa un único miembro— y los grupos diferentes leen el topic de forma independiente, como suscripciones distintas.

Este modelo resuelve el problema «colas + broadcast» de una vez: un grupo se comporta como una cola (2.º consumidor del grupo); dos grupos se comportan como pub/sub (cada grupo recibe todo).

El equilibrio del grupo

La regla de oro: toda partición es consumida por exactamente un miembro del grupo. Con 12 particiones:

  • 1 consumidor → consume las 12 particiones (poco paralelo).
  • 3 consumidores → 4 particiones cada uno.
  • 12 consumidores → 1 partición cada uno (máximo equilibrio).
  • 17 consumidores → 12 trabajan y 5 se quedan ociosas (sobra).
# topic pedidos con 6 particiones, grupo "facturacion"
# consumidor-1  -> particiones 0,1,2
# consumidor-2  -> particiones 3,4,5
# consumidor-3  -> (recién llegado) espera rebalanceo

Aquí se aplica la regla de la lección anterior: los consumidores horizontales se añaden hasta el número de particiones; pasada esa cifra, no aceleras nada.

Grupos: misma carga, configs distintas

El mismo topic puede ser leído por varios grupos, cada uno con su propio offset. Es la analogía «topic» del módulo 1 llevada a Kafka:

const { Kafka } = require('kafkajs');
const kafka = new Kafka({ brokers: ['localhost:9092'] });

// Grupo A: reconstruye el estado del pedido (reads del orden completo)
const a = kafka.consumer({ groupId: 'estado-pedidos' });
await a.subscribe({ topic: 'pedidos', fromBeginning: true });
await a.run({ eachMessage: async ({ message }) =>
  aplicarEstado(JSON.parse(message.value)) });

// Grupo B: solo analítica (puede leer desde el inicio o lo nuevo)
const b = kafka.consumer({ groupId: 'analitica' });
await b.subscribe({ topic: 'pedidos', fromBeginning: false });
await b.run({ eachMessage: async ({ message }) =>
  registrarMetrica(JSON.parse(message.value)) });

// Cada grupo lleva SU offset; el avance de B no afecta a A.

El rebalanceo y sus momentos de pausa

Cuando un miembro entra o sale del grupo (o se cae), Kafka detona un rebalancing: el coordinador (un broker) reparte las particiones de nuevo entre los miembros vivos. Durante ese lapso, las particiones no se consumen (revoked) y el grupo pierde progreso temporal.

  • Eager rebalance: todos revocan todo y se reasigna desde cero. Simple, pero con «stop the world».
  • Cooperative sticky: solo se reasignan las particiones afectadas (mínima disrupción). Ideal para procesos de larga duración.
  • Session timeout: si un miembro no manda heartbeat en el tiempo fijado, se declara muerto y se rebalancea.
const consumidor = kafka.consumer({
  groupId: 'estado-pedidos',
  sessionTimeout: 10000,          // 10 s sin heartbeat => muerto
  heartbeatInterval: 3000,
  rebalanceTimeout: 30000,
  // kafkajs con retry configura el partitionAssigner
});

// cb en rebalance: pausa y commit antes de soltar las particiones
await consumidor.subscribe({
  topic: 'pedidos',
  fromBeginning: true,
  beforeEachRebalance: () => consumidor.commitOffsets() // flush de offsets
});

El consejo de oro: commitea los offsets antes de devolver el control. Así, al rebalancear, el grupo retoma exactamente donde se quedó y no reprocesa.

Medir el lag: el termómetro del grupo

El lag es la distancia entre el último evento escrito y el offset de un consumidor. Un lag creciente = los productores van más rápido que los consumidores. Es la métrica que más alertas dispara en un clúster sano:

# kafka-consumer-groups.sh: ver lag por partición
kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group estado-pedidos

# Salida típica:
# GROUP           TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG
# estado-pedidos  pedidos  0          10042           10050           8
# estado-pedidos  pedidos  1          5001            5180            179
# estado-pedidos  pedidos  2          88              90              2

# Lag alto y constante => añade consumidores (o particiones)
  • LAG ≈ 0: grupo al día. Todo bien.
  • LAG moderado y decreciente: está recuperando un atraso; normal tras un pico.
  • LAG creciente: el sistema se ahoga: escalar consumidores, optimizar el procesado o subir particiones.

Consumidores en producción: checklist

  • group.id estable y semántico: un grupo por «rol», no por instancia.
  • Commit manual después de persistir efectos (at-least-once + idempotencia).
  • Heartbeat corto y procesado que respete el max.poll.interval.ms (si tardas más, te expulsan del grupo). Divide el trabajo pesado en batches.
  • Observa lag y estado del grupo con alertas: es tu primera señal de problemas.
  • Con procesos de larga duración, usa rebalanceo cooperativo para no parar todo.

Error clásico: lanzar un consumidor por instancia dentro del mismo grupo con la intención de duplicar el throughput, cuando las particiones no llegan. La asignación no se multiplica; se reparte. Revisa primero el lag y las particiones.

Ejercicio

  1. Crea un topic de 4 particiones y consume con un grupo de 1 consumidor; luego con 4 y con 6. Describe cómo cambia la asignación en cada caso usando kafka-consumer-groups.sh --describe.
  2. Lanza un consumo lento (sleep por evento) y genera tráfico para ver crecer el LAG. Escala a 4 consumidores y observa la recuperación.
  3. Responde: ¿qué le pasaría a un consumidor que tarda 15 minutos en un evento, si su max.poll.interval.ms es 300000? ¿Y a la partición que estaba consumiendo?

Resumen

  • Un group.id = una vista de la misma cola; varios groups = varias vistas (pub/sub).
  • Cada partición la consume un único miembro del grupo: el paralelismo lo limita el nº de particiones.
  • Rebalancing reparte particiones al entrar/salir miembros; commitear antes de soltar evita reprocesos.
  • El lag mide cuánto te atrasas: la métrica más importante del consumo.
  • Escala consumidores hasta igualar particiones; controla heartbeats y tiempos de proceso.
