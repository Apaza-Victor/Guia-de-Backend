Kafka: conceptos

🚀 Avanzado 10 min Mensajería Backend Módulo 3 · Kafka y event streaming

Introducción

Apache Kafka no es «una cola más». Es un log distribuido, particionado y replicado: los eventos se anexan (append-only) a un archivo inmutable y los consumidores avanzan un puntero de lectura. Nadie borra el pasado; se conserva y se relee.

Esa diferencia de filosofía con RabbitMQ explica casi todo lo demás: el alto throughput (millones de eventos por segundo), el orden por clave, la reproducción de historial y la facilidad para reconstruir estados.

Topics y particiones

Un topic agrupa eventos del mismo tipo (pedidos, usuario.creado). Pero un topic grande no vive en un solo archivo: se particiona. Cada partición es una secuencia ordenada e inmutable de eventos numerados.

# topic "pedidos" con 4 particiones
pedidos-0  [ ev0 | ev1 | ev2 | ... ]  <- offsets 0,1,2...
pedidos-1  [ ev3 | ev4 | ... ]
pedidos-2  [ ev5 | ... ]
pedidos-3  [ ev6 | ... ]

# Cada evento tiene un OFFSET: su posición dentro de su partición

La partición es la unidad de paralelismo y de orden: dentro de una partición hay orden total; entre particiones, no. Cuántas particiones tenga un topic define cuánto puedes balancear y escalar a la vez que cuánto pierdes en orden global.

Offsets y consumo

Encada partición, el consumidor lleva un offset: el número del próximo evento que toca leer. Consumir no elimina nada; solo mueve el puntero. Por eso dos servicios pueden leer el mismo topic con offsets independientes, y por eso Kafka puede reproducir el historial desde el principio (auto.offset.reset=earliest) o solo lo nuevo (latest).

# Leer desde el comienzo el topic 'pedidos' con la CLI
kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 \
  --topic pedidos \
  --from-beginning

Brokers y replicación

Un clúster de Kafka son varios brokers (servidores). Cada partición tiene una copia líder (la que acepta lecturas/escrituras) y réplicas (copias de respaldo sincronizadas). Si el líder muere, una réplica es promovida a líder: eso es alta disponibilidad.

  • Replication factor 3: 3 brokers guardan cada partición → aguanta la caída de 2 brokers.
  • ISR (in-sync replicas): réplicas que están al día con el líder; solo ellas pueden ser promovidas.
  • acks: cuántas confirmaciones exige el productor antes de considerar escrito un evento (0, 1 o all).
# Describir el topic para ver particiones, líderes y réplicas
docker exec kafka kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --describe --topic pedidos

# Salida ilustrativa:
# Topic: pedidos  Partition: 0  Leader: 1  Replicas: 1,2,3  Isr: 1,2,3
# Topic: pedidos  Partition: 1  Leader: 2  Replicas: 2,3,1  Isr: 2,3,1

Retención: Kafka conserva, las colas olvidan

Una cola de RabbitMQ o SQS elimina el mensaje al confirmarlo. Kafka lo conserva según retención (por defecto 7 días o hasta un límite de bytes). Esto abre casos que una cola no puede resolver:

  • Releer el historial completo para depurar un bug.
  • Repoblar un sistema nuevo (ej. una base de búsquedas) desde cero.
  • Hacer event sourcing: el topic ES el sistema de registro.

Regla mental: RabbitMQ te dice «toma el mensaje y olvídate»; Kafka te dice «aquí están los hechos, lee cuando quieras y vuelve a leer cuando quieras». Elige infraestructura según el tiempo de vida que necesitan tus datos.

Cuándo usar Kafka

  • Sí: event streaming, pipelines de datos, eventos de dominio con varios consumidores, log de hechos, reconciliación, data lakes.
  • No: una simple cola de tareas de envío de correos, un RPC, workload FIFO estricto de un solo destino.
  • Compensa el coste: Kafka es más pesado de operar (clúster, particiones, retención, monitoreo de consumidores) que las alternativas gestionadas.

Ejercicio

  1. Levanta Kafka con Docker y crea el topic pedidos con 3 particiones y factor de replicación 1.
  2. Usa kafka-console-producer y kafka-console-consumer para publicar 5 eventos; luego relee desde el principio e identifica en qué partición quedó cada uno.
  3. Explora --describe: ¿qué diferencias ves entre particiones en cuanto a líder y réplicas con un solo broker cnn? ¿Qué necesitarías para tener replicación real?

Resumen

  • Kafka es un log distribuido append-only: los eventos se anexan, no se borran al consumir.
  • Los topics se dividen en particiones; dentro de cada partición hay orden y offsets.
  • Los brokers replican particiones; una réplica ISR toma el relevo si cae el líder.
  • La retención permite releer historial y reconstruir estados — algo imposible en una cola clásica.
  • Kafka brilla con eventos y alto volumen; pagas con complejidad operativa.
