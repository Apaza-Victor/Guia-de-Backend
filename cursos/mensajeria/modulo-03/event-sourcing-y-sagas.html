Event sourcing y sagas

🚀 Avanzado 11 min Mensajería Backend Módulo 3 · Kafka y event streaming

Introducción

Todo lo aprendido sobre Kafka —keys, particiones, retención, grupos, offsets— tiene un destino: permitir patrones de arquitectura que una base de datos transaccional clásica no puede sostener. Dos de ellos cierran este curso:

  • Event sourcing: guardar los hechos, no el estado. El topic ES la verdad.
  • Sagas: coordinar transacciones largas entre servicios con eventos y compensaciones, en vez de una transacción distribuida.

Event sourcing: el estado es derivado

En el modelo clásico, guardamos el estado final: INSERT INTO pedidos SET estado='enviado'. En event sourcing guardamos la historia: el pedido no «está enviado», sino que ocurrió pedido.creado, luego pedido.pagado, luego pedido.enviado. El estado actual es una reducción (fold) de los eventos:

// Reducción: el estado = aplicar todos los eventos en orden
function reducir(estado = {}, evento) {
  switch (evento.tipo) {
    case 'pedido.creado':
      return { ...estado, id: evento.pedidoId, items: evento.items, estado: 'creado' };
    case 'pedido.pagado':
      return { ...estado, estado: 'pagado', total: evento.total };
    case 'pedido.enviado':
      return { ...estado, estado: 'enviado', carrier: evento.carrier };
    default:
      return estado;
  }
}

// leer todos los eventos del pedido 7 desde la partición (clave = pedido 7)
const eventos = await leerTopic('pedidos', 'P-7');   // en orden
const estadoFinal = eventos.reduce(reducir, {});     // { estado: 'enviado', ... }

// Ventaja killer: podemos REPROCESAR TODO el historial para
// corregir un bug de algoritmo, o reconstruir un sistema nuevo.

Kafka es un candidato natural para event sourcing por retención y reproducción; pero «natural» no significa modo automático: el topic principal (pedidos) se hace compactado o se respalda con topics de comandos, y el estado actualizado para consultas vive en una read model.

CQRS: la pareja inseparable

Si el topic es la escritura, necesitas una lectura rápida. CQRS (Command Query Responsibility Segregation) separa ambas: se escriben eventos (comandos/escritura) y se mantiene una proyección optimizada para consultas que reacciona a esos eventos.

# Proyección (read model) rehidratada por el topic
from confluent_kafka import Consumer, KafkaError

class ProyeccionPedidos:
    def __init__(self, store):
        self.store = store   # ej. tabla "pedidos_consulta" en Postgres

    def aplicar(self, evento):
        table = self.store['pedidos_consulta']
        if evento.tipo == 'pedido.creado':
            table.insert(id=evento.pedidoId, items=evento.items, estado='creado')
        elif evento.tipo == 'pedido.pagado':
            table.update(id=evento.pedidoId, estado='pagado', total=evento.total)
        elif evento.tipo == 'pedido.enviado':
            table.update(id=evento.pedidoId, estado='enviado')

consumidor = Consumer({'bootstrap.servers': 'localhost:9092',
                       'group.id': 'proyeccion-estado'})
proyeccion = ProyeccionPedidos(store)

while True:
    msg = consumidor.poll(1.0)
    if msg:
        proyeccion.aplicar(json.loads(msg.value()))
        consumidor.commit(asynchronous=False)

Las consultas responden con la proyección (rápida, indexada), las escrituras publican eventos (inmutables, auditables). Ese es el patrón que usan los sistemas financieros, de logística y de inventario grandes.

Sagas: transacciones largas por compensación

Cuando un pedido toca ventas, inventario, pagos y envío, las bases de datos son distintas; una transacción ACID distribuida (2PC) es cara y frágil. La alternativa pragmática es la saga: una secuencia de transacciones locales que se coordina con eventos, y si una falla, se ejecutan compensaciones de las anteriores.

# Saga coreografiada de un pedido (cada paso escucha su evento previo)

pedido.creado ──> reservar stock
                  si ok: stock.reservado ──> cobrar
                                            si ok: pago.aprobado ──> generar envio
                                            si NO: stock revertido (compensación)
                  si NO: pedido.rechazado

# Compensaciones en cadena:
# pago falla  -> des-reservar stock      (compensación de reservar)
# envio falla -> reembolsar pago         (compensación de cobrar)
#                                          y des-reservar stock

Cada paso es una transacción local (su propia base), y el orquestador —un consumidor que ve los eventos— decide si continuar o compensar.

Saga coreografiada en código

El servicio de stock escribe un evento con el resultado. El servicio de pagos escucha, y ante un fallo emite la compensación:

// SERVICIO DE PAGOS: escucha 'stock.reservado' y cobra
await consumidor.subscribe({ topic: 'stock', fromBeginning: false });

await consumidor.run({
  eachMessage: async ({ message }) => {
    const ev = JSON.parse(message.value);
    if (ev.tipo !== 'stock.reservado') return;

    try {
      const cobro = await pasarela.cobrar(ev.pedidoId, ev.total);
      await publicar('pagos', { tipo: 'pago.aprobado', pedidoId: ev.pedidoId });
      console.log('Pago OK:', ev.pedidoId);
    } catch (e) {
      // COMPENSACIÓN: stock debe revertir la reserva
      await publicar('stock', { tipo: 'stock.revertido', pedidoId: ev.pedidoId });
      await publicar('pedidos', { tipo: 'pedido.rechazado', pedidoId: ev.pedidoId,
                                  motivo: e.message });
      console.error('Pago fallido, compensando:', ev.pedidoId);
    }
  }
});

La saga no usa un coordinador central (coreografía): cada servicio «sabe» su paso y su compensación. La variante orquestada usa un servicio coordinador que publica comandos y espera eventos.

Consejos para llevarlo a producción

  • Eventos versionados (pedido.pagado.v1): los consumidores antiguos no se rompen.
  • Conclina la mutabilidad: publica todo con correlationId para unir los pasos de una saga.
  • Idempotencia en cada paso: los reintentos por rebalanceo no duplican efectos.
  • Metrica la duración de la saga: una saga que nunca cierra es un error lógico + deuda.
  • Toda compensación debe poder compensarse: diseña el camino de vuelta antes del de ida.

Recuerda: Kafka te da el bus, no el patrón. Event sourcing y sagas son decisiones de diseño tuyas; el broker solo aporta orden, retención y confirmación. Usa loop de verificación: ¿puedo reprocesar todo desde cero? ¿mi saga se atora ante un fallo intermedio?

Ejercicio

  1. Escribe la función reducir para los eventos de una cuenta bancaria (cuenta.abierta, deposito.hecho, retiro.hecho) y calcula el saldo final de un historial de 4 eventos.
  2. Modela la saga de «pago de pedido» con tres compensaciones en un diagrama y haz una tabla paso/evento/falta/compensación.
  3. Implementa una mini-saga coreografiada con dos consumidores de Kafka (stock y pagos) y verifica qué eventos se encadenan cuando el cobro falla.

Resumen

  • Event sourcing guarda hechos inmutables; el estado se deriva reduciendo la historia.
  • CQRS separa escritura (eventos) de lectura (proyección optimizada).
  • Las sagas coordinan transacciones largas con pasos + compensaciones, sin 2PC.
  • La coreografía decide por eventos; la orquestación con un coordinador central.
  • Idempotencia, versionado y correlación son las llaves del patrón en producción.
