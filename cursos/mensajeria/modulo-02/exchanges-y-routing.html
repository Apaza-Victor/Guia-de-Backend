Exchanges y routing

🚀 Avanzado 10 min Mensajería Backend Módulo 2 · RabbitMQ y colas

Introducción

RabbitMQ ofrece cuatro tipos de exchange, y cada uno define una política distinta para decidir qué colas reciben un mensaje. Elegir el tipo correcto es la decisión de diseño central de cualquier sistema con RabbitMQ.

  • direct: una cola, una routing key exacta.
  • fanout: broadcast a todas las colas sin mirar keys.
  • topic: routing key con patrones y comodines.
  • headers: reglas sobre headers del mensaje, no sobre keys.

Direct: la ruta exacta

El binding declara una routing key literal; el mensaje llega si su routing key coincide exactamente. Varias colas pueden ligarse con la misma key (cada una recibe una copia) o con keys distintas.

const amqp = require('amqplib');

async function directDemo() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  await ch.assertExchange('tareas', 'direct', { durable: true });
  await ch.assertQueue('colas-procesar', { durable: true });
  await ch.assertQueue('colas-fallar', { durable: true });

  // Binding exacto: solo "critica" entra a colas-fallar
  await ch.bindQueue('colas-procesar', 'tareas', 'critica');
  await ch.assertQueue('colas-importante');
  await ch.bindQueue('colas-importante', 'tareas', 'critica');

  // Llega a "colas-procesar" y también a "colas-importante"
  ch.publish('tareas', 'critica', Buffer.from('reiniciar-cola'));
  await conn.close();
}

Fanout: broadcast total

El exchange fanout ignora la routing key y entrega una copia a todas las colas ligadas. Es el «topic puro»: cada suscriptor recibe cada evento, sin filtros. Perfecto para eventos globales que todo el mundo debe ver.

async function fanoutDemo() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  await ch.assertExchange('notificaciones', 'fanout', { durable: true });
  const qEmail = await ch.assertQueue('fork-email');
  const qSms = await ch.assertQueue('fork-sms');
  const qPush = await ch.assertQueue('fork-push');

  // Sin key: todas las colas reciben TODO
  await ch.bindQueue(qEmail.queue, 'notificaciones', '');
  await ch.bindQueue(qSms.queue, 'notificaciones', '');
  await ch.bindQueue(qPush.queue, 'notificaciones', '');

  ch.publish('notificaciones', 'ignorar-esta-key',
    Buffer.from('{"mensaje": "pedido enviado"}'));
  // email, sms y push reciben la misma copia
  await conn.close();
}

Si mañana quieres notificar también por WhatsApp, declaras una cola nueva y la lías a notificaciones: el productor no cambia una sola línea.

Topic: routing con comodines

Rebusca la routing key contra patrones separados por puntos. Dos comodines:

  • * (asterisco): sustituye a una palabra.
  • # (almohadilla): sustituye a cero o más palabras.

Es la combinación perfecta de direct (filtra) y fanout (multidestino).

async function topicDemo() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  await ch.assertExchange('eventos', 'topic', { durable: true });
  await ch.assertQueue('facturacion', { durable: true });
  await ch.assertQueue('stock', { durable: true });

  // facturacion escucha TODO lo de pedidos; stock solo stock
  await ch.bindQueue('facturacion', 'eventos', 'pedido.*');
  await ch.bindQueue('stock', 'eventos', 'pedido.procesado');

  ch.publish('eventos', 'pedido.creado', Buffer.from('{...}'));
  // -> facturacion (pedido.*) SÍ, stock (pedido.procesado) NO

  ch.publish('eventos', 'pedido.procesado', Buffer.from('{...}'));
  // -> facturacion SÍ, stock SÍ
  await conn.close();
}

Con # puedes capturar árboles enteros: usuario.# recibe usuario.creado y usuario.cuenta.bloqueada.

Headers: routing por atributos

Cuando la decisión depende del contenido (no de la key), usa headers. El binding declara atributos y una regla x-match (all/any). Es menos común y más lento; úsalo con moderación.

const amqp = require('amqplib');

async function headersDemo() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  await ch.assertExchange('auditoria', 'headers', { durable: true });
  const q = await ch.assertQueue('solo-privado');

  // Binding: entra si el header es "auditor" y prioridad alta (x-match=all)
  await ch.bindQueue(q.queue, 'auditoria', '', {
    'x-match': 'all', auditor: 'cicd', prioridad: 'alta'
  });

  ch.publish('auditoria', '', Buffer.from('despliegue a prod'), {
    headers: { auditor: 'cicd', prioridad: 'alta' }
  });
  await conn.close();
}

Cuándo usar cada uno

  • direct → colas de tareas por prioridad o tipo: critica, normal.
  • fanout → notificaciones y eventos globales donde todos deben enterarse.
  • topic → eventos de dominio con jerarquía: pedido.creado, pago.aprobado.
  • headers → routing complejo por metadatos que no caben en una key (evitar si puedes).

Si tu routing se complica, recuerda que puedes encadenar: exchange → cola → otro exchange. Modulariza el enrutado en piezas pequeñas y legibles en vez de una cascada de cabeceras.

Ejercicio

  1. Diseña los bindings para que: la cola alertas-rojas reciba alerta.# y la cola alertas-app reciba alerta.app.*. ¿Qué llega a cada una para la key alerta.app.critica?
  2. Implementa con fanout una difusión de status.up a tres servicios que deben reiniciar su caché.
  3. Responde: ¿por qué no se debe usar fanout para una cola de tareas de facturación donde cada factura debe procesarse una sola vez?

Resumen

  • Direct: coincidencia exacta de la routing key.
  • Fanout: broadcast incondicional a todas las colas ligadas.
  • Topic: patrones con * (una palabra) y # (cero o más).
  • Headers: reglas sobre atributos del mensaje con x-match.
  • El exchange elegido define la semántica de tu sistema (trabajo vs evento).
