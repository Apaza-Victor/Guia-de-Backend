RabbitMQ: conceptos

🚀 Avanzado 10 min Mensajería Backend Módulo 2 · RabbitMQ y colas

Introducción

RabbitMQ implementa el protocolo AMQP 0-9-1. A diferencia del modelo ingenuo «productor → cola → consumidor», en RabbitMQ el productor nunca publica a una cola directamente: publica a un exchange, y es el exchange quien decide a qué colas deja el mensaje mediante las reglas que llamamos bindings.

Entender esos cuatro elementos —exchange, queue, binding y routing key— es entender RabbitMQ. Son la misma arquitectura flexible que permite colas, pub/sub y routing selectivo con el mismo servidor.

Los cuatro elementos

  • Exchange: el buzón de entrada del mensaje. Recibe mensajes de los productores y los enruta con su lógica propia (direct, fanout, topic, headers).
  • Queue (cola): búfer durable donde esperan los mensajes hasta que un consumidor los tome y confirme.
  • Binding: el enlace «intereso por X de este exchange». Define qué llega a cada cola.
  • Routing key: la etiqueta que el productor pone al mensaje y que el exchange compara contra los bindings para decidir.
# Modelo AMQP (diagrama mental)
Productor -> EXCHANGE --routing key---> BINDING -> QUEUE -> Consumidor
                      \--otros bindings--> QUEUE 2 -> Consumidor 2

Un exchange tiene nombre, tipo y flags (durable). Las colas, por su parte, se suscriben a los exchanges con bindings; una cola puede tener muchos bindings del mismo o de distintos exchanges.

Declarar con Node.js: el primer ejemplo

El flujo mínimo en código. Declaramos un exchange eventos, una cola registros, el binding entre ambos y publicamos un mensaje:

const amqp = require('amqplib');

async function setup() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  // 1. Declarar el exchange (durable: sobrevive a reinicios)
  await ch.assertExchange('eventos', 'topic', { durable: true });

  // 2. Declarar la cola (durable también)
  await ch.assertQueue('registros', { durable: true });

  // 3. Binding: la cola 'registros' escucha los eventos 'usuario.*'
  await ch.bindQueue('registros', 'eventos', 'usuario.*');

  // 4. Publicar: routing key 'usuario.creado' coincide con el binding
  ch.publish('eventos', 'usuario.creado', Buffer.from(JSON.stringify({
    usuarioId: 4242
  })), { persistent: true });

  console.log('Evento publicado y enrutado a la cola "registros"');
  await conn.close();
}

setup();

La «magia» está en el paso 3 y el 4: el binding usuario.* captura cualquier routing key que empiece por usuario.. El productor jamás menciona colas: publica solo con una routing key.

Consumir de la cola

El consumidor, por el otro lado, no necesita saber nada del exchange: solo escucha su cola y confirma cada mensaje con ACK:

# Consumidor en Python con la librería pika
import pika, json

conexion = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
canal = conexion.channel()

# La misma cola debe existir (mismas propiedades)
canal.queue_declare(queue='registros', durable=True)

def handler(ch, method, properties, body):
    evento = json.loads(body)
    print(f'Evento {method.routing_key}: usuario {evento["usuarioId"]}')
    # Trabajo completado -> confirmar
    ch.basic_ack(delivery_tag=method.delivery_tag)

canal.basic_consume(queue='registros', on_message_callback=handler)
canal.start_consuming()

Sin el basic_ack, RabbitMQ volvería a entregar el mensaje en el próximo intento (at-least-once, como vimos en la lección anterior).

Durabilidad, vhosts y otras piezas

  • Durability: un exchange/cola durable: true sobrevive al reinicio del broker. Las colas durables además guardan mensajes persistentes. Sin ambos flags, todo desaparece al apagar.
  • Durabilidad (persistence): mensajes marcados persistent: true se escriben en disco. Sin él se guardan solo en memoria.
  • Virtual host (vhost): espacio de aislamiento lógico dentro del broker. Usa un vhost por entorno (dev, staging, prod) o por equipo.
  • Default exchange: un exchange especial e implícito cuyo nombre es vacío. Publicar sin exchange equivale a sendToQueue: enruta directo a la cola con el nombre igual a la routing key.
  • Binding key / routing key: en un binding queue.bind(exchange, key) la key define el patrón a emparejar.

  2. Ejecuta el ejemplo de Node.js con Docker y verifica en el panel (pestaña Exchanges → Bindings) que la cola registros recibe el mensaje.
  3. Responde: si el consumidor Python se conecta a una cola que el productor declaró con durable: false, pero con el mismo nombre y propiedades distintas, ¿qué error esperarías ver?

Resumen

  • El productor publica al exchange, nunca directamente a una cola.
  • El exchange, con bindings y routing keys, decide el destino de cada mensaje.
  • Colas y exchanges durables sobreviven reinicios; mensajes persistentes, además, sobreviven a discos.
  • Los vhosts aíslan entornos dentro del mismo broker.
  • Consumir sin ACK = reentrega = posibles duplicados (idempotencia).
