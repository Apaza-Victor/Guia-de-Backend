Consumidor resiliente

🚀 Avanzado 10 min Mensajería Backend Módulo 2 · RabbitMQ y colas

Introducción

El mundo real no procesa tareas sin fallar: hay payloads corruptos, dependencias caídas, timeouts y datos que nadie puede interpretar. Un consumidor resiliente no es el que nunca falla, sino el que falla con elegancia: confirma lo bueno, reintenta lo transitorio y aparta lo irrecuperable sin bloquear la cola.

Tres mecánicas hacen esto posible:

  • ACK y NACK: confirmar éxito o rechazar un mensaje de forma explícita.
  • Dead-letter queue (DLQ): el «buzón de lo irrecuperable».
  • Reintentos con backoff: gg control: reintentar sin saturar ni emitir mil intentos instantáneos.

Ack, nack y requeue

Recordando la lección de garantías: sin confirmación, RabbitMQ reenvía. Pero RabbitMQ da más control que el simple ACK:

const amqp = require('amqplib');

async function consumidorResiliente() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();
  const q = await ch.assertQueue('pagos', { durable: true });
  ch.prefetch(1);

  ch.consume(q.queue, async (msg) => {
    let data;
    try {
      data = JSON.parse(msg.content.toString());
    } catch (e) {
      // Payload corrupto: NUNCA reintentar, es veneno puro.
      console.error('Mensaje corrupto:', msg.content.toString());
      return ch.nack(msg, false, false); // requeue = false -> DLQ
    }

    try {
      await cobrar(data);
      ch.ack(msg);                      // éxito
    } catch (err) {
      if (esTransitorio(err)) {
        console.warn('Reintentando:', data.id);
        return ch.nack(msg, false, true); // requeue = true -> reintento
      }
      // Falla permanente: apartarlo
      return ch.nack(msg, false, false);
    }
  }, { noAck: false });
}

function esTransitorio(err) {
  return ['TIMEOUT', 'CONN_REFUSED', 'UNAVAILABLE'].includes(err.code);
}

La decisión clave está en nack(msg, allUpTo, requeue): el tercer argumento decide si el mensaje vuelve a la cola (reintento inmediato) o se descarta de ella.

Reintentos a ciegas = loop infinito: un nack(requeue: true) sin límite reencola el mismo mensaje una y otra vez, consumiendo CPU y multiplicándose en logs. La DLQ es quien rompe círculos viciosos.

La dead-letter queue

Una cola se declara con un argumento x-dead-letter-exchange: los mensajes que se rechacen con requeue: false (o expiren, o superen el límite de intentos) terminan ahí. El worker de la DLQ los inspecciona, alerta y, si el bug se arregla, los reenvía a la cola limpia.

import pika

canal = pika.BlockingConnection(pika.ConnectionParameters('localhost')).channel()

# Exchange 'errores' + cola DLQ donde aterrizan los mensajes malos
canal.exchange_declare(exchange='errores', exchange_type='fanout', durable=True)
canal.queue_declare(queue='pagos.dlq', durable=True)
canal.queue_bind(queue='pagos.dlq', exchange='errores', routing_key='')

# Cola principal con DLQ configurada
canal.queue_declare(
    queue='pagos', durable=True,
    arguments={
        'x-dead-letter-exchange': 'errores'
    }
)

# El trabajador de la DLQ: alerta, repara o descarta
def inspeccionar_dlq(ch, method, properties, body):
    print(f'ALERTA: mensaje a DLQ -> {body.decode()}')

    # Tras revisar, se puede renviar a 'pagos' si se corrigió el payload
    canal.basic_publish(exchange='', routing_key='pagos', body=body,
                        properties=pika.BasicProperties(delivery_mode=2))
    ch.basic_ack(delivery_tag=method.delivery_tag)

canal.basic_consume(queue='pagos.dlq', on_message_callback=inspeccionar_dlq)
canal.start_consuming()

Reintentos con backoff: el patrón delayed retry

Reintentar al instante es tan malo como no reintentar: la dependencia caída probablemente siga caída. La solución es esperar (backoff) por intervalos crecientes. Sin plugins, se simula con colas intermedias + TTL: el mensaje fallido se publica a una cola de «espera» con un TTL de, digamos, 30 s; al expirar, Rabbit lo reenvía (o lo redirige por DLX) a la cola original.

import pika, time

canal = pika.BlockingConnection(pika.ConnectionParameters('localhost')).channel()

# Cola de espera que manda a 'pagos' tras 30 segundos
canal.queue_declare(
    queue='pagos.retry',
    arguments={
        'x-message-ttl': 30000,          # expira a los 30 s
        'x-dead-letter-exchange': '',    # exchange default
        'x-dead-letter-routing-key': 'pagos'  # vuelve a la cola real
    },
    durable=True
)

# Encolar a RETRY (realmente se publica a la cola pagos.retry directamente)
def reprogramar(mensaje, segundos):
    canal.queue_declare(queue='pagos.retry',
        arguments={'x-message-ttl': segundos * 1000,
                   'x-dead-letter-exchange': '',
                   'x-dead-letter-routing-key': 'pagos'})
    canal.basic_publish(exchange='', routing_key='pagos.retry', body=mensaje,
                        properties=pika.BasicProperties(delivery_mode=2))

# En el consumidor: ante un fallo transitorio
reprogramar(json.dumps(datos_pago), 30)  # segunda oportunidad en 30 s

Puedes encadenar retry → retry2 → DLQ para escaleras de 30 s → 60 s → 2 min → DLQ.

Monitoriza la cola antes de que reviente

La resiliencia también es observar. Tres métricas que no deben pasar desapercibidas en el panel o tu sistema de monitorización:

  • Ready count: mensajes listos por procesar. Si crece sin parar, los workers no dan abasto.
  • Unacknowledged: mensajes en vuelo. Si se acumula, el worker se ha colgado (no ACK-nada).
  • DLQ size: mensajes caídos. Cada entrada aquí es un bug o un dato irrecuperable.
# vía API de gestión de RabbitMQ
curl -s -u guest:guest http://localhost:15672/api/queues/%2F/pagos |
  jq '{ready: .messages_ready, unacked: .messages_unacknowledged,
       total: .messages}'

# Salida de ejemplo:
# { "ready": 1240, "unacked": 3, "total": 1243 }  <- cuidado, ready alto!

Ejercicio

  1. Escribe un consumidor que distinga tres casos: éxito (ack), error transitorio (nack requeue) y error permanente (nack sin requeue a la DLQ).
  2. Configura una cola envio-email con DLQ y publica un payload intencionalmente malformado. Verifica que aparece en la DLQ y no vuelve a la cola principal.
  3. Implementa la escalera de reintentos 30s→60s→veneno con colas TTL y explica qué ocurre si el TTL se configura más pequeño que el tiempo real de procesamiento.

Resumen

  • Talgo: ACK si funcionó, NACK con requeue si es transitorio, NACK sin requeue si es permanente.
  • La DLQ aísla lo irrecuperable y evita loops infinitos de reintentos.
  • El reintento con backoff (colas TTL / plugin delayed) espera antes de insistir.
  • Monitoriza ready, unacknowledged y DLQ: son los tres semáforos de la salud.
