Colas prioritarias y TTL

🚀 Avanzado 9 min Mensajería Backend Módulo 2 · RabbitMQ y colas

Introducción

No todos los mensajes merecen el mismo trato. Un pago fallido que hay que reintentar debería saltarse la fila de los correos de marketing; y un verificador de identidad web, esperar solo unos minutos por si alguien necesita un reenvío.

RabbitMQ cubre ambos casos con mecanismos de la propia infraestructura:

  • Prioridad: saltarse la cola cuando el mensaje es más importante.
  • TTL (time-to-live): morir solo (o redirigirse) tras un lapso si nadie lo consumió.
  • Colas delayed: mensajes que esperan un tiempo definido antes de ser entregables.

Colas prioritarias

Se activa declarando la cola con x-max-priority (número máximo de niveles, p. ej. 10). Cada mensaje lleva un header priority del 0 al máximo; el broker ordena la cola para que primero salga el de mayor prioridad.

const amqp = require('amqplib');

async function prioridadDemo() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  // Cola con niveles de 0 a 10
  await ch.assertQueue('tareas', {
    durable: true,
    arguments: { 'x-max-priority': 10 }
  });

  // Mensaje normal (prioridad 0 por defecto)
  ch.sendToQueue('tareas', Buffer.from('{"tipo":"marketing"}'),
    { persistent: true });

  // Usuario PRO pagando: salta la fila
  ch.sendToQueue('tareas', Buffer.from('{"tipo":"pago-urgente"}'), {
    persistent: true,
    priority: 10
  });

  console.log('pago-urgente se procesará antes que marketing');
  await conn.close();
}

prioridadDemo();

Límite y advertencia: si defines priority: 999 sobre una cola con x-max-priority: 10, RabbitMQ lo trunca a 10. Y una cola prioritizada es más lenta (reordenación interna): no la uses para todo, solo cuando de verdad importe el orden de servicio.

Message TTL: el reloj del mensaje

El TTL define cuántos milisegundos vive un mensaje sin ser consumido. Pasado el tiempo, RabbitMQ lo expulsa: lo descarta o, si la cola tiene DLX, lo reenvía (patrón retry que ya vimos). Se puede fijar:

  • Por mensaje (propiedad expiration): valiosa para ofertas y códigos con vigencia.
  • Por cola (argumento x-message-ttl): política global para toda la cola.
import pika

canal = pika.BlockingConnection(pika.ConnectionParameters('localhost')).channel()

# Cola con TTL base de 5 minutos
canal.queue_declare(queue='ofertas', arguments={'x-message-ttl': 300000})

# Este cupón en concreto vence en 30 segundos (TTL por mensaje manda)
canal.basic_publish(
    exchange='', routing_key='ofertas',
    body=b'{"cupon":"FLASH30","descuento":30}',
    properties=pika.BasicProperties(expiration='30000',
                                     delivery_mode=2)
)

# El cupón FLASH30 desaparece a los 30 s si nadie lo consumió

Dato sutil: el TTL se cuenta desde que el mensaje llega a la cola, no desde que se entrega al worker. Un mensaje en vuelo (ya entregado) no se expira hasta que vuelve.

Colas delayed: el despertador

La combinación TTL + DLX permite una cola «de espera»: publicas el mensaje con TTL de N segundos y una DLX que apunta a la cola real. Al expirar, pasa a la cola de trabajo. Es el patrón delayed retry ya usado en la lección anterior, y RabbitMQ ofrece además el plugin oficial rabbitmq_delayed_message_exchange para hacerlo con un solo exchange:

# Activar el plugin de mensajes delayed
rabbitmq-plugins enable rabbitmq_delayed_message_exchange

# Con Docker
docker exec rabbit rabbitmq-plugins enable rabbitmq_delayed_message_exchange
const amqp = require('amqplib');

async function delayedDemo() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  // Exchange de tipo x-delayed-message
  await ch.assertExchange('retrasados', 'x-delayed-message', {
    durable: true,
    arguments: { 'x-delayed-type': 'direct' }
  });
  const q = await ch.assertQueue('recordatorios', { durable: true });
  await ch.bindQueue(q.queue, 'retrasados', 'aviso');

  // El mensaje no será entregable hasta dentro de 2 minutos
  ch.publish('retrasados', 'aviso', Buffer.from(JSON.stringify({
    tipo: 'recordatorio', correo: 'cliente@correo.com'
  })), {
    headers: { 'x-delay': 120000 }   // 120 s de espera
  });

  console.log('Recordatorio programado para +2 min');
  await conn.close();
}

delayedDemo();

Dónde brilla cada mecanismo

  • Prioridad: colas de soporte pagado vs gratuito, mensajes críticos de monitorización, reintentos urgentes.
  • TTL: cupones que expiran, ofertas por tiempo limitado, datos de sesión temporales, limpieza automática de colas sucias.
  • Delayed: recordatorios («en 24 h envía esto»), cierre de carritos abandonados, escalado de alertas, trabajo programado a hora exacta.

No confundas delayed con CRON: una cola delayed programa mensajes individuales, no procesos periódicos. Para «ejecuta esto cada día a las 3:00», sigue usando un cron que publique el mensaje.

Ejercicio

  1. Declara una cola soporte con x-max-priority: 10 y publica 3 mensajes con prioridades 0, 10 y 5. Verifica el orden de consumo en el panel.
  2. Configura una cola cupones con TTL de 1 minuto y DLQ, publica un cupón y observa cómo «muere» a la DLQ a los 60 s.
  3. Diseña con delayed un flujo: «20 minutos después de la primera falta de pago, envíame un recordatorio de vencimiento, una vez».

Resumen

  • La prioridad se configura con x-max-priority y el header priority por mensaje.
  • El TTL (por cola o por mensaje) expira los mensajes no consumidos; con DLX, los redirige.
  • TTL + DLX = colas de espera («delayed») sin plugins.
  • El plugin rabbitmq_delayed_message_exchange añade un exchange x-delayed-message con header x-delay.
  • Prioridad, TTL y delayed resuelven problemas distintos; úsalos deliberadamente.
