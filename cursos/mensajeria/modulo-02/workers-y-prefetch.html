Workers y prefetch

🚀 Avanzado 9 min Mensajería Backend Módulo 2 · RabbitMQ y colas

Introducción

Hasta aquí hemos visto colas y exchanges. Ahora el caso que justifica a RabbitMQ en casi todos los backends: repartir trabajo pesado entre varios procesos. El patrón se llama cola de trabajo (work queue): un productor publica tareas, y un cierto número de workers las consumen en paralelo.

El truco está en la repartición. RabbitMQ, por defecto, entrega los mensajes en round-robin: al primer worker, luego al segundo, al tercero, y vuelta. Cada mensaje va a un solo consumidor. Así se reparte la carga… pero no siempre de forma justa. Ahí entra el prefetch.

Round-robin y el problema de la carga

El round-robin reparte por orden de llegada al broker, no por capacidad. Si el worker A tarda 1 segundo por tarea y el B tarda 5 (o puede procesar 3 a la vez), el reparto se desequilibra: el broker ya entregó las tareas 1-2-3-4 a A y B por turnos, sin saber que A va más lento.

# Productor encola 6 tareas con round-robin
# El broker entrega: tarea1->A, tarea2->B, tarea3->A, tarea4->B...
# Si A es rápido, la fila de B crece; si B es lento, la de B se atasca.

Solo cuando los mensajes se consumen y confirmamos con basicAck es que el broker puede saber en qué punto vamos de cada cola.

El prefetch (basicQos): reparto justo

prefetch(N) limita cuántos mensajes «en vuelo» (no confirmados) puede tener un consumidor. El broker no le envía más mientras no confirme alguno. Resultado: el worker estable, rápido, recibe más; el lento no acumula.

const amqp = require('amqplib');

async function worker() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();
  const q = await ch.assertQueue('tareas', { durable: true });

  // Reparto justo: máx. 1 mensaje no confirmado por worker
  ch.prefetch(1);

  ch.consume(q.queue, async (msg) => {
    if (!msg) return;
    const tarea = JSON.parse(msg.content.toString());

    console.log('Procesando', tarea.id);
    await procesarTarea(tarea);      // trabajo real (puede tardar)
    console.log('Lista', tarea.id);

    ch.ack(msg);                     // libera el cupo del prefetch
  }, { noAck: false });

  console.log('Worker esperando con prefetch=1');
}

process.on('SIGINT', async () => {
  await conn.close();
  process.exit(0);
});

Con varios workers prefetch(1) los mensajes se reparten por disponibilidad real: el más veloz termina y pide el siguiente.

El productor de la cola de trabajo

Publicar tareas duras con persistencia para que ningún trabajo se pierda si se reinician los workers:

# Productor en Python: tareas con persistente = True
import pika, json

conexion = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
canal = conexion.channel()
canal.queue_declare(queue='tareas', durable=True)

for i in range(1, 101):
    tarea = json.dumps({'id': i, 'tipo': 'generar_reporte', 'anio': 2026})
    canal.basic_publish(
        exchange='',
        routing_key='tareas',
        body=tarea.encode(),
        properties=pika.BasicProperties(delivery_mode=2)  # persistent
    )

conexion.close()
print('100 tareas publicadas')

Persistencia = mensajes a disco con el flag delivery_mode=2 + cola durable. Las tareas sobreviven al reinicio del broker.

Escalar añadiendo workers

La belleza de la cola de trabajo: escalar = crear otro proceso. Levantas tres instancias del mismo worker y RabbitMQ se encarga de repartir. No hay sticky sessions, no hay pérdida de distribución; los workers son idénticos e intercambiables.

# Tres workers del mismo código, tres procesos
node worker.js &
node worker.js &
node worker.js &

# O con PM2
pm2 start worker.js -i 4 --name cola-tareas
# pm2 cluster: 4 workers compitiendo por la misma cola

Atención a los estados: un worker es seguro de multiplicar solo si no guarda estado local. Si necesita estado (qué archivo lleva, en qué página va), guárdalo en la base o Redis, nunca en memoria del proceso.

Consejos de producción

  • prefetch bajo: 1 o 2 para tareas pesadas; sube a 10-50 para tareas ligeras y rápidas.
  • ACK siempre al final: dentro del try del trabajo, nunca antes.
  • Maneja errores: si la tarea falla, decide entre nack (reintento) y requeue: false + DLQ (veneno). Lo verás en la próxima lección.
  • Mensajes pequeños y planos: evita meter binarios grandes en la cola; guarda la referencia (ID, URL del bucket) y deja que el worker descargue.

Ejercicio

  1. Implementa el worker de Node.js con prefetch(1) y publica 100 tareas desde el productor Python. Verifica en el panel que se consumen en paralelo.
  2. Modifica uno de los workers para que tarde 5 s por tarea y el otro 100 ms. Sin prefetch, ¿qué observas en las colas? ¿Y con prefetch(1)?
  3. Responde: ¿qué le pasaría a una tarea cuyo worker muere a mitad de procesamiento y nunca llama a ack?

Resumen

  • Patrón work queue: una cola, N workers idénticos procesando en paralelo.
  • El round-robin reparte por orden; el prefetch reparte por disponibilidad.
  • basicQos(prefetch=1) limita mensajes no confirmados por worker → reparto justo.
  • Escalar colas de trabajo = levantar más procesos del mismo worker.
  • Persistencia (cola durable + mensajes persistentes) para no perder tareas.
