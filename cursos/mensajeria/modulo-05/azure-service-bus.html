Azure Service Bus

🧠 Experto 12 min Mensajería y Sistemas Asíncronos Módulo 5 · Brokers y proveedores

Introducción

Azure Service Bus es el servicio de mensajería gestionado de Microsoft, pensado para integración en la nube de Azure: colas, tópicos con suscripciones, sesiones, programación de mensajes y deduplicación incluida.

Es especialmente fuerte en escenarios empresariales: soporta transacciones, dead-letter con causas, filtrado complejo y compatibilidad con AMQP desde cualquier lenguaje. Si tu stack vive en Azure, es la opción natural.

Definición

Azure Service Bus ofrece colas (competencia de consumidores) y tópicos con suscripciones (pub/sub), junto a sesiones para ordenar mensajes, planificación, deduplicación y soporte nativo de AMQP.

Por qué importa. Su ventaja es la integración con servicios Azure (Functions, Logic Apps, Event Grid) y funcionalidades de integración empresarial difíciles de montar a mano.

Cuándo usarlo. Úsalo en arquitecturas Azure que necesiten orden por sesión, deduplicación o transacciones entre colas; para ingesta analítica masiva siguen brillando más Kafka o Event Hubs.

Conceptos clave

  • Cola: entrega a un solo consumidor con peek-lock y delete de confirmación.
  • Tópico y suscripción: copia de cada mensaje para cada suscripción con filtros SQL.
  • Sesiones: agrupan mensajes de un mismo id para que los procese un solo consumidor.
  • Deduplicación: descarta duplicados dentro de una ventana temporal por mensaje id.
  • Dead-letter automático: cola de cuarentena por mensaje con motivo y excepciones.

Ejemplo intermedio

Un tópico con suscripciones y filtro SQL hace llegar cada evento solo a los interesados.

Ejemplo real

Una compañía migra su core bancario a Azure: cada operación de pago se envía a un tópico con filtros, las sesiones garantizan que el id de la cuenta se procesa en orden, la deduplicación evita dobles cargos y la DLQ audita cada mensaje rechazado con su motivo.

  • Usa sesiones cuando el orden por entidad sea obligatorio.
  • Activa la deduplicación en emisores que reintentan sin querer.
  • Revisa la DLQ periódicamente: cada mensaje allí tiene un motivo que diagnosticar.

Las transacciones de Service Bus permiten enviar y recibir de varias colas en un único commit, ideal para integraciones complejas.

Explicación

  • El peek-lock reserva el mensaje durante el lock duration y lo elimina solo al completar.
  • Las sesiones agrupan flujo de mensajes por una clave y lo entregan a un único consumidor.
  • La deduplicación usa el message id dentro de una ventana para descartar duplicados.
  • Los filtros SQL se evalúan dentro del broker, evitando descargas innecesarias.
  • La DLQ clasifica cada mensaje con motivo (expired, max delivery, session con fallo).

Errores comunes

  • No completar mensajes recibidos: reviven al terminar el lock y duplican trabajo.
  • Activar sesiones en todo: limitan el paralelismo al agrupar mensajes.
  • Ignorar la parte de la DLQ con motivos automáticos.

Buenas prácticas

  • Combina deduplicación y sesiones para flujos de pago sin dobles procesamientos.
  • Pasa las colas que ya no se usan a ARM/IaC para que el entorno sea reproducible.
  • Observa las métricas de mensajes en la DLQ y alerta ante crecimiento.

Ejercicio

  1. Crea una cola Service Bus y procesa mensajes en modo peek-lock.
  2. Monta un tópico con dos suscripciones con filtros distintos y verifica el enrutado.
  3. Activa la deduplicación y envía un mensaje duplicado: comprueba que solo entra uno.

Resumen

  • Service Bus ofrece colas y tópicos gestionados con sesiones y filtros.
  • El peek-lock y la deduplicación protegen contra pérdidas y duplicados.
  • La DLQ automática clasifica los mensajes fallidos por motivo.
