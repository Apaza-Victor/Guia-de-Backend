AWS SQS y SNS

🧠 Experto 13 min Mensajería y Sistemas Asíncronos Módulo 5 · Brokers y proveedores

Introducción

Amazon simplifica la mensajería con dos servicios gestionados: SQS para colas (una entrega por consumidor) y SNS para difusión pub/sub (cada suscriptor recibe copia). Ambos eliminan la operación del broker y se integran con el resto de servicios AWS.

SQS ofrece dead letter queues, visibilidad por mensaje, retención configurable y escalado automático; SNS agrega filtrado de mensajes y entrega a SQS, Lambda, HTTP y email. Juntos forman la mensajería estándar en la nube de Amazon.

Definición

SQS es un servicio de colas gestionado (Simple Queue Service) con entregas at-least-once y ventana de visibilidad; SNS es un servicio pub/sub (Simple Notification Service) que difunde mensajes a distintos tipos de suscriptores.

Por qué importa. Al ser gestionados, no operas brokers, escalas con el uso y pagas por petición; su integración con Lambda, S3 e IAM acelera el desarrollo en AWS.

Cuándo usarlo. Usa SQS para trabajos encolados con ack por mensaje y DLQ; usa SNS para difundir eventos a varios destinos o a colas regionales distintas.

Conceptos clave

  • Cola estándar: entrega al menos una vez, reorden posible; FIFO: orden estricto y deduplicación.
  • Visibility timeout: el tiempo que un mensaje queda oculto de otros consumidores tras tomarlo.
  • Dead Letter Queue: redrive hacia una cola de emergencia tras superar recepciones.
  • SNS Topic con filtros: cada suscripción recibe solo mensajes que cumplen su política.
  • Fanout SNS→SQS: una sola publicación reparte copias a varias colas.

Ejemplo básico

Envie un mensaje a una cola SQS y léalo desde un worker Lambda con el SDK de AWS.

Ejemplo intermedio

Publica un evento en SNS y deja que un fanout lo entregue a dos colas SQS distintas.

Ejemplo real

Un processing de pedidos AWS: la API publica en SNS, el fanout duplica hacia 'facturas' y 'inventario', y un worker Python lee de 'facturas'. Si un cargo falla 3 veces, SQS reenvía a la DLQ y una alerta CloudWatch avisa al equipo.

  • Usa colas FIFO para pagos donde el orden importa, estándar para el resto.
  • Configura redrive policy para no enviar a DLQ mensajes recuperables.
  • Prueba el visibility timeout para no procesar dos veces un trabajo lento.

SQS no garantiza que un mensaje se procese una sola vez: la idempotencia en el worker sigue siendo obligatoria.

Explicación

  • El visibility timeout oculta el mensaje durante el procesamiento; si el worker muere, el mensaje vuelve.
  • La cola FIFO garantiza orden, pero limita throughput: sopesa precio y rigor.
  • SNS añade los atributos de mensaje que permiten a las suscripciones filtrar.
  • El fanout SNS→SQS replica el patrón pub/sub sin tocar lógica del productor.
  • La DLQ de SQS incluye timestamp del envío y motivo, ideal para diagnosis.

Errores comunes

  • Olvidar el delete_message: el mensaje reaparece y se procesa cientos de veces.
  • Visibility timeout menor que el trabajo: otro worker toma el mensaje a mitad.
  • Usar cola estándar donde el orden es crítico: los reordenes rompen la lógica.

Buenas prácticas

  • Configura WaitTimeSeconds=10 para reducir llamadas vacías y coste.
  • Activa la métrica de mensajes disponibles en CloudWatch para vigilar el backlog.
  • Empareja SNS con una DLQ por cada suscripción para no perder eventos de nadie.

Ejercicio

  1. Crea una cola SQS y procesa 20 mensajes con un worker Lambda.
  2. Monta un fanout SNS con dos suscripciones SQS y verifica que ambas reciben copia.
  3. Configura el redrive a DLQ tras 3 recepciones y observa el reenvío.

Resumen

  • SQS gestiona colas con visibilidad, DLQ y escalado automático.
  • SNS difunde eventos con filtrado y fanout a múltiples destinos.
  • Idempotencia y visibility timeout correctos evitan el doble procesamiento.
