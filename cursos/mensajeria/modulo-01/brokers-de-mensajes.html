Brokers de mensajes

🚀 Avanzado 10 min Mensajería Backend Módulo 1 · Fundamentos

Introducción

Un broker de mensajes es el servidor que recibe mensajes de los productores, los almacena y los entrega a los consumidores. Puede ser un proceso propio (RabbitMQ, Kafka) o un servicio gestionado en la nube (SQS, SNS, Redis Streams en memoria). Elegir bien el broker equivale a decidir cuánto tráfico, durabilidad y complejidad necesitas.

Los cuatro protagonistas del backend moderno, cada uno con personalidad propia:

  • RabbitMQ: el gestor de colas clásico. Maestro del routing flexible.
  • Apache Kafka: el log distribuido. Pensado para streams de eventos y alto volumen.
  • Redis Streams: colas muy rápidas dentro de un Redis ya existente.
  • AWS SQS/SNS: colas y topics gestionados, sin servidor que administrar.

Comparativa rápida

Así se posicionan frente a las preguntas clave:

  • Modelo: RabbitMQ y SQS son colas (con soporte de topics vía exchange o SNS). Kafka y Redis Streams son logs con clara vocación de eventos.
  • Garantías: RabbitMQ y SQS entregan at-least-once; Kafka ofrece exactly-once en modos especiales; Redis Streams depende del consumidor.
  • Orden: en Kafka el orden se garantiza por partición; en RabbitMQ y SQS el orden global no está garantizado (SQS FIFO sí lo permite).
  • Reproducción: Kafka permite releer mensajes viejos (los conserva por retención); una cola de RabbitMQ o SQS elimina el mensaje tras el ACK.
  • Operación: SQS/SNS no requieren infraestructura. RabbitMQ y Kafka requieren clústeres que vigilar.

RabbitMQ: colas con routing fino

Se apoya en exchanges que enrutan cada mensaje a colas mediante reglas (direct, fanout, topic). Es la elección natural para tareas de trabajo, notificaciones y ACKs manuales. Su modelo de consumo es push: empuja el mensaje al consumidor.

# Levantar RabbitMQ con Docker para probar en minutos
docker run -d --name rabbit \
  -p 5672:5672 -p 15672:15672 \
  rabbitmq:3-management

# Consola de administración disponible en http://localhost:15672
# Usuario por defecto: guest / guest

Apache Kafka: el log distribuido

En Kafka un mensaje es un evento anexado a un topic particionado y replicado entre brokers. Los consumidores no borran nada: avanzan un puntero (offset). Eso permite releer historial, reconstruir estados y alimentar pipelines de datos. Es la opción reina del event streaming y las arquitecturas orientadas a eventos.

# Kafka necesita ZooKeeper (o KRaft) + los brokers
docker run -d --name kafka -p 9092:9092 \
  apache/kafka:3.7.0

# Crear un topic con 3 particiones y replicación 1
docker exec kafka kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic pedidos \
  --partitions 3 --replication-factor 1

Redis Streams y AWS SQS/SNS

Redis Streams (XADD, XREADGROUP) añade colas con confirmación y consumer groups a un Redis que ya tienes corriendo. Extrema baja latencia (microsegundos) y cero infraestructura extra, a cambio de durabilidad limitada y mensajes que se pierden bajo presión de memoria.

AWS SQS es la cola gestionada por excelencia: 99,9 % de disponibilidad, retries, dead-letter y visibilidad. SNS es el topic hermano (fanout). Juntos forman el stack clásico de AWS para mensajería asíncrona.

# Ejemplo con boto3: enviar y recibir de una cola SQS
import boto3

sqs = boto3.client('sqs', region_name='us-east-1')
url = 'https://sqs.us-east-1.amazonaws.com/123456789012/pedidos'

sqs.send_message(
    QueueUrl=url,
    MessageBody='{"pedido":"P-2026-0001","total":129.90}'
)

resp = sqs.receive_message(QueueUrl=url, MaxNumberOfMessages=1)
if resp.get('Messages'):
    mensaje = resp['Messages'][0]
    print('Recibido:', mensaje['Body'])
    # Confirmar para que SQS lo elimine
    sqs.delete_message(QueueUrl=url,
                       ReceiptHandle=mensaje['ReceiptHandle'])

Cómo elegir tu broker

  • Tareas y notificaciones con routing flexible → RabbitMQ.
  • Stream de eventos, historial y alto throughput en millones de msg/s → Apache Kafka.
  • Quieres cachear y encolar en el mismo servidor con latencia mínima → Redis Streams.
  • No quieres administrar infraestructura y ya estás en AWS → SQS + SNS.
  • Regla de oro: si solo necesitas «proceso esto una vez», una cola simple basta; no cargo Kafka porque «está de moda».

No las mezcles por capricho: usar RabbitMQ para tareas y Kafka para eventos de dominio es una combinación legítima y común. Usar dos brokers para lo mismo es deuda técnica.

Un entorno local con Docker Compose

Para estudiar RabbitMQ y Kafka juntos, un docker-compose.yml te levanta ambos:

services:
  rabbitmq:
    image: rabbitmq:3-management
    ports:
      - "5672:5672"
      - "15672:15672"

  kafka:
    image: apache/kafka:3.7.0
    ports:
      - "9092:9092"
    environment:
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_NODE_ID: 1
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://localhost:9092

Con docker compose up -d tendrás ambos listos para las lecciones del módulo 2 (RabbitMQ) y del módulo 3 (Kafka).

Ejercicio

  1. Elige un escenario propio (envío de correos, sincronización de datos, pipeline de analítica) y razona cuál de los cuatro brokers encaja mejor.
  2. Levanta RabbitMQ con Docker y publica un mensaje a la cola hola-mundo usando el panel de administración.
  3. Investiga: ¿qué garantía de entrega ofrece SQS de forma nativa y qué problema resuelve una cola FIFO de SQS?

Resumen

  • RabbitMQ destaca por routing flexible y colas de trabajo con ACKs.
  • Kafka es un log distribuido: eventos reproducibles, orden por partición y alto volumen.
  • Redis Streams agrega colas rápidas a un Redis existente; SQS/SNS aportan colas gestionadas sin servidor.
  • Elige según modelo (cola vs evento), garantías, orden, durabilidad y si quieres operar infraestructura.
