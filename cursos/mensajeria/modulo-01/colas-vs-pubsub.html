Colas vs Pub/Sub

🚀 Avanzado 9 min Mensajería Backend Módulo 1 · Fundamentos

Introducción

Cuando hay un mensaje nuevo, ¿quién debe recibirlo? La respuesta define dos modelos de mensajería opuestos:

  • Cola (punto a punto): el mensaje se entrega a un consumidor. Los demás que escuchen la misma cola compiten, pero nunca dos procesan el mismo mensaje.
  • Pub/Sub (topic): el mensaje se publica en un topic y se copia a todos los suscriptores interesados. Es un broadcast con filtro por interés.

La confusión más común es creer que una cola y un topic son lo mismo. Comparten infraestructura, pero resuelven problemas distintos: repartir trabajo en un caso y notificar a muchos en el otro.

Cola: repartir trabajo entre consumidores

Una cola se usa para tareas que exactamente un proceso debe ejecutar. Piensa en el envío de correos: si tres workers escuchan la cola emails, cada correo debe procesarse una sola vez, así que el broker lo entrega a un único consumidor.

# Diagrama de competencia: 1 mensaje, 1 consumidor
Producción -> [cola "emails"]
                      |
              +-------+--------+
              | worker-1      |  consume el mensaje
              | worker-2      |  (los demás no lo ven)
              | worker-3      |
              +--------------+

Si pones más consumidores, el trabajo se reparte entre todos: es la forma más sencilla de escalar procesamiento. La respuesta del sistema es «entregado a uno, listo».

Pub/Sub: notificar a todos los interesados

Un topic se usa cuando varios sistemas necesitan reaccionar al mismo hecho. En una tienda, cuando un pedido se concreta: el servicio de inventario quiere descontar stock, el de facturación quiere generar la boleta, el de notificaciones quiere avisar al usuario y el de analítica quiere registrar el evento.

# Diagrama de broadcast: 1 mensaje, muchos suscriptores
Publicador -> [topic "pedido.completado"]
                       |
       +---------------+---------------+
       | sub factura    | sub inventario |
       | sub notificaciones | sub analítica |
       +---------------+---------------+
       # Cada suscriptor recibe una copia

El publicador no sabe quién escucha ni cuántos son. Añadir un suscriptor nuevo (por ejemplo, un servicio de recomendaciones) no obliga a tocar al publicador: esa es la magia del desacople por topic.

Ejemplo de implementación

Con la librería amqplib de Node.js y RabbitMQ, publicar a una cola y a un topic se ve casi igual desde el productor; la diferencia está en el modelo (qué exposiciones se enrutan). Primero, la cola de trabajo:

const amqp = require('amqplib');

async function publicarEnCola() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();
  const q = await ch.assertQueue('emails', { durable: true });

  ch.sendToQueue(q.queue, Buffer.from(JSON.stringify({
    destino: 'cliente@correo.com',
    asunto: 'Tu pedido va en camino'
  })), { persistent: true });

  console.log('Mensaje encolado para un único worker');
  await conn.close();
}

async function publicarEnTopic() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  await ch.assertExchange('eventos', 'topic', { durable: true });
  ch.publish('eventos', 'pedido.completado', Buffer.from(JSON.stringify({
    pedidoId: 'P-2026-0001', total: 129.90
  })));

  console.log('Evento publicado para todos los suscriptores');
  await conn.close();
}

Observa la diferencia de intención: sendToQueue entrega a una cola concreta, publish a un exchange que replica el mensaje a cada binding que coincida.

Cuándo usar cada uno

  • Cola: un correo, un trabajo de importación, un redimensionamiento de imagen, un webhook de pago que debe procesarse una vez. Si más de un consumidor lo tomara, sería un bug.
  • Topic: un hecho de dominio con varios efectos: pedido completado, usuario creado, ticket cerrado, alerta disparada. El desconocimiento entre emisor y oyentes es una ventaja.
  • Híbrido: en la práctica se combinan: un topic entrega el evento a varios servicios, y cada servicio lo canaliza hacia su propia cola interna para repartirlo entre sus workers.

Regla de oro: pregunta «¿cuántos procesos deben reaccionar?». Si la respuesta es «uno», usa cola. Si es «muchos», usa topic. Si es «muchos, cada uno con su equipo de workers», combina ambos.

Ejercicio

  1. Clasifica estas situaciones como cola o topic: (a) enviar un PDF generado, (b) avisar del alta de un usuario a 4 servicios, (c) procesar pagos de una pasarela, (d) difundir una alerta de seguridad a todos los componentes.
  2. Escribe el JSON de un evento usuario.creado y decide qué suscriptores naturales tendría en tu propia aplicación.
  3. Responde: si usaras una cola donde el evento «usuario.creado» debería llegar a facturación e inventario, ¿qué problema aparece cuando solo uno de los dos la consume?

Resumen

  • Las colas entregan cada mensaje a un único consumidor: reparten trabajo.
  • Los topics copian el mensaje a todos los suscriptores: difunden hechos.
  • La cola escala añadiendo workers; el topic escala añadiendo suscriptores.
  • Los sistemas reales suelen combinar ambos: topic para difundir, cola interna para procesar.
