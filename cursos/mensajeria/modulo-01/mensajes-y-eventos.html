Mensajes vs eventos

🚀 Avanzado 8 min Mensajería Backend Módulo 1 · Fundamentos

Introducción

«Mensaje» y «evento» se usan como sinónimos en muchos textos, pero en el diseño de sistemas de mensajería distinguen dos intenciones muy distintas. Confundirlos conduce a APIs confusas: un sistema que no sabe si lo que recibe es una orden que debe ejecutar o un hecho que ya ocurrió.

  • Mensaje dirigido (comando): «haz esto». Pide trabajo, espera ejecución.
  • Evento de dominio: «esto ya pasó». Informa de un hecho consumado, no pide nada.

El mensaje dirigido

Un mensaje dirigido nombra una acción y apunta a un receptor (aunque el broker lo abstrae). Ejemplos: enviarEmail, generarFactura, importarCatalogo. Su verbo va en imperativo y el emisor espera (o confía) en que alguien lo procese:

{
  "tipo": "mensaje",
  "accion": "enviar_email",
  "version": 1,
  "id": "msg-7f3a91",
  "timestamp": "2026-01-12T09:41:02Z",
  "payload": {
    "destinatario": "cliente@correo.com",
    "plantilla": "confirmacion_pedido",
    "pedidoId": "P-2026-0001"
  }
}

Un mensaje resultado bien pensado es idempotente: si se procesa dos veces por un reintento, el efecto no se duplica (no enviar dos correos, no cobrar dos veces). Esa característica será clave en la lección de garantías de entrega.

El evento de dominio

Un evento de dominio describe un hecho del pasado, en tiempo pasado, con el nombre del suceso: pedido.completado, usuario.registrado, pago.aprobado. No contiene instrucciones, solo la información del hecho y metadatos para trazarlo:

{
  "tipo": "evento",
  "nombre": "pedido.completado",
  "version": 1,
  "eventId": "evt-58c9d1",
  "correlationId": "carr-orden-8842",
  "timestamp": "2026-01-12T09:41:02Z",
  "payload": {
    "pedidoId": "P-2026-0001",
    "usuarioId": "U-99",
    "items": [
      { "sku": "A-01", "cantidad": 2 }
    ],
    "total": 129.90
  }
}

Fíjate en dos campos extra: eventId (identidad del hecho) y correlationId (cadena que une todos los eventos de una misma operación de negocio). Con ellos puedes deduplicar y reconstruir el recorrido completo de un pedido.

Ejemplo: el alta de un usuario

El mismo hecho de negocio «el usuario se registró» produce una orden para un servicio y un evento para el resto. En la práctica ambos van por caminos distintos del broker:

const amqp = require('amqplib');

async function registrarUsuario(usuario) {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();

  // 1) MENSAJE dirigido: la cola 'emails' procesará el correo
  ch.sendToQueue('emails', Buffer.from(JSON.stringify({
    accion: 'enviar_email', id: `ms-${usuario.id}`,
    payload: { destinatario: usuario.correo, plantilla: 'bienvenida' }
  })), { persistent: true });

  // 2) EVENTO de dominio: el topic 'usuarios' difunde el hecho
  await ch.assertExchange('usuarios', 'topic', { durable: true });
  ch.publish('usuarios', 'usuario.registrado', Buffer.from(JSON.stringify({
    eventId: `evt-${Date.now()}`, timestamp: new Date().toISOString(),
    payload: { usuarioId: usuario.id, correo: usuario.correo }
  })));

  await conn.close();
}

// facturación, recomendar luego ese correo: todos escuchan el topic

La cola recibe una orden única; el topic entrega el hecho a cuantos quieran escuchar, sin que el productor los conozca.

Claves para distinguirlos

  • Tiempo del verbo: imperativo (envía, genera) = mensaje; pasado (enviado, generado) = evento.
  • Receptor: el mensaje tiene un destinatario lógico; el evento no conoce ni le importa quién lo oye.
  • Efecto: el mensaje provoca trabajo; el evento ya es el resultado del trabajo hecho.
  • Naming: colas de comandos emails, facturas; topics de eventos pedido.completado, usuario.registrado.
  • Persistencia: los eventos se conservan como historia (Kafka los guarda por retención); los mensajes de cola se consumen y desaparecen.

Práctica recomendada: publica eventos en tiempo pasado (pago.aprobado), no en imperativo (aprobar-pago). El nombre imperativo obliga a los oyentes a interpretar su rol; el pasado describe el hecho sin ambigüedad.

Ejercicio

  1. Escribe cinco «cosas» que te gustaría publicar en tu sistema y clasifícalas como mensaje o evento. Corrige los nombres que no sigan la regla del tiempo del verbo.
  2. Completa el JSON del evento pago.rechazado con eventId, correlationId, timestamp y un payload mínimo.
  3. Responde: ¿por qué convertir el mensaje enviar_email en un evento email.enviado antes de enviarlo sería un error de diseño?

Resumen

  • Un mensaje dirigido pide una acción («haz esto») y tiene un destinatario lógico.
  • Un evento de dominio describe un hecho consumado («esto pasó») y va a todo interesado.
  • Los mensajes deben ser idempotentes; los eventos se nombran en tiempo pasado con eventId y correlationId.
  • El naming honesto (cola de comandos vs topic de eventos) hace legible tu arquitectura.
