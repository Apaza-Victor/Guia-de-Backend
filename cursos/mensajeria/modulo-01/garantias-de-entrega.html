Garantías de entrega

🚀 Avanzado 9 min Mensajería Backend Módulo 1 · Fundamentos

Introducción

Imagina que el mensaje «cobrar 129,90 a la tarjeta de Paula» viaja por tu broker. El consumidor lo recibe y, justo antes de responder al broker, su máquina se cae. El broker no sabe si se procesó o no. Esta ambigüedad —la misma que tienen las redes y cualquier sistema distribuido— obliga a definir una garantía de entrega.

Hay tres garantías posibles, y señalar exactamente su coste y su peligro es la parte más importante de esta lección.

At-most-once: máx. una vez

El broker entrega el mensaje y no vuelve a preguntar nada. Si el consumidor se cae a mitad de proceso, el mensaje se pierde silenciosamente. Se usa cuando perder un mensaje es aceptable (telemetría, métricas, logs) y la latencia importa más que la completitud:

  • Ventaja: máxima velocidad, mínima complejidad.
  • Riesgo: pérdida de mensajes sin notificación.
  • Ejemplo: contadores de analytics donde perder un evento no cambia el informe.

En RabbitMQ, at-most se obtiene con autoACK y publicaciones no durables:

const amqp = require('amqplib');

async function consumirSinAck() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();
  const q = await ch.assertQueue('metricas');

  // noAck = true: el broker ya no reclama nada, entrega y olvida
  ch.consume(q.queue, (msg) => {
    registrarMetrica(JSON.parse(msg.content.toString()));
  }, { noAck: true });

  console.log('Consumiendo métricas: pérdidas aceptables');
}

At-least-once: mínimo una vez

El consumidor devuelve un ACK (acknowledgment) solo cuando termina. Si el proceso falla sin ACK, el broker vuelve a entregar el mensaje. Garantiza que no se pierda nada, pero admite duplicados:

  • Ventaja: ningún mensaje desaparece.
  • Riesgo: el mismo mensaje puede procesarse dos veces por culpa de un reintento.
  • Ejemplo: correos, facturación, integraciones — la mayoría del backend serio.

La contramedida a los duplicados es la idempotencia: diseñar el procesamiento para que aplicar la misma operación dos veces produzca el mismo resultado. Antes de enviar el correo, registra el hash del mensaje en la base y verifica si ya se procesó:

const amqp = require('amqplib');

async function procesarConAck() {
  const conn = await amqp.connect('amqp://localhost');
  const ch = await conn.createChannel();
  const q = await ch.assertQueue('pagos', { durable: true });

  ch.consume(q.queue, async (msg) => {
    const cobro = JSON.parse(msg.content.toString());
    const yaProcesado = await dbExiste('cobros', cobro.idDeOperacion);

    if (!yaProcesado) {
      await apiPagos.cobrar(cobro.tarjeta, cobro.monto); // 1ª y única vez
      await dbGuardar('cobros', cobro.idDeOperacion);
    }

    // Solo aquí, trabajo completado: confirmar al broker
    ch.ack(msg);
  }, { noAck: false });

  console.log('Consumiendo pagos: mínimo una vez + idempotencia');
}

Fíjate: el ACK se envía después de persistir. Si el proceso muere antes del ACK, el broker reintentará, y la verificación de idempotencia evitará el doble cobro.

Exactly-once: exactamente una vez

El ideal matemático: cada mensaje se procesa exactamente una vez. En la práctica no existe de forma universal y gratuita; se alcanza por construcción, combinando transacciones entre el procesamiento y el ACK:

# Exactly-once por transacción local: ACK + efecto en la misma base
import json
import psycopg2
from psycopg2.extras import Json

conn = psycopg2.connect('dbname=tienda user=app')
cur = conn.cursor()

def consumir(msg_id, payload):
    with conn:
        # Insertar el cobro y marcar el mensaje en la MISMA transacción
        cur.execute(
            'INSERT INTO cobros(msg_id, monto) VALUES (%s, %s)',
            (msg_id, payload['monto'])
        )
        cur.execute('INSERT INTO acks(msg_id) VALUES (%s)', (msg_id,))
    # Si el commit llegó, el trabajo está hecho Y el ACK registrado: una sola vez

Kafka ofrece un modo transactional producer (exactly-once dentro de su propio ecosistema). Pero el estándar de la industria para la mayoría de los casos es: at-least-once + idempotencia, mucho más simple de operar.

Regla práctica: salvo casos muy calificados, usa at-least-once y haz el consumidor idempotente. El exactly-once «real» requiere transacciones distribuidas que cuestan latencia y complejidad desproporcionadas para la mayoría de negocios.

Redelivery y la causa de los duplicados

El duplicado no aparece porque el broker sea caprichoso, sino por combinaciones normales de fallos:

  • Fallo antes del ACK: el mensaje se procesó pero el ACK nunca llegó → reintento duplicado.
  • Conexión caída: RabbitMQ reencola mensajes «no confirmados» cuando un consumidor se desconecta.
  • Timeout: ken el procesado tardó más que la ventana del broker y este volvió a entregar.
  • Partición del cliente de Kafka: tras un rebalanceo, el offset se reprocesa desde el último commit.

La respuesta no es culpar al broker, sino modelar la idempotencia desde el inicio: registra un identificador único en el mensaje (idDeOperacion, eventId) y úsalo como clave única en tu almacenamiento.

Un mensaje completo para entrega confiable

Reúne todo lo aprendido en esta lección y en la de mensajes vs eventos:

{
  "tipo": "mensaje",
  "accion": "cobrar_pedido",
  "version": 1,
  "idDeOperacion": "op-8aa4c1",   // clave de idempotencia
  "correlationId": "carr-orden-8842",
  "entrega": "at-least-once",      // en espera de confirmación
  "timestamp": "2026-01-12T09:41:02Z",
  "payload": {
    "pedidoId": "P-2026-0001",
    "tarjetaUltimos4": "4242",
    "monto": 129.90
  }
}

Hasta los brokers más simples permiten interpretar este mensaje con ACK y deduplicación completa.

Resumen

  • At-most-once pierde mensajes sin avisar: útil para telemetría, no para negocio.
  • At-least-once con ACK garantiza que nada se pierde a costa de posibles duplicados.
  • Exactly-once universal no existe; se aproxima con transacciones o con idempotencia.
  • La idempotencia (clave única en el mensaje + verificación en el consumidor) es la herramienta maestra.
  • Regla general: at-least-once + consumidor idempotente.
