Request/Reply con mensajería

🧠 Experto 11 min Mensajería y Sistemas Asíncronos Módulo 4 · Patrones de mensajería

Introducción

La mensajería asíncrona se asocia a olvidar y seguir, pero a veces necesitas una respuesta: validar un documento, consultar una protección, pedir un informe. El patrón Request/Reply lleva esa conversación al mundo asíncrono.

El productor publica una petición con un identificador correlacion y una dirección de respuesta, y un consumidor procesa y devuelve el resultado a esa dirección. Así se combina lo mejor de HTTP con el desacople de las colas.

Definición

Request/Reply (también llamado correa de mensajería) publica una petición en una cola de trabajo y recoge la respuesta en una cola o tópico específico, enlazando ambas con un correlation id.

Por qué importa. Permite peticiones síncronas a través de brokers asíncronos, con retry, backlog y buffering propios del transporte por colas.

Cuándo usarlo. Úsalo cuando el proceso es largo o el servicio de destino es frágil, o cuando necesitas reintentos sin bloquear el hilo de la API.

Conceptos clave

  • Correlation id: el identificador que casa cada petición con su respuesta.
  • Reply to: la cola o tópico al que el consumidor debe publicar la respuesta.
  • Timeout: el límite de espera del peticionario antes de dar por fallida la llamada.
  • El patrón evita acoplar a un servicio concreto: el destino se resuelve por la cola.
  • REST sigue latiendo para bajo acoplamiento, pero msgId la cola protegen al servidor de picos.

Ejemplo básico

Con RabbitMQ, el peticionario crea una cola de respuesta temporal y envía la petición indicando reply_to y correlation_id.

Ejemplo intermedio

El consumidor procesa y responde usando el reply_to y el correlation_id de la petición.

Ejemplo real

Una app de contabilidad genera facturas PDF que tardan varios segundos. La API publica un Request/Reply a una cola de workers: el hilo HTTP queda libre, el front espera un callback, y si el worker se cae, la petición se reintenta sin perder el correlación.

  • Define siempre un timeout y un fallback para cuando no llega la respuesta.
  • Usa el correlation id para enrutar respuestas incluso con múltiples peticiones en vuelo.
  • Registra en el log la petición y respuesta con el mismo correlación para depurar.

Request/Reply no sustituye a REST: úsalo para procesos largos o frágiles. Para llamadas rápidas, HTTP es más simple y observable.

Explicación

  • El desacople se mantiene porque el peticionario desconoce qué servicio procesa la petición.
  • El correlation id hace el patrón seguro frente a respuestas desordenadas o duplicadas.
  • El timeout convierte una espera infinita en un error controlado.
  • La cola de respuesta exclusiva se destruye al cerrar la conexión, evitando basura.
  • Con varios peticionarios compartiendo colas de respuesta se necesita el correlation id sí o sí.

Errores comunes

  • Olvidar el correlation id: las respuestas se mezclan entre peticiones.
  • Esperar sin timeout: un worker caído dejará la petición colgada para siempre.
  • Usar la misma cola de respuesta para muchos clientes sin correlación.

Buenas prácticas

  • Genera correlation ids con UUID para evitar colisiones.
  • Monitorea el tiempo de respuesta del patrón como una métrica de cola.
  • Considera responder con referencia a un evento posterior cuando la respuesta tarde demasiado.

Ejercicio

  1. Implementa un Request/Reply simple y verifica que casa la respuesta con la petición.
  2. Añade un timeout y comprueba el comportamiento cuando el consumidor no responde.
  3. Envía dos peticiones de tipos distintos y asegura que cada respuesta llega a su dueño.

Resumen

  • El patrón Request/Reply envía peticiones por cola y recoge respuestas por correlación.
  • El correlation id y el timeout lo hacen seguro frente a desorden y fallos.
  • Es ideal para procesos largos o frágiles donde HTTP se quedaría corto.
