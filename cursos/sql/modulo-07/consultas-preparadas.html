Consultas preparadas

⚔️ Avanzado 11 min SQL Módulo 7 · SQL en el backend

El peligro

Todo lo que llega de una API (un nombre, un filtro) es texto no confiable. Si lo concatenas en un SELECT, el usuario puede reescribir tu consulta:

Concatenar entrada en SQL es el error de seguridad número uno en backend.

Consultas preparadas = la barrera

En vez de incrustar el valor, declaras un parámetro y pasas el dato por separado. La base distingue «estructura de la consulta» de «valor», así que un valor malicioso nunca puede ejecutarse como SQL:

En el código del backend

El driver escapa el valor por ti. Parámetro ≠ SQL: eso es todo el truco.

Advertencias

  • Los parámetros solo valen para valores, no para nombres de columna ni de tabla (eso se valida en código con listas permitidas).
  • No intentes «sustituir manualmente»: usa la API de tu driver, no el escapar de a mano.
  • Las consultas preparadas además se cachean y se reutilizan: a menudo son más rápidas en bucles.

La regla de oro

Si en tu código hay un '${' o un + nombre + dentro de una cadena SQL, esa línea es una vulnerabilidad. Sustitúyela por la versión parametrizada de tu driver.

Ejercicio

  1. Escribe una consulta preparada en tu stack favorito.
  2. Prueba la inyección ' OR '1'='1 en la versión concatenada y anota el resultado.
  3. Busca en tu código alguna cadena SQL concatenada y corrígela.

Resumen

  • Concatenar entrada = puerta abierta a la inyección.
  • Preparada = estructura y valores separados.
  • Nombres de columnas/tablas no van en parámetros.
  • La regla: nunca armar SQL con entrada del usuario.
