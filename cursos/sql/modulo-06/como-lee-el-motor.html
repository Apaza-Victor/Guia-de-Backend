Cómo lee el motor

⚔️ Avanzado 11 min SQL Módulo 6 · Optimización

Introducción

SQL es declarativo: dices QUÉ quieres, no CÓMO conseguirlo. El motor decide el cómo. Para optimizar bien, hay que saber cómo piensa ese motor.

Las tres fases

  1. Parseo: ¿es SQL válido? ¿existen las tablas y columnas? Se valida sin leer datos.
  2. Optimización: el optimizador estima costos (filas a leer, índices disponibles, estrategias) y genera un plan de ejecución.
  3. Ejecución: el motor recorre el plan, lee datos y devuelve filas.

El plan depende de estadísticas (cuántas filas por valor), índices, y a veces órdenes mal elegidos. De ahí que un plan pueda ser «sabio» aunque tu consulta se escriba torcida… o al revés.

El costo

El motor estima un «precio» por operación: leer un bloque de disco, aplicar un filtro, ordenar. La moneda ideológica: menos bloques leídos = más rápido. Un FULL TABLE SCAN lee la tabla entera (barato para 100 filas, brutal para 50 millones).

Errores de optimizador

  • Estadísticas desactualizadas: el plan cree que hay 10 filas y hay 10 millones.
  • Funciones sobre la columna: WHERE YEAR(fecha)=2025 rompe el uso del índice (mejor rango de fechas).
  • Comodín inicial: LIKE '%texto' tampoco usa índice.
  • JOIN con costes altos: el optimizador elige estrategia (nested loop, hash…) según sus estimaciones.

Y luego está el cache

Los datos viven en páginas de memoria caché. Repetir una consulta es insoportablemente rápido si ya está en caché. Por eso medir «a ciegas» engaña: mide consultas frías y calientes.

Ejercicio

  1. Escribe «el mismo resultado» de dos formas: con función sobre columna y con rango.
  2. Razona por qué una puede usar índice y la otra no.
  3. Piensa: ¿qué necesita el optimizador para decidir bien?

Resumen

  • SQL es declarativo; el motor decide el plan.
  • Parseo → optimización → ejecución.
  • Menos bloques leídos = más rápido.
  • Funciones y comodines rompen índices.
  • El caché maquilla las mediciones.
