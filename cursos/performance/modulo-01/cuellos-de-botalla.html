Identificar cuellos de botella

🚀 Avanzado 9 min Performance Backend Módulo 1 · Medir rendimiento

Introducción

Cuando un servicio se degrada, alguien tiene que responder «¿qué recurso se agotó?». La respuesta cae casi siempre en una de cuatro categorías: CPU, memoria, I/O (disco y red) o red/otra dependencia. Cada una tiene síntomas distintos y herramientas distintas. Confundirlas es la principal causa de optimizaciones que no arreglan nada.

La idea central: un sistema va a la velocidad de su recurso más escaso. Tú solo tienes que descubrir cuál es.

Cuello de botella: CPU

El procesador está al 100% y las peticiones se encolan. Síntomas clásicos: más CPU del servidor (o del contenedor) que se consume, las colas crecen, y subir la máquina mejora el rendimiento (escalado vertical ayuda). Este patrón indica lógica pesada: cálculo, serialización, regex, cifrado o ineficiencias de algoritmo.

En el servidor, el diagnóstico empieza por medir y ver qué hilo consume:

# Uso de CPU en tiempo real. La columna %CPU alta de un proceso = CPU-bound
top -b -n 1 | head -20
#   PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
# 28401 root      20   0  482M  120M   42M R 100.0   0.6 812:07.12 node build.js

# Historial de carga del sistema (load average de 1/5/15 min)
uptime
#  14:02:11 up 12 days,  3:21,  2 users,  load average: 3.4, 2.9, 2.1

# VMSTAT: %us = usuario, %sy = sistema, wa = esperando I/O
vmstat 1 5
# procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
#  r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
#  5  0      0  81240  18000 220000    0    0   300   100  500  900 70 15 10  5  0

Regla rápida: r (processes en cola de JIT en vmstat) mayor que el número de núcleos es señal de cola de CPU; us alto = tu código; sy alto = syscalls/sistemas (context switches, red); wa alto = disco.

Cuello de botella: memoria

La memoria se agota de dos formas: pico (una petición que carga todo a RAM de golpe) y fuga (crecimiento lento hasta el swap o el OOM-kill). Síntomas: swap activo, procesos que empiezan a ralentizarse mientras el disco se llena de intercambio, y muertes súbitas por Out-Of-Memory.

# Uso de memoria por proceso y total
free -h
#               total        used        free      shared  buff/cache   available
# Mem:           16Gi       12.1Gi       774Mi       342Mi       3.1Gi       3.4Gi
# Swap:          2.0Gi       1.8Gi       220Mi     <-- swap lleno = problema real

# ¿Qué procesos comen más? RES = memoria residente en RAM
ps aux --sort=-%mem | head -8
# USER  PID %CPU %MEM VSZ  RSS COMMAND
# root 28401 100 62.1 32G 9.8G node src/server.js

Para fugas: perfila el heap (Node: --heap-prof; Python: tracemalloc) y dispara el mismo camino de código mil veces —una fuga se detecta porque la línea base de memoria no vuelve a bajar.

Cuello de botella: I/O de disco

El disco es decenas de miles de veces más lento que la RAM. Cuando wa (wait I/O) se dispara, hay un servicio escribiendo o leyendo de forma desmedida: logging excesivo, archivos temporales, o una base de datos sin índices que hace full-scans a disco (añade «tópico» con la lección de optimización de BD).

# Lectura/escritura por dispositivo y % de utilización
iostat -x 1 3
# Device            r/s     w/s     rMB/s     wMB/s   %util  await
# sda             125.0    45.0      8.2       2.3     98.0  25.4  <-- %util al límite

# ¿Qué proceso escribe? (respuesta casi siempre: tu logging o la BD)
lsof -Pt 2 | awk '$8>1000000 {print $1, $8}' | head

Cuando el disco es el límite, las optimizaciones de código no sirven: la respuesta es escribir menos (menos logs), leer menos (caché, índices) o mover datos a I/O asíncrono.

Cuello de botella: red y dependencias

A veces el más difícil de ver: el servicio responde bien localmente, pero en producción va lento. La latencia se va en la red —RTT al cliente, ancho de banda, DNS— o en una dependencia externa (una API de pagos, una cola remota) que no cumple su parte. Herramientas: curl -w (desglosa tiempos de red), traceroute, y, sobre todo, el trazado distribuido para saber a quién le estás esperando.

# Desglose de tiempos de una petición HTTP
curl -s -o /dev/null -w \
  "DNS: %{time_namelookup}s
   Conectar: %{time_connect}s
   TTFB: %{time_starttransfer}s
   Total: %{time_total}s
   Bytes: %{size_download}\n" \
  https://api.mi-servicio.com/usuarios/42

# Si TTFB - Conectar es grande -> el servidor tarda en responder (o su dependencia tarda)
# Si Conectar es grande -> problema de red al servidor, no del servidor

El consejo operativo: si el % de tiempo de red es dominante, más CPU local no arregla nada; se resuelve acercando el contenido (CDN, módulo 3) o pidiendo al proveedor externo que cumpla su SLO.

Orden de actuación

Diagnosticar antes de optimizar es media batalla. Secuencia recomendada cuando algo va lento:

  1. Reproduce con una pruebas de carga (ya sabes hacerlas).
  2. Mira CPU/memoria/I/O/red del servidor durante la prueba.
  3. Identifica el recurso saturado al 100% y queda atrapado hasta ahí.
  4. Ese recurso marca la solución: CPU → perfil y optimiza código; memoria → capa cache y streaming; disco → caché e índices; red → CDN y dependencias.

Ejercicio

  1. Corre vmstat 1 5 y top en una máquina con tu servicio desplegado durante una prueba de carga. Anota us, wa, r y el %MEM de tu proceso.
  2. Clasifica tu servicio en una de las cuatro categorías de cuello de botella con esos números.
  3. Responde: «¿es mejor invertir en más CPU, más RAM, un índice en la BD o una CDN?». Tu respuesta debe salir de los datos del punto 2.

Resumen

  • Cuatro cuellos de botella típicos: CPU, memoria, disco (I/O) y red/dependencias.
  • CPU alta con us alto → optimiza código; con wa alto → el disco es el siguiente.
  • Memoria: distingue pico de fuga; swap lleno es bandera roja inmediata.
  • Disco: logs, archivos temporales y full-scans de BD son los sospechosos principales.
  • Red/dependencias: el desglose de curl -w y el trazado distribuido te dicen a quién esperas.
  • Diagnostica el recurso saturado antes de elegir la solución: cada cuello tiene un remedio distinto.
