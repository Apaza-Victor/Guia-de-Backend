¿Qué es performance?

🚀 Avanzado 9 min Performance Backend Módulo 1 · Medir rendimiento

Introducción

Cuando alguien dice «la API está lenta» no está diciendo nada técnico todavía. ¿Lenta para quién? ¿Cuánto es lento? ¿Lentitud promedio o lentitud en el peor momento? El rendimiento de un backend solo existe en forma de números medibles: tiempo de respuesta, peticiones por segundo y distribución de esos tiempos.

Este primer módulo construye ese vocabulario. La meta es que nunca más hables de rendimiento con intuición, sino con tres métricas concretas: latencia, throughput y percentiles.

Latencia y throughput

Son las dos medidas que lo resumen todo:

  • Latencia: cuánto tarda una sola petición en completarse. Se mide en milisegundos (ms). Es lo que percibe un usuario individual.
  • Throughput: cuántas peticiones puede procesar el sistema por unidad de tiempo. Se mide en requests por segundo (RPS). Es lo que le importa al operador del sistema.

Son inversamente dependientes: si la red o el servidor están saturados, el throughput no puede crecer sin que la latencia se dispare. Y un sistema con latency baja pero throughput bajo decepciona cuando llega mucha gente. Necesitas ambas.

Ejemplo concreto: una API que responde en 80 ms a una petición pero solo aguanta 50 peticiones en simultáneo por nodo. El usuario individual está contento; con 5 000 usuarios simultáneos, las colas crecen y esa misma latencia pasa a 900 ms.

Percentiles: p50, p95, p99

El «promedio» es una mentira estadística para sistemas en producción. Con quince respuestas lentas entre millones, el promedio casi no se mueve, pero esos quince usuarios vivieron un desastre. Por eso se usan percentiles: el valor por debajo del cual cae un porcentaje de las observaciones.

  • p50 (mediana): la mitad de las peticiones completan en este tiempo o menos. Representa la experiencia típica.
  • p95: el 95% completa en este tiempo o menos. Solo el 5% es peor. Sensible a colas.
  • p99: el 99% completa en este tiempo o menos. Es el «peor 1%», lo que ven tus usuarios de peor suerte y el que mejor descubre colas y timeouts.

Calcular percentiles es trivial y no ocupa mucho CPU. Este ejemplo calcula p50, p95 y p99 desde una lista de latencias medidas en milisegundos:

import statistics

latencias_ms = [82, 84, 87, 90, 91, 95, 120, 340, 1050, 2500, 71, 76]

def percentil(datos, p):
    ordenado = sorted(datos)
    indice = max(0, int((p / 100) * len(ordenado)) - 1)
    return ordenado[indice]

print("p50:", percentil(latencias_ms, 50))
print("p95:", percentil(latencias_ms, 95))
print("p99:", percentil(latencias_ms, 99))
print("promedio:", round(statistics.mean(latencias_ms), 1))

# Salida típica:
# p50: 89.5
# p95: 2500
# p99: 2500
# promedio: 467.2

Observa la diferencia: el promedio (467 ms) parece terrible, pero la mitad de las peticiones respondió en 90 ms. Y el p99 de 2,5 s delata un problema real de colas o de una dependencia externa lenta que el promedio escondía.

Midiendo en el mundo real

Una forma rápida de medir latencia desde la terminal es disparar la misma petición muchas veces y extraer el percentil con awk:

# 100 peticiones, guardando solo el tiempo total (tiempo_total) de curl -w
for i in $(seq 1 100); do
  curl -s -o /dev/null -w "%{time_total}\n" https://api.mi-servicio.com/usuarios/42
done | sort -n | awk 'NR == 50 {print "p50:", $1 "s"}
                       NR == 95 {print "p95:", $1 "s"}
                       NR == 99 {print "p99:", $1 "s"}'

# Salida típica en un backend sano:
# p50: 0.082s
# p95: 0.131s
# p99: 0.540s

Y si quieres medir la latencia que aporta una función concreta dentro del código, el cronómetro de alta resolución de Node es tu amigo:

const { performance } = require('node:perf_hooks');

async function perfila(fn, etiqueta) {
  const inicio = performance.now();
  await fn();
  const ms = performance.now() - inicio;
  console.log(`${etiqueta}: ${ms.toFixed(2)} ms`);
  return ms;
}

// Uso:
await perfila(() => usuarioService.obtenerPerfil(42), 'obtenerPerfil');
await perfila(() => cache.set('perfil:42', perfil), 'set cache');

Guarda estos tiempos y agrega el percentil al final del día: así empieza un panel de rendimiento real.

El efecto cola

La causa número uno de p99 altos no es un algoritmo lento: es la cola. Si el servidor recibe más trabajo del que puede terminar, las peticiones esperan en fila mientras las anteriores se procesan. Cada petición extra que llega, espera más. Por eso la latencia crece más que proporcionalmente cuando el sistema se acerca a su límite.

Moraleja: monitoriza p95/p99 bajo carga, no solo en reposo. Una prueba en «modo pico» es la que revela dónde empieza a formarse la cola.

Ejercicio

  1. Elige tu endpoint más usado y mide 100 peticiones reales con el script de curl de arriba. Anota p50, p95 y p99.
  2. Calcula la diferencia entre p50 y p99: si es mayor de 4-5 veces, hay cola o una dependencia externa lenta de por medio.
  3. Escribe en una frase qué porcentaje de usuarios experimenta cada tiempo que mediste. Ejemplo: «el 95% responde en menos de 150 ms, pero el 1% más desafortunado espera casi un segundo».

Resumen

  • Performance se mide con latencia (tiempo por petición) y throughput (peticiones por segundo).
  • El promedio esconde problemas: usa p50, p95 y p99 para ver la experiencia típica y la del peor 1%.
  • El p99 alto casi siempre significa colas; se dispara antes de que el promedio mueva un milímetro.
  • Medir latencia desde curl o con perf_hooks es el primer paso hacia cualquier optimización seria.
