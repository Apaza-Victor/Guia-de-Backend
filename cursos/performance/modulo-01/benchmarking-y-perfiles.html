Benchmarking y perfiles

🚀 Avanzado 9 min Performance Backend Módulo 1 · Medir rendimiento

Introducción

La prueba de carga te dice qué está lento bajo demanda. El perfilado te dice dónde se va el tiempo. Un profiler observa el programa mientras corre y responde: «el 63% del tiempo de cada petición lo gasta join_productos()». Casi siempre, el resultado sorprende: no es donde imaginabas.

El benchmarking, por su lado, compara dos alternativas (versión A vs versión B, algoritmo X vs Y) de forma controlada para decidir con números en vez de corazonadas.

Perfilado en Python con cProfile

cProfile mide cuántas veces se llama cada función y cuánto tiempo consume (incluyendo todo lo que llama internamente). Ejecutar un script con el profiler es un cambio de una línea:

# Perfila los primeros 2000 requisitos de un informe de ventas
python -m cProfile -o perfil.prof generar_informe.py 2000

# Ordena el resultado por tiempo acumulado y muestra lo primero
python -m pstats -s cumtime perfil.prof

Los detalles del propio script de prueba importan más que la herramienta. El código debe ejercitar el camino que realmente importa —con datos realistas, no con dos filas—:

# generar_informe.py
import cProfile


def agregar_linea(resumen: list, venta: dict) -> None:
    linea = f"{venta['producto']}: {venta['total']:.2f} EUR | {venta['fecha']}"
    resumen.append(linea)  # list.append crece sin copiar toda la lista


def generar(cantidad: int) -> list:
    resumen = []
    for i in range(cantidad):
        venta = {"producto": f"sku-{i % 50}", "total": i * 1.1, "fecha": "2026-01-0" + str(i % 9)}
        agregar_linea(resumen, venta)
    return resumen


if __name__ == "__main__":
    cProfile.run("generar(2000)", sort="cumtime")

Con perfiladores gráficos (Python snakeviz, Node flamegraphs), el resultado se ve como llamas: cada barra es una función, la anchura es el tiempo en ella, y la altura, la profundidad de las llamadas.

Perfilado en Node.js

Node trae un profiler de CPU integrado: genera un archivo .cpuprofile que puedes abrir en Chrome DevTools o en herramientas de visualización:

# Ejecuta el servidor 20 segundos tomando muestras del stack 1000 veces/seg
node --cpu-prof --cpu-prof-dir=profiles --cpu-prof-interval=1000 src/servidor.js

# Abrir profiles/*.cpuprofile en Chrome DevTools:
# DevTools → Performance → cargar archivo (Load Profile)

Y midiendo una función puntual dentro del código, con alto-resolución:

const { performance } = require('node:perf_hooks');

const N = 100_000;
const datos = Array.from({ length: N }, (_, i) => ({ id: i, grupo: i % 100 }));

const inicio = performance.now();
const mapa = new Map();
for (const fila of datos) {
  if (!mapa.has(fila.grupo)) mapa.set(fila.grupo, []);
  mapa.get(fila.grupo).push(fila);
}
console.log(`Agrupar ${N} registros: ${(performance.now() - inicio).toFixed(2)} ms`);
// Importante: revisar si el coste es aceptable y compararlo con
// la alternativa (reduce, filtros anidados) antes de tocar nada.

Nota: las mejoras micro como esta casi nunca son la respuesta. El profiler primero te mostrará el 80% del tiempo en 2 o 3 funciones: ahí trabajas.

Flame graphs y el patrón del tiempo real

Un flame graph es la mejor balanza para decidir. En producciones reales, las sorpresas típicas son:

  • JSON.stringify de objetos enormes que se serializan en cada petición.
  • Regex sobre cadenas largas, sobre todo con backtracking cuadrático.
  • Copias de listas dentro de bucles (list[:], spread ..., slice).
  • Logging síncrono de alto volumen, que escribe a disco en el hilo principal.
  • Serialización en la capa de BD: toda la fila se convierte a objeto aunque solo se use una columna.

El 90% de los casos de rendimiento de producción terminan en esta lista corta. Perfilar es descartar rápido el 10% restante.

Benchmarking honesto

Benchmarkear es medir comparaciones, y las comparaciones se autoengañan con facilidad. Tres reglas de oro:

  1. Mide las dos versiones en el mismo proceso y máquina, alternando el orden (para no premiar siempre a la primera por la caché del sistema).
  2. Repite y reporta más que el promedio: mejor mediana y percentiles que media.
  3. Mide el escenario real, no el ideal. Si en producción hay 200 campos por objeto, tu benchmark no puede usar objetos de 2 campos.

Un loop de benchmark en JavaScript que evita el error de medir una sola ejecución:

const { performance } = require('node:perf_hooks');

function benchmark(fn, iteraciones = 1_000) {
  // Calentamiento: deja que JIT y cachés se estabilicen
  for (let i = 0; i < 100; i++) fn(i);
  const tiempos = [];
  for (let i = 0; i < iteraciones; i++) {
    const t0 = performance.now();
    fn(i);
    tiempos.push(performance.now() - t0);
  }
  tiempos.sort((a, b) => a - b);
  const mediana = tiempos[Math.floor(tiempos.length / 2)];
  const p95 = tiempos[Math.floor(tiempos.length * 0.95)];
  return { mediana_ms: mediana.toFixed(3), p95_ms: p95.toFixed(3) };
}

const generarIdClasico = (i) => "cli-" + i;
const generarIdPlantilla = (i) => `cli-${i}`;
console.log("clasico:  ", benchmark(generarIdClasico));
console.log("plantilla:", benchmark(generarIdPlantilla));
// Decidir con números, no con opiniones.

Ejercicio

  1. Elige la función más llamada de tu servicio (o el endpoint más usado).
  2. Perfílala en tu lenguaje: cProfile + snakeviz en Python, --cpu-prof en Node.
  3. Mira el flame graph y escribe las 3 funciones que más tiempo consumen. Si una de ellas no aparece en tu lista mental de sospechosos, estás ante el punto exacto que el profiler quería mostrarte.
  4. Compara dos alternativas de implementación con el loop de benchmark de arriba y decide con la mediana y el p95.

Resumen

  • El perfilado responde «dónde» se va el tiempo; la prueba de carga, «cuándo» se rompe.
  • cProfile ordena por tiempo acumulado; Node exporta .cpuprofile que DevTools visualiza.
  • Los flame graphs agrupan el tiempo por pila de llamadas: busca las barras anchas.
  • El 90% de los casos reales: serialización, regex, copias en bucles, logging síncrono y mapeos innecesarios.
  • El benchmark honesto usa calentamiento, mediana y p95, y escenario realista.
