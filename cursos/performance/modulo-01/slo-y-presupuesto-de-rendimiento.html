SLO y presupuesto de rendimiento

🚀 Avanzado 8 min Performance Backend Módulo 1 · Medir rendimiento

Introducción

«Queremos que el sistema vaya rápido» no es un objetivo. Un objetivo tiene número, ventana de tiempo y porcentaje de tolerancia. Un SLO (Service Level Objective) es exactamente eso: la promesa escrita y medible de cuánto tiempo puede tardar tu servicio, y con qué frecuencia puede fallar, sin que lo consideres un incidente.

El presupuesto de rendimiento es la cara práctica: si una petición de usuario no puede tardar más de 500 ms de principio a fin, ese tiempo se reparte como un presupuesto entre los servicios involucrados —app, base de datos, caché, dependencia externa— y cada equipo sabe cuántos milisegundos le corresponden.

SLI, SLO y SLA

Tres siglas que conviene no mezclar:

  • SLI (indicador): la métrica que mides de verdad. Ejemplo: «p95 de latencia del endpoint de login en milisegundos» o «porcentaje de peticiones con error HTTP 5xx».
  • SLO (objetivo): el umbral que decides. Ejemplo: «el p95 de login será menor a 300 ms y tendremos al menos el 99.5% de peticiones sin errores, medido en ventanas mensuales».
  • SLA (acuerdo): el contrato comercial que se firma con un cliente y normalmente promete menos que el SLO para tener margen. El SLA se escribe en contratos; el SLO se escribe en dashboards.

Regla práctica: SLO interno = SLA externo × holgura. Si vendes un SLA de 99.9%, persigue un SLO interno de 99.95%. Lo que no mides con SLIs no lo puedes prometer con SLOs.

Definiendo un SLO de rendimiento

Una definición útil deja explícitas cuatro cosas: el SLI, el umbral, la ventana y el margen de error. Aquí tienes un ejemplo configurable en JSON, listo para guardarse junto al código o en un sistema de alarmas:

{
  "servicio": "api-usuarios",
  "slo_latencia": {
    "nivel": "p95",
    "max_ms": 300,
    "ventana": "30 dias",
    "tolerancia_fallas": "0.2%"
  },
  "slo_disponibilidad": {
    "slis": ["proporcion_respuestas_exitosas", "proporcion_5xx"],
    "minimo": 0.995,
    "ventana": "30 dias"
  },
  "presupuesto_total_peticion": {
    "max_ms": 500,
    "desglose": {
      "api_gateway": 50,
      "servicio_usuarios": 100,
      "base_de_datos": 80,
      "capa_cache": 20,
      "servicio_externo_pago": 250
    }
  }
}

El desglose del presupuesto es oro para el equipo: si el servicio_externo_pago se pasa de sus 250 ms, sabes dónde buscar antes de correr detrás de tu propio código.

Presupuesto de rendimiento y capacity planning

El presupuesto guía dos trabajos: las optimizaciones de código (no necesito un p95 de 80 ms para la pantalla de inicio, y si lo tengo, tengo margen para dedicar algo de presupuesto a una feature nueva) y el capacity planning (cuánta máquina necesito cuando el tráfico estimado pase de X RPS).

Capacity planning en una línea: estima el tráfico pico esperado, multiplica por los recursos que consume cada petición y añade un colchón. Un cálculo simplificado:

# Estimación de nodos necesarios para soportar el pico
trafico_pico_rps = 2000          # 2000 peticiones/segundo en hora punta
rps_por_nodo = 250               # medido con prueba de carga
colchon = 1.6                    # +60% de margen para reinicios y picos imprevistos
tiempo_reserva_ms = 0.0006       # 600 microsegundos de CPU por petición

nodos = (trafico_pico_rps / rps_por_nodo) * colchon
print(f"Nodos necesarios: {math_ceil(nodos)} (redondeado)")

# Si una feature nueva duplica la CPU por petición -> nodos = (2000 / 250) * 1.6 * 2
# Comparar con el presupuesto: si no cabe, la feature paga con optimizaciones.

La magia no está en la fórmula, sino en que alguien la repite tras cada release. El capacity planning es un proceso periódico, no un cálculo único.

Alarmando contra el presupuesto

Un SLO sin alarma es un deseo. El patrón más usado es calcular el error budget disponible y disparar cuando se está gastando demasiado rápido:

# Consulta de ejemplo con PromQL: minutos de error budget consumidos por latencia p95
# El SLO es: p95 < 300ms el 99.8% de las veces en 30 dias.

# Presupuesto total permitido: 30 * 1440 * 0.002 = 86.4 minutos
# Minutos actuales sobre umbral (simplificado con un contador de eventos):
sum(rate(http_p95_over_budget_events_total[1h])) * (30 * 1440 / 30) < 86.4

# Alerta lanzada cuando el gasto anualizado de error budget supera lo disponible

No importa la herramienta: la idea es que el presupuesto agote un «banco de fallos» por mes. Cuando el banco se vacía, el equipo deja de hacer features nuevas y arregla la causa. Así el rendimiento deja de ser una opinión y pasa a ser un contrato con uno mismo.

Ejercicio

  1. Elige el flujo crítico de tu producto (por ejemplo, «login» o «checkout») y escribe el SLO de latencia en el formato JSON de arriba: SLI, p95 máximo, ventana y tolerancia.
  2. Fija su presupuesto total (¿cuánto puede tardar de punta a punta?) y reparte el presupuesto entre los servicios intervinientes.
  3. Estima cuántos nodos necesitarías para tu tráfico pico actual con el script de capacity planning y compáralo con lo que ya tienes desplegado.

Resumen

  • Un SLO es un objetivo medible: valor + ventana + porcentaje de tolerancia.
  • Se compone de SLIs (las métricas) y deja holgura frente al SLA comercial.
  • El presupuesto de rendimiento reparte los milisegundos del flujo completo entre servicios.
  • El capacity planning usa el presupuesto y el tráfico estimado para decidir cuánta máquina hace falta.
  • Las alertas gastan un error budget mensual; vaciarlo significa parar de escribir features y arreglar.
