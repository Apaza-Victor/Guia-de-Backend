Pruebas de carga

🚀 Avanzado 10 min Performance Backend Módulo 1 · Medir rendimiento

Introducción

Una prueba de carga simula tráfico real contra tu sistema para responder una pregunta concreta: ¿cumple mi SLO cuando llegan 200, 500 o 2 000 usuarios simultáneos? El punto de partida es siempre el mismo del módulo: tienes un presupuesto de rendimiento y ahora lo pones a prueba.

Existen tres herramientas rey. k6 (scriptable en JavaScript, moderno e integrable en CI), Locust (scripts en Python, muy buen modelo de usuarios concurrentes) y JMeter (histórico, con interfaz gráfica). Elegir una importa menos que entender los escenarios; aquí verás los tres.

Tipos de escenario

Cada prueba responde a un objetivo distinto:

  • Prueba de carga normal: mantener el tráfico esperado durante un tiempo (p. ej. 200 RPS durante 15 min) y confirmar que la latencia se mantiene dentro del SLO.
  • Prueba de estrés: subir la carga poco a poco hasta que el sistema empiece a degradarse. Descubre el límite y cómo falla (gracioso o catastrófico).
  • Prueba de pico (spike): disparar el tráfico de golpe, muy alto, y ver cómo reacciona ante la súbita demanda. Típica para ventas, lanzamientos o eventos.
  • Prueba de resistencia (soak): carga estable durante horas o días para encontrar fugas de memoria y degradación lenta.

Regla práctica: corre la prueba contra un entorno que se parezca a producción (misma base de datos, misma caché, misma red). Probar contra tu laptop homologa una isla, no tu servicio.

Prueba de carga con k6

k6 define escenarios en un script JavaScript con etapas de carga. Aquí, un spike que sube a 300 usuarios virtuales en 30 segundos:

import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 50 },    // rampa de subida
    { duration: '30s', target: 300 },   // pico: 300 usuarios virtuales
    { duration: '30s', target: 0 }      // rampa de bajada
  ],
  thresholds: {
    'http_req_duration{expected_response:true}': ['p(95)<300'],
    'http_req_failed': ['rate<0.01']
  }
};

export default function () {
  const res = http.get('https://api.mi-servicio.com/productos/lista?cat=juguetes');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1); // 1 segundo de «pensamiento» entre peticiones por usuario
}

Ejecutarla es un comando, y la salida te da directo los percentiles que definiste como SLO:

k6 run spike.js

# Fragmento de resultado esperado:
#     http_req_duration........: avg=122ms  min=38ms  med=98ms  max=940ms
#       { expected_response:true }........: p(90)=180ms p(95)=255ms p(99)=610ms
#     http_req_failed...........: 0.32%  ✓ ✓ ✗ (el 0.32% falló)
#     iter_duration.............: avg=1.13s  min=1.04s  max=1.95s

# thresholds:
#   p(95)<300 -- p(95)=255ms: ✓   (cumple el presupuesto)
#   rate<0.01 -- 0.32%:      ✗   (el 0.32% de errores rompe el umbral del 1%)

Observa el poder de los thresholds: k6 falla la ejecución en CI si el p95 o la tasa de errores superan lo pactado. El SLO se vuelve código.

Prueba de carga con Locust

Locust define al usuario como una clase Python con pesos que simulan proporción de tráfico entre endpoints:

from locust import HttpUser, task, between

class UsuarioTienda(HttpUser):
    wait_time = between(1, 3)  # el usuario «piensa» entre 1 y 3 segundos

    @task(4)  # 4 de cada 5 peticiones consultan catálogo
    def ver_catalogo(self):
        self.client.get("/productos/lista?cat=juguetes")

    @task(1)  # 1 de cada 5 hace checkout completo
    def comprar(self):
        with self.client.post("/carrito/comprar", json={"producto": 42}, catch_response=True) as r:
            if r.status_code != 201:
                r.failure("checkout fallo con status " + str(r.status_code))

# Ejecución desde el CLI:
# locust -f usuario_tienda.py --host https://api.mi-servicio.com \
#   --users 500 --spawn-rate 20 --run-time 10m

El 80/20 entre catálogo y checkout reproduce el patrón de tráfico real mucho mejor que disparar el mismo endpoint a todas partes.

Cómo leer los resultados

Tres lecturas, en este orden obligatorio:

  1. ¿Cumple el SLO bajo esa carga? Si no, el problema no es la prueba: es el sistema. Deja de probar y empieza a perfilar.
  2. ¿Dónde empieza a degradarse? Normalmente la latencia del p99 se dispara antes que la del p50: es la señal de cola.
  3. ¿Qué recurso se satura primero? La prueba de carga debe ir acompañada del monitoreo del servidor (CPU, memoria, I/O, conexiones a la BD). Sin el monitoreo, el resultado de k6 es solo un dato suelto.

Ejercicio

  1. Toma el script de k6 de arriba y ajusta los stages a un escenario «normal» (por ejemplo 50 usuarios constantes durante 5 minutos).
  2. Corre el spike contra tu propio endpoint y anota en qué stage p(95) dejó de cumplir tu SLO.
  3. Repite con el monitoreo del servidor abierto: ¿qué recurso (CPU, memoria, BD, red) se saturó primero? Ese es tu cuello de botella.

Resumen

  • Las pruebas de carga piden una pregunta concreta: ¿cumplo mi SLO bajo N usuarios?
  • Los escenarios base son: carga normal, estrés, pico y resistencia. Cada uno responde algo distinto.
  • k6 (JS), Locust (Python) y JMeter (GUI) son las tres herramientas canónicas; k6 integra thresholds en CI.
  • Una prueba de carga sin monitoreo del servidor es un dato a medio leer.
  • Si el SLO se rompe bajo carga, deja de probar y empieza a perfilar (siguiente lección).
