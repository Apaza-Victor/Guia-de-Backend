Optimizar I/O

🚀 Avanzado 8 min Performance Backend Módulo 2 · Optimización

Introducción

Toda la trasferencia de datos que no es memoria es I/O: leer un archivo del disco, escribir un log, subir un CSV, servir una descarga. El I/O es órdenes de magnitud más lento que el cálculo —una lectura de disco es ~100 000 veces más lenta que un acceso a RAM—. Cuando el I/O se hace mal, ni el CPU ni la RAM sirven de nada: el proceso pasa horas esperando a que lleguen los datos.

Tres herramientas ordenadas: asíncrono (no bloquear), buffering (leer/escribir en bloques) y streaming (no cargar todo en memoria).

I/O síncrono frente a asíncrono

La lectura síncrona bloquea el hilo: nada más corre hasta que el archivo termine de leerse. En un solo script de consola, da igual; dentro de un servidor con 1 000 peticiones vivas, cada lectura síncrona congela todas las demás (vista en la lección de concurrencia). La versión asíncrona delega y deja el hilo libre.

const fs = require('node:fs');
const { readFile } = require('node:fs/promises');

// MAL dentro de un servidor: bloquea el event loop para TODO el mundo
app.get('/backup/datos', (req, res) => {
  const contenido = fs.readFileSync('/app/datos/export.json', 'utf8');
  res.send(contenido); // ~50 ms aquí = ~50 ms de parón global bajo carga
});

// BIEN: asíncrono, el event loop sigue atendiendo a los demás
app.get('/backup/datos', async (req, res) => {
  const contenido = await readFile('/app/datos/export.json', 'utf8');
  res.send(contenido);
});

La regla: jamás I/O síncrono en el camino crítico de una petición (a menos que el archivo sea diminuto y arranques así el servidor). En Python pasa exactamente igual: open().read() en un handler FastAPI bloquea ese hilo, mientras aiofiles o asyncio.to_thread lo evita.

Buffering: leer y escribir en bloques

Leer de uno en uno pero en 1 byte es la forma más lenta de tocar un disco. Cada lectura tiene un coste de sistema (syscall) y de posicionamiento del cabezal en disco. La solución se llama buffering: leer/escribir en bloques grandes y dejar que el sistema acumule datos.

# Lento: 1 byte -> 1 syscall. Un archivo de 10 MB = 10 millones de syscalls
with open("export.csv", "r") as f:
    datos = ""
    while True:
        byte = f.read(1)
        if not byte:
            break
        datos += byte

# Rápido: buffer de 64 KB desde el principio
with open("export.csv", "r", buffering=65536) as f:
    lineas = []           # lee en bloques de 64 KB, mucho menos I/O al sistema
    for linea in f:       # la iteración por líneas ya usa el buffer
        lineas.append(linea)

# El modo binario + lectura por trozos es igual de efectivo para archivos pesados:
with open("export.csv", "rb") as f:
    while chunk := f.read(65536):   # 64 KB por llamada
        procesar(chunk)

En la terminal, la misma idea la ajustas con dd: el tamaño de bloque (bs) decide cuántos syscalls tardas en copiar un archivo. Un bs=64K copia cientos de veces más rápido que un bs=1.

# Compara los tiempos (time) con bs=1 vs bs=64K:
#   dd if=export.csv of=/tmp/copia bs=1 count=100000
#   dd if=export.csv of=/tmp/copia bs=64K count=10

# El bloqueo de E/S de red también se tunea:
#   sysctl -w net.core.rmem_max=134217728   # ~128 MB para buffers de red

Streaming: sin cargar todo en memoria

Cargar un archivo de 2 GB en memoria para luego enviarlo por HTTP es el camino a un OOM-kill. El streaming lee un trozo, lo envía, lee el siguiente: la memoria se queda plana aunque el archivo sea enorme. Node lo expresa elegantemente encadenando streams.

const fs = require('node:fs');
const { pipeline } = require('node:stream/promises');

// MAL: readFile entero + string en memoria. Un 2 GB -> 2 GB en RAM.
app.get('/descargar/video', async (req, res) => {
  const b = await readFile('/media/video.mp4');
  res.send(b);
});

// BIEN: stream pipe, memoria constante (~64 KB por vuelta)
app.get('/descargar/video', (req, res) => {
  const fuente = fs.createReadStream('/media/video.mp4');   // no lee todo
  pipeline(fuente, res);                                    // disco -> red, en trozos
});

El equivalente en Python/FastAPI se resuelve con FileResponse, que internamente hace streaming del archivo sin colgarlo en RAM:

from fastapi import FastAPI
from starlette.responses import FileResponse

app = FastAPI()

@app.get("/descargar/video")
def descargar():
    # Servido en trozos; la memoria del proceso no depende del tamaño del archivo
    return FileResponse("/media/video.mp4", filename="video.mp4")

El streaming también vale para procesos: un CSV de 10 millones de filas puede ir filtrándose línea a línea sin que dataframes ni listas exploten la memoria. Y del lado del protocolo, las respuestas HTTP con Transfer-Encoding: chunked envían los trozos a medida que se producen — la base de los SSE que ve en el curso de IA.

El I/O escondido: el logging

El error de I/O más común que no parece I/O es el logging síncrono de alto volumen: cada línea de log es una escritura al disco (o peor, un round-trip a stdout). En producción con console.log en un bucle, ese log se convierte en el cuello de botella número uno.

Receta mínima:

  • Loguear en nivel INFO como máximo en producción; DEBUG fuera de los caminos calientes.
  • Si necesitas volumen, envía los logs a stderr/colas y que un proceso externo (o la infraestructura) los recoja; nunca bloquees la petición esperando el write.
  • Redúcelo a resumen: «en vez de duplicar 50 eventos, loguea un agregado».
// Necesario (el log tiene un coste real)
if (evento.importante) log.info({ usuario: evento.clienteId }, "compra confirmada");

// Innecesario bajo carga masiva: 1 syscall por línea, en producción, multiplicado por 1000
// log.debug({ cada_entrada: listaCompleta }); // deja DEBUG aislado de prod

Ejercicio

  1. Busca en tu código cualquier readFileSync, read() bloqueante o open().read() en el camino de peticiones y conviérte a la versión asíncrona o a FileResponse/stream.
  2. Encuentra la carga o descarga de archivos más pesada de tu sistema y reescríbela con streaming; vigila la memoria del proceso antes y después (no debe subir con el tamaño del archivo).
  3. Mide tus console.log en la prueba de carga: coméntalos temporalmente y compara el throughput. Si sube, tienes tu siguiente optimización.

Resumen

  • El I/O es el recurso más lento del sistema: nunca lo bloquees en el hilo de una petición.
  • I/O asíncrono (fs/promises, aiofiles, asyncio.to_thread) mantiene el hilo libre.
  • El buffering (bloques de 64 KB) reduce las syscalls y acelera cualquier traslado de datos.
  • El streaming (createReadStream, FileResponse) mantiene la memoria plana con archivos enormes.
  • El logging síncrono es I/O escondido: nivela y delega; nunca escribas por petición.
  • Todo esto se demuestra con la prueba de carga y la observación del disco (iostat) de antes y después.
