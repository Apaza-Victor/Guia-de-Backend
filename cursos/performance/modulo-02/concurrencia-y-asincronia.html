Concurrencia y asincronía

🚀 Avanzado 9 min Performance Backend Módulo 2 · Optimización

Introducción

«Hacer las cosas a la vez» no significa hacerlas más rápido: significa no quedarse ocioso mientras algo lento esté sucediendo. En el backend, casi todo el tiempo que pasa una petición se va esperando —la base de datos, la red, un archivo—. El arte de la concurrencia es aprovechar esas esperas.

Hay dos modelos mentales: la asincronía (un solo hilo que no se bloquea y atiende mil conexiones mientras espera) y el multihilo (varios hilos/CPU ejecutando en paralelo de verdad). La palabra clave para decidir es I/O-bound frente a CPU-bound.

El event loop de Node.js

Node procesa todo en un solo hilo con un bucle de eventos: cuando encuentra una operación lenta de I/O (BD, red, disco), la delega y sigue atendiendo a otra petición. Por eso un Node estándar maneja miles de conexiones concurrentes sin variables compartidas que se pisen… mientras el hilo no se bloquee con trabajo pesado de CPU.

Observa la diferencia entre bloquear el hilo y no hacerlo:

// MAL: bloquea el event loop. Mientras tarda, NADIE más se atiende.
const crypto = require('node:crypto');
app.get('/hash-sincrono', (req, res) => {
  const hash = crypto.createHash('sha256').update(JSON.stringify(compras)).digest();
  // Durante estos ~200 ms con datos grandes, la API entera deja de responder
  res.json({ hash });
});

// BIEN: delega el trabajo a worker threads y mantiene el hilo libre
const { Worker } = require('node:worker_threads');
app.get('/hash-asincrono', (req, res) => {
  const worker = new Worker('./worker_hash.js', { workerData: compras });
  worker.once('message', (hash) => res.json({ hash }));
});

// El event loop sigue atendiendo peticiones mientras el worker calcula.
// Regla: todo lo que sea esperar se hace async; solo el cálculo real se
// externaliza a workers/clusters porque consume CPU de un solo hilo.

Un detector rápido: si una petición que debería tardar 30 ms tarda 300 ms solo bajo carga, sospecha de un bloqueo del event loop en otro endpoint. La lección de profiling ya te mostró cómo encontrarlo con flame graphs.

Python: asyncio para I/O, hilos para CPU

Python tiene el mismo dilema con distinto vocabulario. asyncio ejecuta un solo hilo cooperativo: las corutinas ceden al hacer I/O. Para trabajo que usa CPU de verdad, asyncio no acelera nada (el GIL limita la CPU por proceso); ahí entran ThreadPoolExecutor o procesos con ProcessPoolExecutor.

import asyncio
import aiohttp

# I/O-bound: lanzar 50 peticiones HTTP en paralelo en un solo hilo
async def descargar(session, url: str) -> bytes:
    async with session.get(url) as r:
        return await r.read()

async def descargar_todas(urls: list[str]) -> list[bytes]:
    async with aiohttp.ClientSession() as session:
        return await asyncio.gather(*(descargar(session, u) for u in urls))

# Uso: 50 peticiones HTTP en ~el tiempo de UNA, en un solo hilo
# resultados = asyncio.run(descargar_todas([f"https://api.o/feed/{i}" for i in range(50)]))

Y el caso CPU-bound, donde los hilos sí reparten entre núcleos:

from concurrent.futures import ThreadPoolExecutor
import hashlib

def calcular_reportes(datos: list[dict]) -> list[str]:
    resumen = []
    for venta in datos:
        resumen.append(hashlib.sha256(str(venta).encode()).hexdigest())
    return resumen

# Un worker pool de 8 hilos reparte el cálculo entre los CPU disponibles
with ThreadPoolExecutor(max_workers=8) as pool:
    trozos = [datos[i::8] for i in range(8)]                # reparte la carga
    resultados = list(pool.map(calcular_reportes, trozos))

# En Flask/FastAPI: las peticiones CPU-pesadas así no bloquean a las demás.

Regla resumen: I/O → async (un solo hilo basta). Cálculo → hilos/procesos. Mezclar mal es la causa de «parecía más rápido, pero ahora todo se bloquea».

Los límites físicos

La concurrencia no es gratis ni es infinita:

  • El hilo tiene memoria y contexto: miles de hilos pesan mucho más en RAM que miles de corutinas (una corutina ~KBs; un hilo ~MBs de stack).
  • El CPU tiene un tope físico: un proceso CPU-bound no mejora con más hilos que núcleos disponibles. 16 hilos en 4 núcleos = 16 hilos peleando por 4 CPUs.
  • Los recursos externos también tienen tope: si la BD está al límite, 200 conexiones concurrentes no hacen nada salvo empeorar la cola (pool_max de la lección de BD).

En la práctica: para I/O, siempre asíncrono; para CPU, como mucho núcleos workers; y nunca trates de «acelerar» una capa externa saturada con más concurrencia local.

Backpressure: una idea imprescindible

Si el productor de peticiones entra más rápido de lo que el sistema consume, no hay modelo de concurrencia que lo salve: las colas crecen y la latencia se dispara (el efecto cola del módulo 1). El backpressure es el mecanismo para frenar la entrada cuando no se puede seguir el ritmo: límites de tareas en cola, rechazos con 429 o 503 (sobrecarga), y workers que solo piden más trabajo cuando terminan uno.

# nginx: límite de peticiones concurrentes con respuesta educada
http {
  limit_req_zone $binary_remote_addr zone=api:10m rate=50r/s;
  server {
    location /api/ {
      limit_req zone=api burst=100 nodelay;
      # Cuando se supera la tasa, nginx responde 503 y protege el backend
      proxy_pass http://app_backend;
    }
  }
}
# límite de conexiones simultáneas a la app:
# limit_conn_zone $binary_remote_addr zone=conn:10m;
# limit_conn conn 20;

Proteger la entrada con límites es optimización de rendimiento, no un capricho: los límites evitan los dos colapsos clásicos, el efecto dominó y el apagón total. El mismo principio aplica con respuestas 429 (demasiadas peticiones) o 503 (servicio temporalmente sobrecargado) cuando la entrada supera lo que el sistema puede digerir.

Ejercicio

  1. Clasifica las operaciones de tu servicio en I/O-bound o CPU-bound (consulta, archivo, correo → I/O; hashes, reportes, transformaciones pesadas → CPU).
  2. Busca en tu código cualquier operación lenta que se ejecute de forma bloqueante en el hilo principal (lectura de archivo síncrona, hash grande, JSON.parse de megas) y haz una async/worker equivalente.
  3. Mide antes/después con tu prueba de carga: la latencia p95 bajo carga fue el indicador que dolió antes y que ahora debería mejorar.
  4. Revisa si tienes backpressure (límites de tasa o de cola) frente al backend; si no, plantéalo con la configuración de nginx de arriba.

Resumen

  • Asincronía = un hilo no bloqueado que aprovecha las esperas de I/O.
  • Node: el event loop atiende miles de conexiones, pero cualquier trabajo CPU pesado lo bloquea.
  • Python: asyncio para I/O, hilos/procesos para CPU.
  • No más hilos que núcleos para CPU ni más conexiones de las que la BD soporta: cada recurso tiene tope.
  • El backpressure limita la entrada (503/429) y evita que las colas destruyan la latencia.
  • Mide siempre antes/después: la concurrencia «bien» se demuestra con datos, no con sensaciones.
