Optimizar APIs

🚀 Avanzado 9 min Performance Backend Módulo 2 · Optimización

Introducción

La API que sirves es donde el usuario siente el rendimiento. Hay una mala noticia: devolver una lista de 10 000 productos con sus 200 campos en cada respuesta ni es útil ni es rápido; y una buena noticia: los arreglos son mecánicos y medibles. Esta lección aplica tres palancas: menos datos (paginación y payload mínimo), menos llamadas (batch) y menos bytes en la red (compresión).

Paginación con cursores

Devolver todo de golpe es el anti-patrón de rendimiento: la lista crece, la memoria de cada nodo se va con ella, la BD escanea más y el cliente espera más para nada. La paginación por cursor (parámetro que indica el último elemento visto) escala mejor que page/limit basado en offset, porque el offset obliga a la BD a contar y descartar filas antes de la página.

La respuesta típica de lista paginada y cómo encadenarla:

{
  "data": [
    { "id": 101, "nombre": "Balón de fútbol", "precio": 12.5 },
    { "id": 102, "nombre": "Camiseta local", "precio": 25.0 }
  ],
  "paginacion": {
    "limite": 50,
    "proximo_cursor": "eyJpZCI6MTAyfQ==",
    "anterior_cursor": null
  },
  "total_estimado": 3200
}

El cursor suele ser el id de la última fila (base64 → id + filtros). La clave: es una consulta «mayor que el cursor, ordenado por id, limit N» que usa el índice de orden y no se degrada con la página 100.

app.get('/productos', async (req, res) => {
  const { cursor, limite = 50 } = req.query;

  // Decodificar: el cursor guarda el último id visto + los filtros activos
  const ultimoId = cursor ? JSON.parse(Buffer.from(cursor, 'base64')).id : 0;

  // Consulta con "mayor que" en vez de OFFSET: usa el índice de id
  const filas = await db.query(
    `SELECT id, nombre, precio FROM productos
     WHERE id > $1 AND activo = true
     ORDER BY id
     LIMIT $2`,
    [ultimoId, limite]
  );

  const siguiente = filas.length === limite
    ? Buffer.from(JSON.stringify({ id: filas.at(-1).id })).toString('base64')
    : null;

  res.json({ data: filas, paginacion: { limite, proximo_cursor: siguiente } });
});

Devolver solo lo necesario

Cuánto más ancho es cada JSON, más lento es todo: más CPU en serialización, más bytes de red, más milisegundos de TTFB. Dos técnicas baratas:

  • SELECT solo las columnas que la respuesta usa: «SELECT *» es el germen de payloads de megas.
  • Filtrar campos en la serialización (proyección): ignora activo, roles, notas_internas, etc. del JSON de salida.

Ejemplo de recorte con proyección explícita en Node:

// En vez de devolver el objeto completo al cliente...
const usuarioCompleto = await db.query(
  'SELECT * FROM usuarios WHERE id = $1', [req.params.id]
);

// ...devuelve solo la proyección pública, sin notas internas ni hash
function proyeccionPublica(u) {
  return {
    id: u.id,
    nombre: u.nombre,
    email: u.email,
    avatar_url: u.avatar_url
  };
}

app.get('/usuarios/:id/datos-publicos', async (req, res) => {
  const u = await db.query('SELECT id, nombre, email, avatar_url FROM usuarios WHERE id = $1', [req.params.id]);
  res.json({ datos: proyeccionPublica(u) });
});

Mismo patrón del lado cliente (fields=nombre,precio) si tus clientes tienen necesidades variadas. Menos datos = menos latencia, sin tocar nada más del sistema.

Operaciones por lotes

Si el cliente necesita información de 20 recursos distintos, obligarle a hacer 20 peticiones multiplica por 20 el tiempo de ida y vuelta (RTT), el handshake y el trabajo. La API por lotes recibe una lista y devuelve las respuestas en un solo round-trip:

# En vez de 20 peticiones HTTP, una petición batch con N ids
curl -X POST https://api.mi-servicio.com/productos/importar/consultar \
  -H "Content-Type: application/json" \
  -d '{"ids": [1001, 1002, 1003, 1004]}'

# Respuesta: un objeto clave->producto, un solo round-trip
# {
#   "1001": { "id": 1001, "nombre": "Balón" },
#   "1002": { "id": 1002, "nombre": "Camiseta" }
# }

En el backend, una consulta WHERE id IN (...) resuelve el lote entero (verifica el tamaño máximo, típico 100, para no abusar):

from fastapi import FastAPI, HTTPException

app = FastAPI()

MAX_LOTE = 100

@app.post("/productos/lote")
def producto_por_lote(ids: list[int]):
    if len(ids) > MAX_LOTE:
        raise HTTPException(status_code=413, detail="Lote maximo 100 ids")

    # Un solo query para todos los ids
    filas = repositorio.buscar_por_ids(ids)   # WHERE id IN (...)
    return {fila.id: fila.model_dump() for fila in filas}

El resultado: el caso «pedir 20 recursos» pasa de ~20 RTTs a 1. En una red con 50 ms de RTT, son 1000 ms ahorrados de golpe.

Compresión gzip y brotli

El JSON es muy comprimible: los textos repiten claves y valores. Comprimiendo con gzip o brotli, un payload de 200 KB pasa a 20-30 KB. El coste es CPU para comprimir/descomprimir (pequeño) y el beneficio es ancho de banda y TTFB. Siempre que el cliente lo anuncie con Accept-Encoding.

Para probarlo a mano, la diferencia se ve al instante:

# Sin compresión
curl -s -H "Accept-Encoding: identity" -o /dev/null -w "tamano: %{size_download}B tiempo: %{time_total}s\n" \
  https://api.mi-servicio.com/productos/lista

# Con gzip
curl -s -H "Accept-Encoding: gzip" -o /dev/null -w "tamano: %{size_download}B tiempo: %{time_total}s\n" \
  https://api.mi-servicio.com/productos/lista

# Con brotli (mejor ratio para texto)
curl -s -H "Accept-Encoding: br" -o /dev/null -w "tamano: %{size_download}B tiempo: %{time_total}s\n" \
  https://api.mi-servicio.com/productos/lista

En Express, activar la compresión es instalar y configurar (el nivel 6 de gzip o brotli se negocia por Accept-Encoding):

const express = require('express');
const compression = require('compression');

const app = express();
app.use(compression()); // comprime JSON/HTML > ~1 KB según Accept-Encoding

// brotli se activa igual con el middleware correspondiente:
// app.use(compression({ brotli: { enabled: true, quality: 4 } }));
app.get('/productos/lista', async (req, res) => { /* ... */ });

Una pausa importante: la compresión no sustituye a la proyección. Comprimir 2 MB sigue enviando una respuesta pesada que el cliente descomprime; la combinación ganadora es menos datos y comprimidos.

Ejercicio

  1. Audita tu endpoint de listas más usado: ¿devuelve todo el objeto? ¿tiene paginación por offset? Aplícale la paginación por cursor y la proyección mínima.
  2. Mide el payload de tu mayor endpoint con los tres Accept-Encoding de arriba y anota la reducción en bytes y en tiempo.
  3. Identifica un caso donde el cliente hace N peticiones para una pantalla; sustitúyelo por un endpoint batch y mide el tiempo total antes y después.

Resumen

  • Paginación por cursor: «id > cursor» en vez de OFFSET; no se degrada con la página.
  • Payload mínimo: SELECT solo las columnas usadas y proyecta el JSON de salida.
  • Batch: una petición por lote (IN ...) sustituye a N round-trips.
  • gzip/brotli recortan el ancho de banda y el TTFB; negocia por Accept-Encoding.
  • Menos datos + compresión ganan juntos; la compresión no perdona los payloads hinchados.
  • Todas son mejoras medibles con curl -w o tu prueba de carga.
