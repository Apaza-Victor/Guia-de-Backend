Caching y estrategias

🚀 Avanzado 10 min Performance Backend Módulo 2 · Optimización

Introducción

El caché es el arma de rendimiento más efectiva porque ataca al problema de raíz: la mayoría de las peticiones piden los mismos datos que otra persona acaba de pedir. Si esos datos —catálogo, perfiles, precios— se sirven desde una capa rápida sin volver a calcularlos ni leer la base de datos, la latencia cae de decenas de milisegundos a microsegundos y la carga sobre la BD se desploma.

Pero el caché también es la fuente número uno de bugs sutiles: contenido obsoleto servido sin dolor hasta que alguien lo nota. Por eso esta lección dedica la mitad a las estrategias y a la invalidación.

Cache-aside (lazy caching)

El patrón más usado: la aplicación consulta el caché primero; si hay un miss (no está), lee la fuente de verdad, la guarda en caché con TTL y responde. En el siguiente hit, sale directo de caché.

Con Redis y Node, el flujo es directo:

import { createClient } from 'redis';

const redis = createClient({ url: 'redis://cache:6379' });

async function obtenerProducto(id) {
  const clave = `producto:${id}`;

  // 1. Intentar por el caché
  const cacheado = await redis.get(clave);
  if (cacheado) return JSON.parse(cacheado);   // hit: cero lectura a la BD

  // 2. Miss: leer la fuente de verdad
  const producto = await db.query(
    'SELECT * FROM productos WHERE id = $1', [id]
  );

  // 3. Guardar con TTL (60 s en este caso) y responder
  await redis.set(clave, JSON.stringify(producto), { EX: 60 });
  return producto;
}

// Uso: la primera llamada tarda ~30 ms (BD),
// las siguientes ~2 ms si el TTL no ha expirado.

Ventajas: simple, no toca el flujo de escritura, los datos se calientan solos cuando se piden. Inconveniente: la primera petición tras expirar el TTL siempre paga el coste completo (se conoce a ese raro usuario como «el que calienta el caché»).

Read-through y write-through

Las variantes «perfectas» mueven el caché al lado de la fuente de verdad y no al código de negocio:

  • Read-through: una librería/DAO gestiona el patrón anterior por ti: pides repo.get(id), y si no está en caché, la librería lee la BD y la llena. Tu código no sabe que existe un caché.
  • Write-through: al escribir, primero escribes en el caché y después en la BD (o viceversa). Garantiza que el siguiente read encuentre el dato fresco; lo malo es que paga el coste de escribir dos veces.
  • Write-behind: escribes solo al caché, y un proceso posterior sincroniza la BD. Muy rápido, pero pierdes algo si el proceso cae antes de flushear.
# Cache-aside read-through con redis-py y un repositorio
import json
import redis

cache = redis.Redis(host="cache", port=6379)
TTL_SEG = 300


def obtener_perfil(usuario_id: int) -> dict:
    clave = f"perfil:{usuario_id}"
    valor = cache.get(clave)
    if valor is not None:
        return json.loads(valor)          # hit

    perfil = repositorio.buscar(usuario_id)   # la fuente de verdad
    if perfil is not None:
        cache.setex(clave, TTL_SEG, json.dumps(perfil))  # miss -> rellena
    return perfil


def guardar_perfil(usuario_id: int, datos: dict) -> None:
    # Write-through: guardar en BD y refrescar el caché en la misma operación
    datos["actualizado_en"] = "2026-02-01T10:30:00Z"
    repositorio.guardar(usuario_id, datos)
    cache.setex(f"perfil:{usuario_id}", TTL_SEG, json.dumps(datos))

Primeros pasos con Redis

Redis es el estándar para caché en memoria compartida en el backend: sub-milisegundo, con TTL nativo y estructuras útiles. Un par de comandos esenciales desde el CLI:

# Conectarse y cachear un valor con expiración
redis-cli -h cache
SET producto:42 '{"nombre":"Balón","precio":12.5}' EX 60    # TTL de 60 segundos
GET producto:42
TTL producto:42        # segundos restantes de vida
DEL producto:42        # invalidación manual

# Solo guardar si NO existe (evita sobrescribir un caché aún válido)
SETNX producto:42 '{"nombre":"Balón","precio":12.5}'

# Cachear un listado con expiración y forzar revalidación posterior
SET lista:juguetes '[{"id":1},{"id":2}]' EX 120

El comando SETNX sirve además para implementar un sencillo lock distribuido. Y recuerda la regla de oro de las claves: recurso:id, minúsculas, sin espacios, con TTL, y con «versión» cuando cambie el formato (producto:v2:42).

Invalidación: el arte difícil

Cachear es fácil; mantenerlo coherente es el trabajo. Tres estrategias, de más simple a más robusta:

  1. TTL corto: aceptas que los datos vivan obsoletos un rato (segundos/minutos) y se autocorrijan. Ideal para catálogos, precios con margen de error y feeds.
  2. Invalidación directa: cuando algo cambia, DEL de las claves afectadas. Simple pero frágil: olvidaste una clave y el dato viejo se sirve hasta que expire.
  3. Versionado + invalidación por eventos: publicas un evento «producto_actualizado» y los listeners borran la clave. Es la que escala en arquitecturas con varios servicios.
// Invalidación directa tras una escritura, en el mismo proceso
app.post('/productos/:id', async (req, res) => {
  const id = req.params.id;
  await db.query('UPDATE productos SET ... WHERE id = $1', [id]);

  // Borrar las claves que dependen de este producto
  await redis.del(`producto:${id}`);          // el detalle
  await redis.del('lista:juguetes');          // el listado que lo muestra
  res.status(200).json({ ok: true });
});

Regla práctica: si no estás seguro de poder invalidar bien una clave, ponle un TTL conservador y acepta la inconsistencia momentánea. Un dato viejo 30 segundos casi siempre es un precio mucho menor que un bug de datos eternos.

El efecto stampede (y su remedio)

Un miss golpea a todos a la vez: cuando el TTL de una clave popular expira, 100 peticiones leen de la BD al mismo tiempo si 100 procesos piden la clave. Esto es un cache stampede. Remedios: TTL con jitter (aleatorio) que espacie las expiraciones, y single-flight (una sola recarga bajo lock) para que solo uno recalcule mientras los demás esperan.

// Añadir jitter al TTL: cada relleno expira en un momento ligeramente distinto
const TTL_BASE = 120;
const jitter = Math.floor(Math.random() * 20); // +0..19 s
await redis.set(clave, json, { EX: TTL_BASE + jitter });

Ejercicio

  1. Elige 3 datos de tu sistema que se lean mucho y cambien poco (catálogo, países, config). Clasifícalos: ¿qué TTL tolerarían? ¿Qué nivel de inconsistencia es aceptable?
  2. Implementa cache-aside con Redis (o el sistema que tengas) para el más leído y mide la latencia antes y después con curl -w o tu herramienta habitual.
  3. Anota las claves que tendrías que borrar si cambias un producto y compara con la lista de claves que tu código realmente usa: cualquier desajuste ahí es un bug de invalidación futuro.

Resumen

  • El cache-aside lee caché → miss → lee fuente → rellena con TTL → responde.
  • Read-through y write-through mueven el caché a la capa de datos; write-behind gana velocidad y pierde durabilidad.
  • Redis ofrece TTL, SETNX y sub-milisegundo; las claves se nombran recurso:id con TTL y versión.
  • Invalidación: TTL corto, DEL directo o eventos. Si dudas, TTL conservador gana en seguridad.
  • El jitter en el TTL evita el cache stampede.
  • La CDN es la misma idea llevada al borde de la red (se amplía en el módulo 3).
