Optimizar bases de datos

🚀 Avanzado 10 min Performance Backend Módulo 2 · Optimización

Introducción

La base de datos suele ser el recurso más caro y el más fácil de saturar. Casi todos los backends lentos tienen al menos uno de estos tres males: consultas sin índice (full scan), el problema N+1 (una consulta extra por fila) o conexiones que se abren a lo loco. Esta lección ataca los tres con herramientas concretas.

El método es siempre el mismo: leer el plan de ejecución antes de tocar nada, porque el plan te dice la verdad sobre lo que la base hará con tu consulta.

Índices: qué son y qué no son

Un índice es una estructura auxiliar (B-tree, por defecto) que permite encontrar filas sin recorrer toda la tabla. En una tabla de 10 millones de filas, una búsqueda por usuario_id sin índice recorre 10 millones de registros; con índice, salta directa a los pocos que tocan.

El precio: cada índice ocupa disco y ralentiza las escrituras (INSERT/UPDATE/DELETE deben mantenerlo a día). La regla de oro: índices para las columnas que usas en WHERE y JOIN, y no más.

# psql: crea índices sobre los campos de filtro y de orden más usados
psql -d tienda <<'SQL'
CREATE INDEX idx_ordenes_usuario           ON ordenes (usuario_id);
CREATE INDEX idx_ordenes_fecha_codigo      ON ordenes (fecha DESC, codigo);
CREATE INDEX idx_productos_precio          ON productos (precio)
  WHERE activo = true;                     -- índice parcial: solo filas activas

EXPLAIN (FORMAT JSON)
SELECT * FROM ordenes WHERE usuario_id = 42;
SQL

Un índice compuesto como (fecha DESC, codigo) resuelve un solo query de orden+ficheros. Un índice parcial ahorra espacio indexando solo lo que se consulta. Fan-out desmedido: cada índice añadido para una consulta rara es deuda que pagan todas las escrituras.

Leyendo el plan de ejecución

EXPLAIN ANALYZE ejecuta la consulta de verdad y reporta qué hizo la base: índice o scan completo, qué estima, cuántas filas filtró y cuánto tardó. Es la herramienta máxima de diagnóstico:

psql -d tienda <<'SQL'
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.codigo, p.nombre
FROM ordenes o
JOIN productos p ON p.id = o.producto_id
WHERE o.usuario_id = 42
ORDER BY o.fecha DESC;
SQL

-- Resultado simplificado (postgres):
-- Sort  (cost=0.87..0.89 rows=8 ...) (actual time=0.20..0.20 rows=8 loops=1)
--   ->  Nested Loop (actual time=0.02..0.11 rows=8 loops=1)
--         ->  Index Scan on ordenes_usuario_idx (actual rows=8 loops=1)
--         ->  Index Scan on productos_pkey (actual rows=1 loops=8)
-- Como ves: usa el índice idx_ordenes_usuario y el PK de productos.
-- Si viera "Seq Scan on ordenes", ahí estaría el cuello de botella.

La señal de alarma máxima es Seq Scan sobre una tabla grande con un rows=1000000.0 estimado. La solución casi siempre es un índice nuevo. Pero deja que la base te lo confirme: EXPLAIN tras crear el índice debe mostrar Index Scan y un tiempo muchísimo menor.

El problema N+1

El N+1 es el error de rendimiento más común en ORMs: pides una lista de 100 pedidos y el ORM ejecuta 1 consulta para la lista y luego 100 consultas más, una por cada pedido, para rellenar el cliente. Eso es 101 round-trips a la base para algo que se hace con un solo JOIN o una consulta por lotes.

El patrón malo (en pseudo-código de objeto-relacional) y la solución de eager loading:

// MAL: 1 consulta (pedidos) + N consultas (un cliente por pedido)
const pedidos = await pedidosRepo.buscarPorUsuario(42);
for (const pedido of pedidos) {
  const cliente = await clientesRepo.buscarPorId(pedido.cliente_id); // 1 query por pedido
  pedido.cliente = cliente;
}
// Con 100 pedidos -> 101 queries. Con 10.000 pedidos en producción -> desastre.

// BIEN: 2 consultas en total
const pedidos = await pedidosRepo.buscarPorUsuario(42);
const idsClientes = [...new Set(pedidos.map((p) => p.cliente_id))];
const clientes = await clientesRepo.buscarPorIds(idsClientes); // IN (...) en 1 query
const mapaClientes = new Map(clientes.map((c) => [c.id, c]));
for (const pedido of pedidos) pedido.cliente = mapaClientes.get(pedido.cliente_id);

La auditoría es inmediata: activa el log de consultas lentas o cuenta queries por petición con tu ORM, y busca cualquier endpoint donde el número de queries crezca con el tamaño de la lista. Ese es el N+1.

Pooling de conexiones

Abrir una conexión a la BD no es gratis: handshake TCP, autenticación, estado. Con tráfico alto, abrir una por petición agota el tope de conexiones del servidor y todo espera. La respuesta es un pool: un conjunto fijo de conexiones reutilizables de las que el código toma prestada una, hace la consulta y la devuelve.

# psycopg2 + pool. connection_pool comparte N conexiones entre todos los hilos/workers
from psycopg2 import pool

# 20 conexiones reutilizables a la tienda
pool_bd = pool.SimpleConnectionPool(
    1, 20, host="db", dbname="tienda", user="app", password="secreto"
)

import threading

def consultar_por_usuario(usuario_id: int):
    with pool_bd.getconn() as con:          # toma prestada y devuelve al terminar
        with con.cursor() as cur:
            cur.execute("SELECT * FROM ordenes WHERE usuario_id = %s", (usuario_id,))
            return cur.fetchall()

# Uso concurrente sin abrir una conexión por request:
# 20 peticiones a la vez usan las 20 conexiones del pool sin negociar nuevas.

Conceptos de ajuste: pool_max del app server y max_connections de la BD. Si el pool se agota, la app espera por una conexión (latencia en cola) o falla si hay timeout; hallar el tamaño correcto es parte normal del tuning bajo tu prueba de carga.

Prioridad de optimización

Cuando una consulta va lenta, este orden evita trabajo perdido:

  1. EXPLAIN ANALYZE: ¿Seq Scan innecesario? → índice.
  2. ¿Devuelvo columnas que no uso? → SELECT solo lo necesario.
  3. ¿Hay N+1 en el código? → batch / eager loading.
  4. ¿Conexiones per-petición? → pooling.
  5. ¿Sigue lento? → piensa en la fuente de verdad: caché (lección anterior) o escala (módulo 3).

El 80% de las veces te quedas en el paso 1.

Ejercicio

  1. Elige la consulta más frecuente de tu sistema y ejecuta EXPLAIN (ANALYZE, BUFFERS).
  2. Si ves Seq Scan o un coste desproporcionado, crea el índice adecuado (compuesto o parcial si aplica) y vuelve a ejecutar: el plan debe cambiar y el tiempo caer.
  3. Activa el conteo de consultas por petición en tu ORM y audita los endpoints de listas buscando N+1. Arregla al menos uno con la técnica de batch.
  4. Revisa si tu app abre una conexión por petición y sustitúyela por un pool.

Resumen

  • Los índices aceleran lecturas y pagan en escrituras; úsalos para WHERE y JOIN y nada más.
  • EXPLAIN ANALYZE es la herramienta central: Seq Scan sobre tabla grande = señal de alarma.
  • El N+1 convierte 1 consulta en 1+N: se arregla con JOIN o consultas por lotes (IN ...).
  • Un pool de conexiones reutiliza conexiones y evita agotar la BD bajo tráfico.
  • Orden de ataque: EXPLAIN → SELECT mínimo → N+1 → pooling → caché/escala.
  • El caché y las réplicas de lectura (módulo 3) son el siguiente paso cuando la BD sola no da.
