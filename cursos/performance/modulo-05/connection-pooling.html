Pooling de conexiones y sockets

🔥 Avanzado 11 min Performance y Optimización Módulo 5 · Optimización del runtime

Introducción

Abrir una conexión TCP, hacer handshake TLS o autenticar contra la base de datos cuesta decenas de milisegundos. Si cada petición abre una nueva, estás pagando ese coste por cada mil peticiones, y el servidor de datos sufre el churn de conexiones.

El connection pooling reutiliza sockets ya establecidos: un pool mantiene N conexiones abiertas listas, las presta a los requests y las recoge al terminar. Menos handshakes y latencia de origen.

Definición

Un pool de conexiones mantiene un conjunto de conexiones abiertas y reutilizables a un servicio (BD, Redis, HTTP), prestando y recibiendo de forma segura ante la concurrencia.

Por qué importa. Elimina el coste de crear conexiones por request, reduce la carga agregada en el destino y evita agotar el límite de conexiones de la base de datos.

Cuándo usarlo. Úsalo siempre que haya un servicio de datos o remoto detrás. Ajusta el tamaño del pool al paralelismo esperado, no al número de peticiones totales.

Conceptos clave

  • Un pool presta conexiones reutilizables a hilos/requests concurrentes.
  • min y max controlan cuántas se mantienen y cuántas se pueden abrir.
  • Adaptadores (psycopg2, redis-py, ioredis) ya incluyen pools nativos.
  • Las conexiones idle se reciclan (idle timeout) para no arder sockets.
  • La parametrización del pool depende de usuarios concurrentes, no de requests/minuto.

Ejemplo básico

Creamos un pool de SQLite/Postgres SQLAlchemy y medimos el ahorro.

100 consultas reutilizando pool: 0.045s

Ejemplo intermedio

Configuramos un pool de redis-py con timeout para picos.

Ejemplo real

Una API con 2000 req/min usaba una conexión MySQL nueva por petición. Con un pool de 20 conexiones y pool_pre_ping, la CPU del MySQL cayó un 60% y la latencia de la primera consulta bajó 3x. Los picos ya no agotaban el límite de conexiones.

  • Fija el pool al paralelismo real (nº de workers * hilos por worker).
  • Habilita pre_ping / health check para descartar conexiones muertas.
  • Monitoriza el uso del pool: que nunca llegue a saturarse en pico.

Un pool muy grande es tan malo como uno pequeño: muchos sockets idle y concurrencia en el destino.

Explicación

  • Crear una conexión tiene coste de handshake, auth y memoria; el pool paga una vez.
  • El pool entrega una conexión libre y la marca como prestada; al devolverla queda disponible.
  • pool_pre_ping valida la conexión antes del uso para no fallar por socket roto.
  • Los timeout del pool controlan la espera cuando se agota: mejor esperar que sobresubscribir.
  • El tamaño óptimo ≈ latencia × throughput, ajustado con pruebas de carga.

Errores comunes

  • Crear un engine nuevo por petición: pool que nunca se usa.
  • Pool sin límite: el servidor de BD explota en sockets.
  • No liberar conexiones en excepciones: fugas de pool que parecen límites de conexión.

Buenas prácticas

  • Siempre en contexto (with / try-finally) para devolver la conexión.
  • Ajusta pool_recycle a la vida de los sockets de tu proxy.
  • Añade métricas de uso: pool size, waiting, timeouts.
  • Prueba de carga: ajusta max y observa los timeouts del pool.

Ejercicio

  1. Compara 500 consultas con y sin pool (create_engine en cada una).
  2. Pon max_connections=2 y lanza 10 hilos: observa las esperas.
  3. Activa pool_pre_ping tras matar una conexión y verifica la recuperación.

Resumen

  • Los pools reutilizan conexiones y eliminan el coste de crearlas.
  • Tamaño = paralelismo real, con timeout para picos.
  • Sin pool, el churn de conexiones come CPU del destino y tu latencia.
