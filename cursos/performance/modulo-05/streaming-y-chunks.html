Streaming y respuestas por chunks

🔥 Avanzado 10 min Performance y Optimización Módulo 5 · Optimización del runtime

Introducción

El tiempo hasta el primer byte (TTFB) importa más de lo que parece: los usuarios y las pruebas de rendimiento lo perciben como la espera real. Una respuesta gigante de 50 MB enviada como un bloque llega al cliente mucho más tarde que la misma data en flujo.

El streaming envía fragmentos (chunks) tan pronto como están listos: el cliente empieza a procesar o renderizar sin esperar la cola completa. HTTP/1.1 lo permite con Transfer-Encoding: chunked.

Definición

El streaming descompone la respuesta en fragmentos enviados incrementalmente; con Server-Sent Events (SSE) el servidor empuja eventos hacia el cliente sobre una conexión abierta.

Por qué importa. Mejora la percepción de latencia (primer byte temprano), reduce la memoria del servidor (no acumula el body completo) y habilita feeds y notificaciones push sin WebSocket.

Cuándo usarlo. Úsalo para descargas grandes, feeds de eventos, log streaming y actualizaciones en vivo. No lo use para JSON minúsculo donde el overhead no compensa.

Conceptos clave

  • Transfer-Encoding: chunked envía trozos de datos o datos continuos.
  • El primer byte llega cuando empieza la escritura, no al final.
  • SSE (text/event-stream) empuja eventos sin renegar la conexión.
  • Los streams de archivo evitan cargar el archivo completo en memoria.
  • El cliente consume a medida: total bytes idénticos, percepción mucho más rápida.

Ejemplo real

Una API de importación devuelve el resultado de validar cada fila en directo: el cliente ve progreso línea a línea en vez de esperar minutos por un JSON final. La percepción de latencia cayó de 3 minutos a 2 segundos.

  • Envía el estado inicial y ve alimentando los eventos.
  • Desactiva el buffering del proxy (X-Accel-Buffering: no) o el stream no vuela.
  • Para archivos, usa send_file con streaming para no cargarlos en RAM.

Los reverse proxies pueden bufferear: revisa proxy_buffering off en Nginx para SSE.

Explicación

  • Chunked permite emitir antes de conocer la longitud final.
  • El cliente recibe el primer fragmento en cuanto se escribe: TTFB mínimo.
  • SSE es unidirectional y sencillo; WebSocket sirve bidireccional.
  • Streaming de archivos reduce el pico de memoria del servidor a un buffer.
  • Los proxies deben desactivar el buffering o el 'streaming' se vuelve un simulacro.

Errores comunes

  • Proxy que bufferea sin avisar: el cliente recibe todo el final.
  • Conteo de keep-alive o lecturas incompatibles con chunked.
  • SSE sin cabecera text/event-stream: el navegador lo trata como binario.

Buenas prácticas

  • Usa Response con generador y el framework hace chunked solo.
  • Para SSE, desactiva compression y buffering en la capa de proxy.
  • Prueba el TTFB con curl -N contra la respuesta stream.
  • Elimina los flush del framework si el buffer era el simulacro.
