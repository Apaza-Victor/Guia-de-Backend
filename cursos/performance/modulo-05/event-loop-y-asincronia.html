El event loop y la asincronía

🔥 Avanzado 11 min Performance y Optimización Módulo 5 · Optimización del runtime

Introducción

Node.js, Python asyncio y Go comparten una idea: un solo hilo de ejecución atiende miles de conexiones si no bloqueas. Cada operación de I/O se delega al sistema y el hilo sigue con la siguiente tarea.

El event loop es el corazón de ese modelo. Entender qué bloquea y qué no decide si tu servicio atiende 10.000 peticiones por segundo o se congela con 500.

Definición

El event loop ejecuta callbacks y operaciones sin bloquear, alternando tareas en cola; las operaciones síncronas de CPU o de I/O bloqueante cortan ese ciclo y degradan la concurrencia.

Por qué importa. En un runtime de un solo hilo, una sola función síncrona lenta (JSON.stringice de un gigante, un hash costoso, un fs.readFile sync) bloquea a todos los demás clientes.

Cuándo usarlo. Usa I/O asíncrono para todo, aísla el trabajo de CPU en workers y evita operaciones síncronas en el hot path. Para cómputo CPU-bound servido a muchos, prefiere workers.

Conceptos clave

  • El event loop rota por fases: timers, callbacks, poll, check, close.
  • Las operaciones async se ejecutan en el pool de la librería, no en el loop.
  • Un callback síncrono largo bloquea el loop (event loop starvation).
  • setImmediate / process.nextTick / dost: ordenan microtareas en el bucle.
  • El bloqueo se detecta con samplings y en Node con perf_hooks / async_hooks.

Ejemplo real

Un servicio FastAPI convirtió un hash bcrypt (CPU síncrona) en un worker dedicado: el event loop dejó de congelarse y el p95 de latencia bajó 4x. El secreto: nada síncrono pesado en el camino del request.

  • Anti el bloqueo de CPU fuera del loop con workers o threads.
  • Usa I/O estrictamente async (asyncpg, aiohttp) en el hot path.
  • Mide el loop lag: el tiempo que un callback espera por el bucle.

En Node, los crypto native ya usan threads libres; el win es conocer qué es síncrono en tu runtime.

Explicación

  • El event loop atiende I/O sin esperar: cuando la petición llega, delega y sigue.
  • Una operación síncrona de CPU bloquea el procesamiento de otros requests.
  • Los workers (threads/procesos) aíslan el trabajo costoso fuera del loop.
  • El loop lag se mide con instrumentación (EventLoopMonitor, perf_hooks).
  • La asincronía no es paralelismo: mejora la concurrencia, no la velocidad de CPU.

Errores comunes

  • Bloquear con time.sleep o fs.readFileSync en un servicio async.
  • Encadenar await sin límite: encima secuencial de I/O que podría ser paralelo.
  • Olvidar el límite de workers: un pool sobresuscrito duplica latencia.

Buenas prácticas

  • Instrumenta el loop lag antes de optimizar: es tu mapa.
  • Usa librerías async puras en todo el stack (DB, Redis, HTTP).
  • Paraleliza I/O independientes con asyncio.gather / Promise.all.
  • Escala workers por CPU, no por conexiones: el loop no es la muchedumbre.

Ejercicio

  1. Mide cuántos 'pings' atiende tu loop mientras haces 10 sleepsync de 1s.
  2. Mueve el bloqueo a to_thread y repite la medición (pings ya no esperan).
  3. Monitorea el loop lag con una métrica manual y explica la mejora.

Resumen

  • El event loop logra alta concurrencia si el trabajo es I/O async.
  • Cada bloqueo síncrono roba tiempo a todos los clientes.
  • Descargar CPU a workers y paralelizar I/O libera el loop.
