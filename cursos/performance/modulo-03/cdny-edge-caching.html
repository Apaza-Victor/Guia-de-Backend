CDN y edge caching

🚀 Avanzado 8 min Performance Backend Módulo 3 · Escalabilidad y despliegue

Introducción

Aunque tu backend sea rapidísimo, cada kilómetro de distancia física suma milisegundos: un usuario en Buenos Aires contra un servidor en Madrid acumula 100-200 ms solo de latencia de red. Una CDN (Content Delivery Network) replica tu contenido en cientos de servidores «del borde» (edge) distribuidos por el mundo; la petición la responde el edge más cercano al usuario, sin viajar hasta tu origen.

Y el edge caching es la versión de caché con más rendimiento que existe: la respuesta se sirve sin tocar ni tu balanceador, ni tu API, ni tu base de datos. El coste para tu equipo: decidir qué es cacheable y controlar su expiración con headers.

Qué se cachea en el edge

La decisión de cacheabilidad es tuya y se expresa en headers. Lo ideal para el edge:

  • Recursos con contenido público e idéntico para todos: imágenes, CSS/JS, catálogos, páginas de precios, descripciones. Cachea agresivamente.
  • Recursos públicos pero cambiantes: feeds, noticias, estados de envío. Cachea con TTL corto o validación.
  • Lo que NO se cachea: cualquier cosa privada/autenticada (perfiles, saldos, carritos) — salvo que la CDN ofrezca probing por cookies o token.

La regla del balance: cada recurso cacheado que coincide con el mismo usuario que pide de nuevo = cero backends. Es el multiplicador de capacidad más barato que existe.

Headers de caché: Cache-Control

El servidor de origen declara si un recurso puede quedar en caché y por cuánto tiempo con Cache-Control. Verifica lo que envían tus respuestas con la terminal:

# Inspeccionar los headers de las respuestas
curl -sI https://mi-servicio.com/catalogo.json | grep -i -e cache -e etag -e edad
# cache-control: public, max-age=300, stale-while-revalidate=60
# etag: "abcdef-123456"
# age: 120

# Directivas típicas:
#   public, max-age=3600    -> cacheable en edge y navegador durante 1h
#   private, max-age=0      -> solo en el navegador, nunca en CDN (datos personales)
#   no-store                -> nunca en caché (tokens, datos bancarios)
#   stale-while-revalidate  -> sirve obsoleto mientras revalida en segundo plano
#   s-maxage=300            -> TTL DIFERENTE para las CDN/proxies (edge)

El matiz que manda con CDNs: s-maxage fija la duración en los caños intermedios (proxy, CDN) distinta de la del navegador. Y el ETag es el mecanismo para la revalidación barata: el edge pide «¿cambió?», el origen responde 304 sin payload, y el cache sigue sirviendo la copia.

En Express, fijar estos headers es trabajo de un middleware por ruta:

const express = require('express');
const app = express();

// Catálogo público: cacheable por la CDN durante 5 minutos (s-maxage)
app.get('/catalogo/precios.json', (req, res) => {
  res.set('Cache-Control', 'public, max-age=60, s-maxage=300, stale-while-revalidate=60');
  res.json(preciosActuales);      // si cambia, invalidar con purge o subir TTL de version
});

// Datos privados: nadie comparte este recurso (ni edge, ni proxy)
app.get('/perfil/:id', (req, res) => {
  res.set('Cache-Control', 'private, no-store');
  res.json({ usuario: req.usuario });   // con 'no-store' la CDN no lo toca
});

Invalidación en la CDN

El TTL protege a medias: 5 minutos de catálogo viejo es aceptable; un precio desactualizado 5 minutos durante una oferta puede ser un problema. Para eso, las CDNs ofrecen purge: eliminar una URL (o patrón) de todos los edges al instante.

# Purge selectivo por URL (ej. Fastly/Cloudflare invokes purging por API/CLI)
# Los clientes de CDN exponen una operación de purge:
curl -X POST https://api.fastly.com/service/$SERVICIO/purge/catalogo/precios.json \
  -H "Fastly-Key: $FASTLY_KEY"
# -> {"status":"ok"}

# Patrón alternativo muy usado (cache busting): cambia la URL al versionar.
#   /catalogo/v2/precios.json -> ninguna copia antigua puede sobrevivir al cambio de URL:
#   dejas de servir la versión v1, y solo existe v2. Cero purge manual.

Diseño perfecto de producción: URL versionada (cache-busting) para assets inmutables (no necesitas purge) + TTL corto con s-maxage + revalidación con ETag para los cambiantes. El purge manual queda como último recurso.

El efecto global

Pon números a la diferencia. Un catálogo de 2 MB servido desde un origen en Madrid a un usuario en Montevideo puede tardar 400 ms solo de red. Servido por el edge local de la CDN: 20 ms y cero carga sobre tu backend — que pasa de servir esa URL a no verla jamás. En la punta de escala, la tuya es una de las optimizaciones con mayor retorno por minuto de configuración.

Regla práctica: la CDN transforma «mi backend responde en 150 ms» en «el usuario no está hablando con tu backend». Cuando el desafío es mundial, es la única palanca que funciona de verdad.

Ejercicio

  1. Lista tus endpoints y clasifícalos en cacheables (públicos) y no-cacheables (privados). Fija para cada uno un Cache-Control correcto y revísalo con curl -sI.
  2. Elige el recurso más solicitado de tus públicos y aplica public, s-maxage. Delante de una CDN (o mejor, de un proxy de caché local como nginx caching) mide cuántas peticiones dejan de llegar a tu origen.
  3. Si un recurso debe actualizarse rápido: decide entre TTL corto/ETag (revalidación) o purge; añade el bash de purge a tu runbook.

Resumen

  • Una CDN replica tu contenido en el edge; el usuario habla con el servidor más cercano, no con tu origen.
  • El edge caching saca las respuestas públicas de tu backend por completo.
  • Cache-Control: public/private + max-age + s-maxage es el idioma con la CDN.
  • s-maxage fija el TTL del edge; el ETag permite revalidar sin reenviar el payload.
  • URLs versionadas (cache-busting) evitan el purge en assets inmutables.
  • Dato privado → no-store; el purge solo para emergencias.
  • Es la palanca de mayor retorno cuando el desafío es distribuir contenido por todo el mundo.
