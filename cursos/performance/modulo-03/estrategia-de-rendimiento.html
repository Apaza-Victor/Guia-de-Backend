Estrategia integral

🚀 Avanzado 9 min Performance Backend Módulo 3 · Escalabilidad y despliegue

Introducción

Ya sabes medir, optimizar y escalar. La última pieza es no olvidarlo: el rendimiento no es una tarea que se hace una vez, es un proceso. Si el equipo no lo sostiene, en dos trimestres la deuda técnica devuelve la latencia a como estaba antes de empezar.

Esta lección cierra el curso con la disciplina: el ciclo medir → optimizar → escalar convertido en rutina, presupuestos automatizados que se ejecutan en cada release y una revisión periódica del sistema completo.

El ciclo completo: medir → optimizar → escalar

El orden no es aleatorio y nunca se salta un paso:

  1. Medir (módulo 1): SLOs, pruebas de carga, perfiles y diagnóstico de cuellos de botella. Lo que no se mide vuelve a romperse.
  2. Optimizar (módulo 2): caché, bases de datos, concurrencia, APIs e I/O. Aplicar con la prueba como testigo: la respuesta debe mejorar cuantificablemente.
  3. Escalar (módulo 3): nodos, balanceo, bases de datos a escala, CDN. La última palanca, que solo entra cuando medir muestra que el rendimiento local ya no alcanza.

La trampa clásica es saltarse la medición: optimizar una función que no importa, o escalar mientras hay un índice que falta. El ciclo existe para impedir exactamente eso.

El presupuesto como contrato en CI

El SLO y el presupuesto definidos en el módulo 1 se convierten en pruebas automatizadas: cada release corre una prueba de carga ligera con thresholds que fallan la entrega si el p95 supera el umbral. Así el rendimiento entra en el flujo diario y ninguna feature nueva puede empeorarlo sin que el equipo lo confirme.

Un presupuesto tiene sentido si queda documentado y versionado junto al código:

{
  "version": 1,
  "presupuesto_peticion": {
    "max_p95_ms": 300,
    "max_errores_pct": 0.5
  },
  "por_endpoint": {
    "GET /catalogo/precios": { "p95_max_ms": 100, "cacheable": true },
    "POST /carrito/comprar":  { "p95_max_ms": 400 },
    "GET /perfil":            { "p95_max_ms": 200, "privado": true }
  },
  "capacidad": {
    "rps_objetivo": 1500,
    "nodos_minimos": 3,
    "check_escalado_cada": "semana"
  },
  "proceso": {
    "pruebas_en_ci": true,
    "revision_periodica_dias": 30,
    "responsable": "equipo-performance"
  }
}

Con k6, ese presupuesto se ejecuta automáticamente como etapa de CI, tal como viste en «pruebas de carga»:

// budget.ci.js: versión corta para CI (1-2 min)
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 40,                                // carga ligera, solo regresiones
  duration: '60s',
  thresholds: {
    'http_req_duration{expected_response:true}': ['p(95)<300'],
    'http_req_failed': ['rate<0.005']
  }
};

export default function () {
  const res = http.get('https://ci.mi-servicio.com/catalogo/precios');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(0.5);
}
// Paso en el pipeline:  k6 run budget.ci.js
// Si los thresholds fallan -> el release se detiene, no se despliega.

En un pipeline real, la orden de la prueba se ve así (una etapa más del CI, con sus umbrales que ya vienen del presupuesto JSON):

# Etapa del pipeline: verificación de rendimiento antes de desplegar
k6 run budget.ci.js --quiet --summary-export=resumen.json

# k6 responde con código de salida no-cero si los thresholds fallan;
# el pipeline se detiene ahí (exit != 0) y el release no avanza.
if [ $? -ne 0 ]; then
  echo "Presupuesto superado: p95 o errores fuera de rango. Revisar."
  exit 1
fi

# Y por si algo se pierde en el log: el manager de CI muestra el resumen
cat resumen.json | jq '.metrics.http_req_duration.values["p(95)"]'

Métricas siempre encendidas

El presupuesto en CI detecta regresiones de laboratorio. Para que el sistema viva sano en producción, el monitoreo debe medir siempre (aquí conecta tu curso de Observabilidad):

  • Latencia por endpoint en percentiles (p50/p95/p99) y tasa de errores, con alerta cuando el error budget se agota.
  • Throughput y uso de los recursos (CPU, memoria, I/O) por nodo: verás la cola formándose antes del pico.
  • Rendimiento de la BD: tiempo de consulta, conexiones activas, índice faltante (pg_stat_user_indexes que se está sin usar).
  • Latencia de dependencias: tus servicios externos deben tener su propio SLO; si uno no lo cumple, piensa caché, variar o cambiar de proveedor.

Revisa estos paneles en una cadencia fija (una hora al día, el ritual del café) y una revisión profunda mensual con tu carga de producción real.

Revisión periódica y cultura

La frecuencia y la salida del proceso, para que no muera por desinterés:

  1. Semanal: miramos p95/p99, throughput y alertas de error budget. Si algo se dispara, abrimos ticket.
  2. Mensual: correr una prueba de carga con el escenario nuevo (volumen estimado del próximo mes) y el capacity planning correspondiente. La prueba de tensión de la «estrategia» se hace en un entorno de staging.
  3. Trimestral: revisión de arquitectura: ¿el índice sigue justificado? ¿la caché sigue caliente? ¿este endpoint que ya nadie usa de verdad necesitaba esa complejidad?

El peor enemigo es la burocracia vacía, así que la regla es: cada revisión termina con una acción concreta (un índice, un timeout, un nodo más, un SLO actualizado). Si la acción no aterriza en un ticket, la reunión no sirvió.

Regla práctica: el rendimiento se paga como deuda cuando se ignora: cada release sin su prueba es una apuesta. Con el presupuesto de CI y la revisión mensual, la apuesta desaparece.

Ejercicio

  1. Escribe el presupuesto JSON de tu sistema siguiendo la plantilla: por endpoint, con umbrales y responsables.
  2. Convierte los dos umbrales clave en un script de CI (k6 u otra herramienta) y añádelo a tu pipeline: la próxima feature ya no podrá empeorar el p95 sin que el pipeline proteste.
  3. Programa tu revisión periódica real (en tu calendario, con fecha): la primera dentro de 4 semanas. Anota qué 3 métricas mirarás siempre.

Resumen

  • El ciclo es medir → optimizar → escalar, sin atajos: medir decide, optimizar arregla, escalar da aire.
  • El presupuesto de rendimiento vive versionado como código y se ejecuta en CI con thresholds.
  • El monitoreo de producción (percentiles, recursos, BD, dependencias) está siempre encendido.
  • Revisión semanal (paneles), mensual (carga + capacity) y trimestral (arquitectura).
  • Toda revisión termina en una acción concreta con ticket; si no hay acción, cuestiónate la reunión.
  • Con esta rutina, el rendimiento deja de ser un proyecto: es un proceso que no se olvida.
