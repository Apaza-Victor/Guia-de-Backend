Bases de datos a escala

🚀 Avanzado 10 min Performance Backend Módulo 3 · Escalabilidad y despliegue

Introducción

Escalaste la API a 20 nodos detrás de tu balanceador… y ahora toda la carga cae sobre una única base de datos. Las bases de datos se escalan distinto que los servidores de aplicación: son difíciles de replicar sin romper consistencia. Esta lección va en orden de menor a mayor dolor: replicas de lectura (primero), particionado (tablas grandes) y sharding (la última bala).

Réplicas de lectura

En la mayoría de los sistemas, las lecturas superan ampliamente a las escrituras (10:1 o más). Las réplicas de lectura son copias de la base que responden a los SELECT mientras el primario (leader) atiende las escrituras y se las replica. Así, la carga de lectura se reparte entre N servidores y el primario respira.

El costo: consistencia eventual — una réplica puede estar unos milisegundos por detrás (replicación asíncrona). Para datos de sesión, catálogo y lecturas generales es perfecto; para el saldo bancario, no.

Configuración mínima en PostgreSQL:

# En el primario (postgresql.conf): marcar como replicación y abrir slot
#   wal_level = replica
#   max_wal_senders = 10
#   hot_standby = on

# En la réplica (postgresql.conf):
#   hot_standby = on          # servirá lecturas mientras replica

# Clonar datos del primario a la réplica (pg_basebackup)
pg_basebackup -h primario -D /var/lib/postgresql/data -R -X stream -U replicador
# El flag -R deja lista la configuración de streaming en standby.signal

Y la aplicación reparte las lecturas hacia un pool de réplicas:

import random
import threading
import psycopg2

# Pooles separados: escrituras al primario, lecturas a las réplicas
with threading.Lock():
    def obtener_lectura():
        replica = random.choice(["replica-1", "replica-2", "replica-3"])
        return psycopg2.connect(host=replica, dbname="tienda", user="app", password="secreto")

    def obtener_escritura():
        return psycopg2.connect(host="primario", dbname="tienda", user="app", password="secreto")

# Rutas de solo lectura -> replica (catálogo, perfiles, reportes)
def listar_productos(categoria: str):
    con = obtener_lectura()
    with con.cursor() as cur:
        cur.execute("SELECT * FROM productos WHERE categoria = %s", (categoria,))
        return cur.fetchall()

# Rutas de escritura -> primario (compras, actualizaciones)
def registrar_compra(datos: dict):
    con = obtener_escritura()
    with con.cursor() as cur:
        cur.execute("INSERT INTO compras (...) VALUES (...)", datos)
    con.commit()

La transición es suave: primero mueves los reportes y catálogos; solo después te atreves con las rutas calientes.

Particionado (tablas gigantes)

Cuando una tabla tiene cientos de millones de filas, incluso con índice el rendimiento se degrada: el índice es enorme, la caché no cabe y los análisis tardan. El particionado divide la tabla lógicamente en otras más pequeñas —típicamente por fecha («orders_2026», «orders_2027»)— manteniendo una sola vista lógica. Las consultas con el criterio de partición van directas al trozo correcto.

PostgreSQL 12+ lo hace con PARTITION BY heredado, sin cambiar las consultas de la aplicación:

psql -d tienda <<'SQL'
CREATE TABLE compras (
  id bigint,
  fecha timestamp NOT NULL,
  usuario_id int,
  total numeric
) PARTITION BY RANGE (fecha);

-- Particiones por año
CREATE TABLE compras_2026 PARTITION OF compras
  FOR VALUES FROM ('2026-01-01') TO ('2027-01-01');
CREATE TABLE compras_2027 PARTITION OF compras
  FOR VALUES FROM ('2027-01-01') TO ('2028-01-01');

-- Las consultas de un año usan solo su partición (la app no cambia nada):
EXPLAIN SELECT * FROM compras WHERE fecha BETWEEN '2026-06-01' AND '2026-06-30';
--  ->  Seq Scan on compras_2026 ...     <- solo el trozo de 2026
SQL

Para análisis o ANALYZE/relativos: hacer VACUUM ANALYZE y borrar particiones viejas (DROP TABLE compras_2019) se vuelve trivial: no tocas a los datos vivos.

Sharding: repartir los datos en varios servidores

El sharding es lo último: en vez de una BD gigante, varias BDs (shards) cada una con una parte de los datos, donde una clave de reparto (usuario_id, pais) decide a qué shard va cada fila. Gana espacio y throughput total; pierde operaciones cruzadas: consultas «a todos los shards» y transacciones entre shards son caras o imposibles.

{
  "estrategia": "hash_mod",
  "num_shards": 4,
  "shard_id": "usuario_id % 4",
  "conexiones": {
    "shard_0": { "host": "db-0", "puerto": 5432 },
    "shard_1": { "host": "db-1", "puerto": 5432 },
    "shard_2": { "host": "db-2", "puerto": 5432 },
    "shard_3": { "host": "db-3", "puerto": 5432 }
  },
  "reglas": {
    "mismo_usuario_siempre_mismo_shard": true,
    "transacciones_cruzadas": false,
    "migracion_de_shards": "duplicar_datos_y_redirigir"
  }
}

El detalle que más duele es la migración: cambiar mod 4 por mod 8 rebalancea el 50% de los datos. Por eso se recomienda consistir en una clave estable y suficiente de sobra desde el día uno.

Cuándo tocar cada palanca

El desescalonamiento evita sufrir: primero optimiza (índices, N+1), luego caché, después réplicas de lectura, después particionado de las tablas gordas y por último sharding. Cada paso tiene un coste operativo creciente; la mayoría de sistemas nunca necesitan pasar del tercero.

Regla práctica: si una lectura se sirve desde caché de verdad, las réplicas apenas sufren; y si una tabla anual se particiona bien, el sharding queda para escenarios realmente exóticos.

Ejercicio

  1. Inventa una tabla candidata del caso de la tienda (compras) y escribe el DDL con partición por rango de un año. Verifica con EXPLAIN que una consulta del semestre toca solo su partición.
  2. Repite tu prueba de carga sirviendo las lecturas de catálogo desde una réplica y comprueba la reducción de carga en el primario.
  3. Discute (y escribe): ¿qué operaciones de tu sistema romperían si los datos se repartieran en 4 shards? Ese análisis es la respuesta a «¿me toca sharding?».

Resumen

  • Orden de escala: optimización/caché → réplicas de lectura → particionado → sharding.
  • Réplicas de lectura reparten SELECT; el primario escribe. Paga con consistencia eventual.
  • La app separa los pooles de conexión: escrituras al líder, lecturas al azar entre réplicas.
  • El particionado parte tablas por rango (fechas) manteniendo una sola vista lógica.
  • El sharding reparte los datos en varias BDs por clave; rompe transacciones y consultas cruzadas, y migrar es costoso.
  • Si la mayoría de tus lecturas salen de caché, casi nunca llega la hora del sharding.
  • La CDN elimina otro montón de tráfico antes de llegar siquiera a tu backend: siguiente lección.
