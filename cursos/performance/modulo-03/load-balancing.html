Load balancing

🚀 Avanzado 9 min Performance Backend Módulo 3 · Escalabilidad y despliegue

Introducción

El load balancer (balanceador de carga) es el repartidor de tráfico de tu sistema: recibe cada petición, decide qué nodo del grupo debe atenderla y la reenvía. Con él, varias réplicas se comportan como un solo servicio frente al cliente. Sus dos trabajos son repartir el trabajo y apartar los nodos enfermos con health checks.

Las estrellas del mundo abierto son nginx y HAProxy. Te mostraremos ambos, porque las decisiones (round-robin, least-connections, sticky) son las mismas.

Algoritmos de balanceo

  • Round-robin: alterna los nodos uno tras otro, repartiendo de forma pareja y simple. Insuficiente si uno es más potente que los otros o si algunas peticiones son mucho más costosas.
  • Least-connections: envía la petición al nodo con menos conexiones activas. Mejor que round-robin cuando las peticiones duran distinto: elige el nodo con menos ocupación, no el siguiente de una rotación rígida.
  • Pondered (ponderado): asigna pesos: un nodo de 8 vCPU recibe el doble que uno de 4.
  • IP-hash / sticky sessions: siempre el mismo cliente va al mismo nodo. Útil solo como muleta para servicios con estado en memoria; la solución correcta sigue siendo hacerlo stateless (lección anterior).
  • Consistent hashing: para cachés distribuidas: mantiene el «mapeo» estable aunque entren o salgan nodos.

Regla práctica: empieza con least_conn. Solo vuelve al sticky si un servicio con estado en memoria no se puede corregir todavía; y entonces que sea un checklist urgente de «hágase stateless».

Balanceo con nginx

Un upstream de tres réplicas con least-connections, health check pasivo y retries es una configuración de pocas líneas:

# /etc/nginx/conf.d/api-balancer.conf
upstream backend_api {
    least_conn;                       # mejor nodo = menos conexiones activas
    server api-1:8080 weight=3;       # tres veces el tráfico que api-3
    server api-2:8080 weight=3;
    server api-3:8080 weight=1;       # máquina más pequeña
}

server {
    listen 80;

    location /api/ {
        proxy_pass http://backend_api;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_next_upstream error timeout;   # si falla, reintenta en otro nodo
        proxy_connect_timeout 2s;
        proxy_read_timeout 30s;              # timeouts cortos: no esperar a un nodo colgado
    }
}

Verificar con la terminal y los logs:

# Chequear sintaxis y recargar sin cortar el servicio
nginx -t && nginx -s reload

# Los nodos caídos se marcan en los logs de error o con un endpoint de estado
curl -s http://balanceador/api/health | jq .
# {"estado":"ok","nodos":["api-1","api-2"],"caidos":["api-3"]}

Balanceo con HAProxy

HAProxy es el estándar donde el rendimiento importa de verdad: soporta health checks activos (sondea los nodos por sí mismo) y una interfaz de estadísticas en vivo:

# /etc/haproxy/haproxy.cfg
global
    maxconn 20000

defaults
    mode http
    timeout connect 3s
    timeout client  30s
    timeout server  30s

frontend http_in
    bind *:80
    default_backend api_nodes

backend api_nodes
    balance leastconn                  # menos conexiones activas
    option httpchk GET /health         # health check activo cada 2s por defecto
    server api-1 api-1:8080 check fall 3 rise 2
    server api-2 api-2:8080 check fall 3 rise 2
    server api-3 api-3:8080 check fall 3 rise 2

listen stats
    bind *:8404
    stats enable
    stats uri /stats                   # http://balanceador:8404/stats
    stats refresh 5s

La diferencia operativa clave: HAProxy comprueba sus nodos con check y los retira solos; nginx (en esta configuración mínima) confía en el reintento. Para producción seria, los dos se usan juntos muy a menudo: HAProxy delante y nginx en los nodos.

Health checks y timeouts

El health check es lo que hace que el conjunto no falle: si un nodo empieza a responder 500 o no responde, el balanceador lo saca del reparto. Sin health checks, todos los errores llegarían igual al usuario en el nodo roto.

  • Pasivo (nginx): te enteras cuando ha fallado; reintenta en otro nodo.
  • Activo (HAProxy, nginx plus): sondea periódicamente /health y mantiene los nodos malos apartados.

Y los timeouts son parte de la estrategia: un nodo colgado que no responde nunca debe ser tratado como caído rápido, no dejar que las peticiones esperen 60 segundos. Un valor de 2-3 s de conectividad y 30 s de lectura es un punto de partida razonable.

Ejercicio

  1. Monta el upstream de nginx de arriba con 3 réplicas de tu API (puede ser la misma imagen en 3 puertos) y verifica que las peticiones se reparten.
  2. Detén un contenedor a la vez: ¿las peticiones siguen funcionando? ¿cuánto tardan en venir de otro nodo? Ajusta timeouts y health checks para que sea inmediato.
  3. Abre los stats de HAProxy (o los acces logs de nginx) y confirma con tu prueba de carga que el reparto es parejo entre los nodos cuando todos están sanos.

Resumen

  • Un load balancer reparte peticiones entre réplicas y aísla los nodos enfermos.
  • Round-robin es simple; least-connections reparte mejor cuando las peticiones duran distinto.
  • Los pesos igualan la asimetría entre máquinas; el sticky/IP-hash es una muleta, no una solución.
  • nginx: configuración por upstream; HAProxy: health checks activos y stats en vivo.
  • Los timeouts cortos convierten un nodo colgado en un nodo apartado rápido.
  • El complemento ideal del estado compartido viene de la lección anterior: ser stateless.
