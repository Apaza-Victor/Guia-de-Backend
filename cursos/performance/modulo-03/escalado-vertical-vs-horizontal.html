Escalado vertical vs horizontal

🚀 Avanzado 9 min Performance Backend Módulo 3 · Escalabilidad y despliegue

Introducción

Cuando el servicio ya no da para todo el tráfico tienes dos caminos. El escalado vertical compra más recursos para la misma máquina: más CPU, más RAM, un disco más rápido. El escalado horizontal añade máquinas: un segundo (o vigésimo) nodo que reparte el trabajo con el anterior. Ambos son legítimos; la gracia es saber cuál necesitas en cada momento.

Y hay una condición que decide todo: si el servicio guarda estado en sus procesos, no puedes escalar horizontal simplemente. Esta lección empieza por ahí.

Escalado vertical: el arreglo rápido

Subir de 4 GB a 16 GB de RAM, de 2 vCPU a 8 vCPU, o moverte a un disco NVMe. Ventajas: no tocas el código, no cambia la operación, y funciona de inmediato para servicios con un cuello de botella de recursos (CPU o memoria). Desventajas: tiene un tope físico y económico —no existe una máquina infinita, y además son carísimas— y no aporta tolerancia a fallos: si la máquina cae, cae todo.

En la práctica, el escalado vertical es el punto de partida razonable (un solo nodo sano aguanta mucho) y la respuesta cuando el problema es claramente CPU-local en un solo proceso (visto en «cuellos de botella»). Pero llega un tráfico y un momento donde comprar RAM deja de ser la jugada.

Regla práctica: si escalando vertical tu prueba de carga mejora hasta el nivel del presupuesto, sigue vertical. El día que la RAM pedida equivalga al coste de dos o más nodos, cambia de estrategia.

Escalado horizontal: más nodos

En vez de un nodo gigante, tres nodos medianos detrás de un balanceador (siguiente lección). Ventajas: crecimiento casi ilimitado, tolerancia a fallos (si uno cae, los otros siguen) y despliegues sin ventana de mantenimiento. Desventajas: la operación se complica (balanceo, métricas distribuidas, monitoreo) y obliga a que el código no dependa de «la máquina concreta».

Con Docker Compose, pasar de 1 a 3 réplicas de la API es un comando:

# docker-compose.yml (fragmento)
# services:
#   api:
#     build: ./app
#     ports: ["8080:8080"]     # el balanceador reparte detrás

# Escalar la API a 3 réplicas (misma imagen, mismos datos)
docker compose up --scale api=3 -d

# En orquestadores (Kubernetes) es igual de mecánico:
# kubectl scale deployment api --replicas=3

El truco del comando es que «funcione» oculta el trabajo real: las 3 réplicas deben hablar con la misma caché, la misma BD y atender cualquier petición sin importar a cuál caiga.

La condición: servicios stateless

Un servicio es stateless cuando no guarda en su proceso nada que se necesite en la siguiente petición: sesiones, contadores, archivos subidos, objetos en memoria. Si dos réplicas distintas de la misma API atienden las dos mitades de una conexión y cada una tiene su propio estado, es un desastre anunciado.

La respuesta canónica: todo estado va a la caché/BD compartida (Redis para sesiones y contadores, object storage para archivos) y el proceso queda limpio y reproducible. Un token JWT firmado por cualquiera de las réplicas es memorable: la sesión vive en el token, no en el proceso.

// MAL: la sesión vive en memoria del proceso; la réplica B no la conoce
const sesiones = new Map();
app.post('/login', (req, res) => {
  sesiones.set(req.body.token, { usuario: req.body.usuario, exp: Date.now() + 3600000 });
  res.json({ ok: true });
});
app.get('/perfil', (req, res) => {
  const s = sesiones.get(req.headers.authorization);
  if (!s || s.exp < Date.now()) return res.status(401).end();
  res.json({ usuario: s.usuario });   // falla si esta petición cae en otra réplica
});

// BIEN: sesión autocontenida y verificable por cualquier réplica (JWT)
const jwt = require('jsonwebtoken');
const FIRMA = process.env.FIRMA_JWT;          // clave compartida por todas las réplicas
app.post('/login', (req, res) => {
  const token = jwt.sign({ usuario: req.body.usuario }, FIRMA, { expiresIn: '1h' });
  res.json({ token });
});
app.get('/perfil', (req, res) => {
  const token = (req.headers.authorization || '').replace('Bearer ', '');
  try { res.json({ usuario: jwt.verify(token, FIRMA).usuario }); }
  catch { res.status(401).end(); }            // cualquier réplica valida el token
});

Revisa tu lista mental de estado: sesiones en memoria, upload/files en disco local, contadores con let contador++… todos son obstáculos al escalado horizontal.

Cuando el estado no cabe en un token (grande, revocable, temporal), la herramienta es Redis: las réplicas comparten la misma sesión sin guardarla en su proceso:

import redis

# Redis compartido: TODAS las réplicas leen y escriben la misma sesión
cache = redis.Redis(host="redis-compartida", port=6379, decode_responses=True)


def iniciar_sesion(usuario_id: int, datos: dict) -> str:
    import secrets
    token = secrets.token_hex(16)
    clave = f"sesion:{token}"
    cache.hset(clave, mapping={"usuario_id": usuario_id, **datos})
    cache.expire(clave, 3600)          # sesión de 1 hora, muerta sola
    return token


def obtener_usuario_de(token: str) -> dict | None:
    datos = cache.hgetall(f"sesion:{token}")   # funciona desde CUALQUIER réplica
    return datos or None

¿Y los datos? Ese es otro escalado

Escalar la API horizontal es relativamente fácil; escalar la base de datos no lo es (lección «bases de datos a escala»). El momento crítico llega cuando 10 réplicas de la API golpean a UNA base de datos: tu nuevo cuello de botella será la BD. La secuencia natural es: primero caché (para quitar lecturas), luego réplicas de lectura y particionado, y solo después añadir API nodes.

Ejercicio

  1. Levanta tu servicio en un contenedor y enrólalo en Compose o Kubernetes con 3 réplicas. Prueba a hacer login y navegar: ¿funciona? Si algo se rompe, ese algo es tu estado local.
  2. Audita el estado de tu aplicación: sesiones, archivos, contadores en memoria. Lista cada uno y decide dónde debería vivir (Redis, object storage, JWT).
  3. Decide (con tu prueba de carga): ¿estás en el momento vertical (recursos locales) o en el horizontal (varios nodos)? Razona la respuesta con los datos del módulo 1.

Resumen

  • Vertical: más recursos en la misma máquina; rápido, simple, sin código que tocar, pero con tope y sin tolerancia a fallos.
  • Horizontal: más nodos detrás de un balanceador; escala casi infinito y sobrevive a fallos operacionales.
  • La condición del horizontal es ser stateless: todo estado vive en caché/BD/almacenamiento compartido, no en el proceso.
  • Los tokens firmados (JWT) y redis son las herramientas típicas para quitar estado al proceso.
  • El cuello de botella siguiente al escalar nodos es la base de datos: por eso el orden es caché → BD a escala → más nodos.
  • Lo siguiente es repartir el tráfico: load balancing.
