Redis Streams: el log de eventos

🔥 Avanzado 13 min Redis y Caching Módulo 6 · Colas y streaming

Introducción

Pub/Sub evapora los mensajes y las lists entregan una sola vez. Para eventos con historial, relectura y consumidores grupales nace Redis Streams: un log append-only donde cada entrada tiene un ID, se puede leer desde cualquier punto y ningún evento se pierde.

Streams combina lo mejor: velocidad de Redis, persistencia opcional, IDs monótonos y consumo replayable. Es la pieza que convierte Redis en un bus de eventos ligero.

Definición

Redis Streams es una estructura de log de eventos: XADD añade entradas con ID autoincremental, XREAD las lee desde un punto y XRANGE permite consultar rangos por ID o tiempo.

Por qué importa. Da durabilidad (los eventos persisten), orden global y capacidad de relectura: ideal para auditorías, déficits... eventos productivos y estado reconstructo.

Cuándo usarlo. Úsalo cuando necesites 'qué pasó antes' o varios consumidores procesando el mismo evento. Para notificación efímera sigue con Pub/Sub.

Conceptos clave

  • XADD crea una entrada con ID y campos: el log crece append-only.
  • El ID es unix-milliseconds-secuencia, monótono y ordenable.
  • XREAD lee desde el primer evento no leído o desde un ID dado.
  • XREADCOUNT … permite lotes de lectura por grupo.
  • XTRIM recorta el log a un tamaño máximo (MAXLEN) para acotar memoria.

Ejemplo básico

Registramos eventos de pedido en un stream y los leemos desde el principio.

1758700000000-0
1758700000000-0 {'estado': 'creado', 'pedido': 'p-1'}
1758700000001-0 {'estado': 'pagado', 'pedido': 'p-1'}

Ejemplo intermedio

Leemos solo los eventos nuevos desde el último ID leído por el consumidor.

Ejemplo real

Una app de pedidos registra cada transición de estado en un stream. El equipo reconstruye el historial completo de un pedido con XRANGE y, si falla un job de facturación, reprocesa desde el ID que sangró.

  • Fija MAXLEN e IDTRIM para que el log no crezca infinito.
  • Usa XREVRANGE para leer las historias más recientes primero.
  • Los IDs permiten 'leer desde donde se quedó', base del replay.

Con MAXLEN ~ 100000 tienes un buffer de eventos reciente sin consumir RAM.

Explicación

  • El ID garantiza orden total: cualquier consumidor ve la misma secuencia.
  • XADD es O(1) respecto a la longitud del stream.
  • XRANGE acepta rangos de IDs y rangos temporales (unix-ms).
  • XREAD con block bloquea hasta nuevo evento: evita polling.
  • Los streams de Redis no se borran solos: XTRIM o MAXLEN los acotan.

Errores comunes

  • XNACK o XCLAIM antes de grupos: errores por usar comandos de consumer group mal.
  • Encadenar eventos enormes en campos numerosos: streams con grandes payloads consumen RAM.
  • Ignorar el ID máximo de lectura y reprocesar de cero en cada despliegue.

Buenas prácticas

  • Usa XADD con * para que Redis genere el ID automáticamente.
  • Prueba XREAD block para reemplazar polling de procesos.
  • Agrupa campos con estructura plana en el hash del evento.
  • Establece MAXLEN en producción antes de que el log explote de memoria.

Ejercicio

  1. Crea un stream de eventos de usuario y añade 5 eventos.
  2. Lee un rango de eventos entre dos IDs con XRANGE.
  3. Prueba XTRIM a MAXLEN 3 y verifica qué entradas quedan.

Resumen

  • Redis Streams es un log append-only con IDs monótonos e historial.
  • XADD, XREAD y XRANGE cubren escritura, consumo y consulta.
  • MAXLEN/XTRIM controlan la memoria del flujo de eventos.
