Sesiones en Redis

🔥 Avanzado 10 min Redis para Backend Módulo 3 · Caché

El problema de las sesiones en memoria

Si la sesión vive en la RAM de una instancia, el balanceador puede mandar la siguiente petición a otra instancia… y el usuario queda deslogueado. Redis centraliza las sesiones: cualquier instancia lee la misma sesión.

Modelo: sesión como hash con TTL

El token es un string aleatorio (opaco) que viaja en la cookie. El servidor nunca guarda datos de usuario en la cookie: solo el identificador.

Implementación Python

Seguridad: guarda también un hash del user-agent y la IP. Al cargar la sesión compara: si cambia de golpe, revócala (posible token robado).

Redis vs JWT

  • JWT: sin estado en el servidor, pero no puedes revocarlo en el acto (a menos que añadas lista negra).
  • Sesión en Redis: estado centralizado, revocable, y el payload no viaja al cliente (menos expuesto).
  • Híbrido habitual: JWT de corta vida como acceso + sesión/refresh en Redis para renovar y revocar.

Ejercicio

  1. Implementa crear/cargar/cerrar sesión con expiración deslizante.
  2. Añade la revocación de todas las sesiones de un usuario.
  3. Compara en una tabla JWT vs sesión en Redis para: revocar, escalar, exponer datos.

Resumen

  • Sesión = hash session:<token> + TTL deslizante.
  • Redis permite escalar horizontalmente sin perder logins.
  • La revocación es borrar una clave: instantáneo.
  • JWT y sessions conviven: token corto + refresh revocable.
