Replicación y réplicas de lectura

🔥 Avanzado 11 min Redis y Caching Módulo 5 · Persistencia y alta disponibilidad

Introducción

Un única instancia de Redis termina por saturarse: todas las lecturas compiten con las escrituras en el mismo hilo. La solución clásica es replicar: un maestro acepta escrituras y varias réplicas sirven lecturas.

La replicación también te protege: si el maestro cae, promueves una réplica y el sistema sigue sirviendo. Es la base de cualquier despliegue con alta disponibilidad.

Definición

REPLICAOF hace que una instancia copie exactamente el dataset de otra (el maestro) y aplica el mismo stream de escrituras en tiempo real.

Por qué importa. Separa carga de lectura en nodos dedicados, reduce la presión del maestro y habilita failover sin downtime.

Cuándo usarlo. Úsala para escalar lecturas, dar tolerancia a fallos o preparar Sentinel. No la uses para escrituras distribuidas: Redis no soporta multi-master.

Conceptos clave

  • El maestro acepta consultas de escritura (roles=master).
  • Las réplicas se conectan con REPLICAOF host puerto.
  • La sincronización inicial copia el RDB y después aplica el backlog.
  • el maestro responde solo lecturas cuando replica=only-read.
  • Replica -fugitiva sirve para endpoints... usa wait para durabilidad síncrona.

Ejemplo real

Un sistema de reportes lee de una réplica dedicada para no competir con el tráfico productivo del maestro, y por la noche la réplica se usa para backups pesados sin ralentizar las APIs.

  • Dirige las lecturas de informes y analítica hacia las réplicas.
  • Nunca escribas en una réplica: su dataset se sobrescribe en resync.
  • Alertas en master_link_status=down disparan el failover.

Replica de lectura no es alta disponibilidad por sí sola: sin Sentinel, la réplica no asciende sola.

Explicación

  • La replicación copia el RDB maestro en el arranque (full sync) y después aplica el buffer de comandos.
  • PSYNC permite sincronización parcial si el backlog sigue disponible.
  • Las réplicas propagan sus propias réplicas: se pueden encadenar topologías.
  • master_repl_offset mide dónde está cada nodo en el stream de escrituras.
  • wait permite a un cliente esperar que N réplicas persistan una escritura (durabilidad síncrona).

Errores comunes

  • Escribir en réplicas en modo read-only produce errores READONLY.
  • Considerar la replicación un backup: replica sola no protege contra errores humanos (DEL masivo).
  • Cambiar la topología en caliente sin verificar el backlog pierde datos intermedios.

Buenas prácticas

  • Configura un ID único por maestro (replica-announce-ip) en entornos con NAT.
  • Monitorea master_link_status y repl_backlog_histlen.
  • Usa réplica preferida para BGSAVE y backups cuando el maestro sufre picos.
  • Documenta el failover manual con replicaof no one antes de automatizar.

Ejercicio

  1. Levanta dos Redis en puertos distintos y conecta la segunda como réplica.
  2. Crea una clave en el maestro y léela desde la réplica.
  3. Promueve la réplica y comprueba que sigue respondiendo lecturas.

Resumen

  • REPLICAOF replica el dataset completo en tiempo real.
  • Las réplicas escalan lecturas y son la base del failover.
  • Sin Sentinel o manual de promoción, no hay alta disponibilidad real.
