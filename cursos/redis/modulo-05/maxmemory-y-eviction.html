maxmemory y políticas de desalojo

🔥 Avanzado 10 min Redis y Caching Módulo 5 · Persistencia y alta disponibilidad

Introducción

Redis guarda todo en RAM, y la RAM es finita y cara. Si un developer dispara un loop que genera claves sin TTL, la memoria se agota y Redis comienza a fallar: las escrituras llenan el sistema de latidos.

La configuración maxmemory define un techo y la política de desalojo (eviction-policy) indica qué claves sacrificar primero. Elegir bien la política salva el servicio; elegir mal, entierra el caché.

Definición

maxmemory fija el límite de RAM del dataset; maxmemory-policy decide el conjunto de claves a evictar cuando se alcanza (LRU, LFU, random, noeviction).

Por qué importa. Sin techo, Redis puede consumir el host entero y caer con OOM killer. Con política, el sistema degrada el caché de forma controlada en vez de reventar.

Cuándo usarlo. Define maxmemory en 60-80% de la RAM del servidor y usa políticas según el uso: allkeys-lru para caché, volatile-lru para datos con TTL, noeviction para colas que no deben perderse.

Conceptos clave

  • maxmemory en bytes (o mb/gb) fija el tope del dataset.
  • volatile-lru desaloja las claves con TTL menos recientes.
  • allkeys-lru desaloja cualquier clave no usada recientemente.
  • noeviction devuelve error a escrituras cuando se llena.
  • LFU (allkeys-lfu) descarta las menos frecuentes, no solo las menos recientes.

Ejemplo real

Un portal de noticias usa Redis de cache-aside. Configuran allkeys-lru con 512 MB y observan como, en picos, las claves menos leídas caen mientras las populares siguen en memoria: el hit rate se mantiene alto sin intervención humana.

  • Empieza con allkeys-lru para caché y checkea el hit rate.
  • Mide evicted_keys: eviction alta indica que tu caché es pequeña.
  • Protege las colas de trabajo con noeviction o datasets separados.

Para claves concretas es mejor no evictar, marca TTL: separa el caché del estado crítico.

Explicación

  • LRU aproximado (sampling) no escanea toda la memoria: evalúa pocos candidatos por muestra.
  • volatile-* solo ataca claves con expiración: las que no expiran se quedan.
  • LFU cuenta frecuencias de acceso y entierra claves que raramente se piden.
  • noeviction convierte la escritura en error OOM: útil para colas y contadores de negocio.
  • El hit rate y evicted_keys son las dos métricas para calibrar el techo.

Errores comunes

  • Usar noeviction en caché de HTTP y llenar la cola hasta bloquear escrituras.
  • Poner maxmemory mayor que la RAM del host: el kernel OOM-kill pega primero.
  • Despreciar los bytes de overhead: 80% de RAM es un techo realista, no 100%.

Buenas prácticas

  • Configura maxmemory desde config_set en desarrollo y desde redis.conf en los nodos.
  • Supervisa used_memory, maxmemory y evicted_keys en tu monitor.
  • Para estado crítico (carritos, trabajos) usa otra instancia con noeviction.
  • Combínalo con TTL agresivo para que la eviction sea la excepción, no la norma.

Ejercicio

  1. Pon maxmemory a 1 mb y añade 1000 claves: observa evicted_keys crecer.
  2. Compara allkeys-lru vs allkeys-lfu con un acceso sesgado a pocas claves.
  3. Prueba noeviction y captura el error OOM escribiendo al límite.

Resumen

  • maxmemory pone un techo a la RAM y la política decide qué se sacrifica.
  • allkeys-lru es el encaje natural para cachés; noeviction para estado crítico.
  • Monitoriza evicted_keys y el hit rate para calibrar el límite.
