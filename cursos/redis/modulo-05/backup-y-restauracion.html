Backup y restauración

🔥 Avanzado 10 min Redis y Caching Módulo 5 · Persistencia y alta disponibilidad

Introducción

La persistencia evita perder memoria, pero un disco roto, un error humano o un borrado masivo hacen que el RDB y el AOF tampoco sirvan si no los has copiado fuera del nodo. Un backup de Redis es tan importante como el de la base de datos.

La estrategia es sencilla: generar volcados con BGSAVE desde una réplica (para no cargar al maestro), copiarlos a un almacenamiento externo y probar restaurarlos de forma periódica.

Definición

Un backup de Redis es una copia del archivo RDB (y opcionalmente del AOF) fuera del nodo, que permite reconstruir el dataset tras una pérdida total.

Por qué importa. Replica, Sentinel y RDB/AOF protegen contra caídas, pero ningún mecanismo interno sobrevive a un borrado accidental o a la destrucción del servidor.

Cuándo usarlo. Hazlo siempre que el dataset tenga valor residual; con un SLA de recuperación definido (RTO) y objetivo de pérdida (RPO) claro.

Conceptos clave

  • Concatena BGSAVE + copia del dump.rdb: snapshot consistente.
  • Realiza backups desde réplicas para no golpear al maestro.
  • El RTO (tiempo de recuperación) y RPO (pérdida máxima) definen cuánto backup necesitas.
  • PRUNE (LIMIT) política: cuántos snapshots conservar y cuánta antigüedad.
  • Prueba de restauración: el único test que garantiza que el backup sirve.

Ejemplo básico

Generamos un snapshot desde la réplica y lo copiamos al directorio de backups.

backup creado: /backups/redis/dump-2026-09-24.rdb

Ejemplo intermedio

Restauramos: detenemos redis, sustituimos el RDB y arrancamos de nuevo.

Ejemplo real

Un operador programó cada noche una copia del RDB de la réplica a un bucket S3 con retención de 14 días. Ante un borrado masivo de claves a las 3:00 AM, restauró el snapshot de las 00:00 y el equipo perdió solo 3 horas de datos.

  • Respeta el mismo directorio/dir del archivo de config al restaurar.
  • Verifica la versión de Redis del backup frente al servidor destino.
  • Documenta el runbook: pasos exactos y responsables.

Si el servicio duplica el tráfico, prepara un AOF restaurado con redis-check-aof antes del pico.

Explicación

  • Un backup desde réplica evita el fork pesado del BGSAVE en el maestro.
  • El snapshot es consistente: se toma de un punto en el tiempo aunque el RDB se escriba en segundo plano.
  • Para RPOs mínimos combina el RDB nocturno con AOF del mismo nodo replicado.
  • Restaurar en una instancia limpia es más seguro que reemplazar el RDB de un nodo vivo.
  • Borra con cuidado el AOF al restaurar solo desde RDB: puede sobrescribir el snapshot.

Errores comunes

  • Copiar el RDB mientras se escribe (sin BGSAFE) deja un archivo corrupto.
  • Restaurar un RDB de versión de Redis superior en una inferior falla.
  • Olvidar la copia externa: RGSAVE en el mismo disco no protege de un fallo de disco.

Buenas prácticas

  • Automatiza con cron o en tu pipeline de CI: un backup manual se olvida.
  • Cifra y limita los accesos al bucket de backups.
  • Ejecuta una restauración de prueba trimestral y anota el tiempo real.
  • Mantén al menos 2 copias: una en disco local y otra remota.

Ejercicio

  1. Programa BGSAVE desde una réplica y copia el RDB a /backups.
  2. Simula un borrado masivo y restaura desde el snapshot.
  3. Ajusta la retención a 14 días y comprueba la purga automática.

Resumen

  • El RDB de una réplica es el origen ideal de backups externos.
  • Restaurar es copiar el snapshot al dir y arrancar: probarlo de verdad cuenta.
  • Define RPO/RTO y automatiza con retención para que nunca falte.
