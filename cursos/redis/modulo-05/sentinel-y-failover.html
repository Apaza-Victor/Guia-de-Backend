Sentinel y failover automático

🔥 Avanzado 12 min Redis y Caching Módulo 5 · Persistencia y alta disponibilidad

Introducción

Una réplica solo sirve si alguien decide promoverla cuando el maestro cae. Vigilar un proceso y tomar esa decisión es exactamente el trabajo de un agente supervisor: entre bambalinas, cada vuelta al mundo de Redis.

Redis Sentinel es el supervisor oficial: detecta caídas, elige una nueva réplica maestra, notifica a los clientes y reintenta el antiguo maestro como esclavo cuando vuelve. Con Sentinel, el negocio no depende de un humano despierto.

Definición

Sentinel es un proceso separado que vigila maestros y réplicas, declara caídas tras consenso entre quórum de Sents, promueve a una réplica y reconfigura a los clientes.

Por qué importa. Automatiza la recuperación ante fallos y convierte una topología manual en un sistema de alta disponibilidad de verdad.

Cuándo usarlo. Úsalo en producción desde una topología de 3+ réplicas. No lo uses en local o para un solo nodo: añade complejidad sin beneficio.

Conceptos clave

  • Sentinel vigila el maestro con sentinel monitor.
  • El quórum es el número mínimo de Sents para declarar caída (consenso).
  • down-after-milliseconds define cuánto esperar antes de sospechar.
  • failover-timeout controla el tiempo para completar la promoción.
  • Los clientes se conectan a Sentinel con sentinel get-master-addr-by-name.

Ejemplo básico

Configuración mínima de un Sentinel en /etc/redis/sentinel.conf.

sentinel monitor: mymaster 127.0.0.1 6379 2

Desde Python consultamos quién es el maestro actual a través de Sentinel.

Ejemplo real

Un equipo operativo corre 1 maestro + 2 réplicas y 3 Sentinel. Al apagarse el maestro, Sentinel x quórum promueve una réplica en segundos y la app conecta sin tocar código.

  • Despliega Sentinel en hosts distintos para que el quórum sea significativo.
  • Fija el mismo nombre de servicio (mymaster) en todos los clientes.
  • Prueba el failover en staging antes de confiarlo a producción.

Sentinel es para alta disponibilidad, no para escalado de escritura: el maestro sigue siendo uno.

Explicación

  • Los Sents intercambian mensajes por el bus (puerto 26379) y eligen líder en caso de caída.
  • El quórum protege contra falsos positivos y comunicaciones particionadas.
  • Ni bien la réplica sube, Sentinel la reconfigura para que replique del nuevo maestro.
  • El antiguo maestro, al volver, se demote automáticamente y pasa a réplica.
  • Los clientes que usan sentinel.master_for siempre resuelven el rol actual.

Errores comunes

  • Correr todos los Sents en el mismo host anula el consenso si cruje la máquina.
  • Confundir quórum con majority de réplicas a integralidad de datos.
  • Omitir password en los Sents cuando el maestro tiene auth: la vigilia falla en silencio.

Buenas prácticas

  • Despliega un número impar de Sents (3, 5) para mayorías limpias.
  • Añade sentinel auth-pass para clústeres con contraseña.
  • Monitoriza los eventos +sdown, -sdown, +switch-master del log de Sentinel.
  • Combina sentinel con replicacion de lectura por DNS round-robin para ambientes red.

Ejercicio

  1. Levanta maestro + réplica + doble Sentinel en local y mata el maestro.
  2. Observa el failover y verifica el nuevo maestro en segundos.
  3. Conecta un cliente por Sentinel y verifica que resuelve el nuevo rol.

Resumen

  • Sentinel vigila, consensa y automatiza la promoción de maestros.
  • El quórum y los timeout controlan cuándo y cómo caer.
  • Con 2 réplicas y 3 Sents obtienes alta disponibilidad real de Redis.
