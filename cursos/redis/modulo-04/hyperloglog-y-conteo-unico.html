HyperLogLog: conteo único aproximado

🔥 Avanzado 11 min Redis y Caching Módulo 4 · Estructuras de datos avanzadas

Introducción

Contar cuántas visitas únicas tuvo una página, cuántos IP distintos realizaron login o cuántos tokens circulan es caro si guardas cada elemento. Guardar todos los únicos en un set puede terminar con la memoria de tu servidor.

HyperLogLog (HLL) estima la cardinalidad de un conjunto usando probabilidad: con solo 12 KB por clave obtienes un error menor al 1% sin importar si hay 1 millón o 1.000 millones de elementos.

Definición

HyperLogLog es una estructura probabilística que estima el número de elementos únicos añadidos con PFADD y lo lee con PFCOUNT, sin almacenar los elementos en sí.

Por qué importa. Permite responder preguntas de cardinalidad (visitantes únicos, dispositivos distintos) sobre volúmenes enormes con memoria constante y operaciones O(1).

Cuándo usarlo. Úsalo cuando necesites conteos de únicos aproximados y te sobre la memoria. No lo uses si necesitas el valor exacto o recuperar los elementos, para eso hay sets y bloom filters.

Conceptos clave

  • PFADD añade uno o varios elementos a la aproximación.
  • PFCOUNT devuelve la cardinalidad estimada de una o varias claves.
  • PFMERGE fusiona varias HLL en una sin recalcular desde cero.
  • El error estándar es 0,81%, ajustable por parámetro.
  • No guarda los elementos originales: no puedes listarlos después.

Ejemplo real

Un producto de analítica contabiliza usuarios únicos por día y por país a partir de eventos de varios servidores. Cada servidor aporta su HLL parcial y un worker las fusiona cada hora.

  • Ten una clave HLL por shard y usa PFMERGE para el total.
  • Acota el periodo con TTL para no acumular claves olvidadas.
  • No uses HLL para auditorías: no permite reconstruir la lista de elementos.

Si necesitas conteos exactos sobre millones, HLL no sirve; ahí entran los bloom filters que verás combinados con estas estructuras.

Explicación

  • HLL estima por la longitud de la racha de ceros iniciales en los hashes de los elementos (la calcular de Cardinalidad de Flajolet).
  • PFCOUNT es O(1) si la clave cabe en cache y no hay fusión pendiente.
  • Añadir el mismo elemento varias veces no incrementa la estimación (es un set lógico).
  • 12 KB fijos por clave: el coste de memoria no crece con el número de elementos.
  • Varias claves sumadas con PFCOUNT devuelven estimaciones peores que PFMERGE previo.

Errores comunes

  • PFCOUNT con muchas claves a la vez recalcula fusión en cada llamada: caro.
  • Esperar exactitud: el resultado es una estimación, no un conteo SQL.
  • Añadir elementos y esperar poder recuperarlos: HLL no conserva los datos.

Buenas prácticas

  • Usa HLL para métricas de negocio diarias y deja exactitud solo donde la ley lo exige.
  • Prefiere claves cortas con periodo para mantener un bajo número de HLL activas.
  • Valida contra un set en desarrollo para conocer el error real de tu caso.
  • Combínalo con bitmaps: HLL para únicos globales, bitmap para rachas.

Ejercicio

  1. Cuenta usuarios únicos de una lista de 20 con duplicados y compara con len(set()).
  2. Crea HLL diarias y fusiona la semana en una clave semanal.
  3. Repite el conteo con sets y mide la diferencia de memoria en INFO.

Resumen

  • HLL estima cardinalidades con error <1% usando 12 KB constantes.
  • PFADD, PFCOUNT y PFMERGE cubren conteo, consulta y agregación.
  • Es la opción correcta para únicos a escala masiva sin memoria infinita.
