Scripts Lua en Redis

🔥 Avanzado 12 min Redis y Caching Módulo 4 · Estructuras de datos avanzadas

Introducción

Cuando una operación necesita varios comandos con lógica condicional, las transacciones no bastan: un saldo que no debe bajar de cero, un token con reintentos, un límite con ventana deslizante. Meter la decisión en la app abre carreras imposibles de depurar.

Redis ejecuta scripts Lua en el servidor de forma atómica: EVAL recibe el código y las claves desde el cliente, y todo corre del primer al último comando sin interrupciones.

Definición

EVAL (y EVALSHA) ejecutan un script Lua en el servidor de forma atómica y con acceso directo a los comandos Redis mediante la tabla KEYS y ARGV.

Por qué importa. Mover la lógica al servidor elimina carreras y red: una sola llamada atómica en lugar de varias con reintentos (WATCH) en la app.

Cuándo usarlo. Úsalo cuando la invariante exija leer y escribir con lógica condicional (límites, depósitos, swaps). No lo uses para lógica pesada de CPU prolongada: bloquearía Redis.

Conceptos clave

  • EVAL recibe el script, el número de claves y las claves/argumentos.
  • Las claves van en KEYS y los parámetros en ARGV.
  • redis.call devuelve errores reales; redis.pcall los captura para manejarlos.
  • EVALSHA evita reenviar el script usando su SHA1 tras SCRIPT LOAD.
  • Los scripts son atómicos: ningún otro cliente se intercala mientras corren.

Ejemplo básico

Un contador que solo se incrementa si no supera un máximo: límite atómico en una línea.

Ejemplo intermedio

Un swap atómico entre dos saldos que valida fondos dentro del servidor.

Ejemplo real

Un servicio de tokens por hora usa un script para incrementar el contador del usuario y aplicar expiración deslizante en una sola operación, recortando el abuso sin trabajo de retry en la app.

  • Usa EVALSHA en caliente: carga el script con SCRIPT LOAD y llama por SHA.
  • Valida datos antes con redis.pcall para devolver errores limpios.
  • Mantén los scripts en archivos y súbelos en el arranque del servicio.

Desde Redis 7 puedes usar funciones (FUNCTION LOAD) para gestionar scripts versionados en el propio servidor.

Explicación

  • La cola completa del script se ejecuta de forma ininterrumpida por el único hilo de Redis.
  • KEYS y ARGV no deben interpolarse: siempre se pasan por separado para evitar inyección.
  • Debes declarar cuántas claves consume el script como primer argumento de EVAL.
  • Los scripts largos o con bucles infinitos congelan Redis: son síncronos.
  • EVALSHA requiere cargar el script primero; si el SHA no existe devuelve NOSCRIPT y debes reenviarlo.

Errores comunes

  • Concatenar valores dentro del script con string.format('KEYS[%d]') rompe el reparto de claves.
  • Buis diarias manejadas con GET fuera del script reintroducen carreras.
  • Scripts que hacen red o esperas (sleep) bloquean a todos los clientes.

Buenas prácticas

  • Empieza con EVAL para prototipar y migra a EVALSHA o funciones al pasar a producción.
  • Escribe logs con redis.log para depurar sin romper el script.
  • Acota el script a operaciones de pocas claves: cuantos más KEYS, menos se escala en cluster.
  • Haz tests sobre una instancia aislada: un bug en Lua no se ve hasta producción.

Ejercicio

  1. Implementa un rate limiter de ventana fija por hora con Lua.
  2. Crea un script que solo entregue un cupón si el contador no llegó a 10.
  3. Convierte el swap en una función de Redis y llámala por nombre.

Resumen

  • Lua permite ejecutar lógica condicional atomically dentro de Redis.
  • KEYS y ARGV, redis.call y EVALSHA son los bloques esenciales.
  • Son la herramienta definitiva para invariantes multi-comando y rate limiting fino.
