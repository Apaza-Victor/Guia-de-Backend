Integración completa con el backend

🔥 Avanzado 12 min Redis y Caching Módulo 7 · Redis en producción

Introducción

Llegamos al final del camino: Redis ya no es un 'bonus', es una pieza central. Un backend de tráfico alto combina caché-aside para lecturas, sesiones persistentes, rate limiting contra abusos y una cola de tareas de segundo plano, todo sobre el mismo Redis o un clúster.

Esta lección junta las piezas vistas en el curso: el objetivo es que veas cómo ensamblar tus propias APIS con Redis como columna vertebral de memoria y eventos.

Definición

Una arquitectura típica de backend con Redis estructura el estado en particiones de claves (cache:, sesiones:, rl:, queues:) y aplica patrones (cache-aside, TTL, locks, rate limiting) por dominio con el mismo cliente.

Por qué importa. Reduce dramáticamente la latencia media, desacopla el trabajo pesado y permite escalado horizontal con un single source of truth en memoria.

Cuándo usarlo. Adopta este nivel de integración cuando la API mida en p95 altos o la base de datos sufra de carga de lectura; no lo hagas antes de tener un stack funcional.

Conceptos clave

  • Una convención de prefijos organiza los dominios: cache:*, sesiones:*, rl:*, colas:*.
  • Cache-aside + TTL + locks cubren las lecturas calientes.
  • Las sesiones en Redis se leen en todos los pods: estado distribuido real.
  • Rate limiting con INCR+EXPIRE y ventana fija/deslizante.
  • Las colas con BLPOP o Streams mueven el trabajo pesado fuera de la request.

Ejemplo básico

Un endpoint de perfil lee de caché, rellena desde BD en miss y tiene sesión compartida.

perfil: {"nombre": "ana"} | uid: 7

Ejemplo intermedio

Middleware de rate limiting por IP con ventana fija y bloqueo de abuso.

Ejemplo real

Una API de e-commerce: catálogo en caché, carrito en sesiones, límites de compra por usuario y generación de facturas en cola. La base de datos aguanta solo el CRUD esencial; el resto vive en Redis y las facturas salen en background.

  • Netea los TTL del caché contra la volatilidad de cada dato.
  • Mantén las escrituras del carrito en la BD original para consistencia.
  • Escala réplicas de lectura para el caché y el rate limit global.

En alta escala separa dominios en instancias distintas (caché vs colas) para aislar perfiles de acceso.

Explicación

  • El prefijo en las claves permite ACLs y rastreo por dominio.
  • Cache-aside con TTL por dato equilibra frescura y coste de regeneración.
  • Sesiones en Redis con expiración automática evitan el tedioso logout de limpieza.
  • Rate limiting atómico con INCR+EXPIRE no necesita transacciones.
  • Colas y Streams desacoplan la peor latencia del flujo principal de la API.

Errores comunes

  • Mezclar dominios en una misma clave sin prefijo: colisiones y ACGs rotos.
  • Codificar toda la lógica de negocio en Redis y olvidar que la BD es la fuente de verdad.
  • No vigilar el TTL de las sesiones y acumular registros muertos en memoria.

Buenas prácticas

  • Diseña un mapa de claves (keymap) documentado antes de codificar.
  • Da jerarquía con ':' y ordena por dominio: cache:perfil:7.
  • Centraliza el cliente Redis (singleton) y reutilízalo en todos los servicios.
  • Promete los tiempos: escribe métricas de hits/misses y latencia por operación.

Ejercicio

  1. Implementa un endpoint con caché de 60s y sesión compartida entre dos 'pods'.
  2. Añade rate limiting por IP y por usuario mediante la misma primitiva.
  3. Mueve una tarea lenta (email) a una cola con BLPOP y verifica el desacople en la API.

Resumen

  • Un backend de producción combina caché, sesiones, límites y colas sobre Redis.
  • La convención de prefijos y los TTL por dominio mantienen el sistema ordenado.
  • Redis acelera la API y la protege, pero la BD sigue siendo la fuente de verdad.
