Probando APIs con curl

💻 Básico 11 min Fundamentos de Backend Módulo 6 · APIs y HTTP en la práctica

Introducción

Tu mejor amigo para comprobar que una API funciona es curl: hace peticiones HTTP reales desde la terminal y muestra cada respuesta tal cual.

Dominar curl te permite depurar endpoints, inspeccionar headers y automatizar comprobaciones sin abrir un navegador.

Definición

curl es una herramienta de línea de comandos que transfiere datos con protocolos de red, entre ellos HTTP, permitiéndote enviar peticiones completas y ver la respuesta en crudo.

Por qué importa. Antes de escribir tests automatizados necesitas ver qué devuelve tu API de verdad: curl te muestra status real, headers y cuerpo sin capas de abstracción.

Cuándo usarlo. Úsalo en desarrollo para probar endpoints, depurar errores, reproducir un bug reportado o enviar peticiones con autenticación.

Conceptos clave

  • curl URL hace una petición GET y muestra el cuerpo.
  • -i muestra también las cabeceras de respuesta.
  • -X METHOD fuerza un método concreto.
  • -H agrega cabeceras; -d envía datos en el body.
  • -o /dev/null -w nos deja ver solo el status code.

Ejemplo básico

La primera petición: un GET a una API pública y luego el mismo GET con cabeceras visibles.

HTTP/2 200
content-type: application/json; charset=utf-8
{
  "id": 1,
  "name": "Leanne Graham",
  ...
}

Ejemplo intermedio

Enviar datos en el body y comprobar solo el status code de la respuesta.

Ejemplo real

Al consumir APIs protegidas suele haber un paso previo: obtener un token y reutilizarlo en cada petición mediante un header de autorización.

  • Empieza con -i o -v para ver todo lo que viaja por la red.
  • Respeta el endpoint según el entorno: usa la URL correcta en cada entorno.
  • Guarda las respuestas a archivo con -o para inspeccionarlas después.

jq formatea el JSON y hace legible la salida; en Windows puedes instalarlo o usar PowerShell.

Explicación

  • Sin -X, curl usa GET o POST según haya datos con -d.
  • -d envía application/x-www-form-urlencoded por defecto; usa -H para indicar JSON.
  • -s silencia la barra de progreso y -w permite formatos de salida personalizados.
  • -v muestra el diálogo completo TLS/HTTP, oro puro para depurar.
  • En Windows, el escapado de comillas cambia; usa archivos con --data @archivo.json.

Errores comunes

  • Olvidar -H Content-Type: application/json y hacer que el servidor reciba texto plano.
  • Usar comillas simples dentro de comillas simples en PowerShell.
  • No escribir el JSON del -d como cadena válida y romper el body.
  • Pedir en producción datos que solo existen en local y recibir 404.

Buenas prácticas

  • Crea scripts .curl en tu repo para las peticiones recurrentes.
  • Empieza con GET y -i para ver el status real antes de debuggear el body.
  • Usa --silent --show-error para no perder errores entre el ruido.
  • Pasa credenciales por variables de entorno, nunca en el historial de la terminal.

Ejercicio

  1. Haz un GET a cualquier API pública y localiza el status en la respuesta.
  2. Crea un POST con JSON a jsonplaceholder y comprueba que responde 201.
  3. Repite una petición con -v y compara lo que ves con la versión sin -v.

Resumen

  • curl lanza peticiones HTTP reales y muestra la respuesta cruda.
  • Métodos, cabeceras y body se controlan con -X, -H y -d.
  • Ver el status code y las cabeceras acelera cualquier depuración.
