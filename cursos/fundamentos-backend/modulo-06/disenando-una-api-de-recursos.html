Diseñando una API de recursos

⚙️ Intermedio 12 min Fundamentos de Backend Módulo 6 · APIs y HTTP en la práctica

Introducción

Detrás de cada API bien mantenida hay una decisión de diseño: qué recursos existen, cómo se llaman y cómo se relacionan. Antes de escribir una sola línea de servidor, el contrato debe estar claro.

En este módulo vas a diseñar la API de una tienda: recursos, colecciones, identificadores y rutas anidadas, siguiendo las convenciones que usan los equipos de backend profesional.

Definición

Un recurso es una entidad (usuarios, pedidos, productos) que tu API expone mediante URLs consistentes y métodos HTTP estándar: la colección en plural y cada elemento con su identificador.

Por qué importa. Un buen diseño hace la API predecible: quien la consume sabe encontrar cualquier dato sin leer documentación a oscuras. Mal diseñada, cada endpoint es un mundo y el mantenimiento se dispara.

Cuándo usarlo. Usa recursos cuando hay entidades con CRUD; evítalo cuando solo expones operaciones o cálculos, que piden otra aproximación.

Conceptos clave

  • Los sustantivos en plural nombran colecciones: /usuarios, /pedidos.
  • Cada elemento se alcanza con su id: /usuarios/42.
  • Relaciones anidadas con sentido: /usuarios/42/pedidos.
  • snake_case en el payload JSON y kebab-case en las URLs.
  • Versiona en la URL: /v1/usuarios.

Ejemplo básico

Un mapa de rutas real para la colección de usuarios, expresado como estructura de datos.

POST /v1/usuarios -> crear_usuario GET /v1/usuarios/{id} -> obtener_usuario PUT /v1/usuarios/{id} -> actualizar_usuario DELETE /v1/usuarios/{id} -> eliminar_usuario

Ejemplo intermedio

Rutas anidadas con cabeza: usa solo las que aportan y evita enterrar demasiados niveles.

Ejemplo real

En un ecommerce real, el equipo define primero el contrato (una tabla de rutas o un OpenAPI sencillo) y solo después escribe el código del servidor.

  • Nombra recursos desde el dominio del negocio, no desde la base de datos.
  • Mantén el mismo estilo en todos los endpoints: la consistencia vale más que la creatividad.
  • Documenta ejemplos reales de respuesta junto a cada ruta.

Muchos frameworks generan las rutas a partir de estos nombres; un buen diseño inicial evita renombrar URLs (y romper clientes) más adelante.

Explicación

  • La URL identifica el recurso; el método HTTP expresa la acción sobre él.
  • Las colecciones en plural son el estándar de REST y de casi toda API pública.
  • Anida solo cuando la relación se lee con naturalidad: cliente a pedidos sí; pedidos a cliente suele ir como campo.
  • Versionar la API en la URL evita romper a los consumidores al evolucionar.
  • Un recurso no es una tabla: agrupa bajo él lo que tenga sentido de negocio.

Errores comunes

  • Mezclar singular y plural entre endpoints (a veces /usuario, a veces /users).
  • Anidar demasiado: /a/{id}/b/{id}/c/{id} en vez de aplanar con query params.
  • Cambiar la forma de una URL sin versionar: rompe a los clientes de golpe.
  • Nombrar recursos desde la base de datos en lugar del dominio.

Buenas prácticas

  • Define el contrato delante de todos antes de programar.
  • Usa siempre el mismo formato de error en todas las rutas.
  • Piensa primero en quien consumirá la API, no en tu base de datos.
  • Revisa APIs famosas (GitHub, Stripe) para aprender convenciones.

Ejercicio

  1. Diseña las rutas de una API de biblioteca (libros, autores, préstamos).
  2. Extiende construir_url para aceptar filtros como query con ?categoria=tech.
  3. Escribe la tabla de rutas de una API de música y critica dos rutas anidadas.

Resumen

  • Los recursos se nombran en plural y se identifican por su id en la URL.
  • La URL identifica recursos; los métodos HTTP definen la acción.
  • Un contrato claro y consistente ahorra mantenimiento y rompe menos clientes.
