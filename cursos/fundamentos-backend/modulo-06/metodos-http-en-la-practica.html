Métodos HTTP en la práctica

⚙️ Intermedio 13 min Fundamentos de Backend Módulo 6 · APIs y HTTP en la práctica

Introducción

Ya sabes qué es HTTP; ahora toca lo que importa: usar cada método con intención. GET para leer, POST para crear, PUT y PATCH para modificar y DELETE para borrar.

Un mismo recurso cambia de comportamiento según el método que reciba, y saber distinguirlos es lo que separa una API coherente de un caos.

Definición

Los métodos HTTP expresan la intención de una petición sobre un recurso: GET lee, POST crea, PUT reemplaza, PATCH modifica parcialmente y DELETE elimina.

Por qué importa. Los clientes (frontends, apps, otros servicios) confían en el significado de cada método para construir sus flujos; usarlos mal genera efectos inesperados y bugs difíciles de rastrear.

Cuándo usarlo. GET para operaciones que no alteran estado; POST para crear y disparar acciones; el resto según la semántica exacta de la operación.

Conceptos clave

  • GET es seguro: no debe cambiar el estado del servidor.
  • POST no es idempotente: dos llamadas crean dos recursos.
  • PUT reemplaza el recurso completo; PATCH modifica solo lo indicado.
  • DELETE elimina el recurso y normalmente responde 200 o 204.
  • OPTIONS y HEAD también existen: negocian capacidades y cabeceras.

Ejemplo básico

Un mini cliente que mapea cada método con su uso sobre una API.

crear en /v1/usuarios con {'nombre': 'Ana'}
leer /v1/usuarios/1
actualizar parcialmente /v1/usuarios/1 con {'rol': 'admin'}

Ejemplo intermedio

En el servidor, cada método responde de forma distinta al mismo recurso. Veamos el patrón con Express (Node).

Ejemplo real

Un error clásico: usar PUT para cambiar solo el email puede borrar el resto de los campos. La semántica de cada método protege tus datos.

  • GET nunca debe disparar efectos secundarios: los crawlers y arañas lo usan masivamente.
  • En POST responde 201 Created; en DELETE, 204 No Content.
  • Rechaza métodos no soportados con 405 Method Not Allowed.

La idempotencia de PUT y DELETE permite reintentar sin corromper el estado; POST, al no ser idempotente, requiere cuidado con los reintentos automáticos.

Explicación

  • Cada método comunica intención: legibilidad para humanos y semántica para máquinas.
  • PUT reemplaza todo el recurso; PATCH solo los campos enviados.
  • DELETE es idempotente: borrar un recurso ya borrado responde 404 en lugar de duplicar el efecto.
  • Los proxies y los cachés tratan los métodos según su definición: GET se cachea, POST no.
  • El anti-patrón de usar POST para todo pierde toda la semántica de HTTP.

Errores comunes

  • Usar GET para eliminar o crear recursos (rompe caché y seguridad).
  • Emplear POST donde corresponde PUT o PATCH y crear duplicados.
  • Responder 200 en vez de 201 o 204: los clientes no distinguen la acción realizada.
  • Mezclar PUT con PATCH y sobrescribir campos que no evolucionaron.

Buenas prácticas

  • Elige el status code que describa mejor la acción: 201 al crear, 204 al borrar.
  • Si dudas entre PUT y PATCH, pregúntate: ¿reemplazo el recurso o solo una parte?
  • Documenta la idempotencia de cada endpoint para que los clientes reintenten con seguridad.
  • Usa constantes para los métodos en tu código, nunca strings sueltos.

Ejercicio

  1. Implementa un contador con GET para leer, POST para sumar y explica por qué se duplican los incrementos.
  2. Traduce cinco operaciones de una tienda al método HTTP correcto.
  3. Comprueba con curl qué status devuelve tu API al repetir un mismo DELETE dos veces.

Resumen

  • GET lee, POST crea, PUT reemplaza, PATCH modifica y DELETE elimina.
  • La semántica correcta protege cachés, clientes y la integridad de los datos.
  • Los status codes completan la historia: 201, 204, 404 o 405.
