REST y sus alternativas: GraphQL y gRPC

⚙️ Intermedio 12 min Fundamentos de Backend Módulo 6 · APIs y HTTP en la práctica

Introducción

REST domina el ecosistema, pero no es la única respuesta. Cuando los clientes piden datos muy variados o el volumen interno es enorme, aparecen GraphQL y gRPC.

Elegir bien el estilo de API depende del contexto: aquí verás qué resuelve cada uno y cuándo aplicarlo.

Definición

REST organiza recursos con URLs y métodos HTTP; GraphQL deja que el cliente pida exactamente los campos que necesita mediante un solo endpoint; gRPC llama a métodos remotos con contratos binarios muy eficientes.

Por qué importa. El transporte define la experiencia de tus clientes: elegir el protocolo adecuado reduce tiempo de carga, tráfico de red y complejidad de mantenimiento.

Cuándo usarlo. REST para APIs públicas e integraciones simples; GraphQL cuando hay muchos clientes con necesidades distintas; gRPC para comunicación interna entre microservicios con alto rendimiento.

Conceptos clave

  • REST: recursos, verbos HTTP y JSON; simple y universal.
  • GraphQL: un único endpoint /graphql y el cliente elige su esquema.
  • gRPC: define métodos en un .proto y usa HTTP/2 con mensajes binarios.
  • El overfetching de REST frente al control fino de GraphQL.
  • gRPC sobresale en latencia baja y streaming entre servicios.

Ejemplo básico

Un resumen ejecutable para comparar los tres estilos de una vez.

REST      -> recursos + metodos HTTP + JSON (API publica)
GraphQL   -> un endpoint, el cliente elige campos
gRPC      -> metodos remotos binarios sobre HTTP/2 (interno)

Ejemplo intermedio

GraphQL resuelve el overfetching: cada cliente pide solo lo que necesita en una sola petición.

Ejemplo real

En un sistema de microservicios, el equipo suele hablar internamente con gRPC y exponer al exterior una API REST (o GraphQL) que traduce las llamadas.

  • REST para el borde público y gRPC para la red interna.
  • GraphQL brilla en apps móviles con pantallas que necesitan datos muy distintos.
  • Empieza simple: REST hasta que duela; llega a GraphQL o gRPC cuando haya razón.

Los protocol buffers serializan de forma binaria: hasta diez veces más rápido que JSON en tráfico interno, ideal para streaming.

Explicación

  • REST triunfa por simplicidad: cualquier cliente con HTTP lo entiende.
  • GraphQL centraliza el esquema y evita versionar un endpoint por cada campo nuevo.
  • gRPC mejora rendimiento y tipado fuerte, pero es menos amigable para navegadores.
  • La complejidad se paga: GraphQL añade consultas peligrosas (recursión, N+1) y gRPC herramientas de depuración menos directas.
  • La decisión correcta depende del contexto, no de la moda: empieza por REST.

Errores comunes

  • Elegir GraphQL por moda sin necesidad real de su flexibilidad.
  • Usar gRPC en el borde público y complicar la vida a tus clientes.
  • No proteger GraphQL con límites de profundidad y abrirte a consultas abusivas.
  • Cambiar de estilo de API sin medir primero el coste de la migración.

Buenas prácticas

  • Mide primero: ¿hay overfetching real? ¿importa de verdad la latencia?
  • Mantén el contrato documentado en cualquier estilo (OpenAPI o schema de GraphQL).
  • Los microservicios internos se benefician de gRPC; las APIs públicas, de REST.
  • No mezcles estilos en la misma familia de endpoints sin una razón clara.

Ejercicio

  1. Escribe la consulta GraphQL para los cinco últimos pedidos con su cliente.
  2. Define un .proto con dos métodos para un chat.
  3. Enlista tres señales de que un proyecto debería adoptar GraphQL.

Resumen

  • REST es simple y universal; GraphQL da control fino de campos; gRPC da rendimiento.
  • El estilo se elige por contexto, no por moda.
  • Es habitual combinar: gRPC interno con REST o GraphQL público.
