Consumiendo APIs externas

⚙️ Intermedio 12 min Fundamentos de Backend Módulo 6 · APIs y HTTP en la práctica

Introducción

Tu backend rara vez trabaja solo: cobra a través de una pasarela, envía correos por un proveedor y geolocaliza usuarios mediante una API externa.

Consumir una API de terceros bien es tan importante como diseñar la tuya: respetar límites, paginar y tratar cada error.

Definición

Consumir una API externa es enviar peticiones a un servicio de otro equipo y transformar su respuesta en datos útiles para tu aplicación, respetando su contrato y sus límites.

Por qué importa. Casi todo producto de backend usa servicios externos, y hacerlo mal deriva en bloqueos por rate limit, datos inconsistentes y costes imprevistos.

Cuándo usarlo. Úsalo cuando necesites una capacidad que no debes construir (pagos, emails, mapas); evita depender de APIs frágiles para tareas que controlas mejor internamente.

Conceptos clave

  • Cada API externa tiene su propio contrato: lee la documentación primero.
  • El rate limit limita peticiones por ventana; superarlo bloquea temporalmente.
  • La paginación pide resultados en páginas; recórrelas todas para datasets completos.
  • Las API keys viajan en headers como Authorization o X-API-Key.
  • Los timeouts evitan que tu backend se quede colgado si el externo falla.

Consumir una API con la librería requests de Python y manejar la posible falta de datos.

Ejemplo real

Patrón robusto para producción: timeout, reintentos con backoff exponencial y respuesta degradada si el externo cae.

  • Define timeout siempre; sin él tu proceso puede colgarse para siempre.
  • Reintenta solo errores transitorios (5xx y timeouts), nunca los 4xx.
  • Cachea respuestas estables para no llamar dos veces seguidas al externo.

Los reintentos con backoff exponencial son el estándar en integraciones: espera 1s, 2s, 4s antes de desistir.

Explicación

  • El contrato de una API externa (formato, límites, errores) es sagrado: documéntalo en tu código.
  • Los 429 (rate limit) y 5xx son transitorios; 404 y 400 suelen ser bugs de tu integración.
  • Paginación: sigue el mecanismo del propio servicio (page, offset o cursor).
  • Nunca loguees las API keys ni las pongas en el código: ve a variables de entorno.
  • Un API externa caída no debe tumbar tu servicio: aísla el fallo y responde de forma degradada.

Errores comunes

  • Olvidar el timeout y quedarse colgado ante un proveedor lento.
  • Loggear la API key en los registros de error.
  • No comprobar resp.status_code y parsear un cuerpo que llegó con error.
  • Hacer llamadas en bucle sin respetar el rate limit (429).

Buenas prácticas

  • Empieza en sandbox si existe: mismo contrato, cero costes y datos reales.
  • Guarda las credenciales en variables de entorno del servidor.
  • Mide la latencia: si el externo tarda 800ms, tu endpoint también.
  • Escribe un wrapper: si cambia la API externa, solo tocas un archivo.

Ejercicio

  1. Consume una API pública (por ejemplo de clima) y muestra el JSON formateado.
  2. Añade paginación manual a obtener_todo si el servicio no trae has_more.
  3. Escribe la versión con reintentos para un POST que devuelva 429.

Resumen

  • Consumir APIs externas exige respetar su contrato, sus límites y sus errores.
  • Timeout y reintentos con backoff protegen tu backend de los fallos ajenos.
  • Las claves se gestionan en el entorno y nunca en el código.
