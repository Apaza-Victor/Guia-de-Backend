Códigos de Estado HTTP

💻 Básico 12 min Fundamentos de Backend Módulo 3 · HTTP

¿Qué son los códigos de estado?

La respuesta HTTP siempre lleva un código de 3 dígitos que resume cómo terminó la petición: 200 todo bien, 404 no existe, 500 falló el servidor... Son la primera pista que tiene un cliente para saber si su llamada funcionó y por qué.

Se organizan en 5 familias según el primer dígito, y esa agrupación ya te dice de qué va el problema antes de mirar el número.

Las cinco familias

  • 1xx · Informativas: la conexión sigue en curso (100 Continue).
  • 2xx · Éxito: la petición llegó y se procesó bien.
  • 3xx · Redirección: hay que ir a otra URL (301, 302, 304).
  • 4xx · Error del cliente: la petición era inválida o no autorizada; el cliente debe corregir algo.
  • 5xx · Error del servidor: el servidor falló al cumplir una petición válida.

Los más comunes en APIs

200 OKÉxito genérico. GET que devuelve datos, PUT exitoso, etc.
201 CreatedSe creó un recurso (POST). Ideal acompañarlo de la URL del nuevo recurso.
204 No ContentOperación correcta sin body que devolver (borrado exitoso).
301 / 302Redirección permanente / temporal a otra URL.
304 Not ModifiedLa copia en caché sigue siendo válida; reutiliza la local.
400 Bad RequestPetición mal formada o body que no cumple el contrato.
401 UnauthorizedNo estás autenticado: falta token o es inválido.
403 ForbiddenAutenticado pero sin permiso para esa acción o recurso.
404 Not FoundEl recurso no existe (o se oculta para no filtrar datos).
409 ConflictEl estado actual choca con la operación (email ya registrado).
422 Unprocessable EntitySintaxis OK pero validación de negocio falló (campos requeridos).
429 Too Many RequestsSuperaste el límite de peticiones; espera al header Retry-After.
500 Internal Server ErrorError inesperado del servidor. No dejes que el cliente vea el detalle.
502 / 503 / 504El proxy/gateway no obtuvo respuesta (502), servicio no disponible (503) o timeout (504).

Buenas prácticas

  • Usa el código correcto, no el 200 siempre: ayuda a depurar y a clientes automáticos.
  • Envía un body descriptivo junto al error con un identificador del problema.
  • Nunca expongas trazas o SQL en el cuerpo de un 500.
  • Mantén consistencia: define un formato de error común en toda tu API.

Ejercicio

  1. Asignale el status code a cada caso: login con contraseña falsa, recurso borrado, datos inválidos, token caducado.
  2. En tu API, define una respuesta de error uniforme (claves, formato) y aplícala en 3 endpoints.
  3. Consulta las DevTools de una web que conozcas y anota 3 códigos distintos que observes.

Resumen

  • Los status codes resumen el resultado de cada respuesta HTTP.
  • El primer dígito indica la familia: 1xx info, 2xx éxito, 3xx redirección, 4xx error del cliente, 5xx error del servidor.
  • En APIs dominan 200, 201, 400, 401, 403, 404, 409, 422, 429 y 500.
  • Usa códigos precisos y responde errores con un body consistente y sin detalles internos.
