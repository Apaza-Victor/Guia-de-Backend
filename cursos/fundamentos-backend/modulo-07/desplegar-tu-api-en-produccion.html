Poner tu API en producción

⚙️ Intermedio 12 min Fundamentos de Backend Módulo 7 · De cero a producción

Introducción

Tener la API funcionando en local está bien, pero el trabajo termina cuando corre en producción, accesible las 24 horas, con HTTPS y migraciones aplicadas.

El primer despliegue asusta, pero es una lista corta y repetible: preparar el artefacto, copiarlo al servidor, configurar y servir con HTTPS.

Definición

Desplegar es llevar tu código en funcionamiento a un servidor accesible públicamente: preparar el artefacto y sus datos, ejecutarlo con las variables correctas y exponerlo con un servidor web.

Por qué importa. Un despliegue manual y bien documentado genera confianza operativa; hacerlo bien te permite automatizarlo después con CI/CD sin dolor.

Cuándo usarlo. Despliega cuando el proyecto tenga sentido de negocio y esté estable; refina el proceso con cada release: más despliegues pequeños y controlados.

Conceptos clave

  • Artefacto: compilado o imagen del servicio lista para ejecutarse.
  • Entornos: dev, staging y producción; cada uno con sus variables.
  • Migraciones: cambios de esquema aplicados en orden y con control.
  • PM2 o systemd mantienen el proceso vivo y lo reinician si cae.
  • Nginx o similar pone HTTPS y actúa de reverse proxy.

Ejemplo básico

Preparar el servicio para producción en Node: build, migraciones y arranque.

> npm run compile
> node dist/index.js
API de la tienda escuchando en :3000 (produccion)

Ejemplo intermedio

Mantener el proceso vivo con systemd (Linux) o PM2.

Ejemplo real

Flujo real en un VPS: reverse proxy con HTTPS delante de la API y respaldo antes de migrar.

  • Prueba el artefacto en staging antes de tocar producción.
  • Haz copia de seguridad de la base de datos antes de migrar.
  • Mide un endpoint después del deploy para confirmar que responde bien.

Con docker compose este flujo se reduce a subir la imagen y un docker compose up -d; de ahí que la contenerización sea el siguiente paso lógico.

Explicación

  • Despliegue reproducible es el mismo artefacto en staging y producción: solo cambian las variables.
  • Las migraciones se aplican con backup y control; romper datos no se arregla con un git revert.
  • systemd o PM2 garantizan que el proceso vuelva a arrancar si cae.
  • Nginx aporta HTTPS, compresión y tolerancia; hoy HTTPS ya no es opcional.
  • Documenta el runbook: los pasos exactos de cada despliegue.

Errores comunes

  • Desplegar a ciegas sin haberlo probado en staging.
  • Olvidar las variables de entorno de producción y arrancar con defaults.
  • Aplicar migraciones sin backup y romper datos de forma irreversible.
  • Exponer el puerto del servicio sin HTTPS ni reverse proxy.

Buenas prácticas

  • Empieza con un despliegue manual documentado; luego automatízalo.
  • Fija el commit o tag que estás desplegando.
  • Añade un GET /health que compruebe la base de datos para verificar el deploy.
  • Copia de seguridad antes y plan de rollback de las migraciones.

Ejercicio

  1. Crea un /health que compruebe la conexión a la BD y verifícalo con curl al arrancar.
  2. Describe en un runbook los seis pasos del despliegue de tu API.
  3. Adapta el systemd unit de ejemplo a tu servicio y a sus rutas reales.

Resumen

  • Un despliegue reproducible: artefacto, variables, migraciones y proceso vivo.
  • systemd o PM2 mantienen la API encendida y Nginx trae HTTPS.
  • Copia de seguridad antes, healthcheck después y runbook siempre.
