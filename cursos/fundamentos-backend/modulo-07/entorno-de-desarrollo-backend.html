Configurando tu entorno de desarrollo

💻 Básico 10 min Fundamentos de Backend Módulo 7 · De cero a producción

Introducción

Antes de programar el backend necesitas un lugar donde probar: editor, terminal, runtime y una forma de ejecutar tu API localmente.

Un entorno bien montado te ahorra horas: menos fricción para empezar y la misma experiencia en cualquier máquina.

Definición

El entorno de desarrollo es el conjunto de herramientas (editor, terminal, runtime, gestor de dependencias) con el que escribes, ejecutas y depuras tu código de backend en local.

Por qué importa. Una configuración reproducible garantiza que tu código funcione igual en tu portátil, en el de un compañero y en producción, sin sorpresas.

Cuándo usarlo. Configúralo al empezar cada proyecto (versiones declaradas y dependencias fijadas) y arréglalo cuando el resto del equipo no consiga reproducir tu entorno.

Conceptos clave

  • El runtime (Node, Python, PHP) debe quedar fijado a una versión.
  • El gestor de dependencias (npm, pip, composer) genera un lockfile.
  • El editor con terminal integrada y atajos: VS Code es el estándar.
  • El servidor de desarrollo con recarga en caliente acelera las pruebas.
  • .editorconfig y linters unifican el estilo del equipo.

Ejemplo básico

Fijar la versión del runtime y declarar los comandos de arranque.

v20.11.0
added 70 packages in 3s
> servidor de desarrollo escuchando en :3000

Ejemplo intermedio

Declarar la versión del engine y fijar las dependencias con lockfile.

Ejemplo real

En un equipo real se usa .nvmrc, dependencias fijadas y, a menudo, contenedores para que todo el mundo (y el CI) reproduzca el mismo entorno.

  • Versiona el lockfile siempre: garantiza dependencias idénticas.
  • Usa contenedores si tu servicio depende de Redis o de una base de datos local.
  • Define claramente el comando de arranque en la documentación del repo.

El .env no se versiona; en su lugar se sube un .env.example con las claves vacías.

Explicación

  • Un entorno reproducible es el primer paso hacia despliegues predecibles.
  • El lockfile elimina la coordenada depende de la máquina.
  • Declarar engines del runtime avisa antes de que un cambio de versión rompa todo.
  • El servidor con recarga en caliente (watch) acorta el ciclo de pruebas.
  • Los contenedores resuelven el síndrome en mi máquina funciona.

Errores comunes

  • Olvidar subir el lockfile y que cada uno instale versiones distintas.
  • Versionar el .env y exponer credenciales en el repositorio.
  • Ejecutar todo como superusuario en local.
  • Instalar dependencias globales cuando deberían ser del proyecto.

Buenas prácticas

  • Fija versiones de runtime y dependencias desde el primer día.
  • Nunca pongas credenciales reales en archivos del repo.
  • Arranca el servidor con watch para iterar rápido.
  • Documenta: requisitos, instalación y comando de arranque.

Ejercicio

  1. Crea un proyecto nuevo con npm init y añade el script dev con watch.
  2. Escribe un .nvmrc y comprueba qué versión usarías con nvm use.
  3. Añade un paso de CI que instale con npm ci y arranque con npm start.

Resumen

  • Un entorno reproducible fija runtime, dependencias y arranque.
  • El lockfile y las versiones declaradas evitan el en mi máquina funciona.
  • Documenta el mínimo comando para que cualquiera levante el proyecto.
