Arquitectura Cliente-Servidor

💻 Básico 10 min Fundamentos de Backend Módulo 4 · Arquitectura Web

¿Qué es la arquitectura Cliente-Servidor?

La arquitectura Cliente-Servidor divide cualquier sistema en dos roles bien diferenciados:

  • Cliente: quien solicita. Es la parte que interactúa con el usuario o emite peticiones (navegador, app móvil, script, otro servidor).
  • Servidor: quien responde. Espera peticiones, las procesa y devuelve recursos o datos.

Es el modelo base de toda la web: cuando abres https://github.com, tu navegador (cliente) envía un request HTTP y el servidor de GitHub responde con el HTML de la página.

Cómo funciona la comunicación

Una misma petición puede pasar por varios intermediarios (DNS, CDN, balanceadores, proxies) sin que cambie el modelo: siempre hay un lado que pide y otro que entrega.

Características clave

CentralizaciónLos datos y la lógica viven en el servidor; el cliente solo presenta y gestiona la interacción.
EscalabilidadPuedes tener muchos clientes contra pocos servidores, o escalar servidores sin tocar a los clientes.
IndependenciaCliente y servidor evolucionan por separado mientras mantengan el contrato (API) acordado.
Punto únicoEl servidor concentra la responsabilidad: si cae, todos los clientes lo notan.

Variaciones del modelo

No siempre es un navegador contra un servidor. Algunas variantes habituales:

  • Multi-cliente: web + móvil + API pública consumiendo el mismo backend.
  • Servidor a servidor: un microservicio pide datos a otro (también es cliente-servidor).
  • Cliente enriquecido: el frontend hace gran parte del trabajo y la API solo expone datos (SPA).
  • Arquitectura de 3 capas: presentación (cliente) + lógica (backend) + datos (base de datos).

Cuándo usar esta arquitectura

Es la opción natural para cualquier sistema con múltiples usuarios y un punto de verdad central. Los límites aparecen cuando el servidor se convierte en cuello de botella: ahí entran en juego el cache, los reverse proxies y los load balancers que verás en este módulo.

Ejercicio

  1. Dibuja el flujo de una petición contra tu-api.local/users/1 indicando quién es el cliente y quién el servidor.
  2. Añade al dibujo un único intermediario (CDN o proxy) y explica qué hace en la cadena.
  3. Identifica una situación de tu día a día donde un cliente consuma a un servidor "sin querer" (IoT, telemetría, webhooks).

Resumen

  • Cliente-Servidor separa el que pide del que entrega.
  • La web completa se apoya en este modelo con requests y responses HTTP.
  • El servidor es el punto central de datos y lógica.
  • Permite muchos clientes, escalar de forma independiente y evolucionar ambos lados por separado.
  • Sus puntos débiles (cuellos de botella) se resuelven con cache y proxies.
