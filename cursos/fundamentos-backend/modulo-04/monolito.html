Monolito

💻 Básico 8 min Fundamentos de Backend Módulo 4 · Arquitectura Web

¿Qué es un monolito?

Un monolito es una aplicación Backend en la que toda la funcionalidad vive dentro de un solo programa ejecutable: autenticación, catálogo, pagos, notificaciones... todo en un mismo proceso, un mismo código y (habitualmente) una misma base de datos.

Cuando haces un deploy, despliegas una sola pieza. Aunque en el frontend se vea como muchos servicios, detrás hay una única API que lo gestiona todo.

Las partes de un monolito

Internamente sí se puede (y se debe) organizar. Un monolito típico separa sus responsabilidades en módulos:

  • Presentación / API: expone rutas HTTP y traduce peticiones en acciones.
  • Lógica de negocio: las reglas del producto: precios, permisos, validaciones.
  • Acceso a datos: consultas a la base de datos y modelos.
  • Infraestructura: mailing, colas, almacenamiento de archivos.

Cuándo un monolito es buena idea

Durante mucho tiempo el monolito fue la apuesta correcta por defecto:

  • Equipos pequeños: menos piezas que coordinar, onboarding rápido.
  • Fase inicial: el producto aún está aprendiendo qué necesita realmente.
  • Despliegue simple: copias una carpeta o subes una imagen y ya está.
  • Transacciones directas: la lógica y los datos viven juntos, sin red de por medio.

El problema real del monolito no es el tamaño, es el acoplamiento: cuando cada cambio de una parte obliga a re-desplegar todo y a coordinar a todo el equipo, empieza a doler. Esa es la puerta de entrada al resto de arquitecturas que verás en este módulo.

Ventajas y desventajas

VentajasSimplicidad, un solo repositorio, debugging end-to-end fácil, pruebas de integración sencillas, menor latencia interna.
DesventajasEscala todo junto, despliegues grandes y arriesgados, equipo bloqueado por áreas, adopción lenta de tecnologías nuevas.

El monolito modular

Hoy la recomendación práctica es el monolito modular: una sola aplicación, pero con límites claros entre módulos que solo se comunican por sus interfaces públicas. Conservas la simplicidad del monolito y el día que una parte justifique su propio servicio, la puedes extraer sin reescribir el resto.

Ejercicio

  1. Toma la app de un curso anterior (por ejemplo la librería o la API de tareas) y enumera sus módulos en un monolito.
  2. Identifica qué módulos usan otros directamente y busca 1 acoplamiento que podrías resolver con una interfaz.
  3. Responde por escrito: ¿cuándo tendría sentido extraer uno de esos módulos a un servicio aparte?

Resumen

  • Un monolito agrupa toda la funcionalidad en un solo programa.
  • Es la opción correcta para equipos pequeños y productos en fase inicial.
  • El riesgo real es el acoplamiento, no el tamaño.
  • El monolito modular mantiene límites claros dentro de una sola aplicación.
  • La escalabilidad extrema no obliga a empezar con microservicios.
