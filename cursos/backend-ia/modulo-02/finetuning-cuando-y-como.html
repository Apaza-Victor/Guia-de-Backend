Fine-tuning: cuándo y cómo

🧠 Experto 10 min Backend para IA Módulo 2 · Features con IA

Introducción

El fine-tuning entrena una copia de un modelo base sobre tu dataset para que imite tu tono, tu formato o tus reglas. Es la herramienta adecuada para un puñado de problemas muy concretos — y la herramienta equivocada, cara e innecesaria, para la mayoría.

La regla que debe guiarte como backend: si el problema es de conocimiento, usa RAG; si el problema es de comportamiento o formato, considera fine-tuning. Esta lección te da el criterio y el proceso completo.

RAG vs fine-tuning

Pregúntate siempre primero: ¿el problema es «no sabe mis datos» (RAG) o «sabe pero no se comporta como quiero» (fine-tuning)?

  • RAG aporta hechos que cambian (catálogo, precios, política) y no requiere entrenar nada; se actualiza reindexando.
  • Fine-tuning aporta un estilo y un formato estable (siempre responde en JSON, tono de soporte, resúmenes con estructura propia), pero los hechos que aprendió pueden quedar obsoletos y NO sustituye la búsqueda de datos.
  • Combinados: fine-tuneas el tono y el formato, y usas RAG para el contenido. Es el patrón de muchos asistentes corporativos.

Un criterio práctico: si necesitas más de algunos cientos de ejemplos consistentes de «input → respuesta perfecta», el fine-tuning puede valer la pena; con menos, un buen prompt con RAG renderá igual.

El dataset: conversaciones de chat

El formato estándar copia la estructura de mensajes: cada ejemplo es una conversación con roles. Lo que entrenas es la respuesta esperada del asistente dado el historial.

{"messages":[{"role":"system","content":"Asistente de soporte de TiendaX. Responde con el formato: {estado: string, texto: string}"},{"role":"user","content":"¿Dónde está mi pedido 998?"},{"role":"assistant","content":"{\"estado\":\"en_envio\",\"texto\":\"Tu pedido 998 salió hoy de nuestra bodega.\"}"}]}
{"messages":[{"role":"system","content":"Asistente de soporte de TiendaX. Responde con el formato: {estado: string, texto: string}"},{"role":"user","content":"Quiero cancelar mi suscripción"},{"role":"assistant","content":"{\"estado\":\"error\",\"texto\":\"No encontramos una suscripción activa con tu cuenta.\"}"}]}

Cada línea es un ejemplo JSONL. Los ejemplos deben ser consistentes: si la mitad devuelve JSON y la otra texto plano, el modelo ajustado será un promedio mediocre de ambos. La calidad del dataset vale más que su tamaño.

Lanzar un fine-tune vía API

Una vez subido el archivo JSONL, creas el job de entrenamiento. El backend espera, revisa el progreso y, al terminar, recibe un identificador del modelo ajustado que puedes usar de inmediato en tu cliente.

from openai import OpenAI

client = OpenAI()

# 1. Sube el dataset
archivo = client.files.create(
    file=open("dataset_finetune.jsonl", "rb"),
    purpose="fine-tune"
)

# 2. Lanza el entrenamiento
job = client.fine_tuning.jobs.create(
    training_file=archivo.id,
    model="gpt-4o-mini",
    suffix="soporte-tiendax"
)
print("Job:", job.id)  # ftjob_XXXXXXXX

# 3. Consulta hasta que llegue a "succeeded"
estado = client.fine_tuning.jobs.retrieve(job.id)
print(estado.status, estado.fine_tuned_model)
# succeeded ft:gpt-4o-mini:personal:soporte-tiendax:AB12CD

El modelo resultante se referencia como ft:gpt-4o-mini:personal:soporte-tiendax:AB12CD y se usa idéntico a uno base: basta pasar ese nombre en model. Úsalo en tu capa de cliente desde la variable de entorno, no escrita a fuego.

Evaluar antes de promocionar

Nunca promuevas un modelo ajustado solo porque «entrenó bien». Guarda un conjunto de evaluación que el modelo no haya visto y compara tus métricas contra la base sin ajustar:

evaluacion = [
    {"prompt": "¿Dónde está mi pedido?", "esperado": "estado"},
    {"prompt": "¿Puedo cancelar?", "esperado": "error"},
]

def exactitud(predicciones, esperados):
    aciertos = sum(p == e for p, e in zip(predicciones, esperados))
    return aciertos / len(esperados)

# Compara exactitud vs el modelo base con el mismo prompt
print("Exactitud modelo base:", exactitud(predicciones_base, evaluacion))
print("Exactitud modelo ajustado:", exactitud(predicciones_afinado, evaluacion))

Si el ajustado no gana por una diferencia real en tu conjunto de evaluación, no lo promuevas: el costo de un fine-tune (tiempo, entrenamiento e inferencia) debe justificarse con una métrica. Recuerda que el modelo ajustado suele tener precio de entrada y salida más caro que el base.

  2. Convierte uno de tus casos en 3 ejemplos en formato JSONL del dataset de chat.
  3. Define una métrica simple de evaluación (por ejemplo, % de respuestas que parsean como JSON) y explica cómo compararías el modelo base vs el ajustado.

Resumen

  • RAG aporta conocimiento actualizable; el fine-tuning aporta estilo, tono y formato estable.
  • El dataset usa el formato de conversación JSONL y debe ser consistente.
  • El entrenamiento se lanza vía API y entrega un identificador de modelo utilizable directamente.
  • Evalúa siempre contra un conjunto que el modelo no haya visto, comparando con la base.
  • El fine-tuning cuesta más en entrenamiento e inferencia: solo lo adoptas si gana la métrica.
