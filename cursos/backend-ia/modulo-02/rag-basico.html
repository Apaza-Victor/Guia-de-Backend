RAG básico

🧠 Experto 12 min Backend para IA Módulo 2 · Features con IA

Introducción

RAG (Retrieval Augmented Generation) es el patrón para darle al modelo datos que no conoce o que cambian con frecuencia: tus FAQ, tu catálogo, tu documentación interna. En vez de reentrenar el modelo, recuperas los fragmentos relevantes de tu base y se los inyectas en el prompt como contexto.

El pipeline tiene dos fases: indexado (partir documentos, vectorizarlos y guardarlos) y recuperación (vectorizar la pregunta, buscar los fragmentos más parecidos y responder con ellos).

Chunking: partir documentos con sentido

No puedes vectorizar un manual de 200 páginas en un solo vector. Se divide en chunks (fragmentos) que quepan en el contexto y sean autocontenidos. El tamaño depende del caso, pero entre 300 y 800 tokens con un pequeño solape es un punto de partida razonable.

def chunkear(texto, tamano=500, solape=60):
    palabras = texto.split()
    chunks = []
    i = 0
    while i < len(palabras):
        fragmento = " ".join(palabras[i:i + tamano])
        chunks.append(fragmento)
        i += tamano - solape
    return chunks

manual = "Nuestra política de devolución... " * 40  # texto largo de ejemplo
chunks = chunkear(manual)
print(len(chunks), "chunks generados")
# 7 chunks generados

El solape evita que una idea se parta exactamente en la frontera. En la práctica también cortarás por límites naturales (párrafos, secciones de Markdown) en vez de partir por palabras a ciegas.

Guardar vectores con pgvector

Para un índice real, lo más común es una vector database. pgvector convierte tu PostgreSQL en una de ellas con una simple extensión: la columna vector guarda los embeddings y la base encuentra los más cercanos con un operador de distancia.

CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE documentos (
  id       SERIAL PRIMARY KEY,
  chunk    TEXT,
  fuente   TEXT,
  meta     JSONB,
  embedding vector(1536)
);

CREATE INDEX idx_docs_embedding
  ON documentos USING hnsw (embedding vector_cosine_ops);

-- Los 3 chunks más parecidos a $query (distancia coseno)
SELECT chunk,
       1 - (embedding <=> $formatoVector::vector) AS similitud
FROM documentos
ORDER BY embedding <=> $formatoVector::vector
LIMIT 3;

El índice hnsw es de tipo ANN (approximate nearest neighbor): cambia un poquito de exactitud por velocidad, y a partir de miles de documentos es la diferencia entre responder en milisegundos o en segundos.

Indexado: del documento al vector

El job de indexado recorre tus documentos, los parte en chunks, genera un embedding por chunk y hace un INSERT. Se ejecuta cada vez que subes o editas un documento, normalmente como tarea en segundo plano.

from openai import OpenAI
import psycopg

client = OpenAI()

def indexar_documento(texto, fuente):
    chunks = chunkear(texto)
    respuesta = client.embeddings.create(
        model="text-embedding-3-small",
        input=chunks
    )
    with psycopg.connect("dbname=tienda") as conect:
        with conect.cursor() as cur:
            for chunk, dato in zip(chunks, respuesta.data):
                cur.execute(
                    """
                    INSERT INTO documentos (chunk, fuente, embedding)
                    VALUES (%s, %s, %s)
                    """,
                    (chunk, fuente, dato.embedding)
                )
        conect.commit()

El indexado es idempotente por diseño (cada documento tiene su fuente): al reindexar un documento borras sus chunks anteriores e insertas los nuevos, sin tocar los demás.

Recuperación: buscar y responder

Ahora la parte que corre en cada request: vectorizar la pregunta, recuperar los mejores chunks y construir el prompt con ese contexto. El modelo debe responder basándose solo en el contexto, para no inventar datos.

def responder(consulta):
    vector = client.embeddings.create(
        model="text-embedding-3-small",
        input=[consulta]
    ).data[0].embedding

    with psycopg.connect("dbname=tienda") as conect:
        with conect.cursor() as cur:
            cur.execute(
                """
                SELECT chunk FROM documentos
                ORDER BY embedding <=> %s::vector
                LIMIT 3
                """,
                (vector,)
            )
            contexto = [fila[0] for fila in cur.fetchall()]

    mensajes = [
        {"role": "system", "content":
            "Responde basándote EXCLUSIVAMENTE en el contexto entregado. "
            "Si la respuesta no está en el contexto, di que no tienes esa información."},
        {"role": "user", "content":
            f"Contexto:\n\n{'---'.join(contexto)}\n\nPregunta: {consulta}"}
    ]
    respuesta = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=mensajes,
        temperature=0.2
    )
    return respuesta.choices[0].message.content

Ese prompt es la esencia del RAG: primero hechos de tu base, después la orden de no inventar, después la pregunta del usuario. Con un umbral de similitud, una consulta sin contexto no fuerza una respuesta basura.

Ejercicio

  1. Escribe un script que indexe 3 documentos pequeños (por ejemplo, tres FAQs) con pgvector y la función chunkear de esta lección.
  2. Implementa responder(consulta) y pregunta algo que solo pueda responderse con esos documentos.
  3. Haz una pregunta fuera de tema y verifica que el modelo admite no saber, en lugar de alucinar.

Resumen

  • RAG recupera fragmentos de tus datos y se los da al modelo como contexto para responder.
  • El chunking parte los documentos en piezas autocontenidas, con solape para no perder contexto.
  • Los embeddings se guardan en una vector database; pgvector es la integración natural con PostgreSQL.
  • El indexado corre en segundo plano; la recuperación corre en cada request.
  • El prompt del RAG fija la regla clave: responder solo con base en el contexto entregado.
