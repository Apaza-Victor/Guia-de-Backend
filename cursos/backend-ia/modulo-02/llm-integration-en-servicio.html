Integrar LLMs en un servicio

🧠 Experto 10 min Backend para IA Módulo 2 · Features con IA

Introducción

Llamar a un LLM desde una ruta de Express o FastAPI «a pelo» funciona el primer día y explota el segundo: la configuración está dispersa, no hay reintentos, un proveedor caído cuelga tu request y no puedes probar nada sin pagar tokens.

La solución es el mismo patrón de siempre en backend: una capa de cliente dedicada. Todo lo que sabe cómo hablar con el modelo vive en un módulo propio, y el resto de tu aplicación depende de una interfaz sencilla y estable.

Un cliente LLM reutilizable

Encapsula modelo, endpoint y configuración en una clase. Los detalles del proveedor quedan dentro; fuera solo queda un método que recibe mensajes y devuelve texto.

class LlmClient {
  constructor({ apiKey, model = null, baseUrl = 'https://api.openai.com/v1/chat/completions' }) {
    this.apiKey = apiKey;
    this.model = model;
    this.baseUrl = baseUrl;
  }

  async completar(mensajes, { temperature = 0.3, maxTokens = 2048 } = {}) {
    const res = await fetch(this.baseUrl, {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Authorization': `Bearer ${this.apiKey}`
      },
      body: JSON.stringify({
        model: this.model,
        messages: mensajes,
        temperature,
        max_tokens: maxTokens
      })
    });

    if (!res.ok) {
      const detalle = await res.text();
      throw Object.assign(new Error(`LLM ${res.status}: ${detalle}`), { status: res.status });
    }

    const data = await res.json();
    return data.choices[0].message.content;
  }
}

export const llm = new LlmClient({
  apiKey: process.env.OPENAI_API_KEY,
  model: process.env.LLM_MODEL || 'gpt-4o-mini'
});

Fíjate en el model: se lee de entorno con un valor por defecto. Ese único cambio te permite usar el mismo código contra distintos modelos o versiones sin tocar nada más.

Retries con backoff y jitter

El proveedor de IA es la parte menos confiable de tu sistema: experimenta caídas y rate limits propios. La capa de cliente debe reintentar de forma segura para evitar que un fallo temporal rompa tu API.

import asyncio, random

backoff = {1: 1, 2: 2, 3: 4}  # segundos por intento

async def completar_con_reintentos(fn, intentos_restantes=3):
    try:
        return await fn()
    except _EsReintentable as e:
        if intentos_restantes <= 1:
            raise
        espera = backoff.get(intentos_restantes, 4) * (1 + random.random() * 0.5)
        await asyncio.sleep(espera)
        return await completar_con_reintentos(fn, intentos_restantes - 1)

class _EsReintentable(Exception):
    pass

El jitter (multiplicar la espera por un valor aleatorio) evita el efecto avalancha: cuando el proveedor se recupera, todos los reintentos no llegan a la vez. Solo reintentas errores transitorios — 429, 5xx, timeout de red — nunca 400 ni 401.

Timeouts: la IA no puede colgarte

Una llamada al modelo puede tardar decenas de segundos. Tu API no puede esperar indefinidamente: define un límite y degrada con elegancia cuando se supera.

async function completarConTimeout(promesa, ms) {
  const controller = new AbortController();
  const temporizador = setTimeout(() => controller.abort(), ms);

  try {
    const res = await fetch(this.baseUrl, {
      method: 'POST',
      headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${this.apiKey}` },
      body: JSON.stringify(payload),
      signal: controller.signal
    });
    return await res.json();
  } finally {
    clearTimeout(temporizador);
  }
}

try {
  const data = await completarConTimeout(payload, 30_000);
} catch (err) {
  if (err.name === 'AbortError') {
    return { ok: false, error: 'El modelo tardó demasiado; reintenta o usa un modelo menor.' };
  }
  throw err;
}

El timeout no es un lujo: es la diferencia entre un pico de tráfico y un outage. Procesos más lentos pueden responder 202 con una cola (lo cubres con workers), pero una request síncrona debe tener cota dura.

Probar sin gastar tokens

Una capa de cliente bien aislada se prueba con mocks del fetch o del HTTP, sin llamar jamás a la API real en tus tests:

# Ejecuta los tests apuntando a un mock local
export LLM_BASE_URL="http://localhost:8081/mock-llm"
node --test test/llm-client.test.js

# El mock responde de forma determinista y sin coste:
# POST /mock-llm -> {"choices":[{"message":{"content":"hola desde el mock"}}]}

Prueba al menos: respuesta feliz, 429 (verifica un reintento), 500 (verifica backoff) y timeout (verifica el error controlado). Con esto tu feature de IA es tan testeable como cualquier otra integración.

Ejercicio

  1. Crea una clase LlmClient con método completar() que lea key, modelo y endpoint de variables de entorno.
  2. Añade reintentos con backoff + jitter para 429 y 5xx, y un timeout con AbortController.
  3. Escribe un test con un mock de fetch que devuelva 429 dos veces y éxito a la tercera, y verifica que el cliente lo resuelve sin fallar.

Resumen

  • La integración del LLM vive en un cliente dedicado, no en las rutas de tu API.
  • El modelo se configura por entorno para poder cambiar de versión sin tocar código.
  • Reintenta con backoff exponencial y jitter solo ante errores transitorios.
  • Fija timeouts: una llamada lenta debe degradar, no congelar el servicio.
  • Aísla el cliente para poder probar con mocks sin gastar tokens.
