APIs de completions y chat

🧠 Experto 12 min Backend para IA Módulo 5 · IA generativa y LLMs

Introducción

Todas las APIs de modelos hablan un idioma parecido: envías una lista de mensajes con roles y recibes una completion. Dominar ese contrato es la base de cualquier integración.

En el backend, además del JSON, debes gestionar timeouts, retries, límites de tokens y errores de rate limit con el mismo rigor que con cualquier API externa.

Definición

La API de chat completions recibe mensajes con roles system, user y assistant y devuelve un mensaje generado junto a metadatos de uso de tokens.

Por qué importa. Conocer el contrato exacto evita bugs silenciosos: modelos mal elegidos, contextos desbordados y costes descontrolados.

Cuándo usarlo. Úsala para casi todo lo conversacional y de generación. Para salidas estrictamente estructuradas prefiere response models, que es esta misma API.

Conceptos clave

  • Mensajes: lista ordenada de roles y contenidos.
  • system: instrucciones que fijan la conducta del modelo.
  • user y assistant: turnos reales de la conversación.
  • max_tokens: tope de salida, no de entrada.
  • Rate limits: cuota por minuto que debes respetar y reintentar.

Ejemplo real

Un servicio en producción no tuesta los credenciales y trata los errores de la API de forma explícita.

  • Carga la API key desde el entorno, nunca en el código.
  • Maneja 429 y 5xx con backoff y una cola de reintentos.
  • Trata la respuesta como no fiable: valida antes de usar.

Un fallback a otro proveedor o un mensaje de error templado es mejor que un 500 de tu servicio.

Explicación

  • El sistema es la única probada forma de fijar reglas persistentes entre llamadas.
  • max_tokens limita la salida y por tanto tu coste por request.
  • Los retries deben ser idempotentes: si el pedido ya se creó, no lo dupliques.
  • Los tokens de entrada y salida se facturan distinto según el modelo.
  • Con timeout corto y retries limitados tu endpoint no se hunde ante una API lenta.

Errores comunes

  • Poner la API key en el código o en el log.
  • Reintentar a ciegas sin backoff: amplifica el problema del proveedor.
  • Olvidar max_tokens y recibir salidas interminables y caras.

Buenas prácticas

  • Empieza con un modelo pequeño y sube solo si la calidad lo exige.
  • Centraliza la llamada en una función con timeout y retries.
  • Registra modelo, tokens y duración: es tu factura y tu pista de debug.

Ejercicio

  1. Haz una llamada y comprueba la estructura de respuesta.usage.
  2. Reintroduce un 429 simulado y observa el backoff.
  3. Implementa una función hablar() con historial limitado a veinte mensajes.

Resumen

  • El contrato de chat completions son mensajes con roles system, user y assistant.
  • Timeout, retries con backoff y API keys desde el entorno son obligatorios.
  • max_tokens y el monitoreo del uso controlan coste y calidad.
