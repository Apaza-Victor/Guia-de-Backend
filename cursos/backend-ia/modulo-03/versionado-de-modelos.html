Versionado de modelos

🧠 Experto 10 min Backend para IA Módulo 3 · Producción de IA

Introducción

Tu feature de IA depende de dos versiones: la de tu código y la del modelo que responde. La segunda es propiedad del proveedor y puede cambiar sin aviso: un «gpt-4o-mini» hoy no es el mismo dentro de tres meses. Versionar el modelo es tratarlo como una dependencia más, con versión fija, pruebas y plan de rollback.

Model registry

Un model registry centraliza qué versión está aprobada, qué versión se usa y qué versiones están obsoletas. Sirve tanto para modelos externos (pines de nombres y fechas) como para modelos propios (artefactos guardados). Tu código nunca escribe el nombre del modelo: lo consulta.

// config de modelos versionados por entorno
const REGISTRO = {
  produccion: {
    clasificar_ticket: { nombre: 'gpt-4o-mini',   fecha: '2025-08-01', estado: 'activo' },
    resumir:           { nombre: 'gpt-4o',        fecha: '2025-08-01', estado: 'activo' },
    analizar_sentimiento: { nombre: 'claude-3-5-sonnet', fecha: '2025-09-15', estado: 'bajo_revision' }
  },
  staging: {
    clasificar_ticket: { nombre: 'gpt-4o-mini',   fecha: '2025-08-01', estado: 'activo' },
    analizar_sentimiento: { nombre: 'claude-3-5-sonnet', fecha: '2025-09-15', estado: 'activo' }
  }
};

function modeloDe(env, feature) {
  return REGISTRO[env][feature].nombre;
}

// en la llamada real, el modelo viene del registry, no del código duro
const modelo = modeloDe(process.env.NODE_ENV, 'clasificar_ticket');
const respuesta = await llm.completar(mensajes, { modelo });

Como un package.json, el registry vive en el repo, se revisa en PR y habilita un commit trivial como «update modelo a 2025-09-15» que el CI evalúa contra tu eval set antes de tocar producción.

Fijar la versión del proveedor

Cuando el proveedor te deja elegir (por timestamp o por etiqueta de despliegue), fija la versión explícita en vez de la etiqueta mutable. Así una nueva versión no cambia el comportamiento de tu producción sin que tú decidas migrar.

import Anthropic from '@anthropic-ai/sdk';

const anthropic = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });

// Mutable: cambia silenciosamente cuando Anthropic lo actualiza
// const modelo = "claude-3-5-sonnet-20240909";

// Pin por timestamp: produccion se comporta igual hasta que decidas migrar
const modeloFijado = 'claude-3-5-sonnet-20240909';

const respuesta = await anthropic.messages.create({
  model: modeloFijado,
  max_tokens: 800,
  messages: [
    { role: 'user', content: req.body.pregunta }
  ]
});

Define una política de caducidad: por ejemplo, «migrar dentro de 30 días de publicado el nuevo pin». La migración es un PR que cambia el registry y corre el eval set completo, igual que un bump de versión de librería.

A/B testing y canary

Antes de migrar un modelo para todos, enruta un subconjunto de tráfico real al nuevo pin y compara métricas del eval set y de producción. Primero el 5%, luego sube si no hay regresión.

const CANARY = {
  activo: false,
  pinNuevo: 'gpt-4o-2025-08-16',
  pinActual: 'gpt-4o-2025-04-01',
  porcentaje: 0.05               // 5% del tráfico
};

function modeloPara(req) {
  if (CANARY.activo && Math.random() < CANARY.porcentaje) {
    return CANARY.pinNuevo;      // grupo de tratamiento
  }
  return CANARY.pinActual;       // grupo de control
}

// Por cada respuesta, guarda qué pin respondió y sus métricas
const pin = modeloPara(req);
const data = await llm.completar(mensajes, { modelo: pin });
await registrarExperimento({
  pin,
  ok:      validar(data.contenido),
  latencia: data.latencia_ms,
  fecha:   new Date().toISOString(),
});

Los flags de canary se gobiernan por configuración (tu proveedor de feature flags), no por redeploys. El log de experimento que guardamos aquí es el que alimenta el panel de monitoreo de la lección anterior.

Rollback sin tocar código

Si el canary falla, vuelves al pin anterior con un cambio de configuración: un flag que reenvía al pin base. Ese debe ser el procedimiento automático de tu equipo, medido en minutos y probado en staging periódicamente (los rollbacks que no se ensayan no funcionan cuando importa).

# El CI del registry valida cada PR: formato, pin existente y eval set
# - [ ] Evaluar el clip tipo a cada pin del canary
# - [ ] Subir el porcentaje de canary siguiendo la "escalera": 5% -> 25% -> 100%
# - [ ] Si otra métrica empeora, volver a pinActual con un solo comando:
#   feature-flag set modelo.produccion.gpt4o.canary --value off

# El rollback es config, no nueva emisión de binario:
#   curl -X POST https://flags/api/v1/flags/migracion-gpt4o \
#     -d '{"enabled": false}'

Regla final: código y modelo se lanzan por separado. Tu código debe funcionar con el pin anterior y con el nuevo, porque el rollout del modelo y el del software no están acoplados en el tiempo.

Ejercicio

  1. Crea un registry en JSON con 3 features y fija cada modelo con su pin completo y su estado.
  2. Simula un canary al 10% con el nuevo pin y registra pin, ok y latencia por llamada.
  3. Escribe el comando de rollback que apaga el canary, y confirma que la app vuelve al pin base sin recomplar.

Resumen

  • El model registry centraliza versión, estado y uso de cada modelo; el código lo consulta, no lo fija.
  • Pinea la versión del proveedor, nunca la etiqueta mutable, para que nada cambie en silencio.
  • A/B y canary prueban el pin nuevo en tráfico real y crecen en una escalera controlada.
  • El rollback es un cambio de configuración, no un redeploy: rápido y ensayado.
  • Modelo y código se versionan y se lanzan por separado.
