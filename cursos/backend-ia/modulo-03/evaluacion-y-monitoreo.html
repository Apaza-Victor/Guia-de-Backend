Evaluación y monitoreo

🧠 Experto 11 min Backend para IA Módulo 3 · Producción de IA

Introducción

Un LLM puede parecer excelente en las demos y degradarse en producción: cambias el prompt, el proveedor despliega una versión nueva del modelo y nadie se entera. La evaluación y el monitoreo son las dos caras del control de calidad de una feature de IA.

La evaluación responde «¿es buena hoy?» con un dataset propio. El monitoreo responde «¿sigue siendo buena ahora?» con datos de cada llamada real.

Construir un eval set propio

No evalúes con el dataset genérico del proveedor: construye tu propio conjunto con casos reales de tu dominio. Veinte casos bien escogidos de tu servicio (reembolsos, envíos, etc.) valen más que miles de preguntas de ejemplo. Guarda cada par caso → salida esperada en código, para que forme parte de tu CI.

CASOS_PRUEBA = [
    {"input": "Reembolso del vuelo retrasado", "esperado": "reembolso",   "contexto": "viajes"},
    {"input": "Cambiar la fecha de mi reserva", "esperado": "modificacion", "contexto": "viajes"},
    {"input": "Mi pedido no ha llegado",        "esperado": "envio",       "contexto": "ecommerce"},
]

def evaluar_modelo(modelo, casos):
    aciertos = 0
    for caso in casos:
        respuesta = modelo(caso["input"], caso["contexto"])
        aciertos += 1 if respuesta["clase"] == caso["esperado"] else 0
    return aciertos / len(casos)

acc = evaluar_modelo(mi_modelo, CASOS_PRUEBA)
print(f"Exactitud en el eval set: {acc:.1%}")

El eval set crece con cada incidente: si un caso real salió mal, lo agregas al conjunto para que el siguiente cambio de prompt deba arreglarlo, no romperlo.

Métricas clave de calidad

Cuando tu modelo predice una etiqueta (categoría, sentimiento, intención), las métricas estándar se computan sobre un tensor de predicción y uno de referencia. Entre las clásicas: la exactitud (cuántas respuestas coinciden) y la distancia Hamming (en cuántos bites difieren las predicciones del objetivo).

import torch

def calcular_metricas(modelo, X_test, Y_test):
    y_pred = modelo(X_test)  # (n, n_clases), valores en [0, 1]

    def hamming(target, pred):
        y1, _ = target.min(dim=1)   # límite inferior del objetivo
        y2, _ = target.max(dim=1)   # límite superior del objetivo
        repr_ = (y1 - 0.5).abs() + (y2 - 0.5).abs()
        num = ((y2 - y1) - repr_) / 2
        denom = ((y2 - y1) + repr_) / 2
        return num.sum() / denom.sum()

    metricas = {
        "exactitud": (y_pred.round() == Y_test).float().mean().item(),
        "hamming":   hamming(Y_test, y_pred).item(),
    }
    return metricas

metricas = calcular_metricas(modelo, X_test, Y_test)
print(metricas)
# {"exactitud": 0.9, "hamming": 0.05}

Deja tu umbral de aprobación fijado por contrato (por ejemplo «exactitud > 0.85» en CI): cualquier cambio de prompt o de modelo que baje la métrica debe romper el despliegue, no sorprenderte en producción.

Observabilidad de cada llamada

En producción, un feature flag no te dice qué tan bien respondió el modelo. Registra por llamada: el prompt resumido (nunca PII en claro), los tokens reales, la latencia y si el resultado pasó la validación. Con esos logs puedes graficar tasa de respuestas válidas, costo por feature y regresiones tras cada cambio.

import json, time

def escribir_log_llm(registro):
    ruta = f"logs/llm/{registro['fecha'][:10]}.jsonl"
    with open(ruta, "a", encoding="utf-8") as f:
        f.write(json.dumps(registro, ensure_ascii=False) + "\\n")

t_inicio = time.time()
data = llama.chat(mensajes, max_tokens=300)
latencia = time.time() - t_inicio

escribir_log_llm({
    "fecha":       time.strftime("%Y-%m-%dT%H:%M:%S"),
    "feature":     "clasificar_ticket",
    "modelo":      "gpt-4o-mini",
    "tokens_entrada": data.usage.prompt_tokens,
    "tokens_salida":  data.usage.completion_tokens,
    "latencia_ms": round(latencia * 1000),
    "ok":          status == 200,
})

Con esa base en JSONL (y un índice en tu proveedor de logs) construyes los tableros del módulo anterior: costo diario vs presupuesto, latencia p95 y el % de respuestas que superan la validación. Monitorear no es opcional: es la única forma de saber cuándo el proveedor cambia el comportamiento bajo tus pies.

Ejercicio

  1. Escribe un eval set de 10 casos reales de tu feature con su clase esperada y calcula la exactitud de tu modelo actual.
  2. Añade un caso real que falló (regresión) y confirma que la exactitud baja; eso es tu umbral mínimo en CI.
  3. Registra cada llamada en JSONL con tokens y latencia, y calcula el costo total del día con los precios de la lección de costos.

Resumen

  • El eval set propio (casos reales + salida esperada) es tu contrato de calidad ejecutable en CI.
  • Exactitud y Hamming miden cuánto se apartan las predicciones del objetivo; fija umbrales que rompan el despliegue.
  • La observabilidad registra prompt, tokens, latencia y validez por llamada.
  • Los logs estructurados alimentan los tableros de costo y las alertas de regresión.
  • Si cambias prompt o modelo, re-ejecuta el eval set completo: es tu red de seguridad.
