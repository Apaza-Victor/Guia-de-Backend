Arquitecturas de IA en backend

🧠 Experto 11 min Backend para IA Módulo 3 · Producción de IA

Introducción

Con las piezas de los tres módulos podemos diseñar sistemas completos. Esta lección arma tres arquitecturas típicas de una empresa real: el chatbot con historial, el asistente con agentes y el pipeline RAG en producción. Ninguna es «el prompt del futuro»: todas son backends normales con una dependencia de red con memoria.

Chatbot con historial persistido

El chatbot clásico mezcla memoria del usuario (mensajes anteriores) con contexto de negocio. El backend guarda el historial en Redis por sesión, arma los mensajes con el contexto y aplica límites de tokens de la lección de costos en cada request.

import { createClient } from 'redis';
import crypto from 'node:crypto';

const redis = createClient();
await redis.connect();

const MAX_HISTORIA = 10; // últimos 10 turnos, recorte de ventana

async function obtenerMensajes(sessionId) {
  const clave = `chat:${sessionId}`;
  const lista = await redis.lRange(clave, -MAX_HISTORIA, -1);
  const historial = lista.map((m) => JSON.parse(m));

  return [
    { role: 'system', content: 'Eres soporte de la plataforma.' },
    ...historial,
  ];
}

export async function chatHandler(req, res) {
  const sessionId = req.body.sessionId ?? crypto.randomUUID();
  const mensajes = await obtenerMensajes(sessionId);
  mensajes.push({ role: 'user', content: req.body.mensaje });

  const data = await llm.completar(mensajes, { modelo });

  await redis.rPush(`chat:${sessionId}`,
    JSON.stringify({ role: 'user', content: req.body.mensaje }),
    JSON.stringify({ role: 'assistant', content: data.contenido })
  );
  await redis.expire(`chat:${sessionId}`, 30 * 86400); // inactividad

  res.json({ respuesta: data.contenido, sessionId });
}

Detalles de producción: recorta la ventana de tokens antes de enviar, nunca dejes crecer el historial sin límite, y usa el mismo sessionId que el cliente para mantener la conversación viva entre requests.

Asistente con agentes

Cuando el asistente necesita actuar (consultar la base, llamar una API interna), entra la arquitectura de agentes del módulo 2: el modelo produce tool_calls, tu backend las ejecuta y devuelve los resultados como contexto. El bucle se repite hasta que el modelo responde sin herramientas.

const HERRAMIENTAS = {
  consultar_saldo: { fn: consultarSaldo, descripcion: 'saldos de cuenta' },
  crear_recibo:    { fn: crearRecibo,    descripcion: 'genera un comprobante' },
};

async function resolverAsistente(mensajes) {
  for (let turno = 0; turno < 5; turno++) {
    const data = await llm.completar(mensajes, {
      tools: Object.keys(HERRAMIENTAS),
    });

    if (!data.tool_calls.length) return data.contenido;

    for (const llamada of data.tool_calls) {
      const resultado = await HERRAMIENTAS[llamada.nombre].fn(llamada.args);
      mensajes.push({
        role: 'tool',
        tool_call_id: llamada.id,
        content: JSON.stringify(resultado),
      });
    }
  }
  throw new Error('Demasiados turnos de herramientas');
}

Regla de oro repetida: nunca ejecutes una tool_call que no esperabas (validación de guardrails del módulo 3) y registra cada paso para poder auditar por qué el asistente actuó. El corte de turnos evita los bucles infinitos que queman tokens.

Pipeline RAG en producción

El RAG del módulo 2 en producción se vuelve asíncrono: el indexado corre por trabajos (colas), no en el request. El request solo lee del índice y reúne contexto. La separación evita que un usuario pague por procesos de ingestión y mantiene la búsqueda rápida.

# worker/ingesta.py: corre en una cola, no en el request
import pickle
from redis import Redis

redis = Redis(decode_responses=False)

def indexar_documento(ruta, embedding_fn):
    chunks = dividir_texto(open(ruta, encoding="utf-8").read())
    vectors = [pickle.dumps(embedding_fn(c)) for c in chunks]
    redis.delete(f"rag:{ruta}")
    for c, v in zip(chunks, vectors):
        redis.rPush(f"rag:{ruta}", v)       # búsqueda por similitud simple
    redis.expire(f"rag:{ruta}", 7 * 86400)  # cache de contexto semanal
    redis.publish("ingesta:fin", ruta)

# app/main.py: el request solo consulta el índice
def responder_con_rag(ruta, pregunta, embedding_fn, llm):
    chunks = [pickle.loads(v) for v in redis.lRange(f"rag:{ruta}", 0, -1)]
    contexto = top_similares(chunks, embedding_fn(pregunta), k=4)
    prompt = ["Busca en este contexto y responde.", f"{contexto}", pregunta]
    return llm(prompt)

Los trabajos de ingesta se disparan cuando la fuente cambia (webhook, cron), y el request nunca toca el documento original: siempre responde sobre una copia vectorizada en caché. Así, una fuente caída no rompe el chatbot que usa su último índice.

Despliegue, escalado y cierre

Las tres arquitecturas se despliegan como cualquier servicio: contenedor, cola, Redis y un proveedor LLM externo con su pin. El escalado es horizontal (todas las piezas son stateless salvo Redis, que escala aparte), y los guardrails, costos, monitoreo y versionado del módulo 3 son los requisitos, no el añadido.

# docker-compose de un servicio de IA típico
services:
  api:
    build: .
    ports: ["8080:8080"]
    env:
      OPENAI_API_KEY: ${OPENAI_API_KEY}     # nunca en el repo
      REDIS_URL: redis://redis:6379
      MODELO_REGISTRO: prod
    depends_on: [redis]
  redis:
    image: redis:7-bookworm
    volumes: ["redis-data:/data"]
  worker_ingesta:
    build: .
    command: python -m worker.ingesta
    env:
      REDIS_URL: redis://redis:6379
    depends_on: [redis]

# 3 réplicas del API detrás de un load balancer; Redis aparte.

Con esto cierras el curso: en cada lección trabajaste una «skill» para un sistema como este. La IA en el backend no es magia: es un pipeline con límites, mediciones, seguridad y versionado, controlado por código como cualquier otra feature.

Ejercicio

  1. Levanta el chatbot con historial en Redis y prueba 3 turnos seguidos manteniendo el sessionId.
  2. Convierte tu feature en asistente con agentes (una tool_call propia) con corte máximo de 5 turnos.
  3. Mueve la ingesta de tu RAG a un worker separado que los requests no bloqueen, y despliega el docker-compose localmente.

Resumen

  • El chatbot persiste el historial en Redis y recorta la ventana de tokens en cada request.
  • El asistente con agentes itera tool_calls con límite de turnos; nunca ejecuta llamadas inesperadas.
  • El RAG en producción separa la ingesta (cola/worker) de la lectura (request rápido).
  • Todo el sistema se despliega como contenedores stateless con Redis aparte; los secretos nunca viajan en el repo.
  • Los guardrails, costos, monitoreo y versionado son parte de la arquitectura, no un capricho.
