✅ Checklists

Pasa la lista antes de cada despliegue, de cada pull request o de cada reunión de revisión de código. No confíes en tu memoria: confía en la lista.

Checklist de despliegue seguro

  • ☐ HTTPS activo con certificado válido en todos los dominios (TLS 1.2 mínimo).
  • ☐ Cabeceras de seguridad configuradas: HSTS, X-Content-Type-Options, CSP básica.
  • ☐ Contraseñas guardadas con hash salado (bcrypt o argon2), nunca en texto plano.
  • ☐ Secreto de la app, claves de API y credenciales fuera del repositorio (.env ignorado por Git).
  • ☐ Puertos del sistema cerrados salvo los necesarios; SSH solo con llaves y no por contraseña.
  • ☐ Backup automático de la base de datos probado con una restauración real.
  • ☐ Logs sin datos sensibles: sin contraseñas, tokens ni información personal sin necesidad.
  • ☐ Límites de peticiones y rate limiting activos en los endpoints públicos.
  • ☐ Sistema operativo y dependencias actualizados (parches de seguridad).
  • ☐ Monitoreo y alertas configurados para CPU, memoria, disco y errores 5xx.
  • ☐ Plan de rollback conocido: restaurar la versión anterior si algo falla.

Checklist de código limpio

  • ☐ Nombres de variables, funciones y clases explican su propósito sin necesidad de comentario.
  • ☐ Funciones pequeñas que hacen una sola cosa, con un nombre que lo diga.
  • ☐ Sin código duplicado: extrae lo repetido a una función o constante compartida.
  • ☐ Sin lógica muerta: elimina código sin usar, comentarios obvios y desarrollos abandonados.
  • ☐ Manejo de errores explícito: petición con try/catch o manejo de promesas que no se traga fallos en silencio.
  • ☐ Sin secretos ni datos de entorno hardcodeados en el código.
  • ☐ Las pruebas cubren los casos importantes y pasan en local antes del commit.
  • ☐ Los nombres y la estructura se mantienen consistentes con el resto de la base de código.

Checklist de revisión de PR

  • ☐ Entiendo el contexto: la descripción explica por qué existe este cambio y qué problema resuelve.
  • ☐ Las pruebas automáticas pasan en CI y hay test razonable para el cambio.
  • ☐ No hay secretos, credenciales ni archivos locales en el commit (.env, logs, binarios).
  • ☐ El PR no mezcla cambios no relacionados: cada PR resuelve una sola cosa.
  • ☐ Las migraciones de base de datos son seguras y con rollback planificado.
  • ☐ El manejo de errores cubre los caminos de fallo, no solo el camino feliz.
  • ☐ Rendimiento sensato: sin consultas N+1 evidentes ni bucles innecesarios.
  • ☐ La documentación necesaria se actualizó (README, API, variables de entorno).
  • ☐ Lo verifiqué en local o con los pasos de reproducción indicados.
  • ☐ Dejo comentarios concretos y respetuosos; aprobo cuando el cambio está listo.

Guía de despliegue seguro

Resumen: desplegar una aplicación en internet es fácil; desplegarla segura es otra cosa. Esta guía cubre lo mínimo antes de abrir puertas al mundo: terminar TLS con un proxy inverso, endurecer el servidor, configurar el firewall y proteger el acceso remoto.

Completa la guía con la checklist de despliegue seguro de esta misma página: hazla tuya antes de cada salida a producción.

Guía rápida de Node.js para backend

Resumen: el punto de partida para construir APIs con Node: crear el proyecto, levantar un servidor HTTP, leer las variables de entorno y definir las primeras rutas con Express, el framework más extendido.

Después de este primer servidor, sigue el flujo completo: rutas, controladores, servicios y base de datos. Tienes todos los pasos en el curso de Node.js de Backend Academy.

Cheatsheet de SQL

Resumen: las consultas más frecuentes en una hoja: leer, filtrar, ordenar, agrupar, combinar tablas y modificar datos. La referencia que usarás en cada proyecto que toque una base relacional.

¿Necesitas más profundidad? El curso de SQL de Backend Academy te lleva de las primeras consultas hasta la optimización con índices.
